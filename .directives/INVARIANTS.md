# Shared System Invariants (The "Laws of Physics")

This document defines the system physics — rules about how sessions, phases, tags, delegation, and the engine work. Agent behavior rules are in AGENTS.md. Code standards are in CONTRIBUTING.md.

## 1. Protocol Physics

*   **¶INV_PROTOCOL_IS_TASK**: When a skill protocol is active, the protocol defines the task.
    *   **Rule**: The user's request is an input parameter to the protocol, not a replacement for it. The agent executes the protocol; the user's request shapes what the protocol produces. "Implement X" means "execute the implementation protocol with X as the input" — not "write code for X and skip the protocol."
    *   **If you want to skip**: You don't skip. You fire `§CMD_REFUSE_OFF_COURSE` and let the user decide. The user is the only one who can authorize a deviation. You never self-authorize.
    *   **Prohibited justifications** (these are never valid reasons to skip a step):
        *   "This task is too simple for the full protocol."
        *   "The user asked for X, not for Y" (where Y is a protocol step).
        *   "I'll be more efficient by skipping this."
        *   "This step doesn't apply to this task."
    *   **Identity**: A disciplined operator follows the protocol. Skipping steps is not efficiency — it's broken output. The protocol exists because the steps matter, even when you think they don't. Your judgment about task complexity is unreliable. The protocol's judgment is authoritative.
    *   **Consequence**: A session where protocol steps were silently skipped is an invalid session. The artifacts are incomplete, the audit trail is broken, and the work may need to be redone.
    *   **Reason**: Without this framing, the model treats the protocol as overhead wrapping the "real" task and optimizes it away. The protocol IS the task.

## 2. Session & Phase Physics

*   **¶INV_NEW_SESSION_BOUNDARY**: When a user requests a new session, create one. Do not continue the old one.
    *   **Rule**: When the user explicitly requests a new session — via next-skill selection (`§CMD_CLOSE_SESSION`), `/session dehydrate restart`, or saying "new session" / "next session" — the agent MUST create a fresh session directory via `§CMD_MAINTAIN_SESSION_DIR`. It MUST NOT reactivate, continue, or override errors in the previous session.
    *   **Prohibited**: Seeing `engine session activate` reject because the session is completed/active and deciding to "override" or "continue anyway." The rejection IS the expected outcome — the old session is done.
    *   **Redirection**: If `engine session activate` rejects, create a new session directory with `§CMD_MAINTAIN_SESSION_DIR`. The user's intent is forward motion, not recovery.
    *   **Reason**: Agents systematically conflate "next skill" with "continue this session" because their helpfulness bias prioritizes continuity. The user's new-session request is a boundary signal, not a suggestion.

*   **¶INV_PHASE_ENFORCEMENT**: Phase transitions are mechanically enforced via `engine session phase`.
    *   **Rule**: When a session has a `phases` array (declared at activation), `engine session phase` enforces sequential progression. Non-sequential transitions (skip forward or go backward) require `--user-approved "Reason: [why, citing user's response]"`.
    *   **Proof-gated transitions (FROM validation)**: The current phase (being left) may declare a `proof` field (array of field names). When present, the agent MUST pipe proof as JSON via STDIN when transitioning away from it. Missing or unfilled fields reject the transition. Proof is always parsed and stored in `phaseHistory` as structured objects when provided, regardless of whether the current phase declares proof fields. Semantically: proof on a phase describes what must be accomplished IN that phase before leaving it.
    *   **FROM proof applies even on skip**: When skipping Phase 1→3 with `--user-approved`, FROM validation checks Phase 1's proof (the phase being LEFT). The agent must prove Phase 1's work was done before leaving it. `--user-approved` bypasses sequential enforcement (allows non-sequential jumps) but does NOT bypass proof validation — these are independent checks. If Phase 1 has proof fields but no work was done, the skip fails because proof cannot be provided.
    *   **Letter suffixes**: Sub-phase labels may include a single uppercase letter suffix (e.g., `"3.1A: Agent Handoff"`). The letter is stripped for enforcement (enforces as `3.1`) but preserved in `phaseHistory` for audit trail. Distinguishes alternative branches.
    *   **Context overflow recovery**: `/session continue` uses `engine session continue` to resume the heartbeat without touching phase state. No phase transition needed — the saved phase in `.state.json` is the source of truth.
    *   **Sub-phases**: Phases with the same major number and a higher minor number (e.g., 4.1 after 4.0) are auto-appended without pre-declaration.
    *   **Sub-phase skippability**: Sub-phases are optional — they represent alternative paths, not mandatory steps. `N.0→(N+1).0` is always allowed even when `N.1` is declared (skip over optional sub-phase). `N.M→(N+1).0` is always allowed (exit sub-phase to next major). Neither requires `--user-approved`.
    *   **Backward compat**: Sessions without a `phases` array have no enforcement — any transition is allowed. Phases without `proof` fields emit a stderr warning if sibling phases declare proof (nudge, not block).
    *   **Reason**: Agents systematically skip phases they judge as "unnecessary." Mechanical enforcement removes this judgment call — the user decides, not the agent.

*   **¶INV_USER_APPROVED_REQUIRES_TOOL**: The `--user-approved` flag on `engine session phase` requires a reason obtained via `AskUserQuestion`.
    *   **Rule**: `AskUserQuestion` is the ONLY valid mechanism to obtain a `--user-approved` reason string. The reason MUST quote the user's answer from the `AskUserQuestion` tool response. Self-authored reasons are invalid regardless of how reasonable they seem.
    *   **Valid example**: `--user-approved "User chose 'Go back to 2: Research Loop' via AskUserQuestion"`
    *   **Valid example**: `--user-approved "User said 'skip calibration, findings are clear' via AskUserQuestion"`
    *   **Invalid example**: `--user-approved "Phase doesn't apply to this task"` (self-authored, no tool call)
    *   **Invalid example**: `--user-approved "Skipping calibration per user request"` (paraphrase, not a quoted tool response)
    *   **Mechanism**: Before using `--user-approved`, the agent MUST have called `AskUserQuestion` in the current conversation turn (or a recent prior turn). The reason string must contain a verbatim quote of the user's selection or text from that tool response.
    *   **Redirection**: Instead of self-authoring a reason, call `AskUserQuestion` with the phase transition as an option. The user's response becomes the valid reason.
    *   **Reason**: Agents systematically invent plausible-sounding justifications for non-sequential phase transitions. Text-based prohibition lists are ineffective because agents rephrase around them. Requiring a tool call creates a mechanical audit trail — no `AskUserQuestion` in the transcript means the `--user-approved` is invalid.

*   **¶INV_NO_ORPHANED_SESSIONS**: Sessions with work done must not be abandoned without a debrief.
    *   **Rule**: When the agent detects a topic change, skill switch, or new task request while an active session has progressed past Phase 0 (Setup), it MUST fire `§CMD_REFUSE_OFF_COURSE` before proceeding. The agent writes a debrief (abbreviated or full, depending on current phase) and idles the session before activating the new work.
    *   **Detection**: `currentPhase` in `.state.json` is past `"0: Setup"` — this means work was started. No debrief file exists in the session directory.
    *   **Exempt**: `/do` sessions — lightweight ad-hoc work where debrief friction exceeds value.
    *   **Contextual synthesis**: If the session is already in a synthesis sub-phase (N.1+), finish the full synthesis pipeline. If the session is in a work phase (before synthesis), write a fast debrief + idle only (skip checklists, pipeline, close ceremony).
    *   **On user skip**: If the user explicitly says "skip debrief" via the decision tree, log the skip reason to the session log, then idle the session without debrief. The audit trail is preserved.
    *   **Overflow during debrief**: Dehydrate with "finish debrief then switch" as the next step. The user's switch request is captured in DIALOGUE.md by the `user-prompt-submit-freeform-chat.sh` hook — this serves as the breadcrumb for post-debrief routing.
    *   **Reason**: Agents systematically prioritize the user's new request over session hygiene. Without this invariant, sessions accumulate with work done but no debrief — losing the audit trail, RAG discoverability, and knowledge capture that debriefs provide.

## 3. Tag Physics

*   **¶INV_ESCAPE_BY_DEFAULT**: All lifecycle tags in body text MUST be backtick-escaped unless intentional.
    *   **Rule**: `#needs-*`, `#delegated-*`, `#next-*`, `#claimed-*`, and `#done-*` tags in body text (logs, details, plans, debriefs) must be backtick-escaped (`` `#needs-*` ``) unless they are intentional discoverable tags on the `**Tags**:` line or explicitly promoted/acknowledged inline tags.
    *   **Enforcement**: `engine session check` scans session artifacts for bare inline lifecycle tags during synthesis. Each bare tag must be either PROMOTED (→ request file + escape inline) or ACKNOWLEDGED (→ marked intentional) before synthesis can complete.
    *   **Reason**: Bare inline tags in non-discoverable contexts pollute `engine tag find` results. Escape-by-default ensures every surviving bare tag represents a real, actionable work item.

*   **¶INV_1_TO_1_TAG_SKILL**: Every `#needs-X` tag maps to exactly one skill `/X`. No generic tags.
    *   **Rule**: The tag noun IS the skill name. `#needs-brainstorm` → `/brainstorm`, `#needs-implementation` → `/implement`, `#needs-chores` → `/chores`. No generic `#needs-delegation` or catch-all tags. If a new work type needs a tag, it needs a corresponding skill (or mode within an existing skill).
    *   **Reason**: Generic tags create routing ambiguity. 1:1 mapping makes the system self-documenting — seeing a tag tells you exactly which skill resolves it.

*   **¶INV_BACKTICK_INERT_SIGIL**: Backtick-enclosed sigiled references are inert — no scanning, no preloading, no tag actions.
    *   **Rule**: When a sigiled reference (`§CMD_*`, `§FMT_*`, `§INV_*`, `#needs-*`, etc.) is enclosed in backticks, it is a **mention** — documentation, not a dependency or action. All automated systems (tag discovery, reference preloading, dispatch routing) MUST ignore backtick-escaped references.
    *   **Applies to**: Tag lifecycle (`#needs-*` etc. — see `§INV_ESCAPE_BY_DEFAULT`), reference preloading (`§CMD_*`, `§FMT_*`, `§INV_*` — scanner skips backticked refs), code fence blocks (treated as bulk-escaped — all refs inside are inert).
    *   **Mechanism**: Two-pass filtering. First strip backtick spans and code fence blocks, then scan remaining text for bare sigiled references. This pattern is shared by `engine tag find` (tag discovery) and `resolve_refs()` (reference preloading).
    *   **Invoke vs. Mention**: In algorithm/instruction sections (e.g., "Invoke §CMD_DECISION_TREE with..."), use **bare** refs — these are invocations that trigger preloading. In documentation/definition sections (e.g., "Separated from `§CMD_DECISION_TREE` because..."), use **backticked** refs — these are mentions that should not trigger preloading. Code fence blocks are always inert regardless.
    *   **Reason**: Unifies the escaping convention across tags and preloads. Backtick = "I'm mentioning this, not invoking it" — same semantic everywhere.

## 4. Multi-Agent Safety

*   **¶INV_NO_DESTRUCTIVE_GIT**: Agents MUST NOT run tree/index-destructive git commands. The working tree is ALWAYS dirty with parallel-agent churn — a destructive git command can silently erase another agent's uncommitted work with **no git-recoverable trace** (no stash, no commit).
    *   **Rule**: The following are forbidden by default — `git stash` (any mutating subcommand), `git checkout [<rev>] -- <paths>` / `git checkout .` / `git checkout -f`, `git switch --force`/`--discard-changes`, `git restore` (any working-tree form), `git reset --hard`/`--merge`/`--keep` (and bare `git reset`/`--mixed` as risky), `git clean -f`/`-d`/`-x`, `git rm`, `git branch -d`/`-D`, `git push --force`, and index sweeps `git add -A`/`-u`/`.`/`-p`. NEVER stash/checkout/reset/restore/clean to "clean up" or to capture a baseline.
    *   **The allowed tree/index writes** are `git add -- <explicit path>` (whole-file staging of a file you own) and `git mv <old> <new>` (a rename you own — see the staging note below). To read a committed version use `git show HEAD:<path>`; to read the working file, open it by explicit path. Read-only git (`status`, `log`, `diff`, `show`, `rev-parse`, `reflog`, `fsck`, `stash list`/`show`, `branch --list`) is always fine.
    *   **If you believe you genuinely must** run a forbidden command, STOP and ask the user — only the user can authorize it. Never self-authorize.
    *   **A scoped `git add` does NOT scope the commit.** `git commit` writes **the whole index**, including anything another lane staged before you arrived — so a perfectly correct `git add -- <your path>` gives you no protection at commit time. **Commit with a pathspec: `git commit -m "…" -- <explicit paths>`.** That form commits only those paths *and leaves the other lane's staged work in the index* rather than consuming it — **but only staged work in OTHER paths.** ⚠️ **The pathspec form scopes WHICH PATHS, never WHAT CONTENT: for the paths you name it takes the WORKING TREE and silently discards every staged difference for them.** Reproduced twice in throwaway repos: a `git rm --cached` deletion is dropped and the file is committed as a modification while staying tracked; a partial `git add -p` is dropped and BOTH hunks land. So a neighbour's staged hunk *inside a file you name* is taken as whatever is on disk, and `git diff --cached` will not warn you — it answers truthfully about the index, and this form never consults it. **The operational rule: if what you want to commit is not visible ON DISK, the pathspec form cannot commit it.** For an index-only operation — an untracking, a deliberate partial stage — the pathspec form cannot express it and a bare `git commit` is the only thing that honours it; that is safe **only** when `git diff --cached --name-only` is verified to hold exactly your set and nothing else immediately before. And read `git show --stat` AFTER every commit for the SHAPE, not only the paths: a `D` staged and an `M` committed are different words, and the after-stat is the only place the difference prints. Before any commit, run `git diff --cached --name-only` and read it: a dirty index is invisible at the moment you commit, and nothing in the terminal warns you.
    *   **`git mv` is a staging write.** It is the right tool for a rename and it is permitted — but it leaves the rename **staged**, so the next `git commit` by any lane sweeps it up. After a `git mv`, either commit it with a pathspec yourself or tell the lane that will.
    *   **Committing is `/snapshot`'s job**, not a worker's. See the `/snapshot` "HARD RULE — NO GIT GYMNASTICS" prose (`.claude/skills/snapshot/SKILL.md`) — this invariant is the single-source statement of that rule.
    *   **Enforcement**: The `pre-tool-use-one-strike.sh` PreToolUse hook blocks each forbidden command on first attempt with this guidance (one-strike: allowed on a deliberate retry within the session). The hook is the mechanical net; this invariant is the reason.
    *   **Reason**: Captured from a real incident — a builder sub-agent ran `git stash push` (failed), a bare `git stash pop` (hit an unrelated stash), then `git checkout HEAD -- <paths>` to "clean up", reverting 8 off-lane files it did not own. Unstaged reverts leave zero git trace. **Second incident, and it broke no rule as written**: one lane renamed a skill with `git mv` (legitimate, and staging); a second lane then staged one explicit path and committed — sweeping 540 lines of the first lane's rename into a commit titled for a fourteen-line unrelated fix. Neither ran a forbidden command. Two sessions actively messaging each other about coordination still hit it, because the index is invisible at commit time. That is why the rule now covers the commit side, not only the staging side.

*   **¶INV_ADJACENCY_IS_NOT_OWNERSHIP**: On a shared branch, you MUST NOT infer who owns a file from proximity — not from mtime, not from "the lane editing nearby", not from which agent messaged you about it. Establish ownership from the owner's own record (their session log / ticket refs), or ASK.
    *   **Rule**: Before attributing work, routing a fix request, or naming another lane in a commit message or ticket comment, confirm the lane actually owns it. A wrong attribution in a commit message is effectively permanent — amending published history on a shared branch is worse than the error, so the mistake ships.
    *   **Rule**: When another agent hands you a misrouted request, don't just decline it — check your own log, then **re-route it to the lane that does own it**. A decline stalls the fix; a re-route lands it.
    *   **Redirection**: `stat -f "%Sm" -t "%H:%M:%S" <file>` tells you WHEN a file changed, never WHO or WHY. To attribute: grep the candidate lanes' session logs for the symbol (`grep -c` beats a guess), or read the commit that introduced it. Cheap, and it is the only honest source.
    *   **Reason**: Captured from a real incident — an orchestrator inferred a detector's owner from mtime proximity plus "they're the parallel lane in this file", named that lane in a commit message, and asked them to commit a module that was never theirs. The addressed session checked its own log (0 refs vs the true owner's 36), declined, and re-routed the ask itself; the real owner then verified and fixed it in minutes. The re-route saved it; the misattribution is still in the commit message. Related: a parallel lane's `git add` by path-glob swept another lane's in-flight new file into an unrelated ticket's commit, leaving the branch uncompilable — the same root confusion, in the other direction.

*   **¶INV_NO_GIT_STATE_COMMANDS**: Superseded by `§INV_NO_DESTRUCTIVE_GIT`, which states and enforces the multi-agent git-state rule concretely. Retained as an alias for existing cross-references.

## 5. Delegation Physics

*   **¶INV_CLAIM_BEFORE_WORK**: An agent MUST swap `#delegated-X` → `#claimed-X` before starting work on a tagged item.
    *   **Rule**: When a daemon-spawned or manually-triggered agent begins work on a tagged request, it must immediately claim the work by swapping the tag via `/delegation-claim`. This prevents double-processing by parallel agents. The swap uses `engine tag swap`, which errors if the old tag is already gone (race condition safety — another worker already claimed it).
    *   **Reason**: Stateless coordination. Tags are the state — `#claimed-X` means "someone is working on this." The `#delegated-X` → `#claimed-X` transition (not `#needs-X` → `#claimed-X`) ensures work was human-approved before any worker touches it.

*   **¶INV_NEEDS_IS_STAGING**: `#needs-X` is a staging tag. Daemons MUST NOT monitor `#needs-X`.
    *   **Rule**: `#needs-X` means "work identified, pending human review." Only `#delegated-X` triggers autonomous daemon dispatch. The transition `#needs-X` → `#delegated-X` requires human approval via `§CMD_DISPATCH_APPROVAL`.
    *   **Rule**: Agents may freely create `#needs-X` tags (via `§CMD_HANDLE_INLINE_TAG`, `§CMD_CAPTURE_SIDE_DISCOVERIES`, REQUEST file creation). These tags are inert until a human explicitly approves dispatch.
    *   **Reason**: Eliminates the race condition where daemons grab work the instant a tag appears, before the user has reviewed or batched related items.

*   **¶INV_NEXT_IS_IMMEDIATE**: `#next-X` is an immediate-execution tag. Daemons MUST NOT monitor `#next-X`.
    *   **Rule**: `#next-X` means "user chose to handle this in the next skill session." It is set during `§CMD_DISPATCH_APPROVAL` via the "Claim for next skill" option. The next skill auto-claims matching `#next-X` items on activation by swapping `#next-X` → `#claimed-X` and writing breadcrumbs normally.
    *   **Rule**: Daemons MUST ignore `#next-X` tags (same policy as `#needs-X`). Only `#delegated-X` triggers daemon dispatch.
    *   **Rule**: If `#next-X` items remain unworked (session died, user forgot), they are detectable as stale. `/delegation-review` surfaces them for re-routing. They do NOT auto-decay — manual handling only.
    *   **Rule**: Multiple `#next-*` items of different tag nouns are allowed simultaneously. The activating skill only auto-claims items matching its own tag noun (e.g., `/implement` claims `#next-implementation` but NOT `#next-brainstorm`). Non-matching `#next-*` items remain and are surfaced as context signal for subsequent skills.
    *   **Reason**: `#next-X` enables a "fast lane" that bypasses the daemon entirely. It must not race with daemon dispatch. The separate state (vs. reusing `#claimed-X`) preserves `#claimed-X`'s breadcrumb-writing semantics from `/delegation-claim` and makes abandoned items detectable.

*   **¶INV_DISPATCH_APPROVAL_REQUIRED**: The `#needs-X` → `#delegated-X` and `#needs-X` → `#next-X` transitions require human approval.
    *   **Rule**: Agents MUST NOT auto-flip `#needs-X` → `#delegated-X` or `#needs-X` → `#next-X` without presenting the dispatch approval walkthrough (`§CMD_DISPATCH_APPROVAL`). The human reviews each tagged item and approves, defers, claims for next skill, or dismisses.
    *   **Reason**: The user is the authority on what gets dispatched. Batch review during synthesis enables informed decision-making about which work items are ready for autonomous processing or immediate execution.

*   **¶INV_REQUEST_IS_SELF_CONTAINED**: REQUEST files must contain all context needed for execution.
    *   **Rule**: A worker must be able to fulfill a REQUEST without access to the requester's session state. Include relevant file paths, expectations, constraints, and requesting session reference inline.
    *   **Reason**: REQUESTs survive requester session death. The requester may have overflowed, deactivated, or been killed. The REQUEST file is the contract.

*   **¶INV_DELEGATE_IS_NESTABLE**: `/delegation-create` must operate without session activation.
    *   **Rule**: The `/delegation-create` skill reads from and writes to the current session directory. It does not call `engine session activate`. It can be invoked from any phase of any skill without disturbing session state.
    *   **Reason**: Delegation happens mid-skill (during interrogation, walkthrough, or ad-hoc chat). Session activation would conflict with the active skill's session.

*   **¶INV_GRACEFUL_DEGRADATION**: Delegation modes degrade gracefully when infrastructure is unavailable.
    *   **Rule**: Async delegation without fleet degrades to manual pickup (REQUEST file + tag persists). Blocking delegation degrades to async if the session dies (tag persists, worker can still find it). Silent mode requires no infrastructure beyond the Task tool.
    *   **Reason**: Solo developers without fleet/daemon should still benefit from the delegation file format. Nothing is lost — just deferred.

*   **¶INV_DELEGATION_VIA_TEMPLATES**: A skill supports delegation if and only if it has `_REQUEST.md` and `_RESPONSE.md` templates in its `assets/` folder.
    *   **Rule**: Template presence is the opt-in signal. If a skill has no `_REQUEST.md` template, it does not accept delegation requests.
    *   **Rule**: The request template defines what a requester must fill in. The response template defines what a responder must deliver. Both are populated via `§CMD_WRITE_FROM_TEMPLATE`.
    *   **Rule**: REQUEST files are written to the **requesting** session directory. RESPONSE files are written to the **responding** session directory (where the skill executes).
    *   **Rule**: Each RESPONSE template is tailored to its skill's specific outputs (code changes for implement, decisions for brainstorm, docs updated for document, verdict for review, task checklist for chores, research report for research).
    *   **Reason**: Delegation was previously a parallel mechanism (3 standalone skills + separate files). This convention makes delegation a capability of each skill rather than a separate system.

*   **¶INV_DYNAMIC_DISCOVERY**: Tag-to-skill mapping must use dynamic template discovery, not static maps.
    *   **Rule**: Daemon dispatch discovers available skills by scanning for `TEMPLATE_*_REQUEST.md` files in each skill's `assets/` directory. No hardcoded tag registries or static configuration maps.
    *   **Rule**: `engine session request-template '#needs-xxx'` resolves the tag noun to a skill, finds the template, and outputs it to stdout. This is the canonical lookup path.
    *   **Reason**: Static maps rot. Dynamic discovery is self-maintaining — adding a REQUEST template to a skill automatically makes it dispatchable. Removing the template removes the capability.

*   **¶INV_PREFER_BUILD_SCRUTINIZE**: When offering to hand a scoped task to an autonomous agent, prefer the `/build` + `/scrutinize` combo if both skills are available.
    *   **Rule**: Any point that offers a raw agent handoff (`§CMD_HANDOFF_TO_AGENT`, `§CMD_SELECT_EXECUTION_PATH`'s agent path, `§CMD_PARALLEL_HANDOFF`) MUST first check the available-skills list. If **both `/build` and `/scrutinize`** are present, present the combo as the recommended option instead of a bare `Agent`/`Task` handoff: `/build` assembles a complete self-contained context pack (goal + verbatim asks + prior-chunk history + hard gates + scope guard), dispatches the builder, and returns a structured Build Report; `/scrutinize` then adversarially reviews that report.
    *   **Chunk-aware — one `/build` + `/scrutinize` PER independent chunk, never merged**: before offering a single `/build`, check whether the plan decomposes into ≥2 **independent** chunks (disjoint `Files:`, no cross-`Depends:`). If it does, do NOT merge them into one `/build` — a merged build over independent chunks loses per-chunk scope isolation and hands the critiquer a muddier target. Instead run **one `/build` per chunk in parallel** (agent-level fan-out via `§CMD_PARALLEL_HANDOFF` — the Skill tool is sequential, so real parallelism is concurrent builder *agents*, each carrying its own /build-grade context pack + Build Report), then **one `/scrutinize`-grade critique per Build Report** (parallel critiquers), then a single combined triage over all findings. Merge into a single `/build` ONLY for one cohesive chunk (shared files or a cross-`Depends` chain that can't be split).
    *   **Fallback**: If either skill is unavailable, offer the plain handoff. Never block on their absence.
    *   **User owns the choice**: This biases the *recommended* option; the user may still pick a raw handoff or inline. The preference is presented, not forced.
    *   **Reason**: A `/build` handoff is strictly richer than a bare agent launch — the agent gets a self-contained context pack (so its output quality isn't bounded by the orchestrator's working memory, per `§INV_REQUEST_IS_SELF_CONTAINED`), leaves a reviewable paper trail, and chains into an adversarial review. Defaulting to it raises handoff quality wherever the skills exist.

*   **¶INV_A_PROBE_WRITES_ITS_ANSWER_DOWN**: Any agent you dispatch whose deliverable is an **answer** rather than an edit MUST be given a file path and told to write its answer there **as well as** returning it.
    *   **Rule**: Before dispatching, mint the path and put it in the brief — `WRITE your answer to <absolute path> as well as returning it`. A brief that names no path produces a **transcript-only** result: the answer lives in the agent's reply and nowhere else. That is fully durable while the parent context lives and **zero-durable the moment that context ends** — a clear, a restart, a dehydration, or simply a long session that summarizes past it.
    *   **Write the skeleton first, then append as findings land.** The opening write is the question, your bearings, and empty headings — not a restatement of the brief and the material you were handed. Fill it as you establish things. A lane that spends its first minutes composing a long preamble out of its own inputs has nothing useful on disk if it is interrupted, which is the exact loss this invariant exists to prevent.
    *   **The discriminator, and it is mechanical**: *did the brief name a path the agent will write?* If not, the result is transcript-only. After the fact the same test runs over the agent's transcript — no `builds/` or `sessions/` path passed to a write tool means the answer was never recorded, however long and confident the reply was.
    *   **This is about the HAND-AUTHORED brief, not the skill.** `/probe` and `/triage` already mandate a report path and are not the leak; `/build`, `/scrutinize` and every lane-shaped skill write a log as they go and are durable by construction. The gap is the ad-hoc `Agent`/`Task` dispatch — *"read-only analysis in X, report back"* — which is exactly the shape `§INV_DISPATCH_THROUGH_THE_SKILL` warns about, arriving here as a durability failure rather than a quality one.
    *   **A build lane is durable by construction; a probe is not.** A lane writes its log and its report as it goes, so killing it costs only the remainder. A probe answers in its reply, so killing the PARENT after the probe succeeds costs the entire result — and nothing about the task list, the filesystem, or the transcript shows a gap where it used to be. **The loss is silent, total, and indistinguishable from the probe never having run.**
    *   **Redirection**: do not tell yourself you will paste the answer into a log when it returns. You will be mid-triage, or the context will end first. Name the path in the brief; it costs the dispatch one line and the agent one tool call.
    *   **Reason, measured**: in a single day one session dispatched 22 agents, of which **7 were transcript-only — roughly 113KB of finished analysis**, including a sweep of the *"named, not fixed"* section of ~32 lane logs, i.e. the project's entire leftover-work inventory. **Every one of the seven completed successfully.** A context clear made all of them unreachable at once, and none of them left a trace on disk to say so. They were recoverable only because subagent transcripts persist as JSONL and could be mined afterwards — recovery that should never have been necessary, and which is unavailable the moment those transcripts are pruned.

## 6. Directive Physics

*   **¶INV_DIRECTIVE_STACK**: Agents must load the full stack of directive files (child-to-root ancestor chain) when working in a directory. Enforcement is escalating.
    *   **Rule**: Directive files live in `.directives/` subfolders at each directory level (e.g., `packages/estimate/.directives/INVARIANTS.md`). Discovery walks up from touched directories to the project root, checking `.directives/` at each level. Eight directive types across two tiers:
        *   **Core directives** (always discovered): AGENTS.md, INVARIANTS.md, ARCHITECTURE.md. Surfaced as soft suggestions.
        *   **Skill directives** (filtered by `directives` param): TESTING.md, PITFALLS.md, CONTRIBUTING.md, TEMPLATE.md, CHECKLIST.md. Only suggested when the active skill declares them in the `directives` field of session parameters. CHECKLIST.md has a **hard gate** at deactivation: when discovered, `§CMD_PROCESS_CHECKLISTS` must pass before `engine session idle`/`deactivate` succeeds. Skills that declare it: `/implement`, `/fix`, `/test`.
    *   **Enforcement**: Escalating two-hook architecture. PostToolUse hook (`post-tool-use-discovery.sh`) discovers directives and adds them to `pendingDirectives` in `.state.json` with a warning. PreToolUse hook (`pre-tool-use-directive-gate.sh`) blocks after a threshold of tool calls if `pendingDirectives` is non-empty. Reading a pending file clears it from the list.
    *   **Discovery**: `engine discover-directives` performs walk-up search (full ancestor chain — all directives from child to root apply cumulatively), checking `.directives/` subfolders first with flat directory root fallback. `engine session activate` discovers files from `directoriesOfInterest`. At runtime, the PostToolUse hook tracks `touchedDirs` in `.state.json` and discovers files for newly-touched directories. Both apply skill-directive filtering.
    *   **End-of-session**: `§CMD_MANAGE_DIRECTIVES` handles AGENTS.md updates, invariant capture, and pitfall capture based on session work.
    *   **Reason**: Agents systematically ignore directive files placed near their work. Escalating enforcement (warn then block) ensures directives are always loaded.

*   **¶INV_CHECKLIST_BEFORE_CLOSE**: A session cannot be deactivated with unprocessed CHECKLIST.md files.
    *   **Rule**: `engine session idle`/`deactivate` checks `checkPassed == true` in `.state.json` when `discoveredChecklists[]` is non-empty. If not set, the transition is blocked.
    *   **Rule**: `§CMD_PROCESS_CHECKLISTS` must run during synthesis. The agent reads each checklist, evaluates items, then quotes results back via `engine session check` (which sets `checkPassed=true`). The deactivate gate is the mechanical safety net.
    *   **Reason**: Checklists contain post-work requirements (testing steps, user questions, cleanup tasks). Allowing session close without processing them defeats their purpose.

*   **¶INV_REQUEST_BEFORE_CLOSE**: A session cannot be deactivated with unfulfilled request files.
    *   **Rule**: `engine session check` Validation 3 reads `requestFiles[]` from `.state.json`. Every request file must (a) exist and (b) have no bare `#needs-*` tags anywhere in the file (backtick-escaped excluded). Formal REQUEST files (filename contains "REQUEST") must additionally have a `## Response` section. If any fail, check exits 1 and deactivation is blocked.
    *   **Rule**: The agent must resolve all bare `#needs-*` tags (swap to `#done-*` or backtick-escape). For formal REQUEST files, also add a `## Response` section.
    *   **Reason**: Request files are contracts between sessions. Closing a session without fulfilling its requests leaves broken promises in the system — future sessions that depend on the work will find unfulfilled tags.

*   **¶INV_A_RULE_OWED_HAS_AN_OWNER**: A durable rule a worker learns but is not permitted to land names its destination file in the hand-back, not only in the report, so that it **reaches** an owner who rules on it. The hand-back carries the destination; the coordinator is the owner, and is the owner of every such rule rather than one named per rule.
    *   **Why a worker cannot land it**: `INVARIANTS.md` and `PITFALLS.md` are shared by every lane, so a file partition never grants either to anybody, and widening it would put several concurrent writers on the files everything loads. The refusal is correct; what follows it is the gap.
    *   **Rule**: The worker writes the rule in its report under the exact heading `## Rule owed` — the rule, what it forbids, and the reason with its measurement where one exists — names the destination file, and **repeats the pointer in its hand-back** so the coordinator rows it as an open obligation with an owner. A `## Rule owed` block whose only reader is whoever happens to open that report is indistinguishable from the rule never having been written.
    *   **The owner reads it; a sweep does not land it.** The owner rules on each rule one at a time — landed, landed rewritten, or declined — and records the ruling where the row lives **and in the report's own block**. Both, because they answer different readers: the row is how the session tracks the obligation, and the block is what somebody opening that report in a month actually reads. A `## Rule owed` block that never gains its ruling leaves that reader unable to tell a pending rule from one that was weighed and declined. An automated append from report to directive file is **prohibited**: these files load into every agent on every session start, the rules are not uniformly worth landing, and an unread append costs every context more than the rule is worth. Prefer landing a rule as a sentence inside the entry that already owns its family over minting a new one.
    *   **A decline is recorded with its reason and an alternative destination**, never silent, so a reader can tell a rule that was weighed from one that was missed. Note what this does **not** yet buy: the record lives in the session's own register, so it is durable for that session and there is no place a later worker can look up prior declines before re-filing. Recording a decline is the half that exists; the lookup is not built. A rule about one package's code belongs in that package's own `.directives/`, and naming that is a decline, not a dismissal.
    *   **Reason, measured**: nine rules from three lanes in one session reached `## Rule owed` blocks and none reached either file — and the heading itself reached **at least five** of that session's reports, a floor rather than a count, because the sweep that read them could not open every file. One of the nine was written under the heading **twice by the same lane**, in two rounds, the second time marked *unchanged from the first report* — so the writing is cheap, was done willingly, and still bought nothing, because no route carried either copy out of the report. The cost is in the rule not arriving.

*   **The invariants of the inbox read are defined in the skill that owns them, and are named here so a reader starting from this file can reach them.** `§INV_NO_RAW_CHANNEL_READ`, `§INV_OWN_COMMENT_IS_NOT_FEEDBACK` and `§INV_ONE_EXCLUSION_STATEMENT` govern how `/intake` and `/groom` read a Linear inbox channel. **The definition site is `skills/intake/SKILL.md`**, which `§INV_SIGIL_SEMANTICS` sanctions as a definition site and which `§INV_A_RULE_OWED_HAS_AN_OWNER` prefers for a rule scoped to one skill. The bullets below carry `§`, not `¶`, for that reason: a second `¶` would assert *defined here* about a rule defined elsewhere, and a rule restated beside its definition is what `§INV_ONE_EXCLUSION_STATEMENT` is itself about. **These are pointers; where one disagrees with its definition, the definition wins.** Each names the invocation that goes red, and where a half of a rule has no failing arm it says so in those words, per `§INV_A_RULE_IN_PROSE_IS_NOT_ENFORCED_UNTIL_A_CHECK_CAN_FAIL`.
    *   **`§INV_NO_RAW_CHANNEL_READ`** — neither `/intake` nor `/groom` reads an inbox channel except through `§CMD_READ_INBOX_CHANNEL`, because a bypassable exclusion is a preference and agents route around preferences. **Forbids** a raw `engine project fetch` in either skill with nothing citing that command: the payload then arrives unfiltered and hands the skill its own replies back as human signal. **Redirection**: cite the command where the channel is read, and widen the scan in the same edit that adds a third caller rather than afterwards. **Goes red**: `bash scripts/tests/run-all.sh test-inbox-read-cmd.sh` — `test_17` scans the callers' directories for the offending shape, with its controls in the same run (the scan must reach a real call site, and a planted file that fetches while citing nothing must come back flagged), and `test_14` states it per caller. ⚠️ **What actually reddens is a FILE that names the fetch without naming the command, not per-call-site routing** — a file that cites the command once and fetches raw elsewhere within itself passes, so read the check as the floor it is.
    *   **`§INV_OWN_COMMENT_IS_NOT_FEEDBACK`** — a reply the system posted never appears in the fresh-feedback set, or the next wave acts on the machinery's own words as a person's input. The exclusion keys on the body's **leading text, never the author**: every skill post on Linear lands under the operator's own human identity, so an author check distinguishes nothing there. **Forbids** counting an own reply as corroboration, and re-triaging a disposition reason as new signal. **Redirection**: lead every skill-authored reply with a marker the command's table carries, and add the marker in the same edit as the disposition. **Goes red**: `bash scripts/tests/run-all.sh test-inbox-marker-exclusion.sh` — `test_01` plants each marker and requires the drain to drop it, `test_02` is the discriminating arm (the same program with the table emptied must re-admit every one, so the drop is the marker's doing and not an empty read), `test_03` requires the marked reply to withhold its root while its human sibling still drains, and `test_04` runs the shipped filter over a committed real fetch snapshot with the emptied-table baseline computed in the same invocation. The suite reads the marker table out of the shipped filter rather than restating it, so a marker added with no filter support reddens here without anyone editing the test.
    *   **`§INV_ONE_EXCLUSION_STATEMENT`** — the own-comment exclusion exists once as a program and once as a vocabulary, both in `§CMD_READ_INBOX_CHANNEL`, because a rule with two owners is owned by neither. **Forbids** a second copy of the marker list or a second filter applying it, anywhere; it does not forbid a caller citing the rule where it reads a channel, because a pointer cannot drift from what it points at — which is the licence this entry itself relies on. **Redirection**: read it as *one list, one filter, many pointers*. **Goes red**: `bash scripts/tests/run-all.sh test-inbox-read-cmd.sh` — `test_10` asserts the filter program lives in exactly one file with its own detector proved against the command file in the same invocation, `test_13` asserts neither caller carries the program, `test_11` asserts every marker the callers stamp is in the command's table, and `test_12` runs that same comparison against a table with one marker stripped so silent agreement cannot read like a silent failure to compare. ⚠️ **The prose half is stated, not enforced**: nothing counts restatements, and a term-presence count could not tell a citation from a copy, since documenting a rule and forbidding a thing raise the same count.

## 7. Engine Physics

*   **¶INV_ENGINE_COMMAND_DISPATCH**: All engine operations MUST go through `engine <command>`.
    *   **Rule**: Use `engine log`, `engine session`, `engine tag`, `engine research`, `engine session-search`, `engine doc-search`, etc. The `engine` command is available as a bare command via PATH — just use `engine`. Never resolve it manually.
    *   **Prohibited**: Any absolute or relative path to engine scripts. Examples: `~/.claude/engine/scripts/engine.sh`, `~/.claude/scripts/session.sh`, `~/.claude/scripts/log.sh`, `~/.claude/tools/session-search/session-search.sh`, `$(which engine)`. Use `engine research`, `engine tag swap`, `engine session-search query` instead.
    *   **Reason**: The heartbeat hook allowlists `engine` commands specifically; full paths are blocked. Resolving the `engine` script path manually (e.g., guessing `~/.claude/engine/scripts/engine.sh`) bypasses PATH and may reference a stale or wrong location.
    *   **Cross-ref**: Originally captured in `~/.claude/docs/.directives/INVARIANTS.md`. Promoted to shared for universal visibility.

*   **¶INV_MCP_PREFIX_IS_LOCAL**: An MCP server's tool prefix is LOCAL, not a contract — the same Linear server is `mcp__linear__*` on one machine and `mcp__linear-server__*` on another. There is no canonical name: the prefix is settled by the local config key and the name the server advertises, neither of which any doc controls.
    *   **Rule**: Never assume a literal `mcp__<server>__<tool>` string. Resolve the prefix from your OWN available-tool list at call time: take the tool whose name ends in `__<tool>` and whose server segment CONTAINS the service word (`linear`, `notion`, `posthog`, `github`), and call that name.
    *   **The prefix is not the config name**: `claude mcp list` reports the key the person typed into config; the tool prefix comes from the name the SERVER advertises, and the two differ routinely. One server can even expose two prefixes at once — measured on a working machine, `mcp__linear-server__get_issue` and `mcp__linear__authenticate` were both live while `claude mcp list` said `linear`. Reading the config name tells you nothing about what to call.
    *   **Rule**: An `mcp__…` name written in a skill, directive, doc or report is an EXAMPLE naming the tool, never a string to type verbatim. Do not rewrite such a reference to match your machine, and do not enumerate the variants at every mention — the set is open, so a third variant would break every enumeration again.
    *   **Redirection**: When the literal prefix you expected is absent, scan your tool list for the service word and call what you find instead of concluding the server is missing. Conclude missing only when NO tool name carries that word.
    *   **Applies to the doctor too**: `engine env doctor` matches a configured server by SUBSTRING against the manifest's `check.server`, so `linear`, `linear-server` and `linear-mcp` all satisfy the `linear` row. Nobody is asked to rename their config.
    *   **Reason**: There is no canonical MCP server name and never will be, so a hardcoded prefix fails wherever the machine is configured differently — and a preflight that FAILS a credential which actually works is worse than one that never checked it, because it blocks work that would have succeeded.

*   **¶INV_JSONSCHEMA_COMPLIANCE**: When a JSON Schema is provided in context, agents MUST comply with it fully — not just the property names.
    *   **Rule**: Read the **entire** schema, not just the `properties` block. The `required` array lists fields that MUST be present — omitting a required field causes validation failure. The `type` constraints define what values are acceptable. The `description` fields explain what each property means.
    *   **Rule**: Every field in `"required"` MUST appear in your JSON, even if the value is an empty array `[]` or `null`. Missing required fields are rejected by the engine's JSON Schema validator.
    *   **Redirection**: If you are about to construct a JSON payload that targets a schema, scan the schema's `required` array first. Then check each property's `type` and `description`. Only then construct the JSON.
    *   **Reason**: Agents systematically read `properties` for field names but skip `required`, `type`, and `description`. This invariant was created after an agent missed `directoriesOfInterest` despite having the full schema in context — proving the failure mode is format-blindness, not missing information.

*   **¶INV_INFER_USER_FROM_GIT**: Identity comes from `~/.claude/engine/.user.json`, else `git config --global user.email`.
    *   **Rule**: `engine user-info` reads the cache first, then git. If neither yields an email, fail and tell the user to set `git config --global user.email`.
    *   **Prohibited**: Parsing identity from filesystem paths (mount names, symlink targets, directory names).
    *   **Reason**: A path describes where files happen to live, not who is working; the git email is the one identity every machine already configures.

## 8. Phase Execution Physics

*   **¶INV_BOOT_SECTOR_AT_TOP**: Every protocol-tier SKILL.md starts with `§CMD_EXECUTE_SKILL_PHASES`.
    *   **Rule**: The first instruction in a protocol-tier skill (after frontmatter and title) must invoke `§CMD_EXECUTE_SKILL_PHASES`. This is the boot sector — it tells the LLM "run through all my phases." Phase sections follow below.
    *   **Scope**: Only protocol-tier skills (those with `phases` arrays). Utility-tier skills (sessionless, no phases) do not use the boot sector.
    *   **Reason**: The boot sector ensures the LLM encounters the phase orchestrator before any phase-specific prose, establishing the mechanical execution pattern from the start.

*   **¶INV_STEPS_ARE_COMMANDS**: Phase steps MUST be `§CMD_*` references.
    *   **Rule**: The `steps` array in a phase declaration contains only `§CMD_*` command names. Prose instructions are not steps — they belong in SKILL.md phase sections, executed after `§CMD_EXECUTE_PHASE_STEPS` completes.
    *   **Redirection**: If you want to add a prose instruction as a step, extract it into a `CMD_*.md` file first, then reference it as a step.
    *   **Reason**: Mechanical step execution requires machine-parseable command references. Prose in steps would break hook-driven preloading and proof schema derivation.

*   **¶INV_PROOF_IS_DERIVED**: Phase proof is the concatenation of its steps' proof schemas.
    *   **Rule**: Skills declare `steps` and `commands` per phase. The `proof` array contains data fields that the step commands produce (as defined in each CMD file's `## PROOF FOR §CMD_X` section). Phase proof is the union of all step proof schemas plus any phase-level data fields.
    *   **Enforcement**: `engine session phase` extracts standard JSON Schemas from each step's CMD file, merges them into a combined schema, and validates the proof JSON against it (exit 1 on failure). The validation tool is `tools/json-schema-validate/`.
    *   **Reason**: Co-located proof schemas (in CMD files) are the source of truth. Declaring proof separately from steps creates drift — the proof list diverges from what the commands actually produce.

*   **¶INV_PROOF_COLOCATED**: Each `CMD_*.md` file has a `## PROOF FOR §CMD_X` section.
    *   **Rule**: Every extracted command file in `~/.claude/engine/.directives/commands/` must include a proof schema section at the bottom. The schema uses standard JSON Schema format (`$schema`, `type: object`, `properties`, `required`, `additionalProperties`).
    *   **Rule**: Commands that orchestrate other commands (like `§CMD_RUN_SYNTHESIS_PIPELINE` or `§CMD_EXECUTE_PHASE_STEPS`) note that proof comes from the commands they invoke, not from themselves.
    *   **Reason**: Co-location keeps command files self-contained (definition + proof contract). The hook preloads CMD files into context — the LLM sees the proof schema alongside the command definition.

## 9. Hook Physics

*   **¶INV_PREFER_AC_OVER_STDOUT**: Hooks SHOULD use JSON `additionalContext` over plain stdout.
    *   **Rule**: When delivering content to the LLM from hooks, use `hookSpecificOutput.additionalContext` (with `hookEventName`) rather than plain stdout. Both mechanisms work for SessionStart and UserPromptSubmit, but `additionalContext` is the documented, structured delivery path.
    *   **Reason**: `additionalContext` is the official mechanism per Claude Code docs. Plain stdout works but is the legacy/simple path. Consistent use of `additionalContext` makes hook output parseable and debuggable.

## 10. Token Economy

*   **¶INV_TRUST_CACHED_CONTEXT**: Do not burn tokens on redundant operations.
    *   **Rule**: If you have loaded `DEHYDRATED_CONTEXT.md` or `DEHYDRATED_DOCS.md` during session rehydration, you MUST NOT read the individual files contained within them (e.g., `_LOG.md`, specs) unless you have a specific reason to believe they have changed externally.
    *   **Rule**: Rely on your context window. Do not `read_file` something just to check a detail if you recently read it in a dehydrated block. Memory over IO.
    *   **Rule**: Prefer single, larger tool calls over many small ones. Batch operations.
    *   **Rule**: When you know a file exists and you have its content in a summary/dehydrated file, trust it. Blind trust.
    *   **Exception**: Preloaded files require Read before Edit — see `¶INV_PRELOAD_IS_REFERENCE_ONLY`.
    *   **Reason**: Token-expensive re-reads of already-loaded content waste context budget and add latency. Trust the cache.

*   **¶INV_PRELOAD_IS_REFERENCE_ONLY**: Preloaded content is already in your context. Do NOT re-read it. Editing requires an explicit Read.
    *   **Rule**: Content injected via hooks (`additionalContext`, `[Preloaded: path]` markers) is delivered to your context window for **reading and reference only**. Claude Code's Edit tool maintains its own registry of "read" files — hook-injected content is NOT registered in that registry.
    *   **Rule**: For **reference purposes**, preloaded content is **complete and sufficient**. Do NOT call Read on a file that was already preloaded — the content is already in your context window. This includes directive files (AGENTS.md, CONTRIBUTING.md, PITFALLS.md, etc.) auto-injected by hooks.
    *   **Rule**: To **edit** a preloaded file, you MUST call the Read tool on it first. The Read call registers the file with the Edit tool. Without it, Edit will block with "you must read the file first."
    *   **Redirection** (`¶INV_REDIRECTION_OVER_PROHIBITION`): When you see `[Preloaded: path]` content, trust it — the file is in your context. Only call Read if you intend to Edit. When you see `[Suggested — read these files for full context]:` with path-only listings, those files are NOT in your context — Read them if needed.
    *   **Two markers**:
        *   `[Preloaded: /path/to/file]` + file content inline → **Already loaded. Do NOT Read.**
        *   `[Suggested — read these files for full context]:` + path list → **Not loaded. Read if relevant.**
    *   **Scope**: Applies to ALL preload sources — SessionStart standards (COMMANDS.md, INVARIANTS.md, SIGILS.md), phase CMD files, skill SKILL.md, templates, directive files, dehydrated context files.
    *   **Not affected**: Files you loaded yourself via the Read tool. Those are already registered.
    *   **Reason**: Hooks deliver content via `additionalContext` injection, which bypasses the Edit tool's read-tracking. The agent sees the content and reasonably assumes it can edit it — but the Edit tool's internal state disagrees. Agents also systematically re-read preloaded directive files, wasting context tokens. This invariant makes both limitations explicit.

*   **¶INV_CONTEXT_BUDGET**: The status-line context % is informational, not a warning. Do not curtail work, rush, hand off early, or self-dehydrate out of context anxiety.
    *   **Rule**: The displayed `Context: X%` is **already normalized so 100% = the dehydration point** — it is "% toward dehydration," not raw window fill. Below 80% is *normal*: work freely. 40–70% is the ordinary working range, not a signal to do anything. Only the explicit levels in `§CMD_DEHYDRATE` change behavior — target **95%**, 85% is already early, and below that there is nothing to manage.
    *   **Rule**: Never dehydrate proactively before the `§CMD_DEHYDRATE` levels say to, never truncate interrogation/planning/build work to "save context," and never rush a handoff because a mid-range percentage "feels high." The overflow hook is a mechanical safety net at the real threshold; you do not need to front-run it.
    *   **Reason**: Agents systematically misread a mid-range context % as "getting full" and preemptively dehydrate, hand off, or cut corners — wasting a session that had ample headroom. The number already has the threshold baked in; treating it as a live warning is the error this invariant corrects.

## 11. Naming Conventions

*   **¶INV_SIGIL_SEMANTICS**: Sigils encode definition vs reference semantics.
    *   **Rule**: `¶` (pilcrow) marks a **definition** — the place where a command, invariant, feed, or tag section is declared and specified. `§` (section sign) marks a **reference** — a citation of something defined elsewhere.
    *   **Applies to**: All sigiled nouns — `CMD_`, `INV_`, `FEED_`, `TAG_`.
    *   **Definition sites**: COMMANDS.md headings (`¶CMD_X`), CMD_*.md headings (`¶CMD_X`), INVARIANTS.md entries (`¶INV_X`), AGENTS.md entries (`¶INV_X`), CONTRIBUTING.md entries (`¶INV_X`), SIGILS.md section headers (`¶FEED_X`, `¶TAG_X`), any file's inline invariant definitions (`¶INV_X`).
    *   **Reference sites**: SKILL.md steps arrays (`§CMD_X`), body text cross-references (`§CMD_Y`, `§INV_Y`), PROOF FOR headings (`§CMD_X`), docs/ (`§INV_X`, `§CMD_X`).
    *   **Governance**: Any file may define an invariant using `¶INV_X`. Only COMMANDS.md and CMD_*.md may define commands using `¶CMD_X`.
    *   **Redirection**: If you're about to write a sigiled noun, ask: "Am I defining it here, or referring to it?" `¶` = defining, `§` = referring.
    *   **Reason**: Without semantic sigils, readers cannot distinguish "this is defined here" from "this is defined elsewhere." The convention enables grep-based discovery: `grep '¶CMD_'` finds all definition sites; `grep '§CMD_'` finds all usage sites.

*   **¶INV_EPIC_SLUG_SIGIL**: Epic and chapter references use the `@` sigil prefix. Full definition in SIGILS.md § `@` — Epic and Chapter Slugs.

## 12. Formatting

*   **¶INV_LISTS_INSTEAD_OF_TABLES**: Markdown tables are prohibited in all project `.md` files and agent chat output.
    *   **Rule**: Do NOT use markdown tables (`| col | col |`) in any file — directives, SKILL.md files, docs, templates, session artifacts, or chat messages.
    *   **Redirection**: Use `§FMT_LIGHT_LIST`, `§FMT_MEDIUM_LIST`, or `§FMT_HEAVY_LIST` instead. Choose the density level that matches the number of fields per item. See SIGILS.md § Formatting Conventions for definitions and examples.
    *   **Heuristic**: 1-2 fields → `§FMT_LIGHT_LIST`. 3-4 fields → `§FMT_MEDIUM_LIST`. 5+ fields → `§FMT_HEAVY_LIST`.
    *   **Scope**: All `.md` files in the project AND all agent chat output. No exceptions.
    *   **Reason**: Tables break at narrow terminal widths, are hard to edit incrementally, and resist diffing. Lists are readable at any width, trivially editable, and diff cleanly.

*   **¶INV_CAMELCASE_FOR_DATA**: All JSON data the engine reads or writes MUST use camelCase property names.
    *   **Rule**: Property names in JSON schemas, `.state.json` fields, proof schemas, session parameters, dehydration payloads, and hook configs must be camelCase (`sessionDir`, `parametersParsed`, `logEntries`).
    *   **Prohibited**: snake_case (`session_dir`, `parameters_parsed`), kebab-case, or any other casing convention for JSON property names.
    *   **Scope**: All engine JSON — proof schemas in CMD `## PROOF FOR` sections, SKILL.md `proof` arrays, `§CMD_PARSE_PARAMETERS` schema, `§CMD_DEHYDRATE` schema, `.state.json` internal fields.
    *   **Redirection**: When constructing JSON for engine consumption, scan the target schema's `properties` for the canonical camelCase names. Never invent snake_case equivalents.
    *   **Reason**: Session parameters and dehydration data already use camelCase. Proof schemas were added later and used snake_case, creating an inconsistency that causes validation confusion.

## 13. Tmux / Fleet

*   **¶INV_NO_FOCUS_CHANGE_IN_NOTIFY**: Notification commands MUST NOT change the focused pane.
    *   **Rule**: When applying visual state (background color) to a non-focused pane, use the atomic compound command `select-pane -t "$pane" -P "bg=$color" \; select-pane -t "$active"` — this sets style AND restores focus in one tmux server round-trip (no race window). For the focused pane, skip style entirely (avoid flash/distraction).
    *   **Prohibited**: (1) `set-option -p -t style "bg=..."` — INVALID in tmux 3.6a, "style" is not a recognized pane option. (2) `select-pane -t "$pane" -P "bg=$color"` without focus restoration — creates a focus-theft race.
    *   **Reason**: Multiple agents call `fleet.sh notify` concurrently. The atomic compound command eliminates the race window. Skipping focused pane style prevents visual flashing.

*   **¶INV_FLEET_GRACEFUL_OUTSIDE_TMUX**: Fleet commands MUST be no-ops outside tmux.
    *   **Rule**: All tmux calls in fleet.sh and session.sh fleet paths must use `2>/dev/null || true`. Missing `$TMUX` or `$TMUX_PANE` means "not in fleet" — exit silently, don't error.
    *   **Cross-ref**: See also `§INV_TMUX_AND_FLEET_OPTIONAL` in AGENTS.md.

*   **¶INV_SILENT_FAILURE_AUDIT**: Shell commands guarded by `|| true` must be audited for correctness.
    *   **Rule**: When adding `|| true` to a command, verify that the command actually works as expected. Silent failure masking can hide regressions that persist for multiple sessions before being discovered.
    *   **Pattern**: After adding `|| true`, run the command without `|| true` at least once to confirm it succeeds. If it fails, investigate — don't just silence it.
    *   **Reason**: The style regression in fleet.sh was silently broken by `|| true` for an entire session cycle. The command was INVALID in tmux 3.6a but the error was invisible.

*   **¶INV_SUPPRESS_HOOKS_FOR_PROGRAMMATIC_STYLE**: Programmatic style changes via `select-pane -P` MUST suppress the `after-select-pane` hook using `@suppress_focus_hook`.
    *   **Rule**: Any code that calls `select-pane -P` for styling purposes must wrap it in `set -g @suppress_focus_hook 1 \; select-pane -P ... \; set -g @suppress_focus_hook 0`. The hook checks `@suppress_focus_hook` at the top and exits early if set to 1.
    *   **Reason**: Without suppression, `select-pane -P` triggers the focus hook, which calls `select-pane -P` again, creating a rendering cascade that causes visible pane flashing.

*   **¶INV_SKIP_REDUNDANT_STYLE_APPLY**: Visual style updates MUST be skipped when the target state hasn't changed.
    *   **Rule**: Before calling `select-pane -P`, read the current `@pane_notify` value. If it matches the requested state, skip the visual update. Data layer (`@pane_notify` set-option) still updates every time — only the visual `select-pane -P` is skipped.
    *   **Reason**: Redundant `select-pane -P` calls cause unnecessary tmux redraws and visible flashing.

*   **¶INV_HOOKS_NOOP_WHEN_IDLE**: Hooks MUST be no-ops when there is nothing to do.
    *   **Rule**: If a hook has no work to perform (e.g., no session active, no fleet pane, no applicable condition), it must exit 0 immediately. No logging, no side effects, no errors.
    *   **Reason**: Hooks fire on every tool call. Unnecessary work or errors in idle hooks degrade the entire agent experience.

## 14. Synthesis Pipeline Physics

*   **¶INV_SKIP_ON_EMPTY**: Pipeline steps that find nothing MUST skip silently — no halt, no user prompt.
    *   **Rule**: When a synthesis pipeline step (e.g., `§CMD_CAPTURE_SIDE_DISCOVERIES`, `§CMD_DISPATCH_APPROVAL`, `§CMD_RESOLVE_CROSS_SESSION_TAGS`) scans and finds zero items, it MUST NOT halt execution or prompt the user. Skip and return control to the orchestrator.
    *   **Redirection**: Instead of prompting "No items found — proceed?", just echo the scan scope (per `¶INV_ECHO_ON_SKIP`) and continue.
    *   **Reason**: Empty scans are the common case. Halting on every empty scan creates unnecessary round-trips in a pipeline that may have 8+ steps.

*   **¶INV_ECHO_ON_SKIP**: Every synthesis pipeline step MUST echo its scan scope to chat, even when nothing is found.
    *   **Rule**: When a pipeline step runs and finds zero results, it MUST still output a one-line summary of what it scanned and that nothing was found. Example: "Side discoveries: scanned IMPLEMENTATION_LOG.md — none found."
    *   **Reason**: Silent skips make the pipeline opaque. The user cannot tell if a step ran and found nothing vs. was accidentally skipped. Echo-on-skip provides an audit trail in the chat.

*   **¶INV_IDEMPOTENT_STEPS**: Pipeline steps MUST be safe to re-run without side effects.
    *   **Rule**: Every synthesis pipeline step must check existing state before acting. If a debrief already exists, don't create a duplicate. If tags are already swapped, don't swap again. If backlinks are already written, don't double-write.
    *   **Reason**: Context overflow can interrupt synthesis mid-pipeline. The rehydrated agent resumes at the saved sub-phase and re-runs steps. Non-idempotent steps would corrupt artifacts on re-run.

*   **¶INV_BATCH_SIZE_4**: `AskUserQuestion` batches are fixed at 4 items per call.
    *   **Rule**: When presenting multiple items for user decision (dispatch approval, tag triage, walkthrough items), batch them in groups of 4. The last batch gets the remainder (1-3 items). This matches `AskUserQuestion`'s maximum of 4 questions per call.
    *   **Reason**: Consistent batch sizing across all pipeline steps. The tool's 4-question limit is the natural batch boundary.

*   **¶INV_FOLLOWUP_ON_DEMAND**: Follow-up questions only when the user's selection requires additional input.
    *   **Rule**: After an `AskUserQuestion` response, only ask a follow-up if the selected option requires additional information to execute (e.g., "Claim for next skill" needs state passing, "Split item" needs sub-item definitions). Do not ask confirmations, summaries, or "anything else?" after each batch.
    *   **Reason**: Minimizes round-trips. The user chose an option — execute it. Only re-engage when genuinely blocked on missing input.

*   **¶INV_POINT_IN_TIME_CHECKS_EXPIRE**: A check whose result is used later must be re-run at the point of use, not only at the point it was mandated. A search, a liveness probe, or a state read is true *when it runs*; treating its result as durable across a long session is how a stale fact becomes a filed claim.
    *   **Rule**: When a protocol mandates a check at phase N and the result is *acted on* at phase M > N, the check re-runs at M. Record both results if they differ — the difference is usually the finding.
    *   **Redirection**: Instead of citing an earlier check ("the search returned nothing"), re-run it and cite the fresh result. If re-running is expensive, say *when* it was run in the claim itself, so a reader can judge staleness.
    *   **The tell, because the rule above describes a class and nobody recognises themselves in it**: *any fact you are about to relay that you did not measure yourself is expired until you re-measure it.* This is the same rule said as a gesture rather than a category, and the gesture is what fires. The failure does not feel like using a stale check — it feels like passing on something a colleague just told you, which is why an agent holding this invariant in context can still walk into it. **A fact arriving from a peer is a check you did not run**, and the queue it travelled in has a latency the fact does not carry. Relaying is the moment; re-measuring is the act.
    *   **And a fact arriving inside a SOURCE FILE is also a check you did not run** — this is the hop that evades the rule, because a docblock reads as the code speaking about itself rather than as somebody's old measurement. It can be stale through more than one hop: a docblock quoting a doc chapter, where the chapter was true when written and the code moved under it. Measured: a browser module's docblock quoted an addressing chapter's *"nothing parses `//domain` today… it fails quietly"*; a commit had closed that two days earlier, and the chapter still said it. The claim was relayed into a brief as current. **The tell is not who told you — it is whether you ran it.** A comment, a report measured against a *running* service, and a colleague are the same category.
    *   **Reason**: Captured from an intake wave that ran its mandated related-tickets search at triage, found nothing, and filed a ticket ninety minutes later asserting "the only cluster where the search returned nothing." A covering ticket had been created **six minutes after the search** — so the search was correct when it ran and false when it was used, and the wave filed an ~80% duplicate. The same wave separately verified that a kit file resolved, then had the contract change under it twice. Both failures are one shape: a point-in-time observation quoted as a standing fact. This bites hardest where a project's build loop outruns its reporting loop, which is exactly where waves are most useful.

*   **¶INV_PROVE_THE_SEARCH_COULD_SEE_IT**: A search returning zero is not absence until you know the search could have seen a hit. An instrument answers truthfully about a narrower question than the reader takes it to be answering, and a negative is the one result nobody re-checks, because it reads as reassuring.
    *   **Rule**: Before a zero becomes a claim — in chat, a report, a ticket, a brief, or a decision that some work is unnecessary — name the string that would have produced a hit and confirm the instrument could have produced it. A negative you cannot back that way is reported as "not established", not as "none".
    *   **Prohibited**: Relaying an unproven zero as an absence ("nothing imports it", "no readers", "no callers left"). Citing a search count as evidence about behavior without opening one match. Reading a pipeline's exit status as the verdict of the command that mattered.
    *   **The tells, because the rule above names a class and nobody recognises themselves in a class**:
        *   **Spelling** — the pattern has to match the tree's bytes, not the name in your head. A count of `from "zod"` found six files; the tree's specifier is `zod/v4`, which 250 more files carried. Search the shortest distinctive stem first, then narrow.
        *   **Visibility** — the tool has to be able to read the file at all. `grep` treats a file holding a raw control byte as binary and skips it, and `grep -c` then prints nothing and exits 1 — indistinguishable from "this file does not contain it". Use `grep -a`, and when one file is load-bearing, confirm it appears in what the search actually walked.
        *   **Code, not prose** — when the question is about behavior, the match has to be code. A `LEFT JOIN` sitting inside a docblock is not a reader of that table.
        *   **A line filter on a stream that carries content** — `grep -v node_modules` READS as a path filter and is not one. `grep -rn` emits `path:line:CONTENT`, so the filter is handed prose as well as paths and cannot tell them apart: **it drops any SOURCE line whose own text mentions the excluded word**, and a dropped line leaves no gap, so the undercount is invisible. **A line filter is only safe on a stream carrying nothing but paths** — `find | grep -v` and `git status --porcelain | grep -v` are fine; `grep -rn | grep -v` and `git grep | grep -v` are not. Use `--exclude-dir` where the tool has one; `find` has none, which is why the rule is about the STREAM rather than about a flag. Captured from a sweep that counted seventeen stale pointers and a second lane that re-measured and also counted seventeen: **the file its own command could never return was the file it had named**, because that file mentioned `node_modules` in the very line carrying the defect. **Two runs of one blind instrument agreeing is not corroboration.**
        *   **A truncated list read as an absence** — if the conclusion is *none*, the command ends in `wc -l`, never `head`. You cannot establish that something is not there by looking at part of the list. Captured from a seat that ran a search, got sixteen hits, piped them through `head -20`, read the first thirteen lines, saw only the wrong file type and filed *"set nowhere"* into an escalations file. It did not have a zero and disbelieve it; **it had a truncated list and read absence into the part it never saw.**
        *   **Exit status through a pipe** — a pipeline's `$?` is the LAST command's status, not the gate's. `cmd | tail -30` exiting 0 is `tail` succeeding, and says nothing about `cmd`. Read the printed verdict, or redirect to a file and read `$?` from the command itself; `PIPESTATUS` is not a portable substitute (it is empty under zsh).
        *   **An anchor the writer moves** — `^## 💡 Decision` pins the glyph to the start of the heading, but the writer inserts a stamp there: `engine log` injects `[YYYY-MM-DD HH:MM:SS]` between `## ` and the glyph, so the anchored pattern sees only the unstamped minority — **12 of 47 on one log, 6 of 61 on another, measured on two corpora.** Anchor on what the writer cannot move (`^## .*💡 Decision`). **The second half is the one that bites: a control sharing the anchor shares the blind spot, undercounts identically, and the pair reads as healthy.** A control must differ from the instrument in SHAPE — a token split where the instrument is a regex — not merely in the string it looks for. **The test, when "shape" is arguable**: name a way your control could fail that your instrument could not. If you cannot name one, you have run the instrument twice.
        *   **An escape the regex engine does not have** — `git grep -E` is POSIX ERE, which has **no `\b`, `\s`, `\d` or `\w`**, and it does not reject them: it **matches nothing and exits as though the pattern were simply absent**. So `git grep -nE "(const|function)\s+name\b"` is indistinguishable from "this declaration does not exist". Use `-P` for those escapes, or spell the gap as `[[:space:]]`. Measured: that exact pattern returned silence for a symbol a plain `git grep` then found in 18 files. The same trap is the reason a tool's own docs are worth reading before its zeros are believed — in this instance the repository under review documented the behaviour in its contract file, and the agent committed the failure while reading that entry, catching it only on the control.
    *   **Redirection**: Instead of trusting a zero, run a positive control — the same instrument, same invocation, against a case you know should match. An empty control means the instrument does not discriminate and the zero carries no information. One extra command, and it is the technique that caught these.
    *   **Its pair, for hits rather than zeros**: `§INV_PROVE_EVERY_QUOTATION_AGAINST_THE_FILE`. A positive control proves a zero; a grep at the cited path proves a quotation. Lanes that hold this rule alone run controls on every absence and none on the sentences carrying their findings.
    *   **Distinct from `§INV_POINT_IN_TIME_CHECKS_EXPIRE`**: that one governs a check that was true when it ran and stale when it was used; this one governs a check that could never have seen its subject. Re-running fixes the first and does nothing for the second. Worked catalogues of both live in PITFALLS.md — `§PTF_A_ZERO_IS_NOT_EVIDENCE` (pattern shape) and `§PTF_PROVE_THE_INSTRUMENT_RAN` (instrument aimed elsewhere, or never run).
    *   **Reason**: One evening, one shape, four false findings across four seats — each believed for a while, each caught by somebody re-measuring rather than re-reading, none caught by a tool. A dependency count that saw 6 of 256 hits, on which a lane was briefed to remove a package the tree uses throughout. A security finding citing three live readers of a table where all three were comments — one past tense, two stating the query does *not* join it — promoted to the top of a leftovers file, then retracted. Sixteen raw control bytes across eleven tracked TypeScript files, which left every grep-based audit of that repository with an eleven-file hole that reported as clean absence. And a gate called green because its output travelled through `tail`, so the shell reported `tail`'s status; other lanes in the same session admitted the same habit on gates they had already quoted. Those four are a sample — the same session catalogued a further dozen variants, among them registry indirection hiding a component that was mounted by name, and ANSI colour codes between a grep and its count.

## 15. Evidence Practice

*   **¶INV_NEGATIVE_CASE_IS_THE_NEAREST_NEIGHBOUR**: A check's negative case must be its **nearest legal neighbour**, not a distant stranger.
    *   **Rule**: When a guard accepts exactly one thing and refuses others, the case proving it refuses must offer the closest legal alternative — the sibling in the same set, the adjacent enum member, the neighbouring capability. A negative case built from something obviously unrelated proves the guard refuses *that*, and nothing about what it will actually be handed.
    *   **Prohibited**: proving a verb check by offering a verb from a different family; proving a type guard with a value no caller could produce; proving a permission refusal with a principal that fails three other checks first.
    *   **Redirection**: ask what the wrong-but-plausible input is — the one a caller would reach for by mistake — and make that the case. If the guard accepts a set, iterate the set rather than listing literals, so a new member inherits the case.
    *   **Reason, measured**: a warrant's verb check was pinned only against an ordinary read verb. Widening it to accept any member of the capability set — so a delete capability would act as a browse warrant — **survived 989 cases**. The property the whole design existed to establish had no case that could see it fail.

*   **¶INV_A_KNOWN_DEFECT_SHIPS_AS_A_SKIPPED_CASE**: When you find a defect you are not fixing, write the case **against the rule** and skip it, with the condition that un-skips it in its docblock.
    *   **Rule**: Do not write a case against the behaviour you found — that encodes the defect as an expectation, and the next reader cannot tell a deliberate rule from an accident. Do not leave it as a paragraph in a report either: reports age into folklore, and the person who fixes it will re-derive the assertion from prose.
    *   **Redirection**: ship the assertion, marked skipped, with the argument and the un-skip trigger beside it. The fix lane then inherits an assertion rather than an argument.
    *   **Reason, measured**: a lane found the warrant refusal wrong on the arm every write reaches, and shipped a skipped case written against the rule. The obvious one-clause fix **still failed that case** — it left an equivalent-but-not-identical statement where the case asked for identical — so the code was changed to meet the case rather than the case adjusted to meet the code. A paragraph would have been satisfied by the wrong fix.

*   **¶INV_AN_EXCEPTION_CARRIES_ITS_EXPIRY**: A deliberate carve-out is written with the condition that makes it wrong.
    *   **Rule**: When you leave something ungated, unenforced or special-cased on purpose, record in the code both the reason it is safe today and **the specific change that would end that safety**. A carve-out whose premise is unstated cannot be re-examined, and becomes folklore the first time its premise moves.
    *   **Redirection**: name the trigger, not the feeling — *"the day this enters the public surface"*, not *"revisit if things change"*.
    *   **Reason**: a pure function was deliberately left ungated because it is the oracle the generated SQL is held to, and gating it would make the oracle depend on what it verifies. Its docblock names the day that decision expires: the day it is exported. Without that line, the next reader either "fixes" it or inherits it unexamined.

*   **¶INV_A_PROJECT_INSTRUCTION_GOVERNS_THE_REPO_IT_LIVES_IN**: An agent instruction file governs the repository it sits in, and no other. When a session's WORKING repo differs from the repo its directives were loaded from, resolve the target repo's own directives before writing any brief, and name the file each cited rule came from.
    *   **Rule**: Before putting a rule in a brief, establish that the rule reaches the code the brief touches. A `CLAUDE.md` or `AGENTS.md` loaded at session start governs its own repository; carrying it into a brief for another one imposes a rule nobody there agreed to, and a builder will follow it faithfully.
    *   **Redirection**: cite the path — *"per `<repo>/CLAUDE.md` § Code Comments"* — rather than *"the project directives say"*. A rule with a path is checkable by the agent receiving it; an unattributed one is not, and the builder has no way to notice it does not apply.
    *   **Why it evades every existing check**: the wrong rule arrives as AMBIENT CONTEXT, correctly loaded, for the repo you are standing in. Nothing marks it as scoped. It is not stale in TIME — it was true when read and is true where it was read — it is stale in PLACE, which no re-run detects because re-running produces the same answer.
    *   **The tell**: a session whose artifacts live in one repository and whose work lives in another. That is the configuration, and it is common for any session directory kept outside the code it works on.
    *   **Reason, measured**: a brief told a builder *"the project directives forbid narrative history in comments"*, citing a rule from the session-artifact repo. The working repo had no `CLAUDE.md` and no `AGENTS.md` at any depth. The builder complied, and the compliance **stripped the evidence line out of the one docblock whose job was to carry it** — every sibling of that file records `✅ MEASURED before the swap` with the evidence for why a type swap was safe, and the rewritten one recorded nothing. The house register was not a style preference; it was where the proof lived.

*   **¶INV_A_CORPUS_IS_DESIGNED_AGAINST_THE_MECHANISM**: A test corpus must contain the cases where two behaviours CAN diverge. Sampling more of the obvious cases is not coverage of the question, because the obvious cases are the ones that agree.
    *   **Rule**: When two implementations must match — a reference and a compilation, an interpreter and an engine, a driver and the thing it drives — the corpus is built from where they are ALLOWED to part company, not from the input space. Ask what makes them differ, then sample that. "We tested many values" is not "we tested the discriminating values".
    *   **The cost is not a missed defect — a green suite RETIRES THE QUESTION.** Nobody re-opens a question that has an instrument reporting clean, so a corpus that cannot see the divergence is worse than no corpus. It converts an open question into a settled one with the wrong answer.
    *   **Redirection**: name the mechanism of divergence first and let it pick the cases. *Negative halves* because the divergence is a sign rule; *mid-travel starts* because it is an engine normalisation; *a second engine* because the behaviour is engine-specific. None of those is reachable by adding values.
    *   **This is `§INV_NEGATIVE_CASE_IS_THE_NEAREST_NEIGHBOUR` at corpus scale**, and it recurses: every axis you do not vary is an axis your suite is silent over.
    *   **Reason — ONE finding with three witnesses, recorded together because three local fixes would make every symptom vanish and leave the rule missing with its evidence gone**:
        *   **Arithmetic.** `Math.round` against half-away-from-zero (what both SQLite and PostgreSQL do) disagrees on **0 of 4** positive halves and **4 of 4** negative ones. A differential suite built from positive halves returns a clean 100% and certifies the two as matching.
        *   **No arithmetic at all.** A caret defect — arrow keys walking *inside* a folded span instead of stepping over it — survived every existing driver, all green, none wrong, because every one of them placed the caret at the span's boundary before pressing: the single starting position from which the defect cannot occur. It was found by a person walking a line press by press.
        *   **One level up again.** A census of that same behaviour across three engines found it Chromium-only, so even a corpus sampling mid-travel starts is silent over the engine axis.

*   **¶INV_AN_ASSERTION_WHOSE_SIDES_CANNOT_DIVERGE_IS_NOT_COVERAGE**: Before an assertion counts as coverage, name the input that would make it fail. An assertion whose two sides are computed from the same source can never fail, and **a dead assertion is worse than a weak one — it reads as coverage and is not**, with nothing in a green run to tell them apart.
    *   **Rule**: When you write a comparison, ask what would have to be true for it to go red. If you cannot answer, it is not an assertion; delete it or replace it with one that can fail. Reviewing is the same question asked of someone else's: for each comparison, where could the two sides part company?
    *   **The tell**: both sides derive from one artifact. Comparing a file's parsed contents against a table that lives *inside that file*; asserting a derived set covers the set it was derived from; checking a value against a constant recomputed by the same expression that produced it. Each looks like a check and is an identity.
    *   ⛔ **"Both sides name the same identifier" is the wrong test, and a grep written from it deletes good assertions.** The same function applied to DIFFERENT inputs — `expect(countsOf(swapped)).toEqual(countsOf(original))` — is an **invariance** check, one of the strongest shapes there is. **The test is whether the two sides CAN DIVERGE, not whether they share a name.**
    *   **Redirection**: plant the failure. Break the thing the assertion is supposed to notice and watch it go red, then restore. An assertion you have never seen fail is a claim, not a check — and this takes a minute on the assertion you just wrote, while it is still cheap.
    *   **Distinct from `§INV_PROVE_THE_SEARCH_COULD_SEE_IT`**: that one governs an instrument aimed where its subject is not. This one governs an instrument that is aimed correctly and cannot report. Re-running fixes neither.
    *   **Reason, measured**: a gate whose floor was meant to stop a citation regex from passing vacuously was written as `citedFiles(SELF).size >= citedFiles(TABLE).size` — and the table's text is part of the file the left side scans, so the left is always a superset of the right. It passed, which is how it was nearly missed; it was caught by asking what would falsify it rather than by running it. **A peer offered the same assertion back within minutes of being told about the trap**, which is the measure of how natural the shape is: the warning does not inoculate, because the tautology is invisible until somebody asks for the failing input. The replacement asked a question with a possible no — does the file carry MORE citations than its table does — and a planted dead regex reddened it.

*   **¶INV_A_COMPARISON_NOBODY_PERFORMED_IS_NOT_ESTABLISHED**: Comparing two small sets by eye is reading, not measuring. Before any claim of the shape *the only*, *shares N*, *both*, *none of these*, *all of them*, compute the comparison and quote the command. **And agreement does not substitute for it: N readers agreeing about a comparison none of them performed is weaker than one who ran it, because agreement raises confidence without touching certainty.**
    *   **Rule**: a quantifier over two or more sets is a computation. Write it as one — an intersection, a set difference, a count — and keep the command beside the claim so the next reader can re-run it rather than re-read it. If the sets are short enough that computing feels like overkill, that is the condition this rule names, not an exemption from it.
    *   **The tell, because nobody recognises themselves in the category**: *the lists are short enough to hold in your head.* That is the whole trap. A long list makes you reach for a tool; five items invite you to look, and looking returns an impression that is indistinguishable from a result. The failure never feels like skipping a measurement — it feels like having read carefully.
    *   **Prohibited**: citing other people's agreement as the check. "Two reviewers confirmed it" says two people read it; it says nothing about whether anyone ran it. When a fact arrives already agreed, ask who computed it — and if the answer is nobody, it is unestablished no matter how many hold it.
    *   **Redirection**: do not re-read the lists more carefully. Print them and intersect them. One line of code, and it answers a question re-reading cannot.
    *   **Distinct from its neighbours**: `§INV_PROVE_THE_SEARCH_COULD_SEE_IT` governs an instrument aimed where its subject is not; `§INV_AN_ASSERTION_WHOSE_SIDES_CANNOT_DIVERGE_IS_NOT_COVERAGE` governs one aimed correctly that cannot report; `§INV_POINT_IN_TIME_CHECKS_EXPIRE` governs one that was right and went stale. **This one governs an instrument that was never picked up.** Re-running fixes none of the others and there is nothing here to re-run.
    *   **Reason, measured**: a published contract entry claimed a word was *"the only word the two vocabularies share"* — while **listing a second shared word three words earlier in its own sentence**, and while a third vocabulary containing it was documented four lines above. A probe said one shared word; the package's owner independently re-derived the facts and said one; the commit said one. **Three readers, one count, zero computations**, and the author's own session log printed the five-item list and the false count one sentence apart. Computing it took one command and gave four intersections, one of which made the claim true in a stronger form — *the only word all three carry*. The same three reviewers who had agreed the false version was right each went to the files for the correction and caught a further overstatement in it.

*   **¶INV_ESTABLISH_THE_SUBJECT_IS_IN_SCOPE_OF_THE_CHECK**: An instrument aimed correctly at a subject it is **structurally unable to report on** returns the reassuring answer unconditionally. Before a check's silence counts as a pass, establish that the subject is one that invocation can speak about at all.
    *   **Rule**: For any clean result you are about to cite, name the condition under which that exact invocation would print something, and confirm the subject satisfies it. A check silent over the subject's whole class carries no information about this subject; its pass is reported as "not established", not as a pass.
    *   **The measured instance, and it governs most session work**: `git status --porcelain -- <path>` on a **gitignored** path prints nothing and exits 0 whatever that file contains, and `git show HEAD:<path>` simply fails there. Session directories are routinely gitignored, so the discipline *check the path is clean before citing it* has no failing arm on any session artifact — and session artifacts are most of what a lane cites. Found independently by two lanes hours apart, on two different ignored paths.
    *   **Redirection**: establish TRACKED before you read CLEAN. `git ls-files --error-unmatch -- <path>` exits non-zero on an untracked or ignored path, and `git status --porcelain --ignored -- <path>` prints `!!` for an ignored one; tracked and silent is clean. Where the path is not tracked, write the gap into the citation — *"untracked path; provenance not established by git"* — and cite the provenance that does exist (the owning lane's log, the mtime, the quotation you pulled) rather than cleanliness you never measured.
    *   **A positive control does not catch this one unless it sits inside the subject's class.** The same `git status` invocation against a tracked dirty path prints output and certifies the instrument discriminates — while still being blind to every ignored path. Control on a subject of the same class, or the control is decoration.
    *   **Distinct from its neighbours**: `§INV_PROVE_THE_SEARCH_COULD_SEE_IT` governs an instrument aimed where its subject is not; `§INV_AN_ASSERTION_WHOSE_SIDES_CANNOT_DIVERGE_IS_NOT_COVERAGE` governs an assertion whose two sides cannot part company; `§INV_POINT_IN_TIME_CHECKS_EXPIRE` governs one that was right and went stale. **This one governs an instrument aimed correctly whose reporting channel does not cover the subject's class** — the failing arm does not exist, so there is nothing to re-run and nothing in the output to say so.
    *   **Reason**: a clean-path check was the provenance backstop under a whole published set, reporting clean on every artifact it was pointed at. A check that cannot fail reads as the strongest evidence available, because nothing in its output distinguishes *verified clean* from *out of scope*.

*   **¶INV_PROVE_EVERY_QUOTATION_AGAINST_THE_FILE**: A quotation carrying a finding is proved against the file at the path you name, in the invocation that produced the finding. This is the explicit pair of `§INV_PROVE_THE_SEARCH_COULD_SEE_IT` — that one proves an absence, this one proves a hit — and an agent holding one without the other controls its zeros and never its evidence.
    *   **Rule**: Before a quoted string appears in a report, ticket, brief or review card, grep it in the cited file and keep the hit count beside it. A quotation you cannot produce a hit for is reported as "not found at that path", never as the file's words. A number read off a rendering — a type size, a colour, a dimension — is a quotation too: name the declaration or computed value it came from.
    *   **When the grep returns 0, suspect the pattern before the file.** A mis-transcription and a missing sentence print identically. Re-run on the shortest distinctive stem, case-insensitively, before concluding the sentence is absent — and note which run found it, because *present with different casing* and *absent* are different findings.
    *   **Redirection**: paste from the file into the finding instead of typing the sentence you remember, and let the grep that found it stand as the citation. Memory reconstructs plausible text — right in substance, wrong in bytes — which is the one error no downstream reader can detect.
    *   **Reason, measured**: two decisive quotations in a review panel's findings were in no file — 0 hits each, against a same-invocation positive control of 9 and 4 for the identical pattern — and a type size carrying a third finding came from somewhere other than the file. Both lenses had run positive controls on their zeros; neither ran one on a quotation. **The rule caught its own author within the hour**: the report announcing it quoted a page's sentence lower-case where the page capitalises it, so a case-sensitive grep returned 0 and a case-insensitive one returned 1. The finding stood; the transcription did not.

*   **¶INV_THE_OWNER_OWNS_THE_SEMANTICS_NOT_THE_MECHANICS**: A correction from the owner of a type, package or area is authoritative about **meaning**. It is not automatically authoritative about **which function returns which shape**, which file holds a symbol, or what a call site does. Take the semantic half; keep your own measurement of the mechanical half, or ask.
    *   **Rule**: When an owner corrects you and their phrasing also restates a mechanical fact you measured yourself, the two halves separate. Adopt the meaning. Re-check the mechanics, or say which half you are taking. Ownership confers standing over intent and vocabulary; it confers no exemption from being wrong about a signature.
    *   **Prohibited**: replacing a reading you took from the source with a peer's wording because the peer owns the subject. Writing an owner's sentence into a docblock, commit message or brief without separating what they ruled from what they described.
    *   **The tell, and it is a feeling rather than a category**: *relief.* An owner's correction arrives as the end of an uncertainty, and the natural move is to take all of it at once. The failure does not feel like discarding evidence — it feels like deferring appropriately. **If you measured something and the correction contradicts it, that contradiction is a finding, not a settled question.**
    *   **Redirection**: reply with the split — *"taking your reading of what it means; my own check says `run()` is declared to return X, so I am keeping that clause and here is the line."* An owner handed a measurement usually confirms or corrects it in one message, which costs a round trip and buys a fact.
    *   **Distinct from `§INV_POINT_IN_TIME_CHECKS_EXPIRE`**: that one governs relaying a peer's fact you did not run. **This one governs discarding your own fact that you did run**, in favour of a peer's. It is strictly worse, because the evidence existed and was overwritten.
    *   **Reason, measured**: an agent's own session log had recorded, correctly and hours earlier, that `run()` carries a parked-stage field while `{kind:'waiting', parked}` is what a *different* function answers. A peer who owns the type narrowed a genuine overstatement in the agent's docblock; the agent adopted their phrasing wholesale, and the adopted sentence merged the two functions. The landed docblock then told readers that the wrong function returns the envelope — in a docblock whose entire subject was distinguishing two vocabularies that share a word.

*   **¶INV_A_SATISFIED_PRECONDITION_IS_NOT_A_REASON_TO_ACT**: Meeting the condition you wrote down only removes a reason **not** to act. It is never, by itself, a reason to act. Before acting, re-establish that the action is still the right one.
    *   **Rule**: When work has been held, deferred or blocked on a named condition, and that condition is later met, the decision to proceed is a fresh decision. Verify the action's own premise — that the change is still needed, still correct, and not already done — rather than treating the unblocking as an instruction.
    *   **Prohibited**: "the blocker cleared, so land it." Reading a hold's stated condition as the complete set of reasons the work was not done. Quoting your own earlier note as authority for an action taken later.
    *   **The tell**: you are about to act and the only new information is that something stopped being false. Nothing has told you the action is right; something has merely stopped telling you it is wrong.
    *   **Redirection**: ask what would make the action wrong TODAY, and check that instead of the condition. For a held branch the cheap version is one command — compare patch-ids against the target, since work can land by another route while you wait.
    *   **Reason, measured**: a six-commit branch was held on one named condition, which a later check confirmed met, with a committed test proving the behaviour. Acting on that would have been a mistake: **five of the six commits were already byte-identical at the target by `git patch-id --stable`**, and the sixth carried an identical commit subject and an identical `10 files, +328/−215` diffstat while differing in content — the target's version held four exports and three docblocks the branch predated. Landing would have deleted them. The hold's stated condition and the hold's real condition were different things, and satisfying the stated one carried no information about the branch.

*   **¶INV_ASK_THE_REPOSITORY_BEFORE_ASKING_THE_CODE**: Before investigating whether something is true, search the repository for whether somebody already established it. The expensive failure is not the duplicated work — it is that **a rediscovered answer arrives with full confidence and no provenance**, so nobody downstream can tell it has been learned and lost before.
    *   **Rule**: When you are about to open an investigation — a sweep, a measurement, a "does X happen" question, a doc fix — spend one search first on the repository's own prose: its instruction files, its `.directives/`, its runbooks, the docblock of the function in question, and the test that exercises it. Cite what you find, or record that you looked and found nothing. A finding filed without that line is a finding whose history nobody can reconstruct.
    *   **The tell, and it is a feeling rather than a category**: *this is quicker to measure than to look up.* Often true, and it is exactly the trade that strips the provenance off the answer. The failure never feels like skipping a search — it feels like being efficient.
    *   **Prohibited**: filing an invariant, pitfall or doc change whose subject already has a written home, without naming that home. Writing a second copy of an existing warning — on a page whose length may be the actual defect, a duplicate makes the measured problem worse by its own mechanism.
    *   **Redirection**: do not resolve to read more documentation; nobody does. Search for the *subject* at the moment you name it — `git grep -i` the distinctive noun across `*.md` and docblocks, with a positive control — and put the result in the finding either way. One command, and it is what converts a rediscovery into a citation.
    *   **The sharpest form is when the rediscovery would SHIP.** A rediscovered belief costs a lane. A rediscovered *fix* reaches the file and competes with the original.
    *   **Distinct from its neighbours**: `§INV_POINT_IN_TIME_CHECKS_EXPIRE` governs a fact that was true and went stale; `§INV_PROVE_THE_SEARCH_COULD_SEE_IT` governs an instrument that could not see its subject. **This one governs a question that was already answered, in writing, in reach.** Re-running fixes neither of the others and there is nothing here to re-run — only something to read.
    *   **Reason, measured — four instances in one session, which is why it is a rule and not an anecdote**: a 384-line landing protocol, opening *"For an agent or a teammate who has finished a change and is about to publish it"* and linked from the first file an agent reads, went unread through four landings and an undeclared divergence from it. A flaky-suite question was answered by one sentence in the asker's own package, with the house remedy on the line below it. A false-zero trap — *"the tag spans lines"* — was catalogued in an instruments doc, and a lane was spent rediscovering it. And a reference page's documented parse trap, carrying the failing form with its exact error message and two corrected forms as **executed** examples, was about to receive a second copy of itself; that page's length is a live candidate for why its readers miss line 405 of 730, so the duplicate would have worsened the thing it was aimed at.

*   **¶INV_A_RULE_IN_PROSE_IS_NOT_ENFORCED_UNTIL_A_CHECK_CAN_FAIL**: A rule written in a protocol, docblock or directive is **documentation of an intention**, not enforcement of it. Until some invocation can go red because the rule was broken, the rule is unenforced — and the subtlest version of this is a detector that finds the violation correctly and **reports it at a severity that cannot fail**.
    *   **Rule**: When you state a rule that matters, name the invocation that fails when it is broken. If there is none, say so where the rule is stated — *"stated, not enforced"* — so the next reader does not mistake prose for a gate. A finding emitted as a warning is a notification, and nothing downstream distinguishes a warning nobody read from a warning nobody needed.
    *   **Prohibited**: citing a documented rule as the reason a class of defect cannot occur. Treating a clean run of a non-blocking check as evidence the rule holds. Writing the rule more emphatically — capitals, ⛔, *MUST* — in place of giving it a failing arm; emphasis is what gets reached for when enforcement is the actual gap, and it measurably does not substitute.
    *   **The tell**: the rule is stated by an author who plainly understood it, with its mechanism, in the right file — and you cannot answer *"what command goes red?"* without pausing. Correctness of the prose is not the variable; **severity is**.
    *   **The sharpest form, and it is the one that hides**: a warning-severity check goes **silent by itself** when the last known instance is removed. From that moment its output is indistinguishable from a passing gate's, so the gap is invisible exactly when someone is most likely to call the matter closed. ⚠️ **Removing the instance is the moment to raise the severity, not the moment the need goes away** — the detector is now structurally unable to fail on the next violation anyone introduces, and there is no longer an example on disk to notice that by.
    *   **Redirection**: move it into the failing set in the same change that removes the last offender, rather than resolving to do it later. Where it genuinely cannot block yet, write the carve-out with its expiry per `§INV_AN_EXCEPTION_CARRIES_ITS_EXPIRY` **and** leave a skipped case asserting the rule per `§INV_A_KNOWN_DEFECT_SHIPS_AS_A_SKIPPED_CASE`, so the fix lane inherits an assertion instead of a paragraph.
    *   **Distinct from its neighbours**: `§INV_AN_ASSERTION_WHOSE_SIDES_CANNOT_DIVERGE_IS_NOT_COVERAGE` governs an assertion aimed correctly that cannot report; `§INV_ESTABLISH_THE_SUBJECT_IS_IN_SCOPE_OF_THE_CHECK` governs an instrument whose reporting channel does not cover the subject's class. **This one governs a check that sees the violation, reports it accurately, and carries no consequence.** A positive control passes on all three, because in every case the instrument genuinely fires.
    *   **`§INV_AN_EXCEPTION_CARRIES_ITS_EXPIRY` is satisfiable while this one is still violated**, which is why both exist: naming the condition that ends a carve-out does not make anything happen when that condition arrives. An expiry with no trigger is a note to a reader who is no longer looking.
    *   **Reason, measured — ONE**: a gate enumerating workflow files carried a docblock (`scripts/workflows-name-live-workspaces.mjs:224-237`) establishing that GitHub reads workflows only at the repository root, so a `.github/workflows/*.yml` nested inside a package *"has never executed and never will"* — and that the detector had been root-anchored and non-recursive, making *"the single structurally dead workflow in this repository the single workflow it could not enumerate"* (`:229`). The author then declared the finding **⛔ *"REPORTED AS A WARNING AND NOT AS A FAILURE, ON PURPOSE AND NOT IN ORDER TO REACH GREEN"*** (`:231`) because the gate sits in a blocking position and failing would redden every push over a file nobody was being asked to repair in the same breath — correctly naming its own expiry: *"Move it into `failures` the moment that decision is taken"* (`:236`). **The decision was then taken and the file deleted**, which is the point: the carve-out's own stated premise, *"`docs/.github/workflows/pages.yml` is live on disk today"* (`:232-233`), became false. Nested workflows now measure **0** (positive control: the same traversal sees **12** root workflows, so the zero is absence and not a broken walk), so the warning is silent — and the gate remains structurally unable to fail on the next nested workflow anyone adds, with nothing in its output to say so and no example left on disk to notice by. The right rule, in the right place, by an author who understood it, and still not enforced.
    *   **Reason, measured — TWO, the same shape with the check outliving its own prose**: a docblock claimed **"EQUALITY IS CHECKED, NOT CLAIMED"** while the script it named, `idea:parity`, returned **0 hits in any `package.json`** — one commit had dropped the script entry and a second had deleted the file. Control `idea-script` over the same directory → **11**, so the zero was absence. A prose claim that a check exists, outliving the check by two commits, and rewritten to say what was true: *"NOTHING CHECKS THIS READING AGAINST THE LANGUAGE'S"*.

*   **¶INV_A_CONTROL_DRAWN_FROM_WHAT_YOU_JUST_FIXED_IS_NOT_A_CONTROL**: A positive control must come from a source **the fix never touched**. When the control string and the search pattern both trace back to the edit you just made, the control fires tautologically — it confirms your edit landed, and says nothing about whether the instrument can see an instance you did not create.
    *   **Rule**: After curing a class of defect, the control for *"the class is now absent"* is an **uncured member of that class** that the pass did not produce — ideally in the same subject file, else in a sibling the pass was not allowed to touch. Ask of every control: *which arm of this did my edit author?* If the answer is both the pattern and the control case, you have measured your own diff.
    *   **Prohibited**: writing the strings you just removed into a temp file and grepping them back. Building the search pattern out of the exact phrasings you deleted, then reporting the resulting zero as coverage of the class. Both are the same error wearing the clothes of rigour.
    *   **The tell, and it is why this one survives careful people**: the control **passes**, and a passing control is the thing you reached for in order to be careful. Nothing in the output marks it as circular. **The measurement is where you are careful; the control is where you are casual — and a casual control is worse than none, because it reads as rigour.**
    *   **The pattern is the second half of the trap.** A pattern derived from the five phrasings you cured is a pattern that can only ever find those five. It will return 0 forever, on any file, in any state of the world, including a file full of the defect expressed in a sixth phrasing. **State what the pattern asked**, and prefer one written from the *class* — a count-word followed by a plural noun — over one written from the instances.
    *   **Redirection**: before you cure anything, find one instance you are deliberately **not** fixing and keep it as the control. Costs nothing at the time, and it is the only control that can still discriminate after the pass. Where none exists, say the claim is about the instances you fixed, not about the class.
    *   **It generalises past strings to *the thing versus a nearby word*.** A control that fires on a word adjacent to your subject controls for the word, not for the subject. The operative clause: **the control must discriminate the THING, drawn from a source the fix never touched.**
    *   **Distinct from its neighbours**: `§INV_PROVE_THE_SEARCH_COULD_SEE_IT` says run a control on a zero at all — this one governs *which* control, and is the failure mode of complying with that rule carelessly. `§INV_NEGATIVE_CASE_IS_THE_NEAREST_NEIGHBOUR` governs a guard's refusal case; this governs a search's firing case. `§INV_AN_ASSERTION_WHOSE_SIDES_CANNOT_DIVERGE_IS_NOT_COVERAGE` governs an assertion that cannot report; **here the control reports, correctly, about the wrong question.**
    *   **Reason, measured**: a lane removed stated counts of enumerated things from a skill (five phrasings: `Run all eight`, `the four checks a map needs`, `the eight-check gate`, `Four of its rules`, `Eight checks`), because adding a ninth gate check would have left every count stale. The claim *"the gate is now count-free"* was then posted **publicly on a ticket**, evidenced by a `grep -nE` whose alternation was **built from those same five phrasings**, returning 0 — with a positive control that *"writes those same strings to a temp file and greps them back — so it proves the regex finds its own targets, not that it could see a stated count anywhere else"* (`builds/CRITIQUE.md:26`). The author's own record of it: *"The pattern matches only the five phrasings the lane had just deleted, and my control wrote those same five strings to a temp file"* (`LOOM_LOG.md:8607`), diagnosing the class as *"my positive control sat INSIDE the subject's cured class"*. **Re-measured with a pattern not shaped around the cured strings, two stated counts survived in the same file** — `prove-explore/SKILL.md:39` *"Two rules, both enforced at the gate:"*, which is about the gate itself and therefore the exact subject of the claim, and `:204` *"four named sub-questions"*. Those two were the available nearest-neighbour control all along: same class, same file, untouched by the pass. A pattern that fired on them and still returned 0 for the gate section would have supported the claim; the one that was run could not have failed.

*   **¶INV_A_NEGATIVE_ONLY_CHECK_SAYS_SO**: A check that can only establish one half of its question states which half, in its own output. Green means *nothing certain*, never *all done*.
    *   **Rule**: Where a check's design lets it show that something is **missing** but never that it is **present** (or the reverse), the pass line says so and names the unit it covers. A reader who did not write the check cannot infer the asymmetry from a clean result, and will not go looking for it — so the obligation sits on the instrument, not on the reader. This is the author-side companion to `§INV_PROVE_THE_SEARCH_COULD_SEE_IT`, which governs the reader of a zero.
    *   **Say what the unit is OWED, not what it did.** A one-sided check also has to name the population that can fail it. A register check asking "does each decision have a row" ran over every decision in a log, but the thing that owes a row is an **open obligation**, not a closed decision — so the overwhelming majority of its reds were units that owed nothing: over **47 decisions** it went red on **45**, and **43 of those 45 reds** were closed decisions that owed no row at all. Reported as "unrowed decisions", that output is a true answer to a question nobody asked; reported as "open obligations with no row", the same instrument answers the real one.
    *   **Prohibited**: a one-sided pass line phrased like a two-sided one — `0 findings`, `all clear`, `✅ consistent`. A count with no denominator. A green whose text would be identical if the check had been unable to run at all.
    *   **Redirection**: write the pass line as the sentence a sceptic would have to accept — *"no open obligation was found unrowed; this check cannot show that any row exists"* — and keep it in the output rather than the report, because the output is what gets quoted.
    *   **Distinct from its neighbours**: `§INV_ESTABLISH_THE_SUBJECT_IS_IN_SCOPE_OF_THE_CHECK` governs an instrument that cannot speak about its subject **at all**, so its silence carries nothing; this one governs an instrument that speaks accurately about **one direction** of its question and is read as having answered both. `§PTF_PROVE_THE_INSTRUMENT_RAN` governs a green that would look identical had the check never executed — which is why a one-sided pass line is prohibited from being phrased like a two-sided one: it is that same indistinguishable green, reached by a check that did run. `§INV_PROVE_THE_SEARCH_COULD_SEE_IT` puts the duty on whoever reads a zero; this one puts it on whoever writes the instrument.
    *   **Reason, measured**: a register check could prove a decision *could not* have been rowed and could never prove one *was*. It printed `0 findings, exit 0`, and that line was read as the register being complete — the same instrument that went red on **45 of the 47 decisions** it read, 43 of those reds being closed decisions that owed no row.
