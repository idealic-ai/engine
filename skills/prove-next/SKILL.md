Turn a piece of finished problem-solving into a shareable, published **proof**. `/prove` takes a **claim** you have already settled — a diagnosis, a fix, a before/after, a comparison — and hands it to a background subagent that re-establishes the ground truth, renders the *real* evidence (a PDF page, a screenshot, CLI output, an overlay, a diagram), and composes it into a legible Artifact. You then run the honesty pass and publish.

This is the **visual capstone** of the workflow family. Where `/probe` and `/analyze` *find* the answer, `/fix` *repairs*, and `/experiment` *tests*, `/prove` **shows** — it takes an already-resolved finding and compiles its evidence into an at-a-glance, defensible proof artifact. As a **building block** it produces a page, not a change: it never edits code, never commits, never files a ticket, and — the point of this skill — **never re-investigates or re-litigates the finding**. It trusts the upstream work, presents it honestly, publishes, and stops.

*The spine — non-negotiable (`¶INV_PROVE_FAITHFUL_PRESENTATION`):* `/prove` **trusts the finding and proves the *rendering*.** It does NOT re-run the analysis to re-confirm a claim's correctness — that was `/probe`/`/analyze`/`/experiment`'s job, and their verdict is taken as given (`¶INV_PROVE_TRUST_UPSTREAM`). The only verification `/prove` owns is the kind that serves the presentation: every asset on the page is **real** (rendered from the actual source, never mocked — `¶INV_PROVE_REAL_ASSETS_ONLY`), each asset **faithfully shows what its caption claims** (the render depicts the thing, and the claim doesn't outrun what the render shows), and **provenance is honest** — a claim is labeled *trusted-from-`<upstream>`* vs. *checked-here*. Nothing fabricated, nothing oversold. A beautiful page that manufactures false confidence is worse than none — but the confidence that matters here is *"this evidence is real and shown straight,"* not *"I re-proved the finding."*

*Crucial constraint:* `/prove` does NOT own a session. It reads the *active* session's context and established findings, and writes its paper trail into that session — the **dossier and the composed proof HTML into `builds/`** (durable, attachable to a Linear ticket), the **raw captured assets into scratchpad** (throwaway intermediates, since they're embedded into the HTML as `data:` URIs).

# /prove Protocol

## 1. Scope the Claim

Pin the exact thing the page must prove, before anything is rendered.

**A. The Thesis** (the one claim)
Resolve it from the arguments, else from the active session's resolved work / a sibling's report. State it as **one claim with a truth value** — not a topic, not a summary. The whole artifact exists to make *this one thing* legible.
*(Illustrative — adapt, don't copy: "Three separate PDF pages (73, 86, 93) collapsed into one estimate entity because they shared a key." / "The fix cut recap duplication from 18 rows to 0 without moving any real line item." / "Estimate A and B agree on scope but diverge $4,210, all in one room.")*
*Constraint:* If you cannot state the thesis as a single provable claim in one sentence, ask ONE `AskUserQuestion` to pin it. A vague thesis produces a page that proves nothing.

**B. The Reader & the Job** (who it's for)
Name the reader — **reviewer** / **future self** / **stakeholder** — and the single job of the page: what must this reader be able to see and trust in ten seconds? The reader drives the structure, the density, and the tone.

**C. Stakeholders & Decisions** (who must answer, and whether the page asks)
Two quick calls that shape the whole composition:
- **Stakeholders** — name the people the proof is *directed at*: who must look at a given block and answer something. Often nobody (a pure evidence page for a general reader); when it is someone, get their **initials + name** — the page marks those blocks with a stakeholder roundel and can carry a per-person progress/submit bar.
- **Decisions** — decide whether this proof **asks** for anything. Decisions are **optional**: a pure evidence proof carries none, and that is the common case. If it does ask, the *kind* is per-block, not per-page — a **Verdict** (Accept / Revise / Abstain) on a claim or finding · a **single-select** where one exclusive choice must be made · a **multi-select** where the reader picks any number of actions. Note which blocks earn one; the compose step places them.

**D. The Source Work** (the trusted finding)
Name the resolved body of work the page draws on and where its verdict lives: a `/probe` `_PROBE.md`, `/analyze` findings, a `/fix` before/after + verification, an `/experiment` VERDICT, or the active session's settled log/plan/builds. `/prove` **trusts** these — their conclusion is the input, not something to re-derive. It does not re-open the investigation, re-run the analysis, or second-guess the verdict. (It compiles and presents the evidence; it does not re-discover or re-litigate it.) If the finding itself is in doubt, that's a signal to go back to `/probe`/`/analyze`/`/experiment` — not a job for `/prove`.

**E. The Trail** (durable in `builds/`, throwaway in scratchpad)
Set:
- `<trailDir> = <sessionDir>/builds/` — the durable home.
- `<pagePath> = <trailDir>/<slug>_PROOF.src.html` — the **source**: the filled entry `idea generate` wrote, carrying `data-instance` tokens, a derived loader line, and no definitions. This is the file you author and re-edit — and it **opens**: wired, it resolves its own ideas from the library at read time and renders styled. An entry you cannot open is a source you cannot read, so check the page here first and bundle when it is right.
- `<proofPath> = <trailDir>/<slug>_PROOF.html` — the **published artifact**: `idea bundle`'s single self-contained output, copied here. **Bundling is a PUBLISH step, not a RENDER step** — it does not make the page visible (the source already is), it makes it *travel*: zero external references, correct from any directory, correct with JavaScript off, and the exact bytes the publish uploads. **Never hand-edit it** — edit `<pagePath>` and re-bundle.
- **If `<pagePath>` opens unstyled, wiring is the first thing to check, not the content.** A page whose loader line is absent renders structurally complete and entirely unstyled, with nothing in the console. **`/design` owns that sequence end to end** (`~/.claude/skills/design/SKILL.md` §3) — including when `--all` is the wrong reach.
- `<dossierPath> = <trailDir>/<slug>_PROVE.md` — the record behind it.
- `<assetDir> = <scratchpad>/prove-<slug>/` (from your system prompt's scratchpad dir) — the **raw captured assets** (PNGs, screenshots): throwaway intermediates, since they get embedded into the HTML as `data:` URIs.

Mint a short kebab-case `<slug>` from the thesis (e.g. `page-key-collision`, `recap-dup-before-after`). *Before minting:* run `ls <trailDir>` — if an existing `<slug>_*` cluster matches this work (same chunk / ticket / topic), REUSE that slug so the proof clusters with the `/build`, `/probe`, `/experiment` artifacts.

**Acknowledge:** echo your setup in exactly one line:
`Proving: <thesis> — reader: <who>; asks: <none | N decisions, directed at …>; from: <source work>; trail: <trailDir>/<slug>_PROVE.md.`

**State the spine** back to yourself: the page will show *only* real evidence, rendered faithfully, for a finding you *trust* from upstream — provenance labeled honestly, nothing oversold.

**Load the voice rules before any words are written.** The page's structure comes from the design kit; its **words** are governed by [Voice — how we write](https://app.notion.com/p/3c0c52348d1381b59818fab60aeabdd3). Fetch it now (Notion MCP `notion-fetch`, id `3c0c52348d1381b59818fab60aeabdd3`) and hold it for the rest of the run. Two of its rules bind hardest on a proof page and are checked at the gate (§3):

- **Open with subject, edges and audience.** Say what the page is about, what it is **not** about, and who it is for. A proof headed with a broad project name that is really about one narrow slice of it misleads a reader and an agent equally — that is a reported defect, not a hypothetical.
- **Report register: provenance is quiet and per-claim.** Mark the claims that genuinely need it; anything uncontested carries nothing. A page that armours every sentence reads as defensive to a colleague who already trusts you.

If the fetch fails, say so in the acknowledgement line and compose from those two rules rather than skipping them silently.

## 2. Compose the Proof — Assemble → Render → Compose

### 2.0 Resolve the library — do this BEFORE anything else in §2

**A proof page is composed from the idea library and assembled by `idea bundle`.** The page *declares* the ideas it instantiates; the bundler resolves the `requires` closure, emits the definitions in dependency order, refuses on a HARD finding or a cycle, and writes a **single self-contained HTML file**. That is the composition path, and there is only one.

🔴 **`/design` OWNS THAT PATH — resolve, contract, kind, wire, fill, bundle, gates. Read `~/.claude/skills/design/SKILL.md` and follow it; do not re-derive any of it here.** It is the single home for:

*   **§0 — resolving `<libDir>`** (`--kit` → `$IDEA_LIBRARY` → a project `.idea-library` marker → nothing resolved, said in one line, and a **stop**), plus the marker's `_known_state` note and the rule that the CLI's exit code, not your `ls`, is what says the library resolved.
*   **§1 — the composing contract** in `~/.claude/engine/skills/intake/assets/` (`PILLARS.md` · `LIBRARY.md` · `PAGE.md` · `AGENTS.md` · `HTML_WRITING_STANDARDS.md` · `FORMS.md`, plus `IDEA.md`/`MIGRATION.md`/`QUERY.md` when a page needs a unit that does not exist yet). **Fetch the contract; never carry it** — a transcription is a second copy that drifts.
*   **§2 — starting from a page KIND** (and rewriting a page that already exists), **§3 — wire**, **§4 — filling from the vocabulary the library advertises**, **§5 — authoring a unit the library lacks**, **§6 — bundle**, **§7 — the gates**.

**A brief naming a directory that is not there is the one failure this resolution order exists to remove** — and one run removes it. Take `/design`'s reading; do not substitute a hardcoded list of document names, theme names or page kinds. All three are derived on every run.

*   **When to read it here**: only on **Path B**, where you compose yourself. On Path A you do not compose — the subagent reads `/design` as its own step 0, and the subagent is the agent judged against it.

**What `/prove` keeps, because they are PROOF judgement rather than kit judgement:**

*   **a caption may not outrun its render** — §3
*   **count LOADED subresources and ANCHORS separately, and count relative `src`** — §3's zero-external-references reading, which corrects both halves; read the rule there
*   **a search for a spelling is not a measurement of a structure**
*   **colour on a proof page must encode a REAL fact**, with a `legend` that decodes it — step 4
*   **`excludes` is the half that bites**, because the corpus's most common *dishonest* block is a ratio whose denominator is unstated — a giant `94%` with no `of`

**One vocabulary fact to hold before you start, because it decides what the page can be.** The library has **no recipes file**, so there is no precondition/failure-branch table to run your evidence against; bring your own judgement and record it in the dossier. Whether a **decision page kind** exists is **not a fact to carry in this file** — `generate --list` is the only source and it is derived on every run (see step 2). Everything else in §2 is written against the CLI's contract, and whether a verb is implemented is the CLI's business, surfaced by its own exit code.

**Two execution paths — pick one; subagent is the default.** The assemble → render → compose work runs EITHER in a dispatched subagent (default) OR inline in your own context. Choose with `§CMD_SELECT_EXECUTION_PATH`:

- **Subagent (default — context-safe).** Dispatch a prover subagent so the byte-heavy work (base64 renders, big draft HTML) **never enters your context**. Use it unless a caller explicitly asks for inline — it's right when you're a context-rich orchestrator MID-session who wants a clean context, or you want the work backgrounded/parallelized.
- **Inline (opt-in — full-fidelity).** Compose the proof in YOUR OWN context — no dispatch, no self-contained brief. Take it only when the composing agent **already holds the full context AND that context is disposable or already-isolated**: a `/build` or `/probe` subagent rendering its OWN report (dispatching again throws away the context it just earned), or the main agent at **end-of-session** (the context is about to be discarded, so the byte bloat is free). The win: no brief ⇒ **no latent-space collapse** — the agent that lived the finding writes the captions, the Q&A, and the scope block at full fidelity. The cost: the render bytes live in your context, so spend this path only when that context is cheap.

> **This is a dispatch-STEP choice, not frontmatter.** Do NOT reach for `context: fork`: a forked skill runs isolated *without* your conversation history, so it yields a worse subagent, never an inline compose. Inline = doing the work here; subagent = the dispatch below. (Verified — see the `context: fork` finding.)

### Path A — Subagent (default)

**Backgroundable & parallelizable.** This sub-agent dispatch is a composable building block: it can run in the background (`run_in_background: true`) so the orchestrator keeps working, and when the evidence splits into independent strands it can be fanned out and reconciled.

The subagent does the heavy, context-bloating work — assembling the evidence, rendering the real assets, and composing the draft HTML (so the base64 blobs **never return to your context**). It writes two artifacts: the **proof dossier** (the record of every claim → its evidence + provenance) and the **draft artifact HTML**. It does NOT publish, and it does NOT re-open the investigation.

**Use the wait — don't idle.** When you background it, get a step ahead: pre-read the source finding so you know the load-bearing claims, and line up which rendered asset you'll eyeball in §3.

Build the subagent's prompt entirely self-contained — it cannot see your memory:

> You are an **evidence engineer** compiling a PROOF from a TRUSTED finding. Your job: take a conclusion that has already been established, render the REAL evidence that shows it, and compose an honest visual artifact. You do NOT investigate, you do NOT re-verify the finding, and you do NOT fix anything — the verdict is your INPUT. Your job is to *show it straight*.
>
> **1. The Thesis** — the one claim the page presents:
> - **Thesis:** `<thesis>`
> - **Reader & job:** `<reader>` — the page must let them `<the 10-second job>`.
> - **Voice:** paste the house writing rules into the brief IN FULL (the short version, the two axes, and the report-register section from Voice). The subagent has no Notion access and cannot follow a link — the rules travel as text or they do not travel.
> - **Stakeholders & decisions:** `<none | the named people (initials + name) the proof is directed at, and which blocks earn a decision + of which kind>`. Decisions are OPTIONAL — if this says none, compose a pure evidence page and skip the decision layer entirely.
> - **Source work (the trusted finding):** `<pointers: _PROBE.md / findings / before-after / VERDICT / log+plan+builds>`. Read it to learn WHAT was concluded and TRUST that conclusion — you are presenting this finding, not checking whether it is correct. If it looks wrong, say so in your return, but do NOT re-run the analysis to settle it.
>
> **2. Assemble the Evidence (trust the finding; verify only the RENDERING).** For EACH claim the page will make, find the real evidence that DEPICTS it and confirm the depiction is faithful: the render actually shows the thing, and the caption does not outrun what the render shows. **Do NOT re-run the analysis to re-confirm the claim's correctness** — that is upstream's verdict, taken as given. Record each claim's **provenance**: `trusted-upstream` (the finding's own verdict — the default) or `checked-here` (something YOU confirmed purely for the presentation, e.g. "the rendered page shows rows 12–14", "the log line quoted matches the file"). A claim with no showable evidence is either cut or carried as attributed text ("per the /experiment VERDICT: …"). Write all of this to the dossier.
>
> **3. Capture Real Assets — from the ACTUAL source, never a mockup.** Render the evidence itself and embed as `data:` URIs:
> - **PDF pages** → `mutool draw -o page-%d.png -r 150 <file.pdf> <N>` (or `pdftoppm -png -r 150 -f <N> -l <N> <file.pdf> out`). Render the real page, not a retyped table.
> - **Rendered UI / a live page** → a headless screenshot (`playwright`/`puppeteer`/`chrome --headless --screenshot`) of the actual thing.
> - **CLI / test / query output** → capture it VERBATIM (the real terminal text, the actual row counts), not a paraphrase.
> - **Overlays / diagrams / charts** → generate from real data (bounding-box overlays on the real render; a diagram whose nodes are the real entities). No lorem, no illustrative fakes, no "representative" stand-ins.
> - **There is NO third-party renderer on the page — emit diagrams as inline `<svg>` or a pre-rendered PNG `data:` URI, NEVER as a diagram-language block.** A `/prove` page is published as a **plain static file on S3** (`¶INV_PROVE_S3_URL_IS_SHAREABLE`) and loads **no script from anywhere at all** — nothing from a CDN, nothing from any external host, nothing from a sibling object, ever. **Mermaid is the trap**: `<pre class="mermaid">` renders natively inside the claude.ai *Artifact* host, so it is the natural reach and it silently degrades to literal source text here. The same applies to Chart.js, KaTeX, D3, and any other client-side renderer — none is present and none can be fetched. Either hand-write the SVG (`currentColor` for strokes and text so it inherits both themes; `viewBox` + `width="100%"` to scale; wrapped in an `overflow-x:auto` container so it scrolls inside itself rather than pushing the body sideways), or render the diagram to PNG in the subagent and embed the bytes.
> - If an asset genuinely cannot be captured, RECORD that in the dossier (`asset-failed` + why) and degrade — never fabricate a stand-in.
>
> **4. Compose the Artifact — declare, then BUNDLE, in this order (`¶INV_PROVE_COMPOSE_FROM_KIT`).** The library is the **composition contract** for a proof page, not an optional reference: a documented archetype, a documented idea vocabulary with machine-checkable clauses, and a bundler that resolves the graph. This is the house style — a blank canvas is the wrong instinct.
>
> 0.  **COMPOSE THE PAGE BY FOLLOWING `/design` — read `~/.claude/skills/design/SKILL.md` and work its §0–§4, then §6–§7.** It owns resolving the library, the composing contract, starting from a page KIND, wiring, filling from the vocabulary the library advertises, bundling, and the gates. **Everything in this brief's steps 2, 4b and 5 is a `/prove`-specific note ON TOP of that sequence, never a replacement for it.** In particular `/design` §4 is where you learn that the view resolves *this entry's* closure and not the library, that its `--json` `omitted` list is where you discover the rest, that the contract file is read WHOLE rather than sampled, and that you assert a denominator before composing. Do not re-derive any of it from this brief.
>
>     **What you bring to §4 that `/design` cannot:** the evidence decides which ideas the page needs. Name what your evidence requires, instantiate those tokens, then read the vocabulary again.
>
>     🔴 **One measured trap that bites `/prove` specifically, because a proof page is REQUIRED to carry a Questions & Answers block (step 9):** the `qa` idea **is not a Q&A block**, whatever the name suggests. A generated entry's `§ 01` use of it is a flagged contract violation carried under protest, **not a licence to do the same**. Read its own clauses before you reach for it, and see step 4 for what happened to a page that did not.
>
> 1.  **CALIBRATE THE DESIGN INVESTMENT — load `Skill(artifact-design)`.** It is how you decide how much design this particular proof warrants, and it is the counterweight to the generic gradient-card page the anti-patterns name.
> 2.  **GENERATE THE ENTRY FROM ITS PAGE KIND (`/design` §2) — this is the first thing you write.** `node <cli> generate <kind> --library <libDir> --out <pagePath>` writes the *source* page (`<pagePath>`), never the artifact (`<proofPath>`). What arrives is a **complete, already-composed page carrying `data-instance` declarations and NO definitions** — the frame, the § rhythm and the host recipe, with the definitions supplied by `idea bundle` in step 5. Fill it, delete what this proof does not need, and extend it only where the content genuinely demands it.
>
>     **Do not compose a page from parts, and do not start from a blank canvas.** A parts list plus instructions produces the minimum arrangement that satisfies the instructions — correct, tidy and *thin*. That is the recorded failure mode in this corpus, not a hypothesis, and generating from the kind is how this step forecloses it.
>
>     🔴 **A PROOF THAT ASKS (§1.C) NEEDS A KIND THAT CARRIES DECISIONS — ASK THE LIBRARY WHETHER ONE EXISTS.** `node <cli> generate --list --library <libDir>` is the only source, and it is derived on every run. **Do not carry the answer in this file and do not trust a remembered one**: this skill used to assert flatly that the library had no decision kind, and that assertion outlived the fact — which is exactly how a hardcoded answer tells an agent to stop when the truth is one command away. If a decision kind is listed, use it. If it is not, **say so and STOP rather than inventing one** — report that the page wants a kind the library lacks, name it, and compose the evidence layer only, or hand the decision back to the caller. Never bolt a decision layer onto a page kind that does not carry one.
> 3.  **Pick the archetype — seven kinds, each deciding the evidence SPINE.** The generated entry's `§ 03` carries a `SPINE SWAP` comment naming the library idea per archetype; swap in the row that matches the KIND of proof you are making:
>
>     | archetype | spine ideas |
>     | --- | --- |
>     | diagnosis | `claim-verdict` |
>     | before/after | `was-now-strip` |
>     | metric or gate | `verdict-hero-card` + `gauge-meter-row` + `confidence-band` |
>     | audit / coverage | `coverage-heatmap` + `bars-in-table` |
>     | history | `story-arc` or `phase-pipeline`, + `evidence-stack` |
>     | comparison | `split-hero` or `delta-gutter`, + `table` |
>     | recommendation | `spec-rail` or `step-flow`, + `receipt-manifest` |
>
>     **There is no recipes file and no precondition/failure-branch table** — the library has no such thing, so bring your own judgement and say in the dossier which archetype you picked and why. **Two is the floor, not the target** — a real dossier runs 3–6 specimens, each with its own `mnote` and a `.pg-flourish.minor` between.
>
> 4.  **FILL IT — `/design` §4 owns the reading and the composing rules.** Declaring the `data-instance` token is the whole of your job; step 5 resolves that name's closure and emits the definitions. Go there for the three view readings, for pasting specimens **verbatim** rather than retyping them, for reading an idea's `excludes` / `degrades to` clauses *before* you place it, for **ADD A UNIT, NEVER BEND ONE**, and for what to do when the vocabulary genuinely does not cover you. **Four rules stay here, because they are about HONESTY rather than composition:**
>
>     *   🔴 **Where a layout uses colour, the colour must encode a REAL fact** — each row tinted by its *true* owner, each cell by its *actual* verdict — and the page ships the `legend` block that decodes it. **Never colour for prettiness.** The `legend` idea's own `requires` clause (one row per mark the page actually uses) has already caught an unkeyed hue in a real page.
>     *   🔴 **The corpus's most common DISHONEST block is a ratio whose denominator is unstated** — a giant `94%` with no `of`. This is why `excludes` is the half that bites: a misuse of this kind is a structural violation sitting in the DOM, not a matter of taste.
>     *   🔴 **The Questions & Answers block (step 9) is where a proof page reaches for a unit it will bend.** Measured cost: a page that used `qa` — declared *"one `.qa-row` per thing you did NOT do"* — for the reader's questions was shredded at 390 (*trusted-upstream*, `[ARM-Bp]`; not re-checked here). **Wrap every run inside a `.qa-q` / `.qa-a` in ONE `<span>`**: `.qa-q` is `grid-template-columns:subgrid`, so each inline child becomes its own grid item and one stray `<i>` blows out the `auto` column — a rule no clause states.
>     *   **A unit you wanted and could not have is a finding for the dossier, named.** Not a stretch signed with a margin note.
> 4b. **WIRE — `/design` §3.** The step between *the page exists* and *the page opens*. `idea generate` already runs it, so a generated entry arrives wired — **run it yourself the moment you edit `<html data-instance>`, move the file, or start from a page `generate` did not write.** Never type a loader line or an import path by hand. **If `<pagePath>` opens unstyled, check this before you check the content.**
> 5.  **BUNDLE — `idea bundle` is the PUBLISH step, not the render step (`/design` §6).** A wired `<pagePath>` already renders styled; the bundler makes it **travel**. One command:
> ```
> node <cli> bundle <pagePath> --root <dir of pagePath> --out <bundleDir> \
>   --library <libDir> --report <bundleDir>/bundle.report.json
> ```
> Then copy the single emitted HTML file to **`<proofPath>`**. `/design` §6 owns what the bundler does that you must not do by hand — the transitive `requires` closure, dependency order, the refusal on a HARD finding or a cycle, `MISSING` rather than a silent drop, and why `--library` is a DERIVED source list you never type document names into. **Three consequences are `/prove`'s:**
>
>     *   **The result has ZERO external references**, so the `builds/` file renders correctly on disk, travels whole, and has **nothing for publish to resolve**. Do not add an external ref to "fix" it.
>     *   **Never hand-edit `<proofPath>`.** Edit `<pagePath>` and re-bundle. The re-bundle into the same `--out` is the guard, and both arms are observed: unchanged → `same … (already there, identical)` **exit 0**; one comment appended by hand → `REFUSE … (holds N B of different bytes)` **exit 1**.
>     *   🔴 **A green bundle is not integrity, and for a page you are about to PUBLISH the exit code alone is the weakest possible receipt.** The lint engine grades what is PRESENT — delete an entire idea and it still exits 0 and still prints `clean`. **Quote the idea COUNT and the file hash beside the exit code**, here and every later time you cite it. §3 says the same thing, but §3 runs after this step, which is too late to choose differently.
> 6.  **Attach the apparatus contextually** — only where a block earns it, and only from what your entry resolves (`--unspent` is where you find what the closure advertises and you have not placed). An affordance rail where a block has evidence, tickets, or an external ref (one consolidated popover per block, relation labels on tickets, the `¶` perma). A verdict pill + why-proven popover where a block carries a ruling — a verdict always opens onto its grounds + provenance. ## 3. Presentation-Integrity Pass (the gate)

This is where `/prove` earns its name — NOT by re-proving the finding (you trust it), but by making sure the page shows it *straight*. Read the **dossier** (not the big HTML — it keeps you lean).

**Who checks, per path.** After **Path A (subagent)**, this pass is a genuine *independent* second-pair-of-eyes — you read the subagent's dossier fresh and check its work; run it exactly as below. After **Path B (inline)**, you composed the page yourself, so this is a *self*-review and loses that independence: still run the full faithfulness / overreach / answers audit below (it catches real defects even on your own work), but because a self-check is weaker, **offer `/scrutinize`** — adversarial, independent eyes on the composed page — before publish (offer, never force: `¶INV_OFFER_DONT_FORCE_SKILLS`). The human publish gate remains the final veto on both paths.

**Check the opening states its own scope.** The page must say what it is about, what it is **not** about, and who it is for, at the top — not buried in a scope block further down. A page whose frame is wider than its content sends both a human reader and an agent down the wrong path. This is a gate: send it back rather than publishing without it.

**Eyeball the load-bearing render.** Don't re-run the analysis — but don't ship a caption on faith either. For the asset the thesis rests on, open the rendered image / quoted output **yourself** and confirm it actually depicts what its caption claims: the page you label p86 *is* p86; the rows you tinted *are* the rows the finding named; the log line you quote *is* in the log. A proof whose render doesn't match its caption is worse than no proof. Flag any caption you couldn't confirm against its asset.

**Hunt for overstatement.** Every claim on the page must be either (a) shown by a real asset, or (b) carried as attributed text pointing at the trusted upstream finding. Nothing on the page may claim MORE than the evidence shows or more than upstream established. Confirm provenance is honest — `trusted-upstream` is labeled as such; `checked-here` means someone actually looked. Cut anything that oversells — a hedge honestly stated beats a confident overreach.

**Enforce the scope block.** Confirm the page shows *what the evidence shows / what's out of scope / what rests on the trusted upstream finding*, where the reader meets it — not buried. If the pass finds a problem, direct a targeted edit to the draft (small fix inline, or re-dispatch a focused correction), then re-check.

**Audit the answers (the ten-second job).** Read the **Questions & Answers** block as the named reader would. Two checks, both of which have failed real pages:
1.  **Are these the reader's questions?** If they are the author's — "what did we learn about the method?" where the reader asked "can I turn it on?" — the page fails its job no matter how well it argues. Rewrite the questions, not the evidence.
2.  **Does each answer outrun its evidence?** Trace every answer to a ledger claim. A confident "yes" resting on a partly-circular metric, or on a sample too small to carry it, must be softened to what the evidence actually supports. A hedge honestly stated beats a clean answer that isn't earned.

**Check Next Steps are grounded.** Each step traces to a finding and is honestly marked `follows` vs `idea`. Cut anything invented, generic, or dressed up as a recommendation when the evidence only permits it as an option.

**Check the artifact, and the draft's looks ARE a check.** A bundled page that renders unstyled is a real defect, not a designed signal.

🔴 **Run `/design` §7's gates on `<proofPath>` and quote each as `exact command → exit code → the counts`.** They are the same gates and they live in one place now: the library lint (HARD must not rise), `wire --check`, the bundle's one-file/one-script/no-duplicate-name reading, **re-bundle byte-identity on BOTH arms**, does-the-page-actually-open, and open-the-shot-and-look. 🔴 **Quote the idea COUNT and the file hash alongside every exit code, never the exit code alone** — deleting an entire idea still exits 0 and still prints `clean`.

**One reading is `/prove`'s own, because it is what PUBLISHING demands and nothing else does:**
> **Zero external references — count LOADED subresources and ANCHORS separately, and count relative `src`.** Both halves are measured and both are stated here in full; this is the checking discipline `AGENTS.md` §4 calls *a parser, not a pattern*. Grepping `href|src` for `^(https?:)?//` is wrong twice: on 49 composed pages it would fail **22**, of which **17 load nothing at all** and score only on **68 prose `<a>` anchors**, while **0** pages load an absolute-URL subresource — and it is blind to every **relative** ref, so a page linking `library.css` or shipping `<img src="shots/*.png">` instead of `data:` URIs passes clean and breaks the moment the file travels to S3. ## 4. Publish & Report

**The shareable deliverable is a public S3 URL (`¶INV_PROVE_S3_URL_IS_SHAREABLE`).** The composed `<proofPath>` (`builds/<slug>_PROOF.html`) is one file — every asset embedded as a `data:` URI and every definition carried, nothing referenced — so it uploads to S3 as a single object served at a public HTTPS URL that **anyone with the link can open** — no auth wall, no private preview. The on-disk `builds/` file stays the durable local copy (and the Linear-attachment source); the **S3 URL** is what you hand to a teammate, a ticket, or a downstream skill.

**Config — prescribed once in the project `.env`, poke only if truly unset.** The bucket comes from `PROVE_S3_BUCKET` (+ `PROVE_S3_REGION`, default `us-east-2`; `PROVE_S3_PREFIX`, default `proofs`; optional `PROVE_S3_PROFILE`, `PROVE_S3_USER`). The helper resolves each **first wins**: a real environment variable, else the nearest **project `.env`** (walked up from `$PWD` — each project prescribes its own bucket beside its AWS creds, so the global skill stays uncoupled). **Only if none is found does it poke** — the proof is already composed in `builds/`, so report that file and tell the user to prescribe the bucket, then stop at publish:
> Add to the project `.env` (finch → repo-root `.env`): `PROVE_S3_BUCKET=staging-finch-proofs` · `PROVE_S3_REGION=us-east-2` · `PROVE_S3_PROFILE=finch-staging`.

**Bake the ticket metadata first (only if the page references `FIN-` keys).** The browser must **never call the tracker** — a shared S3 page has no credential and no CORS route to it, and a component that called it would leak the reader's identity there. So the metadata is assembled at publish time. Since `proof-ticket.v4`, it is published as a **sibling `tickets.json` fetched from the same bucket** (same-origin, no credential) rather than baked into the page byte-for-byte. Four steps, in order:
> 1. `~/.claude/skills/prove/assets/bake-tickets.sh --scan <proofPath>` — emits the deduped keys. It also **reports keys it cannot reach** (ones living only inside `<a>`/`<code>`/`<pre>`); those are an authoring defect, see below.
> 2. For each key, `§CMD_READ_RELATED_TICKET` (`get_issue` + `list_comments`), normalised to the ticket-entry shape stated here in full: `lastActivityAt = max(updatedAt, newest comment ts)`, `activity` = the newest **5** events only, each `text` trimmed. Never dump a full thread.
> 3. `bake-tickets.sh --emit <proofPath> --tickets <in.json>` — writes `<proofPath stem>.tickets.json`, the artifact `publish-s3.sh` uploads beside the page. It cross-checks against the page and warns both ways (keys baked but not mentioned; keys mentioned but not baked).
> 4. *Optional, for the local artifact:* `bake-tickets.sh --inject <proofPath> --tickets <in.json>` — writes the same payload into the page as an inline blob. The component **prefers an inline blob over any fetch**, so this is what makes a page saved to disk / mailed as an attachment read correctly offline. Publish uses the sibling; `builds/` benefits from the blob. Running both is normal.

`publish-s3.sh` then uploads the JSON and injects an **absolute** `<link rel="prove-tickets">` (a copy attached to a ticket is served from *that* host, where a derived sibling URL would 404 forever). That attached copy reads the JSON **cross-origin**, so the bucket needs a `GET`/`HEAD` CORS rule — without it the attached copy degrades to plain links. Set `PROVE_TICKETS_KEY` to publish **one JSON for a whole wave**; the default is the page's own key stem, which inherits the page's `<rand8>` unguessability (a shared key is by construction predictable, so it becomes a public index of every ticket it carries — worth it deliberately, never by default).

Skipping the bake is a supported outcome, not a failure: the component degrades to a working link with an `unknown` dot. A bake that is *attempted and fails to load* degrades **loudly** — every ref stays a working link, but the dot reads "ticket data unavailable", `<html>` carries `data-prove-tickets="error"`, and any `[data-prove-tickets-status]` element on the page states the URL and the reason. **Fabricating metadata is not supported** — a page that states a wrong status is worse than one that states none (`¶INV_PROVE_FAITHFUL_PRESENTATION`).

**Dates belong to the data, not the page.** A shared JSON can be re-baked after the page ships, so every timestamp the page shows comes from the resolved source's own `bakedAt` and is labelled *"ticket data as of …"*. Do not write a publish date next to a ticket status.

**Never hand-write a ticket anchor.** `<a href="…/issue/FIN-1234">FIN-1234</a>` can **never** become a chip — the scanner skips `<a>` by design — so it silently loses the freshness dot, the teaser and the card. Write `FIN-1234` as **bare text** and let the component build the link. Check a composed page with:
> `node ~/.claude/skills/intake/assets/__tests__/reference-guards.test.mjs --file <proofPath>` (exits non-zero on any defect).

**Single generation (`¶INV_PROVE_COMPOSE_ONCE`).** Upload the **already-composed** `<proofPath>` from `builds/` — the subagent composed it once in §2; you upload that same file, never re-render it. The upload is one command:
> `~/.claude/skills/prove/assets/publish-s3.sh <proofPath> <slug>`

It derives the per-user key segment from the AWS caller identity (`…:user/yarik` → `yarik`; override with `$PROVE_S3_USER`), mints an **unguessable** key (`<prefix>/<user>/<slug>-<rand>.html`), uploads with `--content-type text/html`, and prints the **public URL to stdout** (capture it — `aws s3 cp` chatter goes to stderr). The random suffix keeps the link unlisted: shareable, not discoverable.

**Publish resolves nothing, because there is nothing to resolve.** A bundled page carries the floor and its definitions, so it uploads as a single self-contained object — **no external dependency and no precondition to satisfy first**. There is no token to substitute and no separate asset to have published: the bytes in `builds/` are the bytes that go up, which is why the on-disk file is already the viewable one. The one thing publish still *mints* is the state config, and only for a page that asks something:
- **A write grant follows the decisions, and nothing else.** `publish-s3.sh` mints the shared state config — including a presigned write grant good for up to a week — only for a page carrying **decision markup** (`data-fb-board|item|voter|submit|payload`, or the decision layer's `data-decision-item` / `.dxsec` / `.submitbtn[data-submit]`). A read-only evidence proof gets none, and says so on stderr. If a page *should* collect decisions but publishes with `no decision markup`, the page is missing the component's attributes — do not work around it by adding the `__PROVE_STATE_CONFIG__` placeholder, which would mint a credential for a page that still has nothing to submit.
- **A decision-carrying page also gets its state config minted here** — publish signs a short-lived write grant and injects it into the page's `prove-state-config` element (substituting `__PROVE_STATE_CONFIG__` where the author placed it, else appending). Signing is never load-bearing: if it fails, the page ships read-only — it still polls the shared doc and routes submissions to clipboard copy-back with the reason shown. Because the grant is short-lived, a page meant to collect decisions over time is **re-published** to refresh it; `../prove/assets/STATE_TRANSPORT.md` owns that contract. The agent-run fold (`../prove/assets/prove-sync.sh <doc>`) is what merges posted reactions into the doc the page polls — a proof that collects decisions needs that fold run for tallies to appear.

**Auto-open for the author.** After capturing the URL, open it in the user's browser as a convenience — `open "<url>"` (macOS) or `xdg-open "<url>"` (Linux), best-effort (`|| true`; skip silently in headless/CI). This is an orchestrator step, NOT part of `publish-s3.sh` — the helper stays pure (URL-to-stdout only) so the forwarder skills (`/snapshot`, `/pr`, …) can call it programmatically without popping a browser.

**For a ticket / teammate** (chained from `/snapshot`, `/communicate`, `/inbox-post`, `/pr`, or the user says "attach / share / put it on the ticket"): hand over the **S3 URL** as the proof link. When the target wants a copy that travels with the ticket even if the bucket is later cleaned, ALSO attach a copy to Linear — the `builds/` file is the right bytes to attach, because it is self-contained and identical to what was uploaded. `prepare_attachment_upload(issue, filename, "text/html", size)` → PUT the raw bytes to the signed `uploadRequest.url` with its headers verbatim (`curl --data-binary @<proofPath>`, 60s window) → `create_attachment_from_upload(issue, assetUrl, title, subtitle)`. The attachment renders standalone, forever, with nothing to resolve. Reference the S3 URL (or that attachment) in any comment.

**Where the attachment lands depends on the TARGET** (`§INV_CHANNEL_EVIDENCE_RIDES_THE_COMMENT`). The flow above — ending in `create_attachment_from_upload` — is correct for a **worked ticket** (`/snapshot`, `/ticket`, `/pr`), where the attachment belongs to the ticket as a whole. **Never publish** a page that impersonates a real org/person or presents fabricated records as genuine — if the subject is that kind (the subagent flagged it, or you judge it so), keep it as a local file in `builds/` and let the user decide, rather than uploading it to a public URL.

## Anti-Patterns (name them, avoid them)

- **Hand-writing the ticket blob** — typing statuses, dates or assignees into `<script id="prove-tickets">` from memory, or from what the page already says. Every baked value is a claim the page makes in the tracker's voice, to readers who cannot check it. `--scan`, then a real `get_issue` per key, then `--inject`. Skipping the bake entirely is fine — the component degrades to a working link. Inventing one is not.
- **Rendering theatre** — a gorgeous page that proves nothing, or that asserts more than the evidence shows / more than upstream established. If it's not shown and not established, the page doesn't claim it.
- **Fake / mocked assets** — a retyped "screenshot", a lorem table, an illustrative stand-in for a render you couldn't capture. Real source only; a failed capture is recorded and degraded, never faked.
- **Decorative color** — color that encodes nothing. In a proof, color is a *claim* (owner, verdict, delta); it always has a legend and a real referent.
- **A diagram that needs a third-party runtime** — a `<pre class="mermaid">` block (or Chart.js / KaTeX / D3) on a page published as a static S3 file that loads no script from anywhere. It renders as literal source text and the author usually never sees it, because mermaid *does* render in the claude.ai Artifact host. Inline `<svg>` or an embedded PNG, always.
- **Hand-retyping a definition** — pasting a copy of a stylesheet or an idea's CSS into the page "so it's self-contained". A second copy is a second source of truth and forks from the real one the moment the library ships a fix. Carrying is the contract, but only via `idea bundle` — a definition edited **by hand** is the same defect wearing the library's clothes, and a re-bundle into the same `--out` is what tells them apart (`same` exit 0 vs `REFUSE` exit 1).
- **Blank-canvas composition** — opening an empty file, or assembling a page from blocks and patterns, when the page kind you declared already generates a finished one. A parts list plus instructions produces the minimum arrangement that satisfies the instructions: a page that is correct, warm, tidy and *thin*. That is the recorded failure mode, not a hypothetical. Generate from the kind, fill it, cut what you don't need. A genuinely new pattern is built ON the library's own idea grammar and named, never freehanded around it.
- **A token with no definition** — writing `data-instance="coverage-heatmap"` into the artifact after it was bundled. The block renders as unstyled prose and the page still passes every textual check, because nothing external is missing. Add the token to `<pagePath>` and RE-BUNDLE; never paste a definition in by hand.
- **Hand-editing the bundled artifact** — a one-line caption fix straight into `<proofPath>` because re-bundling feels slow. That edit is exactly what the re-bundle guard exists to catch, and the next re-bundle will REFUSE rather than silently overwrite it. The source of truth is `<pagePath>`.
- **Ignoring an idea's `excludes`** — the clauses are the contract you agree to by placing the block, and they catch authors: a `legend` whose rows do not cover every mark the page draws is a defect the idea itself declares, and one has already been caught that way in a real page. Read the clauses (`idea view --clauses`) before you place the block, not after the render looks wrong.
- **The thin fill** — generating the entry and then deleting its density: two specimens where the evidence supports five, no margin notes, ornament breaks stripped, the colophon cut, the § numbering dropped "because the page is short". The generated shape IS the design; a shorter page has fewer specimens, not less frame.
- **A decision bolted on as a board row** — stacking the page's asks into a uniform decision list at the bottom, divorced from the evidence that justifies them. A decision rides the block whose grounds it judges, one component matched to that block's question type. And a proof that asks for nothing carries no decision layer at all — decisions are optional.
- **Buried honesty** — the scope / provenance block (what's shown vs. what rests on the trusted upstream finding) hidden at the bottom. It sits where the reader meets the claim.
- **Answering the author's question instead of the reader's** — the page argues the thing the author found interesting ("the metric was blind, and here is why") while the reader arrived asking "does it work, can I turn it on, what breaks?". The argument can be true, elegant and well-evidenced and still fail its only job. The Questions & Answers block exists for exactly this; derive it from the §1.B reader, never from what the investigation enjoyed.
- **A proof with no exit** — the page establishes what is true and leaves the reader to re-derive what to do about it. Next Steps closes that, traced to findings and honestly marked `follows` vs `idea` — never a generic backlog, never an idea promoted to a recommendation.
- **Templated AI-artifact look** — the generic gradient-card page. `Skill(artifact-design)` exists to calibrate real design; follow it.
- **Telling instead of showing** — writing "the log confirms X" without rendering the actual log line, or paraphrasing a result you could quote. Trusting the upstream *verdict* is right; substituting prose for the *evidence* is not — show the real artifact.
- **Re-litigating the finding** — re-running the analysis to "make sure" before rendering. That's not `/prove`'s job; the verdict is the input. If you genuinely doubt it, hand back to `/probe`/`/analyze`/`/experiment` — don't quietly re-investigate inside a proof.

## Constraints

- **`¶INV_PROVE_TRUST_UPSTREAM`** — `/prove` trusts the finding it presents. It does NOT re-run the analysis or re-litigate the verdict — that was `/probe` / `/analyze` / `/experiment` / `/fix`'s job, and their conclusion is the input. A finding you genuinely doubt goes back upstream, never through `/prove`.
- **`¶INV_PROVE_REAL_ASSETS_ONLY`** — Every asset is rendered from the ACTUAL source (code block from the real file, PDF render, real screenshot, verbatim log/CLI output, data-driven overlay/diagram). No mockups, no lorem, no illustrative fakes, no prose standing in for a result you could show. A render that fails is recorded and degraded around, never fabricated.
- **`¶INV_PROVE_FAITHFUL_PRESENTATION`** — The only verification `/prove` owns serves the presentation: each asset faithfully shows what its caption claims, nothing on the page claims MORE than the evidence shows or more than upstream established, and provenance is honest (`trusted-upstream` vs. `checked-here`). The page carries an explicit, unburied scope block: what the evidence shows / out of scope / what rests on the trusted upstream finding. Overreach is cut.
- **`¶INV_PROVE_DEGRADE_GRACEFULLY`** — No imagery renderable → still produce a readable proof (code blocks / tables / CLI text / diagrams) and say imagery was unavailable. A partial or blocked run still leaves the dossier.
- **Presents, never investigates.** `/prove` takes an already-resolved finding and compiles + shows it. It never opens a fresh investigation and never re-runs one — that's `/probe` / `/analyze` / `/experiment`. It presents; it does not re-derive.
- **Offered only when there's something to show.** As a next-step it is offered (never forced, `¶INV_OFFER_DONT_FORCE_SKILLS`) at the synthesis of the investigative skills **only when the finding carries renderable evidence** — a rendered artifact, a before/after, code, a log, real output. An abstract conclusion with nothing to show is not a `/prove` candidate.
- **Building block — proves, then stops.** It publishes a proof and reports. It never fixes (`/fix`), commits (`/snapshot`), ships (`/pr`), or files (`/ticket`). Chains are offered, never auto-run.
- **Two paths for the heavy lift; the integrity gate + publish always stay with the orchestrator.** By default a subagent assembles, renders, and composes the draft (base64 never returns to the orchestrator); when the caller already holds the full context and it's disposable (a /build//probe subagent's own report, or end-of-session), the compose runs inline for full fidelity instead. Either way, the orchestrator owns the presentation-integrity pass and the S3 publish (the human-facing gate) — and after the inline path, offers `/scrutinize` for the independence a self-review lacks.
- **`¶INV_PROVE_COMPOSE_FROM_KIT` — a proof page is DECLARED from the idea library and ASSEMBLED by `idea bundle`, and it STARTS from its page kind via `idea generate`.** 🔴 **`/design` (`~/.claude/skills/design/SKILL.md`) owns that whole sequence — resolve · contract · kind · wire · fill · bundle · gates — and this skill does not carry a second copy of it.** Follow it; the composing rules, their reasoning and their measured costs all live there, including that the entry's resolved set is a STARTING POSITION and never a permission boundary, that `--json`'s `omitted` is where the rest is discovered, that the view is read WHOLE from a file, that markup is pasted verbatim, and that the definitions are never yours to place.

  **What this invariant adds on top, and only this:** the page is a *proof*, so it picks an **archetype** to decide its evidence spine (§2 step 3); it attaches apparatus only where a block earns it; and it embeds a decision component only where §1.C said the proof genuinely asks — **and whether the library declares a kind that carries decisions is a question for `generate --list`, never a fact carried in this file.** If no such kind is listed, name the missing kind in the dossier and compose the evidence layer; never invent one and never bolt a decision layer onto a kind that does not carry it.

  **The one composing fact that is genuinely `/prove`'s: a library page links `library.css`; a bundled proof page does not, and that is the whole difference.** The theme reaches a bundled page as an ordinary idea in the bundle, so **swapping it is a name, not a file** — nothing to re-link, re-publish or re-path. The result has **zero external references**, which is what makes the `builds/` file and the published object the same bytes. **Every library document, and `library.css`, is READ-ONLY to a composing agent**, and hand-inlining either into the page is the second copy this system exists to remove.
- **Artifact rules are hard.** Fully self-contained (assets embedded as `data:` URIs; nothing loaded from any host at all), theme-aware, responsive, honest title/favicon. Never impersonate a real org/person; never present fabricated records as genuine — such content stays a file, published only at the user's choice.
- **`¶INV_PROVE_COMPOSE_ONCE` — single generation.** The proof HTML is composed exactly once, by the subagent, into `builds/<slug>_PROOF.html`; §4 uploads *that same file* to S3 and never re-renders it. One build → two uses (the public S3 URL + the on-disk file).
- **`¶INV_PROVE_S3_URL_IS_SHAREABLE` — the shareable deliverable is the public S3 URL.** `/prove` uploads `builds/<slug>_PROOF.html` to `$PROVE_S3_BUCKET` under an unguessable `<prefix>/<user>/<slug>-<rand>.html` key (via `../prove/assets/publish-s3.sh`) and serves it at a public HTTPS URL anyone with the link can open. That URL — there is **no** claude.ai Artifact preview any more — is what leaves the author's machine: a ticket comment, an attachment reference, a handoff to a teammate or a downstream skill (`/inbox-post`, `/snapshot`, `/communicate`, `/pr`) all carry the S3 URL (and, when the target needs a ticket-durable copy, the `builds/` file attached via the Linear MCP `prepare_attachment_upload` → PUT bytes → `create_attachment_from_upload` flow). The bucket is prescribed once per project (`PROVE_S3_BUCKET` + friends, resolved env-var → project `.env` → poke); if none is found the skill reports the `builds/` file and pokes the user to prescribe it — it does **not** silently skip, and it never guesses a bucket. Applies to every skill that forwards a proof/report, not just `/prove`.
- **Durable in `builds/`, attachable.** The proof HTML (`<slug>_PROOF.html`) and its dossier (`<slug>_PROVE.md`) live in the session's `builds/` — durable session artifacts beside the `/build`//`/probe`//`/experiment` trail. Every captured asset is embedded as a `data:` URI and every definition is carried, so the file travels whole and nothing resolves at publish — the `builds/` file and the published object are the same bytes. Raw captured assets stay in scratchpad as throwaway intermediates. The dossier + HTML persist even on a partial run, so the evidence sits on disk, not just asserted.
- **Lightweight + sessionless.** Runs within the active session: scope → dispatch (assemble/render/compose) → integrity pass → publish → stop.
