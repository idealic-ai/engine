Two independent triage runs from different vantage points, then adjudication on the record. It corroborates and reports; it never files, never decides a disposition, and never edits data.

# /triangulate Protocol (Dual Independent Assessment with Adjudication)

## Why this exists

**Two runs of the same method share the same blind spots**, so their agreement is replication, not corroboration. The failure class this is built for is the one that survives replication: a property of the **data** rather than of the query. One project spent weeks quoting numbers distorted by two organisations that were the same tenant imported twice — invisible to every database query ever run against it, because every query inherited it identically.

Triangulation is the established name for the fix: check a finding from **different vantage points**. Not "check it twice."

**Disagreement is the product, not the failure.** A defect was found in one pass precisely because a screen said one thing and a query said another — the gap *was* the bug. A process that resolves disagreements away destroys its most valuable output.

## What it is, and is not

*   **It is** a wrapper that runs `/triage` twice on different angles and adjudicates the results. Everything `/triage` needs, this needs — it is passing that input through, twice.
*   **It is NOT** a deeper triage. Each run is an ordinary triage. The value is in the *diversity of the pair*, not in the depth of either.
*   **It does NOT decide dispositions.** It returns a corroborated finding; graduating, folding, parking or shipping stays with the caller (`¶INV_INTAKE_DISPATCHES_NEVER_EXECUTES`).

## When to invoke it

**Per subject, by judgement — never universally.** Measured at **~2× a single triage** (106k + 132k tokens on the first real run, plus the adjudicator when needed), and running it on something nobody will act on manufactures agreement theatre.

Invoke when the subject is heading for **a ticket, a decision, a refactor you are about to trust, or a claim in a Project Update** — the places a wrong finding becomes expensive and durable. A signal that will marinate does not need it.

**One standing exception, and it is not a contradiction: `/inbox-post` runs this on every drop it posts** that has something checkable in it. The warning above is about sweeping a backlog nobody will act on, where two matching answers manufacture agreement theatre. A drop someone has just written is the opposite — it is an item with a person behind it, waiting. **Measured**: two drops on [FIN-3445](https://linear.app/finchclaims/issue/FIN-3445) sat 17 days unanswered while the answer already existed on the record, folded into a ticket the reporter could not see from their thread. **Per subject, by judgement** still governs everything else; a fresh drop is where the judgement has already been made.

## 1. Inputs — everything `/triage` takes, plus the angles

**The input is a context pack the caller does not have to predigest** — a claim in prose, URLs, a ticket key, a Linear comment id, local file paths, a handoff prompt, any mix. Assemble what you have; **resolving the rest is `/triage`'s job, and it will do it twice.** Do not stall on normalizing the pack.

**Resolve the MODE ONCE, here, and write the answer into every dispatch string.** Inbox mode is **inferred, not remembered**: it turns ON when the subject is a Linear **comment** or a Linear **inbox channel ticket**, and stays OFF for an ordinary work ticket someone is working. `/triage` § *Inbox mode* carries the full rule and both overrides — `--mode inbox` forces it on, `--mode plain` forces it off. **This wrapper decides it and the angles never re-infer it**, because an angle is handed a handoff path and cannot see the channel behind it. **A wrapper whose caller owns publishing passes `--mode plain` and means it**: `/loom` triangulates a thread's own ticket to decide whether the build is worth investing in, and a comment on that ticket belongs to `/snapshot`, not to this run.

**Resolve BATCH-NESS ONCE, here, and say which way it landed.** Count the **destinations** the pack implies — the threads, tickets or reporters a finding would be posted to. More than one means more than one subject, and §1b governs the run. One destination is one subject however many URLs, screenshots and query results the pack piles around it, and §1b is then dead text for this run. `--batch` forces it on where the inference has nothing to fire on.

**Resolve the owning project ONCE, here, and pass the answer to both runs.** `/triage` § *Resolve the subject* is the procedure: infer the `Product:`-prefixed Linear project from the subject, show the guess with the evidence that picked it, let the operator correct it **before** anything is dispatched, then read that project's Inbox Handbook `## What triage will chase`. Resolving it per-angle instead risks the two runs reading two different projects' recipes, which is not angle diversity — it is two investigations of two different subjects. Where no project owns the subject, say so once and let both runs use the generic recipe.

**Resolve PRIMING ONCE, here, and write the answer into every dispatch string.** Where the resolved project publishes a **known-signal registry** — a forensic checklist, a registry of known root causes with the signature that recognises each — exactly one angle is primed with it and §2c's exclusion requirement fires. **It is inferred from the resolved project rather than passed, for the reason mode and batch are**: a flag is a thing a caller forgets, and this forgetting is invisible — the primed angle comes back classified, specific and confident, and nothing in the returned result shows that the exclusions were never asked for. `--primed <path>` forces it where the inference has nothing to fire on — a registry the handbook does not name, a checklist the caller holds locally. **Where no registry exists nobody is primed**: both reports read `not primed`, §2c is dead text for this run, and the pair behaves exactly as it did before priming existed.

**Say it in one line before dispatching** — `primed: angle B with <recipe path> (inferred: the project's handbook publishes one)` / `primed: none — the project publishes no known-signal registry`. **No angle re-infers it**, because an angle is handed a handoff path and cannot see the handbook behind it: the wrapper writes `--primed <path>` into that one dispatch and `--primed none` into every other, the way `--project none` is written out rather than left off.

**Preflight ONCE, here, before anything is dispatched — when the investigation will reach data, an MCP, a signed-in app or a cloud credential, and lean yes:**

```
engine env doctor --tier triage
```

**A non-zero exit is a STOP.** Fix what it names and re-run. Each angle judges the same question when it starts, so a broken environment would be caught anyway — but it would be caught *twice, in parallel, after the spend*. Triangulation is measured at ~2× a single triage; discovering a missing credential from inside two sub-agents is the most expensive possible moment to learn it. Report the KEY the doctor names, never a capability (`¶INV_UNAVAILABLE_IS_A_CLAIM`). Skip it only when you can say in one clause what both runs will read instead, and say that clause in the report.

Assemble once; both runs receive the same pack:

*   **The subject in full — and where it is a thread, INCLUDING ITS REPLIES**, not just the comment body. Screenshots and attachments too. **An origin comment's replies are part of the signal, not commentary on it**: prior triage results, corrections and the reporter's own follow-ups live there, and passing in the body alone silently withholds the most-processed evidence available. *Learned expensively — a ticket was filed asserting something had never been investigated, four days after a reply on that exact thread said it had, and gave the answer.*
*   **The resolved project**, and its handbook's `## What triage will chase` and `## Boundaries` — the per-project recipe and the neighbour tests.
*   **In inbox mode: the origin comment id** and its channel ticket, **the channel's `## Directions` verbatim** (`¶INV_DIRECTIONS_IN_DESCRIPTIONS` — a sub-agent cannot read the project; an unpassed steer is a lost steer), and **the `## Ticketing Strategy`**, since each run recommends a milestone.
*   **Relevant stakeholders** — who to ask when a run hits a question it cannot close.
*   **The Slack channel-context slice**, if the caller loaded one.
*   **Data access**: the shared read-only connection, already open. Both runs share it; neither opens its own — **so both must be TOLD the endpoint**, in the handoff, by name.
*   **The access directive itself** — `.directives/INBOX_TRIAGE_ACCESS.md`. Nothing auto-loads it and `discover-directives` does not return it, so **name the path in both briefs**. An angle that never reads it does not fail loudly: it goes looking for a route, finds the fallback, and reports a confident diagnosis of the wrong thing. That is not a hypothetical — it has happened, against a public database instance gated by an IP allowlist whose failure mode is a silent timeout.
*   **The angle assignment** — one primary, one corroborating, and **which of the two (at most one) is primed** with the project's known-signal recipe, plus that recipe itself (§2c).

## 1b. Batch — inferred from the DESTINATIONS, and the cause is discovered rather than supplied

**With one subject, nothing in this section applies.** §1 and §2 through §6 run exactly as written, and a caller passing one subject gets today's behaviour unchanged.

**What turns it on**: the pack carries **more than one subject**. **The test is mechanical — count the places a finding would be posted.** Eight drops on an intake channel are eight reporters under eight threads, so eight subjects. Ten URLs, a screenshot and a query result assembled around one complaint post once, so one subject. **`--batch` forces it on** where the inference has nothing to fire on — N drops pasted in as one body, a handoff that names the cohorts only in prose.

**It is inferred rather than passed for the reason inbox mode is** (`/triage` § *Inbox mode*): a flag is a thing a caller forgets, and this particular forgetting is invisible. The run comes back looking entirely normal — one investigation, one confident dossier, one comment — and the failure is the N−1 people who were never told anything, which nothing in the returned result shows.

**Say it in one line before dispatching** — `batch: 8 subjects (inferred: 8 origin comment ids)` / `batch: off — one subject`. An inference nobody can see is one nobody can correct.

**What batch mode changes, and all of it is additive**: both angles and the adjudicator run ONCE over the whole batch (§3), the adjudicator always runs and returns groupings (§4, §5), and the run publishes a full comment per **class** plus a short one per member instead of a single comment (§6).

**BATCH IS NOT SPECIAL — the saving is in the investigation, never in the output.** Per class, a batch publishes exactly what a single-subject run publishes for its subject, with nothing stripped on the grounds that a batch produced it. Read the mode as *N single runs sharing one investigation and one dossier*, and every question about what a class comment should carry answers itself.

### The cause is DISCOVERED. Frame the batch so it can come out either way.

**Frame the batch to the angles as *"these subjects may share a cause, or may be several — group them"*.** Forbidden: *"establish the cause of X"*, *"why does X keep happening"*, and any leading question that names the class. A batch statement that names the class has already answered the question the pair was assembled to test, and both angles inherit it (`¶INV_FRAMING_IS_A_SHARED_CHANNEL`).

**The normal return is GROUPINGS** — a set of *{cause, the subjects it explains}*. **A grouping of one is a grouping**, not a failure to converge.

> ### 🟡 Eight groupings of one is a SUCCESS. Do not let someone "fix" it later.
>
> The likelier batch in the wild is not eight siblings. It is **eight things that merely arrived together** — one wave, one channel, one afternoon — and a caller who batched them on arrival rather than on cause. A run that splits them all the way down has reported exactly that, and each reporter still gets a finding about their own subject, which is the entire point of the mode.
>
> It reads like the mode did nothing. It did the most useful thing available to it — and the output is then **literally eight single runs sharing one investigation**, each with its own full comment, which is what batch mode is for rather than a degradation of it. **The failure is the opposite shape**: one grouping asserted over eight subjects because the framing named a class and both angles were polite about it.

> ### 🔴 Measured — the first time `¶INV_FRAMING_IS_A_SHARED_CHANNEL` was SURVIVED rather than avoided
>
> The trial batch — eight cohort reports on one intake channel — was framed as *"the cold-start matching failure"*: one named class, one leading cause, exactly what the rule above now forbids. **Both angles rejected it anyway.** One established that the failure was candidate **retrieval** rather than matching; the other established that the premise *"a cold-start org can never retrieve the correct claim"* was false; the adjudicator then refuted the code angle's own replacement hypothesis. The licence in §3 worked, under load, on a real batch.
>
> **And the framing was still wrong.** The run was lucky that the class it named happened to be cleanly splittable — a subtler batch, where the wrong class is a plausible one, would have been railroaded by the same wording with nothing to catch it. Read this as *frame the batch neutrally*; never as *the angles handle a leading batch framing*, which is what the same story records if you stop after the first paragraph.

## 2. An angle is a STARTING POINT AND A QUESTION — never a fence

> ### 🔴 Every run may use every tool. Read this before writing a brief.
>
> An angle says **what you lead with and what you are trying to establish**. It does **not** limit what evidence you may touch. If a code-led run needs one database query to settle its own claim, **it runs the query**. If a record-led run needs to open a screenshot, it opens it.
>
> **Independence comes from different questions asked in parallel with no sight of each other's conclusions** — which `--no-post` already guarantees. It never came from starving each run of evidence, and pretending otherwise buys nothing while costing a great deal.
>
> **Why this is written as a warning.** An earlier version of this skill fenced each run to one evidence base — *"do not read tickets", "do not query the database"*. The result was exactly the complaint the method exists to avoid: **not enough evidence.** Both runs reported that the thing they could not settle was one query inside the other's fence, the wrapper recorded low confidence on precisely that question, and one "disagreement" between the runs turned out to be an artifact of each seeing half a picture rather than a real epistemic gap. **A restriction that manufactures the uncertainty it was meant to detect is worse than no restriction.**
>
> So: **lead with your angle, and follow the question wherever it goes.** A run that ends "I could not establish X" when X was one query away has written a bad report, not a disciplined one.

## 2b. Choose leads that FIND DIFFERENTLY

The evidence bases. Each is named by **what it can see that the others cannot** — which is the only property that makes a pair worth running:

*   **db** — stored state: rows, rates, distributions, counts. Whatever the subject persists into, whether that is a database, a state file, a queue or a cache.
*   **ui** — drive the surface and see what a user actually sees. **Where the project provisions a read-only agent account this angle is literally available**: the run signs in and looks at the reporter's screen rather than inferring it from rows. The mechanics — credentials, the sign-in traps, the waits, how to point a session at an account — belong to the project's access directive, which `/triage`'s Reproduce step sends you to. Without such an account a ui-led angle can only reason *about* the interface, which makes it the weakest of the set; with one, treat it as first-class. For a subject with no application, the surface is whatever a caller actually gets back — the command's output, the rendered page, the tool's response.
*   **code** — read the source that ships and trace the path from entry point to the claimed behaviour.
*   **artifact** — open the actual thing complained about: the document, the export, the payload, the generated file, the screenshot.
    > **How to actually open a Linear-hosted attachment**: pass the markdown containing the image reference to **`mcp__linear__extract_images`**. **Do NOT `curl` the `assetUrl` — it returns 401 and always will.** `uploads.linear.app` serves nothing unauthenticated; the bare URL is a *reference*, and access needs a session or a signed URL that Linear mints per-viewer with a ~300-second expiry. A pasted signed link is therefore **not** a durable citation — it works when written and 401s when read. Cite the attachment on its ticket and fetch it through the MCP.
    > *This is written down because a wrapper once concluded the artifact angle was unavailable to sub-agents, on the strength of a single unauthenticated `curl`. It was available the whole time, and the wrong conclusion was one call from being disproved.*
*   **execution** — run it and watch: a repro, the test suite, a trace, a log, a profile. **Distinct from `code`, and the distinction earns its place** — what a program does and what its source appears to say disagree constantly, and only this base can catch it.
*   **history** — what shipped, what was reverted, what was cancelled, what already failed: git log and blame, tickets and their threads, prior reports. (Cheapest of all, and the one whose omission is unrecoverable.)
*   **spec** — what the thing was supposed to do: the contract, the schema, the invariant, the ticket's acceptance signal, the protocol text itself. The only base that can return **"working as written, and the writing is wrong"** — which no amount of reading the implementation will ever produce.

**Rules:**

1.  **The two angles MUST come from different bases — different in what they can SEE, not merely in what they are called.** Two db runs are replication, and so is any pair whose two runs open the same artifact under two labels. **The check is mechanical: name the file, screen, table or command each angle will actually open. Same one → they are one base; re-pick.** The pair this catches most often is `code` + `spec` on an engine protocol, where the source that ships *is* the protocol text — both runs read the same markdown, inherit the same blind spots, and return an AGREE that is replication wearing two names. On a subject like that, pair `spec` with `history` (what the text said before, and what broke when it changed) or with `execution` (run the thing the text governs and watch what it does).
2.  **Match the angle to the claim's shape.** A rendering claim wants ui + code. An extraction claim wants artifact + db. A "we already tried this" claim wants history + code. A failing test wants execution + spec — *does it actually break*, and *was the expectation ever right*. A refactor you are about to trust wants spec + history — *what did the old thing promise*, and *what already broke the last time it was touched*.
3.  **This list is a vocabulary, not a closed set.** A subject that needs a base not named here gets one — name it, and say in one line what it can see that the paired base cannot. What is forbidden is a pair that cannot fail differently, never a base that is missing from the list.
4.  **Both angles must be able to SEE the claim.** Before dispatching, state in one line what each angle could find that would settle the question. **If you cannot say that for an angle, it is the wrong angle** — a pair blind to the same thing produces two "cannot answer" reports and a vacuous AGREE that looks like corroboration and is worth nothing.
5.  **The caller may pin angles** via `--angles`; otherwise choose and *state the choice with its reason* in the report.

**Cost, measured rather than assumed.** The first real run cost **106k and 132k tokens** — the two angles came out roughly equal, so **budget ~2×**, not the "cheap second angle" this section originally claimed. That claim was reasoning presented as a figure and the first run refuted it. The cheapness argument still holds *within* an angle (a `git grep` beats designing a query), but it does not make the pair cheap. Invoke accordingly.

## 2c. A primed angle — at most one, and it reports its exclusions

**Some projects publish a known-signal recipe**: a forensic checklist, and a registry of known root causes with the signature that recognises each. **Handing it to an angle is worth doing** — it stops a run re-deriving something the project already understands, which is the cheapest saving available to this method.

**Whether an angle is primed is settled in §1, not here.** The wrapper infers it from the resolved project, `--primed <path>` overrides, and the answer rides every dispatch string as `--primed <path>` or `--primed none`. This section governs what a primed angle must then **report** — and it is dead text on a run §1 resolved as `primed: none`.

**Prime at most ONE angle.** A shared checklist is a shared channel in the `¶INV_FRAMING_IS_A_SHARED_CHANNEL` sense and **far more specific than framing**: both angles open the same columns, walk the same traversals and consult the same recognition signatures, so the checklist's blind spots become the pair's and their agreement becomes replication. The whole point of the second angle is to find what the first cannot see; priming it with the first's instrument spends it for nothing.

> ### 🔴 A primed angle without exclusions is an ORACLE, and the pair collapses around it
>
> A primed angle is **privileged by construction**: it will always come back more specific and more confident than the open one. So an adjudicator defers to it, and the open angle degrades into a rubber stamp — the harmonising `¶INV_DISAGREEMENT_IS_THE_PRODUCT` forbids, reached not by preferring the louder answer but by trusting the better-equipped one, which is why nothing in the angle-diversity rules catches it.
>
> **The fix is what the primed angle reports, not how many agents run.** A third angle does not cure an oracle; it gives it another deferent.
>
> *   ❌ *"Matched class 7."* — unfalsifiable. The other angle has nothing to argue with, and neither does the adjudicator.
> *   ✅ *"Matched 7; ruled out 4, 11 and 19, and here is the signal that excluded each."* — a **peer**. The exclusions are the surface the other angle and the adjudicator can attack.
>
> **A bare classification hides exactly the part that makes it checkable.** Require the exclusions in the primed brief, in these terms: *"report what you ruled out and the signal that ruled it out, not only what you matched — an exclusion nobody can attack is not a finding."*

**The primed angle still picks a different base from its partner.** Priming changes what a run *knows*, never what it *opens*, so it does not substitute for the pair's diversity. A checklist that opens stored rows is a `db` angle carrying a prior — pair it with something that opens a different artifact, under the mechanical test in §2b rule 1: name the file, screen, table or command each angle will actually open, and re-pick if they are the same one.

**Where the exclusions land**: the report's `## Ruled out` section (`../triage/assets/TEMPLATE_TRIAGE_REPORT.md`), and its `**Primed with**` line names the recipe or says `not primed`. **The dispatch's `--primed` value is what fills that line**, so a report reading `not primed` under a `--primed <path>` dispatch did not read its own flag, and one reading a recipe under `--primed none` primed itself off something it was not given. **Verify the returned report carries both** — a primed report with no `## Ruled out` section did not follow the instruction, so treat its classification as a hypothesis and say so, exactly as you would an angle that never invoked the skill (§3). This is instruction rather than structure; auditing the section is what makes it hold.

## 3. Dispatch both — parallel, THROUGH `/triage`, and neither posts

> ### 🔴 DISPATCH THE SKILL. NEVER HAND-AUTHOR A BRIEF IN ITS PLACE.
>
> Each angle is **a sub-agent whose job is to invoke `/triage`** — write the handoff to `builds/triage-handoff-<subject-id>-<angle>.md`, then dispatch an agent whose prompt says, in these words: *"Invoke the `/triage` skill via the Skill tool with `<handoff path> --no-post --angle <base> --mode <inbox|plain> --project <resolved project> --primed <path|none> [--batch]`. Follow that protocol exactly; do not improvise a method."*
>
> **Fill every flag from the wrapper's own state; none of them is optional.** Two are conditional on an inference the wrapper has already made, and once that inference has landed they are as mandatory as the rest. **`--batch`** rides on §1b having said yes: an angle handed N subjects without it restates them as one and returns a merged finding no per-subject comment can be written from. **`--primed`** rides on §1's priming line and goes on **every** dispatch — the recipe path into the one primed angle, `--primed none` into the other and into the adjudicator — because an angle that re-infers priming from a handoff path infers it from nothing, and a run whose exclusions were never asked for returns a classification nobody can attack. `--mode` carries the answer §1 already settled — `inbox` or `plain`, written out, never left off for the angle to re-infer from a handoff path it cannot read a channel out of. `--project` carries the name §1 resolved, or `--project none` where nothing owns the subject. **A dropped flag is a rule the angle never gets, and the run still looks normal**: without `--mode inbox` neither angle has read-all-three-surfaces, Directions-outrank-the-recipe, Ticketing-Strategy-bounds-the-recommendation or `¶INV_REPLIES_ARE_SIGNAL` in force, while the wrapper goes on to post as usual — the same invisible loss this box exists to stop, one layer down.
>
> **A hand-written `general-purpose` brief is NOT a substitute, however good the brief is.** `/triage` carries discipline this wrapper does not restate and must not re-derive: the report template, the resolve-the-subject procedure, the open-the-attachments rule (and the `curl` 401 trap), the read-all-three-surfaces rule under inbox mode, the Directions-outrank-the-recipe precedence, the Ticketing-Strategy-bounds-your-recommendation rule, and the branch-by-claim-shape recipe. A bespoke brief inherits **none** of it, and the loss is invisible — the reports come back long, confident and well-structured, just in the wrong shape and without the checks.
>
> **Measured, not theoretical.** A wrapper run hand-authored two `general-purpose` briefs instead of dispatching the skill. Both angles produced genuinely good work, and the deviation still cost three things at once: reports in bespoke shapes rather than `TEMPLATE_TRIAGE_REPORT`, so nothing downstream could parse them; neither run inherited the triage skill's own guardrails; and because the wrapper was choosing agent types freely, it chose an unconstrained one for the adjudicator too. **The operator caught it, not the wrapper** — which is why this is a hard rule with a mechanical check rather than a preference.
>
> **Verify it happened**: the dispatched agent's transcript must show a `Skill` call for `triage`. If a run returns without one, it did not run the protocol — treat its output as an unstructured opinion, say so, and re-dispatch.

Dispatch both **simultaneously**, each with `--no-post`, its assigned `--angle`, the resolved `--mode`, the resolved `--project` and the resolved `--primed`. Each does an ordinary triage and returns its report.

**In batch mode both angles receive the WHOLE batch and each runs once over it** — that is the efficiency the mode exists for, and the fan-IN is the safe half. *Measured*: on the trial batch eight signals went into both angles cleanly, and the only reconciling the adjudicator did was a real finding rather than a repair of a mis-ingest. Spend the design attention on the fan-out (§6), not here. The handoff is one file per angle named for the batch — `builds/triage-handoff-<batch-id>-<angle>.md`.

Two rules bind at dispatch, and both exist only to make the fan-out possible later:

*   **Pass every subject's OWN material — its origin body, its replies, its ids, its numbers, its dates — never a list of names.** An angle handed *"the eight cohorts"* returns a class-level finding and not one fact that could be posted to any single reporter's thread.
*   **Require a per-subject row back.** Each angle's report carries a `## Per-subject` section (`/triage` § *A batch of subjects*): one row per subject, saying what **that subject's own** evidence showed and which group the angle puts it in. A subject the angle could not reach still gets a row saying so. Without this section the fan-out has to invent specifics or drop them, and both are worse than not running the mode.

**Independence is structural here, not a rule either agent has to remember** (`¶INV_INDEPENDENCE_BY_CONSTRUCTION`). They start from identical state, write to different files, and **neither posts** — so there is no output of one that the other could see. Nothing needs prohibiting because nothing is reachable.

*Symmetric shared context is fine and should not be stripped.* Both angles seeing the same prior-wave `✅ result` replies does not compromise independence; seeing each other's **conclusions** would. Do not impoverish either run's context in the name of a blindness it already has.

**`--no-post` is the whole reason this is safe**, and it exists for a second reason too: two angle-reports landing on the thread before adjudication show the reporter two possibly-contradictory answers followed by a third comment resolving them — intermediates presented as conclusions. **The wrapper publishes once, at the end, and only when `--post` is on.**

> ### 🔴 License at least one angle to REJECT the question
>
> The two runs are independent of each other and **both depend on the wrapper's framing** — they receive the same statement of the claim, written by the same author. That is a shared contamination channel the angle split does nothing about: **triangulation protects against method blind spots, not against a badly-framed question.** Two angles answering the wrong question in agreement is the failure mode, and it is *more* convincing than a single wrong answer, not less.
>
> So at least one brief must say, in these terms: **"If the premise of this question is wrong, say so and explain why — that is a more useful answer than answering it."** Give it the claim as a *claim to be tested*, never as background it should assume.
>
> The first real run survived this hole by luck: the premise happened to be checkable from one angle's evidence base. Had both bases been silent on the framing, both would have answered obediently and agreed.
>
> **A later run showed the licence is necessary but not sufficient** — both angles used it, both partly rejected the premise, and the framing still steered them somewhere neither noticed. Three words did it. *"More data"* set both to counting **volume, never value**: neither de-duplicated to distinct meaning per claim, nor sampled a single claim to ask what an adjuster actually misses. *"Loses"* hid a **correctness** hazard sitting in plain sight — users may be shown a *wrong* value today under last-writer-wins, needing no migration at all, and neither angle sized it because "loses" points at absence. *"…tables"* named the terminus, so both audited tables and **neither opened the UI** — while one angle's binding conclusion rested on that unopened layer. **So the adjudicator carries a required section for it** (§5, *"what the framing made both miss"*): both runs inherit one author's vocabulary, and that section is the only place in the method where its blind spots can surface.

## 4. Compare — cheaply, before spending a third agent

The wrapper reads both reports and asks one question: **do the verdicts and their load-bearing numbers agree?**

*   **They agree, and at least one reports medium-or-better confidence** → report the agreed finding, naming both angles. **No adjudicator.** Done.
*   **They agree and BOTH report low confidence** → **that is not corroboration and may not stand as a verdict.** Two shallow runs matching is two guesses matching. Report it as *"agreed but unestablished"*, name what neither could reach, and treat the subject as still un-triaged. Agreement between weak evidence is the most seductive false positive this process can produce, because it wears the shape of a confirmed finding.
*   **They differ in any way that matters** → adjudicate.

Be generous about what "differ" means. Different confidence, different scope, a number one found and the other did not — all qualify. The adjudicator is cheap relative to filing a wrong ticket or trusting a wrong refactor.

**In batch mode the adjudicator ALWAYS runs, whatever this comparison says.** The comparison reads verdicts and headline numbers; the grouping is a **per-subject assignment** sitting underneath them, and two angles can agree on the cause, agree on every number, and still put subject F in different groups — which this step cannot see and which decides what F's reporter is told. There is no cheap read that substitutes for it, so do not try to save the third agent here.

## 5. Adjudicate — through the same skill, and it RECONCILES rather than shrugs

**The adjudicator is dispatched exactly like the two angles: a sub-agent that invokes `/triage`**, with `--adjudicate --no-post --mode <inbox|plain> --project <resolved project> --primed none [--batch]` and the two report paths as its subject — **the same full flag set the angles got, for the same reason** (§3): it weighs a disposition against the project's Ticketing Strategy, and a modeless adjudicator weighs it against nothing. **The adjudicator is never primed** — `--primed none`, always, because priming is a licence to *lead* with the checklist and it leads with the two reports. The registry path still travels in its handoff, under the read scope this section sets below: the entry for any class the angles named, and no others. Same skill, same discipline, same report shape — what differs is its **subject** (the two reports, not the claim) and the **shape of its evidence budget**.

Hand-authoring its brief instead of invoking the skill is the same mistake as doing it for an angle. **The mistake is the substituted brief, not the agent type** — every dispatch names some registered agent type (`debugger` fits triage; `analyzer` and `general-purpose` also work), because `Agent(subagent_type: "triage")` does not exist and fails at the tool boundary. Name a real type, then make `Skill(skill: "triage")` its first instruction.

> ### 🔴 It MAY gather evidence — but ONLY evidence that discriminates between the two reports
>
> **The adjudicator is not a blind judge.** Its job is to *actually settle* apparent disagreements, and most of them are settled by one cheap, targeted check: re-run the query one angle ran and see which scope it used; count the map both cited and disagreed about; open the one file whose contents decide whose reading is right. **An adjudicator that returns "they disagreed, someone should measure X" when X was one command away has failed at its job**, exactly as an angle would have.
>
> **The line is PURPOSE, not tools.** It is drawn between two things that look similar and are not:
>
> *   ✅ **Reconciling evidence** — a check whose only function is to discriminate between claims **already on the record**. *"A says 1,937 and B says 1,702; I ran both predicates and A counted all coverage-scope facts while B counted `coverage.limit` only."* That is arbitration, and it is what this role is for.
> *   ❌ **New evidence** — a check that answers a question **neither angle asked**. The moment it opens its own line of inquiry it becomes a third investigator with a stake in its own answer, and its ruling becomes advocacy dressed as arbitration. If it finds such a question, it **names it in "what neither could reach"** and leaves it for the caller — that is a finding, not a failure.
>
> **Where an angle was primed with a known-signal registry (§2c), the adjudicator may read the entry for any class the angles NAMED — matched or ruled out — and no others.** This follows from the line above rather than adding to it: **a named class is a claim on the record.** The primed angle put class 4 on the record by excluding it, so opening class 4's entry to test whether the signal it cited really excludes it is arbitration. A class nobody mentioned is not on the record, and reaching for it — *"might class 12 apply here?"* — is investigation, which the registry makes cheap and cheap is what makes it likely.
>
> **Both halves are load-bearing.** Denying the adjudicator the registry entirely would leave it taking the primed angle's word that signal X rules out class 4, which puts the oracle back at the one step that exists to catch it — **requiring exclusions and denying the checker the means to check them is worse than not requiring them, because it looks rigorous.** Letting it browse the whole registry makes it a third investigator with a stake in its own answer, which is what this box forbids.
>
> **It is already auditable with the machinery below**: `## Checks I ran` requires every check to name the exact A-vs-B discrepancy it settles, and **a registry read for a class nobody named cannot name one**. No new mechanism is needed. **State the weakness plainly**: this is instruction, not structure — nothing physically prevents a wider read, unlike `¶INV_INDEPENDENCE_BY_CONSTRUCTION`, which no agent has to remember.
>
> **Every gathered fact is declared and attributed.** The report carries a **`## Checks I ran`** section: one entry per check, naming *the exact discrepancy it was settling*, the command, and the result. A check that cannot name the A-vs-B discrepancy it discriminates is by definition new evidence and should not have been run.
>
> **Prefer reading first.** Most apparent disagreements are not contradictions at all — they are a different denominator, a different scope, or a different question — and careful reading resolves them at zero cost. Reach for a command only when reading genuinely cannot decide.
>
> **This constraint is INSTRUCTION, not structure**, unlike `¶INV_INDEPENDENCE_BY_CONSTRUCTION`, which no agent has to remember. So it is **audited, not trusted** — and the audit is the `## Checks I ran` section, not a tool count. **A raw tool count no longer distinguishes a good adjudication from a bad one**, because a reconciling adjudicator legitimately runs commands; what distinguishes them is whether every command traces to a named discrepancy. Check that section, and say in the published result how many reconciling checks were run.
>
> **A GENUINE CONFLICT now means much more than it used to.** It is no longer "the reports differ and I could not read my way out of it" — it is *"I tried to settle this and the evidence needed does not exist yet."* That is a strong, expensive claim, and it should be rare. Name the single measurement that would settle it.

**Three outcomes, exactly one of which is a gap:**

*   **AGREE** — the angles land in the same place; the wrapper simply missed it. State the finding, **and carry both angles' confidence with it** — an AGREE where neither run got above low confidence is reported as *agreed but unestablished*, never as a settled result.
*   **RECONCILED** — they appeared to differ and do not. **Name the reason**, which is nearly always one of: a **different denominator** (1.43% *of documents* against 72.16% *of segments* — same funnel, incomparable quantities), a **different scope** (9,408 claims unfiltered against 2,662 filtered to one source), or **a different question** (one measured what the other assumed). *This is the highest-value outcome and the reason the adjudicator exists.*
*   **GENUINE CONFLICT** — they contradict on the same question at the same scope, and settling it needs evidence neither run has. **Name the single measurement that would settle it.**

**A genuine conflict is a successful run, not a failed one.** Its output is not "they disagreed" but *"here is the one thing to measure next"* — which makes the gap the next investigation rather than a shrug. Report it to the caller as a finding in its own right; the caller decides whether to spend that measurement now or proceed with the conflict recorded.

**The adjudication report carries these sections, all required:**

0.  **Checks I ran** — one entry per reconciling check: the exact A-vs-B discrepancy it was settling, the command, the result. **Empty is a valid and common answer** (careful reading settles most disagreements at zero cost) — but a check that cannot name its discrepancy is new evidence and should not have been run. This is the audit for `¶INV_ADJUDICATOR_RECONCILES_WITH_BOUNDED_EVIDENCE`.
1.  **Outcome per sub-question** — AGREE / RECONCILED / GENUINE_CONFLICT for the headline framing and for *each* number or claim the two treat differently. One verdict for the whole pair hides the interesting half.
2.  **The corroborated finding** — what a reader should actually believe, in plain language, **carrying the confidence it genuinely has.** Where it rests on one angle's medium-confidence reading, say exactly that rather than rounding up.
3.  **Where the angles disagreed** — never omitted. If they agreed on everything, say so explicitly; that is a reason to look again, not a gold star.
4.  **What neither could reach** — the questions still open after both runs, and the cheapest measurement that would close each.
5.  **On disposition** — the two recommendations side by side with the tradeoff, explicitly **not** a ruling (`¶INV_INTAKE_DISPATCHES_NEVER_EXECUTES`).
6.  **What the framing made both miss** — the shared-channel check (`¶INV_FRAMING_IS_A_SHARED_CHANNEL`). Both runs inherited one author's vocabulary; this is the only place in the method where its blind spots can surface, so an empty answer here is a claim that needs justifying, not a pass.
7.  **Groupings** — batch runs only, and required there. One entry per grouping: **the cause, the subjects it explains, and the evidence that assigns each subject to it.** Three rules make it usable downstream. **Every subject in the batch appears in at least one grouping** — a subject neither angle could place gets its own grouping named as unplaced, never a silent drop, because a dropped subject is a reporter who gets nothing. **A subject whose evidence spans several classes appears in each of them, by facet**, and is never forced whole into the largest; one drop spanning several scopes is an ordinary intake shape, and flattening it loses whichever facet lost the vote. **A grouping of one is a normal entry**, and so is a batch that returns N of them (§1b). **Each entry carries the per-subject specifics that survive from both angles' `## Per-subject` rows** — the ids, the counts, the dates, the sender, the value that subject actually showed. The fan-out is written from this section, so a grouping carrying only class-level facts has not finished its job, however right the class is.

## 6. Report

**Build ONE dossier** — concatenate, in this order, with a table of contents: the adjudication (or, where no adjudicator ran, a short note saying the two angles agreed), angle A's report, angle B's report, and the context pack, into `builds/triage-<subject-id>-dossier.md` (`<batch-id>` on a batch run — one dossier for the whole batch, because one investigation happened). **The context pack goes INTO the dossier — it is not dropped.** The adjudication carries a required *"what the framing made both miss"* section, and that is a criticism of the wrapper's **own wording**; a criticism nobody can check is worth little, so the thing being criticised must travel with it. It also makes the run reproducible in the way that matters: a reader can see what both angles were given, and therefore what they were never in a position to find. **Reason**: on the run that introduced this, the adjudication's sharpest finding was that three words of the wrapper's framing had steered both angles away from the screen and away from a live correctness hazard. That finding is unverifiable if the framing stays on the orchestrator's disk.

Return to the caller:

```
{ subject, mode: inbox | plain,   // and, when inferred rather than passed, what fired it
  angles: [primary, corroborating], reports: [path, path],
  primed: { angle, recipe } | null,       // what §1 resolved, and what fired it
  outcome: AGREE | RECONCILED | GENUINE_CONFLICT,
  finding,                    // the corroborated result, or null on GENUINE_CONFLICT
  disagreements: [ ... ],     // ALWAYS present; an empty array is a claim, not an omission
  settledBy,                  // on GENUINE_CONFLICT: the one measurement that would settle it
  dossier, repros: [ ... ],   // paths; plus commentUrl when --post was on
  crossPost: "on" | "off",                // "off" only under --no-cross-post
  pointers: [ { ticket, commentUrl, suppressedBy? } ] }  // one row per ticket the comment named; see § Cross-post a pointer
```

**`pointers` is built and returned whole whether or not the cross-post ran.** Under `--no-cross-post` every row carries `commentUrl: null` and `suppressedBy: "--no-cross-post"`, so the caller inherits the roster it now owns.

**`disagreements` is never omitted.** If two genuinely independent angles agreed on everything, say so explicitly — that is worth a second look, not a gold star.

**In batch mode the return carries three more fields and the block above does not change shape:**

```
{ ...,                          // every field above, unchanged
  batch: { count, inferred: <what fired it> | "--batch" },
  groupings: [ { cause, subjects: [ ... ], confidence } ],  // a grouping of one is a normal entry
  postedClasses: [ { grouping, commentUrl } ],             // one row per GROUPING, built from the groupings
  posted: [ { subject, servedBy, commentUrl } ] }          // one row per INPUT subject; see the two ledgers below
```

**`pointers` is a union across the class comments, not a per-class list** — one row per ticket named anywhere in what this run published, each linking the class comment that named it.

### Publishing (`--post`; ON by default in inbox mode)

**Nothing in this sub-section binds a silent run** — a `--no-post` wrapper finishes by returning the block above.

**When `--post` is on, publish ONE comment** on the origin thread — whether the outcome came from the cheap comparison or the adjudicator. The reporter sees one answer, not a debate. (**In batch mode this becomes a full comment per class plus a short one per member** — the same rule over more threads; § *Batch publishing* below.) **Return the posted comment URL to the caller**: that URL is what a caller's `triageAccounting` requires, and a run that investigated well and published nowhere has not finished (`¶INV_TERMINAL_PRODUCER_POSTS`). The accounting attaches here, to the posting path, and nowhere else.

> ### 🔴 The comment reports the SUBJECT. The dossier reports the METHOD.
>
> **Write the comment from `../triage/assets/TEMPLATE_TICKET_COMMENT.md`** (`¶INV_COMMENT_REPORTS_THE_SUBJECT_NOT_THE_METHOD`). It is addressed to **the person who owns the subject**, and every sentence above its one-line `<sub>` footer is about that subject: what's wrong · what the reporter got right and wrong · where (ids + deep links) · the evidence · how widespread · is it still happening · what to do · not established.
>
> **Detail is welcome — length was never the problem.** A long, dense, evidence-heavy comment is usually the right one. What must not appear is the *investigation as a subject*: the angles and what each led with, which run checked which object, whether the convergence was genuine, the adjudicator's per-question outcomes, the critique of this wrapper's own framing. **All of that is real and all of it belongs in the dossier.**
>
> **Measured, not theoretical.** This section used to require the comment to carry *"the verdict, the angles used, where they disagreed"*, plus the context pack attached for audit. On [FIN-3940](https://linear.app/finchclaims/issue/FIN-3940) that produced a comment roughly half of which taught the reader about triangulation — a product owner who wanted to know whether a money column was still wrong. **The wording above did that, not the agent following it.**
>
> **Translate, don't delete.** Each thing you cut has a content-shaped sibling that must survive. The method sentence goes to the dossier; its sibling goes in the comment:
>
> *   **"Angle A checked `bf6d3b5de`, angle B checked `06570f5c4`"** → *"the same change exists under two SHAs, so checking either alone is misleading"*
> *   **"medium-high confidence — the predicate was never run"** → *"nobody has confirmed X on this document; this one query settles it"*
> *   **"the framing steered both angles away from the screen"** → *"is today's $157,514.60 correct? Nobody has checked"*
> *   **"no GENUINE_CONFLICT; every contradiction reconciled"** → nothing; the reader needs the reconciled facts, not the reconciliation
>
> The left side is not worthless; it is worthless **here**. It is how the method improves, so it ships in the dossier where the people who maintain the method read it.

**Link the dossier once — beside the synthesis, not instead of it** (`TEMPLATE_TICKET_COMMENT.md` carries the per-reader card list; the dossier is the *auditor's* card, and the reader who owns the subject gets the readable report as its own). Upload it and embed it as a clickable `[📄 filename](assetUrl)` **alone in its own block with nothing after it** so Linear renders a preview card (`§INV_CHANNEL_EVIDENCE_RIDES_THE_COMMENT` — naming a file in prose is not linking it). **One dossier, not four fragments**: the workings are one reader's question, and whoever wants them wants all of them at once — so the adjudication and both angle reports travel together rather than as competing cards. That is a rule about *this* card's contents, not a cap on how many cards the comment carries; the synthesis and each angle's repro are different readers and get their own. **What changed when the context pack moved inside the dossier is only the destination** — it is published there rather than as a fourth card on a product ticket. Do not read that as the safeguard being removed and restore the old behaviour.

**Upload each angle's repro script as its own attachment — one per angle, never merged.** The dossier stays one card because it is prose; a script is executable and is read by whoever takes the fix, not by the reporter. Two angles that both drove the app produce **two** attachments, each named for its angle (`builds/triage-<subject-id>-<angle>-repro.ts`), because they may reproduce different things at different screens and merging them loses both the attribution and probably one of the repros. **Scripts are TypeScript unless the subject's own language says otherwise — never Python** (`/triage` §Reproduce carries the reasoning); an angle that returns a `.py` did not follow the protocol, so say so when you upload it rather than passing it on silently. The angles run `--no-post` and upload nothing themselves — they return their paths, and **this wrapper uploads them** alongside the single dossier link. An angle that wrote no script contributes no attachment; say so in one clause rather than leaving the reader to wonder.

### Cross-post a pointer to every ticket the finding names

**Every ticket the published comment names gets a one-line pointer posted on it. Every one, unconditionally** (`¶INV_EVERY_NAMED_TICKET_GETS_A_POINTER`). The rule, the shape and the three fills are in `../triage/assets/TEMPLATE_TICKET_COMMENT.md` § *The pointer*, shared with `/triage` deliberately — **a rule binding only one entry point is undone by running the other**, and these two are the same rule reached through two doors.

**`--no-cross-post` turns it off, and nothing else does. The default is ON.** The flag exists for a caller who owns the decision and has a reason the run cannot see — a phase that forbids writes onto other people's tickets, a wrapper that publishes its own updates — exactly as `--mode plain` exists for a wrapper that owns publishing. **Measured**: the first caller of the batch path was in such a phase and turned the cross-post off in handoff prose, which worked only because the run happened to read it. A steer that has to survive prose is a steer that goes missing.

> ### 🔴 The off switch is not the change-based refinement, and it does not reopen it
>
> The refused refinement asked the **run**, at the end of its work, to judge per ticket whether a mention mattered — and the judgement is the failure mode. This is one decision, made **once**, by the **caller**, over the **whole roster**, before anything is dispatched. **Flag absent: every named ticket gets a pointer, and none is skipped for reading borderline. Flag present: none does.** A run that posts to some of its roster has invented a middle that does not exist.
>
> **Off is a stated choice rather than an omission.** Say `cross-post: off (--no-cross-post)` in the run's own line, **build the roster anyway**, and return it whole with every URL empty and the suppression named — so the caller can post the pointers itself and can see exactly what it switched off. A suppressed roster nobody can read is the silent failure the unconditional rule was written against, arriving through the door marked *permitted*.

**Build the roster before the first post**, from the comment body: every ticket key above the `<sub>` footer, minus the thread the comment lands on. **Do not narrow it to the tickets the finding changes.** *Measured*: a run named five tickets in one published comment and one of them learned about it, because the operator noticed and asked — while a ticket whose stated count the finding had just corrected, and a ticket whose acceptance signal the finding had just shown to be hazardous, were told nothing. A change-based rule would have scored the second as borderline, since it was flagged only as a hazard. **The judgement is the failure mode; removing it is the point.**

**The pointer links the published comment, never the dossier.** The dossier is the auditor's card and it is already on the origin thread; a reader arriving from a pointer wants the finding first and reaches the workings through it. **One pointer per ticket, not one per comment** — on a batch run the roster is the union across the class comments and the pointer links whichever class comment named that ticket.

**Return one row per pointer** (`{ticket, commentUrl}`). The same gate that binds the finding binds these (`¶INV_TERMINAL_PRODUCER_POSTS`): an unposted pointer is invisible in exactly the way an unposted finding is. On the run that earned this rule, four tickets were never told and every visible artifact of the run still looked complete.

### Batch publishing — one FULL comment per class, a short one per member

**One subject, one comment. Everything above is unchanged and this sub-section is not for that run.**

> ### 🔴 BATCH IS NOT SPECIAL
>
> **Per class, a batch publishes exactly what a single-subject run publishes for its subject** — a standalone comment carrying the complete output: what's wrong, where, the evidence, how widespread, whether it is still live, the duplicate and related tickets with the routing, the recommendation, what is not established. **Never strip a class comment on the grounds that it belongs to a batch.** Anything a single triangulation would have said, the class comment says.
>
> **The saving is in the investigation and in the dossier. There is no saving in the output.** A batch is N single runs that share one investigation — which is why a batch that splits all the way down (§1b) is literally N singles, and reads correctly as such.

**The unit is the CLASS, not the batch:**

*   **A class comment — one per grouping.** A full single-run comment standing on its own, from `../triage/assets/TEMPLATE_TICKET_COMMENT.md`, filled as if this class were the only thing triangulated. It owns the class-to-ticket routing, the dedupe against existing tickets, and the recommendation.
*   **A member comment — one per subject the class explains.** **Short**: that subject's own specifics, one line saying which class explains it, a link to the class comment, and the dossier. **No second copy of the ticket routing on a member** — it lives on the class comment and the member points at it, because two copies of a routing table drift and the member's is the one nobody updates.
*   **Unrelated classes never share a comment.** That is the *only* thing batch mode does differently from running the subjects separately.
*   **A subject whose evidence spans several classes attaches to each of them BY FACET** — never one comment averaging two causes into a blur. One drop spanning several scopes is an ordinary intake shape rather than an anomaly. Two substantial facets get two member comments, each pointing at its own class comment. **A thin single facet rides as a sentence inside that subject's primary-class member comment instead of earning a standalone one** — naming its class and linking that class comment in the same sentence.
    **Thin means the facet's whole content is a line or two, with no evidence of its own** — nothing this subject specifically showed for that class beyond what the class comment already carries. *Measured at N=2*: the split read as proportionate where both facets were genuinely different and each reporter needed their specific one, and as overhead where a member was a lone thin facet — a one-line footnote got a standalone comment heavier than the signal in it.
    **This governs where a facet is RENDERED, never whether it is FOUND.** The grouping keeps every facet (§5, *Groupings*), and the same run proved why: a subject spanning three classes would have flattened to one label and silently lost two of them without faceting. A run that drops a facet from the finding to save a comment has done the thing the facet rules exist to stop. **The subject ledger records the one URL against both classes**, so a ridden facet still reconciles.

**Where the class comment goes**: on the class's own ticket where one exists, otherwise on the **representative member's thread** — the member whose material is most complete. **When it lands on a member's thread, fold that member's own specifics into it and post no separate member comment for them**; they are served by the comment already on their thread, and the ledger records that URL as theirs.

**Richest representative wins, and two class comments on one thread is correct rather than a collision.** Where two classes both resolve to the same member, that member is the richest representative of both and both class comments land there. Do not spread classes across threads for balance, and do not hold to one home per thread. **The reason is the reason richness picks the home at all: the representative's own material *is* that class's primary evidence**, which is what makes the comment read as a finding about this thread rather than as someone else's report parked on it. *Measured*: two full class comments legitimately landed on one thread on the first real batch run, and it read fine.

**A class with no owning ticket homes on its DEFINITIONAL member** — the subject whose own material is the class's primary evidence — **and its routing says `no single owner`, plus one line that the class is a graduation candidate in its own right.** Do not invent an owner and do not attach the class to the nearest plausible ticket to have one: an unowned class is a real finding about what the record does not yet track, and folding it into a neighbour is how it stops being visible. *Measured*: this was the least-confident call on the first real batch run, and the run settled it — write it as settled.

**A member comment's specifics come from that subject's own material** — its ids and deep links, its own counts and dates, its sender, what its own evidence showed — read from the subject's origin body and the adjudicator's `## Groupings` rows. **Not from the class finding**, which does not contain them:

> ### 🔴 A name-swap member comment is impossible, not merely poor — and that is a measurement
>
> On the trial batch the adjudicated finding was entirely **class-level**: the retrieval mechanism, an org-wide 64,905-never-retrieved against 27,395-found-but-gated split, and a class-to-ticket map. **It carried zero per-cohort specifics.** Making each of the eight comments genuinely about its cohort meant going back to the original signal bodies — one cohort's claim id and carrier number, another's row count and sender address, a third's carrier claim number. **Those facts are not in the adjudicated finding to reuse**, so no amount of careful rewriting recovers them.
>
> **Test your draft**: if a member comment contains nothing that is *false of the sibling members*, you have not written one.

> ### 🔴 The reader must not have to learn what a batch is
>
> `¶INV_COMMENT_REPORTS_THE_SUBJECT_NOT_THE_METHOD` binds both kinds of comment exactly as it binds a single one, and batch adds its own forbidden vocabulary above the `<sub>` footer: `batch` · `cohort of` · `the other reports` · `these eight` · `the sibling threads`. Someone who owns one subject is owed a finding about theirs, not an account of the seven investigated beside it.
>
> **Translate, don't delete.** A sibling's evidence usually does change what is true of *this* subject, and that half is content: *"the same cause is live on 27,395 of the org's 95,386 links"* is breadth and belongs in the comment; *"seven other reports were investigated with yours"* is method and belongs in the dossier. A member comment naming its class comment is content too — it is where the rest of the answer is, not a note about how the run was organised.
>
> **Draw the line where the invariant already draws it. How widespread the defect is is a fact about the SUBJECT and goes in the comment; the roster of which threads this run spanned is a fact about the INVESTIGATION and goes in the dossier.** So naming a sibling **as a place the same defect is live** is breadth and stays — *"the same hold sits behind the Belton and Brandon Steven reports"* tells this reader how far their problem reaches. Naming siblings **as what else was looked at** is roster and goes: that is what `these eight` · `the sibling threads` · `the other reports` mark, and the forbidden list is unchanged. *Measured*: a run wrote a breadth sentence naming two sibling subjects, had to judge it against that list with nothing in the contract to judge by, read it as content, and was right.

**The fan-out is a WRITE, not an investigation — so it does NOT go through `/triage`.** `¶INV_DISPATCH_THROUGH_THE_SKILL` binds every run that **establishes** something, and all three of those — both angles and the adjudicator — are unchanged in batch mode. Composing comments out of evidence already on the record establishes nothing, and re-dispatching the skill per subject would re-run the investigation N times, the exact cost this mode exists to avoid. **This is not a licence to hand-author an investigation brief.** A writer that finds it needs a fact nobody gathered does not go and gather it — it writes that fact into that comment's *Not established* with the cheapest thing that would settle it, and the gap stays visible.

**One dossier for the whole batch, linked from every comment — class and member alike.** One investigation happened, so there is one record of it: `builds/triage-<batch-id>-dossier.md`, carrying the adjudication (with its `## Groupings`), both angle reports and the context pack. **It uploads once per comment**, because attachments are comment-level; the same file on several threads is correct and is not a duplicated card. Do not split it into per-class dossiers — the workings are one reader's question and that reader wants all of them at once.

> ### 🔴 A repo path in a footer is not a link
>
> **Measured**: the first real batch run put its workings in the `<sub>` footer as a `builds/…` repo path. **A teammate without repo access cannot open that**, and a reader who could still has to go find it — which is exactly what `§INV_CHANNEL_EVIDENCE_RIDES_THE_COMMENT` already forbids for the single-subject dossier further up this section: *naming a file in prose is not linking it.* The rule did not fail; the batch path simply never inherited it, because nobody wrote that it did.
>
> **It inherits it unchanged.** Every comment this mode publishes — class and member alike — carries the workings the way a single-subject run carries them: **`prepare_attachment_upload`, PUT the bytes, then embed the returned `[📄 filename](assetUrl)` alone in its own block with nothing after it on that line**, so the tracker renders a preview card instead of plain text. The `<sub>` footer names the method, the provenance and the date. It is not where a file goes.

#### The accounting is TWO ledgers, because a missing member comment is the quiet one

A missing **class** comment is loud: it is the thing the caller asked for and the first thing anyone opens. A missing **member** comment is silent — it lives on a thread this run may never look at again, every visible artifact of the run still looks complete, and the reporter is left exactly where the mode found them. So neither ledger is built from what got posted (`¶INV_TERMINAL_PRODUCER_POSTS`):

*   **The class ledger is built from `## Groupings`, before the first post** — one row per grouping, URL filled in as its comment lands. The adjudicator produced that list, so the wrapper cannot shorten it to match what it managed to publish.
*   **The subject ledger is built from the INPUT subject list, before the first post** — one row per subject, and **every row must resolve to a URL on that subject's own thread**, whether that is its own member comment or a class comment that landed there. The question is not *did I post N times* but *does every subject the caller handed me now have an answer on their own thread*, which is the question the mode exists to answer.
*   **The two must RECONCILE, and that reconciliation is the check.** Every subject row names **every class its evidence reached** — two for a subject with a facet in each, whether those facets earned two comments or one comment carrying a ridden thin facet; every class row is named by at least one subject row. A class nobody names is a grouping with no members — invented. **A subject naming no class was dropped somewhere between the grouping and the posting, and is the quiet failure this pair of ledgers exists to make loud.**

Return both ledgers whole. An empty URL is a failed run rather than a short one, and a caller can count rows against the subjects it passed without reading a word of the finding.

## Critical Invariants

*   **¶INV_ANGLE_IS_A_LEAD_NOT_A_FENCE**: An angle names **where a run starts and what it is trying to establish**. It never limits what evidence that run may reach — **every run may use every tool**, and one that needs the other's usual instrument to settle its own claim simply uses it. Diversity comes from **different leading questions**, which change what gets *found*; independence comes from **parallel dispatch with no sight of each other's conclusions**, which `--no-post` already provides. **Reason, measured**: an earlier version fenced each run to a single evidence base, and both runs then reported that the one thing they could not settle sat inside the other's fence — so the wrapper recorded low confidence on exactly the question an unfenced run would have answered, and one apparent disagreement turned out to be an artifact of each seeing half the picture. **A restriction that manufactures the uncertainty it exists to detect is worse than none.** Single-lead output remains a **hypothesis** until corroborated, and may not be cited as fact in a ticket, a disposition or a board.
*   **¶INV_INDEPENDENCE_BY_CONSTRUCTION**: The two runs are independent because **nothing they produce is visible to each other** — dispatched simultaneously from identical state, writing to different files, neither posting. Independence is a property of the arrangement, not a rule either agent has to remember. **Symmetric shared context does not compromise it**: both seeing the same prior-wave results is fine; seeing each other's *conclusions* is not. Prefer structure over instruction wherever the choice exists — a prohibition an agent must recall is weaker than a mechanism that makes the failure impossible, and this one dissolved the moment posting moved to the caller.
*   **¶INV_DISPATCH_THROUGH_THE_SKILL**: Every run this wrapper spawns — both angles **and** the adjudicator — is a sub-agent that **invokes `/triage`**. The wrapper writes the handoff and names the flags; it never hand-authors a brief in the skill's place. **It does name an agent type — it must**, because `subagent_type` accepts only registered agent types and `"triage"` is not one of them (`Agent type 'triage' not found`). Pick a registered type whose posture fits (`debugger` for triage) and make `Skill(skill: "triage")` the first instruction; what is forbidden is substituting your own brief for the skill's, not the act of choosing a carrier. **Reason, measured**: a wrapper run substituted two hand-written `general-purpose` briefs. The angles did good work and the substitution still cost three things simultaneously — reports in bespoke shapes instead of `TEMPLATE_TRIAGE_REPORT` so nothing downstream could parse them; no inheritance of the triage skill's own guardrails (resolve the subject before investigating · open the attachments and never `curl` an `assetUrl` · read all three surfaces in inbox mode · Directions outrank the recipe · Ticketing Strategy bounds the recommendation · branch by claim shape); and, because the wrapper had taken over agent selection, an **unconstrained agent type for the adjudicator**, whose whole contract is that it may not investigate. **The operator caught it; the wrapper did not.** The loss is invisible precisely because a bespoke brief returns long, confident, well-structured work — it just is not the protocol. Mechanical check: the dispatched agent's transcript must contain a `Skill` call for `triage`; absent that, the output is an unstructured opinion, not a triage. **What it binds is every run that ESTABLISHES something**, which is why a batch changes nothing here: both angles and the adjudicator still go through the skill, once, over the whole batch. Writing the class and member comments afterwards composes evidence already on the record, establishes nothing, and sits outside this rule rather than being an exception to it — and that is not a doorway back to hand-authored briefs, because a writer that needs an ungathered fact records it as unestablished instead of going to gather it.
*   **¶INV_ADJUDICATOR_RECONCILES_WITH_BOUNDED_EVIDENCE**: The adjudicator **may gather evidence, but only evidence that discriminates between claims already on the record.** Re-running a query one angle ran to find which scope it used, counting a map both cited and disagreed about, opening the one file that decides whose reading is right — all arbitration, all encouraged. Opening a line of inquiry **neither angle asked** is not: that makes it a third investigator with a stake in its own answer, and turns its ruling into advocacy dressed as arbitration. Such a question goes into *"what neither could reach"* as a finding. **The line is purpose, not tools.** **Reason**: the blind version produced excellent reconciliations and then hit a wall it could not pass — it reported that neither angle had run an in-tree parity command that would have settled what a config change actually surfaces, and could not run it either. *"They disagreed, someone should measure X"* when X is one command away is a shrug, not a ruling. **Audited, not trusted**: every gathered fact is declared in a **`## Checks I ran`** section naming the exact discrepancy it settles, and a check that cannot name its discrepancy is by definition new evidence. **A raw tool count no longer distinguishes a good adjudication from a bad one** — a reconciling adjudicator legitimately runs commands — so the audit is that section. Consequence worth stating: **GENUINE_CONFLICT becomes a much stronger claim**, meaning *"I tried to settle this and the evidence does not exist yet"*, and should be rare. **Applied to a primed angle's known-signal registry (§2c), the same line scopes the read: the entry for any class the angles NAMED — matched or ruled out — and no others.** A named class is a claim on the record, so testing whether the cited signal really excludes class 4 is arbitration; *"might class 12 apply?"* is a new line of inquiry the registry merely makes cheap. **Both halves matter**: denying the registry entirely leaves the adjudicator taking the primed angle's word, which puts the oracle back at the step that exists to catch it, and requiring exclusions while denying the checker the means to check them is worse than not requiring them because it looks rigorous. **Already auditable** — a registry read for a class nobody named cannot name its A-vs-B discrepancy, so `## Checks I ran` catches it with no new mechanism. **Instruction, not structure**: nothing physically prevents a wider read.
*   **¶INV_ADJUDICATOR_GATHERS_NOTHING**: **Superseded by `¶INV_ADJUDICATOR_RECONCILES_WITH_BOUNDED_EVIDENCE`.** Its prohibition on *all* gathering was too strong: it prevented advocacy at the cost of preventing reconciliation, which is the role's actual purpose. Retained as an alias for existing cross-references; the "no new lines of inquiry" half survives intact in the successor.
*   **¶INV_FRAMING_IS_A_SHARED_CHANNEL**: The two runs are independent of each other and **both inherit the wrapper's framing of the question** — the one dependency the angle split does nothing about. **Triangulation protects against method blind spots, not against a badly-framed question**, and two angles agreeing on the wrong question is *more* persuasive than one wrong answer, not less. Therefore at least one brief must license rejecting the premise: *"if the premise is wrong, say so and explain why — that is a more useful answer than answering it."* Hand each run the claim as a **claim to be tested**, never as background to assume. **Reason**: the first real run survived this hole by luck — the premise happened to be checkable from one angle's evidence base. Had both bases been silent on the framing, both would have answered obediently and agreed, and the agreement would have been believed harder for being unanimous. **In a batch this channel widens**, because the tempting framing is a cause: *"establish why X keeps happening"* hands both angles the class as a premise across every subject at once, and the answer comes back once per subject. Frame a batch as *"these subjects may share a cause or may be several — group them"*, and let the grouping be the finding. **Measured — the first SURVIVAL of this rule rather than an avoidance of it**: the trial batch was framed around one named class; both angles rejected it anyway (one replacing *matching* with *retrieval*, the other falsifying the premise outright) and the adjudicator went on to refute the code angle's own replacement hypothesis. **The licence worked, and the framing was still wrong** — the run was lucky that the named class was cleanly splittable, and a subtler batch would have been railroaded by the same wording with nothing to catch it. Record both halves: a version of this story that stops at *"our angles handled it"* teaches the next author to keep writing leading framings.
*   **¶INV_WEAK_AGREEMENT_IS_NOT_CORROBORATION**: An AGREE where **both** runs report low confidence may not stand as a verdict — two shallow runs matching is two guesses matching. Report it as *"agreed but unestablished"*, name what neither could reach, and leave the subject un-triaged. Every verdict carries both angles' confidence, so a reader can tell corroboration from coincidence. This is the most seductive false positive the process can produce, because it arrives wearing the shape of a confirmed finding.
*   **¶INV_DISAGREEMENT_IS_THE_PRODUCT**: A gap between angles is a finding, not a failure to resolve. Never average two answers, never silently prefer the more confident one, and never drop the quieter angle's result. **One route into "silently prefer the more confident one" is worth naming, because it arrives looking like rigour**: an angle primed with a project's known-signal recipe comes back more specific and more confident than its open partner every time, so an adjudicator defers to it and the open angle degrades into a rubber stamp. **The guard is `¶INV_A_PRIMED_ANGLE_REPORTS_ITS_EXCLUSIONS`** — a primed angle that reports only what it matched is an oracle nobody can argue with; one that reports what it ruled out and on what signal is a peer with an attackable surface. The pass that found a defect by noticing a screen and a query disagreeing would have found nothing under a process that harmonises. **This survives `¶INV_COMMENT_REPORTS_THE_SUBJECT_NOT_THE_METHOD` intact, and the two are easy to collide by accident** — "no method-talk in the comment" must never become "the disagreement disappeared". The line is what the disagreement is *about*: a gap that changes **what is true of the subject** is content and belongs in the comment; the *account of who found what* is method and belongs in the dossier. Worked example, from the run that earned both rules: *"the same change exists under two SHAs, so checking either one alone is misleading"* is a fact about the codebase that a reader needs — it goes in. *"Angle A checked `bf6d3b5de` while angle B checked `06570f5c4`"* is a fact about the investigation — it goes in the dossier. **If cutting the method sentence also deletes a fact, you cut too much: translate it, don't drop it.** **A grouping is disagreement with the CALLER's premise** — the claim that these subjects are one thing — so it is a finding of exactly this kind and must survive into the output. Never collapse a split into the largest group for a tidier set of comments, never absorb a subject the angles could not place into a convenient neighbour, and never flatten a subject whose evidence spans two classes into whichever one won.
*   **¶INV_COMMENT_REPORTS_THE_SUBJECT_NOT_THE_METHOD**: The single published comment is addressed to **the person who owns the subject**, and reports the subject. The workings are a *different artifact for a different reader* — bundled into one dossier and linked once, never pasted into the body. Method-talk gets one `<sub>` line naming the method, the provenance and the date. **Detail is not the enemy**: a long, dense, evidence-heavy comment is usually the right one; a comment that spends its length on how the answer was reached is not. Shared with `/triage` via `TEMPLATE_TICKET_COMMENT.md`, deliberately — a rule that binds only the wrapper is undone by running the other entry point. **Reason, measured**: §6 of this skill used to *require* the comment to carry "the angles used, where they disagreed" and to attach the wrapper's own briefing pack for audit. On [FIN-3940](https://linear.app/finchclaims/issue/FIN-3940) that produced a comment roughly half of which taught a product owner about triangulation while they were trying to find out whether a money column was still wrong. The findings underneath were correct and well-evidenced, which is what makes the failure worth an invariant: **good work posted at the wrong reader still fails.** **In a batch the forbidden vocabulary grows** — `batch` · `cohort of` · `the other reports` · `these eight` · `the sibling threads` — because someone who owns one of several subjects is owed a finding about theirs, not an account of the others investigated beside it. What a sibling's evidence proves about **this** subject is content and stays, stated as breadth; and a member comment naming its class comment is content too, because that is where the rest of their answer is. **The line runs between breadth and roster: how widespread the defect is is a fact about the subject and belongs in the comment, while which threads the run spanned is a fact about the investigation and belongs in the dossier.** So a sibling named as a place the same defect is live is breadth and stays — *"the same hold sits behind the Belton and Brandon Steven reports"*; siblings named as what else was looked at are roster and go, which is what the forbidden phrases mark. *Measured*: a run wrote that breadth sentence, judged it against the forbidden list with nothing in the contract to judge by, read it as content, and was right.
*   **¶INV_EVERY_NAMED_TICKET_GETS_A_POINTER**: A published finding that names another ticket posts a **one-line pointer** on that ticket — **every ticket named, unconditionally**, with no test for whether the mention matters. The roster is built from the comment body before the first post, and each pointer's URL is returned beside the finding's own. **A pointer is one or two sentences** — what routed here, from where, what the finding corrects about *this* ticket — plus a link back to the published comment; it is never the finding, the dossier or a copy of the comment, which stay on the origin thread and travel by link. **It must still say something, or say what changed**: a bare *"you were mentioned"* is noise the tracker already renders, and a stub on a busy ticket teaches people to skip its comments. **Shared with `/triage` via `TEMPLATE_TICKET_COMMENT.md`, deliberately** — a rule binding only one entry point is undone by running the other. **Reason, measured, and it is why the unconditional half is load-bearing**: a run named five tickets in one published comment and only one of them learned about it, because the operator noticed and asked; among the four told nothing were a ticket whose stated count the finding had just corrected and a ticket whose acceptance signal the finding had just shown to be hazardous — which a change-based rule would have scored as borderline, since it was flagged only as a hazard. **The cost was already paid before the rule existed**: the same run rediscovered a finding that had sat three weeks on one of the tickets it cited — same mechanism, same code sites, same symptom refutation, posted by an earlier two-agent investigation — having named that ticket without reading it. **The judgement is the failure mode; removing it is the point.** In a batch the roster is the **union across the class comments** and each pointer links the class comment that named it: **one pointer per ticket, never one per comment**. **The cross-post is ON by default and `--no-cross-post` is the only thing that turns it off** — a caller who owns the decision and has a reason the run cannot see, exactly as `--mode plain` exists for a caller who owns publishing; the default writes onto other people's work tickets, which a phase forbidding such writes may not want. **That switch is not the refused refinement returning**: it is one decision, made once, by the caller, over the whole roster, before dispatch — never the run judging per ticket at the end whether a mention mattered, which is the judgement that failed. There is no middle: flag absent, every named ticket gets a pointer; flag present, none does, the roster is still built and returned whole with empty URLs and the suppression named, and the run says `cross-post: off` out loud.
*   **¶INV_A_PRIMED_ANGLE_REPORTS_ITS_EXCLUSIONS**: Where a project publishes a known-signal recipe — a forensic checklist, a registry of known root causes with their recognition signatures — **at most one angle is primed with it**, and that angle reports **what it ruled out and on what signal**, not only what it matched. **Priming is INFERRED from the resolved project and overridable with `--primed <path>`, resolved once by the wrapper and written into every dispatch string** — the recipe path into the primed angle, `--primed none` into its partner and into the adjudicator. Inferred rather than passed for the reason inbox mode and batch are: a flag is a thing a caller forgets, and this forgetting is invisible, because a classification with no exclusions returns looking more authoritative than one with them. No angle re-infers it — an angle holds a handoff path and cannot see the handbook behind it. **Where no registry exists nobody is primed**, both reports read `not primed`, and the pair behaves as it did before priming existed. **At most one, because a shared checklist is a shared channel in the `¶INV_FRAMING_IS_A_SHARED_CHANNEL` sense and far more specific than framing**: both angles would open the same columns and walk the same traversals, the checklist's blind spots would become the pair's, and their agreement would be replication. **Exclusions, because a primed angle is otherwise privileged** — always more specific and more confident than the open one, so an adjudicator defers to it and the open angle degrades into a rubber stamp, which is the harmonising `¶INV_DISAGREEMENT_IS_THE_PRODUCT` forbids arriving by a route that invariant does not name. *"Matched class 7"* is an **oracle**: unfalsifiable, and the other angle has nothing to argue with. *"Matched 7; ruled out 4, 11 and 19, and here is the signal that excluded each"* is a **peer** — the exclusions are the surface the other angle and the adjudicator can attack. **A bare classification hides exactly the part that makes it checkable.** The fix is the exclusions, **not the agent count**: a third angle does not cure an oracle. **The primed angle still picks a different base from its partner** — a checklist that opens stored rows is a `db` angle carrying a prior, so pair it with something that opens a different artifact, under the mechanical test in §2b. The exclusions land in the report's `## Ruled out` section (`TEMPLATE_TRIAGE_REPORT.md`), so the requirement does not collide with follow-the-template-exactly.
*   **¶INV_BATCH_IS_INFERRED_FROM_ITS_DESTINATIONS**: Batch mode turns itself on when the pack carries **more than one subject**, and the test is mechanical: **count the places a finding would be posted.** Several threads, tickets or reporters means several subjects; one destination is one subject however many URLs, screenshots and query results the pack piles around it. `--batch` forces it on where the inference has nothing to fire on. **Inferred rather than passed, for the reason inbox mode is**: a flag is a thing a caller forgets, and this forgetting is invisible — the run returns one investigation, one confident dossier and one comment, all of which look right, and the failure is the people on the other threads who were never told anything, which nothing in the returned result shows. **With one subject the whole mode is dead text**: the single-subject path is unchanged, end to end.
*   **¶INV_GROUPINGS_ARE_DISCOVERED_NOT_SUPPLIED**: A batch establishes **whether** its subjects share a cause; it is never told that they do. Frame it to the angles as *"these subjects may share a cause, or may be several — group them"*, never as *"establish the cause of X"*, and treat the set of *{cause, the subjects it explains}* as the normal return. **A grouping of one is a grouping**, and a batch of eight returning eight of them is a **success**: the likelier batch in the wild is eight things that merely arrived together, and splitting them all the way down reports exactly that while still giving every reporter a finding about their own subject. It reads like the mode did nothing; it did the most useful thing available to it, and the output is then literally N single runs sharing one investigation. Say so where someone might later "fix" it. **The failure is the opposite shape** — one cause asserted over N subjects because the framing named a class and both angles were polite about it. Every subject appears in **at least one** grouping, a subject neither angle could place gets one of its own marked unplaced, and a subject whose evidence spans classes appears in each by facet rather than being forced whole into the largest.
*   **¶INV_BATCH_IS_NOT_SPECIAL**: **Per class, a batch publishes exactly what a single-subject run publishes for its subject** — a standalone comment carrying the finding, the mechanism, the evidence, the breadth, whether it is still live, the duplicate and related tickets with their routing, the recommendation and what is not established. **Nothing is stripped on the grounds that a batch produced it.** The unit is the **class**, not the batch: each class gets its own full comment, unrelated classes never share one, and every member gets a short comment carrying **its own** specifics plus a link to its class comment — never a second copy of the routing, which would be the copy nobody updates. A subject spanning several classes attaches to each by facet; **a thin facet — a line or two with no evidence of its own — rides as a sentence inside that subject's primary-class member comment rather than earning a standalone one, which is a rule about where a facet is rendered and never about whether it is found.** **Every comment carries the workings as an uploaded attachment**, class and member alike, through `prepare_attachment_upload` and embedded as a card — a repo path in the `<sub>` footer is not a link, and a teammate without repo access cannot open one. **The saving is in the investigation and the dossier; there is no saving in the output**, and a batch is best read as N single runs that share one investigation.
*   **¶INV_MEMBER_COMMENT_IS_WRITTEN_FROM_ITS_OWN_MATERIAL**: A per-member comment is tailored from **that subject's own rows** — its ids and deep links, its own counts and dates, its sender, what its own evidence showed — read from the subject's origin body and the adjudicator's groupings. **A name-swap is not merely poor here; it is impossible.** *Measured*: on the trial batch the adjudicated finding was entirely class-level (the retrieval mechanism, an org-wide 64,905-never-retrieved against 27,395-found-but-gated split, a class-to-ticket map) and carried **zero per-cohort specifics**, so making each comment genuinely about its cohort meant going back to the original signal bodies for one cohort's claim id and carrier number, another's row count and sender address, a third's carrier claim number. **Those facts are not in the class finding to reuse**, and no amount of rewriting recovers them. So the requirement lands at **dispatch**: both angles receive every subject's own material rather than a list of names, and every angle report returns a `## Per-subject` row per subject. Test a draft by asking whether it contains anything *false of the sibling members* — if not, it was not written for this one.
*   **¶INV_TERMINAL_PRODUCER_POSTS**: Whoever produces the *finding a reader should act on* publishes it, once — **on a run that was asked to publish.** A single triage run with `--post` posts its own finding; under triangulation the two runs pass `--no-post` and **the wrapper posts one comment**, reporting the subject with the workings bundled into one linked dossier (`¶INV_COMMENT_REPORTS_THE_SUBJECT_NOT_THE_METHOD`). Intermediates never appear on the thread as if they were conclusions. **And the guard against an unposted report is the GATE, not the poster**: whoever posts returns the resolvable comment URL, and the caller's accounting cannot complete without it. One wave lost three complete investigations to a posting step that was a trailing bullet with nothing checking it — moving the write around would not have helped; making it verifiable does. **The gate binds the posting path only**: a `--no-post` run owes no comment URL, and demanding one of it would be a requirement no silent run could ever satisfy. **It binds the cross-posted pointers the same way** (`¶INV_EVERY_NAMED_TICKET_GETS_A_POINTER`) — one returned URL per ticket the comment named, because an unposted pointer is invisible in exactly the way an unposted finding is. **`--no-cross-post` moves that gate rather than removing it**: the roster is still built before the first post and returned whole, each row carrying `suppressedBy: "--no-cross-post"` instead of a URL, so the caller who took the decision inherits a countable list of what it now owns. An empty URL with no suppression named is still a failed run. **In a batch the gate is TWO ledgers, because the two kinds of post fail with different volumes.** A missing class comment is loud — it is what the caller asked for. A missing member comment is silent: it sits on a thread the run never revisits while every visible artifact still looks complete. So the class ledger is built from the adjudicator's `## Groupings` and the subject ledger from the INPUT subject list, both before the first post, and **every subject row must resolve to a URL on that subject's own thread**. The two reconcile — each subject row names a class row, each class row is named by at least one subject row — and a subject naming no class is the quiet failure surfacing as an empty row rather than as an absence nobody can see.
