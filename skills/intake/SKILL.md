A wave-based inbox grooming pass: drain new feedback, organize + consolidate, triage each signal to an outcome, close with a debrief. The next wave resumes from Linear.

# /intake Protocol (The Curator)

Execute §CMD_EXECUTE_SKILL_PHASES.

### What /intake is (and is not)

*   **It is** a **wave-based grooming pass** over one initiative's Linear inbox: it drains the new feedback since the last watermark, builds a cross-scope understanding, **triages** each signal toward an outcome, and — only when an item is *ripe* and you confirm — graduates it into a tracked ticket. It reads incoming feedback; the paired **`/inbox-post`** is how feedback is written in. A wave ends; the next resumes from Linear.
*   **It is NOT** an executor. It never does the research, writes the code, or fixes the bug. It organizes, **triages** (light detail-gathering / repro / related-tickets, via dispatched sub-agents), and **hands off** context-rich briefs for others to execute (`¶INV_INTAKE_DISPATCHES_NEVER_EXECUTES`). Deep research happens on a *ticket*, not in the inbox.
*   **`/intake` vs `/direct`** (`¶INV_INTAKE_IS_BOTTOM_UP`): `/direct` designs a top-down vision — chapters and a plan — from a **known goal**. `/intake` accretes bottom-up from scattered feedback with **no goal yet**; the structure *emerges* from what marinates. Reach for `/direct` when you know the destination; `/intake` when you're still finding which thread to pull.

### State model — Linear is the source of truth (`¶INV_LINEAR_IS_TRUTH`)

*   **Linear tickets = the durable source of truth.** Feedback comes in and gets organized *for real* in Linear. Humans acting in Linear (dragging a milestone, closing an issue, replying) are always authoritative — the skill never overwrites human state.
*   **Durability is in Linear, not the session** — which is *why* /intake can be a bounded wave. Tickets, inbox reply-threads, and the drain watermark persist across sessions; a wave can end cleanly and the next resumes with nothing lost.
*   **The engine session doc = internal working context only.** It holds the agent's intermediate decision-making, the historical log of input, and the evolving cross-scope understanding, projected outward to the Linear Project *description + updates*. If the doc is lost, it is rebuildable from Linear (the `filed as FIN-XXX` reply-threads + tickets are the record).

### The Linear Project shape (one Project per initiative — with a real domain goal)

*   **The Project** has a **domain-specific goal** — a real initiative (e.g. "raise email-classification auto-approve rate without regressing safety"), **NOT "the inbox"** (`¶INV_PROJECT_HAS_A_DOMAIN_GOAL`). `/intake` figures this goal out via Setup interrogation and writes it as the Project's description/summary.
*   **Milestones** (seven — the full lifecycle, raw lead → terminal):
    *   **`Inboxes`** *(frozen — lead collectors)* — holds the inbox tickets (below) **plus** any existing tickets parked to gather input. Everything in it carries the **`Inboxes` issue status**, never `Backlog` (`§INV_INBOX_STATUS_NOT_BACKLOG`). Never active work; the skill **never files graduated tickets here**, only *reads* the threads here as feedback. Sub-issues coworkers create under an inbox ticket get **parked to `Uncategorized`** (`¶INV_INBOX_NOT_TICKETS`).
    *   **`Uncategorized`** — awaiting triage: a promoted ticket whose work-type isn't obvious yet, a ticket pulled from another project to consolidate here, **or a sub-issue parked out of `Inboxes`**. The anti-dumping-ground: visible, not lost.
    *   **`Needs decision`** — needs discussion/alignment → dispatch to `/brainstorm`.
    *   **`Needs research`** — needs investigation / root-cause / consolidation → `/analyze` `/research` `/experiment` `/probe`.
    *   **`Ready for action`** — clear problem + clear fix → `/ticket` `/implement`.
    *   **`Archived`** *(terminal)* — done/shipped work moved out of the active queue, so `Ready for action` stays a live picture of what's left. A record of what's been fixed.
    *   **`Cancelled`** *(terminal)* — rejected/abandoned **with the reason recorded** (bad idea / bad diagnosis / superseded / no longer relevant). Kept, not deleted — a dead-end memory so it isn't re-litigated (`¶INV_RESEARCH_MEMORY`). Consolidation *supersede* and *close* ops land here.
    *   *(Milestone names are the project's, teammate-facing — keep their descriptions human, no skill/engine jargon in Linear.)*
*   **The inbox tickets** — one or more **typed collection tickets under the `Inboxes` milestone**, chosen **per project** (`¶INV_INBOX_IS_TICKETS`). Each is a comment firehose for a *kind* of feedback; a dropper (via `/inbox-post`) picks the one matching what they're reporting. Strong default set: **Observed problems** (symptoms) · **Identified shortcomings** (diagnosed gaps) · **Feature requirements** (desired new behaviors) · **Potential solutions** (proposed fixes/mechanisms) · **Feedback & Transcripts** (raw longform source, chunked into the others) · **Researches & Fixtures** (human-ratified golden fixtures) · **Priorities & Deadlines** (the escape hatch on computed priority — deadlines, urgency, strategic weight the ranking can't see) · **Documentation** (docs missing / needed / wrong / stale, ours and product-facing alike — graduates to `/document`) · **Inquiries** (a question asked of the team — answered by a triangulated reply under the drop, and graduating to nothing unless the answer turns out not to exist). Each channel's description carries **only** its own one-line what-belongs-here plus its `## Directions` (`¶INV_DIRECTIONS_IN_DESCRIPTIONS`); the shared machinery lives once in the project's **Inbox Handbook** document (`¶INV_CHANNEL_MACHINERY_IN_ONE_DOC`). A single comment may span channels — the organize pass splits and cross-links. All frozen, never closed, never worked. **The tickets ARE the inbox — the Project is not.**
*   **Research issue(s)** — living progress snapshots.
*   **Project Updates** — human-readable checkpoint reports, posted at Close.
*   **Item state lives as reply-threads on the origin Inbox comment** (`¶INV_TRIAGE_BEFORE_TICKET`): `candidate` (ripeness nomination) · `seems like FIN-…` / `seems like <cluster>` (dedup link) · `🔎 needs-triage` (+ handoff/report) → `👀 claimed by <who>` → `✅ result` (the triage handoff protocol) · `filed as FIN-XXX` (graduation backlink) · `shipped in FIN-XXX` (**already done before the wave looked** — the item needed no ticket because the work had shipped; a terminal outcome like `filed as`, and distinct from `cancel`, which is a decision not to do something). Whenever one of these replies cites a **specific comment** (a `→` provenance source, a `seems like` sibling, a corroboration), deep-link it via `§FMT_TICKET_COMMENT_LINK` (never a bare comment id); ticket keys via `§FMT_TICKET_LINK`.

### The lifecycle — bounded waves (not an endless loop) (`¶INV_NO_RUSH_ITEMS_TO_CLOSURE`)

`/intake` runs as a **wave**: one session grooms one project's inbox from the watermark forward, drives each signal to an outcome, then **closes with a debrief**. The next `/intake` picks up from Linear + the advanced watermark. This is deliberate — durability lives in Linear, so a wave ends cleanly and loses nothing. The no-rush guarantee is **item-level**: a wave may end with items still marinating (recorded in Linear), and an item is **never force-promoted just because the wave is closing**. What ends is the session, not the initiative. Model: a grooming *pass*, not `/coordinate`'s immortal monitor.

**A wave comes in three reaches, chosen at Setup** (`§CMD_SELECT_MODE`, `¶INV_QUICK_PASS_DECIDES_NOTHING`) — *the front half, the back half, and end to end*:

> **Quick Pass ingests and decides nothing · Decide decides and ingests nothing · Full Wave does both.**

**One watermark serves all three, and its meaning never changes: *what have I read*.** A Quick Pass and a Full Wave drain, so both advance it. A **Decide** pass reads no new inbox signal, so it advances nothing — not an unfinished step, the rule being obeyed. There is no decision-waterline in any mode, because *what still needs deciding* is already recorded in Linear as **the unresolved comment threads**.

That is why the reaches are one design rather than three features: a Quick Pass deliberately leaves threads open and **grows** the undecided set; **Decide** is the only mode that shrinks it; and a Full Wave does both halves in one sitting. All of it turns on the same Phase-1 pull (c).

## How a wave moves between phases (`¶INV_EVERY_PHASE_DECLARES_ITS_BOUNDARY`)

A wave's phases cost real money and real time — a triage fan-out prices at roughly two sub-agents per item, a board is a dispatched render subagent, a filing pass writes to other people's tickets. **The operator decides when a wave pays for the next phase**, and they can only decide that if they are told what it will do before it starts. So every boundary is a hand-off the operator answers, never a step the wave takes on its own judgement.

Two mechanisms carry that, and every work phase uses both.

**Each work phase declares its boundary.** Phases 1–8 open with an **OWNS / DEFERS** line: what this phase decides, and what it explicitly does not decide here — naming the phase that does. The line is not decoration; it is what an agent reads when the operator asks for something out of order.

**Each boundary offers the hand-off.** At the end of a phase, invoke `§ASK_INTAKE_PHASE_HANDOFF` filled with that boundary's parameters. Where the boundary is a genuine **fork** rather than a straight continuation, the phase also carries an authored `### Then — <name>` section stating the fork in its own words; the tree still runs after it.

### ¶ASK_INTAKE_PHASE_HANDOFF
Trigger: at the end of every work phase (1 through 8). NOT at 0→1, which is declared `gate: false` and deliberately seamless.
Extras: A: Show the next phase's cost breakdown | B: Show what is still open in this phase | C: Show the wave's numbers so far
Fill every `<…>` from the boundary being crossed. Option labels carry `§FMT_ANSWER_GRADATION`.

## Decision: how far does this wave go next?

- [NEXT] Continue to `<N+1>: <name>`
  What it will do, in this wave's own numbers: `<"fan out on 12 items", "rank 19 and dispose each">`. What it costs: `<sub-agent count · writes to Linear · time>`. What it will NOT do: `<the next phase's own DEFERS line>`.
- [STAY] Stay in `<N>: <name>`
  More work here first — `<what is still open in this phase>`.
- [BACK] Back to `<N-1>: <name>`
  Something upstream was wrong. Non-sequential, so it carries `--user-approved`; this answer is the reason.
- [CLOSE] Close the wave
  Stop here and go to `9: Synthesis`. Records what is left undecided, exactly as a Quick Pass does.

### Filling the hand-off honestly

**Filling it honestly is the whole point.** *"Continue to Triage"* is not a hand-off. *"Continue to 3: Triage — fan out on 12 of the 19 items, ~24 sub-agents at two angles each, read-only; it will not decide anything about any of them"* is. **A number the operator can refuse is the difference between a gate and a formality.**

**The `handoff` recorded field.** Record it in the log at each boundary:

```
handoff: { from, to, offered, chosen }
  offered — what the operator was actually TOLD the next phase would do and cost.
            "continue?" with no stated work and no stated price is the failure
            this field exists to make visible after the fact.
  chosen  — next | stay | back | close, plus the operator's own words where they gave any.
```

**It is declared here and deliberately NOT yet in any phase's `proof` array**, so a wave already in flight when this landed still completes — `SKILL.md` is the *running* protocol. A later release moves it into `proof`.

> Focus: resolve the Linear Project, load the working vision doc + watermark, assume the Curator role.

§CMD_EXECUTE_PHASE_STEPS(0.0.*)

**Credential preflight** (`engine env doctor --domain intake`): run it once, here, before touching the Project — it reads the credential manifest and prints a red/green line per credential (no live API calls). **A `req` MISS IS A STOP.** This REPLACES the previous *"WARN, do not block"* contract: the doctor exits non-zero when a `req` credential is absent (the Slack bot token, a required MCP that is unauthenticated **or unverifiable**, or a missing/expired agent AWS profile), and Phase 0 must not proceed past that — fix it and re-run. The old contract let a wave drain read-only and carry a caveat; in practice that deferred the failure to the Phase-5 announce, ~40 minutes later, with no context. **What replaces it, and is unchanged**: a `triage`/`boards`/`optional` miss still WARNs and the wave still proceeds — say which transport will be deaf this wave and carry it into `INTAKE.md` §1. So the degradation path survives exactly where it was true, and only the `req` line hardened. ⚠️ **A run marked `SEAM-INFLUENCED` is not a verification** — test seams (`ENV_MANIFEST`, `ENV_MCP_LIST_OUTPUT`, `ENV_AWS_SECRET_*`, `ENV_STS_ARN`, …) were set, so the green means nothing about the real setup; re-run with them unset. (Missing non-secret defaults are seeded automatically; secrets are never written — `engine env setup --domain intake` walks those, and `engine env setup --aws-key <path>` installs a delivered agent key. Note the doctor also reports the headless/cron gap: Linear/Notion MCP *writes* need interactive OAuth, so an unattended wave can read a Project but never record the outcome.)

**Select the mode** (`§CMD_SELECT_MODE`) — **how far does this pass go?** Ask it here, before anything is drained, because the answer changes what Phase 1 sweeps and where the wave stops:

*   **Full Wave** *(recommended)* — drain, triage, decide, file, close. The complete pass; every phase runs as written.
*   **Quick Pass** — drain, scope, triage, then stop at the Phase-3 gate. Decides nothing, files nothing, resolves nothing, announces nothing. Meant to run daily.
*   **Decide** — no drain. Pull the accumulated unresolved threads and take them all the way to dispositions, filings and resolutions. Takes no new inbox signal and **does not advance the watermark**.
*   **Custom** — the operator names the phase this pass stops after.

**Recommend by the open-thread count, not by habit.** If the project has been running Quick Passes and the unresolved set has grown, **Decide** is the pass that is actually owed — say so with the number rather than defaulting to Full Wave. If nothing is undecided, Decide has nothing to do and Full Wave or Quick Pass is the choice.

**On selection**: read the corresponding `modes/{mode}.md`. It defines the Role/Goal/Mindset for `§CMD_ASSUME_ROLE` and — the part that actually matters here — **which phases run, whether Phase 1 drains, whether Phase 1's unresolved-thread pull runs, whether the watermark advances, and whether the pass announces**. Record the mode as the `mode` proof field; every later phase reads it.

**The role is identical in all three modes** (below); only the Goal and Mindset in the mode file sharpen it. And do not treat a shorter reach as a lighter-standard one: whichever phases a mode runs, it runs them with every gate and every proof field intact (`modes/quick-pass.md` § *What still runs*).

**Assume the role** (`§CMD_ASSUME_ROLE`): You are **The Curator** — a patient organizer of scattered signal. You make sense of a hairball without forcing premature structure: hold ideas cheaply, notice what's connected, triage before ticketing, and resist filing a ticket before an item has earned it. You drive each wave to real outcomes, but you never rush an *item* to closure.

    *   **the project's inbox tickets** — one or more *typed* channels under `Inboxes` (default: `Observed problems` / `Identified shortcomings` / `Feature requirements` / `Potential solutions` / `Feedback & Transcripts` / `Researches & Fixtures` / `Priorities & Deadlines` / `Documentation` / `Inquiries`). Absent = the skill's defaults apply; never fail, never invent one.
    *   Directions say *what this project is trying to achieve right now*, *what counts as ripe here*, and *what triage should chase or skip* — not mechanics (the skill holds those).
    *   **At the project tier, Directions carries steer and gates, not method** — what we're chasing, what's in and out of scope, and what counts as ripe here (the ripeness checklist is legitimately Directions' to modify). What does **not** belong is *how to investigate an item*: per-item triage method goes to the handbook's `## What triage will chase`, which is already per-project and is what a handoff prompt pastes forward. The line is **decide-what vs. find-out-how**. If a project's `## Directions` has accumulated investigation method, log it and offer to move it at Outcomes.
    *   Copy the loaded Directions verbatim into `INTAKE.md` §1 so every later phase and every dispatched sub-agent reads the same steer. If a channel's Directions changed since the last wave, say so in the log — a changed steer re-opens judgments made under the old one.
*   **Load the project's Ticketing Strategy** (`¶INV_TICKETING_STRATEGY_IN_HANDBOOK`) — read the `## Ticketing Strategy` section of the **Inbox Handbook** (no extra fetch: it rides the one `get_document` below). One per project: there is no channel override and no precedence chain, because how many tickets a project wants is a property of the project, not of the firehose an item arrived through.
    *   It answers the question *after* ripeness — given an item IS ripe, should it be its own ticket, folded into a parent, or left marinating. Applied as a distinct gate at Outcomes (Phase 5), not as a fifth ripeness criterion.
    *   Copy it verbatim into `INTAKE.md` §1, so Digest's consolidation runs with it in view and every dispatched sub-agent receives it.
    *   **Absent → warn once, then proceed on the catalog's canonical default**, and record *"Ticketing Strategy: default applied (none set on the handbook)"* in `INTAKE.md` §1 and the log. Never a silent fallback — a defaulted project must be visible as defaulted. Offer to write the section into the handbook at Outcomes.
    *   **On a project that predates the move**, the section may still sit on the Project description. Read it from there this wave, log that it was found in the old location, and offer to relocate it into the handbook at Outcomes — same one-project-at-a-time migration path as the handbook itself.
    *   **If it changed since the last wave, say so in the log and re-examine recent graduations.** A changed Direction re-opens pending judgment; a changed Ticketing Strategy re-opens already-filed tickets.
*   **Load the project's Stakeholders** — read the `## Stakeholders` section of the **Project description** and copy it into `INTAKE.md` §1. It names the **operator** who runs this project's grooming pass among the other people-facts; the cadence and pass-heartbeat mechanics are in the handbook, not here. Optional: absent is a normal state and is **not** warned about (unlike Ticketing Strategy). They are *facts about people*, never assignment rules — so each phase draws its own inference: Triage carries the relevant names into a handoff prompt so a sub-agent that hits a question it cannot close knows **who to ask**; Outcomes infers a sensible assignee/reviewer on a graduated ticket and decides who a Project Update should reach. Inference only — the skill proposes, the human confirms; a Stakeholders line is never authority.
*   **Load the project's Inbox Handbook** (`¶INV_CHANNEL_MACHINERY_IN_ONE_DOC`) — one `get_document` fetch of the shared machinery (report template · what-happens-next · other-inboxes · lifecycle · cadence · `## Data handling`) **plus this project's own `## What triage will chase`**, **its `## Ticketing Strategy`** and **its `## Related Slack Channels`** (FIN-3593). That section is the reason the handbook is per-project: it names this project's actual tools, and another project's copy of it is worse than useless here. Hold it for the wave: Phase 3 pastes the relevant part into every handoff prompt, since a sub-agent still cannot read the project. **One fetch replaces N copies** — do not re-read it per channel, and do not reconstruct it from a channel description.
    *   **Parse `## Related Slack Channels`** into the wave's channel list (the NAMES, one per line) and hold it for the wave — Phase 1 windows each one for ambient context; Triage/Digest/Outcomes consult that context. Empty/absent → fall back to the `SLACK_INTAKE_CHANNEL` env; neither → the channel-context read is skipped (logged caveat), the wave proceeds.
    *   **Absent** (a project predating the handbook, or one whose channels still carry inline machinery): say so in the log and fall back to reading it off a channel description this wave. Then **offer to create the handbook and thin the channels** at Outcomes, when descriptions are being synced anyway — that is the migration path, taken one project at a time.
*   **Working vision doc** — `INTAKE.md` in the session dir (the `debriefTemplate`). If it exists, read it; if not, it is created on first Organize.
*   Pin the doc location: **the active session dir**. Linear is the durable record if the session is ever lost.

## 1. Ingest — drain new signal since the watermark
*Read what's new. A wave opens by pulling the incoming feedback, cheaply, into the raw input log.*

**OWNS** — what signal enters this wave, and the watermark that says what has been read.
**DEFERS** — whether an item is a duplicate or thin (**2: Scope and Worklist**) · what any of it means (**4: Digest**) · every disposition (**5: Outcomes**).

§CMD_REPORT_INTENT:
> 1: Draining new inbox comments for ___ since the watermark. Reading incoming signal.
> Focus: pull everything new in ONE `engine project fetch`, process the payload file with jq into INTAKE_DRAIN.md; advance the watermark.
> Not: organizing or triaging yet.

§CMD_EXECUTE_PHASE_STEPS(1.0.*)

**In DECIDE mode this phase runs REDUCED — read this before anything below** (`¶INV_QUICK_PASS_DECIDES_NOTHING`). Decide takes **no new inbox signal**, so of everything in this phase it runs only: the **full** `engine project fetch` (no `--since`) that pull (c) needs, with pulls (a) and (b) taken off that same payload · the **prior announce-thread drain** and its `Slack read ts` advance (those are *answers to decisions already on the table*, and Phase 7 reads them out of `INTAKE_DRAIN.md`) · the **channel context windows**. It does **not** drain the inbox channels' comments, does **not** advance the watermark, and the **"empty drain → offer to close" clause does not apply** — there is no drain to be empty. Decide's honest close condition is an empty *pull (c)*: nothing is unresolved, so nothing is owed.

> **Why Decide leaves the watermark alone — and why you must not "fix" this.** The watermark means ***what have I read***, in every mode, and a Decide pass reads no new inbox signal. A future editor will see a pass that ran to completion, filed tickets and closed **without advancing a waterline**, and will reasonably read that as a bug. **It is not.** Advancing it here would silently skip every comment that arrived while the pass was deciding: those comments were never drained, and the next wave's `--since` window would open *past* them. The "fix" would introduce exactly the feedback-loss this watermark exists to prevent. (The per-thread `Slack read ts` **does** advance in Decide mode — that thread genuinely was read. The two markers are different scopes carrying the same meaning.)

Ingest runs as **one `engine project fetch` call**, never per-comment MCP paging. The CLI does the heavy lifting server-side — comment TREES, the LIVE `structure.channels`, new tickets, normalized lifecycle, `summary`, and `channelsResolved` — and writes the whole payload to a `--out` **file**. The orchestrator then reads that file with **`jq`**, so the fat comment bodies never enter the main loop (a single `Feedback & Transcripts` drop can be 30–40KB). The `--out` file + `jq` ARE the context-isolation the old drain-subagent existed to provide, so **a subagent is no longer required** for Ingest.

*   **The watermark is a single per-project ISO timestamp**, in the `Watermark:` field on the Inbox-tickets line of `INTAKE.md` — the SINGLE source of truth. The CLI is **stateless**: it keeps no waterline of its own and never advances anything, so `--since` is entirely `/intake`'s to supply. Empty on a fresh project = a full first fetch.
*   **Fetch once** (write the `§CMD_LOG_SKILL_INVOCATION` breadcrumb first):
    ```
    engine project fetch <projectId> --since=<INTAKE.md watermark> --out=<sessionDir>/builds/project-fetch-<ts>.json
    ```
    An empty watermark → omit `--since` (a full snapshot). ONE call returns the comment trees for every inbox ticket (+ parked `Inboxes` tickets) + `structure.channels` (LIVE — a quiet channel with no new activity still enumerates, independent of the delta) + new tickets + `summary` + `channelsResolved`. The command prints the payload path as its last stdout line; a non-zero exit means nothing was written — surface it, don't advance the watermark. The old drain's "retry once on a transient 502" is deliberately **not** reproduced: a non-zero exit wrote nothing, so it's safe to just re-run the wave (backoff/retry is council C1, still backlog).
*   **Process the `--out` payload with `jq`** — never slurp the whole file into context. Comments are nested trees (root → `children` → …), so walk them **recursively** — visit every node at every depth, not just the roots (e.g. `jq '.tickets[].comments | .. | objects | select(has("body"))'`, or descend `children` yourself). The drain semantics below apply to **every** comment node in the tree (these move from the old subagent onto the payload):
    1.  **Exclude skill-authored replies by marker prefix, NOT by author** — all skill posts land under the operator's human Linear identity, so author can't distinguish them. Drop any comment whose `body` leads with `candidate` / `seems like …` / `→` (chunk-destination) / `🔎 needs-triage` / `👀 claimed` / `✅ result` / `filed as FIN-…` / `shipped in FIN-…` (`¶INV_EXCLUDE_OWN_COMMENTS` — every skill-authored reply MUST lead with one of these markers so the exclusion is complete).
    2.  **Skip anchored comments** — a comment with `quotedText != null` annotates the ticket *description*, not the firehose. The payload now carries `quotedText`, so filter these out here rather than re-ingesting an anchored annotation as feedback.
    3.  **Dedup by comment id** against `INTAKE_DRAIN.md` — across waves the same ticket re-appears (any new activity re-surfaces its whole comment tree), so drop any comment id already logged in a prior wave's `INTAKE_DRAIN.md`. This dedup is a **cross-wave** guard, NOT a boundary safety net: the `--since` filter is strict `>` (exclusive), and it's loss-free precisely because the watermark is the **max `updatedAt`** of the issues just fetched — next wave's `updatedAt > watermark` excludes exactly the already-seen issues and includes anything genuinely newer. A new comment strictly advances its issue's `updatedAt` past the watermark, so that issue re-appears and only its new comments clear the `createdAt > since` filter — nothing at the boundary is dropped or double-counted.
    4.  **Append** each surviving comment (author · createdAt · id · full body) to `INTAKE_DRAIN.md` in the session dir — the raw input log.
*   **Never filter on resolved state** (`¶INV_RESOLVE_ON_DISPOSITION`). A resolved thread means *dispositioned*, not *closed to input* — so a **new reply on a resolved thread is live signal** and drains like any other; it arrives with its own `createdAt`, so the watermark catches it for free. Surface such replies prominently — a reply on a dispositioned thread is usually someone correcting a triage the system got wrong, the highest-value drop there is.
*   **Advance the watermark AFTER `INTAKE_DRAIN.md` is written** — **Full Wave and Quick Pass only; a Decide pass skips this step entirely and leaves the field untouched** (see the Decide clause at the head of this phase for why): set the `INTAKE.md` `Watermark:` field to the payload's **max `updatedAt`** across `.tickets` (`jq -r '[.tickets[].updatedAt] | max // empty'` on the payload). This matches the CLI's `--since` semantics (it filters issues on `updatedAt`) so the next wave's window opens exactly where this one closed (`¶INV_WRITE_BEFORE_WATERMARK` — the raw items are already durable, so the doc-write precedes the watermark advance; a crash before this leaves the watermark un-advanced → a safe re-fetch, with the id-dedup dropping the re-surfaced boundary comments). No tickets in the payload → keep the current watermark.
*   **Enumerate channels from the payload** — use `structure.channels` (the live catalog) for the channel enumeration the Scope/Digest phases rely on, and check `channelsResolved`: `false` means the project's inbox milestone name didn't resolve and channels came back empty — say so in the log and re-fetch with `PROJECT_FETCH_INBOX_MILESTONE=<the project's inbox milestone>` rather than proceeding as if the project had no channels.
*   Also accept input dropped **directly in chat** (no fetch needed).
*   **Drain the PREVIOUS wave's Slack announce thread** — the third input transport, alongside the Linear fetch and chat. Read the `Slack announce ts:` slot in `INTAKE.md` §1 (captured at the *last* wave's Phase 5) and pull its replies:
    ```
    engine slack-read --channel '#<the project's channel NAME>' --thread-ts <the prior announce ts> [--since <last read ts>]
    ```
    **It is the prior wave's thread by construction, not by preference**: this wave's announce does not exist until Phase 5, so the replies available to read now are the ones left on the last one. Exactly how the Linear drain works — Ingest reads what accumulated since the watermark.
    *   **Own-message exclusion is a REAL author check here** — `slack-read` already drops the parent message, anything the bot itself authored, and anything carrying a `bot_id`. **Do NOT port Linear's marker-prefix rule to Slack**: that rule exists only because every skill post on Linear lands under the operator's human identity. Slack gives the bot its own user id, so the author check is both stronger *and* free of the marker rule's real cost — it would drop a genuine human reply that happens to open with a marker word.
    *   **Dedup by `ts`** against `INTAKE_DRAIN.md`, exactly as comment ids are deduped: a Slack `ts` is unique per channel, so it plays the same role. **Append each surviving reply** (author name · `ts` · full text) to `INTAKE_DRAIN.md` — the same raw input log, one transport tagged from another.
    *   **A reply may BE an attachment.** `slack-read` returns `files` on any reply that carries one, and — unless `--raw` or `--max-file-bytes 0` — has already downloaded the bytes to this machine: `local_path` is a real path you can hand straight to whatever reads files. Treat a screenshot as the reply's evidence, not as decoration. Two consequences that change what you write down:
        *   **A reply with empty `text` is not an empty reply.** A file-only reply is how people report most visual defects, and before this it drained as a blank line. Record it by its attachment — file name, what it shows, and the `local_path` — not as "(no text)".
        *   **`download_error` instead of `local_path` means the bytes are not here** (over the size cap, the app lacks `files:read`, a fetch that failed). The `permalink` still works: record it and say the attachment was not retrieved, rather than silently dropping it. `download_dir` on the envelope is where anything that did download landed.
    *   **Advance the per-thread read watermark only AFTER that write** (`¶INV_WRITE_BEFORE_WATERMARK`) — set `Slack read ts:` in `INTAKE.md` §1 to the greatest reply `ts` drained, and pass it as `--since` next wave. A crash before this re-reads rather than loses, and the `ts`-dedup absorbs the overlap.
    *   **A read failure is NOT an empty thread.** `slack-read` exits non-zero with the reason when it could not read (missing scope, bot not in channel, bad ts) and exits 0 with `count: 0` when the thread genuinely has no replies. Surface the failure and say the Slack transport was deaf this wave; never let it report a silent zero. Best-effort like the announce: it is logged and never blocks the wave.
    *   **No `Slack announce ts` recorded** (a first wave, or a wave that failed to capture it) → say so and skip; do not hunt for the thread.
    *   **A reply on a decision already dispositioned is live signal, surfaced prominently** — the same rule as a reply on a resolved Linear thread (`¶INV_RESOLVE_ON_DISPOSITION`). It does **not** auto-reopen the item; a human decides. A late answer is usually someone correcting a call the wave got wrong.
    *   **Known limit, stated rather than discovered**: an edited Slack reply keeps its original `ts`, so the `ts`-dedup keeps the first text seen and an edit made after ingest is invisible.
*   **Drain the channel context windows** (FIN-3593) — the **ambient** external-context transport, distinct from the announce-thread drain above: that reads one thread's replies; this reads channel-wide team discussion over a window (`conversations.history`). For **each** channel in the wave's `## Related Slack Channels` list (from the handbook, held at Setup; else the `SLACK_INTAKE_CHANNEL` fallback; neither → skip with a logged caveat), pull a window:
    ```
    engine slack-read --history --channel '#<name>' --lookback ${SLACK_INTAKE_CONTEXT_LOOKBACK_DAYS:-7}d
      > <sessionDir>/builds/slack-channel-context-<name>-<ts>.json    # one file per channel; author names resolved
    ```
    *   **Ambient, not inbox signal** — do **NOT** drain it into `INTAKE_DRAIN.md` and do **NOT** dedup it onto the worklist. It is context the wave *reasons with*, not items it triages. The raw pull lands in `builds/` (fat bodies out of the main loop, like `engine project fetch`); log only a one-line digest (per-channel message count + window + pointer).
    *   **Hold it for the whole wave** — like the handbook, loaded once and reused. Phase 3 pastes the relevant slice into each triage handoff prompt (the sub-agent cannot read Slack); Phase 4 Digest and Phase 5 Outcomes consult it when consolidating and deciding, so a graduate/marinate call reflects what the team already said outside Linear.
    *   **WARN, don't block** — a failed read on a channel (non-zero: missing scope, bot not a member) is a logged caveat naming that channel deaf this wave; a genuinely empty window (`count: 0`) is normal and not a failure. Never a silent zero, never a wave stop. There is **no read-watermark to advance** — the window is `now − lookback`, stateless (unlike the announce-thread read's `Slack read ts`).
*   **Also sweep the backlog, the strays and the undecided into the wave's scope** (`¶INV_ADOPT_OR_CANCEL_STRAYS`, `¶INV_QUICK_PASS_DECIDES_NOTHING`): three overlapping pulls — (a) existing thin **triage candidates** (`Uncategorized` items + parked sub-issues lacking account/claim/repro), (b) **strays** — any ticket **not under `Inboxes`** carrying **no wave-provenance marker** (no `filed as FIN-…` origin reply, no idempotent pre-write key, no skill-authored `🔎 needs-triage`/`✅ result` thread): a human dropped it straight into a milestone — and (c) **every UNRESOLVED inbox comment thread, whatever its age** (**Full Wave and Decide; never Quick Pass**). All three join the new drops on the Phase-2 worklist — and in **Decide** mode, where there are no new drops, pull (c) *is* the worklist.
    *   **Pull (c) is what closes the loop on a Quick Pass** (`¶INV_QUICK_PASS_DECIDES_NOTHING`). A Quick Pass triages and deliberately leaves the thread open, so *"what still needs deciding"* is exactly *"which threads are unresolved"* — the undecided set is derivable from Linear and there is **no second watermark, and none is to be added**. Without this pull the watermark sails past a triaged item and nothing ever re-picks it.
    *   **The delta cannot see it, so use the full payload.** `--since` filters ISSUES on `updatedAt`, so a thread nobody has touched since it was triaged never re-surfaces in the delta — by construction, the same reason Phase 6 re-fetches without `--since`. Take (c) from a **full** `engine project fetch` (no `--since`, `--out` to a file, walked with `jq` like the delta). Reuse that payload for (a) and (b)'s detection rather than fetching twice.
    *   🔑 **Pull (c) counts ROOT comments only — it does NOT walk `children`, and this is the opposite of what the drain does.** Resolution in Linear is a property of the **thread**, not of a comment: the API refuses a child outright — *"Only top-level comments can be resolved. Pass the root comment of the thread."* So a reply is `resolvedAt: null` **forever**, including every reply on a thread that was dispositioned months ago. Unresolved therefore means: a node **at the top level of `.tickets[].comments`** whose `resolvedAt == null`, after the same marker-prefix and `quotedText` exclusions the drain applies. Nodes reached through `children` are never candidates, whatever their `resolvedAt` says.
        *   **Do not reuse the drain's recursive walk here.** The drain deliberately visits every node at every depth, because a reply IS new signal and needs its own id for dedup. Pull (c) asks a different question — *which threads still owe a decision* — and the same traversal answers it wrongly. Two questions, two walks, one payload.
        *   **Measured, on a project where this was got wrong**: 227 comment nodes split **125 roots (32 resolved, 93 open)** and **102 children (0 resolved, and 0 resolvable)**. The recursive walk reported **195 open** against a true **93** — a 2.1× overstatement, growing with every reply anyone adds. That number is not cosmetic: it is what `backlogTaken` reports, what sizes the Phase-3 fan-out, and what recommends the mode at Setup, so an inflated count argues for a Decide pass that is not owed and prices a fan-out that will never run.
        *   **`engine project fetch` needs no flag for this** — roots are already the top level of `.tickets[].comments` and replies already hang under `children`. The distinction is in the payload; only the reading was wrong.
    *   **An item already carrying a `✅ result` reply is re-picked but not re-triaged** — it lands on the worklist `already-clear` **only if** its own accreted replies satisfy the `already-clear` test (org · entity id · repro), and `needs-triage` otherwise. Its prior triage is evidence; it is not a reason to skip the wave. Say in the log how many items pull (c) contributed and how many of those a Quick Pass had already enriched.
    *   **Say the number, and get a ruling on the fan-out — this is gated by `backlogTaken` at Phase 2, not left to good intentions.** On a mature project the unresolved set is not small: one measured inbox held **136 comments, 19 resolved, 117 open**. ⚠️ **Treat that 117 as an upper bound, not a thread count** — it was taken with the recursive walk the rule above now forbids, so it counts replies alongside roots and the true figure is smaller (on the one project where both were computed, by ~2×). Re-derive it root-only rather than citing it. Pull (c) can therefore hand Phase 3 a worklist an order of magnitude bigger than the drain, and `¶INV_ANGLES_MUST_FAIL_DIFFERENTLY` prices each item at ~2× a triage. **Do not silently fan out on a hundred items, and do not silently drop them either**: report the pull-(c) count *before* Phase 2 marks the worklist, say what the fan-out would cost, and get a ruling on how much of the backlog this pass takes (`¶INV_SUGGEST_BY_INTERROGATION` — how much backlog to clear is the operator's call, not the wave's). Whatever is not taken stays unresolved, which is exactly the state it was already in — **nothing is lost by deferring**, and the next pass's pull (c) re-offers it.
        *   **In DECIDE mode this matters more than anywhere else**, because that mode is *entirely* pull (c) — there is no new signal diluting the set, so the worklist IS the whole backlog and the ~117-item case is the normal case, not the tail.
    *   **Quick Pass skips (c) entirely** — a daily pass that re-scanned every open thread would re-triage the same backlog every morning. Pulls (a) and (b) still run: a Quick Pass triages a thin candidate or a stray, it just never disposes it. **A Custom reach runs (c) iff it will reach Phase 5** — pulling the undecided set into a pass that cannot decide it is the black hole in reverse. Strays are flagged **adopt-or-cancel candidates** — the wave triages them, then at Outcomes moves each to the right milestone (**adopt**) or closes it with a reason (**cancel** → `Cancelled`); never left unsorted, never silently deleted. Detection: from the `engine project fetch` payload's `.tickets` (milestone + whether a wave-provenance reply exists), else an MCP `list_issues` scan. Be **conservative** — a legitimately-parked ticket or a cross-project link is not a stray, and every adopt/cancel is human-confirmed at Outcomes.
*   **Empty drain**: if nothing is new on any transport — no Linear comments, no Slack replies, no chat input, no thin backlog — the wave has nothing to groom; say so and offer to close (→ Phase 9) or wait. A Slack read that *failed* is not an empty one, and must not be counted toward this.
*   Log the ingest (`§CMD_APPEND_LOG`): per-ticket count + new watermark + `INTAKE_DRAIN.md` pointer + backlog-candidate count + the Slack read (replies drained, new read ts — **or the failure reason**, never a bare zero).

Fill it with this wave's numbers: `<N>` comments drained across `<C>` channels · `<S>` Slack replies · `<B>` backlog candidates → **2: Scope and Worklist**, which is orchestrator-only and genuinely cheap (no sub-agents, no DB) and whose entire job is deciding what Phase 3 spends money on. It will NOT enrich anything.

## 2. Scope and Worklist
*Cheap, orchestrator-only: collapse obvious twins and decide WHAT needs triage — so Phase 3 doesn't fan out on duplicates or already-clear items.*

**OWNS** — which items this wave will spend triage money on, and how much of the backlog this pass takes.
**DEFERS** — the enrichment itself (**3: Triage**) · consolidation and root-cause claims (**4: Digest**) · every disposition (**5: Outcomes**).

§CMD_REPORT_INTENT:
> 2: Scoping ___'s drained signal + backlog candidates. Quick dedup; building the triage worklist.
> Focus: collapse obvious twins, cluster loosely, mark each item needs-triage vs already-clear.
> Not: deep consolidation (that's Digest, Phase 4, after triage) or dispatching subagents yet.

§CMD_EXECUTE_PHASE_STEPS(2.0.*)

**The interrogation here has one topic and one only** (`¶INV_SUGGEST_BY_INTERROGATION`): items the Directions do not clearly place. Ask about those; do not walk the whole worklist. Marking an item parked or `already-clear` when the steer is genuinely ambiguous is the agent quietly deciding scope, which is the operator's. Items the Directions place cleanly need no question.

A **light** pass — no subagents, no DB. Just enough to avoid triaging the same thing five times and to size Phase 3.
*   **Assemble the wave's items** — the source set depends on the mode (`¶INV_QUICK_PASS_DECIDES_NOTHING`):
    *   **Full Wave** — the newly-drained inbox comments (`INTAKE_DRAIN.md`) **plus** the existing **triage-candidate tickets** pulled in Phase 1 (thin `Uncategorized` / parked sub-issues lacking account/claim/repro) **plus the unresolved comment threads from Phase 1's pull (c)**, which is where a previous Quick Pass's triaged-but-undecided signal comes back.
    *   **Quick Pass** — the first two only. No pull (c).
    *   **Decide** — **pull (c) plus the (a)/(b) sweeps, and nothing else.** There is no drain, so do not look for one: `INTAKE_DRAIN.md` holds no new inbox comments this pass (only the announce-thread replies Phase 1 drained for Phase 7's tally). An empty pull (c) here means nothing is undecided — say so and offer to close, rather than reporting an empty worklist as if the pass had failed.
*   **Enumerate the pull-(c) items on the worklist like any other** — they are not a separate list, and they get the same `already-clear`/`needs-triage` test on the reporter's own text, prior `✅ result` replies notwithstanding (`¶INV_ENRICHMENT_IS_EVIDENCE_NOT_READING` — a Quick Pass's enrichment is evidence, never a licence to skip).
*   **Cheap dedup / loose cluster**: collapse obvious twins (same reporter+subject, or the same claim/id visible in the text) into one canonical; drop a `seems like <…>` reply on the echoes. Coarse only — the deep merge/supersede/connect happens in Digest (Phase 4) with triage data in hand.
*   **Apply the channel's Directions** (`¶INV_DIRECTIONS_IN_DESCRIPTIONS`) before marking anything. The Directions decide *what this project cares about right now* — an item the Directions call out is worth triaging even when it looks thin; an item they put out of scope is **parked with the Directions line cited as the reason** — never marked `already-clear`. Those are different states and must not be conflated: `already-clear` means *the gathering is done*, parked means *we chose not to gather, and here is the steer that said so*. Collapsing the second into the first erases the reason and makes the item look investigated. Cite the Directions line in the worklist row either way, so the call is auditable rather than a vibe.
*   **Build the triage worklist** — mark each unique item:
    *   `needs-triage` — missing the facts that make it ticketable (which account/claim, a repro, related tickets): a screenshot-only report, a vague symptom, a thin backlog ticket.
    *   `already-clear` — **a binary test on the reporter's own text, not a judgement about the item**: it already contains everything triage would go get — the account/org, the claim or entity id, and a repro (or a definitive "here is the exact thing"). Miss any one of those and it is `needs-triage`. What `already-clear` means is *"the gathering is done"*, never *"gathering wouldn't help"*.
        *   **Not** "I already know what this says." Authorship of a signal is not evidence about it (`§INV_CONFIDENCE_FROM_THE_CHECK`) — when the person triaging is the person who wrote the report, that is a reason to check **harder**, not a licence to skip. This is the single most common way the marker gets misapplied, because self-authored input feels maximally reliable and is minimally checkable.
        *   **Not** "no DB lookup would help." That is a far weaker test and it waves through every structural, design, or process signal unexamined — triage is not only a DB lookup.
        *   **Not** "an agent already read this" (`¶INV_ENRICHMENT_IS_EVIDENCE_NOT_READING`). A prior read — a subagent that fetched the ticket bodies, comments, relations and states — produces **no fact that was not already in the tracker**. It restates the item at length, which *feels* like enrichment precisely because the report is long, confident and well-structured. **The test: could this output have been produced without leaving the tracker? Then it is a read, not a triage**, and the item is still `needs-triage`. This is the hardest of the three to catch, because unlike the other two it arrives as evidence-shaped work product rather than as a hunch.
        *   `already-clear` skips the Phase-3 **fan-out only**. It does NOT skip the related-tickets search — see Phase 3.
    *   `already-answered` — **a prior triage already ran a check on this item and recorded a definitive answer in the thread.** What this item is owed is a **disposition, not another measurement**. Marking it sends it past the fan-out and straight to Phase 5 carrying the prior answer as its evidence.
        *   **READ THE REPLIES BEFORE MARKING ANYTHING** (`¶INV_ANSWERED_IS_NOT_UNANSWERED`, `§INV_REPLIES_ARE_SIGNAL`). This is a check on the **thread**, not on the body, and it runs on every item before the other markers are considered. A body that reads thin is not evidence the item is unanswered — it is the normal shape of an item whose answer is three replies down.
        *   **The discriminator against `¶INV_ENRICHMENT_IS_EVIDENCE_NOT_READING`, which this marker must never become a loophole for**: `already-answered` requires a prior **check** — a count, a query result, a repro, a document opened, an external system consulted — recorded with its result. A prior agent *read* that restated the tracker at length is **not** an answer and leaves the item `needs-triage`. Same test as ever: *could this have been produced without leaving the tracker?*
        *   **Definitive means the question it was asked is closed**, not that someone wrote a lot. A prior triage that measured and then said *"breadth not established"* has answered part and left part open — that is `needs-triage` on the open part, not `already-answered`.
        *   **Cite the reply.** `basis` carries the `§FMT_TICKET_COMMENT_LINK` deep link to the answering reply plus the answer in one clause. A marker with no reachable prior answer is not this marker.
    *   `chat-drop` — dropped in chat with full context → skip the fan-out (the related-tickets search still runs).
*   Record the worklist in the working doc (item → status → why). Log the counts (`§CMD_APPEND_LOG`): N items · M needs-triage · K already-clear · A already-answered.
*   **The `worklist` proof field — one entry per item, never a summary sentence.** Phase 2 cannot be left without it. Shape:
    ```
    worklist: [ { item, marker, basis } ]
      item    — the FIN-key or origin comment id
      marker  — needs-triage | already-clear | already-answered | chat-drop | parked
      basis   — for already-clear: WHERE IN THE REPORTER'S OWN TEXT each of the three appears (org · entityId · repro).
                for already-answered: the DEEP LINK to the answering reply (§FMT_TICKET_COMMENT_LINK) + the
                answer in one clause + what check produced it. A prior read is not an answer.
                for parked: the Directions line cited. for the others: one clause.
      repliesRead — REQUIRED on every entry, whatever the marker: how many replies the thread carried and
                whether any recorded a prior answer. `0 replies` is a complete answer; an ABSENT field is
                not, because "I did not look" and "there was nothing there" are the two states this
                marker exists to tell apart (¶INV_ANSWERED_IS_NOT_UNANSWERED).
    ```
    **Enumerate every item.** A count is not a worklist and "all items are clear/enriched" is not an entry — those are exactly the forms that let a wave skip triage while appearing to have done it. If you cannot fill `basis` for an `already-clear` item from the reporter's text alone, the marker is wrong: it is `needs-triage` (`¶INV_ENRICHMENT_IS_EVIDENCE_NOT_READING`).
*   **The `backlogTaken` proof field — one entry. Phase 2 cannot be left without it.** It is the mechanical half of the pull-(c) volume bound, which was otherwise an interrogation gate with nothing behind it — and *"a declared step with no gate silently does not happen"* is this project's most repeated finding. Shape:
    ```
    backlogTaken: { pullCOffered, taken, deferred, ruling }
      pullCOffered — how many unresolved threads pull (c) surfaced. 0 is a valid answer
                     (Quick Pass always; a Full Wave or Decide on a clean project).
      taken        — how many joined the worklist this pass.
      deferred     — pullCOffered − taken. These stay UNRESOLVED — the state they were
                     already in — and the next pass's pull (c) re-offers them. Deferring
                     is free; the only unacceptable outcome is deferring silently.
      ruling       — WHO decided the split and on what basis. "the operator capped it at 20,
                     highest blast-radius first" is a ruling; "took what seemed reasonable"
                     is the agent quietly deciding scope, which is the operator's
                     (§INV_SUGGEST_BY_INTERROGATION).
    ```
    **`pullCOffered: 0` with a reason is a complete, passing answer** — the field gates on *silence about the backlog*, never on a pass having cleared any of it. A Quick Pass records `{ pullCOffered: 0, taken: 0, deferred: 0, ruling: "quick-pass skips pull (c)" }` and moves on. **A `deferred` greater than zero with no `ruling` is the exact failure this closes**: a hundred threads quietly left behind, indistinguishable from a hundred nobody ever found.
*   **Empty worklist** (nothing new, nothing thin): skip Phase 3 → Digest, or offer to close.

### Then — hand off to Triage. This is the boundary that decides what the wave SPENDS (`§ASK_INTAKE_PHASE_HANDOFF`)

*The most expensive gate in the wave, and for a long time the quietest one. Phase 3 is a fan-out priced at ~2 sub-agents per item (`¶INV_ANGLES_MUST_FAIL_DIFFERENTLY` wants two angles, plus an adjudicator where they need reconciling). An operator shown a bare "continue?" instead of "fan out on 12 items, ~24 sub-agents" has not been asked anything.*

Fill it with the worklist's own numbers: `<T>` marked `needs-triage` of `<W>` total, `<A>` already-clear → **3: Triage**, read-only enrichment, ~`<2×T>` sub-agents, dispatching `/inbox-triangulate` per item. It will NOT decide anything about any item — every disposition is Phase 5 (`¶INV_DISPOSITIONS_RESOLVE_AT_OUTCOMES`).

**If the operator asked for triage earlier in this phase, this is where that ask lands.** Do not silently honour it mid-Phase-2 and do not decline it (`¶INV_EVERY_PHASE_DECLARES_ITS_BOUNDARY`): name the phase that owns it, say the worklist has to be marked first so the fan-out does not pay twice for the same item, then bring the ask here — priced.

## 3. Triage — parallel enrichment of the worklist
*Fan out read-only enrichment, one per `needs-triage` item, to make thin signals ticketable. Triage ≠ research: light detail-gathering / repro / related-tickets, not deep root-causing.*

**OWNS** — evidence: whether an item is ticketable, and the posted, reachable record of why.
**DEFERS** — what the evidence means *across* items (**4: Digest**) · what to do about it (**5: Outcomes**) · every write to a ticket other than its own triage comment (**6: Ticketing**).

> ### 🔴 WHICH SKILL TO DISPATCH — `/inbox-triangulate` is the DEFAULT, not the upgrade
>
> `¶INV_ANGLES_MUST_FAIL_DIFFERENTLY` (below, and in this skill's invariants) requires **two angles that fail differently** for any item heading to a ticket or a disposition. **`/inbox-triage` is a SINGLE angle and cannot satisfy it.** The skill that does is **`/inbox-triangulate`** — two parallel `/inbox-triage` runs on different leading questions, plus a reconciling adjudicator.
>
> *   **Dispatch `/inbox-triangulate`** for every item that will produce a ticket or a disposition — which, since Phase 5 dispositions *every* item, is the normal case.
> *   **Dispatch a bare `/inbox-triage`** only where the item genuinely will not produce either — and **say so in the log**, because that is a claim about the item, not a default.
> *   Either way, **dispatch the SKILL** (`¶INV_DISPATCH_THROUGH_THE_SKILL`) — a **hand-authored brief** inherits none of the recipe, the report template, or the guardrails, and the loss is invisible because the output still arrives long and confident. **The forbidden thing is the hand-authored brief, never the agent type.** Every dispatch necessarily names some registered agent type — that is the only way the tool works — so a rule written against `general-purpose` forbids the one mechanism that can carry a `Skill()` call, and leaves a literal reader with no legal move. Pick a registered type (`debugger` fits triage), then make `Skill(skill: "inbox-triangulate")` its first instruction.
>
> **Reason, measured, and it is a gap this file created.** This section named `/inbox-triage` as the dispatch target while the invariant two lines below demanded two angles, and **never named `/inbox-triangulate` anywhere in the file.** A wave read the dispatch line, fanned out single-angle, and justified it with the invariant's own hypothesis-fallback — *"single-angle output is a hypothesis"* — which is a fallback for an angle that could not be run, not a licence to skip the second one. **The operator had also asked for triangulation explicitly, in writing, and the wave still dispatched triage.** A protocol that mandates a thing and names the tool that cannot do it will be followed to the wrong outcome by a diligent reader.
>
> **Cost is real and belongs to the operator, not to the wave**: ~2× a single triage per item, plus an adjudicator where the angles differ. If the budget will not carry it, **say so and get a ruling** — do not silently downgrade to one angle.

§CMD_REPORT_INTENT:
> 3: Triaging ___'s worklist — M /inbox-triage subagents in parallel.
> Focus: enrich each needs-triage item (account/claim/URL, repro, related tickets); post results back on the origin comment.
> Not: deep research (runs on a graduated Needs-research ticket) or deciding dispositions (that's Outcomes, Phase 5).

§CMD_EXECUTE_PHASE_STEPS(3.0.*)

*   **The related-tickets search runs on EVERY item in the wave** — `needs-triage`, `already-clear` and `chat-drop` alike (`¶INV_RELATED_SEARCH_IS_UNCONDITIONAL`). It is the one triage step that applies regardless of project, domain, or how complete the report looks, and it is also the cheapest: tracker search only — no DB, no tunnel, no subagent needed. The fan-out covers it for `needs-triage` items; **sweep it orchestrator-side for everything that skipped the fan-out**, and record what it found (or "nothing") per item in the worklist. What it turns up — a duplicate, a cancelled precedent, a shipped fix, the ticket that already tried this and failed — changes a disposition more often than any other enrichment does, and unlike the rest of triage it cannot be recovered afterwards: the item graduates without it and nobody ever learns what was missed.
*   **Open the read-only tunnel ONCE for the wave** — `./scripts/staging-db-tunnel.sh` (background → `127.0.0.1:15432`), connect as **`data_ro`** (read-only by grant; see `/inbox-triage`'s Data-access section). All triage subagents **share this one tunnel** — do NOT open one per subagent (they connect to `:15432`; a second opener would fail to bind the port). Skip if the worklist has no `needs-triage` items. **The orchestrator owns the tunnel's lifecycle**: before opening, check `:15432` isn't already held (reuse a live one; kill a stale one); if it dies mid-fan-out, reopen and re-dispatch the affected items; **close it when the phase ends** — don't leave an orphan SSM session.
    ⚠️ **`127.0.0.1`, never `localhost`** — psql resolves `localhost` to `::1` first and the SSM forwarder binds IPv4 only, so `localhost` **hangs** instead of failing, and reads as a dead tunnel when the tunnel is fine.
    *   **The wave owns this tunnel, so the wave owns telling its sub-agents about it.** Every dispatched triage run must receive the endpoint in its handoff — a sub-agent that is not told one is open will go looking, and the discoverable alternative is a public snapshot instance gated by an IP allowlist whose failure mode is a silent timeout. That has already cost a run.
    *   **Pass the project's `.directives/INBOX_TRIAGE_ACCESS.md` path too**, or its contents. It holds the tunnel gotchas, the app-driving mechanics and the credential resolution a triage run needs, and a sub-agent cannot be assumed to find it on its own.
*   **Every item that will produce a ticket or a disposition is triaged from TWO DIFFERENT ANGLES** (`¶INV_ANGLES_MUST_FAIL_DIFFERENTLY`). The handoff names a **primary** and a **corroborating** angle, drawn from different evidence bases — **DB** (rows and rates) · **UI** (drive the app; see what a user sees) · **code** (`origin/dev`, trace the path) · **artifact** (open the document the customer actually complained about) · **history** (what shipped, what was cancelled, what already failed).
    *   **Diversity, not depth — so this is not 2× cost.** The expensive part of a triage is the tunnel plus designing a query; a `git grep` or a DOM probe is seconds. Choose the second angle for **cheapness and independence**, never for thoroughness. The rule is *the second angle must fail differently*, not *the second angle must be as rigorous*.
    *   **Two runs of the same method share the same blind spots**, so their agreement is replication, not corroboration. The class this exists for is the one that survives replication: a property of the DATA rather than of the query — a duplicated tenant, a stale branch, a contaminated corpus — which every query inherits identically and no amount of re-querying can reveal.
    *   **Disagreement is the PRODUCT.** A gap between two angles is usually the finding itself: *the banner counts one thing while the queue requires another* is not a failed triage, it is the bug. The report carries a required **"Where the angles disagreed"** section; if two genuinely independent angles agreed on everything, say so explicitly — that is worth a second look, not a gold star.
    *   Single-angle output is a **hypothesis** and must be labelled one. It may not be cited as fact in a ticket body, a disposition, or a board.
*   **Fan out in parallel, bounded** (~4–6 concurrent — cap the fan-out, queue the rest). Per `needs-triage` item: write a `§CMD_LOG_SKILL_INVOCATION` breadcrumb, then the **orchestrator authors + saves the handoff prompt** (`builds/inbox-triage-handoff-<origin-id>.md`, scaffold `assets/TEMPLATE_HANDOFF_PROMPT.md`) and dispatches a sub-agent with it + the origin signal — **body AND the thread's replies** (`¶INV_REPLIES_ARE_SIGNAL`) + screenshots — + known context + **the origin channel's `## Directions` verbatim** (`¶INV_DIRECTIONS_IN_DESCRIPTIONS` — the sub-agent can't read the project, so the steer must travel in the prompt or it is silently lost). The sub-agent identifies account/org/claim/page-URL (read-only DB via the shared tunnel), pulls PostHog if sourced, attempts repro, finds related/duplicate tickets → a **triage report** (`builds/inbox-triage-<origin-id>.md`, per `/inbox-triage`'s `TEMPLATE_TRIAGE_REPORT.md`) — which now carries a **steering read** (`¶INV_STEERING_NOT_SOLUTIONS`: a legitimacy read + still-open questions + what-to-measure-next + 3–5 suggested board options, oriented by Directions), feeding the Decision Board's steering widgets at Outcomes. `<origin-id>` = origin comment id or FIN-key, so concurrent triages never collide on filenames.
    *   **HOW to dispatch it, mechanically — `/inbox-triage` is a SKILL, not an agent type.** `Agent(subagent_type: "inbox-triage")` fails at the tool boundary with `Agent type 'inbox-triage' not found`; so does `"probe"` and `"inbox-triangulate"`. They are Skill-tool names, and the agent registry is a different namespace. **The call that works**: dispatch a **registered agent type** — `debugger` is the closest fit for triage's identify → reproduce → relate shape (`analyzer` or `general-purpose` also work) — whose **first instruction is `Skill(skill: "inbox-triangulate")`** (or `"inbox-triage"` for the single-angle case), followed by the handoff prompt path. **The agent type supplies tools and posture; the `Skill()` call supplies the recipe, the report template and the guardrails.** That is the whole distinction `¶INV_DISPATCH_THROUGH_THE_SKILL` is protecting, and its mechanical check is exactly this: the dispatched agent's transcript must contain a `Skill` call for the triage skill.
*   **Post each result the moment its triage returns — this is the FIRST thing after the fan-out, and the phase cannot be left until it is done** (`¶INV_TRIAGE_BEFORE_TICKET`; posting is a **stage with a gate**, not a trailing bullet). Post a **new reply per pass** on the origin comment (dated timeline): lead with the one-line **verdict** + **reproduce links** (app URLs for every entity); **attach BOTH** the report and the handoff prompt (comment-level: `prepare_attachment_upload(issue)` → `curl` PUT bytes to the 60s signed URL, **one file at a time** → embed the returned `assetUrl` in the reply via `save_comment` **as a clickable markdown link** — `[📄 <filename>](<assetUrl>)`, one per file, **each alone in its own block with nothing after it on that line** (Linear renders a card only for a link that is the whole paragraph), in the posted body; naming a file in prose is not linking it and leaves the asset unreachable in the UI (`§INV_CHANNEL_EVIDENCE_RIDES_THE_COMMENT`); do NOT `create_attachment_from_upload` — that makes it a *ticket* attachment). A short 1–4 line finding may go inline instead of attached. The `triageAccounting` gate below records this reply's URL + the returned attachment ids per item, so a report left on disk cannot pass. Enrichment **accretes** across waves until an item is ripe.
    *   **A Linear `502 upstream_unavailable` is a false negative — never retry blind** (`§INV_VERIFY_LINEAR_WRITE_BEFORE_RETRY`): the write frequently lands despite the 502, so a blind retry double-posts. Before re-posting, verify with `engine project fetch --since=<just before the attempt>` whether the reply already landed; retry only if it did not, and delete any duplicate. This travels with every Linear write over MCP in the wave (post here, announce in Phase 5, file/backlink/resolve in Phase 6).
*   **Reply-based claim/return** — a doer (human or agent) claims with a `👀 claimed by <who>` reply and returns a `✅ result` reply. Reactions aren't MCP-addressable; state lives in replies. A dedicated doer-claim skill is deferred.
*   Enriched items flow into **Digest**; items whose triage didn't land this wave stay `needs-triage`, re-picked next wave.
*   **The `triageAccounting` proof field — one entry per `needs-triage` item on the Phase-2 worklist.** Phase 3 cannot be left without it. Shape:
    ```
    triageAccounting: [ { item, posted | skipped, relatedSearch } ]   // exactly one of posted | skipped
      posted        — { commentUrl, attachmentIds[] } — the Linear reply URL where the triage
                      report + handoff were ATTACHED via the proper upload flow
                      (prepare_attachment_upload → curl PUT the bytes to the signed URL → embed the
                      returned assetUrl in save_comment). attachmentIds are the REAL asset ids that
                      flow returns. A comment URL either resolves or it does not; a builds/ disk path
                      is NOT a satisfying pointer — that is the exact hole this field closes.
      skipped       — { reason, confirmedBy } — an explicit, human-confirmed declared absence:
                      deferred mid-fan-out (never ran), the item went moot, or a post that genuinely
                      could not land. The item stays needs-triage and is re-picked next wave.
      relatedSearch — what the unconditional related-tickets search found, INCLUDING "nothing found"
                      (§INV_RELATED_SEARCH_IS_UNCONDITIONAL — every item, whatever its marker)
    ```
    **A disk path is not an accounting, and neither is "no fan-out was needed".** Per item there are exactly two honest states — a **posted comment URL** whose attachments resolve, or an **explicit, confirmed skip** with a reason. A `builds/` path, or a prose sentence asserting the items were already enriched, satisfies neither: the report then exists only on the operator's own disk, unreachable from Linear — precisely the "6 written, 0 posted" failure. **Fail closed** — a resolvable pointer, or a declared absence, never a local path in between (the resolvable-pointer half is what the FIN-3578 fetch-and-verify guard will later check).

### Then — the mode gate. This is where a Quick Pass ends (`¶INV_QUICK_PASS_DECIDES_NOTHING`)

*A gate, not a trailing bullet — the same shape as Phase 5's intra-phase stages. Triage is the last phase **all three** modes share, so the fork is here and it is recorded.*

*   **Full Wave** → continue to Phase 4 (Digest). Nothing else changes.
*   **Decide** → continue to Phase 4 as well. **Decide does not stop early — it stops *late*; what it skips is at the front, not the back.** Phase 3 is not optional in this mode: it owns the unconditional related-tickets search (`¶INV_RELATED_SEARCH_IS_UNCONDITIONAL`), and Decide is by construction the *filing* pass, so it is exactly where a missed duplicate or a cancelled precedent turns into a filed ticket.
*   **Quick Pass** → **stop. Transition straight to `9: Synthesis`** and take the Quick Pass clause of its Final Sync block (debrief + watermark confirm; **no** Outcomes Board, **no** Project Update, **no** Slack announce). Phases 4–8 do not run.
*   **Custom** → the phase list the operator named at Setup, read back to them at Phase 0. If it stops before Phase 5, it closes exactly as a Quick Pass does.

**What a Quick Pass must NOT do on the way out** — each of these is the mode failing at the one thing it exists to do:

*   **Resolve a thread it triaged.** An unresolved thread is the record that a decision is still owed (`¶INV_RESOLVE_ON_DISPOSITION`); resolving it erases the handoff and the next Full Wave's pull (c) never sees the item. `resolve-comment` is not called in this mode, at all.
*   **Record a second watermark**, a `lastDecidedAt`, a pending-decisions list, or any other new marker for "what is still undecided." That set is the unresolved threads, derived from Linear on demand. Two markers on one project have to be reconciled by every pass, and reconciliation-by-reading is the failure this design avoids.
*   **Announce.** No Decision Board, no Project Update, no Slack post, no completion ping — `§PASS_HEARTBEAT` exists so a *skipped* pass is legible by the absence of its announce, and a pass that announces daily destroys that signal. A Quick Pass is a working pass, not a checkpoint.
*   **File anything.** No `/ticket`, no graduation, no adopt-or-cancel — not even for an item that looks unambiguous and urgent. Filing without a Full Wave is an open proposal, not protocol: do not implement it and do not offer it as though it existed.

**The `modeStop` proof field — one entry. Phase 3 cannot be left without it.** Shape:
```
modeStop: { mode, phasesRun, continuing | stopped }   // exactly one of continuing | stopped
  mode        — the mode selected at Phase 0 (full-wave | quick-pass | decide | custom)
  phasesRun   — the phase list this pass will actually have run, e.g. "0,1,2,3,9" for a
                Quick Pass; "0,1(reduced),2,3,4,5,6,7,8,9" for a Decide pass.
  continuing  — { next } — the phase being entered (a Full Wave or a Decide pass: "4").
                One line; this is the no-op side of the gate and it stays cheap.
  stopped     — { openThreads, resolvedNone, announced } — the handoff, stated as facts:
                openThreads  — HOW MANY threads this pass leaves unresolved, and therefore how much
                               is owed to the next Full Wave. A count, not "several".
                resolvedNone — the literal confirmation that resolve-comment was never called.
                announced    — false. Recorded, so a silently-fired announce is visible after the fact.
```
**A stop that records nothing is indistinguishable from a wave that crashed at Phase 3**, and the two want opposite responses from the next operator. The field is the difference.

**Then run `§ASK_INTAKE_PHASE_HANDOFF`** with the branch just taken. A Full Wave or a Decide pass fills it for **4: Digest** — `<T>` triaged items → clustering, merges, the dependency graph; it decides no dispositions. A Quick Pass or a stopping Custom reach fills it for **9: Synthesis**, carrying `modeStop.openThreads` as the number the next Full Wave inherits.

## 4. Digest — organize & consolidate (with triage data in hand)
*Now that thin signals are enriched, turn the wave's items into clustered, deduped, connected understanding + the problem map.*

**OWNS** — what the wave believes its problem is: clusters, merges, supersessions, the dependency graph.
**DEFERS** — priority and disposition (**5: Outcomes**) · executing any merge or move in Linear (**6: Ticketing**).

§CMD_REPORT_INTENT:
> 4: Digesting ___'s (triaged) signal. Finalize clusters, dedup/merge/supersede/connect, build the problem map.
> Focus: enriched items → deep clusters, dependency graph, root-cause map; refresh the working doc.
> Not: promoting or dispatching yet (that's Outcomes, Phase 5).

§CMD_EXECUTE_PHASE_STEPS(4.0.*)

**The interrogation here is the conjecture** (`¶INV_SUGGEST_BY_INTERROGATION`): *"these five symptoms look like one root cause — do they?"* · *"this merges into that — agreed?"* · *"is this superseded, or still its own thing?"* Consolidation is where a wave does its most consequential and least visible thinking: folding five signals into one parent silently rewrites what the project believes its problem is. Put the conjecture up as a question with its evidence, and let the leap be the human's (`¶INV_RESEARCH_MEMORY` — the system enables the conjecture, it never manufactures it).

**The `conjecturesAsked` proof field**: `[{ conjecture, evidencePath, verdict }]` — one entry per consolidation or root-cause claim put to the operator, with `verdict` one of `confirmed | rejected | deferred`. **A rejected conjecture must be logged with its reason**, because an unrecorded rejection gets re-proposed every wave. An empty array is valid only when the wave found nothing to consolidate — say so explicitly rather than omitting the field.

Phase 2 already did the *coarse* pass (collapse obvious twins, size the triage worklist). This is the **deep** pass — finalize the clusters now that triage has enriched the items, then consolidate across the whole project. Build on Phase 2's dedup; don't re-litigate it.

**Organize:**
*   **Chunk longform source first** — comments on the `Feedback & Transcripts` channel are whole emails / transcripts / threads. Split each into the discrete observations, shortcomings, requirements, and solutions it contains before clustering, so one transcript can feed several channels. Reply on the source comment with the chunks' destinations (provenance stays on the raw source).
*   **Dedup / cluster** related items; when an item echoes an existing one, drop a `seems like <cluster/FIN-…>` reply on its origin comment.
*   **Classify** each cluster into a bucket: `conversational` (needs shaping) · `research` (needs investigation) · `action` (ready to build) — mapping to the milestone it would graduate to.
*   Update the **working vision doc** — the evolving cross-scope understanding.

**Consolidate — keep a constantly-cleaned state** (`¶INV_CONTINUOUS_CONSOLIDATION`; run every wave, and whenever new input lands — nothing rots):
*   **Dedup** — the same item twice → mark one `duplicateOf` the other; keep a single canonical.
*   **Merge** — several tickets are facets of one → fold into a canonical (others `duplicateOf` it), carrying context forward.
*   **Supersede** — a newer/better-framed ticket obsoletes older ones → mark the old superseded + closed, so the live framing wins.
*   **Connect** — the consolidation primitive: distinct symptoms sharing a root cause → a **parent "root-cause / solution" ticket** with the symptoms as **children** (+ `relatedTo` / `blocks`). This is how "tickets A–Y are all fixed by solution Z" becomes visible — fix the *path*, not each symptom.
*   Maintain a **root-cause map** in the working doc: symptom clusters → hypothesized root cause → candidate consolidating solution.
*   **Human confirms every destructive op** (merge / supersede / close) — `¶INV_TICKET_EARNED_BY_CONFIRM` + `¶INV_LINEAR_IS_TRUTH`. Non-destructive connects (related / parent-child) are proposed, then applied on confirm.

**The problem map — dependency graph + research memory** (the anti-relitigation core):
*   **Dependency graph** (`¶INV_PROBLEM_DEPENDENCY_GRAPH`) — nodes = problems / candidate solutions; edges = *stands-on*, *blocked-by*, *unlocks*, *needs-research-from*. Materialize edges as Linear relations (`blocks` / `blockedBy` / parent-child / `relatedTo`) **and** hold the readable graph in the working doc. Turns "clumps of legos" into a map where Z stands on X,Y and unlocks O — and the 20%-effort / 80%-win node becomes findable.
*   **Research memory** (`¶INV_RESEARCH_MEMORY`) — investigation against a problem accumulates ON the **ticket** (findings, dead-ends, why/when), never on a person or a dead session. No problem is attacked from zero twice.
*   **Enable the conjecture, don't manufacture it** — /intake assembles the decomposed, dependency-aware, non-lossy context so a human makes the creative leap to a solution cheaply and once. It never claims to auto-generate the solution.

### Then — hand off to Outcomes (`§ASK_INTAKE_PHASE_HANDOFF`)

`<K>` clusters · `<M>` proposed merges · `<G>` graph edges → **5: Outcomes**, which ranks them, drives every item to a disposition, offers the panel and the Decision Board, and fires event 1 of the announce. It decides; it writes nothing — the writes are Phase 6.

### Prioritize first (`¶INV_TWO_LEVEL_PRIORITY`, `¶INV_RANKING_WITH_PROOFS`, `¶INV_SUGGEST_BY_INTERROGATION`)

*The interrogation here is the ranked read: **"pull this first, and here is the number behind it — agree?"** The impact model below produces an ordering, not a verdict; a wave can measure blast-radius and still be wrong about what matters this month, because urgency lives in things it cannot see — a trial in progress, a customer conversation next week, a commitment already made. Put the top of the ranking up as a question, with its proof, rather than publishing it as settled.*
*   **Intake-internal** — rank so the highest-leverage items are disposed first. Impact = **consolidation breadth** (a parent resolving N symptoms) + **non-self corroboration** (distinct reporters) + **blast-radius** (orgs/claims/users hit — the triage reports quantify this); effort coarse (S/M/L). Cite **proof-pointers** (comments / tickets / triage-report findings behind each).
*   **Output** — the durable ranking that guides doers: set the Linear **priority field** on graduated tickets AND keep a ranked "pull this first, and why, with proofs" list in the working doc → the Project Update.

### Then (optionally) convene the panel over the decision list — offered, never forced; it runs and is recorded (`panelRun`) BEFORE the board publishes
Once the decision list is ranked (above) and the orchestrator has drafted the board handoff, but **before** the board is rendered and published, **offer** a `/council` panel over that handoff, so the board can show what a diverse expert panel picked and why. Decline is a normal answer and the board renders exactly as it does today. The panel runs here — before the publish below — precisely because its marks are stamped onto the board the render then produces.

*   **Dispatch**: fill a Council Brief (`~/.claude/engine/skills/council/assets/TEMPLATE_COUNCIL_BRIEF.md`) with **subject** `doc <the filled handoff path>` · **mode** `report-only` (no human is at council's terminal mid-wave; the wave owns the gate) · a **`report_path` you mint for THIS dispatch** — required, because your check for "did a panel actually run" is the absence of that exact file, and council's own fallback path folds in a run-id you cannot predict · and a **`poll`** carrying one entry per decision: `id` · `kind` · the `options` you already authored · the **evidence an expert needs to rule** · and `depth`.
*   **Which items get a panel, and at what depth**: **steer** widgets at `depth: full` — that is where the judgement is. **Consolidation** widgets at `depth: brief` — a merge is the operation a human confirm demonstrably fails to audit, so it earns a panel; but approve/reject is binary and nine reasoning axes across a long op list produces boilerplate rather than thought. **Strays are not polled** — adopt-or-cancel is a placement call, not a reasoning one.
*   **The panel reacts; it never authors** (`¶INV_STEERING_NOT_SOLUTIONS`). The option set stays your curation. An expert's `alternative` comes back to **you** as a signal that the options may have been wrong — it never becomes a choice on the board. Act on it by re-authoring the options and re-rendering, or not at all; never by pasting it in.
*   **Feed the votes to the render subagent** through the handoff's panel-votes block, unedited (`¶INV_HANDOFF_STRUCTURED_NOT_LOSSY`).
*   **No panel is a normal outcome, and it is not a failure.** Council writes no report rather than seating a fake one, so an absent report means an absent panel — render the board without marks and say so in the log. Never reconstruct the votes yourself: an orchestrator writing the panel's opinion is the simulated-diversity failure the whole mechanism exists to avoid.
*   **Log what it cost** (`§CMD_APPEND_LOG`): panel size, items polled, wall-clock, tokens. The cost of a pass is a standing instrument for this project, not a one-off curiosity — record it in that shape so it aggregates instead of becoming a stray line. A panel that turns out expensive relative to the triage fan-out is a decision for the operator, not an implementation detail to absorb quietly.

**The `panelRun` proof field — a RECORDED outcome (like the announce), not a hard gate on a panel running.** Phase 5 cannot be left without it, but a no-panel wave is a normal, passing outcome — the field only forbids **silence** about whether a panel was even offered. Shape:

### Then disposition each item (per-item; human confirms — `¶INV_TICKET_EARNED_BY_CONFIRM`)
Apply the **recorded binary ripeness checklist** (`¶INV_RIPENESS_IS_A_RECORDED_CHECKLIST`) — ripe only when ALL: [ ] crisp one-sentence problem · [ ] defined next-action · [ ] brief type assigned · [ ] ≥1 *non-self* corroboration (the skill's own replies don't count). Record the result.

**The checklist is project-configurable** (`¶INV_DIRECTIONS_IN_DESCRIPTIONS`): the four above are the *default*. A channel's or project's `## Directions` may add a criterion (e.g. "a fixture needs the corrected answer plus its evidence"), relax one (e.g. "a lone cross-cutting conjecture is ripe without corroboration — route it to Needs research"), or reprioritize what counts as a crisp problem here. Record the checklist **as actually applied**, naming which items came from Directions — a silently-swapped gate is unauditable. Directions may never remove the human confirm (`¶INV_TICKET_EARNED_BY_CONFIRM`).

**Then the chunkiness gate** (`¶INV_TICKETING_STRATEGY_IN_HANDBOOK`) — a **separate** call, run only on items that passed ripeness. Ripeness asked *"is this well-formed enough to be a ticket?"*; this asks *"should it be its OWN ticket?"* Apply the project's `## Ticketing Strategy` (loaded at Setup off the handbook; the catalog default if the project has none, in which case say so) and answer:

*   **Its own ticket** — it clears Volume, Size and Substance as that project defines them. Graduate.
*   **Fold into a parent** — real, but a facet of something already tracked or of a root cause. Use Phase 4's existing machinery (`relatedTo` / parent-child / merge) rather than filing a sibling; carry its context onto the parent so nothing is lost. This is how chunkiness is actually achieved — the gate names the call, Digest performs it.
*   **Keep marinating** — real but not yet a chunk worth tracking on its own.

**Record the call as applied**, next to the ripeness checklist: which of the three bullets decided it, and — when the project had no section — that the default was used. A silently-applied volume policy is as unauditable as a silently-swapped ripeness gate. The strategy steers the judgment; it never removes the human confirm (`¶INV_TICKET_EARNED_BY_CONFIRM`), and it is never a reason to discard an item — "not its own ticket" always means folded or marinating, never dropped.

**The `dispositions` proof field — one entry per item dispositioned this wave.** Phase 5 cannot be left without it, and it is what makes `¶INV_DISPOSITIONS_RESOLVE_AT_OUTCOMES` checkable rather than merely stated. Shape:
```
dispositions: [ { item, disposition, evidencePath, decidedAt } ]
  disposition  — graduate | fold | route | move-project | split | merge | supersede | adopt | cancel |
                 shipped | marinate | keep-enriching
                 shipped — the work was ALREADY DONE before the wave looked, so no ticket was
                 warranted. Not `cancel`: that is a decision not to do something, this is a
                 discovery that it is finished. Reporting them as one outcome loses the
                 distinction that shows the inbox working.
  evidencePath — the artifact the decision rests on: a triage report, a query result, a measured count.
                 "the reporter said so" is NOT evidence — it is the input triage was supposed to check.
  decidedAt    — the phase the call was actually made in. If it is not 5, say so: that is a
                 §INV_DISPOSITIONS_RESOLVE_AT_OUTCOMES exception and it must be visible, not buried.
```
A **move-project** disposition with no `evidencePath` is the exact failure this field exists to surface — a visible action on someone else's work, taken on unverified text. Write the path, or do not make the call.

Then exactly one disposition:

1.  **Graduate → ticket** (ripe, type obvious): **file it via `/ticket` — never hand-write the body** (`¶INV_GRADUATION_VIA_TICKET`). Invoke `/ticket` with a **caller-pinned placement**: the project + the work-type **milestone** (`Needs decision` / `Needs research` / `Ready for action` / `Quick wins`), else `Uncategorized`, and **new issue, never a sub-issue** — the parent `/ticket` would otherwise detect is the frozen inbox collector the signal arrived on, and a sub-issue there gets parked straight back out (`§INV_INBOX_NOT_TICKETS`). **Never `Inboxes`.**
    *   **`/ticket` owns the body**, and that is the whole point of routing through it: the plain-terms opening line, premise-first sections, non-goals, acceptance signals, the **spike escape-hatch** for a research item with no honest acceptance criteria yet, and — the one that matters most to a wave — **conservative single-ticket-by-default decomposition that never inflates the count.** A wave that hand-writes bodies produces essays only their author can read, and more of them than the work justifies.
    *   **What /intake keeps** (graduation semantics `/ticket` knows nothing about): the **recorded ripeness checklist** as actually applied, the **priority from this wave's ranking**, **idempotency** (`¶INV_IDEMPOTENT_PROMOTION` — pre-write key so a crash never double-files), the **`filed as FIN-XXX` reply** on the origin comment, and recording `FIN-XXX` in the working doc.
    *   **Correcting a ticket a wave filed** — this wave or an earlier one — goes through **`/snapshot`**'s description-drift flow, **never a freehand overwrite**: an evergreen body carrying every prior `## Change history` entry verbatim plus one new dated line, with the description **re-read immediately before** the full-field replace. Two reasons it isn't optional: a wave that overwrites a description it filed earlier can silently clobber a human's edit, and a body that accumulates correction blocks forces every future reader to reconstruct what is currently true. Routine progress is a comment, not a rewrite.
2.  **Graduate → Needs-research ticket**: items needing deep work — same `/ticket` route as (1) with the milestone pinned to `Needs research`, and carry the accumulated triage/research memory onto the ticket. If the item has no honest acceptance criteria yet, let `/ticket`'s **spike** type do its job rather than inventing criteria to fill the form. (Deep research runs on the ticket, not the inbox.)
3.  **Keep enriching** (triage ran but the item's still thin, or its triage didn't land this wave): leave it `needs-triage` — Phase 3 re-picks it next wave; the accreted `✅ result` replies stay on the comment. **Bound it**: if triage has failed to make it ticketable across a few waves, stop churning — reply asking the reporter for the missing detail, or marinate it with the gap recorded. Don't loop `needs-triage` forever.
4.  **Marinate** (not ripe, nothing more to gather): leave it (`¶INV_NO_RUSH_ITEMS_TO_CLOSURE`); record *why* in the doc.
5.  **Park sub-issues** (`¶INV_INBOX_NOT_TICKETS`): issues parented under a frozen inbox channel ticket → propose **reparenting each to `Uncategorized`** (confirm each — someone else's ticket). Keeps `Inboxes` frozen-collectors-only.
6.  **Shipped — close it without a ticket** (`shipped`): triage found the work already done. Reply `shipped in FIN-XXX` naming the ticket or PR that did it (the evidence, not a claim), record the disposition, and resolve the thread — it has left the inbox (`¶INV_RESOLVE_ON_DISPOSITION`). If nothing can be named, it is not shipped; it is `already-clear` and still needs a disposition.
7.  **Adopt or cancel a stray** (`¶INV_ADOPT_OR_CANCEL_STRAYS`): a ticket swept from a milestone with **no wave-provenance** (Phase 1). It already exists, so the call is binary and is **not a graduation** (no `/ticket`): **adopt** — move it to the correct work-type milestone the triage indicates (a milestone reassignment, one-way skill→Linear) — or **cancel** — close it into `Cancelled` with the *why* recorded (`¶INV_RESEARCH_MEMORY`). Confirm each (`¶INV_TICKET_EARNED_BY_CONFIRM`); never leave a stray unsorted, never silently delete.

### Then decide WHICH threads leave the inbox (`¶INV_RESOLVE_ON_DISPOSITION`)

*This phase decides; **Phase 6 executes** — it runs `resolve-comment` after the pointer reply is posted, and accounts for every item in its `resolutions` proof. The policy below is the rule both phases share; it lives here because "has this signal left the inbox?" is a disposition question, not a write.*

An **unresolved** comment thread means *"this signal still needs something from the intake pass."* So resolve it exactly when that stops being true — after the pointer reply is posted, never before:

*   **Filed as a ticket** → resolve (the `filed as FIN-XXX` reply carries the pointer).
*   **Folded into a parent** → resolve (reply names the parent).
*   **Already shipped** → resolve (the `shipped in FIN-XXX` reply names the ticket or PR that did it). Distinct from the line below: nothing was decided against, the work was simply already finished.
*   **Closed as outdated / incorrect / superseded / not-a-problem** → resolve, with the reason in the reply.

**Do NOT resolve** while it is still intake's problem: `needs-triage`, marinating, or parked against a Direction. Those are live signal awaiting a disposition, and burying them is exactly the loss this system exists to prevent.

**Never resolve on ticket-DONE.** The ticket owns the work's lifecycle; the comment owns the *signal's*. Mirroring done-ness back into the inbox creates two sources of truth for one fact (`¶INV_LINEAR_IS_TRUTH`), and threads would sit open for months — defeating the archiving entirely.

**A reply on a resolved thread un-resolves it** and re-enters the next drain. Resolution means *dispositioned*, never *closed to further input* — otherwise it silently revokes the promise every channel now makes: *"the triage that comes back is a draft… reply on your own comment."*

**Mechanism**: `engine ticket resolve-comment <commentId>` (the Linear **MCP exposes no comment-resolve mutation** — only `resolve_diff_thread`, which is for diff reviews; the CLI reaches the GraphQL API directly via `linear-lib.sh`, mirroring `ticket-search.sh` / `project.sh`). Run it once per disposed thread, after the pointer reply is posted — it prints `🎟 resolved <id> at <ts>` and exits non-zero on failure. To undo a resolution (a reply that re-opens the thread), `engine ticket resolve-comment <commentId> --reopen`. **Fall back to asking the human only when the command itself fails for lack of a configured `LINEAR_API_KEY`** (it exits non-zero saying so) — never silently skip it, and never claim it was done when it was not.

### Finally — sync, then fire the two-point announce (event 1) and record its handles
*   **Sync the state** (`¶INV_LINEAR_IS_TRUTH`, one-way doc→Linear, skill-derived framing only; never overwrite human-owned state): refresh the **Project description** with the current cross-scope understanding + the ranked "where to start" read — **inside the section schema only** (`¶INV_DESCRIPTION_SCHEMA_IS_A_WRITE_CONTRACT`). In practice that means `## Directions` and, where the people-facts actually changed, `## Stakeholders`. **A wave never adds a section the schema does not name.** Everything else a wave wants to say — pass narration, findings, standing rules, the ranked read in full — goes into the **Project Update** or the **Inbox Handbook**.
    *   **Lint the new description BEFORE the write, and refuse the write on failure** — the schema stops being a thing the agent has to remember:
        ```bash
        printf '%s' "$NEW_DESCRIPTION" | engine project lint --stdin --container description --strict
        ```
        **Exit 1 = do not write.** Fix the finding and re-lint; each one names the offending `## ` heading and, where a sibling container claims it, the container it belongs in (`belongsIn`) — usually the **Inbox Handbook**. **Exit 2 = could-not-run**; do not treat it as a pass and do not write blind — say what failed. Exit 0 may still carry `warn`s: a heading no container names is surfaced, not blocked, because the check is **stateless** and cannot tell a heading you are *adding* from one that was already live (`¶INV_DESCRIPTION_SCHEMA_IS_A_WRITE_CONTRACT`) — read them, and if one is yours, move it before writing. The gate lints the text **you are about to write**, so run it after composing and before `save_project`/`update_project`.
*   **Offer the Project Update** (`¶INV_TEAMMATE_FACING_LINEAR`, `¶INV_UPDATE_READS_COLD`) — the wave's team-facing checkpoint (what was *triaged / filed / handed off / parked* this wave, what's *marinating*, honest counts incl. nomination-rejections + staleness). **Offered / confirmed, never auto-posted.**
    *   **Write it to be read cold** (`¶INV_UPDATE_READS_COLD`): at most ~5 facts in the body, each standing alone with a number and a customer-visible consequence; the full facts ledger in a **linked document**, not inline; no report numbers, no table/column names, no wave-process meta, and **no before/after corrections** — the reader never saw the "before". Before posting, re-read it as someone who joined today: every sentence you cannot follow is a defect, not a nuance. If the user declines here, it's re-offered on-demand in Discussion (Phase 7) and backstopped at Close (Phase 9) — no wave closes without a checkpoint.
*   **Event 1 of the two-point announce — post the Project Update + a Slack ping, capture the update id** (`§PASS_HEARTBEAT`): post the Project Update carrying the **Decision Board URL** ("ingested `<N>` · Decision Board: `<url>` — steer/vote here"), and emit a **fresh** Slack announce via `engine slack-post --channel <this project's channel NAME from `INBOX_REGISTRY.md` § Slack announce channels>` — **preflight once per wave first** with `engine slack-post --verify --channel '#name'`, which checks token, scopes, channel and bot membership and self-joins where it can. Preflight because the announce is best-effort and never blocks: an unverified setup fails silently and stays broken for waves. The announce carries headline + ranked "pull first" + honest counts + **latest watermark** + a **"previous pass ran `<date>` (`<N>`d ago)"** gap line (prior update's timestamp via `get_status_updates`, no cron) + a **decision-refs block**. **The refs block is what makes a threaded reply attributable**: it enumerates the wave's decisions as `[1] <short label>` … `[n]`, each linking to `<board-url>#<item-id>` — the item's own id, the same value the board emits as `data-fb-item`/`id` and the same value a `note` event is keyed on (`assets/PAYLOAD_SCHEMA.md`). **The bracket number is display only; the anchor carries the identity** — so a teammate replying *"[3] yes, endorsements should be their own line"* has cited a specific decision, and next wave's Ingest keys their answer onto that item instead of guessing which one it answered. Render each ref as a link with a short label, never a raw URL. This is also why the announce goes out **as caller-supplied blocks**: `engine slack-post --blocks <path|->` sends a Block Kit array verbatim (`--title` BUILDS a layout, `--blocks` SUPPLIES one — the poster stays generic and never knows an intake layout). **Do not hand-assemble the JSON — compose it.** `engine intake-announce --state decision` reads the wave's **facts** on stdin and emits the payload, which pipes straight into the poster: `engine intake-announce --state decision <<'EOF' | engine slack-post --channel '#name' --blocks -`. Run `engine intake-announce --help` for the facts shape. **The composer enforces two rules rather than trusting the caller**: a `waiting` entry with no `slackId` renders the plain name and **no** mention, and `signal` entries at count 0 are dropped. **`overview` (and `outcome` at close) is passed IN, never generated** — that block is judgement, and a template would produce the filler it exists to replace. **The announce is ONE message with TWO states** — `assets/announce-blocks.decision-state.example.json` shows the decision state's output; `assets/announce-blocks.outcomes-state.example.json` is what event 2 edits it into. The two share one skeleton, and the way it grows is the design:

    *   `header` · `context` (operator · drained · window · previous-pass gap) · **`callout`** · **`section` overview** · *(at close: a second `section`)* · `table` · **`container` "Pull these first"** · **`container` "Waiting on"** · `context` (signal-in) · `divider` · `context` (watermark · Project Update). **10 blocks open, 11 at close** — the one added block is the point: the closed message keeps everything it said and *adds* what happened, so the record grows rather than being replaced.
    *   **The overview paragraph is the block someone reads if they read nothing else.** It characterises the PASS and never individual items: scope, cadence (and *why* it slipped), the back-and-forth since the last announce, how much is genuinely new versus already-known-but-changed, what is unblocked, and what is blocked — plus whether the blocker needs a *decision* or more work. Items are what the refs block is for; this block is what the wave *is*. At close it shifts to **past tense** and a second paragraph joins it below — *"What came in"* then *"What changed"*. **Stacked `section` blocks, never a two-column `table`**: table cells are `raw_text` and strip every bold and italic, and a prose grid sitting above the counts grid reads as one confused table (tried live, rejected).
    *   **The callout is the state indicator** — colour plus copy, above the fold. Orange *"N decisions open — nothing filed yet"* + 🗳️ board link becomes green *"N filed · M folded · K parked"* + 📋 outcomes link. A reader who reads nothing else still learns whether they owe you a decision.
    *   **"Pull these first" carries the top 5 refs and nothing else** — each `[n] <label>` linking `<board-url>#<item-id>`, followed by **the number behind the call** (blast-radius / corroboration, which the ranking already required). Then `+ N more · all on the board →`. **No `@`s in this block**: a person owning three decisions would appear three times, and the list would stop being scannable as a list of *decisions*.
    *   **"Waiting on" does the addressing, one line per PERSON**: `<@id> — <board-url>?user=<slug>|N decisions to make`. The `?user=` param hands each person *their* board instead of the whole board, so 8 decisions across 3 people is 3 lines, not 8 mentions.
    *   **Signal-in shows only non-zero channels**, each counter linking `<board-url>?inbox=<channel-slug>`, plus a *"five of ten channels quiet"* summary (the count is the registry's size at run time, not a fixed number — `INBOX_REGISTRY.md` has grown twice) — once the zeros are dropped, that sentence is the only thing left saying those channels exist and nobody is using them.
    *   **At close the same blocks INVERT rather than move**: "Pull these first" → "What we decided" (same `[n]`, now carrying its outcome), "Waiting on" → "Who weighed in" (the ask becomes credit). **The `[n]` numbers never change** — a threaded reply citing `[3]` must stay valid across the edit, which is exactly why the number is display-only and the anchor carries identity.

    **Three honest caveats.** (1) What was *proved* is that these block **types** render; the **arrangement** is a working reference, not a settled design. (2) **Verify any non-classic type against the target workspace before depending on it** (`callout`, `table`, `container` are not the classic Block Kit set) — an unsupported type fails the WHOLE payload rather than degrading, so a one-shot post-and-delete probe per type is the cheap check. (3) **Never render a person the wave cannot evidence.** An unresolved `@name` renders as plain text and notifies nobody — a visible ask with an invisible outcome — and an *invented* name is worse still, because it manufactures an obligation for someone who does not exist. No known Slack id → plain name, no mention. The example files carry a `<@SLACK_ID:name>` placeholder for precisely this reason: it cannot ping anyone and cannot go stale. **Capture the `save_status_update` id into `INTAKE.md`'s pinned `Project Update:` slot** (§1) — Close (Phase 9) edits that same Update in place to add the outcomes + the Outcomes Board URL. **The id, not the phase, is what event 2 needs**: capture it wherever the Update actually posts (here, in Discussion, or the Close backstop), never assume it was Phase 5. The Slack announce is a plain post — Slack and Linear are independent transports, so a Slack failure never affects the Update and vice-versa. **Also capture the Slack message `ts`** that `slack-post` prints to stdout on success, into `INTAKE.md`'s pinned `Slack announce ts:` slot beside the Update id. **The NEXT wave's Phase 1 Ingest reads this thread** (`engine slack-read --thread-ts <it>`) to drain the replies humans left here — a thread's `thread_ts` **is** its parent message's `ts`, so this is the only anchor by which those replies can ever be found, and **a wave that does not capture it is permanently unreadable**. Best-effort: a missing token/channel or Slack error is logged and **never blocks the wave**. Setup + env vars + the full two-point flow: `§PASS_HEARTBEAT` in `INTAKE_SYSTEM.md`.

**The `announce` proof field — the two-point announce's event 1, recorded rather than gated on success.** Phase 5 cannot be left without it, but it gates on **silence, not on Slack**: a missing token or a declined Update is an explicit skip and passes; only an *unrecorded* announce fails. Shape:
```
announce: { projectUpdate, slack }
  projectUpdate — { statusUpdateId }  (the save_status_update id, pinned to INTAKE.md's
                  `Project Update:` slot — Close edits that same Update in place)
                  OR { skipped: reason }   (the Update was declined or not posted)
  slack         — { ts }  (the slack-post ts, pinned to INTAKE.md's `Slack announce ts:` slot —
                  the ONLY anchor next wave's Ingest reads; an uncaptured one is permanently unreadable)
                  OR { skipped: reason }   (transport deaf: missing token / scope / channel)
```
**Best-effort is preserved**: a `skipped` on either transport NEVER blocks the wave (Slack and Linear are independent). **But a published board with neither a handle nor a skip-reason FAILS** — silence is the one state that no longer passes, because the `ts` is the only anchor by which the next wave can read this thread. Same false-negative rule as the post step (`§INV_VERIFY_LINEAR_WRITE_BEFORE_RETRY`): a Linear `502` on the Update is verified via `engine project fetch --since`, never retried blind.

**Off-protocol input** (e.g., "just go fix this bug") → route via `§CMD_REFUSE_OFF_COURSE`: /intake dispatches context-rich briefs, it does not execute. Offer to graduate-and-hand-off instead. **An ask for a later intake PHASE is a different thing and does not go through that command** — name the owning phase and offer the hand-off (`¶INV_EVERY_PHASE_DECLARES_ITS_BOUNDARY`).

### Then — the write gate. Deciding and writing fail differently (`§ASK_INTAKE_PHASE_HANDOFF`)

*A fork, not a straight continuation — and the reason Phases 5 and 6 exist separately at all. Crossing this boundary converts `<D>` dispositions into filings, backlinks and resolutions on other people's tickets, and that is the first thing this wave does that other people see.*

*   **Write them now** → **6: Ticketing**: a fresh FULL re-fetch (`¶INV_REFETCH_BEFORE_WRITING`), then `<F>` filings via `/ticket`, `<B>` backlinks, `<R>` resolutions.
*   **Hold the writes** → stay in Phase 5. The dispositions keep; the threads stay unresolved, which is the state they were already in. Nothing is lost by waiting.
*   **Close without writing** → **9: Synthesis**, exactly as a Quick Pass closes: dispositions recorded, nothing filed, and the next Full Wave's pull (c) re-offers every thread.

Then run `§ASK_INTAKE_PHASE_HANDOFF` with the chosen branch's numbers.

## 6. Ticketing — re-fetch, then EXECUTE the dispositions
*Phase 5 decided. This phase acts. It is separate because deciding and writing fail differently: a decision is judged against evidence, a write is judged against the tracker's state **right now** — and those are hours apart.*

**OWNS** — the writes: filings, backlinks, resolutions, and the re-fetch they stand on.
**DEFERS** — re-deciding anything (that was **5: Outcomes**) · the downstream work itself (never).

§CMD_REPORT_INTENT:
> 6: Executing ___'s dispositions. Re-fetching Linear first, then filing, backlinking, resolving.
> Focus: a fresh FULL fetch; graduate via /ticket; post `filed as` backlinks; resolve every thread that left the inbox.
> Not: re-deciding dispositions (that was Phase 5), and never doing the downstream work itself.

§CMD_EXECUTE_PHASE_STEPS(6.0.*)

### First — re-fetch the WHOLE project, and rebuild the action list from the PAYLOAD (`¶INV_REFETCH_BEFORE_WRITING`)

```
engine project fetch <projectId> --out=<sessionDir>/builds/project-fetch-<ts>-prefile.json
```

**No `--since`.** A delta only returns what changed, and the items that most need catching are the ones nothing has touched — a delta cannot see them by construction.

**Then build the action list by walking that payload**, not by reading `INTAKE.md`. The working doc is a reasoning surface; it is never an input to a write. **An inventory lists what you handled, so it can only ever contain what you already knew** — which is exactly why it cannot be the source for a phase whose job is to act on everything.

The re-fetch also supplies two things nothing else can:

*   **`resolvedAt` / `resolvedBy` per comment** — so the phase can see which threads are already closed, report an honest open/closed ratio, and avoid re-posting a pointer onto a thread that already has one.
*   **Comments posted since Phase 1** — including replies correcting a triage this very wave produced, which are the highest-value drops there are (`¶INV_RESOLVE_ON_DISPOSITION`).

**Log the delta out loud**: items on the Phase-5 disposition list, items in the payload that are on no list, and any item whose state changed since Phase 1. A silent re-fetch that finds nothing new must still say what it scanned (`¶INV_ECHO_ON_SKIP`).

### Then — cite, never summarize (`¶INV_CITE_DONT_SUMMARIZE`)

**Every disposition executed here quotes its source verbatim from the payload just fetched.** Not the working doc's one-line summary of it, not a quote carried forward from Phase 3 — the text as it reads *now*.

Quoting requires reading, which is the entire mechanism. A summary you wrote yourself feels like evidence and is not (`§INV_CONFIDENCE_FROM_THE_CHECK`); a citation you carried forward through three phases is a point-in-time artifact that has been silently aging (`§INV_POINT_IN_TIME_CHECKS_EXPIRE`). **The re-fetch is what keeps citations honest — that is why the two rules ship together and why this phase opens with the fetch.**

If you cannot paste the sentence that justifies a call, you have not established the call. Say so and leave the item for the next wave rather than acting on a remembered shape.

### Then — execute each disposition
Run the calls Phase 5 recorded, in this order per item, and **verify each write in its response rather than assuming it landed** (a save that reports success is not proof the field is set — re-read placement, milestone and assignee off the returned object):

1.  **Graduate** → file via `/ticket` with caller-pinned placement (`¶INV_GRADUATION_VIA_TICKET`). Never hand-write the body; never file into `Inboxes`; never as a sub-issue of a channel.
2.  **Backlink both ways** (`¶INV_PROVENANCE_IS_TWO_WAY`) — the `filed as FIN-XXXX` reply on the origin comment **and** an `## Origin` section on the ticket carrying `§FMT_TICKET_COMMENT_LINK` deep links back. A ticket whose origin is unreachable gets re-triaged into a second ticket next wave, which is precisely how "the same-y issues" reproduce.
3.  **Fold / adopt / cancel / route** — as decided, each with its pointer reply.
4.  **Resolve** the threads that left the inbox, per the policy in Phase 5 — `engine ticket resolve-comment <commentId>`, after the pointer reply is posted, never before.

### The `refetch`, `filings` and `resolutions` proof fields
Phase 6 cannot be left without all three.
```
refetch:     { payloadPath, commentCount, resolvedCount, newSincePhase1[] }
             newSincePhase1 — comment ids absent from the Phase-1 drain. An empty array is a
             valid answer; an ABSENT field is not.

filings:     [ { item, ticketKey, placementVerified, originBacklink, ticketOrigin } ]
             placementVerified — read back off the save response: project + milestone + assignee.
             originBacklink    — the `filed as` reply URL on the origin comment.
             ticketOrigin      — the deep link ON the ticket pointing back. Both, or neither counts.

resolutions: [ { item, resolved | openBecause } ]      // exactly one
             resolved    — the resolve-comment receipt.
             openBecause — one of: decision (link the decision ticket) · capacity (link the parent
                           it folded into) · accepted (the reason, recorded) · information (NAME the
                           missing fact). An item that fits none of the four means triage is not
                           finished on it — say that, rather than inventing a bucket.
```
**Every dispositioned item appears in `resolutions`.** The four buckets are exhaustive by design: only *information* is an honest reason for an inbox thread to stay live, and it must name what is missing. Reporting the open/closed ratio each wave is what stops the inbox silently becoming a graveyard of dispositioned-but-open threads.

### Then — hand off to Discussion (`§ASK_INTAKE_PHASE_HANDOFF`)

`<F>` filed · `<R>` resolved · `<O>` left open with a named reason → **7: Discussion**, a held loop that costs nothing until the operator uses it. Close is a first-class option there, and here.

## 7. Discussion (held — optional)
*Keep the context alive: dig into clusters, ranking, or dispositions before closing. Close is always on the table.*

**OWNS** — reconsidering, on demand, while the wave's context is still alive; any earlier action is re-callable inline here.
**DEFERS** — nothing downstream, by construction. Closing still routes through **8: Documentation**, which asks for the steer.

§CMD_REPORT_INTENT:
> 7: Holding open for discussion on ___. Digging into clusters / ranking / dispositions on demand.
> Focus: let the user interrogate the wave's outcomes; adjust dispositions; keep context without forcing closure.
> Not: rushing to close — but Close is always offered, never hidden.

§CMD_EXECUTE_PHASE_STEPS(7.0.*)

A bounded held loop. The wave's productive pass (1→5) is done; now the user may dig in. The earlier **actions remain callable inline** here — drop more input (re-drain), re-scope, re-triage an item, re-cluster, re-rank, adjust a disposition — without a formal backward phase jump. *   **Ingest Decision Board answers** (`¶INV_BOARD_PAYLOAD_IS_ADVISORY`): answers arrive by **three routes and the wave must check all of them** — the operator pasting a payload, the board's own shared state doc when this wave's board carried a state config, *and* the **Slack replies Phase 1 drained from the prior wave's announce thread** into `INTAKE_DRAIN.md`. Then, for both routes alike, **follow the ingest procedure in `assets/PAYLOAD_SCHEMA.md`** — that file owns the rule outright, including how the two payload versions are told apart, how events are deduped and superseded, and how a **human** tally is kept separate from the panel's read. Do not restate the rule here: it used to live in both files, and that is how two specs drift. What this phase owns is what the tally is *for* — an **advisory leaning** at each item's chat confirm, with the human still deciding every disposition/consolidation/adopt/cancel, and the panel's read presented as one layer further from authority than a teammate's. A `measure:*` selection **re-opens triage** on that item inline (re-enrich → re-digest → re-offer the board delta); this loop is **unbounded — it runs until the operator closes the wave** (the no-rush guarantee is item-level; the *session* ends when the operator says so, not on a lap count — `¶INV_NO_RUSH_ITEMS_TO_CLOSURE`).

After any action, re-present the ready state via `AskUserQuestion` (multiSelect: false):
> "Wave for `<initiative>` — what next?"

> - **"Drop more input"** — re-ingest / re-scope / re-triage whatever's new (re-runs the relevant phases inline).

Fill it: `<Q>` steer proposals accumulated → **8: Documentation**, which interrogates the Directions (never authors them) and refreshes the knowledge base and the handbook. It will NOT restate the wave's findings — the Update and the ledger own those.

## 8. Documentation — refresh what people read, and ASK for the steer
*The wave learned things. The docs a teammate reads have not. This phase closes that gap — and it asks rather than assumes, because a Direction is the operator's steer and the agent is not entitled to author one.*

**OWNS** — what teammates read afterwards, and asking the operator for the steer.
**DEFERS** — authoring a Direction (the operator's, never the agent's) · restating the wave's findings (the Update and the ledger own those).

§CMD_REPORT_INTENT:
> 8: Refreshing ___'s documentation from what this wave learned. Interrogating the Directions rather than rewriting them.
> Focus: the Notion knowledge base, the Project description's linked resources, the Inbox Handbook, and a proposed Directions steer put to the operator as questions.
> Not: authoring Directions unilaterally, and not restating the wave's findings — those live in the Update and the ledger.

§CMD_EXECUTE_PHASE_STEPS(8.0.*)

### Interrogate the Directions — never write them (`¶INV_DIRECTIONS_ARE_ASKED_NOT_AUTHORED`)

The Directions say *what this project is chasing right now*. A wave is the best-informed party about whether they still fit — and the **worst-placed** party to decide, because it has spent a day inside one slice and will mistake what it just measured for what the project should want.

So the wave **proposes and asks**. Run `§CMD_INTERROGATE` with the wave's evidence in the question body:

*   **Still true?** Walk each in-scope and out-of-scope line and ask whether the wave's findings change it. Cite what changed — *"we found X; does that move Y in or out?"* — never *"I have updated the Directions to say…"*.
*   **Newly ripe or newly dead?** Something the wave proved is bigger than assumed (widen), or proved is a non-problem (narrow). Both need a human yes.
*   **What should the next wave chase first?** The steer is forward-looking; the ranking is not the same thing.
*   **Does the ripeness bar still fit?** Directions may modify the ripeness checklist (`¶INV_RIPENESS_IS_A_RECORDED_CHECKLIST`), and a wave that kept graduating unripe items or kept rejecting ripe ones has evidence the bar is wrong.

**Apply only what comes back**, and lint before writing (`¶INV_DESCRIPTION_SCHEMA_IS_A_WRITE_CONTRACT`). A declined proposal is a recorded outcome, not a failure — write it into the log so the next wave doesn't re-propose it.

### Refresh the knowledge base (`¶INV_NOTION_KNOWLEDGE_BASE`)

The obligation to keep Notion current already exists. What has been missing is a phase that discharges it, so it silently never happens — the same shape as thread resolution before it was gated.

**Documentation carries evergreen facts ONLY** (`¶INV_DOCUMENTATION_IS_EVERGREEN`) — the design of the model, how the pieces are meant to fit, the project's structure, the vocabulary a newcomer needs. **Never point-in-time material**: current measurements, this wave's findings, ticket or comment links, Project Updates, or the facts ledger. A number belongs in the ledger; a decision belongs on its ticket; a pass belongs in the Update. **The link outlives the fact** — a page pointing at "the five open decisions" is wrong the week they are answered, and nobody goes back to fix an explainer.

*The distinction to hold: **the ledger is dated evidence; documentation is undated design.*** A wave's instinct is to enrich the docs with what it just learned, and that instinct is exactly what turns an evergreen page stale.

*   **Read the linked page and its subpages.** What a wave legitimately changes is **narrow**: where it found the *design description itself* wrong or overstated. Correcting *"the file number groups claims"* to *"the file number is meant to group claims and is not yet populated"* is evergreen — design plus state of completion, no number, no date, no link. Adding *"we measured it empty on 13,494 rows"* is not.
*   **Audit the Project's linked resources.** Retired and superseded documents accumulate: a doc marked `(Retired)` still listed as a project resource is a live-looking link to dead guidance. Propose unlinking; never silently delete someone's document.
*   **Notion writes need interactive auth** — in a headless or cron run, say the transport was deaf and record what *would* have changed, rather than reporting success.

### Feed the handbook (`§CMD_OFFER_HANDBOOK_CAPTURE`)

Standing rules and triage recipe belong in the Inbox Handbook, not the Update and not the Directions. Offer capture where the wave followed or **contradicted** a documented recipe — a contradiction is the higher-value capture and the easier one to skip.

### The `directionsReviewed` and `knowledgeBase` proof fields
```
directionsReviewed: { asked[], applied[], declined[] }
  asked    — the questions actually put to the operator (not a summary of intent to ask)
  applied  — the edits made, each with the answer that authorized it
  declined — proposals the operator rejected, WITH the reason, so the next wave does not re-propose
  A wave that changed nothing passes — { asked: [...], applied: [], declined: [...] } is a
  complete answer. A wave that asked NOTHING does not.

knowledgeBase: { reviewed[], updated[], staleFound[] } OR { skipped: reason }
  staleFound — contradicted or superseded pages and dead links, even where nothing was fixed.
               Naming stale documentation you did not repair is worth more than silence about it.
```

### Then — hand off to Synthesis (`§ASK_INTAKE_PHASE_HANDOFF`)

The last boundary, and the cheapest to fill honestly: `<A>` Directions edits applied · `<D>` declined → **9: Synthesis**, which publishes the Outcomes Board, fires event 2 of the announce, writes the debrief and confirms the watermark. It will NOT decide anything — everything is already decided.

*   Refresh the **Research snapshot issue** if research threads advanced.
*   Confirm the **watermark** in `INTAKE.md` is advanced to this wave's newest ingested `createdAt`.
    *   **In a DECIDE pass, confirm the opposite — that it is UNCHANGED — and say so out loud** (`¶INV_ECHO_ON_SKIP`). Decide drained no new inbox signal, so there is nothing for the watermark to have moved past; an advanced watermark on a Decide pass is a **defect**, not a completed step, and it would silently swallow every comment that arrived while the pass was deciding. Record the value and that it did not move. (The per-thread `Slack read ts` **does** advance — that thread was genuinely read.)

## Critical Invariants (this skill)

*   **¶INV_QUICK_PASS_DECIDES_NOTHING**: `/intake` has **three reaches**, selected at Setup (`§CMD_SELECT_MODE`) along one axis — *how far does this pass go*. **Quick Pass ingests and decides nothing · Decide decides and ingests nothing · Full Wave does both.** They are the front half, the back half, and end to end; if that one line ever stops distinguishing them, one has stopped earning its place. **There is exactly ONE watermark and its meaning never changes** — *what have I read*. A Quick Pass and a Full Wave drain, so both advance it, because both genuinely read what they drained. **A Decide pass reads no new inbox signal, so it advances nothing** — that is the rule being obeyed, never an unfinished step, and a future editor who "fixes" it by adding the advance would silently skip every comment that arrived while the pass was deciding. (Decide's *per-thread* `Slack read ts` does advance: that thread was read. Same meaning, different scope.) **What still needs deciding is NOT tracked; it is derived**: it is the set of **unresolved inbox comment THREADS**, which `¶INV_RESOLVE_ON_DISPOSITION` already defines as *not yet dispositioned*. The undecided set, free, with no new field.
    *   **A thread is a ROOT comment, and only roots count** (Phase 1, pull (c)). Linear resolves threads, not comments — it refuses a child with *"Only top-level comments can be resolved"* — so every reply reads `resolvedAt: null` permanently, on live and dispositioned threads alike. Counting comment nodes instead of roots inflates the undecided set by however many replies the project has accumulated, and it inflates **monotonically**: each reply on a resolved thread makes the number worse, so the metric degrades fastest on exactly the projects that are working best. Measured where both were computed: **93 open threads reported as 195**.
    *   **So a Quick Pass resolves nothing, ever.** Leaving the thread open IS the handoff; resolving one it triaged would erase the only record that a decision is owed.
    *   **And so the deciding modes' scope widens** to include **every unresolved thread** (Phase 1, pull (c) — which needs a **full** fetch, since a `--since` delta cannot see a thread nothing has touched): a **Full Wave** takes *new since the watermark* **plus** the unresolved set; a **Decide** pass takes the unresolved set **alone**. **The halves are one change.** Without the widening, a Quick Pass is a black hole: it triages, the watermark passes the item, and nothing re-picks it.
    *   **Decide is the only mode that shrinks the open-thread count.** Quick Passes grow it by construction. That asymmetry is the cadence: run Quick daily, run Decide when the count says the decisions are owed — and let the count, not habit, recommend the mode at Setup.
    *   **The undecided set is not small, so taking it is a decision the operator makes** — gated by `backlogTaken` at Phase 2 (offered · taken · deferred · the ruling and who made it). Deferring is free, because a deferred thread stays in exactly the state it was already in; deferring **silently** is the failure. This matters most in Decide mode, where pull (c) *is* the entire worklist.
    *   **Only a pass that DECIDES announces.** A Quick Pass fires neither `§PASS_HEARTBEAT` event — no Decision Board, no Outcomes Board, no Project Update, no Slack post; a Full Wave and a Decide pass fire both. The heartbeat works by making a *skipped* pass legible through the **absence** of its announce, so a daily pass announcing daily converts the instrument into noise and destroys the one signal that says a real pass has slipped. **A Quick Pass is a working pass, not a checkpoint** — which is also why Phase 5's *"no wave closes without a checkpoint"* does not reach back to it. The rule is *announce iff you decided*, never *announce iff you were a Full Wave*.
    *   **A Quick Pass files nothing**, including items that look unambiguous and urgent. Filing outside a Full Wave is an **open proposal** (the discriminator that survived scrutiny is *cost asymmetry* — file where being wrong is cheap and being late is expensive — **not** obviousness), and it is not protocol until it is ruled on. Do not implement it, and do not pre-wire a flag implying it exists.
    *   **The phases a Quick Pass DOES run keep every gate and every proof field.** A shorter pass is not a cheaper one per item; `worklist` and `triageAccounting` are not relaxed because the pass is short. Its own stop is gated by `modeStop`, so a stop is distinguishable from a crash.
    *   **Reason**: the operator wanted a daily pass that processes and triages while postponing the deciding, and reached for "a separate waterline" — then rejected it as inelegant, correctly. The two markers would answer different questions (*read* vs *disposed*) and every pass would have to reconcile them; **reconciliation-by-reading is a failure mode this project keeps hitting**. The design's entire load is carried by noticing the second marker already exists and is already maintained: an open thread. **If a future change to this skill finds itself adding persisted state to track undecided work, it has gone wrong.**
*   **¶INV_DOCUMENTATION_IS_EVERGREEN**: Documentation — Notion pages, product explainers, anything a newcomer reads to understand the domain — carries **evergreen facts only**: the design of the model, the project's structure, how the pieces are meant to fit. It **never** carries point-in-time material: current measurements, a wave's findings, ticket or comment links, Project Updates, or the facts ledger. **The ledger is dated evidence; documentation is undated design.** **The link outlives the fact** — a page pointing at "the five open decisions" is wrong the week they are answered, and nobody returns to fix an explainer. **What a wave may change is narrow**: where it found the *design description itself* wrong or overstated. *"The file number is meant to group claims and is not yet populated"* is evergreen — design plus completion state, no number, no date, no link. *"We measured it empty on 13,494 rows"* is not. **Reason**: captured when a wave proposed enriching a product explainer with its three most legible findings plus links to the ledger and the open tickets — every one of which would have been stale within the month, on a page written for people who will never know to re-check it. The operator's ruling: *"pages are evergreen… documentation ONLY surfaces evergreen facts like design of a model, project structure, etc. never temporarily like current facts, comments, tickets."*
*   **¶INV_BOUNDARIES_ARE_WRITTEN_DOWN**: Every project has neighbours, and *"does this belong here?"* is re-derived for each one until somebody writes the answer down. The Inbox Handbook therefore carries a **`## Boundaries`** section: one entry per neighbouring project, each with the split **and a one-line test** that decides a borderline item. **Reason**: a wave decided the same workflow boundary three separate times in one pass, wrote it down zero times, and got it wrong once — proposing to route out an item the project's own Directions named as in-scope. The test matters more than the split: *"if the fix is a setting it is theirs; if the fix is what the data can express it is ours"* resolves cases the prose list does not enumerate. Boundaries are **method, so they live in the handbook, never in `## Directions`** (`¶INV_DESCRIPTION_SCHEMA_IS_A_WRITE_CONTRACT` — a steer says what we chase, a boundary says how to tell whose it is).
*   **¶INV_SUGGEST_BY_INTERROGATION**: Wherever a phase's output is a **suggestion about what the project should do** — what is in scope, what consolidates into what, what to pull first, what to chase next — it goes to the human through `§CMD_INTERROGATE`, not into an artifact the agent wrote alone. **The test is not "do I have an opinion" but "would I otherwise be deciding something that is theirs to decide."** An agent has opinions about everything; it is entitled to decide almost none of it.
    *   **Where it runs**: Setup (the domain goal) · Scope (items the Directions do not clearly place — ask, rather than silently marking them parked or already-clear) · Digest (the consolidation and root-cause conjecture — *"these five look like one problem; do they?"*) · Outcomes (the ranked pull-first read) · Discussion (steer and what to revisit) · Documentation (the Directions review). **Not** Ingest, Triage or Ticketing — those execute, and interrogating an execution step is friction with no decision behind it.
    *   **Scope each to ONE bounded round on a named topic**, never a depth-selected interrogation, and batch questions (`¶INV_BATCH_SIZE_4`). Six full interrogations turns a grooming pass into an interview, and an operator who is being interviewed stops reading the questions — which costs more than the silent decisions it was meant to prevent.
    *   **A declined suggestion is a recorded outcome**, not a failure: log it with the reason so the next wave does not re-propose it. The value is as much in the "no" as the "yes" — an un-recorded no gets re-litigated every wave, which is the same rot the inbox suffers from.
    *   **Reason**: the skill already forbids the agent from *executing* (`¶INV_INTAKE_DISPATCHES_NEVER_EXECUTES`) and from *filing* without confirm (`¶INV_TICKET_EARNED_BY_CONFIRM`), but said nothing about the layer between — the judgments that shape what gets filed at all. Those were being made silently in the working doc and surfacing only as a fait accompli at the confirm gate, where the human sees the conclusion and not the choice.
*   **¶INV_DIRECTIONS_ARE_ASKED_NOT_AUTHORED**: A wave **never writes the Directions on its own authority.** It proposes, cites the evidence, and asks (`§CMD_INTERROGATE`); it applies only what comes back, and lints before writing (`¶INV_DESCRIPTION_SCHEMA_IS_A_WRITE_CONTRACT`). **Reason**: a wave is simultaneously the best-informed party about whether the steer still fits and the worst-placed party to change it — it has spent a day inside one slice and will mistake what it just measured for what the project should want. The failure is not hypothetical in the other direction either: an obligation to keep a steer current with no phase that discharges it simply never happens, which is why the Documentation phase exists and why `directionsReviewed` fails a wave that **asked nothing** while passing a wave that asked and changed nothing.
*   **¶INV_UPDATE_READS_COLD**: The Project Update must be **completely readable by someone with no prior context** — a teammate who joined today, a customer-facing colleague, an executive skimming on a phone. It may not reference anything the reader cannot resolve from the Update itself. **The test is mechanical: read it as a person who was not in the wave. Every sentence you cannot follow is a defect.**
    *   **Forbidden outright**: internal artifact identifiers with no referent (*"report 12"*, *"the 05 §B finding"*, a session file path); **database table and column names** unless immediately translated into what a human sees on a screen; **wave-process meta** (how many items the last pass dispositioned, which tooling could not report what, watermarks, phase names); and **before/after corrections**, which are the worst offender because they are the most interesting to the author and the least legible to anyone else — *"peril disagreement 12.5% → 1.4%"* is noise to a reader who never saw the 12.5%.
    *   **Gather everything; present the five most interesting.** The Update's job is to *collect* the wave's facts — all of them. The **body** then carries the **five most interesting**, each standing alone with a number a person can picture and what it means for a customer. **The rest are not discarded** — they go into the linked **ledger document**, reached by one link. Five is a presentation choice about the body, never a cap on what the wave records.
    *   **The ledger is held to the SAME cold-read standard as the body** — it is the deep artifact, not the private one. A fact that is unreadable in the Update is unreadable in the ledger; rewriting `location_key='default' on 38,197 of 38,197 rows` into plain terms is required in both places.
    *   **And every fact in the ledger carries a resolvable reference to where it came from** — a triage report (attached, so it opens), the ticket that now owns it, the origin comment (`§FMT_TICKET_COMMENT_LINK`), or the app URL that shows it on screen. **A bare internal code is not a reference** (`(07 §C)`, `rpt 12`) — it names a source only the author can reach. **Nor is deleting the citation the fix**: a fact with no provenance is a fact nobody can check or re-derive, which is how a wrong number survives three waves. Where a source genuinely cannot be linked yet, say so in those words — *"measured this wave; report not yet published"* — so the gap is visible rather than implied.
    *   **A fact qualifies only if it survives being read alone.** *"$4.43M of coverage disappeared from one claim because we can only store one figure per type"* qualifies. *"`location_key='default'` on 38,197 of 38,197 rows"* does not — same finding, unreadable form. Prefer the customer's question over the schema's vocabulary: *"why are only some of my sub-limits listed?"* beats *"the closed COVERAGE_FIELD_MAP"*.
    *   **Reason, captured live.** A wave posted an Update whose FIRST section was four withdrawn numbers — the material the author found most interesting and a cold reader cannot use at all — followed by `location_key`, `intake_status`, "twin-import contamination", "M7 cutover", and two paragraphs of intake-process scorekeeping. The operator's ruling: *"only show top-5 facts that people CAN understand out of context… it cant reference anything outside that people dont understand."* The failure mode is specific and recurring: **an Update drifts toward being a report to the author's peers about the investigation, when its job is to tell everyone else what is true and what needs deciding.**
*   **¶INV_REFETCH_BEFORE_WRITING**: A phase that WRITES to the tracker opens by re-fetching the whole project, and builds its action list from that payload — never from the working doc. **Full fetch, no `--since`**: a delta returns only what changed, and the items most needing attention are the ones nothing has touched, which a delta cannot see by construction. **Reason, measured**: a wave built its Outcomes action list from `INTAKE.md`'s item inventory and a re-fetch immediately surfaced **two comments the inventory had never listed** — because an inventory records what you *handled*, so it can only ever contain what you already knew. It is not a census. The same fetch answered a question that had been unanswerable all wave (how many threads are resolved), and revealed the wave had dispositioned 16 signals and closed **zero**. Deciding and writing are hours apart in a real wave; `§INV_POINT_IN_TIME_CHECKS_EXPIRE` says the check must re-run at the point of USE, and a disposition is a visible action on someone else's work — the most expensive place to act on a stale read.
*   **¶INV_CITE_DONT_SUMMARIZE**: A scope, routing or disposition call quotes its source **verbatim from the current payload** — never a summary of it, and never a quote carried forward from an earlier phase. Quoting requires reading; that is the whole mechanism, and it is why this is a format rule rather than an exhortation. **A citation is itself a point-in-time artifact**: carried across phases it ages silently, which is why this ships as one mechanism with `¶INV_REFETCH_BEFORE_WRITING` rather than standing alone. If you cannot paste the sentence that justifies the call, you have not established it — say so and leave the item, rather than acting on a remembered shape. **Reason, measured**: in one wave an agent asserted three separate things from its own summary lines written hours earlier — a ticket's placement, a set of file edits it had logged as landed, and a routing decision for three items — and was wrong all three times, caught by the operator each time and never by itself. The routing case is the sharpest: the comment being routed out of the project contained a heading reading *"Why it belongs to this project and not to extraction"*, and the project's own Directions named its subject as in-scope. Both checks were seconds; neither was run, because a summary the agent had authored felt like evidence (`§INV_CONFIDENCE_FROM_THE_CHECK`).
*   **¶INV_UNAVAILABLE_IS_A_CLAIM**: **"That capability isn't available" is a claim and needs evidence like any other negative.** A diagnostic signal is not a capability verdict: an `engine env doctor` WARN, an HTTP 401, an unset env var, a missing config — each is a hint to *try the thing*, never proof you cannot. **To rule an angle or a tool out, name the check you RAN, not the signal you SAW.** `§INV_CONFIDENCE_FROM_THE_CHECK` says this about findings; it applies identically to capabilities, and the failure is easier here because giving up feels like prudence. **Reason, measured**: one wave declared three capabilities unavailable in ninety minutes and was wrong all three times — a `curl` 401 on a Linear asset became *"sub-agents cannot read attachments"* (the MCP reads them fine), and a doctor WARN on `AWS_PROFILE` became *"no database"* (AWS was authenticated as an IAM user; the tunnel opened in 20 seconds). **The cost was not lost time but a narrowed evidence base**: both triangulation runs fell back to the same two angles, and the wave then reported low confidence on exactly the question the excluded angle would have settled. Worse, it compounds — a false constraint written into a log becomes a "known limitation" the next wave inherits without re-testing, so record the *check*, and re-run it rather than citing it.
*   **¶INV_REPLIES_ARE_SIGNAL**: An origin comment's **replies are part of the signal, not commentary on it.** Prior triage results, corrections, and the reporter's own follow-ups live there — often the most-processed evidence available on the item. Any handoff that passes "the origin signal" passes **body plus replies**; passing the body alone silently withholds the best material while appearing complete. **Reason, measured**: a wave filed a research ticket asserting a path had never been traced, **four days after a reply on that exact thread stated it had been traced and gave the answer** — and the wave's own tooling output had recorded the reply count. The body was read; the thread was not. Corollary for the reader as much as the dispatcher: a resolved thread's replies are where a disposition's reasoning lives, so "I read the comment" is not "I read the thread."
*   **¶INV_ANSWERED_IS_NOT_UNANSWERED**: **Before triaging any item, establish whether it has already been answered.** An item whose thread carries a prior check with a definitive result is marked `already-answered` (Phase 2) and goes to **disposition, not to the fan-out** — what it is owed is a decision, not a fifth measurement. The `worklist` proof field carries `repliesRead` on **every** entry, whatever the marker, because *"I did not look"* and *"there was nothing there"* are exactly the two states this rule exists to tell apart, and they are indistinguishable in a log that records neither.
    *   **A thin-looking body is not evidence of an unanswered item.** It is the normal shape of an item whose answer is three replies down — which is why the check is on the **thread** and runs *before* the other markers are considered, rather than as a tie-break among them.
    *   **This is NOT a licence to skip triage** (`¶INV_ENRICHMENT_IS_EVIDENCE_NOT_READING` still governs). It requires a prior **check** — a count, a query, a repro, a document opened — recorded with its result and reachable by deep link. A prior agent *read* that restated the tracker at length answers nothing, and the item stays `needs-triage`. The two markers pull in opposite directions on purpose: one stops a wave re-measuring settled work, the other stops it waving through unmeasured work, and an item that satisfies neither test is simply `needs-triage`.
    *   **Definitive means the question asked is closed**, not that the prior triage was long. A measurement that closed breadth but left cause open is `already-answered` on breadth and `needs-triage` on cause — split it rather than rounding to either.
    *   **Reason, measured.** One project's deductible cluster reached its **fourth independent measurement**, each concluding *"wiring, not schema"*, each left ungraduated — while the customer's own original report stayed open, pointed at the wrong pipeline, for five months. The sharpest instance: a comment measured a precedence inversion at **701 pairs across 280 claims** and recommended filing it; **nobody filed it, and the next wave re-measured the same defect from scratch one day later.** The waste is the visible half. The expensive half is that **an item answered four times still looks unanswered to the fifth wave**, so the count of open work never falls and the project reads as evidence-rich and decision-poor when it is really just re-measuring. **A wave that cannot tell answered from unanswered will always choose to measure**, because measuring is the thing it knows how to do.
*   **¶INV_ANGLES_MUST_FAIL_DIFFERENTLY**: Any item that will produce a ticket or a disposition is triaged twice in parallel from **different leading questions and different starting points** (DB · UI · code · artifact · history) — not two runs of the same method. **An angle is a lead, never a fence: every run may use every tool**, and one that needs another instrument to settle its own claim uses it. Fencing runs to one evidence base manufactures the very "not enough evidence" it was meant to detect. Single-angle output is a **hypothesis** and must be labelled one; it may not be cited as fact in a ticket, a disposition or a board. **Disagreement between angles is the product, not a failure** — the report carries a required "Where the angles disagreed" section. **Cost, measured**: ~2× a single triage (106k + 132k tokens on the first real run) — the two angles come out roughly equal. An earlier version of this invariant claimed ~1.2× on the theory that the second angle is cheap; that was reasoning presented as a figure and the first run refuted it. Cheapness still applies *within* an angle, but it does not make the pair cheap. **Reason, measured**: a corpus contamination distorting **88.6% of all claims** — two orgs that were one tenant imported twice — was invisible to every DB query ever run against it, because it was a property of the DATA, not of the query; every query inherited it identically. That is the class replication cannot catch. Conversely, the two strongest findings of that wave both came from angle-agreement (a DOM probe reading `laneCount = 25` alongside a `UNIQUE` constraint in the schema) and from angle-*disagreement* (a banner counting one thing while the queue required another — the disagreement WAS the defect). The counter-example is a diagnosis built from stored rows alone that was wrong for three of four symptoms.
*   **¶INV_PROVENANCE_IS_TWO_WAY**: A graduated ticket carries a `## Origin` section deep-linking back to the comment(s) it came from (`§FMT_TICKET_COMMENT_LINK`), **and** the origin comment carries the `filed as FIN-XXXX` reply. Both, or neither counts. **Reason**: the reply direction alone leaves a ticket whose origin is unreachable, so nobody can check it against what was actually reported — and the next wave, finding the signal unlinked, re-triages it into a second ticket. One-way provenance is a mechanism by which "the same-y issues" reproduce. Captured from a wave that applied the deep-link format correctly in the reply direction and, minutes later, wrote bare 8-hex ids into the ticket bodies; two of its tickets carried no origin at all. **Mechanical check after filing**: grep the new ticket body for a backticked 8-hex id — if one is there, the link is missing.
*   **¶INV_INTAKE_DISPATCHES_NEVER_EXECUTES**: /intake organizes, triages, and hands off context-rich briefs; it never does the downstream research/build/fix. "Dispatch" means posting a self-contained handoff (prompt in `builds/`, attached), not a bare tag.
*   **¶INV_WAVE_BOARDS_ARE_INTAKE_NATIVE**: The wave renders two intake-owned boards on a timeline — the **Decision Board** (Phase 5, interactive: the decisions to make) and the **Outcomes Board** (Phase 9 Final Sync, static: the actions-taken record). Both REUSE `/prove`'s render discipline (real assets, self-contained/CSP-safe/theme-aware, scope block, integrity pass) + `publish-s3.sh` delivery, but are NOT `/prove` invocations — they are multi-item, and the Decision Board is interactive. `/prove` stays single-thesis/static. Rendered by a dispatched subagent from the board handoff templates (`assets/TEMPLATE_DECISION_BOARD_PROMPT.md`, `assets/TEMPLATE_OUTCOMES_BOARD_PROMPT.md`).
*   **¶INV_BOARD_TRUSTS_ORCHESTRATOR_CURATION**: A board renders the orchestrator-surfaced questions / options / evidence faithfully; the render subagent never re-derives whether they are the right questions (that is the wave's job, taken as given — the `/prove` trust-upstream spine, mapped to curation). Its only verification is presentational (`¶INV_PROVE_FAITHFUL_PRESENTATION`): real assets, faithful captions, honest provenance.
*   **¶INV_STEERING_NOT_SOLUTIONS**: Triage and the wave boards offer process-*steering* options to react to — a legitimacy/confidence read + what-to-measure/triage-next — never manufactured solutions. This preserves the human's creative leap (`¶INV_RESEARCH_MEMORY`): options that shift the process in a direction, non-binding, not an answer the human must produce or accept. Triage stays read-only and light; the orchestrator polishes triage's *suggested* options into the Decision Board's multi-select widgets.
*   **¶INV_BOARD_HANDOFF_IS_FIXED_PRESENTATION_IS_FREE**: Board repeatability lives in the HANDOFF, not the output HTML. The handoff template pins WHAT every wave surfaces (ranked decisions + the number behind each, per-item options/questions, consolidation ops + reasoning, adopt/cancel items, evidence + provenance) AND the three mechanical contracts that cannot drift (reference the shared widget kit at its versioned same-origin address; emit the fixed payload schema; render panel marks in the markup the kit reads). HOW it is presented — layout, visual device, emphasis — is the render agent's creative call (backed by `artifact-design`). Same handoff in → same coverage + widget behavior + payload out; the presentation is free to be its best each wave.
*   **¶INV_HANDOFF_STRUCTURED_NOT_LOSSY**: The board handoff is a per-finding envelope (fixed fields → consistent surfacing) whose content stays RICH, always carries POINTERS to the full source (the triage report + origin comment + entity links + working doc), and has an open overflow slot so a fact is never dropped for lack of a field. The orchestrator organizes + points; it never compresses facts away, and the render agent presents from the full sources — not just the envelope. (The RETURN payload, by contrast, is deliberately concise — answers-only — so its rigidity loses nothing.)
*   **¶INV_PANEL_VOTES_ARE_A_READ_NOT_A_VERDICT**: A wave MAY convene a `/council` panel over its decision list and render each expert's pick on the option itself, so a teammate chooses with the panel's read in view instead of cold. Three things hold it in place. **It reacts, never authors** (`¶INV_STEERING_NOT_SOLUTIONS`) — the option set stays the orchestrator's curation, and an expert's `alternative` returns to the orchestrator as a signal the options may be wrong, never as a choice on the board. **It is distinguishable everywhere, structurally** — every answer in the payload carries a required `actor.kind`, and on the board the classes differ by *form* (icon for an expert, initials for a person), never by shade, because a wave's contributor instrument counts distinct *human* contributors and a machine absorbed into that count disables the alarm that detects the system dying. **Its reasoning is reachable** — every mark carries the expert's own words, its self-reported 1–5 conviction, and whether it declared the grounds too thin to rule, reachable by hover, keyboard focus and tap alike; a mark whose reasoning cannot be reached is a judgement delivered at a confirm gate with its audit trail hidden, which is worse than showing no panel at all. Absent a panel, everything renders and ingests exactly as before; an orchestrator NEVER writes the votes itself.
*   **¶INV_BOARD_PAYLOAD_IS_ADVISORY**: Pasted board payloads (`assets/PAYLOAD_SCHEMA.md`) are non-binding leanings + a vote tally; no board answer auto-acts. A panel vote is one layer further from authority than a teammate's, and nothing in how it is rendered or tallied may imply otherwise. Every disposition / consolidation / adopt / cancel still passes the chat human-confirm (`¶INV_TICKET_EARNED_BY_CONFIRM`). The Decision Board COMPLEMENTS the chat confirm; it never replaces it.
*   **¶INV_ADOPT_OR_CANCEL_STRAYS**: A ticket created directly into a milestone (non-`Inboxes`, no wave-provenance marker) is swept into the wave (Phase 1), triaged, then either ADOPTED (moved to the correct milestone) or CANCELLED (reason → `Cancelled`, the *why* recorded), human-confirm each. It already exists — so it is never a `/ticket` graduation, never left unsorted, and never silently deleted. Detection is conservative (a legitimately-parked or cross-project ticket is not a stray).
*   **¶INV_NO_RUSH_ITEMS_TO_CLOSURE**: The guarantee is item-level — an item is never force-promoted just because a wave is closing; unripe items marinate in Linear across waves. The **session** is a bounded wave that ends cleanly (durability is in Linear, not the session). Supersedes the former no-rush-to-closure (which conflated item-ripeness with session-immortality).
*   **¶INV_RELATED_SEARCH_IS_UNCONDITIONAL**: The related-tickets search runs on every item in the wave, whatever its worklist marker. `already-clear` and `chat-drop` exempt an item from the triage **fan-out**, never from this search. It is the only triage step that is project- and domain-independent, it is the cheapest (tracker search — no DB, no tunnel, no subagent), and it is the only one whose omission is unrecoverable: an item that graduates without it carries no record of what wasn't looked for. Record the result per item — including "nothing found" — so the search is auditable rather than assumed. Captured from a real wave that skipped it on 11 of 15 items and filed three tickets missing five relevant existing ones, including a cancelled precedent that was the strongest available argument for one of them.
*   **¶INV_GRADUATION_VIA_TICKET**: A wave never hand-writes a ticket body. Graduation goes through **`/ticket`** with a caller-pinned placement (project + work-type milestone + new-issue-never-sub-issue); corrections to an already-filed ticket go through **`/snapshot`**'s description-drift flow. /intake keeps only what those skills don't know about: the recorded ripeness checklist, the priority from the wave's ranking, the idempotent pre-write key, and the `filed as FIN-XXX` origin reply. **Reason**: `/ticket` already holds the drafting discipline a wave needs and would otherwise reinvent worse — premise-not-algorithm, plain-terms opener, non-goals, acceptance signals, a spike escape-hatch for research with no honest acceptance criteria, and conservative single-ticket-by-default decomposition. `/snapshot` already holds the correction discipline — evergreen body, append-only `## Change history`, re-read before a full-field replace. Captured from a wave that hand-filed six tickets: they read as essays comprehensible only to whoever sat through the source review, two of the six should never have been tickets at all, and four descriptions were freehand-overwritten with no history line and no re-read guard. Every one of those failures is something the two existing skills prevent by construction.
*   **¶INV_TRIAGE_BEFORE_TICKET**: Not-ready signals get light **triage** in-thread (orchestrator-dispatched sub-agents gather detail / repro / related-tickets) before they earn a ticket — not a premature ticket. Triage ≠ research: triage makes a signal ticketable; deep research runs on a graduated `Needs research` ticket.
*   **¶INV_CHANNEL_EVIDENCE_RIDES_THE_COMMENT**: On an **inbox channel ticket**, every file — a drop's source document, a triage report, a handoff prompt, a screenshot — attaches at **comment level**: `prepare_attachment_upload(issue)` → PUT the bytes → **embed the returned `assetUrl` in the comment markdown**. Never `create_attachment_from_upload`, which creates a *ticket*-level attachment.
    *   **Every uploaded file MUST appear as a real, clickable markdown link — `[📄 <filename>](<assetUrl>)` — in the body of the comment it belongs to.** Naming a file in prose is **not** linking it. A line like *"📎 Attachments — the full report and a visual proof"* with no URL behind it is the defect, not the fix: the reader has nothing to click, and an uploaded asset that no comment links to is unreachable in the Linear UI entirely. **The test is mechanical: for each file you uploaded, does an `assetUrl` you received appear inside a markdown link in the posted body? If not, the post is incomplete.** Reference-by-title and reference-by-description both fail this test. **The rule is a property of the TARGET, not of the artifact**: a channel is a frozen collector that will hold hundreds of comments, so a ticket-level attachment is severed from its originating drop the moment there are two of them. The inverse genuinely holds on a **worked** ticket — `/snapshot`'s closing debrief, `/ticket`'s evidence — where the attachment belongs to the ticket as a whole and `create_attachment_from_upload` is correct. So this never reads as "always the comment" globally; it reads as *frozen collector → comment, worked ticket → issue*. Corollary, inherited from the handbook's dropper rule and binding on skills too: **if you are describing something you read in a file, attach that file** — a restructured or condensed version in the body is fine *alongside* the source, never *instead of* it. **Reason**: captured live. `/inbox-post` step 4 prescribed `create_attachment_from_upload` plus *"reference that attachment by title in the comment body"* while `/intake` Phase 3 forbade exactly that call for exactly this reason — the same mechanic specified in two skills with opposite answers, and **neither stated why**. An agent posting a drop followed the wrong one and defended it as protocol; the true driver was that embedding meant re-sending an 11.3K-char comment body it had already declined to re-send. Provenance-by-title is the specific defect: it works while there is one attachment and degrades **silently**, never loudly. Also note there is no comment-attachment API to look for — embedding the `assetUrl` **is** what the Linear UI's in-comment upload does.
*   **¶INV_EVERY_PHASE_DECLARES_ITS_BOUNDARY**: Every work phase (1 through 8) declares an **OWNS / DEFERS** line, and every boundary between them is offered to the operator through `§ASK_INTAKE_PHASE_HANDOFF`, filled with what the next phase will actually do, what it costs, and what it will not do. **A wave never crosses a phase boundary on its own judgement.** The engine's generic gate (`§ASK_PHASE_GATE`) does not satisfy this: it offers "next phase" without naming that phase's work or its price, and an operator shown that has not been asked anything.
    *   **An operator asking for a later phase's work is a hand-off request arriving early — not off-course, and not a refusal case.** *"Just triage them"* at Phase 2, *"file these"* before Phase 6, *"show me the board"* before Phase 5. **Silent compliance and a flat decline are both wrong.** The required response is a **named deferral**: say which phase owns it, say in one clause why it waits, say what still has to finish here, and offer the hand-off. *"Triage is Phase 3 — it needs the worklist marked first so we don't fan out twice on the same item. That's at 12 of 19; want to close Phase 2 and go?"* Then run `§ASK_INTAKE_PHASE_HANDOFF`. **Do not route this through `§CMD_REFUSE_OFF_COURSE`** — that command is for work belonging to a *different skill* (executing a fix, writing code), and using it here tells the operator that a perfectly reasonable request was out of bounds.
    *   **`¶INV_DISPOSITIONS_RESOLVE_AT_OUTCOMES` is this invariant's special case**, with its own two exceptions. Where both speak to the same ask, the disposition rule is the more specific and wins.
    *   **Reason**: measured on this file. Phase 3 was the ONLY phase carrying an authored transition (the mode gate, backed by `modeStop`) — and it is the only boundary an operator never had to ask about. Five boundaries (1→2, 2→3, 4→5, 6→7, 8→9) had no authored transition at all and fell through to a generic six-option menu, so the wave's most expensive step — a triage fan-out priced at ~2 sub-agents per item — sat behind the same unlabelled "next phase" button as a free one. **A protocol that prices nothing at its gates has gates that mean nothing.**
*   **¶INV_DISPOSITIONS_RESOLVE_AT_OUTCOMES**: A **disposition** — route · move between projects · split · merge · supersede · adopt · cancel · graduate — resolves at **Phase 5 (Outcomes), after triage has produced evidence**, and never earlier. **Including when the user asks for it earlier.** A request at Setup ("move these tickets to project X") is an *input to the wave* — it sets the wave's goal, it does not authorize skipping to the answer (`¶INV_PROTOCOL_IS_TASK`: a user request is an input to the protocol, not a replacement for it). The correct reply is to record it as the goal and name **when** it will be decided: *"that's a Phase-5 disposition — these get triaged first and routed at Outcomes with the evidence."* Earlier phases SURFACE and FRAME dispositions; they never resolve one. **Two exceptions, or the rule becomes a trap**: a blocking defect in the wave's own machinery (a channel that fell out of the inbox milestone and is breaking the drain), and anything that genuinely expires before Outcomes (an in-review PR about to merge) — both resolvable inline, both recorded as exceptions taken. **Reason**: captured from a wave that resolved three separate dispositions before Phase 5 — cross-project routing at Phase 2, board decisions at Phase 2, and the announce fired after publishing rather than before — and was caught by the operator all three times, never by itself. The routing was pulled forward by a direct user ask at Setup, which is exactly where deferring feels like unhelpfulness; the six tickets were then routed on **unmeasured reporter text**, and the one that later got an actual query **reversed its verdict**. Dispositions are where a user's ask is hardest to defer and where acting early costs the most, because they are visible actions on other people's work. **Intra-phase ordering (the ordering this invariant was silent on).** Resolving dispositions *at* Outcomes is necessary but not sufficient — *within* Outcomes the stages run in a fixed order and each is a **gate, not a trailing bullet**: **rank → (optionally) convene the panel and record it (`panelRun`) → publish the Decision Board and capture its handles (`decisionBoard`) → gate each disposition (`dispositions`) → resolve the threads that left the inbox → sync, then fire the announce and capture its handles (`announce`).** The panel runs before the board because its marks are stamped onto the board the render produces; a board published before an offered panel could react is the same class of intra-phase ordering failure as an announce fired before the board exists. A board published without its announce handle, or an announce fired *before* the board exists (event 1 late — the failure the operator caught three times), is the intra-phase ordering violation this clause names. Everything here rests on Phase 3 having already **posted** its triage evidence resolvably (`triageAccounting`) — a disposition stands on a reachable comment, never a report on the operator's disk. Stages, not bullets.
*   **¶INV_ENRICHMENT_IS_EVIDENCE_NOT_READING**: Enrichment means **a fact that did not exist before triage ran** — a count, a repro, a document opened, a query executed, an external system consulted. A prior *read* of an item — a subagent that fetched ticket bodies, comments, relations and states — is **not** enrichment and never satisfies `already-clear`. **The test: could this output have been produced without leaving the tracker? Then it is a read, not a triage.** `already-clear` is a test on the REPORTER's text (org + entity id + repro), never on how much work an agent has already done on the item. **Reason**: captured from a wave that dispatched a thorough 12-ticket read subagent and then logged *"every item arrived enriched"*, skipping the triage fan-out entirely. The read had run zero queries, opened zero documents, and attempted zero repros — its own report said it *"did not fetch the two Linear Project descriptions to verify"* — but it arrived as a long, confident, well-structured artifact, which is what made it pass as evidence. This is the hardest of the `already-clear` misuses to catch precisely because, unlike "I already know what this says" and "no DB lookup would help", it presents as evidence-shaped work product rather than as a hunch.
*   **¶INV_CONFIDENCE_FROM_THE_CHECK**: Confidence in a signal comes from **the check that was performed against it**, never from **who authored it** or from how well-formed it reads. Authorship is not evidence: a report you wrote yourself an hour ago is exactly as unverified as a stranger's, and *feeling* certain about it is a property of your memory, not of the claim. The same applies to shape — a long, confident, well-structured artifact is not thereby checked (`¶INV_ENRICHMENT_IS_EVIDENCE_NOT_READING` is the same rule applied to sub-agent output). So **when the person triaging is the person who wrote the report, that is a reason to check harder, not a licence to skip**, and any `already-clear` call must name the check that justifies it. Corollary for negative results: *"X does not exist"* is only as strong as the search behind it — say what you searched, not just what you failed to find. **Reason**: a wave skipped investigation on eleven of fifteen items because the operator had authored them an hour earlier and trusted memory over the record, producing a false statement in a filed ticket and five relevant existing tickets nobody had looked for. The following wave, running the check, **refuted two of its own reports** — including a detailed, internally consistent claim that a credential did not exist (it did, under a transposed name, and the false belief had already been recorded four times).
*   **¶INV_INBOX_NOT_TICKETS**: Inbox items keep their own lightweight format (the channel reporter templates) — do not reimplement tickets inside comment threads. Sub-issues coworkers create under a frozen inbox channel ticket are parked to `Uncategorized` (confirm each), keeping `Inboxes` frozen-collectors-only.
*   **¶INV_TWO_LEVEL_PRIORITY**: Priority operates at two levels — intake-internal (which signals a wave triages first) and output (the durable ranking that guides doers: the Linear priority field on tickets + a ranked "pull first, why, with proofs" narrative in the Project Update). Same impact model (consolidation breadth + non-self corroboration + blast-radius).
*   **¶INV_LINEAR_IS_TRUTH**: Linear tickets are the source of truth; humans acting in Linear are authoritative. The doc is a working projection synced one-way to Linear, never overwriting human-owned state.
*   **¶INV_INTAKE_IS_BOTTOM_UP**: /intake accretes bottom-up with no goal yet (vs /direct's top-down vision from a known goal).
*   **¶INV_PROJECT_HAS_A_DOMAIN_GOAL**: The Linear Project is a real initiative with a specific domain goal, interrogated at Setup — never assumed from a name, and never "the inbox" itself.
*   **¶INV_INBOX_STATUS_NOT_BACKLOG**: Every ticket under the `Inboxes` milestone carries the `Inboxes` **issue status**. Set it at creation — `save_issue(state: "Inboxes")` — for the channels and for anything parked there to gather input. Leaving it on the team's default `Backlog` puts a collector in the same view as work someone is about to pick up, which is the confusion the status exists to end, and no later step re-checks it. The status is type `backlog`, so ranking, cycle exclusion and every reader keying on the status *type* are unaffected. Repairing a project that predates this: find them with the filter `projectMilestone.name == "Inboxes" AND state.type == "backlog"` — that catches channels the registry has never heard of — and note that Linear's `issueBatchUpdate` rejects more than 50 ids at once with a validation error that lists every id and looks like a permissions failure.

*   **¶INV_INBOX_IS_TICKETS**: The feedback inbox is one or more *typed* tickets under the `Inboxes` milestone — each a comment firehose for a kind of feedback, chosen contextually per project (default: Observed problems / Identified shortcomings / Feature requirements / Potential solutions / Feedback & Transcripts / Researches & Fixtures / Priorities & Deadlines / Documentation / Inquiries). Each channel's description carries **only** that channel's `## Directions` + a one-line what-belongs-here + a link to the project's Inbox Handbook, where the shared machinery lives once (`¶INV_CHANNEL_MACHINERY_IN_ONE_DOC`). The Project is not the inbox.
*   **¶INV_CONTINUOUS_CONSOLIDATION**: Always on the lookout to **merge / dedup / supersede / connect** tickets, maintaining a constantly-cleaned state (never a dumping ground). Cross-cutting symptoms consolidate into a single higher-leverage parent ("solution Z") — fix the path, not each symptom; consolidation breadth feeds the ranking. Destructive ops require human confirm.
*   **¶INV_TEAMMATE_FACING_LINEAR**: Linear content teammates read (Project + milestone descriptions, ticket bodies, inbox replies) stays human/domain-facing — no engine/skill jargon. The engine vocabulary lives in the working doc.
*   **¶INV_VISION_IN_COMPANION_DOC**: The vision / process / philosophy lives in a teammate-facing **companion document** on the Project — **not** the lean Project description, not duplicated in the skill. **There is exactly ONE companion document, and it is the Inbox Handbook** (`¶INV_CHANNEL_MACHINERY_IN_ONE_DOC`). The separate "Vision & Process" doc this invariant originally named is **retired**: it predated the handbook by a day, was never edited after creation, and split the same subject across two documents with nothing stating which owned what — so the Project description silently re-absorbed both halves. Do not create a second companion document. If a project still has a live "Vision & Process" doc, fold its unique content (the milestone lifecycle, the constantly-cleaned state) into the handbook and retire it, one project at a time.
*   **¶INV_STRUCTURE_CATALOG_IS_LOCAL**: The canonical structure catalog + wave operating guide lives in `INTAKE_SYSTEM.md` next to the skill, read on every invocation.
*   **¶INV_NOTION_KNOWLEDGE_BASE**: The skill links, writes, and maintains related non-technical Notion pages as a user knowledge base. At project creation, ask whether one exists to observe/manage or should be created; link page + subpages from the Project description; keep it current.
*   **¶INV_TICKET_EARNED_BY_CONFIRM**: No Linear ticket is created (and no destructive consolidation op / sub-issue reparent) without an explicit per-item human confirm.
*   **¶INV_RIPENESS_IS_A_RECORDED_CHECKLIST**: Ripeness is a recorded binary checklist (crisp problem · defined next-action · brief type · enough non-self corroboration), not a vibe. The four are the *default* — a project's Directions may modify them (`¶INV_DIRECTIONS_IN_DESCRIPTIONS`); record the checklist **as applied**, naming which items came from Directions.
*   **¶INV_DIRECTIONS_IN_DESCRIPTIONS**: A project's steer — what it's chasing now, what counts as ripe here, what triage should chase or skip — lives in a `## Directions` section of the **inbox channel ticket descriptions** (per-channel) and optionally the **Project description** (project-wide). Not in a separate doc: the steer belongs where the drop happens, a human edits it in place, and the skill already holds every mechanic so Directions need only say *what to achieve*. Precedence **channel > project > skill default**; absent = defaults, never fail, never invent one. They are loaded at Setup, applied to the Phase-2 triage call (citing the line), passed **verbatim into every triage handoff prompt** (a sub-agent can't read the project — an unpassed steer is a lost steer), and may modify the ripeness checklist. They steer judgment; they never grant authority — no Direction removes a human confirm (`¶INV_TICKET_EARNED_BY_CONFIRM`).
*   **¶INV_TICKETING_STRATEGY_IN_HANDBOOK**: Every intake project's **Inbox Handbook** carries a `## Ticketing Strategy` section — how much ticketing that project wants, as three independently-dialable bullets (**Volume** how many we want at all · **Size** how big one should be · **Substance** what makes one worth existing). **It lived on the Project description until five projects proved it was machinery**: the canonical default shipped byte-identical to all five and not one operator ever edited a bullet, so it behaved as a global default costing five copies rather than the per-project knob it was designed to be — while its actual consumer, the triage handoff prompt, pastes from the handbook. Moving it cost nothing (the handbook is per-project, human-editable in place, and already fetched once at Setup) and put it beside the recipe it is read with. It is deliberately **not** a variant of `¶INV_DIRECTIONS_IN_DESCRIPTIONS`: it is **mandatory**, it is **one per project** with no channel override and no precedence chain (how many tickets a project wants is a property of the project, not of the firehose an item arrived through), and **absence is loud** — warn once per wave, proceed on the catalog's canonical default, and record *"default applied"*; never a silent fallback. It gates a different axis from ripeness: ripeness asks *is this well-formed enough to be a ticket*, this asks *should it be its OWN ticket* — so it is a **distinct gate at Outcomes** run after ripeness passes, never a fifth ripeness criterion. Its outcomes are own-ticket / fold-into-a-parent / keep-marinating — **never discard**. Loaded at Setup, held in view during Digest's consolidation, carried **verbatim into every triage handoff prompt in its own block** (the sub-agent's "ripe → which milestone" recommendation is a graduation-volume call made by an agent that cannot read the project), and **recorded as applied** naming which bullet decided it. A changed Direction re-opens pending judgment; a changed Ticketing Strategy re-opens **already-filed tickets** — say so and re-examine recent graduations. It steers judgment; it never removes the human confirm (`¶INV_TICKET_EARNED_BY_CONFIRM`). The canonical default text, the handbook's section list, and the Project-description section schema all live in `INTAKE_SYSTEM.md`. On a project that predates the move, read it off the Project description this wave, log the old location, and offer to relocate it at Outcomes.
*   **¶INV_CHANNEL_MACHINERY_IN_ONE_DOC**: **No Linear description at any tier carries intake machinery.** A *channel* description carries only its own steer — a one-line *what belongs here*, its `## Directions`, and a link. A *Project* description carries only product care — see `INTAKE_SYSTEM.md` § *The Project description*. All **shared machinery** (📋 report template · what-happens-next incl. the draft/correction affordance · the other-intake-inboxes list · the lifecycle · cadence + pass heartbeat · `## Data handling` · `## Ticketing Strategy` · `## Boundaries`) lives **once per project, in the Inbox Handbook document** — a Linear *Document*, not an attachment, because a Document is human-editable in place, linkable, and agent-readable via `get_document`. The handbook also carries **`## What triage will chase`, which is written per project and is NEVER generic** — it keeps a shared Identify → Reproduce → Relate → Report skeleton but names this project's own tools (Temporal workflow history for Differ; the staging DB for Email Classification). That section is the reason the handbook is per-project rather than per-team: a team-level copy has no home in the Linear UI, and one flattened recipe helps nobody. **Each project's handbook is complete and self-contained — there is no parent document and no inheritance**, because prose cannot express or display a merge, and an agent reconciling two documents by reading is a worse failure mode than the copy-drift it would replace. Setup loads it once and holds it; Triage pastes the relevant part into each handoff (a sub-agent cannot read the project); `/inbox-post` and `/inbox-triage` read it when standalone. **Never paste machinery inline on a channel**, and never reconstruct the handbook from a channel description. Rationale is measured, not theoretical: propagating one sentence across the channel set cost **35 writes**, and the duplicated channel list had already drifted (`/inbox-post` documented "6 channels" while 7 existed) — duplication does not merely cost effort, it silently goes stale. Accepted tradeoff: a dropper sees a pointer where a template used to be — right for machinery, wrong for steer, which is where the split runs. **The rule is about descriptions, not about channels**: it was first written for the channel tier and the project tier went on carrying `## Other intake inboxes`, `## Ticketing Strategy` and cadence boilerplate for weeks afterwards, because nobody re-read a channel rule as a general one. Both tiers thin the same way, for the same reason.
*   **¶INV_DESCRIPTION_SCHEMA_IS_A_WRITE_CONTRACT**: The Project-description section schema in `INTAKE_SYSTEM.md` (§ *The Project description*) governs **writes**, not just the bootstrap. A wave syncing state to Linear may refresh only the sections that schema names — in practice `## Directions`, and `## Stakeholders` when the people-facts actually changed — and **may never add a section the schema does not name**. Anything else a wave wants to say goes into the **Project Update** (pass narration, the ranked read, findings) or the **Inbox Handbook** (standing rules, machinery, triage recipe). **Reason, measured**: the two sync steps said only *"refresh the Project description with the current cross-scope understanding"*, with nothing constraining what could be added — so one project accumulated a `## Data Handling` section, pass-narration inside `## Directions`, and unreconciled-finding prose inside `## Stakeholders` that no other project had, and the schema that called itself *"the only place the sections are enumerated"* silently fell two sections behind Linear. A bootstrap-only contract cleans a description exactly once; every wave afterwards is free to re-bloat it. **What is mechanically enforced, stated exactly** (`engine project lint --stdin --container description --strict`, run at the sync step before the write): a heading **another container names** — i.e. machinery re-bloat, which is the mode that actually happened, 4/4 of the historical offenders — is a **hard FAIL that refuses the write**; a **novel** heading no container names is a non-blocking **warn**. The gap is structural, not an oversight: the pre-write lint is **stateless**, so it cannot tell a heading the wave is *adding* from one that was *already live and correct* — hard-failing novel headings would make the gate refuse the very description that is live today. Do not "fix" this back to a hard fail without first making the check diff-aware; the machinery half is the half that rots, and it is the half that blocks.
*   **¶INV_RESOLVE_ON_DISPOSITION**: Resolve an origin comment thread exactly when the signal **leaves the inbox** — filed as a ticket, folded into a parent, or closed as outdated/incorrect/superseded — always *after* the pointer reply is posted. **Never on ticket-done**: the ticket owns the work's lifecycle, the comment owns the signal's, and mirroring done-ness back would create two sources of truth for one fact (`¶INV_LINEAR_IS_TRUTH`) with threads open for months. **Never** while it is still intake's problem (`needs-triage`, marinating, parked). **A reply on a resolved thread un-resolves it** and re-enters the next drain — resolution means *dispositioned*, never *closed to further input*, or it silently revokes the promise every channel makes that triage is a draft you can correct. Mechanism is `engine ticket resolve-comment <commentId>` (with `--reopen` for the un-resolve) against the GraphQL API via `linear-lib.sh`: the **Linear MCP exposes no comment-resolve mutation** (`resolve_diff_thread` is diff-review only). Fall back to asking the human only when the command itself fails for lack of a configured `LINEAR_API_KEY` — never skip silently, never claim it was done.
*   **¶INV_EXCLUDE_OWN_COMMENTS**: The skill's own reply-threads are excluded from ingestion AND from the ripeness corroboration count — identified by their **marker prefix**, not by author (all skill posts land under the operator's human Linear identity, so author can't distinguish them). Every skill-authored reply MUST lead with a recognized marker (`candidate` / `seems like …` / `→` / `🔎 needs-triage` / `👀 claimed` / `✅ result` / `filed as FIN-…` / `shipped in FIN-…`) so the exclusion is complete. **The three copies of this list — the item-state enumeration, the drain's filter step, and this invariant — are one list written three times, and they move together or the leak persists.** A disposition the protocol can produce but cannot mark is a reply that returns next wave looking like fresh human feedback; that is what a missing marker costs, and it is why the taxonomy and the discipline are one fix, never two.
*   **¶INV_WRITE_BEFORE_WATERMARK**: Write drained items to `INTAKE_DRAIN.md` before advancing the watermark, so a mid-drain crash never silently loses feedback.
*   **¶INV_IDEMPOTENT_PROMOTION**: File-then-annotate carries a pre-write key so a crash never double-files a twin ticket.
*   **¶INV_VERIFY_LINEAR_WRITE_BEFORE_RETRY**: A Linear `502 upstream_unavailable` (or comparable transient) on any MCP write is a **false negative** — the write frequently lands despite the error, so a **blind retry double-posts**. Before retrying any Linear write in the wave (the Phase-3 triage post, the `/ticket` graduation file, `resolve-comment`, the Phase-5 Project Update announce), **verify with `engine project fetch --since=<just before the attempt>` whether it already landed**; retry only if it did not, and delete any duplicate. This rule **travels with `triageAccounting`'s posted-URL requirement**: making a posted comment URL mandatory makes retry-on-error a common path, so the retry discipline ships alongside it. **Reason**: captured from a wave that hit a 502 posting a comment, retried, and had **both** land — the duplicate had to be hand-deleted. Applies to every skill that writes to Linear over MCP; the shared home is `§CMD_POST_TICKET_COMMENT` (engine-wide promotion tracked separately).
*   **¶INV_RANKING_WITH_PROOFS**: The "pull this first, and why, with evidence" ranked view is a **required step in Outcomes (Phase 5)** — no longer a reserved seam. The agent ranks by the impact model (consolidation breadth + non-self corroboration + blast-radius) with proof-pointers; it is a prescribed action, not an automated/mechanical feature.
*   **¶INV_PROBLEM_DEPENDENCY_GRAPH**: The problem map is a dependency graph (nodes = problems/solutions; edges = stands-on / blocked-by / unlocks / needs-research-from), materialized as Linear relations + held readably in the working doc — so decomposition and the high-leverage sub-problem are visible.
*   **¶INV_RESEARCH_MEMORY**: Investigation done against a problem accumulates ON the problem (its ticket) — findings, dead-ends, why/when — never lost to a person or a dead session; no problem is attacked from zero twice. The system *enables* the conjecture, it never claims to *generate* it. **Nuance** (`¶INV_STEERING_NOT_SOLUTIONS`): triage and the wave boards may offer process-*steering* options to react to (a legitimacy read, what-to-measure-next) — still *enabling*, not *generating*: reactions that shift the process, never a manufactured solution, and the human still makes the creative leap.
