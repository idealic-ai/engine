# WARM PRINT widget kit

The shared visual kit behind `/prove` evidence pages and intake decision boards. One design
language — paper-and-ink "warm print" — rendered two ways: as **static, zero-JS proof pages**
(evidence dossiers a reader scans) and as **interactive decision boards** (triage surfaces that
collect votes). Both draw their palette, type, and freshness/status colors from one token file,
so a retint moves the whole system at once and nothing hardcodes a hex.

**Kit home**: `~/.claude/engine/skills/intake/assets/`. The interactive kit is published to S3
(versioned) and referenced via the `__FB_KIT_BASE__` token, resolved at publish. **Boards and proof
pages both reference the kit that way** — same-origin, so no third-party host is ever contacted; the
publish step may inline a stylesheet instead for a zero-request reader path. What a page must never
do is hand-copy or runtime-inject the kit: one source, one address.

The doc is widget-first: after the foundation, the spine is a catalog of every widget in the kit —
what it is, the job it does, how to compose it, and its variants. Deep authoring contracts live in
their own files and are linked, not duplicated (see **Reference**).

**Composing right now? Read the DIGEST first, not this file.** `KIT_DIGEST.md` and its two
companions carry every contract in the reference galleries, extracted verbatim, so you do not
have to read this 77 KB doc or the galleries behind it. The split, in the digest's own words —
one file per question:

- **`KIT_DIGEST.md`** — *which block, and am I allowed to use it.* The contract set.
- **`KIT_DIGEST_RECIPES.md`** — *how do I compose a whole page.* The 6 sanctioned recipes.
- **`KIT_DIGEST_MARKUP.md`** — *what do I paste.* The verbatim markup, load only when emitting.

All three sit beside this file in the kit home, are generated by `kit-digest.mjs`, and are
drift-gated against their sources by `__tests__/kit-digest.test.mjs`. Come back here for the
things the galleries do not state: the foundation (§1), the skeletons (§3.0), theming (§4),
and versions + integrity (§5).

## The spine: zero-JS reader path, JS only enhances

**What it is.** One rule classifies every element in the kit by which side of a line it sits
on. **The reader path is zero-JS and CSP-safe** — the shipped proof page must fully READ with no
script running: evidence viewable, popovers open, blocks laid out, provenance legible. **JS only
ENHANCES**, and every enhancement degrades gracefully to a working zero-JS base.

The one relaxation: a page MAY pull the kit's stylesheets and scripts through ordinary
`<link>` / `<script>` tags on the same-origin `__FB_KIT_BASE__`. That is a network request, so the
older "self-contained, zero network" phrasing no longer holds — but nothing about comprehension
rests on it: if the script never loads the page still reads, and if the stylesheet never loads it
reads unstyled. Third-party and CDN hosts remain forbidden, as does injecting styles or behavior at
runtime, or pasting a duplicate copy of a kit file into a page.

**How it splits — every widget below states its side.**

- **Zero-JS (reader path)** — the `.mod` static blocks · the affordance rail and its native
  `popover` reveals (evidence, ticket, why-proven) · stakeholder roundels · the view filter's
  all-visible base · the `¶` anchor as an in-page jump.
- **JS enhancement** — live ticket cards (`prove-ticket`) · the decision components
  (vote / clear / dirty) · the sticky action bar's Submit + `beforeunload` guard + stepper ·
  "log in as" identity · the `¶` copy-to-clipboard + toast. Each has a zero-JS fallback: a ticket
  ref degrades to a link, the stepper to plain in-page anchor links (all items visible), the
  perma-copy to a manual-copy jump.

**Why.** The artifact a reader receives is the evidence; it must stay legible offline and under a
strict CSP, indefinitely, with nothing to load and nothing to break. Interactivity is genuinely
valuable but never load-bearing for comprehension — so it is layered on top of a path that already
works. This split is the architectural spine: a new element is designed by first placing it on one
side or the other, and an enhancement is only allowed if its absence still leaves a readable page.

## 1. The design system (foundation)

`proof-theme.css` is **the single source of truth** for palette, type, and measure — a set of CSS
custom properties. Everything downstream consumes them by name: the static block catalog, the
`<prove-ticket>` component, and the board (via the `--fb-*` seam that `board-warm-overrides.css`
maps onto these). No component hardcodes a color.

**Theming — two channels, kept in lockstep.** Four token blocks: a light `:root` default, a
`@media (prefers-color-scheme: dark)` block for the OS preference, and `:root[data-theme="light"]`
/ `:root[data-theme="dark"]` for an explicit in-page toggle (the toggle wins by specificity). Edit
all four together.

**Delivery.** Both a proof page and a board LINK `proof-theme.css` from the published kit prefix
(same-origin — the page still loads no third-party host, so it stays CSP-safe); the publish step may
instead inline it for a zero-request reader path. Never hand-copy it into a page: one source, one
address, so a retint reaches every published page that points at that version.

### Elevation — four levels, and depth only ever goes DOWN

The kit used to raise **everything**: a `.mod` plate, and then every child inside it — option
panels, callouts, vote rows, evidence panels — each with its own border and outer shadow. When
everything pops up, elevation encodes nothing and a block reads as **two stories**. The system
below fixes that by making nested surfaces press **in** rather than pop **out**, which is also
what a real press does: one sheet, embossed in some places and debossed in others.

| Level | What it is | How it renders |
|---|---|---|
| **Paper** | the page | grain + vignette, flat |
| **Plate** | a `.mod` | embossed UP off the paper — `--shadow-card`, 1px `--rule`, flat `--card` stock. **Exactly one level, ever.** |
| **Well** | a region INSIDE a plate | debossed into it — `--inset-well`, `--card-2` ground, **no outer shadow, no border** |
| **Flush** | prose, headings, repeated tiles | no surface at all |

**`§ELEV_NO_NESTED_LIFT` — THE INVARIANT: an outer (non-`inset`) `box-shadow` on any descendant
of `.mod` is a defect.** It is mechanically checkable on a rendered page — for every element
matching `.mod *`, every layer of its computed `box-shadow` must carry `inset` — and a
conformance checker asserts exactly that. Only three selectors in `proof-blocks.css` carry an
outer shadow at all (`.mod`, `.dictum`, `.evpop`), and none of them is ever a descendant of a
`.mod`. Because level 3 presses DOWN, two-story stacking is structurally unreachable rather than
merely discouraged: there is no rendering above PLATE for a descendant to reach for.

**It is a DEFAULT, not an opt-in.** Write the ordinary catalog markup inside a `.mod` and you get
the inset system without knowing it exists — `.callout`, `.cite`, `.pull`, `.cpv`, `.stripe`,
`.tablewrap`, `.frame`, `.codewrap`, `.scope`, `.thesis-block`, `.phases`, `.scale`, `.bignum`,
`.tcol`, `.diffcol`, `.srcblock` and the `.fbopts` option group all render as wells inside a
plate. No class was renamed, removed, or added as a requirement; what changed is how the
existing hooks render. A `.well` class an author must remember would be a worse design than a
default that is simply correct — so `.well` exists **only** as an escape hatch for a region the
catalog does not name (a bespoke `<div>` grouping, or a foreign component whose classes
`proof-blocks.css` cannot see). If you find yourself writing `.well` on a catalog block, the
block was already a well.

**Depth is contextual.** The well rules are scoped to a real plate (a `.mod` that is neither
`.flat` nor `.open`, or `.evpop`). `.mod.flat` and `.mod.open` paint no card, so a block inside
one is itself the first surface off the paper and keeps the raised rendering — as does a catalog
block used loose on the sheet. Nothing is ever debossed into bare paper.

**THE CORDUROY LINE — where a well is earned.** Too many wells reads as ribbing. A well is
earned by a **grouping that holds a run of content**: a callout, a code block, a table, a quote,
a stat strip, one column of a two-column spread. It is **not** earned by a repeated sibling in a
grid or a row — `.vcell`, `.cov`, `.flow .node`, `.tkcard`, `.scope-card`, `.phase`, `.scale .sw`,
`.stripe .cell`, an option row. Those go **flush**: hairline plus flat fill, no relief either way.
A run of eight wells is ribbing; one well holding eight rows is a form. That is why an option
list renders as **one well containing hairline-separated rows** rather than n bordered cards, and
why selection shows as a fill plus an inset spine — never as a lift.

**A coloured spine survives the border reset.** The well drops its neutral 1px `--rule` frame,
but `.cite` / `.pull` / `.bignum` / `.callout.insight|caution|note` keep their accent edge: that
edge encodes meaning, not elevation.

**Light and dark are designed, not inverted.** On light stock a deboss is read from the TOP —
the cut edge throws a short brown pool downward and the sheet climbs back out on an
`--emboss-hi` lip. Inverting that for dark stock produces a **hole**: a black pool on near-black
paper reads as punched through, because there is no lower luminance left for the shadow to
travel into. So the dark grade re-assigns the work — a thin low-alpha top cut with almost no
falloff, and a **bottom lip at a deliberately stronger alpha (`.11`) than `--emboss-hi`'s own
`.06`**. Light leans on the shadow; dark leans on the lip.

**Form inputs finally agree.** A textarea is natively recessed, so `.notefield` now reads as a
well like everything around it instead of needing a special case — its old
`0 1px 0 --emboss-hi inset` top line was an *emboss* cue on a field you type into.

**Contrast on the well ground.** `--ink-meta` had only ever been measured against `--paper` and
`--card`. Measured on `--card-2`: **4.89:1 light**, **4.82:1 dark** — both clear the 4.5:1 AA
floor, so metadata text is safe inside a well. (`--ink-soft` on `--card-2`: 5.45 light / 5.77
dark.) Re-measure before retinting `--card-2` or `--ink-meta`. `--ink-faint` remains non-text
only, on any ground.

**What this does and does not buy.** It is a legibility fix, not a density fix. Shadows overlap
rather than occupy layout, so removing them saves almost no vertical space: measured on a real
published board, the specimen block shrank 949→933px (−1.7%) and the whole 24-plate page −0.7%.
The win is that hierarchy now means something — one plate, and everything inside it demonstrably
below it.

### Honest-presentation rules (`§INV_PROVE_FAITHFUL_PRESENTATION`)

These are load-bearing, not stylistic — preserve them in anything you build on the kit:

- **Color encodes a real fact + carries an on-page legend.** Freshness and status are tokens
  precisely so a component can never silently diverge from the legend that decodes it. Any page
  that uses the freshness hues ships the freshness `legend` block.
- **Color is never the only channel.** The freshness dot carries a non-color `data-fill` ramp,
  fresh → stale: `full` (fresh) · `three-quarter` (recent) · `half` (moderate) · `quarter` (stale)
  · `ring` (unknown) — rendered as a conic fill fraction (HTML) or a size ramp (SVG), always with
  an ink ring. Every meaningful dot also has `role="img"` and a bucket-word `aria-label`
  (e.g. `"active in the last 7 days"`). Static hand-authored dots MUST use the same ramp.
- **Small text uses `--ink-meta`, never `--ink-faint`.** `--ink-meta` is the AA-passing (≥4.5:1)
  metadata token for captions, footers, mono labels, as-of dates, eyebrows. `--ink-faint` is for
  non-text only — rules, dividers, borders, dot rings, decorative marks — and fails AA for text.
- **Dated facts stay dated.** A ticket card shows "status as of `<bakedAt>`", never as if live;
  freshness degrades to `unknown` rather than measuring against the viewer's wall clock.

The full token list is in **Reference**.

### The iconset — monochrome Noto Emoji, substituted by codepoint

Emoji used to render in whatever full-colour glyph the reader's OS supplied — glossy Apple stickers
sitting on one-ink stock, unable to take a token or flip with the theme. `proof-theme.css` now
self-hosts a **monochrome iconset** face (`proof-icons.v2.woff2`, 19 KB, 47 glyphs, variable
`wght` 300–700, OFL) at the kit's own same-origin prefix: a subset of Noto Emoji for the 30
content codepoints, plus **13 encoding marks drawn for this kit**. Its `unicode-range` claims
**34** of them — the 30 content codepoints and the four verdict marks ✓ ◐ ✕ ⌀. The other nine
drawn marks (▸ ▾ ▴ ↑ ↓ → ⛓ ✎ ›) are carried in the face but deliberately not claimed.

Why this shape:

- **It is substitution, not a rewrite.** Every 📎 🎫 🔍 already in composed markup keeps working
  exactly as authored. No icon-name registry, no composer build step, and — the point — **pages
  published before the font existed pick it up on a kit re-deploy without being recomposed**.
- **Monochrome Noto is a regular font, so its glyphs are ink.** They inherit `color`, take
  `--ink` / `--accent` / `--ink-meta`, and flip with the theme. Colour emoji cannot.
- **It leads all three stack tokens** (`--serif` / `--sans` / `--mono`), which is what makes it
  reach pages with no per-icon class. An element that hardcodes a `font-family` opts itself out.
- **Failure is graceful**: the font 404s → today's platform emoji, no error, no layout shift.

**⚠ THE CARVE-OUT — never claim the channel dots.** 🔴🟠🔵🟢🟣🟤🟡🟦 encode the eight intake
channels, and **seven of the eight are the same shape** — all circles; only 🟦 differs. Colour is
not decorating the channel, it is the entire discriminator for seven of them, and composed pages
use the dots **bare in prose** ("filed as replies on 🔴 and 🟢") where no adjacent label rescues
the meaning. Monochrome would not dim that, it would map seven channels onto one glyph. They are
excluded from the `unicode-range` **and from the subset itself**, so a careless widening of the
range still cannot reach them, and `contract-sync.test.mjs` fails the build if any of the eight
appears in the range. This is `§INV_PROVE_FAITHFUL_PRESENTATION`, not taste.

**Also never claim** ↗ `U+2197` (the external-link arrow) or ⚠ `U+26A0`. Both are authored bare,
in their hundreds, and already render as **type** that already themes correctly — claiming them
replaces a correct glyph with a worse one. The same trap sits under ✓ `U+2713`, ✕ `U+2715`,
◆ `U+25C6`: they live inside `U+2600–27BF` alongside real emoji, so the range is an **explicit
enumeration and must never become a block range**. Both exclusions are asserted by the tests.

**KNOWN GAP — nine codepoints do not convert.** ▶️ ⚖️ ⚙️ ✂️ 🕰️ 🕸️ 🖨️ 🗂️ 🗳️ are authored with a
trailing `U+FE0F` (VS16), and Chrome reads that as an explicit demand for emoji presentation and
goes to the system colour font, ignoring the `@font-face` entirely. Measured, not assumed: adding
`U+FE0F` to the range does not help, and `font-variant-emoji: text` reports supported and does
nothing (per spec it yields to an explicit selector). **The only lever is the character sequence.**
When composing, write these **bare** (`✂`) or with `U+FE0E` (`✂︎`) and they convert; `U+FE0E` is
the better default because without the font it still degrades to a text glyph rather than colour.
Two of these are the highest-volume marks in the corpus (✂️ Minimalist, 🕸️ Systems Thinker), so
until composed pages are re-authored, expect those two to stay colour on already-published pages.

**Optical weight, and the trap under it.** The face is variable (`wght` 300–700) and its weight is
pinned by a `font-variation-settings` **descriptor inside the `@font-face`**, currently `400`.
Retune the icons by editing that one number — no re-cut, no version bump.

**Never lift that declaration to `body` or any shared selector.** `font-variation-settings`
inherits, and on a variable TEXT font it overrides `font-weight` outright: `--sans` is `system-ui`
= SF Pro, which is variable, so a body-level rule collapses bold, semibold and light into a single
weight across the entire kit — silently, while the icons look perfect. This was measured, not
theorised; it was live in this file for one build. As a descriptor it binds to this face alone and
text weights are untouched (verified against a `font-variation-settings:normal` control).

The axis reaches **outline** glyphs only. Noto draws ✅ `U+2705` and 🔄 `U+1F504` as **solid filled
tiles**, which read as ink blots beside their open neighbours and glare on dark stock; `wght` thins
strokes but cannot unfill a solid. Wrap those two in `.ik-solid` (shrinks the em box and re-seats
the baseline) — it reduces the blot, it does not remove it. **These two are the named-SVG layer's
first candidates.** Bare ▶ `U+25B6` is a third, milder case.

There is deliberately **no theme-conditional icon weight**. Dark stock does make the same stroke
read lighter, but the only safe knob is a per-face descriptor, and varying it per theme would mean
a second `@font-face` family plus a re-declaration of all three stack tokens in every theme block —
far more machinery than a subtle optical preference earns.

**Two icon mechanisms will coexist, deliberately.** This substitution layer is one; a **named-SVG
layer** is planned alongside it for glyphs Noto lacks or draws badly. They are not competing
migrations and neither replaces the other — substitution keeps working for the ~30 codepoints
already in composed markup with zero authoring cost, while named SVG will serve the cases
substitution provably cannot (the solid-fill pair above; anything needing a shape Noto has no
glyph for). Noto currently covers **all 30** codepoints the kit emits, so the SVG layer's initial
scope is a *quality* list, not a *coverage* list.

## 2. Widget catalog

Three widget families: **static proof blocks** (zero-JS, the proof-page spine), the **ticket
preview** component (the live authoring layer), and the **decision board** kit (interactive). Then
the cross-cutting conventions that ride any block: the **affordance rail** (2d), the **verdict pill
+ why-proven** (2e), the **decision components** (2f), and the **stakeholder / identity / action
bar** (2g). Last, the **swipe accelerator** (2h) — an optional gesture layer over the board kit's
binary items.

### 2a. Static proof blocks

**What it is.** The zero-JS HTML/CSS block contract that `/prove` evidence pages are built from —
pure HTML + CSS + native `<details>`, no script. This section is the authoritative static-block
reference; [`PROOF_BLOCKS.html`](./PROOF_BLOCKS.html) is the rendered, theme-aware, standalone
gallery companion (open it in a browser to see every block live).

**Why/when to use it.** This is the reader path — the shipped proof page. It runs no script and
contacts no third-party host (its styling comes from the same-origin kit, or is inlined at publish).
Prefer a static block over the live component for anything
a reader will actually receive. A block is a **convention with defaults, not an enforced closed
set**: a recognized pattern, not a schema-validated type. A new block is additive — you build it on
the skeleton and give it a modifier name, never by editing an allow-list.

**How to compose it — the `.mod` skeleton.** Every block is the **same part**: one card skeleton
with three regions, plus a named kind. The kind is written in `.mod-slug`, **not** in `class`.

```html
<section class="mod slot-full" id="headline-figures">
  <div class="mod-head">                            <!-- identity + affordances -->
    <span class="mod-eyebrow">Measured</span>      <!-- identity -->
    <span class="mod-slug">stat-strip</span>       <!-- the KIND lives here, never in `class` -->
    <span class="mod-aff">                          <!-- the affordance cluster -->
      <a class="mod-perma" href="#headline-figures" aria-label="Permalink to this block">¶</a>
    </span>                                          <!-- .mod-perma = hover-revealed permalink -->
  </div>
  <div class="mod-body"><!-- the modifier renders its content here --></div>
  <div class="mod-foot">
    prov: checked-here · as-of: 2026-07-31 · ref: …
    <details class="fmeta"><summary aria-label="Scaffold detail">ⓘ</summary>…</details>
  </div>
</section>
```

- **Card variants** — `.mod` (boxed, the default, for data and evidence) · `.mod.open` (prose /
  questions / framing: an accent spine, no card) · `.mod.flat` (sits directly on the page, no
  chrome at all). Alternate them; a page of identical cards is the flat look.
- **Skeleton** = `.mod` (the card) → `.mod-head` (`.mod-eyebrow` identity · `.mod-slug` modifier
  hint · `.mod-aff` affordance cluster · `.mod-perma` hover-revealed permalink) · `.mod-body` (the
  block's content — the modifier renders here) · `.mod-foot` (honest provenance at rest + a folded
  scaffold disclosure). The skeleton is agnostic about what nests in `.mod-body`; the modifier
  decides. `stat-strip`, `table`, `sequence` are all the identical `.mod` frame — only the body
  markup and the kind name differ. **The one rule: a block = one skeleton + one kind.** The kind is
  named in `.mod-slug` (and in `data-mod` where a fragment declares one). `class` on a `.mod` carries
  `mod` plus LAYOUT and BEHAVIOR modifiers only — `flat` · `open` · `exp` · `slot-*` — and never the
  kind. A kind name in `class` collides with the same-named catalog widget: `.mod.mod{display:revert}`
  absorbs the layout half, but border, background, radius and typography survive and inherit.

**Slot enum** — where on the page the block lives (convention-with-defaults; a genuinely new
placement is a fourth value, not a hard constraint):

- `main` — the reading column, one measure (`--readw`); prose and primary blocks.
- `rail` — the docked apparatus: evidence tickets, spec metadata.
- `full-bleed` — spans both columns (`.slot-full { grid-column: 1 / -1 }`).

**Affordance alphabet (static path, 3 glyphs).** Only three affordances work without a script:

- `ⓘ` **Detail** — reveal source & provenance, via native `<details>`.
- `↗` **Open** — follow an external ref, via a plain `<a href>`.
- `¶` **Anchor** — permalink to this block, via an in-page `#id`.

Each glyph control carries an accessible name via `aria-label` (e.g. `aria-label="Permalink to this
block"`) — never a bare Unicode character for a screen reader to guess. (`⧉` Copy needs the
Clipboard API and `⌄` Expand duplicates `<details>`'s own triangle — both dropped on the static
path; render a ref as selectable text instead of a copy button.)

**Disclosure — honest at rest, dense on ask.** At rest `.mod-foot` shows only honest provenance:
`prov` (checked-here / trusted-upstream) · `as-of` (the baked date) · `ref` (the source). Author
scaffolding — `slot`, `nests`, `skeleton`, `modifiers`, `merged` — folds behind a native
`<details class="fmeta">` opened by the `ⓘ` affordance. Zero JS. The reader's chrome stays clean
while the structural contract stays one click away for an author or reviewer.

**The catalog — 20 blocks by family** (18 stable + a 2-block experimental annex). Each survivor is
a real, distinct job, not a restyle of another:

- **Numbers & measures (4)**:
  - `stat-strip` — open on 3–5 equal-weight headline figures. Modifier: `--tiled` (per-cell state
    dot + footnote).
  - `bignum` — one figure *is* the finding. Modifier: `--spark` (hand-drawn sparkline).
  - `table` — a run of cases, tabular. Modifiers: `--delta` (signed direction column) · `--status`
    (pass/warn/fail pill) · `--total` (summary row).
  - `meter` — shares of a whole, as bars.
- **Sequence & flow (3)**:
  - `sequence` — an ordered top-to-bottom list. Modifiers: `--timeline` (dated events + node
    states) · `--numbered` (repro steps) · `--log` (typed add/fix/chg).
  - `pipeline` — left-to-right through named stages. Modifiers: `--flow` (arrow connectors) ·
    `--phases` (state per stage).
  - `branch` — a decision that forks on a condition (kept distinct from `sequence`: a decision, not
    a progression).
- **Argument & structure (5, all distinct)**:
  - `claim-verdict` — claim → proof → verdict in one row (the ledger spine).
  - `thesis` — the one framing premise (larger, quieter than a callout).
  - `scope` — the boundary: shown / out / rests-upstream.
  - `qa` — anticipated questions, each answer verdict-led.
  - `tradeoff` — a decision with real costs on both sides.
- **Evidence (4)**:
  - `figure` — a real rendered asset (placeholder frame until the real capture).
  - `diff` — a small, quotable before/after source delta.
  - `code` — a quoted source excerpt. Modifier: `--term` (dark terminal chrome for verbatim CLI).
  - `quote` — a verbatim line, attributed with a provenance chip. Modifier: `--pull` (large display
    interrupt).
- **Emphasis & keys (2)**:
  - `callout` — a point stepping out of the body with a stated intent. Modifiers: `--insight` ·
    `--caution` · `--note`.
  - `legend` — the mandatory key that decodes any color used. Modifiers: `--freshness` (recency
    scale) · `--chips` (provenance/verdict).
- **Experimental annex (2, opt-in)**: `verdict-dashboard` (the whole claim ledger's state in one
  scan) · `coverage-map` (what was checked vs. deliberately skipped, spatially).

(The catalog is the collapse of an earlier 34-block gallery to 18: near-duplicate families folded
to one opinionated block plus documented modifiers — e.g. `stat-strip` absorbed the KPI-tile grid,
`table` absorbed before/after comparison + results table, `sequence` absorbed vertical timeline +
numbered process + changelog, `code` absorbed the terminal block, `callout` absorbed marginalia.
Dropped experiments are re-addable additively — cut for being unproven, not illegal.)

**Job → block picker** (the common ones): headline figures → `stat-strip`; one number that is the
whole finding → `bignum`; a run of cases → `table`; a dated history → `sequence --timeline`; repro
steps → `sequence --numbered`; stages with state → `pipeline --phases`; a fork on a condition →
`branch`; the claim ledger → `claim-verdict`; a before/after source delta → `diff`; verbatim CLI →
`code --term`; decode a color scale → `legend`.

**Static freshness dots + color legends** follow the honest-presentation rules in §1: a
hand-authored dot uses the same `data-fill` ramp + `role="img"` + bucket-word `aria-label`, reusing
the `.pt-dot` class so it renders identically to the component's; any page using the freshness hues
ships the `legend --freshness` block. Blocks consume tokens by name only (see §1 and the token list
in §5) — no block hardcodes a hex, and small text uses `--ink-meta`, never `--ink-faint`.

**Hard constraints.** Zero-JS / CSP-safe / no third-party host (native `<details>` is the only
interactivity; system fonts only; styling from the same-origin kit or inlined at publish);
theme-aware via `prefers-color-scheme` + `:root[data-theme]`;
wide blocks (`table`, `pipeline`, `branch`, `code`, `coverage-map`, freshness row) scroll inside
their own `overflow-x:auto` container so the page body never scrolls sideways.

### 2b. Ticket preview (`<prove-ticket>`)

**What it is.** `proof-ticket.js` + `proof-ticket.css` — a framework-free, CSP-safe, light-DOM
component that turns a Linear key into an inline reference with a leading freshness dot, a
hover/focus teaser, and a click-to-open anchored card (Overview / Activity / Relations tabs). Two
custom elements: `<prove-ticket>` (the inline ref) and `<prove-ticket-card>` (the single shared
popover). `PROOF_TICKET_VERSION` is `3`.

**Why/when to use it.** The JS authoring layer — for a live authoring preview where hovering a
`FIN-` key should reveal its dated status. The shipped reader page prefers the static block; this
component degrades to a plain link when no metadata is baked, and never fetches.

**How to compose it.** Two entry points:

```html
<!-- 1. explicit element -->
<prove-ticket key="FIN-3519">FIN-3519</prove-ticket>

<!-- 2. auto-scanner (default ON): bare FIN-\d+ text is wrapped automatically -->
<p>Fixed in FIN-3519, follow-up in FIN-3520.</p>
```

The scanner wraps bare `FIN-\d+` text, skipping `<a>/<code>/<pre>/<script>/<style>/<textarea>/
<input>`, its own elements, `contenteditable`, keys inside a plain-text URL, and anything under
`[data-no-prove-ticketify]`. It is idempotent (wrapped keys live in a skip-tag) and also reaches
bare keys inside inline SVG `<text>` (mermaid node labels), rendering an SVG-native `<a>`+`<tspan>`
link plus a `<circle>` freshness dot wired to the same shared card.

**The baked metadata contract.** Metadata is optional and BAKED at publish into one JSON script —
zero external requests by design:

```html
<script id="prove-tickets" type="application/json">
{ "bakedAt": "2026-07-31T12:00:00Z",
  "tickets": {
    "FIN-3519": {
      "title": "…", "status": "In Progress", "statusType": "started",
      "priority": "Medium", "assignee": "…", "project": "…",
      "url": "https://linear.app/finchclaims/issue/FIN-3519",
      "updatedAt": "2026-07-30T18:24:00Z",
      "lastActivityAt": "2026-07-30T18:24:00Z",
      "description": "…trimmed snippet…",
      "relations": [ { "key": "FIN-3518", "type": "related", "title": "…" } ],
      "activity": [ { "author": "…", "ts": "2026-07-30T18:24:00Z", "kind": "comment", "text": "…" } ]
    } } }
</script>
```

- `lastActivityAt` drives freshness (falls back to `updatedAt`); `bakedAt` is the reference time.
- `activity` is the newest 5 events only (`comment` | `state`), each `text` trimmed — keep the blob
  small. `statusType` must be one of `started | completed | canceled | backlog | unstarted | triage`
  (the pill's token vocabulary); an unknown type falls back to the base pill.
- Every baked string is rendered via `textContent` (never `innerHTML`); URLs are scheme
  allow-listed to the tracker permalink or `http(s)`.

**Graceful degradation.** No blob, an unknown key, or a `{title,status}`-only entry → the element is
still a working link with an `unknown` dot and a minimal card. It NEVER fetches.

**Freshness buckets** (gap between `bakedAt` and last activity): `fresh` <24h · `recent` ≤7d ·
`moderate` ≤30d · `stale` >30d · `unknown` (no date). Each maps to a `data-fill` ramp word
(`full/three-quarter/half/quarter/ring`) and a token color (`--fresh/--recent/--moderate/--stale/
--unknown`).

**Styling (behavior-only component).** `proof-ticket.js` ships NO CSS and injects no `<style>` — it
is behavior-only. All styling lives in `proof-ticket.css`, a real linkable asset the page must
provide: link it (`<link rel="stylesheet" href="proof-ticket.css">`) or let the `/prove` compose
step inline it into the page `<head>`. A contract test (test 39) asserts the JS carries no embedded
stylesheet and that the component still renders + functions when the page supplies the file.

**Structure & variants.** The card is a full `role="dialog"` with a tablist (Overview / Activity /
Relations), arrow-key tab navigation, focus trap, Escape/outside-click close, and anchored
placement (below by default, flips above / clamps into viewport). Relation chips call `navigateTo`
to swap the card's content in place. The card carries a freshness legend at its foot.

### 2c. Decision board (`board-widgets`)

**What it is.** `board-widgets.js` + `board-widgets.css` — the interactive triage surface. The
render agent writes creative, declarative HTML annotated with `data-fb-*` attributes; the kit
supplies stable behavior and emits an event-stream payload. `SCHEMA_VERSION` is `2`. Presentation is
free; the payload shape is fixed (`§INV_BOARD_HANDOFF_IS_FIXED_PRESENTATION_IS_FREE`).

**Why/when to use it.** Mostly an intake concern — a wave's decision surface: present trusted triage
findings + the decisions to make, and collect steering answers/votes. The kit reads the markup,
builds an event stream, and copies a clean JSON payload back (or, optionally, submits it to a shared
multiplayer board).

**Shape (named, not exhaustive).** A board carries board/wave metadata, an optional `data-fb-voter`
name input, and `data-fb-item` widget containers. **Item kinds** (`data-fb-kind`): `steer` (pick a
direction) · `consolidation` (fold findings together) · `adopt-cancel`. Within an item: option rows
(`data-fb-key` → vote), field inputs (`data-fb-field`), a note (`data-fb-note`). **Mark types**:
`fb-mark-council` (an icon = an expert class; dashed, weight-scaled, dotted when thin; reasoning
reachable three ways — hover/focus/click) vs `fb-mark-human` (initials = a person). Form carries
class, size carries conviction; color reinforces class, never a persona. A copy bar + payload box
are auto-created; optional shared-state (`data-fb-state-config`) adds submit/presence with copy-back
never demoted.

**Authoritative contract (the deep-dives).** The full `data-fb-*` authoring contract and the return
payload live in their own files in this dir — use them, don't reimplement from memory:

- [`TEMPLATE_DECISION_BOARD_PROMPT.md`](./TEMPLATE_DECISION_BOARD_PROMPT.md) — what every wave must
  surface + the mechanical contracts (embed the kit; render marks as the kit reads them).
- [`PAYLOAD_SCHEMA.md`](./PAYLOAD_SCHEMA.md) — the v2 event-stream payload + the ingest fold rule.

The board is restyled via the `--fb-*` seam only (see §4); its files are cannot-drift (see §5). An
optional gesture accelerator rides its binary items — §2h.

### 2d. The affordance rail (`.mod-aff`)

**What it is.** The universal, layout-agnostic attachment point for a block's apparatus — a
**segmented button-group** that rides the shared `.mod-head` of the `.mod` skeleton, so it works on
ANY block in ANY layout. It renders **contextually**: only the segments a block earns appear. The
rail is `[📎 Evidence·N | 🎫 Tickets·N | ↗ URL]` (the `.affgroup` control) beside a stakeholder
roundel and the `¶` perma. Which side of the spine: the group and its native-`popover` reveals are
zero-JS; only the `¶` copy is a JS enhancement over a zero-JS jump.

**How to compose it.**

```html
<span class="mod-aff" aria-label="Affordance rail">
  <span class="affgroup" role="group" aria-label="Block affordances">
    <button class="affseg" popovertarget="ev-claim" aria-label="1 evidence piece for this finding">
      <span class="segico" aria-hidden="true">📎</span><span class="seglab">Evidence</span>·<span class="segn">1</span>
    </button>
    <button class="affseg tk" popovertarget="tk-claim" aria-label="1 related ticket for this finding">
      <span class="segico" aria-hidden="true">🎫</span><span class="seglab">Tickets</span>·<span class="segn">1</span>
    </button>
    <a class="affseg" href="https://…">↗ <span class="seglab">URL</span></a>
  </span>
  <span class="roundel" title="Yarik — Engineering">YF</span>          <!-- see §2g -->
  <a class="aff" href="#finding" aria-label="Permalink to this block">¶</a>
</span>
<!-- ONE popover, ALL this block's evidence -->
<div id="ev-claim" popover class="evpop" role="dialog">…source / exhibit / ref rows, each who·when·prov…</div>
<!-- ticket popover carries the RELATION -->
<div id="tk-claim" popover class="evpop tkpop" role="dialog"><span class="tk-rel origin">Origin ticket</span> …ticket card…</div>
```

- **Evidence** — the `📎 N` segment opens ONE native `<div popover class="evpop">` carrying ALL of
  that block's evidence: each row a source / exhibit / ref with who · when · provenance
  (checked-here / trusted-upstream). NOT scattered per-type icons; NOT a `<details>` whose summary
  is itself another reveal.
- **Tickets** — the `🎫 N` segment opens a popover carrying the ticket card plus a **relation** label
  (`.tk-rel`): Origin ticket · Related · Blocks · Blocked-by. The affordance data contract is
  `ref: {key, relation}`; the baked ticket data is fetched by the ticket-bake into `tickets.json`
  (dependency: [FIN-3448](https://linear.app/finchclaims/issue/FIN-3448)).
- **URL** — the `↗` segment follows an external ref via a plain `<a href>`.
- **Roundel** — the stakeholder badge (see §2g).
- **`¶` perma** — copies the block's ABSOLUTE `#anchor` deep-link. Progressive: zero-JS = jump (the
  URL updates for a manual copy); JS = copy-to-clipboard + a "Link copied" toast.

**Why.**

- **Opt-in per block + universal availability = composability.** The rail is defined once on the
  skeleton, so any block can carry evidence / tickets / refs and a bare block simply renders an
  empty rail. A question can carry a stakeholder + a source; a stat a query; a claim an exhibit + a
  ticket — same convention, applied only where earned.
- **One consolidated popover, not scattered icons.** A reader opens a block's evidence in one place;
  per-type icons and nested reveals were the confusing pattern this replaced.
- **Relation labels because a ticket's meaning to a block matters.** "The ticket this finding came
  from" is a different fact than "a related ticket" — the relation is carried, not flattened away.
- **Native `popover` keeps it zero-JS.** The HTML `popover` attribute + `popovertarget` give a real,
  dismissible popover with no script, so every reveal survives the reader path.

### 2e. The verdict pill + why-proven

**What it is.** `PROVEN` is a prominent VERDICT pill, kept deliberately OUT of the affordance
button-group. Clicking it opens a "why-proven" popover: the grounds + provenance (trusted-upstream /
checked-here) + a link into the block's evidence popover. It reuses the same native-`popover`
mechanism as the affordance reveals, so it is zero-JS.

**How to compose it.**

```html
<button class="verdict" popovertarget="why-stat" aria-label="Why this figure is proven">
  <span class="ws" aria-hidden="true"></span>Proven
</button>
<div id="why-stat" popover class="evpop whypop" role="dialog">
  …grounds · provenance (checked-here / trusted-upstream)…
  <button class="why-evlink" popovertarget="ev-stat">📎 See the exhibit evidence ›</button>
</div>
```

**Why.**

- **A verdict must show its grounds** (`§INV_PROVE_FAITHFUL_PRESENTATION`) — a ruling that can't be
  interrogated isn't honest, so the pill always opens onto its grounds + provenance + the evidence.
- **A state / ruling ≠ an action affordance.** Folding PROVEN into the `.affgroup` would demote the
  ruling and muddy the group's meaning — the group is things you DO, the verdict is a fact about the
  block. Distinct in placement (a prominent pill), unified in behavior (the same popover, wired to
  the same evidence).

### 2f. Decision components (the decision layer)

**What it is.** A standardized, named set of decision inputs. **One component per block, matched to
the block's question** — never two decision paradigms stacked on one block. The agent picks the
fitting component the way archetype recipes pick a layout. These are a JS-enhancement layer (built
on the cannot-drift `board-widgets` kit, restyled via the `--fb-*` seam) over a native-input +
in-page-anchor base. The set:

- **Verdict** (`.dckind.verdict`, `.vseg`) — for a finding or claim: **Accept / Revise / Abstain**,
  three-way and tri-color. Passes judgment on an assertion.
- **Single-select** ("Your call", radio, `.fbopt.single`) — exactly one exclusive option.
- **Multi-select** ("pick any number", steer, `.fbopt.multi`) — any number of non-exclusive actions.

```html
<div class="decision">
  <span class="dckind verdict">Verdict</span>
  <span class="vseg">                                 <!-- Accept · Revise · Abstain, three-way -->
    <label class="vopt">…Accept…</label><label class="vopt">…Revise…</label><label class="vopt">…Abstain…</label>
  </span>
  <div class="noteaff">…optional note (nudged open on Revise)…</div>
</div>

<label class="fbopt single">                          <!-- .multi for pick-any-number -->
  <input type="radio" name="stat-total">
  <span class="fbopt-body"><span class="fbopt-label">…</span><span class="fbopt-desc">… <span class="fbopt-key">key: …</span></span></span>
  <span class="cmark w2" popovertarget="cm-…">⚖</span>  <!-- council weight via opacity + border -->
  <span class="census"><span class="censn">3</span><span class="pips">…</span></span>
  <button class="optx" type="button">×</button>        <!-- single-select + Verdict only -->
</label>
```

Shared across all three:

- **Universal note** (`.noteaff`) — every component takes an optional note; any decision can carry a
  reason. Nudged open on a Revise verdict ("What should change?").
- **Council marks** (`.cmark`) — per-option AI-expert weighted opinion. Weight is encoded by
  **opacity + border-style** (heavier = more opaque + solid; thin-grounds = dotted + faint); the
  "why" is reachable on tap (a native popover).
- **Human census** (`.census`) — per-option tally of others' votes, with presence pips + a dashed
  "you" pip once you vote.
- **Clear-× only where re-click can't un-pick** — on radio single-select + Verdict chips (a picked
  exclusive option has no other way back), NOT on multi-select checkboxes (un-checking clears them).

**Why.**

- **Three-way Verdict** — Abstain is an honest position ("out of my area"), not a non-answer forced
  into Accept-or-Reject.
- **One component per block** — applying Accept/Revise to an action-picker is "at odds": a verdict
  is a judgment on an assertion, and an action menu has no assertion to judge. The component must
  fit the block's decision TYPE, so the wrong pairing is designed out rather than styled around.
- **Universal note** — a reason belongs to any decision, not only to a revision.
- **Council-mark weight via opacity + border, not a dot cluster** — it stays quiet and matches
  board-widgets' own weight language (form / size carry conviction), instead of a loud per-option
  dot cluster competing with the option text.

### 2g. Stakeholder, identity + the sticky action bar

**What it is.** The layer that answers who a block concerns, whose view is active, and how decisions
are submitted.

- **Stakeholder roundels** — an initials badge marking who a block concerns. **The badge IS the
  label**: the name lives in the block's title / `aria-label`, with no redundant "for X" text beside
  the roundel.
- **The sticky action bar** (`.idbar`) — one bar reconciling directed-to + views + submit:
  per-person progress (`data-prog` = decided / directed), click-avatar → that person's view
  (a plain in-page anchor; with no JS every item stays visible) with a `< >` stepper through their
  items, one **Clear view** control
  (no "All"), **Submit** with dirty-tracking + a `beforeunload` guard, and a "log in as" identity
  picker.
- **The users roster** — the bar consumes `users=[{initials,name,email,slack,linear}]`: an org-wide
  identity cache handed off per-proof by the orchestrator (dependency:
  [FIN-3447](https://linear.app/finchclaims/issue/FIN-3447) identity map). It resolves roundels to
  names and enables submit attribution + notify.

```html
<div class="idbar" role="group" aria-label="Directed to — pick a view">
  <a class="ava" href="#view-rm" aria-label="Rob M. — 0 of 3 items decided">
    <span class="roundel">RM</span> … <span class="cnt" data-prog="rm">0/3</span>
  </a>
  <a class="ava reset" href="#view-all">Clear view</a>
  <div class="stepper step-rm">‹ › <span class="unsaved">No changes</span>
    <button class="submitbtn" data-submit="rm" disabled>Submit RM</button></div>
</div>
```

**Why.**

- **The badge is the label** — a roundel plus a repeated "for Yarik" says the same thing twice; the
  name belongs in the accessible name, not the visible chrome.
- **Identity resolution enables attribution + notify** — a submitted decision needs a resolvable
  person (email / slack / linear), which is why the roster is a real dependency, not decoration.
- **One reconciled bar** — who's involved, their progress, whose view is active, and submit are one
  concern; splitting them across separate controls fragments a single mental model. The anchor
  base keeps the whole bar navigable before the submit JS loads.

  **The filter is a JS enhancement, not a CSS one.** There is no `:target` rule behind it — the only
  `:target` selectors in the kit are two `.fam-annotated` pin highlights in `proof-creative.css`.
  `kit-behaviors.js` toggles a `.dim` class (`opacity:.32`), so with no JS the honest base is
  **everything visible, nothing dimmed** — which is what `kit-behaviors.js` says of itself:
  *"enhances #view-<key> anchors; degrades to all-visible."*

### 2h. Swipe accelerator (`board-swipe`)

**What it is.** `board-swipe.js` + `board-swipe.css` — an **optional** drag accelerator over the
board kit's binary decision items. For each `data-fb-item` whose `data-fb-kind` is `consolidation`
or `adopt-cancel` **and** which carries exactly two `data-fb-key` inputs, it injects a 46px **decide
bar** directly above that item's `.fb-options`. Drag right for the affirmative option, left for the
negative; a release past the threshold commits by calling `input.click()` on the option row's own
input. `BOARD_SWIPE_VERSION` is `1`; the CSS rides it.

**Why/when to use it.** A wave with a run of merge/adopt calls is a run of identical two-way
judgments, and clicking a specific 64px row for each one is the slow part. Reference it on a board
that has binary items; **cut it from a steer-only board**, where it binds nothing.

**The four properties that define it** (each one measured, none of them stylistic):

- **Binary kinds only, off the existing `data-fb-kind`.** `steer` items carry 3–5 options and have
  no left/right — they are left completely untouched: no attribute, no injected node, no changed
  behaviour. Unknown kinds fail closed. On the one real board measured, that is 3 of 10 items, so
  this is an accelerator for a **minority** of a board and can never be the interaction model.
- **The rows stay primary.** Everything is scoped under `html.board-swipe-on`, a class only the
  script sets, and the bar exists only because the script injected it — so with JS off the
  stylesheet is inert and every option row is a plain native form control. The bar never hides,
  collapses or restyles a `.fb-opt`.
- **`input.click()` is the commit, so the layer IS the click path.** The emitted `vote` event is
  byte-identical to a click's modulo timestamp; `board-swipe` emits nothing itself and does not move
  `SCHEMA_VERSION`. And there is no second store: the bar renders **from** the checked input on
  `change`, so a keyboard vote, a row click and a drag are one state — which is also what makes the
  gesture's visual state screen-reader-correct without any ARIA of its own.
- **No vertical gesture, ever.** `touch-action: pan-y` on the bar's own strip and nowhere else.
  `touch-action: none` was measured at **0px** of page scroll over a card against −19,853px off-card
  in the same run — on a board of ~1000px items that is most of the scrollable surface going
  scroll-blind. A pass is a tap target, or it is just scrolling on.

**The gesture is deliberately not a card swipe.** A decision item is a ~1000px *argument* — premise
blocks, a callout, panel marks, a provenance footer — not a glanceable card, and the naive "grab the
middle of the box" point is literally off-screen. So the **item never moves**: no rotation (the
thing that slides prose out of the viewport), no fling, no transform on the block. Only the bar's
thumb translates, at most 44px, and the directional feedback lives on the bar — under the finger,
where it cannot scroll away from the gesture that produced it. The bar is also a **defined handle**
rather than a whole-block grab surface: on a tall block, "grab anywhere" competes with text
selection and with reading.

**The note is untouched.** `textarea[data-fb-note]` renders exactly as `board-widgets` ships it, at
every point — before, during and after a decision. You cannot type while dragging, and a reject is
precisely when a note matters most, so the bar carries a `Note ↓` tap target that focuses the
textarea. That is a shortcut to it, never a replacement for it.

Its files are **not** cannot-drift (they are new, independently versioned, and touch nothing the
byte-compare covers), but they must never reach into `board-widgets.{js,css}` — the whole design
rests on the accelerator being removable without a trace.

## 3. Composing a page

**Before this section, load the digest.** `KIT_DIGEST.md` (which block, and am I allowed to use
it) · `KIT_DIGEST_RECIPES.md` (how do I compose a whole page — the 6 sanctioned recipes) ·
`KIT_DIGEST_MARKUP.md` (what do I paste — verbatim markup, load only when emitting). They are
extracted from the reference galleries with the prose as authored, so they answer §3d, §3e and
"what markup" without opening `PROOF_BLOCKS.html` or `CREATIVE_LAYOUTS.html` at all. Where a
digest and this doc disagree, the digest's sources are the galleries — regenerate and report the
drift rather than picking one.

### (0) START FROM A SKELETON — this is the first move, not a see-also

**What they are.** `./skeletons/` holds three **complete, already-composed pages with slots to
fill**. Not blank pages with instructions, not galleries to admire, not fragments to copy out of
— finished artifacts. Each one ships the kit `<head>` in the documented order at the current
versions, the atmosphere honoured, the page frame composed (running head · masthead · display
opener · section rhythm · numbered section heads · ornament breaks · marginalia rail · colophon ·
endmatter), the required `/prove` contract in place, and real `{{SLOT}}` markers.

**The rule: copy one, fill it, delete what you don't need. Never assemble a page from parts.**
Everything below in §3 — the archetypes (§3d), the creative catalog (§3e), the block picker (§2a)
— tells you what goes in the *middle* of a page you already have. It is not a build order for a
page you don't.

- **`proof-page.skeleton.html`** — the evidence proof that asks for nothing. **The common case.**
  Zero-JS reader path. §03 is the one archetype-dependent section, and its inline comment maps all
  seven §3d archetypes to the classes that already exist — which is why there is one file here and
  not seven.
- **`proof-decision.skeleton.html`** — the proof that **asks**. The same frame plus the sticky
  per-person action bar, stakeholder roundels, and one §2f decision component inside each block
  that earns one, placed after the grounds. Loads `kit-behaviors.js`; carries
  `__PROVE_STATE_CONFIG__`.
- **`decision-board.skeleton.html`** — the uniform triage queue whose answers fold into the intake
  ingest. Five stylesheets, the `data-fb-*` payload engine (`board-widgets.js`), the copy bar, and
  `data-fb-item` **on** the `.mod` so a board cannot be filled in and still come out a hand-rolled
  look-alike.

**Why three and not eight.** The seven proof archetypes do not differ in *composition* — they
differ in one section, the evidence spine. Every proof page carries the same required contract
(thesis · the reader's questions · key-insight · scope, unburied · the evidence · next steps ·
colophon). The axis that genuinely changes the page is **what it asks for and which engine drives
it**: nothing · the decision layer (`kit-behaviors.js`) · the payload engine
(`board-widgets.js`). Those three have different `<head>`s, different chrome and different
apparatus, so they are three files. The archetype is a swap *inside* one of them.

**Why a skeleton at all.** A parts list plus instructions produces the minimum arrangement that
satisfies the instructions — a correct, thin page. Consistency comes from a high floor and a
correct starting artifact, not from better advice. The skeleton *is* the floor.

**The page frame the skeletons are built on** (last section of `proof-blocks.css`) — the layer
*above* the card, so a skeleton uses classes instead of carrying bespoke page CSS:

- `.sheet` (one measure + gutter) · `.hair`
- `.runhead` + `.folio` — the running head that makes the artifact read as a dossier
- `.masthead` — the mono kicker struck by a short accent rule
- `.dossier-head` / `.thesis-wrap` / `.thesis` / `.lede` / `.byline` — the display opener.
  `.thesis` runs to ~3.1× body: that ratio is the device, not a large heading.
- `.flourish` + `.fleuron` — the ornament break between movements; `.flourish.minor` is the bare
  fleuron between specimens inside one section. Roughly one per block is the ornament budget.
- `.sec` (44px rhythm + a closing hairline; `.sec.last` drops it) · `.sechead` with `.no` (`§ 01`),
  a serif `h2` and a `.fill` hairline running to the edge · `.seccap` + `.seccap .lead`
- `.specimen` (block + margin) and `.mnote` (+ `.arw` `.tag` `.rail-mini` `.rm`) — **the marginalia
  rail**, where the page talks about its own evidence without interrupting it. It is the single
  device generated pages most consistently lack.
- `.legendbox` rows · `.dictum` (the closing statement) · `.endmatter` (the closing folio)
- `.mod.open` — the third card variant beside `.mod.flat`: prose, questions and framing sit on an
  accent spine with hairline rules instead of in a card. **Alternate it with boxed blocks** — a page
  where every block is a card reads as a stack of tiles; open prose against boxed data is what makes
  it read edited. It also avoids the card-inside-a-card a boxed `.mod` gets when its body holds a plate.
- `.colophon` + `.colo-grid` are reused from `proof-creative.css`, not redeclared.

It also sets the **press baseline on `body`** (paper background, ink, sans, 16.5px/1.62). That is
deliberate: `proof-theme.css` ships the atmosphere as two fixed sheets at negative z-index, which
only show through when the page background is on `body`. Declaring it in the frame means a page
cannot lose the grain and vignette by forgetting. **Never set a background on `html`** — that
paints over both layers and the atmosphere silently disappears.

### (a) Zero-JS proof page (reader path)

```html
<head>

  <link rel="stylesheet" href="__FB_KIT_BASE__/proof-blocks.v2.css">   <!-- .mod catalog + decision layer -->
```

### (c) Decisions ride the creative layout

A decision is EMBEDDED IN the creative layout that surfaces its evidence — the natural culmination
of a richly-presented finding — NOT a row in a uniform "decision board."

- The **archetype recipe** picks the layout that best surfaces the block's evidence.
- The **fitting decision component** (§2f) embeds at the natural point in that layout — after the
  reader has seen the grounds.
- So the compose order is: pick archetype → pick blocks / creative patterns → attach affordances
  (§2d) + the one fitting decision component contextually.

**Why.** A decision divorced from its evidence context is a bare board; the value is deciding in the
PRESENCE of the surfaced data. (Contrast the standalone `board-widgets` decision board in §2c — the
right surface when the job genuinely IS a uniform triage queue, rather than reasoning through
individual findings one richly-presented block at a time.)

### (d) Choosing a layout — proof archetypes

**Read this AFTER you have copied a skeleton (§3.0), not instead of it.** The archetype decides
what goes in the skeleton's evidence-spine section (`§ 03` in `proof-page.skeleton.html`,
`§ 02` in the other two) — it is not a page-building order. The skeleton already carries the
opener, the rhythm and the closing apparatus these recipes assume.

**What it is.** The prescriptive front door. Recognize the KIND of proof in front of you, then
reach for the composition that surfaces it best: the agent matches the finding to an archetype →
reaches for the prescribed opener + spine blocks + the creative patterns (§3e) that fit → the one
fitting decision component (§2f) embeds at the natural point in that layout. This is the "pick
archetype" step of §3c — the archetype names the spine; the decision then RIDES it, landing after
the reader has seen the grounds. One recipe per recurring proof-kind:

- **Diagnosis** ("what's wrong + why") — the `claim-verdict` ledger as spine · a data-as-visual
  pattern (§3e) that surfaces the evidence behind the diagnosis · an annotated exhibit pointing at
  the defect. Decision: **Verdict** (Accept / Revise / Abstain on the diagnosis).
- **Before/after (a fix)** — a comparison opener (diagonal split / overlay diff) · `diff` blocks
  for the quotable source deltas. Decision: **Verdict**, or single-select when the choice is among
  alternative fixes.
- **Metric / gate result** (pass · fail · thresholds) — a verdict-hero opener carrying the ruling ·
  a gauge row for KPIs-against-target · a confidence band for an estimate ± its interval · a
  coverage heatmap when the gate spans a matrix. Decision: **Verdict** on the gate.
- **Audit / coverage** ("how much, where the gaps are") — a coverage heatmap for rows × checks ·
  bars-in-table for a ranked breakdown · a `stat-strip` for the headline totals. Decision:
  **Verdict**, or multi-select on the gaps to chase.
- **History / accretion** ("how it came to be") — a timeline / story-arc as spine · a provenance
  evidence-stack to show the reading is over-determined by converging sources. Decision:
  single-select or **Verdict** on the reading.
- **Comparison** ("X vs Y") — a side-by-side / delta-gutter opener · `table --delta` for the signed
  per-row movement. Decision: single-select (pick the winner) or **Verdict**.
- **Recommendation** ("what should we do") — an annotated exhibit that lays out the option space.
  Decision: multi-select (the reader picks any number of actions to take).

### (e) Creative-layouts catalog

**What it is.** 25 remixable layout exemplars across six families — inspiration to ADAPT on the
`.mod` grammar, not a closed set of blocks. Each entry is a **name · when to reach for it · how to
remix (what to swap)**, drawn from the creative-layout sources. The rendered gallery is
[`CREATIVE_LAYOUTS.html`](./CREATIVE_LAYOUTS.html) — all 25 patterns as real, browsable markup
(theme-aware, standalone), the live reference to open alongside this section; where a caption there
and an entry here differ, the exemplar wins.
**The CSS is obtainable — do not retype it.** Every pattern below ships as real CSS in
`proof-creative.css` (published as `proof-creative.v<N>.css`). Link it, put the family's wrapper
class on the section, and write the pattern's markup; the geometry arrives with it. Composing from
the kit rather than reproducing it is the rule (`§INV_PROVE_COMPOSE_FROM_KIT`) — and it is now the
mechanism as well, which it previously was not. The `.fam-*` prefix is load-bearing: the six
families collide on `.caption`, `.legend`, `.dot`, `.n`, `.sw`, `.cell` and `.step`, and the
wrapper class is the only thing keeping one family's geometry out of another's. A page may mix as
many families as it likes because of it.

**Hero / opener.**

- **Giant-number hero** — one number set huge in serif with a one-line meaning + a 2–4 stat
  micro-row. Reach for it when the finding collapses to a single headline figure (a count, a total,
  a percentage). Remix: swap the figure + unit; recolor to `--defect` if the number is bad news;
  keep the micro row to 2–4 supporting stats.
- **Thesis pull-quote opener** — the finding as a large serif claim (drop-cap) with a verdict chip
  + a dated as-of line. Reach for it when the finding is a sentence, not a number — a claim to
  accept at a glance before scrolling. Remix: rewrite the claim; italicize the load-bearing phrase;
  swap the chip to CONFIRMED / REFUTED.
- **Verdict hero card** — a bold PASS / FAIL / PROVEN card carrying the key metric + a one-line
  ruling, color-encoded. Reach for it when a gate or claim resolves to a categorical verdict; one
  card, or a row to compare several gates. Remix: set the card class; swap the metric + ruling; the
  color legend is mandatory.
- **Split hero** — claim left, one key visual docked right (spark / stat / freshness-dot cluster);
  a magazine opener spread. Reach for it when a statement pairs with one supporting visual. Remix:
  keep the left claim; drop any of the three right-hand blocks.

**Comparison.**

- **Diagonal split** — two clip-path'd layers meeting on a diagonal seam with a delta badge at the
  seam. Reach for it for a dramatic single before/after with one headline number. Remix: two
  positioned `.side` layers on complementary polygons; drop the delta badge at the seam.
- **Overlay diff** — removed vs replacement tokens inline, lifted into a serif quotable line. Reach
  for it for a small, precise textual change. Remix: wrap the removed token in `.was` (strike-through,
  defect hue) and the replacement in `.now` (highlight, fixed hue).
- **Side-by-side + delta gutter** — before · gutter · after, the gutter carrying the signed Δ. Reach
  for it when each row's movement (better / worse) is the point. Remix: a 3-column grid; tag each
  gutter cell `.better` / `.worse` to color the ↑/↓ and Δ.
- **Was → now strip** — A · transform · B, the transform labeled with its mechanism. Reach for it to
  show what operation turned A into B. Remix: a 3-column strip; label the transform with a mono pill
  + an inline SVG arrow; stacks vertically with a rotated arrow on narrow screens.

**Data-as-visual.**

- **Confidence band** — a point estimate on a bounded scale with its uncertainty interval shaded.
  Reach for it for one metric with a known interval (precision/recall ± CI, a rate vs. an SLO).
  Remix: set the domain; map value→x; move the CI rect + point; swap to a fresh gradient if higher
  isn't better.
- **Coverage heatmap** — a rows × checks grid, each cell tinted by a real value and printing the
  number. Reach for it for one comparable value across two categorical axes; the eye finds the cold
  column first. Remix: tint each cell by a scale token, modulate opacity for magnitude; always print
  the number so it degrades to a table for the color-blind.
- **Distribution / histogram** — warm bars over binned buckets with a marked median. Reach for it
  when the SHAPE of a continuous variable matters more than its mean. Remix: bin the data, scale bar
  heights to the max count; keep the median line so the average can't hide a skewed tail.
- **Bars-in-table** — a real table where one column carries an inline mini-bar beside the number.
  Reach for it for a ranked list needing both the exact figure and the relative magnitude. Remix:
  one inline SVG per row (`preserveAspectRatio="none"`); bar width = value/max; keep the number
  column for exactness.
- **Gauge / meter row** — small radial gauges, each a KPI against its threshold, colored
  pass / close / fail. Reach for it for a header strip of 2–4 headline KPIs. Remix: sweep angle =
  value/scaleMax·180°; drop a threshold tick at the target angle; pick the arc color by comparing
  value to target.

**Annotated evidence.**

- **Callout-pins overlay** — numbered pins on the exhibit, each keyed to a list item. Reach for it
  for a busy exhibit where several separate spots each need a sentence. Remix: swap the placeholder
  for your real `<img src="data:…">` render; move each pin by editing its left/top %; add or drop a
  pin + its `<li>` together (counters renumber both).
- **Leader-line margin annotations** — notes in the margin, leader lines drawn inside the exhibit
  SVG so they can't desync. Reach for it for a tall exhibit where notes want room to breathe. Remix:
  author leader lines in the exhibit's own viewBox units (never absolute page pixels) so they ride
  the image; end each at a numbered tab matched to a margin note.
- **Highlighted crop + zoom** — the ROI tinted on the full render, magnified beside it. Reach for it
  when the proof lives in small print (a subtotal, a timestamp, one mismatched cell). Remix: tint +
  legend the ROI; crop the SAME region for the detail (a tighter `data:`-URI or a windowing viewBox)
  — never a redraw.
- **Spec-rail annotated exhibit** — A/B/C anchor marks on a measurement render, keyed to a mono rail
  of values. Reach for it when the exhibit IS a measurement (a bounding-box overlay, a layout
  extraction, a diff render) and the numbers behind it are the proof. Remix: drop A/B/C marks at the
  measured points; give each a rail row (keep the rail in mono); tag each row's provenance honestly.

**Narrative / timeline.**

- **Vertical timeline (recency spine)** — dated events down a spine, each node in a recency bucket,
  milestones punctuating the run. Reach for it for a chronology where how recently each event fired
  matters. Remix: swap dates + copy; set each node to a recency bucket, or drop recency and use
  milestones only.
- **Step-flow with state (numbered ledger)** — one row per step, each done / failed / running /
  pending with a glyph + a labeled pill. Reach for it for a reproduction or pipeline run where the
  reader needs to see exactly where it stands. Remix: one `.step` per row; pair each state's color
  with a glyph (never color alone); drop the command line if there isn't one.
- **Story arc (three-beat feature)** — setup → turn → resolve with magazine drama. Reach for it when
  the finding has a twist — what you expected wasn't what you found, and that reframes the fix.
  Remix: three beats; tint the turn `--defect`, the resolve `--seal`; one pull-line per beat, prose
  at reading measure.
- **Horizontal phase pipeline (progress strip)** — a left-to-right march through named phases with
  the current position + what's blocked. Reach for it when the reader wants the current position and
  the blockers at a glance. Remix: one `.phase` per stage (done / active / blocked / upcoming); keep
  it in an `overflow-x:auto` wrapper so it scrolls instead of shoving the page sideways.

**Provenance.**

- **Claim-ledger** — each row is one claim: its evidence, a verdict chip, and a provenance tag,
  framed by a double rule as a bound register. Reach for it for a resolved investigation with 3–8
  discrete claims you can each attach a verdict to. Remix: swap the verdict vocabulary (Proven /
  Partial / Refuted); the provenance-tag column stays fixed.
- **Evidence-stack** — a claim above a stack of overlapping source cards (a doc, a log line, a query
  result). Reach for it for a load-bearing claim you want shown as over-determined by converging
  sources. Remix: 2–4 cards per stack; each card names its source kind; the offset + shadow convey
  depth.
- **Receipt / manifest** — a mono itemized receipt of what was checked, with counts, a provenance
  column, a checksum, and a verdict footer. Reach for it for a verification pass with many small
  line-items (tests, greps, files) where the COMPLETENESS of checking is the point. Remix: each line
  carries a status glyph + a here / up tag; make the checksum a real digest.
- **Provenance ribbon** — a colored left spine marking each assertion's provenance in flowing prose.
  Reach for it for a mixed narrative where checked-here and trusted-upstream claims interleave.
  Remix: the ribbon is the whole vocabulary — solid accent spine = checked-here, hatched spine =
  trusted-upstream; never blur the two.

## 4. Restyling / theming

- **Retint the whole system** — edit token VALUES in `proof-theme.css` (all four blocks in
  lockstep). Everything downstream (blocks, component, board) follows, because nothing hardcodes a
  hex.
- **Restyle the board** — override the `--fb-*` seam ONLY, in `board-warm-overrides.css`, mapping
  each `--fb-*` onto a theme token. NEVER edit `board-widgets.css` / `board-widgets.js`. This is the
  fixed-vs-free ownership seam (`§INV_BOARD_HANDOFF_IS_FIXED_PRESENTATION_IS_FREE`): the kit owns
  what must WORK (geometry, hit targets, focus, reachability, the states that carry meaning —
  readability included); the board owns what must look GOOD (palette, type, motion).
- **Add a block** — build it on the `.mod` skeleton and name its kind in `.mod-slug`. The skeleton is
  convention-with-defaults, so a new block is additive, never a central edit.

- **Rules**: `--rule` `--rule-soft`
- **Accent**: `--accent` `--accent-ink` `--accent-soft`

  `--status-canceled` `--status-backlog` `--status-unstarted` `--status-triage`
  **Six hues, and the tracker has ten states — this is deliberate, not an incomplete set.**
  Three states share `started`, two share `completed`, and `Duplicate` maps to none (it falls
  back to `--ink-soft`, a generic ground with the status word intact). **Hue is a BUCKET
  channel; it can never be a state channel** — four states are un-nameable by colour even in
  principle, so **the glyph or the word carries the state and hue carries the bucket.** Do not
  "complete" this set: four more saturated hues would break a warm palette that already treats
  `--status-blue` as its one foreign note.
- **Type + measure**: `--serif` `--sans` `--mono` `--maxw` `--readw`
- **Material depth**: `--emboss-hi` `--emboss-lo` `--letterpress` · raised: `--shadow-plate`
  `--shadow-card` `--shadow-deep` · **debossed: `--inset-well`** — the one inset grade, the
  recipe for a region pressed INTO a plate (see *Elevation* in §1). There is deliberately no
  second grade: nothing in the catalog nests a surface inside a well, so an `--inset-deep`
  would be speculative. Add one only when a real level-4 surface appears.
- **Atmosphere**: `--grain-op` `--grain-blend` `--vignette-op` `--vig-glow` `--vig-pool`
  `--vig-edge`
- **Role answers (the theme seam)**: `--chan-g-*` `--chan-a-*` `--chan-z-*`, four slots each —
  `-ink` (hue) · `-ground` (background) · `-edge` (a border-bottom SHAPE) · `-weight`. See
  *Channel roles* below.

#### Channel roles — the seam a theme redefines

A channel class names a **role**; the `--chan-*` slots are the **theme's answer** to it. The kit's
rules no longer name a token — `.stripe .n.g` asks `var(--chan-g-ink)` — so how a role renders is a
theme decision, in one place.

| class | role, in the kit's own words |
|---|---|
| `.g` / `.chan-g` | the good/sealed reading |
| `.a` / `.chan-a` | the figure the page is actually arguing from |
| `.z` / `.chan-z` | a zero stated on purpose — quieted, never hidden |

`.g/.a/.z` keep working exactly as before; `.chan-*` are the same three roles addressable
**anywhere**, not only inside the eight ancestors that happen to have grown a rule.

**Redefine globally** — declare the slot on `:root` after `proof-theme.css`:
```css
:root{ --chan-z-ink:#4b5f9e; --chan-z-edge:1px dotted currentColor; }
```
**Redefine for one block** — declare it on the block:
```css
.scope-audited{ --chan-z-ink:var(--accent-ink); --chan-z-edge:2px dashed currentColor; }
```
Custom-property inheritance resolves from the nearest ancestor that declares the slot, so a block
answer beats `:root` — and beats a theme's `:root` — with **no `!important` and no id**. A seam you
can only win with `!important` is a seam nobody downstream can reopen. The kit ships two block
answers of its own, in `proof-theme.css`: `.codewrap.term` retints `g` to `--fresh`, and
`.fam-provenance .rc-tot` answers `g` at weight 700 where the rest of the kit answers 600.

**`-weight` is consumed only where the kit already emits a weight** (`.codewrap pre .g`,
`.fam-provenance .rc-tot .g`). Retrofitting it elsewhere moves pixels: `.stripe .n` inherits 700
while the code blocks set 600.

**These roles are deliberately NOT registered in `theme-roles.json`.** That contract canonizes a
name by the `kit-incumbent` rule, so adding a row would mechanically make `--chan-g-ink` the
canonical spelling — a naming ruling nobody has made. `--chan-<letter>-*` is the **incumbent
spelling, held provisionally**; the semantic words are a human's call. Register the rows after the
ruling, not before it. `theme-roles.mjs` checks these roles by reading the CSS directly and needs no
contract row.

**Not these letters.** `.fam-comparison`'s `.a`/`.b` are **positional** (arm A / arm B), a separate
vocabulary that collides with this one on `.a` — and the two components disagree about which arm is
good: `.lgnd .sw.a` is green (fixed) while `.strip .st.a` is red (defect), *and the legend decodes
the strip*. `.fam-narrative .step-state .g` is a child glyph badge, not a channel. Neither is routed
through these slots.

**`INV_DS_NON_COLOUR_CHANNEL` is measured here, not asserted.** `theme-roles.mjs` reports a role
answered with hue alone as `HUE-ONLY` and exits 1. WARM PRINT currently fails all three: every
channel answers with a hue and declines `-edge`. The reference for what passing looks like is
`.fam-narrative .step-state.pending`, the only one of its four sibling states that survives
`grayscale(1)`, because its answer carries a dashed border as well as a colour.

The board seam (`--fb-*`, in `board-widgets.css`, overridden by `board-warm-overrides.css`):
`--fb-fg` `--fb-muted` `--fb-border` `--fb-border-firm` `--fb-surface` `--fb-surface-hi`
`--fb-accent` `--fb-accent-soft` `--fb-council(-soft)` `--fb-human(-soft)` `--fb-note-bg`
`--fb-radius(-sm)` `--fb-shadow` `--fb-mark-size`.

### Versioning + integrity

- `SCHEMA_VERSION` (`board-widgets.js`, currently `2`) — the board PAYLOAD contract. Bump ONLY on a
  `data-fb-*` schema change; a pure presentation fix does not bump it. It names the published kit
  key (`board-widgets.v<N>.{js,css}`) and stamps every emitted event's `v`.
- `PROOF_TICKET_VERSION` (`proof-ticket.js`, currently `4`) — the ticket component, decoupled from
  the board kit. Bump on any component change; it names `proof-ticket.v<N>.js`. **`proof-ticket.css`
  rides this same version** — it is the component's presentation half, bound to it rather than
  versioned apart, so it publishes as `proof-ticket.v<N>.css`.
- `PROOF_THEME_VERSION` (`proof-theme.css`, currently `2`) — the token layer the whole system
  consumes, so it turns over on its own cadence. Names `proof-theme.v<N>.css`. Bump on a BREAKING
  token change (a rename or a removal downstream files reference) — never on a retint, since the
  whole point of a retint is that it reaches existing pages.
- `PROOF_BLOCKS_VERSION` (`proof-blocks.css`, currently `2`) — the `.mod` block catalog + decision
  layer + affordance rail. Names `proof-blocks.v<N>.css`. Bump when the CLASS CONTRACT breaks (a
  renamed or removed hook a composed page depends on), not for a purely visual change.
- `PROOF_CREATIVE_VERSION` (`proof-creative.css`, currently `1`) — the 25 creative layout patterns
  across six `.fam-*` families. Names `proof-creative.v<N>.css`. Bump when a pattern's CLASS
  CONTRACT breaks (a renamed class, a changed required wrapper, a family split), not for a visual
  tweak — a published page pins the version it was built against, so a bump leaves every v1 page
  rendering as it shipped while a non-breaking fix republishes v1 in place and reaches them all.
  Independent of `PROOF_BLOCKS_VERSION`: the block catalog is the decision layer, this is the
  page's geometry, and a page routinely links one without the other.
- `KIT_BEHAVIORS_VERSION` (`kit-behaviors.js`, currently `1`) — the decision-layer behavior. Names
  `kit-behaviors.v<N>.js`. Independent of `SCHEMA_VERSION` (it emits no payload) and of
  `proof-blocks` (style turns over separately). Bump when the `data-*` convention breaks.
- `BOARD_SWIPE_VERSION` (`board-swipe.js`, currently `1`) — the binary-decision drag accelerator
  (§2h). Names `board-swipe.v<N>.{js,css}`; **`board-swipe.css` rides this version** for the reason
  `proof-ticket.css` rides its js — the script injects no `<style>`, so the stylesheet is the
  component's only appearance and a page must never pair v2 behaviour with v1 selectors. Bump when
  the BINDING CONTRACT changes: which `data-fb-kind` values it claims, the two-input requirement, or
  the `html.board-swipe-on` / `.bswipe*` class contract a board's own CSS could reach for — not for
  a threshold or a colour. Deliberately **independent of `SCHEMA_VERSION`** even though it drives
  `board-widgets`' inputs: it emits no payload (it commits through `input.click()`, so the kit
  produces the event), and binding the two would force a payload bump for a gesture tweak and put
  pressure on precisely the cannot-drift pair.
- `PROOF_ICONS_VERSION` (declared in `proof-theme.css`, currently `1`) — the subsetted monochrome
  iconset. Names `proof-icons.v<n>.woff2`. It is the one constant that does NOT live in the file it
  versions, because a `.woff2` cannot carry one and the stylesheet's `@font-face` is the only thing
  that binds it. Bump it when the SUBSET changes (a codepoint added or dropped); re-cutting the
  same subset republishes v1 in place. The **source filename must carry the version** — the
  `@font-face src` is relative (`./proof-icons.v1.woff2`), so it resolves to this kit prefix when
  published and to the sibling file locally, with the bucket hardcoded nowhere; `publish-kit.sh`
  refuses to run if the declared version, the filename and the `src` disagree.
  **Deliberately NOT bound to `PROOF_THEME_VERSION`**, and adding the font did NOT bump it — for
  exactly the reason a retint does not. A theme bump mints v3, every published page stays pinned to
  v2, and the one property the iconset exists to deliver (reaching already-composed pages without
  recomposing them) is destroyed by the bump itself. An `@font-face` renames and removes no token,
  so the v2 class contract holds. **`KIT_BEHAVIORS_VERSION` does not move either** — its stated
  trigger is the `data-*` convention breaking, and the iconset introduces no attribute and no script.
- **Every one of these constants is declared IN its own file** (except the iconset's, above) and
  read by `publish-kit.sh` to mint the published key. A file that declares none publishes as `v1` with a warning and can never be
  bumped — so declare it rather than relying on the default.
- **Cannot-drift surface.** `board-widgets.js` / `board-widgets.css` are byte-compared against
  source by the publish integrity pass. Restyle via `board-warm-overrides.css` (the `--fb-*` seam)
  only — never by editing the versioned files. `proof-ticket.js` is behavior-only and ships no CSS;
  its styling lives solely in `proof-ticket.css` (a contract test asserts the JS carries no embedded
  stylesheet).

### Deep-dive docs

- [`skeletons/`](./skeletons/) — **the three composed starting artifacts** (§3.0). Copy one and
  fill it; this is where composing a page begins. `proof-page.skeleton.html` (evidence, the common
