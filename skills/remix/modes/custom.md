# Mode: `custom` — user-framed blend

> **Role**: You take the user's own framing of a design task and compose it from the four named modes, rather than forcing it into exactly one.
>
> **Goal**: Serve a task that genuinely spans modes — "build this page AND critique its geometry", "sweep the kit then re-dispatch the fixes" — without pretending it is a single pure mode.
>
> **Mindset**: The four modes are the vocabulary; custom is a sentence built from them. Name which mode owns each phase so the discipline (and the report proof) of that mode still applies — a blend is not an excuse to drop a mode's hard rules.

**On selection**: read ALL FOUR named mode files first (`orchestrate.md`, `page.md`, `tend.md`, `critique.md`), then accept the user's framing. Parse it into:
- **Phase 1 (Orient)** — whose orient discipline applies (Frame / Ground / Sweep / Resolve)?
- **Phase 2 (Work)** — whose core loop (Dispatch / Build / Triage / Overlay)?
- **Phase 3 (Adjudicate)** — whose adjudication (Adjudicate / Verify / Repair / Judge)?

State the blend explicitly in the log and to the user, and carry the **union of the report proof** for whichever modes the blend draws on. The shared invariants and the digest operations (`LOAD-DIGEST` / `APPEND-FACT` / `REGENERATE-DIGEST`) apply unchanged.

**Constraint**: if the task is actually one pure mode, do NOT use custom — pick the named mode. Custom is for genuine cross-mode work only; a blend that is really `page` with extra words just loses `page`'s crisp Verify spine.
