Weave many tickets through the build pipeline at once. `/loom` takes a batch of tickets, runs each as its own **thread** — triangulate → interrogate → build → scrutinize → snapshot → pr → council — and fans the threads out in parallel while a **conductor** (the parent) keeps them from colliding: it brokers who touches which files, relays messages between the build agents, detects deadlocks, and escalates the decisions that are genuinely yours. A live ledger tracks where every thread is and what documentation the weave has falsified; the session loops — you add threads, adjust a thread, or wrap up — and never rushes to close. When it does end, it writes an **inheritance**: the open rows, in a file a fresh conductor can read without the predecessor's log.

# /loom Protocol (The Conductor)

Execute §CMD_EXECUTE_SKILL_PHASES.

### What /loom is (and is not)

*   **It is** a **parallel-thread orchestrator**. A *thread* is one ticket walking the full chain; many threads run at once. `/loom` composes the building-block skills — it dispatches `/triangulate`, `/ticket`, `/communicate`, `/interrogate`, `/decide`, `/probe`, `/experiment`, `/build`, `/scrutinize`, `/revise`, `/snapshot`, `/pr`, `/council`, `/prove`, `/prove-explore`, `/graph`, `/groom`, `/inbox-post`, `/inbox-next`, `/ticket-search` — and its own work is the conducting: partitioning files, relaying agent messages, brokering conflicts, detecting deadlocks, escalating, keeping the ledger, reading the inheritance a predecessor left, and writing the one its successor reads.
*   **It is NOT** a builder or a writer. `/loom` never writes code, never posts to Linear, never touches git directly (`¶INV_LOOM_COMPOSED_WRITES`). Every mutation happens *inside* a composed skill under that skill's own confirm — `/snapshot` posts the status and commits, `/pr` opens the PR. The conductor orchestrates; the sections do the work.
*   **`/loom` vs `/coordinate`**: `/coordinate` is a persistent fleet monitor that answers standing worker questions. `/loom` is task-scoped — it weaves a specific batch of tickets through a specific pipeline and closes when the batch is done. It reuses coordinate-grade relay/escalation mechanics without being an immortal monitor.
*   **`/loom` vs `/do`**: `/do` is one free-form thread of work. `/loom` is *many* threads at once with a conductor between them.

### The thread (`¶INV_LOOM_THREAD_IS_A_TICKET`)

A **thread** = one ticket/task through the full chain:

> triangulate → interrogate → build → scrutinize → snapshot → pr → council

The **interactive** front (triangulate, interrogate) and the **decision** points (triage, snapshot/pr confirms, council findings) involve you or the conductor; the **autonomous** middle (build, scrutinize) runs as parallel background agents. Not every stage fires on every thread — `/triangulate`, `/snapshot`, `/pr`, and `/council` are **offered** per the Setup dispositions and the offer-don't-force rule (`§INV_OFFER_DONT_FORCE_SKILLS`) — while the **ticket-disposition ask, interrogation** (per its disposition), and **scrutinize** are **mandatory** (`¶INV_LOOM_MANDATORY_STEPS`), never turned off by the Autonomy disposition.

### Thread identity & agent naming (`¶INV_LOOM_AGENTS_NAMED_BY_THREAD`)

Every thread gets a **threadId**: the ticket key `ENG-XXXX` when there is one, else a short SCREAMING slug the conductor derives from the task — `FACTS`, `INTRODOC` (≤12 chars, `[A-Z0-9-]`, starting with a letter, never ending in a hyphen, digit-suffixed on collision: `FACTS`, `FACTS2`) — for a **winged** (un-ticketed) task. A meaningful slug beats a bare letter: `FACTS:build` tells you what the thread is; `A:build` doesn't. Every agent `/loom` spawns belongs to a thread at a stage — `ENG-3141:build`, `ENG-3141:scrutinize`, `FACTS:build`.

**The fleet/status view shows the sub-agent TYPE (`builder`, `writer`, …), not a label you set — so the threadId will NOT appear on its own. You MUST push it into what the agent emits, or the threads are indistinguishable** (the exact symptom this rule exists to prevent). Each of these is required:
*   **Lead the spawn `description` with the threadId in brackets** — `description: "[ENG-3141] build extract-totals"`, `"[FACTS] scrutinize parser"`. That bracketed prefix is what surfaces in the status row next to the `builder`/`writer` type.
*   **Lead the dispatch `prompt` with it too — as its literal first characters**, before any prose: `prompt: "[ENG-3141] You are thread ENG-3141 in a /loom weave. …"`. **The stall sweep below identifies a lane by matching a bracketed tag at the START of the dispatch prompt, so a brief that opens `You are thread ENG-3141…` is a lane the sweep cannot see** — and a sweep that sees no lanes reports no stale lanes, which reads as a clean weave. *(Measured: of this session's lanes whose brief named the session, every one carried its tag later in the prose and none at the head, so the sweep counted zero lanes while the weave ran. The description and the prompt are different strings, and the rule had only ever bound the first.)*
*   **Instruct the agent to prefix EVERY line it emits** — its status/progress reports, its shared-log entries, and its `SendMessage`s to the conductor — with `[<threadId>]`. A build agent's log entry reads `## [ENG-3141] tests green`, not `## tests green`. This is stated in `assets/LOOM_AGENT_DIRECTIONS.md`, which every agent's context pack carries.

This prefix is load-bearing: the ledger, the SendMessage relay, and the fleet view all tell threads apart by it. **Never spawn a loom agent whose `description` and output are not threadId-prefixed.** A winged thread's slug threadId **upgrades to the new `ENG-XXXX`** if a ticket is filed for it — the ticket create/update step runs *after* triangulate + interrogate, before the build, so the ticket carries the scoped understanding.

### The Setup dispositions

Asked once at Setup (`AskUserQuestion`, one per disposition — not `§CMD_SELECT_MODE` mode files). They parameterize the whole session and the escalation/relay reference file:

*   **Autonomy** — how much the conductor decides vs. asks: **Automagic** (proceed autonomously; auto-resolve conflicts where safe; escalate only on the hard floor) · **Careful** (escalate liberally; gate more) · **Allow agents to decide** (agents use judgment on when to escalate; conductor relays). **Autonomy tunes how much the conductor *resolves without asking* — it NEVER licenses skipping a mandatory step.** Automagic that skips the ticket-disposition ask, the interrogation, or the scrutinize agent is a bug, not autonomy (`¶INV_LOOM_MANDATORY_STEPS`).
*   **Council** — *when* `/council` runs, chosen once: **selective before PR** (a panel *before* the PR opens, only on threads you flag) · **auto after each PR** *(default — a panel on every thread once its PR is up)* · **none** *(not recommended)*. The timing is the whole distinction: *before PR* reviews the work before it's proposed; *after PR* reviews the proposed change.
*   **Interrogation** — how much `/interrogate` runs per thread: **Reasonable** (a few rounds → `/interrogate --depth quick`) · **Thorough** (→ `--depth deep`) · **None** (skip the interrogate stage).
*   **Detail importance** — how much granular detail matters, i.e. how hard over-zealous `/scrutinize`/`/council` findings get filtered before they reach you: **Low / ship-it** (downgrade nitpicks; only genuinely-blocking MUST-FIX surfaces; lean on recommended defaults) · **Balanced** *(default)* · **High / every detail** (surface everything for explicit decision). Low does NOT mean auto-accept — a blocking finding always surfaces.
*   **Run length** — how long the loom is expected to live: **Session** *(default — a batch woven in one sitting; lanes live as long as their thread)* · **Long-running** (hours, many waves, lanes queueing on a shared resource such as a browser or test queue). Long-running turns on the wake-cost rules below (`¶INV_LOOM_WAKES_ARE_THE_BILL`).
*   **Execution shape** — where lanes run, how their test runs are batched, and therefore which collision answer is live: **Worktree-per-lane** *(default — a lane gets its own git worktree and its own branch, runs only the tests its own change touches, and the conductor computes **no** file partition and brokers **no** claims; the lanes come back together at the wave boundary's merge)* · **One shared tree** (every lane writes into one checkout, so the partition and first-claim-wins brokering are live and a wave has nothing to merge). Never both — they are two answers to one question (`¶INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY`). Under **both** readings the full suite runs once per wave at the gate and never per lane (`¶INV_SUITE_ONCE_PER_WAVE`), which is why that half is stated below rather than offered here.

**The worktree default rests on a measurement of this machine, and it is the operator's to re-take** (`¶INV_LOOM_WORKTREE_DEFAULT_IS_MEASURED`). What makes a per-lane tree correct by construction is that the checkout's workspace links are **relative** symlinks, so a copied tree keeps its links inside itself instead of reaching back into the original. *Measured here 2026-10-23, on this machine*: a marker planted in the main checkout's `packages/shared/` was found through that checkout's own `node_modules` link and was **absent** through a real worktree's link, both links reading `../../packages/shared` — so the worktree's link resolves into the worktree's own package. 100 of 100 links in the primary monorepo read relative, 0 absolute; a constructed absolute link in the same invocation correctly read the original's marker through a copied tree, which is what makes that absence a reading rather than a mistyped path. Disk: 299GiB free, and a real worktree measured 524MiB without dependencies, so four lanes cost ~2.1GiB (~13.3GiB if each installs its own). **Choose *one shared tree* on a checkout where that does not hold** — absolute workspace links, or headroom that four trees would exhaust — and say so in the ledger. The reading is a property of a machine and a checkout, so it ages: `readlink` a workspace link and plant a marker rather than trusting this paragraph on an unfamiliar repository.

**The dial that arms `assets/__tests__/wave-integration.test.sh` has landed, so that harness is now red by design.** It holds cases asserting the wave boundary's merge half — unreachable while lanes share one tree — and it arms itself off this section. Armed with no integrated wave to read is a **failure, not a skip**: it says the mechanism is specified and unexercised, and it clears when a loom has actually integrated a wave and `WAVE_LOG` points at that loom's log. Run it in any change that touches this section.

**Long-running: wakes are the bill (`¶INV_LOOM_WAKES_ARE_THE_BILL`)**. A lane waiting on a background job makes no model calls; the cost is each WAKE. When a job returns after the prompt cache has expired (minutes), the lane re-reads its whole context at full price, so a lane hours old pays for its entire history on every wake, and a throttled queue turns every small run into another cold wake. Under Long-running:
*   **Live lanes = shared slots, and the slots are shared with every other loom** (`¶INV_SLOT_CAP_IS_GLOBAL`, below). Keep at most as many resource-using lanes live as the shared queue has slots, counted across all looms rather than within this one. Queued work waits unstarted (no context, no wakes), in the operator's priority order. Pause a lane that is only queueing (TaskStop; its transcript and LOG survive) rather than let it idle into the queue.
*   **Batch every run.** One queued run per wake, carrying every case, arm and control the lane needs next. A sequence of small runs is a sequence of cold wakes.
*   **Cap a lane's context.** Near ~150K tokens a lane writes its state to its LOG (done, measured with paths, the exact next step) and hands back. The conductor continues from the LOG with a fresh lane instead of resuming an hours-old one; one re-derivation is cheaper than every later wake at full size.
*   **A message to an idle lane is a wake.** The conductor relays to an idle lane only what changes its next step, batched; FYI-only notes wait for the lane's next natural wake or its hand-back.
*   **Name the rules in every brief** (they reach lanes through `assets/LOOM_AGENT_DIRECTIONS.md` § "Long-running sessions").

**Above-ceiling handling (`¶INV_LOOM_SIMPLIFY_DONT_SCARE`)**: when a technical fork would stall the operator, pose it as a **plain-language choice with a clear recommendation** and take the recommended default if they're unsure (noted in the ledger) — never raw technical internals. Escalate to a senior reviewer only for one-way doors.

### What a lane tests, and how many lanes may run (`¶INV_SUITE_ONCE_PER_WAVE`, `¶INV_SLOT_CAP_IS_GLOBAL`)

*This section and the Execution shape disposition are together what earlier notes call the **batching dial** — how a loom batches its test runs and its workers. The part a loom is asked is the disposition; the part below is fixed.*

**A lane runs the tests its own change touches. The full suite runs once, at the wave gate, against the assembled tree.** This is not a dial, because the alternative is measured rather than arguable. *Measured 2026-10-20, over 105 interleaved order-rotated runs*: the same command spread **10.7s–102.0s** (p50 21.5s, p90 58.1s), which made a lane re-running the whole suite at every step the dominant cost of a parallel run. The remedy is to stop running it per step, not to make it faster.

Three things follow, and each has already been tried the other way:
*   **Do not reduce concurrency to make the suite affordable.** *Every* reduction measured worse: disabling file parallelism came in at **311.1s against a 40.4s baseline**, nearly 8×. It is a falsified remedy, not an untried one.
*   **Do not take a single timing as a reading.** On a spread of 10.7s–102.0s one run says almost nothing; a judgement needs an interleaved, order-rotated distribution. A cache advertised as removing 57% of tracked time measured **inside the noise band** — an advertised figure is not a measurement.
*   **Targeted runs let a cross-cutting break reach the wave gate, where attributing it costs more. That is accepted deliberately.** The gate still catches it, and the per-lane alternative is the cost this rule exists to remove. Do not "fix" it by briefing lanes to run the whole suite.

**The worker cap is global across concurrent looms, not per loom.** Two looms that cannot see each other will together exceed any number each keeps to itself, and they contend over one test queue and one machine. So the count lives where a second loom can read it: **one file per loom under `~/.claude/engine/.loom-slots/`**, named for the loom (its session directory, slugified). Before dispatching a lane, the conductor **rewrites its own file and reads every file in the directory**; the global figure is the sum, and the cap is a refusal to dispatch past it.

*   **Each loom writes only its own file and reads everyone's**, which is what makes this race-free without a lock — one writer per file, so two conductors cannot interleave a read-modify-write on the same bytes.
*   A loom's file carries its **session directory**, its **live lane threadIds**, its **cap**, and a **heartbeat timestamp**, rewritten whenever the lane set changes.
*   **A file whose heartbeat is older than the staleness window is reported as stale and not counted.** A conductor ended by a context clear cannot delete its own file, so stale rows are the expected state rather than an error — and they are *named in the reading* rather than silently dropped, because a slot count that quietly discards rows cannot be told apart from one that found none.
*   **The file also carries the loom's work claims, and a claim outlives the lanes that made it.** A `claims=` line lists the tickets and paths this loom has taken, each `working` or `done-uncommitted`. **Claim on dispatch** (`engine loom-slots --claim <sessionDir> <ticket-or-path>...`), **mark done-uncommitted on hand-back** (`--claim-state <sessionDir> <item> done-uncommitted`), and **release on landing** (`--claim-state … landed`, or `--release` for work dropped unlanded). Before dispatching, read with `engine loom-slots --self <sessionDir> --dispatching <items>`: it prints every other loom's claims and warns, exiting 4, when one matches a ticket key or overlaps a path. A claim is reported however stale its row and however empty its lanes, because that is the case it exists for: *measured 2026-10-23*, a loom read another loom's row as stale with no live lanes and dispatched four lanes into seven tickets that loom had already finished and not yet committed. A conductor rewriting its file by hand keeps the `claims=` line.
*   **The directory is the whole mechanism**: no daemon, no lock service, nothing outside the engine's own tree. It follows the `.project-fetch/` and `.ticket-fetch/` precedent — a gitignored directory at the engine root holding one file per item — so it adds no infrastructure to install or keep running.
*   *Measured 2026-10-23, and the reason the count is stored rather than derived*: deriving it from live sessions was tried first and does not work here. `engine find-sessions.sh active` returned exactly one session and **did not include the live session it was run from**, because discovery is scoped to one session root — so a count derived from it cannot see the looms that cannot see each other, which is the entire requirement. `engine lane-stall` has the matching limit from the other side: it answers a lane's **state** and never its **reachability**, and was observed reporting lanes as `running` whose transcripts were 6,369 minutes old.

### The conductor's job (`¶INV_LOOM_CONDUCTOR_RELAYS`)

While threads run, the parent: runs a live message relay (agents `SendMessage` the parent to report progress); keeps the global slot file current and refuses to dispatch past the cap (`¶INV_SLOT_CAP_IS_GLOBAL`); maintains a *waiting-on* graph (a cycle = deadlock) and polls agent status (silence past a timeout → probe → escalate); and escalates per the hard floor. The rules live in `assets/LOOM_AGENT_DIRECTIONS.md`, fed **by reference** into every build agent's context pack.

**Whether it brokers files at all is the Execution shape disposition's answer, and a loom does exactly one of the two.** Under **one shared tree** it computes an up-front file partition, takes claims on out-of-partition files, and brokers conflicts **first-claim-wins** (`¶INV_LOOM_FIRST_CLAIM_WINS`, the later thread's conflicting step defers to the next wave). Under **worktree-per-lane** it computes **no** partition and brokers **no** claims — every lane owns its own tree, so there is nothing to allocate, and the collisions are found instead by the wave boundary's merge (`¶INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY`). Running both pays for prevention and detection and buys neither: the partition predicts collisions at allocation, the merge finds the ones that actually happened in the text.

**Hard escalation floor (`¶INV_LOOM_HARD_ESCALATION_FLOOR`)** — these ALWAYS reach you, even under Automagic: the **per-thread ticket-disposition question** (always asked before a thread builds — Automagic never suppresses it) · a **cyclic deadlock** the conductor can't break by deferral · a thread's **build failing after retries** · a **scrutinize MUST-FIX** needing a fix/skip/defer call · a **thread loopback** (council/scrutinize → interrogate or build).

### No rush to close (`¶INV_LOOM_NO_RUSH_TO_CLOSE`)

The loop gate defaults to **keep going**, never "shall we close?". A session ends only when you say so. Durability rides in Linear + git (via the composed `/snapshot` + `/pr`), so a `/loom` session can end cleanly with threads still mid-flight — the ledger records where each stands.

**Context pressure is not a licence to close.** Near **~150K tokens** — the same figure this file already gives a lane (`¶INV_LOOM_WAKES_ARE_THE_BILL`, *cap a lane's context*), one number for both sides so neither drifts — a conductor puts wrap-up **on the gate card as a recommendation carrying its reason**; the gate still defaults to keep-going, and your explicit choice is still the only thing that ends the session. **The figure governs when that card appears, and nothing else**: it is not a dehydration trigger, not a deadline, and not a reason to stop taking threads. Recommending early is harmless because it only adds a card you can decline. What the conductor may do unprompted is the opposite of closing: with an involuntary exit (an overflow dehydration) imminent, write its state and its hand-over **first**, because riding into a dehydration unprepared loses the ledger, and that is not an end you chose either. The threshold is numeric rather than a feel, since an unnumbered one is discretion wearing a rule's clothes — which is what `¶INV_CONTEXT_BUDGET` exists to stop.

### Dehydration and rehydration — what a conductor owes a successor (`¶INV_LOOM_HANDS_OVER_A_PATH_NOT_AN_ID`)

**For a conductor writing a hand-over, and for the fresh context that reads it.** `§CMD_DEHYDRATE` owns the payload and the restart; `§CMD_RESUME_SESSION` owns the resume algorithm; both apply unchanged. What they do not know is what a *conductor* holds — a ledger, live lanes, brokered file holds, published boards and owed docs — so this section adds only that content and the forms that are forbidden in it.

**The rows go in the inheritance file, not in the payload's prose.** Write `LOOM_INHERITANCE.md` at the sessions root (`assets/TEMPLATE_LOOM_INHERITANCE.md`, whose *Where it lives* section is the normative address) and list its **absolute path** in `requiredFiles`: the payload is capped and its prose is not addressable, while a row is. Carry every open row — threads, boards with their `docId`, docs owed, rules owed, open operator claims, un-acked seat handovers, and the standing arrangements that die on their own; the file carries one block per kind, in the order the hand-over receipt counts them. **An open row may be passed on; it may never be dropped** (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`).

**The forbidden forms.** Each is a brief that read as executable and was not, measured on a hand-over in this skill's own history. The redirect is what to write instead, because an agent routes around a prohibition and acts on a replacement.

*   ⛔ **An agent id is never a hand-over handle. Hand over the lane's LOG PATH.** A context clear ends every in-process subagent, so *"resume lane X by name"* is structurally unavailable on arrival — not slow, not idle, gone; `SendMessage` to the id answers *no transcript found*. The lane's `builds/<slug>_BUILD_LOG.md` survives, so the brief names it and the successor dispatches a FRESH lane with that log in its context pack. Resuming by name is a live-context move and belongs nowhere in a restart brief. **`engine lane-stall "<sessionDir>"` closes each row with that path, as `logpath=`** — read it there rather than deriving it, take it as everything after `logpath=` to end of line (`sed 's/.*logpath=//'`, never `awk '{print $NF}'`, since a shared-drive session path holds spaces), treat the `agent=` transcript beside it as diagnostic only, and carry `logpath=none` as the reading it is: a lane with no log is a different hand-over, not a lane to point at its transcript instead.
*   ⛔ **A discriminator both states share is not a discriminator.** Name the field that actually differs, and show it differing in the same invocation. *(A brief that said to print the publish endpoint **and bucket** was satisfied by the wrong store: both stores are named `proofs` and only the port separates them.)*
*   ⛔ **A claim is scoped to the tool class it was measured on, and says so.** *"Writes still worked"* and *"the gate is open"* are different statements; a gate's allowlist admits some tool classes and not others, so a success in one class establishes nothing about another. Write the class into the claim.
*   ⛔ **A lane's log is not a record of what it did after it stopped logging.** Read the artifact before briefing its state — a lane can land files after its last entry, and a brief that infers *unwritten* from a closed log sends the next lane to redo work that exists. Where the directory is untracked git cannot correct you either: `git status --porcelain` on an untracked path prints nothing and exits 0 whatever it holds, so establish TRACKED with `git ls-files --error-unmatch` before reading any path as clean.
*   ⛔ **A standing arrangement is named with what blocks on its absence, never as a note that it exists.** A background watcher re-armed at the maximum two-hour timeout dies on a session that outlives it, and the write gate then blocks the next `Agent` dispatch until it is re-armed — so the row names the ceiling, the tool class that blocks, and the re-arm command. On a long session this is a standing cost, not an incident, so the row says how many ceilings it has already crossed. **Name the classes that stayed ALLOWED alongside the ones that block**, because a claim is scoped to the tool class it was measured on and a couple of successful writes in a passing class is how a dead watcher gets recorded as harmless.
*   ⛔ **A restore instruction that contradicts standing advice carries the contradiction and whose authority settled it.** Otherwise the successor reads *"re-arm it"*, meets the advice against restarting a watcher already at the longest timeout allowed, and re-derives the override from scratch — the exact re-derivation this file exists to prevent. The conflict here is structural rather than anyone's error: a watcher whose maximum lifetime is shorter than the session's creates a **mandatory periodic re-arm** that the harness advises against, so the row names which rule was judged the authority and on what grounds. A judgement taken repeatedly and never written down is a judgement the next context cannot inherit.
*   ⛔ **Every command a brief carries is absolute.** A relative `engine log` path is now **refused** when it would land outside the live session — the guard asks `session.sh find` which session is live, compares the physical paths, prints the corrected absolute path and exits 1 without writing. It does not make a relative command safe to carry: the guard **fails open** when session discovery is unavailable, waives on `ENGINE_LOG_ALLOW_FOREIGN_SESSION=1`, and only fires on a path with a `sessions/` segment, so every other relative form still resolves against whatever CWD the successor happens to hold.
*   ⛔ **A sessions root is never typed from a convention. Compute it, and carry the absolute path.** The root is the parent of the active session directory (`engine session find`; `sessionDir` in the hand-over payload), which agrees with the engine's `resolve_sessions_dir` whenever one root is in play — and more than one is, under a symlinked `sessions/`, a shared-drive artifact root, or a `$WORKSPACE` set for one process and not another, where a session directory of the same name can hold different content at each root. A root a successor cannot compute is an address it cannot read, so the brief carries the inheritance file's absolute path and the template's *Where it lives* section rules the read order.
*   **Every figure in the brief carries its timestamp and is marked re-measure.** A hand-over's facts age between the write and the read, and the brief cannot say which ones moved. Saying so near the top is what makes the successor's first act a measurement rather than an action.

**Rehydration — the successor's first acts, before working any row.** Run `§CMD_RESUME_SESSION`, then take **Phase 0's inheritance intake** — the same step, reached with a payload in hand rather than cold, so there is one mechanism and not two. Before acting:
*   **Re-measure what the brief marked re-measure**, and first among them whether each live lane is addressable at all — that reading decides whether the next move is a resume or a fresh dispatch.
*   **Claim rows and say which you left.** Several looms may share the inheritance file, so write the `## ♻️ Inheritance claimed` entry naming the rows taken, the rows left to another owner, and the readings that had moved.
*   **Refuse a row carrying `UNKNOWN` in a field you need to act**, and report it. Acting on a partial row reproduces the loss the file exists to prevent, with no gap left where it used to be.
*   **A falsified brief claim is recorded as a correction, not worked around silently** — and the refutation is checked before it is relayed, to the same standard as the claim it refutes. A refutation generalised from one tool class is how a correct brief gets called wrong.

### Phase shape

`/loom` is `Setup → Loom → Synthesis` — three phases, like `/do`. Intake and per-thread interrogation are **not** upfront phases: they happen **inside the Loom body every time you add a thread**, because you add threads throughout the session, not all at once. Synthesis is reached only by an **explicit** "wrap up" choice at the loop gate (`¶INV_LOOM_NO_RUSH_TO_CLOSE`).

## 0. Setup

§CMD_REPORT_INTENT:
> 0: Setting up a loom over ___. Trigger: ___.
> Focus: session activation, loading the in-scope tickets, choosing the dispositions.
> Not: building or spawning agents — setup only.

§CMD_EXECUTE_PHASE_STEPS(0.0.*)

*   **[MANDATORY] Read the inheritance before the batch.** A predecessor's open rows arrive as a *file*, not as context, so a conductor that goes straight to the batch has dropped them — and nothing in the tree makes a noise about it. This is the only pass that can see **the operator's answers that arrived after the predecessor composed its rows**, which is what makes it a distinct job rather than a repeat of the hand-over's own sweep. It runs on every start, cold or resumed; the resume path (`§CMD_RESUME_SESSION`, *Rehydration* above) reaches the same intake with a payload in hand, and the payload's absolute path wins over the convention when both are available.
    *   **Resolve the file** per `assets/TEMPLATE_LOOM_INHERITANCE.md`'s *Where it lives* section — compute the root, try the candidates in order, report a copy found at more than one root instead of merging.
    *   **No file at any candidate root** → say so and proceed. A first loom in a tree inherits nothing, and that reading written down is the result; silence is not.
    *   **A file** → **re-measure every reading it marked re-measure before acting on any row**, and first among them whether each live lane is addressable at all, because that decides resume-or-redispatch. Then **claim** the rows whose subject this session is taking, **leave** the rest to their `owner`, and **refuse a row carrying `UNKNOWN` in a field you need to act** — report that row rather than acting on the rest of it (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`).
    *   **Write the `## ♻️ Inheritance claimed` entry** — rows claimed, rows left, roots searched, which readings had moved, rows refused. That entry IS the `inheritanceRead` proof, and like `docRegister` it clears on an empty result: a loom that inherited nothing passes by recording the no-file reading, never by skipping the step (`¶INV_LOOM_MANDATORY_STEPS`).
    *   **A claimed row enters the weave as a thread**, through the add-a-thread flow — including its adjacency assessment, which is where several rows on one subject collapse into one thread. **Do not hand the rows to `/groom` to cluster**: its drain is welded to an inbox adapter, so it cannot take an arbitrary pile as input, and a step that assumes otherwise silently loses every row. This step reads, claims, refuses and records; it does not cluster.
*   **Scope**: Understand the batch of tickets/tasks in play — the inherited rows included, since one of them can change what else is worth loading. Load the candidates via `§CMD_INGEST_CONTEXT_BEFORE_WORK` (the `SRC_RELATED_TICKETS` + any `contextPaths` name them).
*   **Ask the dispositions** (`AskUserQuestion`, one question per disposition — Autonomy · Council · Interrogation · Detail importance · Run length · Execution shape; the tool takes four questions per call, so Run length and Execution shape go in a second call). Record the choices as the `dispositions` proof and echo them into the ledger header — **Execution shape** has its own ledger field, because the wave boundary's merge step and the file-brokering job are both conditional on it. These parameterize every downstream stage and the escalation/relay reference file.
*   **[MANDATORY] Open this loom's slot file and read every other loom's** (`§INV_SLOT_CAP_IS_GLOBAL`). Write `~/.claude/engine/.loom-slots/<session-dir slugified>.slots` with this loom's session directory, its cap, an empty lane set and a fresh heartbeat; then read the rest of the directory and report the global figure — live lanes, and **how many rows were stale** rather than dropping them. A loom that cannot read the directory reports that reading and dispatches **one** lane at a time until it can, rather than assuming it is alone: a loom that believes it holds the whole budget is the failure this file exists to prevent.
*   **[MANDATORY] Record the session branch — its NAME and its sha** (`git branch --show-current` and `git rev-parse HEAD`) into the ledger header's `▶️ Loom Opened` block. That is the `sessionBranch` proof, and it is taken **here** rather than at the wave boundary that uses it because it is not reconstructable later: under worktree-per-lane the conductor's tree is not any lane's, so a base read at integration time is a base guessed (`§INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY`). A detached HEAD or a tree with no branch is **recorded as that reading** and reported, never replaced with a plausible name — a loom whose base is unknown does not integrate.

*Phase 0 proceeds to Phase 1 — **transition without a gate menu: pipe Setup's proof to `engine session phase` and move.** `gate: false` removes the menu, never the transition. A conductor that keeps working in Setup is indistinguishable from one in the Loom body until somebody reads the status line.*

## 1. Loom
*The main body — the persistent parallel weave. Adding a thread, interrogating it, building, conducting, and closing a thread all happen here.*

§CMD_REPORT_INTENT:
> 1: Weaving threads in parallel. Autonomy: ___. Council: ___. Interrogation: ___.
> Focus: add threads (ticket/triangulate/interrogate/write surface), fan out named builds, relay, scrutinize, triage, integrate each wave, offer snapshot/pr, council per policy, keep the ledger live.
> Not: writing Linear/git directly, and never closing on its own — mutations go through composed skills; Synthesis is an explicit choice.

§CMD_EXECUTE_PHASE_STEPS(1.0.*)

This phase is the whole working body. It runs a persistent loop: you **add threads** (each scoped interactively as it enters, while other threads' builds run in the background), the conductor **weaves** them, and the loop ends only when you explicitly choose to wrap up (`¶INV_LOOM_NO_RUSH_TO_CLOSE`).

### Adding a thread (whenever you add one — not a batch upfront)
A background build agent cannot ask you questions, so a new thread is scoped here on the main thread, while other threads keep building. **Each step is marked `[MANDATORY]` (always happens — no Autonomy disposition turns it off) or `[OFFERED]` (you or the conductor may skip).** Autonomy tunes how much the conductor *resolves without asking*; it never decides *which steps run* (`¶INV_LOOM_MANDATORY_STEPS`).

**Adding several at once** — before scoping them, assess adjacency:
*   **Very adjacent / near-duplicative** → **`[OFFERED]` group them into ONE thread** (`§INV_OFFER_DONT_FORCE_SKILLS`) instead of parallel threads — one build, one PR. Grouping collapses them; you decide.
*   **A topic from `/groom` is already grouped — `[MANDATORY]` one topic is one thread.** A groom pass hands the conductor topics rather than items, each with its signals, its disposition and any ticket keys. **When a topic carries several tickets they ride that one thread** — never a thread per ticket. This is the grouping rule above arriving pre-decided, so the conductor adopts it rather than re-deriving it, and work stays batched by subject instead of filling the loom with near-identical lanes.
*   **Distinct but simultaneous** → keep separate threads, but **batch their interrogation**: run the interrogation forks in shared rounds (≤4 questions spanning threads) rather than one `/interrogate` per thread, so each thread's answers inform the others (fewer round-trips).

1.  **[MANDATORY] Assign a threadId** — `ENG-XXXX`, or a conductor-derived SCREAMING slug for a winged task (≤12 chars `[A-Z0-9-]`, starting with a letter, never ending in a hyphen, digit-suffixed on collision: `FACTS`, `FACTS2`). Open/append its ledger row (`TEMPLATE_LOOM_LOG.md`).
2.  **[OFFERED] `/triangulate`** (`§INV_OFFER_DONT_FORCE_SKILLS`) — `Skill(triangulate, "<ticket>")` to validate real/ripe before investing a build. A not-ripe result parks the thread. Skip for an already-triaged ticket. **Pass no `--mode inbox` here**: a ticket is not an intake drop, so the run stays silent and hands the finding back to the conductor rather than commenting on the ticket — `/snapshot` owns what reaches Linear.
3.  **[MANDATORY per the Interrogation disposition] Interrogate** — `Reasonable` → `Skill(interrogate, "<ticket> --depth quick")`; `Thorough` → `--depth deep`; `None` → skip. The **disposition** decides whether it runs — the conductor may NOT skip it when the disposition is Reasonable/Thorough, and may NOT substitute an inline chat exchange for the dispatched `/interrogate`. The digest (`builds/<slug>_INTERROGATE.md`) is the scope half of the thread's build context pack.
4.  **[OFFERED] De-risk the scope** (`§INV_OFFER_DONT_FORCE_SKILLS`) — when interrogation surfaced an **open question** or an **unproven approach**, de-risk before investing a build. Most threads skip this; it's for the ones with a real unknown. Distinct from triangulate (which validates the *problem*): these de-risk the *solution*.
    *   **`/probe`** — a directed, read-only investigation for an open question. `Skill(probe, "<the question>")` sweeps code / DB / tickets and returns an answer-first report. Always safe — it writes nothing, so it needs no partition.
    *   **`/experiment`** — a feasibility spike to prove an approach works. `Skill(experiment, "<hypothesis>")` writes + runs code in-tree and returns a proved / disproved / inconclusive verdict. **It touches files while other threads build in parallel, so it MUST respect the partition** — claim its files first (or run in an isolated worktree), never write another thread's territory (`§INV_NO_DESTRUCTIVE_GIT`, first-claim-wins). Run it here, *before* this thread's partition is finalized (step 6), so its kept files fold into the thread's own set.
    The probe report / experiment verdict joins the thread's build context pack alongside the interrogation digest, and can reshape the ticket disposition (next) and the scope.
5.  **[MANDATORY — always ASK] Ticket disposition** (`AskUserQuestion`, composed-writes only) — asked **here, after triangulate + interrogate**, so the ticket reflects the scoped understanding before the build. **Read the destination before recording the disposition** (`§INV_A_DISPOSITION_OPENS_ITS_DESTINATION`, defined in `/groom`'s constraints) — an update names the ticket, a create names the project and whatever its prior-work sweep found, and *keep as-is* names the ticket it is leaving alone. Read its own text, then record: **fetching the ticket is not reading its body, and opening the project is not reading its open set.** What the condition rests on, with no count in it: **one seat, one grooming pass, eight dispositions, and one body actually read.** That seat fetched all eight tickets it disposed and read status and relations rather than bodies, so a predicate keyed on having opened the thing would have passed on every one of them; the single body later deep-read had gained a merge, a landing order and a wave PR the day before, which was most of what that ticket was about to be re-scoped to carry. **A count stood here and was withdrawn at its source**: it read *five of six*, and its author, asked for the eight dispositions themselves, re-read their own log and reported the figure as an inference from the one demonstrated case rather than six verified ones. The mechanism is what binds and it stands on that one case — a call returning status and relations has opened nothing that matters. **What would settle the general claim**: a second seat's independent pass over its own dispositions, which nobody has run. Do not restore a count here without it. **A figure in a brief says whether it was run or relayed** — the seat that withdrew this one had three of its own relayed figures falsified by its own lanes inside an hour, and now marks every figure it hands on as `ran` or `relayed`. Relayed is not a warning; it says the reading is somebody else's and has not been repeated. **One body read per disposition is the price. That it does not amortise across a thread is an argument rather than a measurement** — the one measured thing is that all eight of those destinations were tracker rows, which cost little wall-clock and a lot of context, and a destination that is a file or another seat's ground is unmeasured on that axis. A disposition naming no destination escapes the condition, and naming a destination is not the same as routing to one. **Record what you read, and how deep** — one line per disposition in the thread's own record, naming the destination and whether you read its text, its row only, or nothing. That line is the whole cost, and what it buys works backwards rather than forwards: it is the only part of this that catches a miss after the fact, because the counter-case seat's own record would have read `read: status + relations` for anyone auditing that pass later, where re-reading the draft caught nothing. **The question ALWAYS reaches you** (its answer may be "keep as-is"); it is never skipped by proximity to the offered steps, and Automagic never suppresses it. Three ways:
    *   **Create a new ticket** — `Skill(ticket, "<task>")` for a winged task, framed from the findings; on creation, upgrade the slug threadId to the new `ENG-XXXX`.
    *   **Update the existing ticket** — post the scoped understanding via `/snapshot` or `/communicate`, so it's current before the build.
    *   **Keep it here as-is** — no ticket action; runs against its current ticket, or un-ticketed with its slug.
    Every write happens inside the composed skill under its own confirm (`¶INV_LOOM_COMPOSED_WRITES`).
6.  **[MANDATORY — and the Execution shape disposition decides WHICH of the two it is] Give the thread its write surface.** Under **worktree-per-lane**: create its worktree and its branch, hand it both, and compute **no** partition — overlap is not predicted here, it is found by the wave boundary's merge. Under **one shared tree**: assign a disjoint file set (the `§CMD_PARALLEL_HANDOFF` non-intersection proof) against the currently-running threads; on overlap the thread queues until the conflicting files free (first-claim-wins). **Dispatching a thread with neither is the failure this step exists to prevent** — a lane told nothing about where it may write defaults to the shared tree it can see.
7.  **[MANDATORY] Fan out its build — a concurrent /build-grade AGENT** — spawn a background builder **agent** (Agent/Task tool) with its `description` **leading with the bracketed threadId** (`description: "[ENG-3141] build extract-totals"`) and a full `/build`-grade context pack (goal + interrogation digest + file partition + hard gates + scope guard + `assets/LOOM_AGENT_DIRECTIONS.md` by reference, which tells it to prefix every line with `[<threadId>]`). **Never `Skill(build)`: the Skill tool is sequential, so a `Skill(build)` call blocks the loop and serializes the very parallelism loom exists for. Loom is carved OUT of `§INV_PREFER_BUILD_SCRUTINIZE`'s "prefer /build" wording — its fan-out is /build-*grade agents* run concurrently, not the /build *skill* in-line.**

### Conducting (continuous, while builds run)
*   **Relay** agent `SendMessage`s: maintain the *waiting-on* graph (a cycle = deadlock); poll agent status (silence past a timeout → probe); keep this loom's slot file current as lanes start and land (`¶INV_SLOT_CAP_IS_GLOBAL`). Escalate per the **hard floor**. **Under one shared tree the relay also brokers files** — grant out-of-partition claims when unclaimed, conflicts **first-claim-wins** (loser's step defers); **under worktree-per-lane there are no claims to grant**, and a lane asking for one is a lane whose brief did not reach it.
    *   **The waiting-on graph is ROWED, not remembered (`¶INV_LOOM_WAITING_IS_ROWED`)** — every block a lane reports opens a `## 📡 Relay / Conflict` entry carrying its `Waiting on` in the lane's own words (`assets/LOOM_AGENT_DIRECTIONS.md` § Progress reporting states that grammar), its `Since`, and its resolution; the waiting thread's `🧵 Ledger` `status` cell carries the one-line glance. A graph held only in the conductor's context is a graph a context clear deletes, leaving a cycle to be rediscovered from nothing — and nothing durable then says **why** a lane is waiting until a hand-over, which is exactly the moment it is hardest to reconstruct.
    *   **Instrument the silence-past-a-timeout poll with `engine lane-stall` — do not write a second detector (`¶INV_LOOM_STALL_IS_SWEPT_NOT_SENSED`).** `engine lane-stall "<sessionDir>" [--minutes N]` (default 30) lists every lane that is **not done** whose freshest signal is older than the threshold, reporting per lane the minutes since its transcript last changed, the minutes since its last `## … [TAG] …` heading in the session log, and a **state**: `done` (handed back) · `parked` (its turn ended with no hand-back) · `running`. It **exits 3 when at least one lane is stale** and 0 when none, and it is read-only — it never touches a lane, a transcript or the log. `--all` shows every lane including the fresh ones, which is how you tell *no lane is stale* from *no lane was seen*.
        *   **Run it at two moments, and the second is the one that matters.** At each loop gate, as a cadence (below) — and **before the conductor settles in to wait on live lanes**, because the gate fires on a *unit of progress* and a weave where nothing lands never reaches a gate. A gate-only sweep is absent in precisely the case it exists for.
        *   **Why an external reading rather than better reporting.** Every other progress signal in this weave is **self-reported by the lane** — a `SendMessage`, a `[TAG]` log heading, a `SubagentHandback`. A lane that has hung emits none of them, and an absence is indistinguishable from quiet work. The sweep reads the filesystem, so it sees a lane that cannot speak.
        *   **`parked` is the reading to act on.** A lane whose turn ended with no hand-back chose nothing and recorded nothing — it is the shape an operator sees as an agent hung up waiting. Row it under `## 🅿️ Parked` as `stopped without handing back`, **distinct from a thread the conductor parked for a reason**, with the lane's **LOG PATH** (its only surviving handle) and the next move. Read that log before briefing its state: a lane can land files after its last entry.
        *   **It reports STATE, never reachability.** A dead lane's transcript stays on disk, so the sweep reads it `parked`, not gone — so it does not answer Phase 0's *"is this lane addressable at all"*, which only a `SendMessage` attempt settles. Treating one as the other is a discriminator both states share.
        *   **A `0 lanes seen` result is not a clean weave** and is never reported as one. Re-run with `--all` and reconcile against the `🧵 Ledger`'s live rows; a count below the ledger's means the sweep is not seeing this weave's lanes, most likely because a brief did not lead its prompt with `[<threadId>]`.
    *   **Escalate a deadlock as a DRAWN graph, not as prose** — `Skill(graph, "<the waiting-on edges>")` renders the cycle in the engine's one ASCII diagram vocabulary (`§CMD_FLOWGRAPH`), which is what makes a cycle legible at the moment the operator has to break it. **Instead of** a sentence naming who waits on whom, which is the least readable thing this skill asks anyone to parse. It fires on the cycle rather than on a menu pick — the deadlock is already a hard-floor escalation, so the drawing rides that escalation and costs the gate no slot.
*   **[MANDATORY] Scrutinize on land** — as each thread's build finishes, spawn a concurrent **scrutinize AGENT** (`description: "[<threadId>] scrutinize …"`, threadId-prefixed like the build) — a `/scrutinize`-grade critique of its Build Report — **never `Skill(scrutinize)` (it serializes the critiques)**. Scrutinize ALWAYS runs; the **Detail-importance** disposition filters which findings reach you, never *whether* the critique happens (`¶INV_LOOM_MANDATORY_STEPS`). Run a combined triage across threads (fix / skip / defer), then dispatch fixers.
*   **Offer `/snapshot` then `/pr`** per landed thread (`§INV_OFFER_DONT_FORCE_SKILLS`, composed-writes) — `/snapshot` posts status + commits the reviewed files; `/pr` opens the PR. Advance the ledger.
    *   **Where lanes run in their own trees, `/pr` moves to the wave boundary and `/snapshot` does not** (`§INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY`). The per-thread `/snapshot` is what produces the branch and the sha the merge consumes, so it keeps its place; a per-thread `/pr` would propose the per-lane pull request this loom integrates specifically to avoid. One PR per assembled wave, offered there.
*   **Council per policy** — run `/council` per the **Council disposition**: *auto after each PR* runs a panel once a thread's PR is up; *selective before PR* runs one **before** the PR opens, only on threads you flag; *none* skips it. A council MUST-FIX is a **thread loopback** — escalate, and on confirm loop that thread back to interrogate or build (for a before-PR panel, that loopback happens before the PR ever opens).
*   **Closing snapshot before the proof** — after council settles (and after any PR-review / CI-gate fix cycle it triggered), **run a final `/snapshot`** on the thread. The earlier snapshot committed the reviewed *build* and opened the PR; this one **commits everything that landed since** — the council MUST-FIX fixes, the PR-review and gate fixes — and **advances the ticket to `In Review`** (the PR is up and reviewed; loom does not merge, so In Review is the state a thread lands on). It's the thread's closing checkpoint: `/snapshot` commits the thread's files scoped + gated on green, posts a closing comment, and flips the status (non-regressing) — all under its own batch confirm (`¶INV_LOOM_COMPOSED_WRITES`). Run it **before** the auto-proof, so the proof reflects the fully-committed, review-settled state and links the final commit.
*   **⭐ Prove EVERY thread at its end, while its context is still hot (`¶INV_LOOM_EVERY_THREAD_PROVES`)** — the moment a thread finishes its work, and **before its agent is left to go cold**, compile what it found into a shareable visual proof at a public URL. **Every thread, not only the ones that reach a PR**: a read-only investigation, a measurement lane, a repair, a page correction, a scoping sweep — each ends with a proof page. A lane that shipped proves the change; a lane that only investigated proves **what it established and how it knows**. **The timing IS the rule.** A finished lane still holds its screenshots, its raw command output, the hypotheses it rejected and the reason each fell — none of which survives its context ending, and none of which a later reader can reconstruct from the written report alone. A proof compiled a day later is a summary of a report; a proof compiled while the context is hot is evidence. So the proof is produced **BY the thread as its last act** — put it in the brief when you dispatch, and for a lane that has already returned, **resume it by name** (`SendMessage`) rather than dispatching a fresh agent that would have to re-derive everything it knew. Where a thread genuinely has nothing renderable, `/prove` self-skips and the ledger records **`no renderable evidence`** — an explicit skip, never a silent one. It runs **without a gate**: the proof skills are read-only — they change no code, commit nothing, file nothing — so there is nothing to confirm. Invoke as `Skill(<variant>, "<slug> — problem: <what was broken or unknown>; solved: <what was established or shipped + how it is verified>")`, the variant chosen by the shape test below. They trust the trail and never re-investigate. **Record the returned proof URL on the thread's ledger row** — a thread with no URL and no exemption note is an incomplete thread.
    *   **🪞 A pass the conductor runs in its OWN context is a thread, and proves like one.** The rule binds the *work*, not the *actor* — so a ticket filed inline, a grooming pass, a decision pass, a document published, a measurement taken on the main thread each end in a page, exactly as a dispatched lane does. **The conductor's context is the hottest one in the loom and it is the one place nothing was being proved**: measured on a single evening, every lane whose brief carried the instruction produced a page and everything run inline produced none — a ticket filed with a control on every zero, a grooming pass whose entire output was a controlled measurement, and a document verified by content among them. Dispatching is what made the rule fire, which made the rule a property of dispatch rather than of finishing. A conductor holding its own finished finding **resumes nothing and dispatches nothing** — it invokes the skill itself, in place, before moving to the next unit.
    *   **Two exemptions, and nothing else.** Each is recorded on the row as `exempt — <clause> — <what the thread's whole output was>`; a bare `exempt` is an unworked row and `proofPages` does not clear while one stands, the same shape as a bare `open` on a board row. **It is the conductor's call, never the lane's** — a lane may report that it believes a clause applies and may not act on that belief.
        *   **The SUBJECT would be refused as a ticket's subject.** One discriminator, two uses: `/ticket` §3 step 0 refuses a **guard or check**, **tooling**, **a seat or ownership question**, and **agent-coordination machinery** as ticket subjects, and `¶INV_LOOM_HANDBOOK_BEFORE_FILING` already binds a conductor to that list. A thread whose subject sits in it earns no page either — a lint, a CI job, a hook, gate plumbing, a worktree helper, who owns which file. **The carve-out travels with the list**: in `Product: Orchestration` the orchestration machinery IS the domain work, so a thread on loom, groom, decide, direct, intake or the decision transport is an ordinary subject there and proves. Carrying the carve-out is what stops this clause deleting its own evidence — without it, the lanes whose pages are the thing that works tonight would all be exempt. **And the carve-out stays a project, never a category**: "engine work" and "coordination machinery" buy no page and dodge none, because an exemption any thread can claim by renaming its work is not an exemption.
        *   **NOTHING WAS ESTABLISHED.** Not that the change was small — **size is not the test and may not be cited as one**. The test is whether the thread can name, in one sentence, something a reader did not know before it ran: a figure with its denominator, a zero with the control that fired, a mechanism that was wrong and now is not, or a verdict another agent would act on. A one-character edit that corrected a false belief proves; a large refactor that established nothing does not. **A thread that wrote outward is never exempt under this clause** — a ticket filed, a tracker comment posted, a document published, a commit carrying a corrected mechanism all mean somebody will act on it, so the finding exists whatever the diff size.
    *   **🎚️ Pick the VARIANT by the shape of the answer, and reach past the default.** `/prove` shows one settled claim · `/prove-explore` explains a settled answer too plural to compress, a territory whose sub-questions the brief can name before dispatch · `/prove-visionary` proposes where the answer is NOT settled and someone must choose, options-without-a-recommendation included. **Route by the shape of the answer, never the size of the subject.** The conductor owns this fork because only `/prove-explore` names its siblings — `/prove` names none and silently absorbs a misroute — and because every variant's triggers are written as a human's opening request, so none of them fires at thread-close and picking by the nearest-sounding trigger returns `/prove` every time. Measured: nine consecutive briefs in one session named `Skill(prove, …)` and neither sibling was reached for once. **Name the variant in the dispatch brief** rather than leaving the lane to default, and a closed finding with nothing renderable goes to `/prove-explore` with bare sections before `no renderable evidence` is even considered.
*   **📚 Feed the standing documentation lane — batched, on a landed thread (`¶INV_LOOM_DOC_LANE_IS_STANDING_AND_BATCHED`)** — one doc lane lives for the session and the conductor feeds it; it is not re-spawned per thread. **The register, not the lane's context, is what survives**: the conductor keeps the `## 📚 Docs owed` rows and the lane reads and updates them, because a context clear ends every in-process lane while a written row does not. The feeding is bound by these rules:
    *   **Batched on a landed thread, never per change-event.** A wake is the bill (`¶INV_LOOM_WAKES_ARE_THE_BILL`), and a loom landing a thread every few minutes would otherwise wake the lane constantly. One feed per landed thread, carrying that thread's whole claim surface: its Build Report's `## Files touched (authoritative)`, the subjects it changed, and the open `📚 Docs owed` rows it bears on. A thread that changed no documented behaviour is fed as a row saying so, not as a wake.
    *   **The lane runs `/revise`, which is claim-scoped.** `Skill(revise, "<the landed change>")` — it locates the sentences the change falsified, repairs those, and returns a Revise Report. Its `## Register rows owed` is where the conductor's next rows come from. The lane is **forbidden** the tree's index, pages the change does not reach, tree-wide count audits, and inventing a home for an undocumented change — those are `/document`'s, because a diff cannot scope the tree, and the lane rows them back rather than taking them.
    *   **The register row is the state of record.** A row closes as `revised — <report path>`, or states what the lane found that leaves it open; a bare `open` is an unworked row. **Open the rows as the thread lands** rather than at Synthesis: a register written only at the end is lost by exactly the exit this feeding exists to survive.
*   **⚖️ Row a rule a lane could not land, and rule on it (`¶INV_A_RULE_OWED_HAS_AN_OWNER`)** — the shared directive files sit outside every lane's partition, so a lane that learns a durable rule writes a `## Rule owed` block and emits a hand-back line, `rule owed → <file>: <clause>`. That invariant names **the coordinator** as the party who acts on it, and this is where that happens: on a hand-back carrying such a line, open a `## ⚖️ Rules owed` row as the thread lands, then either **land the rule** in the named file or **decline it with the reason**. Both close the row. **The harvest's selectivity does not reach this row** — a rule owed arrives already judged worth keeping by the lane that paid to learn it, and the cost of dropping one is not a lost finding but a rule the next lane rediscovers; nine were lost in one session, two of them twice. A decline stays visible, because a rule rejected on purpose and a rule dropped on the floor read identically once the session ends. **`rulesOwed` gates this, and it clears on an empty result written down, like `docRegister`**: a weave whose lanes owed no rule passes by recording that reading, never by skipping the register — an unwritten empty and a forgotten register are the same artifact.
*   **📨 Hand a topic to another seat — ROW IT, THEN SEND IT (`¶INV_HANDOVER_IS_A_ROW`, `¶INV_HANDOVER_CLOSES_ON_ACK`)** — a groom pass now routinely ends by routing topics to seats that are not this one, and this is the declared verb for it. **An ad-hoc peer `SendMessage` is not a handover; it is a handover's transport.** The move, in this order:
    1.  **Open the `## 📨 Seat handovers` row first** — `direction: sent`, the seat's **from-name and its pane id**, the topic in one line as the receiving seat will read it, and its **member links** (ticket keys, comment ids, inbox roots). A topic named with no members is a row the seat cannot act on, and the member that most needs writing down is the one that was in no topic at all until the routing found it.
    2.  **Then send** the peer message, and **record the delivery reading on the row** — `queued`, `delivered`, or `send failed — <what>`. A queued send is **not** a read: a peer in a different permission mode holds it for its user, and nothing reports back from a Remote Control or a cloud session.
    3.  **Leave it open.** The sender may not close its own row, because an un-acked handover is the case the row exists to show. The row closes on the receiving seat's **own words** — `taken`, `declined — <why>`, or `already done — <the evidence it gave>` — and a decline closes it as surely as a take, on the `⚖️ Rules owed` argument: a topic refused on purpose and a topic dropped on the floor read identically once the session ends. **An ack that arrives as a peer message is transcribed onto the row**; left in the sender's chat it is the bug restated.
    *   **Row what arrives, too.** `direction: received` is a first-class row, not the sender's read backwards: another seat asking this one to act on its own ground — *as `tree`'s owner, should this changelog entry be written* — is the same shape with an owner and an outcome, and a one-way register leaves that round trip exactly as unrowed as the batch it was sent beside.
    *   ⚠️ **The `→ <seat>` reply is NOT this row and may not stand in for it.** `§INV_GROOM_MARKS_WHAT_IT_WRITES` spends `→` as the route marker a pass posts onto an inbox root, and `§INV_EXCLUDE_OWN_COMMENTS` drops it on the next drain so the pass's own reply does not return as fresh signal. It is what stops the root being re-offered. Nothing on the receiving side reads it as an assignment, and making it mean one would couple two meanings onto one marker — the second of which would stop working quietly.
    *   **This is not `## 🤝 Hand-over written`.** That receipt is a conductor handing its own state to its own SUCCESSOR across a context boundary; this is one seat handing one topic to a PEER that keeps its context and answers in its own time. The two were one word and are two registers.
    *   **`seatHandovers` gates this, and it clears on an empty result written down, like `docRegister`**: a weave that handed nothing to another seat passes by recording that reading, never by skipping the register — an unwritten empty and a forgotten register are the same artifact. Un-acked rows **travel to the inheritance** (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`), and they are the kind most exposed there, because the party who owes the ack is not the party handing over.
*   **🧭 Row a vision deviation as the thread lands; never reconcile it yourself (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`)** — when a landed thread contradicts a vision document the weave executes against (a chapter re-scoped, a dependency re-cut, a measurement superseded, a principle falsified), the conductor opens a `## 📚 Docs owed` row with `destination` reading **`/direct` — reconcile**, and the deviating session stops there. **A deviating session does not reconcile the document**: reconciliation is a later composed `/direct` pass's job, and a session correcting the vision it just deviated from is the author grading its own paper. **The destination is chosen when the row is opened, by one question — is the falsified sentence a statement of FACT about the system, or of INTENT about where it is going?** Fact goes to `/revise`, which repairs a claim by making the sentence true. **Intent, or a fact whose supersession the document's history must keep, goes to `/direct`** — because on a vision, making the sentence true *erases the deviation*, which is the decision trail the document exists to hold, so a misrouted row is repaired into invisibility by a lane doing its job correctly.
*   **Harvest good findings at thread end** (`§INV_OFFER_DONT_FORCE_SKILLS`, composed-write) — when a thread finishes its chain, read its Build Report's `## Out-of-scope noticed (not touched)` section plus any `/scrutinize` deferrals, and **offer `/inbox-post` for the genuinely notable ones only** — real bugs, concrete follow-up work worth tracking — not every incidental note. Be selective: a thread that surfaced nothing worth filing posts nothing. **Signals first, a ticket only for a chunk** (`¶INV_LOOM_HANDBOOK_BEFORE_FILING`): a thread's leftovers are findings, so they leave as inbox drops; offer `/ticket` only where a leftover is a whole landing arc in its own right, and route tooling or gate friction to 🛠️ Tooling & Gates rather than letting it become a ticket.
    *   **One finding → `Skill(inbox-post, "<finding>")`**, straight to its channel.
    *   **Several findings → offer `Skill(groom, …)` first**, to cluster them into topics before anything is dropped. A thread that noticed six things should not produce six drops for somebody to group by hand later.
*   **Thread end is not the only moment (`§INV_OFFER_DONT_FORCE_SKILLS`)** — a conductor or a thread noticing something small and out of scope drops it **immediately** via `Skill(inbox-post, …)`, no ceremony and no waiting for the thread to close. Small things are what a held queue loses.
*   **Find the next thread at thread end** (`§INV_OFFER_DONT_FORCE_SKILLS`) — when a thread lands and the loom has capacity, offer to pull more work: `Skill(inbox-next)` when the batch came from a curated Linear project (ranked, in-project), `Skill(groom, …)` when the candidate work is still a pile of ungrouped items — it hands back topics, and one topic is one thread per the grouping rule above — or `Skill(ticket-search, "<keywords>")` to find related tickets by keyword. A chosen result becomes a new thread (the add-a-thread flow). This is how the no-rush loop refills itself.
*   **Keep the ledger live** — rewrite it as threads advance; surface it at each loop gate. Per thread, record its **mandatory-step completion**: the ticket-disposition answer, whether interrogation ran (or was skipped because the Interrogation disposition is None), and the scrutinize agent's id. This record IS the `threadDispositions` proof that gates Loom→Synthesis (`¶INV_LOOM_MANDATORY_STEPS`) — you cannot close a loom whose threads skipped their mandatory steps.

### The wave boundary — integration (`§INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY`)
*Where a wave's lanes are brought back together, and the only place the once-per-wave suite has a tree to run against. **Specified and unexercised** — the merge half cannot fire until lanes run in their own trees, and the clause below says which half ships before that and which waits.*

**What a wave boundary IS, written because nothing here said it.** The loop gate below fires on a **unit of progress** — one thread landing. A **wave** is the whole fan-out: every lane dispatched since the last boundary. These are different cadences, and integrating at the gate merges one lane at a time, which is per-lane integration wearing the boundary's name. The boundary is reached when **every thread in the current `## 🌊 Wave` block's `Threads fanned out` set has landed or parked and none reads `running`** — the conductor takes that from `engine lane-stall "<sessionDir>" --all`, whose `done` · `parked` · `running` states are already the sweep's output (Conducting above rules what each one means, including that it answers **state, never reachability**). **Detecting the boundary is a read: no slot, no confirm. The merge it leads to is a write and takes one** — the loop gate's rule that a cadence may run unconfirmed but may not publish unconfirmed, applied to something with more consequence than a publish.

**This step and the file partition are two answers to ONE question, and a loom runs exactly one of them.** The partition is **prevention** — disjoint file sets allocated up front so two lanes can never touch one file, which is why no conflict has ever arisen here. A merge is **detection**, and the better instrument: it finds the collisions that actually happened, in the text, at the moment the trees meet, rather than the ones predicted at allocation. Under worktree-per-lane **the conductor computes no partition and brokers no claims**, and this section is what "lanes land" means. Under one shared tree **there is nothing to merge** — every lane committed to the same branch already — and the boundary records `nothing to merge — shared tree`. Running both pays for prevention and detection and buys the conductor back the job the worktree shape exists to remove.

**Which half ships without worktrees.** The boundary, the suite-once-against-a-named-sha, and the wave row are exercisable under the shared tree today, with an empty merge step. **The merge, the ordering and the conflict hand-back are not reachable at all until lanes have their own trees** — two worktrees cannot share a branch, so a lane branch to merge does not exist yet. A conductor must not report the unreachable half as working because the reachable half did.

**The mechanism** — each line answers one of the questions `docs/CYCLICAL_LOOM_VISION.md` § `@engine/execution-shape` asks of this step:

*   **WHO — the conductor**, which already holds the ledger, the lane list and the wave block, and is the only participant that can see every lane's branch at once. This is the loom's **one** git write that no composed skill performs, so `§INV_LOOM_COMPOSED_WRITES` carries a narrow carve-out named in Constraints: the conductor may run the merge of a lane's named branch into the session branch, under the operator's confirm, and **nothing else** — it authors no change, resolves no conflict, and rewrites no history.
*   **ONTO WHAT BASE — the session branch, captured at Setup as a name AND a sha** and echoed into the ledger header (`▶️ Loom Opened`). It is recorded at the open because it is not reconstructable at the boundary: under worktree-per-lane the conductor's tree is not any lane's, and a base inferred later is a base guessed. A loom with no recorded session branch does not integrate — it reports the missing field and stops, rather than choosing one.
*   **IN WHAT ORDER — landing order, first-landed first.** Three reasons, and the order is not arbitrary: it is **already written down**, because each lane's `/snapshot` stamps `committed <sha> on <branch>` into its Outcome as it lands; it makes the conflict loser the **later lander**, so the loom keeps the one precedence rule `§INV_LOOM_FIRST_CLAIM_WINS` already states (*the later thread's conflicting step defers*) instead of acquiring a second; and the later lander is the lane likelier to still be warm, which is the lane the conflict answer needs addressable.
*   **WHAT A CONFLICTING LANE DOES — the later lander resolves its own, in its own tree.** On a conflict the conductor **aborts the merge** and leaves the session branch at its exact pre-merge sha — **never resolves, never `-X`**, the same idiom and the same reason `/pr` §Constraints already binds its cherry-pick to. It then resumes that lane (`SendMessage`, by name, mirroring `§INV_LOOM_EVERY_THREAD_PROVES`'s resume-rather-than-redispatch rule) carrying its branch name, the session branch's sha, and the conflicting paths as `git diff --name-only --diff-filter=U` named them. **The lane merges the session branch INTO its own branch and resolves there** — never the reverse, because the session branch is shared ground the earlier lanes have already landed on, and handing it to a lane as a resolution surface is how one lane's bad merge reaches every other lane's work. The conductor re-attempts once the lane reports resolved. **A second conflict on the same lane is a hard-floor escalation, not a loop.**
*   **WHAT THE SUITE RUNS AGAINST — the assembled tree, named by sha (`§INV_LOOM_GATE_RUNS_ON_THE_INTEGRATED_TREE`).** The once-per-wave suite runs in the conductor's tree on the session branch **after the last merge lands**, and the wave row carries the sha it ran against. **A partially integrated tree is forbidden as its subject**: a wave with one lane merged and another's conflict still open records `suite deferred — <threadId> conflict open` and runs nothing, because a green recorded against an assembly nobody will ever ship is worse than an unrun gate — it is an unrun gate that reads as evidence.
*   **ONE PR FOR THE ASSEMBLED WAVE, offered once the integrated tree is green** (`§INV_OFFER_DONT_FORCE_SKILLS`, composed-writes) — `/pr` on the session branch, whole-branch, linking every ticket the wave carried (`Closes` the primary, `Relates` the rest). **A wave branch is MIXED by construction**, and `/pr` §1 offers on a mixed branch to cherry-pick one ticket's commits onto a fresh branch — which is the per-lane-PR shape declined for this step, arriving as a default rather than as a choice. **Merging `--no-ff` is what makes that decline structural instead of remembered**: a merge commit exists, and `/pr`'s own Merge Commit Rule refuses merge commits in a cherry-pick set and forces the whole-branch path. A fast-forwarded single-lane wave leaves no merge commit and re-opens the fork, so `--no-ff` is load-bearing rather than cosmetic.

**This re-times the closing snapshot's `In Review` flip** described in Conducting above: a thread lands into the wave before the wave's PR exists, so its ticket reaches `In Review` when **the wave PR carrying it** is up, not when its own merge landed. The per-thread `/snapshot` is unchanged — it commits the lane's reviewed slice on the lane's own branch, which is exactly what the merge consumes.

**Record the wave in the `## 🌊 Wave` block as the boundary resolves** — the boundary reading, each lane's merge in landing order with its disposition, the integrated sha, the suite's result against that sha, and the wave PR. That row IS the `wavesIntegrated` proof gating Loom→Synthesis, and like `docRegister` it **clears on an empty result written down**: a loom that never reached a boundary, or one on a shared tree with nothing to merge, passes by recording that reading, never by skipping the step.

**⚠️ When every lane is COLD, this step has no settled answer and does not invent one.** Resuming the losing lane is the whole conflict mechanism, and it is unavailable once the lanes have ended — which is the likely state at a session-end integration, and which **`engine lane-stall` cannot tell you**, because it reports state and not reachability: a `done` or `parked` reading is consistent with both an addressable lane and a gone one, and only a `SendMessage` attempt answering *no transcript found* settles it. So a conflict on a wave whose losing lane is unreachable is a **STOP**: the conductor aborts the merge, rows the conflict under `## 📡 Relay / Conflict` with the branch and the `--diff-filter=U` paths, opens a `## 🔓 Open claims` row for the fallback decision, and escalates. **It does not resolve the conflict itself, hand the conflict to a fresh lane that did not write the code, or drop the wave** — each of those is a choice nobody has made, and `§INV_LOOM_PASS_ON_NEVER_DISCARD` makes passing it on the only legitimate close.

### The loop gate (`AskUserQuestion`, defaults to keep-going per `¶INV_LOOM_NO_RUSH_TO_CLOSE`)
Present after each unit of progress (a thread landing, a batch of builds finishing):

**Lead with the forks, then the exits (`¶INV_LOOM_SURFACES_FORKS_UNASKED`)** — run `Skill(decide)` whenever its §1E cadence says to, and open the gate with the forks it mined, each decided in place; the offer pool below stays underneath it. `/decide` owns the fork test, the cadence, the card discipline and where a non-fork is routed instead — follow it there. It replaces the ad-hoc mid-thread question round, never the dispatched `/interrogate` of the add-a-thread flow's step 3 (`¶INV_LOOM_MANDATORY_STEPS`). A pass that mines nothing presents the menu alone.

**The PASS runs on the cadence; the BOARD renders at a BOUNDARY (`¶INV_LOOM_BOARD_AT_A_BOUNDARY`).** A loom's rhythm is gate → gate → *board at a boundary*, and **not board → board with reports between**. The distinction is which half is expensive. The pass is cheap and clears on an empty sweep (`no forks pending`); the page is not.

*Counted from `/decide` §4's own declared steps rather than timed*, one board is: a **dispatched subagent** to render, an orchestrator integrity pass over every caption, provenance mark, option key and the kit reference, `publish-kit.sh` then `publish-s3.sh`, the `docId` captured into the boards ledger — and then, at a later gate, `prove-sync.sh` to fold, a fetch of the state doc, and the row closed. **It also acquires an obligation nothing else here acquires**: `/decide` §4 states a board published and never read *blocks a wrap-up rather than quietly expiring*, and `decisionPasses` gates Loom→Synthesis on those rows. So each board adds a page, a fold and a row that must be worked before the loom can close.

**That is strictly more than this file already refused at this frequency.** The weave-status page is refused per gate below for a *smaller* cost shape — an assembling subagent, a composed page, an honesty gate, a publish — on the grounds that the gate fires after every unit of progress, making it the most expensive recurring event in the session (`¶INV_LOOM_WAKES_ARE_THE_BILL`). A board is that cost plus an obligation, and the obligations **accumulate**: a loom landing a thread every few minutes would reach Synthesis owing a fold on every board it ever published. **A board per unit of progress is therefore refused, and the refusal is costed rather than asserted.**

**What renders instead, and when.** The loom passes `--no-board` when every mined fork is decidable in chat right now by the operator who is present — that is the common case and it loses nothing, because §5's confirm was always the authority and §6's record is written either way. A board **earns its render** at a boundary, where a page does something a chat question cannot:
> - **a fork must reach somebody who was not in the session**, or must be re-readable by them afterwards;
> - **a fork must survive this session** — it will be inherited, so a successor needs the card rather than a transcript;
> - **an answer has to arrive in the gap**, when no one is at the gate to be asked — the one thing only the state transport does.

The hand-off boundary is where every one of those holds at once, which is why it is the boundary that always renders: each `🔓 Open claims` row crossing into the inheritance needs a card a successor can read without this context.

**A cadence may run without a confirm; it may not PUBLISH without one.** The two properties are independent and conflating them would undo the cost argument above. A condition-fired offer that only **reads** — the stall sweep, the board fold, a reconcile against an open row — rightly takes no slot and needs no confirm: an operator should not have to choose to be told a lane died. A cadence that would **render and publish a page** is the expensive half wearing a cadence's clothes, and it reaches the operator as a boundary decision instead. So when a new condition-fired entry joins this gate, the question is not whether it is confirmed but **whether it publishes**.

**And "reports in between" already exists, free.** The live ledger is surfaced at every gate and is authoritative (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`). What it was missing is not frequency but **content** — it never said why anything was waiting, which is what made a weave with a live ledger read as a weave with no reports. The `🧵 Ledger` `status` grammar, the `📡 Relay / Conflict` `Waiting on` field and the live `🔓 Open claims` block fill that at no recurring cost. A shareable page on top stays `/prove-explore`'s, on demand (below).

**Row every board, then fold and read it at the next gate** — a pass that publishes a Decision Board opens its row in the log's `## 🗳️ Boards` block as it publishes: the board URL, its `docId`, the gate, and the forks it holds. **A row written without the `docId` has lost that board's answers permanently** — `/decide` §4 states the id is not recoverable later. At the next gate, before mining fresh forks, work each open row: run the agent-run fold over its `docId` (the events-inbox→state-doc merge `/prove`'s `assets/STATE_TRANSPORT.md` defines; `/decide` §4 names the command), then read the state doc and carry what teammates answered into the pass. A `404` is **not yet folded**, never zero answers — follow `/decide` §4 there rather than treating an empty read as a verdict. Read boards at a gate the conductor is already awake for, never on a watcher or a poll loop: a wake is the bill (`¶INV_LOOM_WAKES_ARE_THE_BILL`).

**A row closes, or states what the fold found keeping it open.** Folding and reading closes it (`gate N: folded + read`); a row still open after the fold records the finding that leaves it so — `open — no answers yet`, `open — decided in chat at gate 5`, `open — presign expired, answers cannot return`. That reason is a **result of folding, not a note written instead of folding**, which is what stops it being a waiver: you cannot state it without having read the board. A bare `open` is an unworked row, and `decisionPasses` does not clear while one stands — the same shape as `proofPages` accepting `no renderable evidence`, and the conductor's call rather than a lane's. **The ledger row is the board's state of record**: it outlives the pass that published it, so `/decide` keeps only the board URL in its own record and points here for the handles and the fold state (`/decide` §6).

**Work the `🔓 Open claims` rows before mining fresh forks (`¶INV_LOOM_A_FORK_ARRIVES_DECIDABLE`).** The block is live in the log, sibling to the thread ledger, and it is the loom's answer to a lane sitting on an unanswered question. At each gate, per open row: **re-put it** if the thread still waits on it, carrying its `prepared context` so the operator reads a `§FMT_DECISION_CARD` rather than a re-asked question; **close it** against the record path; or **state what leaves it open**. What binds the rows:
> - **A row carries a POINTER to its card, never a copy of the card's fields.** `/decide` §6 already writes the fork, the options as framed, the lean with its trade-off, the falsifier and — per `¶INV_REJECTED_OPTIONS_ARE_RECORDED` — what was decided against, to `builds/<slug>_DECIDE.md`. Point at it. Inlining those fields into a row would both drift from `§FMT_DECISION_CARD` and break `§INV_LISTS_INSTEAD_OF_TABLES`, and the card is not what was missing — **a path to it from the loom's state was.** `/decide` §6 routes a *board's* handles to `🗳️ Boards`, so a fork decided in chat with no board had nowhere in this weave's state to record what it was decided from.
> - **Every row names what the thread does MEANWHILE**, and a thread does not idle on an unanswered fork by default. `/decide` §5's vocabulary is the shape of that answer — proceed provisionally with the falsifier, hand it to the lane inside a stated bound, defer with a trigger — asked when the fork is **raised** rather than when it is answered. `idle` is legitimate and is the only value that spends the operator's attention now, so it carries why idling was the right call.
> - **A row may not close as a bare `answered`.** It closes as `answered gate N — <the choice> — <record path>`, or it states what leaves it open (`open — decided in chat at gate N, not yet recorded`). An answer with no artifact is what leaves a successor holding a decided row with no record of what decided it, so the honest open beats the false close — the same shape as a bare `open` on a board row, and the conductor's call rather than a lane's.

**Record each pass** — a log entry (`## 💡 Decision`) naming the gate it fired at and either the forks it put up with each one's call or **`no forks pending`**, a legitimate outcome: `decisionPasses` gates Loom→Synthesis on the record of the passes, never on a fork count, so an unblocked loom satisfies it with the empty sweep written down rather than a fork found to fill it.

**The gate is a DECLARED POOL surfaced by relevance, never a fixed menu (`¶INV_LOOM_GATE_SURFACES_BY_RELEVANCE`).** `AskUserQuestion` caps what it *displays*, not what a gate may offer: `§CMD_DECISION_TREE` declares N peers, surfaces the most relevant four, and reaches the rest through the built-in Other field — `¶INV_ASK_SURFACE_FOUR` and `¶INV_ASK_SLASH_FOR_MORE` own that mechanism, and this gate uses it rather than restating it. The fixed menu is why every other offer in this file stayed in prose the gate never read, surfaced only when a conductor remembered it.

> "The loom is running. What next?"

**Always surfaced** — the ones that act on the weave itself:
> - **"Add a thread"** — scope + fan out a new thread (the add-a-thread flow above). The session stays open.
> - **"Adjust a thread"** — loop a thread back (council/scrutinize → interrogate or build), or re-triage.

**Surfaced on its condition.** Each names the moment it earns a slot and what it is **instead of**; where its condition does not hold it drops to the pool, reachable via `/`, and the slot goes to the next one whose does (`§INV_OFFER_DONT_FORCE_SKILLS` — an offer that would add nothing is skipped silently, not displayed and declined):
> - **"Keep weaving"** — a lane is live. Nothing to add; let running threads continue, re-present when the next lands.
> - **"Pull more work"** — a thread just landed and the loom has capacity. Routes to the find-the-next-thread offer in Conducting above — `/inbox-next` for a curated project, `/groom` for an ungrouped pile, `/ticket-search` by keyword — and a chosen result enters the add-a-thread flow. **Instead of** the loom going quiet until the operator notices. The offer was already written; what was missing was a gate that reads it.
> - **"Publish a shareable status"** — the weave's state has to reach somebody who was not watching it. The clause below rules what this is and is not. **Instead of** pasting the ledger into a message.
> - **"Wrap up"** — proceed to Synthesis. **Only** when you explicitly choose it. It surfaces on a signalled closing intent, or with the ~150K recommendation card `¶INV_LOOM_NO_RUSH_TO_CLOSE` describes; otherwise it sits in the pool, because a close option displayed at every gate *is* the gate asking "shall we close?", which is the one thing that invariant forbids. Demoting it loses nothing — an explicit "done" already skips the menu entirely (below).

**An offer that fires on a CONDITION needs no slot.** The gate already runs such cadences — the `/decide` pass above it and the board fold — and these join them rather than competing for a slot:
> - **Sweep for stalled lanes.** `engine lane-stall "<sessionDir>"` before the gate card is composed (Conducting above rules the readings and what each one means). One read-only command at a moment the conductor is already awake, so it costs no wake (`¶INV_LOOM_WAKES_ARE_THE_BILL`) — which is why it is a cadence and not an offer: an operator should never have to choose to be told a lane died. Every `STALE` row either advances to a `🅿️ Parked` row with its next move or is resumed from its LOG PATH; a `0 lanes seen` reading is reconciled against the ledger, never reported as clean.
> - **Sweep the log for decisions no register write followed.** `engine sweep-check "<sessionDir>/LOOM_LOG.md"` before the gate card is composed, read by its exit status and never through a pipeline. One read-only command, no skill load, no slot, no confirm — the same shape as the stall sweep above and for the same reason: an operator should not have to ask to be told a decision was logged and no register block has been written since. **Its claim is temporal and narrow.** Exit 3 lists each `UNROWED` decision, one logged after the latest write of every register block (`🧵 Ledger`, `🗳️ Boards`, `📚 Docs owed`, `🔓 Open claims`, `🅿️ Parked`), which therefore cannot have been rowed: row it, or write down that it closed with nothing owed. Exit 0 means only that *no decision is certainly unrowed*; the `FOLLOWED` decisions a later register write came after are **not** shown to be rowed, because that write may not mention them, and rewriting a register block after a decision clears the check without anyone having rowed anything. It compares no content. **A conductor that appends a short Ledger update rather than a full rewrite hides every earlier decision from it**, since the update is a register write; the check cannot tell the two apart. A `0 decision headings` reading is a claim about what the pattern recognised, not a clean log. `/sweep` is the judgement half and fires before a hand-over, never here. ⚠️ **And it reads five of the eight registers: `🌊 Wave`, `⚖️ Rules owed` and `📨 Seat handovers` are not among them** — its register list is hardcoded in `scripts/sweep-check.sh`, so a register declared in the template does not reach it by being declared. So a decision rowed into any of the three is invisible to it in both directions — it cannot confirm one was rowed, and a register write there does not clear a decision either. **The wave rows, the owed rules and the seat handovers are read from the log itself**, never inferred from this check passing; `wavesIntegrated`, the rule register and `seatHandovers` gate on the rows, so a clean exit here says nothing about any of them.
> - **Render the loom's status page.** `engine loom-page "<sessionDir>/LOOM_LOG.md"` — a deterministic present-state render of the log's own registers, for an operator or a teammate who wants to see the weave without reading it. **It takes the LOG FILE, not the session directory**: handed a directory it exits 2 with `Is a directory` and renders nothing. Read-only, no skill load, no slot, no confirm, and nothing about it is restated here: the command owns its behaviour, and a copy of that behaviour in this file would drift from it while a citation cannot. It renders what the log says **now** — it is not a history, not a substitute for the ledger, and not the hand-off's inheritance.
> - **Reconcile a vision.** An open `📚 Docs owed` row names `/direct` as its destination. `Skill(direct, "reconcile <vision path> — <what moved>")`, which **rides this session** (`§INV_RIDE_NEVER_ACTIVATES` — it activates nothing and moves no phase) and runs **without a confirm**: it records what already happened, and gating a record of what happened is how the record goes unwritten. **Instead of** the deviation sitting in the register until a reader discovers the document is wrong. A **revision** — the operator wanting the direction itself different — is not this offer and never fires on a condition: it needs a person asking. It reads and records rather than publishing, so it passes the clause above.
> - **A `/decide` pass that ROUTES an item lands it here.** Its §1B routes an item whose answer is a fact somebody must supply to `/interrogate`, and `¶INV_DECIDE_DISPATCHES_NEVER_EXECUTES` returns that recommendation to its caller, which is this gate. Act on it — `Skill(interrogate, "<the routed subject>")`, or carry the item into the thread's own interrogation — because a routed item the gate drops is a fork re-mined every pass with nobody ever having acted on it. It is not a menu slot: `/decide` owns when it fires.
> - **Harvesting a landed thread's findings** fires at thread end, where Conducting above already puts it (`/inbox-post`, or `/groom` first where there are several). Not a slot either.

**The status page is `/prove-explore`'s, it is ON DEMAND, and it does not replace the ledger.** `Skill(prove-explore, "weave status — <what the reader must be able to understand>")` over the ledger: its own §1 advertises a state-of-a-body-of-work question, so this needs no new artifact. **Its trigger is a reader, never a gate** — the operator handing the state to somebody who was not watching, or a wrap-up whose debrief is written for us rather than for them. ⚠️ **Per gate is refused**: a run dispatches an assembling subagent, composes a page, walks a per-section honesty gate and publishes, and the loop gate fires after every unit of progress — making it the most expensive recurring event in the session, against `¶INV_LOOM_WAKES_ARE_THE_BILL`. **And the ledger keeps its job**: for the conductor's own bearings and for a successor's, the live ledger and `LOOM_INHERITANCE.md` are cheaper and authoritative (`¶INV_LOOM_PASS_ON_NEVER_DISCARD` makes the row authoritative, not a page about it). The only thing the ledger is not is **shareable**, and that single gap is all this offer fills. The page IS a proof page, so a conductor publishing one has already satisfied `¶INV_LOOM_EVERY_THREAD_PROVES` for that pass and owes no second one.

If the user explicitly says "done"/"close", skip the gate and proceed to Synthesis — **after working every open `🗳️ Boards`, `📚 Docs owed` and `🔓 Open claims` row**: fold and read the board, close the doc row against its Revise Report, close the open claim against its record path, or record the finding that leaves any of them open. The menu is what an explicit close skips; the rows are not part of the menu, and this is the gate a closing loom most needs to pass, since nothing later will ask.

**A handing-over close may carry an open row; a close that would DISCARD one may not (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`).** A row that cannot be closed here — a board whose answers have not arrived, a doc claim with no home, an operator fork still unanswered — is **inherited**: written to the sessions root's `LOOM_INHERITANCE.md` with what closes it, and read by the next startup pass (Phase 0's inheritance intake). The gate's intent is unchanged, because it exists to stop answers being thrown away rather than to stop a session ending: pass-on is allowed, discard is still refused. Without this provision a session that intends to hand over cannot satisfy the gate at all — it has no next gate to fold at — so the gate would make the hand-over impossible rather than careful.

**Debrief notes** (for `LOOM.md`):
*   **Final ledger** — every thread, its terminal stage, ticket + PR links, status.
*   **The weave** — which threads ran in parallel, what serialized and why, conflicts brokered, deadlocks/escalations.

*   **Docs owed** — every `📚 Docs owed` row, closed against its Revise Report or stating what left it open.
*   **Open claims** — every `🔓 Open claims` row, closed as `answered — <choice> — <record path>` or stating what leaves it open. A row that was answered in chat and never recorded is reported here as open, not as answered.
*   **Lanes that stalled** — every `🅿️ Parked` row the stall sweep opened as `stopped without handing back`, and how each resolved: resumed from its LOG PATH, re-dispatched, or carried. A weave whose sweep never fired says so, with the reading that establishes it.

A wave that merged nothing because the lanes shared one tree says so; a wave whose suite was deferred on an open conflict reports the conflict and the lane it went back to, never a green it did not take. A loom that never reached a boundary records that reading rather than omitting the bullet.

## Constraints

*   **`¶INV_LOOM_COMPOSED_WRITES`**: `/loom` never writes code, Linear, or git directly. Every mutation goes through a composed skill (`/build`, `/snapshot`, `/pr`) under that skill's own confirm. **One carve-out, named rather than described**: the wave boundary's merge of a lane's branch into the session branch, because no composed skill performs an assembly and a step with no owner runs nowhere (`§INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY`). It is bounded to that single operation under the operator's confirm — the conductor authors no change, resolves no conflict and rewrites no history, and a conflict goes back to the lane that wrote the code. Everything else about this invariant is unchanged, and "the conductor needed to" is not a route to a second carve-out.
*   **`¶INV_LOOM_HANDBOOK_BEFORE_FILING`**: before any composed write into the tracker — `/ticket`, `/snapshot`, `/inbox-post` — the TARGET project's Inbox Handbook is read via `§CMD_READ_PROJECT_HANDBOOK` and its `## Ticketing Strategy` obeyed, because a seat filing into another project obeys THAT project's lines rather than the habits of the project the loom is working in. **`/ticket` and `/inbox-post` cite the atom themselves, so the conductor passes them nothing; `/snapshot` does NOT, so the conductor performs the read itself and passes the strategy in the dispatch** — an invariant here cannot inject a step into a skill it merely invokes, and `/snapshot` is the path that rewrites ticket *descriptions*, where a guard subject can arrive after the gate was passed. Two lines bind the conductor directly: a ticket's **subject** must be domain work, so a guard, tooling, a seat/ownership question or agent-coordination machinery is refused as a subject and redirected — the report to the project's 🛠️ Tooling & Gates channel where it has one, the resolution to the repository at **the destinations that project published** (never a path named in a skill: these files are global and run in repositories that have never heard of one) — and a **finding is a signal, not a ticket**: a thread finishing with findings offers drops first, and a ticket only where the work is a chunk the Size dial recognises. A guard may still be a ticket's acceptance; it may never be its premise, and the way past the gate is naming the instance that is wrong today. **Exactly one project is carved out of the subject half, and it is named rather than described**: `Product: Orchestration` (`P-IDE-10`, team Idealic, `https://linear.app/idealic/project/product-orchestration-bfe9d92b7318`), whose domain work IS the orchestration machinery — loom, groom, decide, direct, intake, and the transport carrying decisions back — so a conductor's boundaries, a hand-off format, a durable ledger row or a decision transport is an ordinary domain subject when it is filed THERE, and refused everywhere else. **The exception is a project, never a category** — "engine work", "coordination machinery" and "tooling" remain refused as subjects wherever they are filed, because a category-shaped exception is one any seat can claim by renaming its work, and the product trackers fill with plumbing anyway. **Every other project's protection is unchanged**: a guard, tooling, a seat/ownership question or agent-coordination machinery is still refused as a subject in each of them, and still redirected to the destinations above. Filing into the carved-out project does not relax the rest of the gate — Volume, Size and Substance still bind, a finding is still a signal, and `/ticket`'s own floor still asks the premise to name the instance that is wrong today. **A missing handbook, or a project with no 🛠️ channel, never blocks a thread** — both degrade in one line and the composed skill's own floor holds.
*   **`¶INV_LOOM_AGENTS_NAMED_BY_THREAD`**: every spawned agent leads its Agent `description` with `[<threadId>]` AND prefixes every line it emits (status, shared-log entry, `SendMessage`) with `[<threadId>]`. The fleet view shows the sub-agent type, not a label, so the prefix is the only thing that tells threads apart — no unprefixed loom agents.
*   **`¶INV_LOOM_MANDATORY_STEPS`**: per thread, the ticket-disposition ask, interrogation (per the Interrogation disposition), and the scrutinize agent are MANDATORY — the Autonomy disposition tunes how much the conductor resolves without asking, never *which steps run*. Build and scrutinize fan out as concurrent AGENTS, never `Skill(build)`/`Skill(scrutinize)` (which serialize the loop). The `threadDispositions` proof gates Loom→Synthesis on their completion.
*   **`¶INV_LOOM_EVERY_THREAD_PROVES`**: every thread ends with a proof page, produced while its context is still hot — **including a pass the conductor runs in its own context**, which is the hottest context in the loom and was the one place the rule did not reach while it bound a dispatched lane; the rule binds the work rather than the actor, so an inline ticket, grooming pass, decision pass, publication or measurement proves in place rather than being dispatched to earn one — and so does EVERY FINISHED ROUND within it (a fix round, a re-review, a rebase-and-regate, a resumed lane each prove what they did when they report done; interim wakes and progress notes are exempt; an earlier round's page never stands in for a later one) — not only threads that reach a PR, and not only threads that shipped code. An investigation proves what it established; a measurement proves what it measured. The proof is the thread's LAST ACT, written by the thread itself: instruct it in the dispatch brief, and resume a finished lane by name rather than sending a fresh agent to re-derive what the first one knew. **Two exemptions and no others**, each recorded on the row as `exempt — <clause> — <the thread's whole output>` and each **the conductor's call, never the lane's**: the thread's SUBJECT would be refused as a *ticket's* subject by `/ticket` §3 step 0 — a guard or check, tooling, a seat or ownership question, agent-coordination machinery — **with that paragraph's `Product: Orchestration` carve-out travelling intact**, so a thread on the orchestration machinery itself still proves and the clause cannot delete its own evidence; or **nothing was ESTABLISHED**, which is not a claim about size — size may not be cited, a one-character edit that corrected a false belief proves, and a thread that filed, posted, published or committed a corrected mechanism is never exempt because somebody will act on it. A bare `exempt` is an unworked row, like a bare `open` on a board row. A thread with nothing renderable records `no renderable evidence` — an explicit skip, reached only after `/prove-explore` with bare sections is ruled out, and the conductor's call too: a lane that hands back without a page is resumed by name to compose one. The thread INVOKES the proof skill and runs its protocol to a published URL, never a hand-composed page in its shape, and **the variant is chosen by the shape of the answer rather than the size of the subject** — `/prove` for one settled claim, `/prove-explore` for a settled answer too plural to compress, `/prove-visionary` where the answer is unsettled and someone must choose; the conductor names it in the brief, because only `/prove-explore` names its siblings and no variant's triggers fire at thread-close, so the nearest-sounding trigger returns `/prove` every time; the conductor then re-gates the published page and republishes a corrected copy if needed. The rule reaches lanes through `assets/LOOM_AGENT_DIRECTIONS.md` (§ "Your last act"), which every brief carries. A ledger row carrying neither a proof URL nor that note is an incomplete thread, and `proofPages` gates Loom→Synthesis on it.
*   **`¶INV_LOOM_GATE_SURFACES_BY_RELEVANCE`**: the loop gate declares a **pool** of offers and surfaces the most relevant four, the rest reachable through the Other field — `§CMD_DECISION_TREE` owns that mechanism (`¶INV_ASK_SURFACE_FOUR`, `¶INV_ASK_SLASH_FOR_MORE`) and this gate uses it rather than restating it. **A fixed four-item menu is forbidden**: the tool caps what is displayed, not what may be offered, and a fixed menu is why `/groom`, `/inbox-next` and `/ticket-search` sat in this file's prose while the gate offered none of them. Add-a-thread and adjust-a-thread always surface; every other offer names **the condition that earns it a slot** and **what it is instead of**, and is skipped silently where it would add nothing (`§INV_OFFER_DONT_FORCE_SKILLS`). Wrap-up is **conditioned, not standing** — a close option displayed at every gate is the gate asking *"shall we close?"*, which `¶INV_LOOM_NO_RUSH_TO_CLOSE` forbids, and an explicit "done" reaches Synthesis without the menu regardless. **An offer that fires on a condition takes no slot** — the `/decide` pass, the board fold, the thread-end harvest and the deadlock drawing are cadences, and a cadence competing for a slot is a design error. **Three things are ruled OUT of the pool, so they are not re-imported**: `/summarize`, because a loom's narrative of its own work is the Synthesis debrief and a second one competes with it; `/report`, because it reconstructs state *blind* from the transcript while a loom's state of record is a deliberately-maintained ledger plus an authoritative inheritance row (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`); and `/design`, because it composes a page directly and `¶INV_LOOM_EVERY_THREAD_PROVES` requires a proof skill's own protocol, *"never a hand-composed page in its shape"* — offering it is a route around that invariant. **A weave status page is `/prove-explore`'s, on demand and never per gate** (`¶INV_LOOM_WAKES_ARE_THE_BILL`); it fills the ledger's shareability gap and replaces neither the ledger nor the inheritance file.
*   **`¶INV_LOOM_SURFACES_FORKS_UNASKED`**: a conductor surfaces the forks holding threads up rather than waiting to be asked — the loop gate runs a `/decide` pass on that skill's §1E cadence and leads with the mined forks above its offer pool, because the operator asking *"what do you need from me"* means a pass was already overdue. `/decide` owns the fork test, the cadence and the card discipline (`§INV_DECIDE_FIRES_PREEMPTIVELY`, declared there); it feeds this gate and never replaces it, and it stands in for the ad-hoc mid-thread question round, never for a mandatory step (`¶INV_LOOM_MANDATORY_STEPS`). The `decisionPasses` proof gates Loom→Synthesis on the record of those passes — each one's gate and its outcome, `no forks pending` included — never on a fork count, so a loom nothing blocked clears it by recording the empty sweep. A pass that publishes a board rows it in the log's `## 🗳️ Boards` block with its `docId` — unrecoverable afterwards per `/decide` §4 — and the next gate folds and reads that row before mining, treating a `404` as not-yet-folded per the same section; the ledger is how answers come back, so no watcher and no poll loop (`¶INV_LOOM_WAKES_ARE_THE_BILL`). **`decisionPasses` gates on those rows too** — each reads `folded + read` or states the finding from the fold that leaves it open, so a loom cannot reach Synthesis discarding answers a teammate left in a board nobody worked; it rides this proof rather than a second one, because a board exists only where a pass ran and the two could never be satisfied apart. The row is the board's **state of record** and outlives the pass that published it — `/decide` §6 keeps the URL and points at the row for the handles.
*   **`¶INV_LOOM_NO_RUSH_TO_CLOSE`**: the loop gate defaults to keep-going. The session closes only on the user's explicit choice — near **~150K tokens** (the figure `¶INV_LOOM_WAKES_ARE_THE_BILL` already gives a lane, one number for both sides so neither drifts) a spent context budget becomes a *recommendation* the conductor puts on the gate card with its reason, never a close it takes for itself; below that figure a mid-range reading is not even that (`¶INV_CONTEXT_BUDGET` — an unnumbered threshold is discretion wearing a rule's clothes). **The figure governs when the card appears, not when anything dehydrates** — different events, and conflating them is how the unnumbered rule misfired. Where an involuntary exit is imminent the conductor writes its state and hands over rather than riding into it, which is a hand-over and not a close, and the user's choice still ends the session.
*   **`¶INV_LOOM_DOC_LANE_IS_STANDING_AND_BATCHED`**: documentation rides ONE standing lane the conductor feeds, fed **batched on a landed thread** and never per change-event, because a wake is the bill and a loom landing threads every few minutes would otherwise wake it constantly. **The conductor owns the register, the lane does not**: the `📚 Docs owed` rows live in the log (and in the inheritance at a hand-over), so what is owed survives a context clear while a lane's memory does not. The lane runs `/revise`, which is **claim-scoped** — a located sentence a landed change falsified, repaired against the code — and is **forbidden** the tree's index, pages the change does not reach, tree-wide count or link audits, and inventing a home for an undocumented change; those are `/document`'s, because no single diff can scope them and a per-thread lane asked to do them either skips them or never finishes. It rows them back instead, and the conductor routes the row. A row closes as `revised — <report path>` or states what the lane found that leaves it open; a bare `open` is an unworked row, and `docRegister` gates Loom→Synthesis on the rows rather than on a doc count, so a loom that falsified no claim clears it with the empty register written down.
*   **`¶INV_LOOM_HANDS_OVER_A_PATH_NOT_AN_ID`**: a hand-over written for a restart names a lane's **LOG PATH**, never an agent id — a context clear ends every in-process subagent, so an id is executable only while the parent context lives and `SendMessage` to it answers *no transcript found* on arrival. The successor dispatches a fresh lane with that log in its context pack. The same brief states every reading's timestamp and marks it re-measure, scopes a claim to the tool class it was measured on, names the field that actually discriminates rather than one both states share, re-reads an artifact before briefing its state (a lane's log is not a record of what it did after it stopped logging, and an untracked path's `git status` is silent at exit 0), names each standing arrangement with what blocks on its absence and how to re-arm it, and writes every command with an absolute path. `§CMD_DEHYDRATE` and `§CMD_RESUME_SESSION` own the payload and the resume; this invariant owns only what a conductor adds to them. **Not every log path is the same handle, and the hand-over says which kind it is.** A lane's own `builds/<slug>_BUILD_LOG.md` briefs a successor on that lane alone; the shared session log briefs it on the whole weave, and `logpath=none` briefs it on nothing. *Measured on one session, 2026-10-23*: `engine lane-stall --all` reported 112 lanes, of which **46 read `logpath=none`** and a further set pointed at the shared `LOOM_LOG.md` — so for those rows "resume it from its log path" lands a successor in an eight-thousand-line shared log, or nowhere, which is a materially weaker handle than this rule reads as promising. A hand-over therefore **names the kind**: `own log` · `shared log only` · `no log`. For the last two the conductor adds what the lane's own log would have carried — the files it touched, what it established, where it stopped — or says that is unrecoverable, because a successor briefed with a path that cannot brief it is worse off than one told the record is missing.
*   **`¶INV_SUITE_ONCE_PER_WAVE`**: a lane runs the tests its own change touches; the **full suite runs once per wave, at the gate, against the assembled tree** — never once per thread and never at each of a lane's steps. *Measured 2026-10-20 over 105 interleaved order-rotated runs*: the same command spread 10.7s–102.0s (p50 21.5s, p90 58.1s), making a per-step full suite the dominant cost of a parallel run. **Three remedies are falsified rather than untried and may not be re-attempted as fixes for it**: reducing concurrency (every reduction measured worse — disabling file parallelism came in at 311.1s against a 40.4s baseline, nearly 8×), trusting an advertised speed-up (a cache advertised at removing 57% of tracked time measured inside the noise band), and judging the change from any single timing (on that spread, one run is near meaningless — a judgement needs an interleaved, order-rotated distribution). Making the suite faster is **out of scope**: this routes around the cost rather than reducing it. The known cost of the rule is accepted deliberately — a cross-cutting break reaches the wave gate, where attributing it is more expensive — and briefing lanes to run the whole suite is not a permitted way to buy that back.
*   **`¶INV_SLOT_CAP_IS_GLOBAL`**: the live-lane cap is enforced **across concurrent looms**, not within one, because two looms that cannot see each other will together exceed any number each keeps privately and will contend over one test queue and one machine. The count lives in `~/.claude/engine/.loom-slots/`, one file per loom; **each loom writes only its own file and reads every file**, which makes the read race-free without a lock. A row whose heartbeat has aged past the staleness window is **reported as stale and not counted** — a conductor ended by a context clear cannot delete its own row, so stale rows are expected, and naming them in the reading is what separates a count that discarded rows from one that found none. A loom that cannot read the directory dispatches one lane at a time and says so, rather than assuming it is alone. **Deriving the count instead of storing it is falsified here** (*measured 2026-10-23*): `engine find-sessions.sh active` returned one session and omitted the live session it ran from, because discovery is scoped to a single session root — and `engine lane-stall` answers a lane's state, never its reachability, reporting lanes as `running` whose transcripts were 6,369 minutes old. The mechanism adds no service and nothing outside the engine's own tree.
*   **`¶INV_LOOM_WORKTREE_DEFAULT_IS_MEASURED`**: worktree-per-lane is the default **on the strength of a measurement of the machine it runs on**, never on figures carried from another repository — disk headroom and workspace-link structure are properties of a checkout, so an imported number cannot establish them. The measurement that justifies it is **a marker planted in a package directory and read back through the workspace link**, with a control in the same invocation that fires: a `readlink` saying `../../` and a grep finding no absolute path are both satisfied by a mistyped path, while a marker that appears through one tree's link and is absent through a copied tree's link is the property itself. *Measured here 2026-10-23*: 100 of 100 links relative in the primary monorepo, the planted marker absent through a real worktree's link with the positive control firing through the main checkout's, 299GiB free and a real worktree at 524MiB. **Where that measurement does not hold the default flips to opt-in** — the operator picks *one shared tree* and the ledger records why — and the reading is not inherited: it is re-taken on a checkout nobody has measured.
*   **`¶INV_LOOM_PASS_ON_NEVER_DISCARD`**: an open row — a board awaiting a fold, a doc claim, an unanswered operator fork — may be **inherited** by a handing-over close and may never be **dropped** by one. It is written to the sessions root's `LOOM_INHERITANCE.md` — at an address **computed** from the active session directory rather than typed, per the template's *Where it lives* section — and read by the next startup pass. The rows are the state and the session log is the narrative; the inheritance file is authoritative for a row from the moment it is written, so no row has two owners. A field the writer could not fill reads `UNKNOWN — <why>` rather than blank, and a successor finding `UNKNOWN` in a field it needs **stops and reports that row** instead of acting on the rest of it — a partial row acted on silently rebuilds the original loss with no gap left where it used to be.
*   **`¶INV_HANDOVER_IS_A_ROW`**: a topic handed to another seat is a **row**, not only a message. A handover that exists only in a peer `SendMessage` and the sender's narrative log is forbidden, because **a topic its seat never picked up then looks exactly like one it took**, and the only way to tell is to read the sender's story. The row is opened **before** the send — the send is the moment a context most often ends, and a row written afterwards is the one the failure mode deletes — and it carries the seat's from-name **with its pane id**, the topic, its **member links**, and the delivery reading rather than a boolean, because a queued send is not a read and silence is not an ack. Measured twice eleven days apart in one weave: five seats handed topics, then seven, five acks returned as peer messages each time, and **not one became a row** on either occasion. The register is `## 📨 Seat handovers`, live in the log and copied to the inheritance, and `seatHandovers` gates Loom→Synthesis on its rows, clearing on an empty result written down like `docRegister`. **It is a different register from `## 🤝 Hand-over written`** — that one is a conductor handing its own state to its own successor, this one is a peer taking a topic or declining it. ⚠️ **`→` may not be spent on it**: `§INV_GROOM_MARKS_WHAT_IT_WRITES` already uses that marker to stop a drained inbox root being re-offered, and nothing on the receiving side reads it as an assignment.
*   **`¶INV_HANDOVER_CLOSES_ON_ACK`**: a handover row **stays open until the receiving seat acks it**, and the sender may not mark it done on sending — an un-acked handover is precisely the case the row exists to show, so a sender closing its own row has written the bug down instead of the handover. The row closes on the receiving seat's **own words**, and a **decline closes it as surely as a take**: `taken`, `declined — <why>` and `already done — <the evidence the seat gave>` all close it, on the `§INV_A_RULE_OWED_HAS_AN_OWNER` argument that a topic refused on purpose and a topic dropped on the floor read identically once the session ends. A bare `acked` is an unworked row and blocks Synthesis, like a bare `open` on a board. **An ack that reached only the sender's chat is not an ack** — the reply is transcribed onto the row, because an ack that is only a peer message is the original defect restated one step later. An open row therefore **travels to the inheritance** (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`) and is the kind most exposed at a hand-over, since the party who owes the ack is not the party handing over; a successor **re-measures the pane before acting on one**, because a seat renamed or a name since taken by another session makes a handover sent nowhere read exactly like one sent.
*   **`¶INV_LOOM_WAITING_IS_ROWED`**: a lane's wait is written down, never only remembered. Every block a lane reports opens a `## 📡 Relay / Conflict` entry carrying `Waiting on` in the lane's own grammar (`assets/LOOM_AGENT_DIRECTIONS.md` § Progress reporting), `Since`, and its resolution, and the waiting thread's `🧵 Ledger` `status` cell carries the glance — a **closed grammar** naming what it waits on, how long, and what it does meanwhile, because `in flight` on a thread that has stopped is not a reading but the absence of one. The *waiting-on graph* is therefore the rows rather than the conductor's context: a graph a context clear deletes is a cycle rediscovered from nothing, and before this nothing durable said **why** a lane was waiting until a hand-over, which is the moment it is hardest to reconstruct. **No fourth register was added for this** — `📡 Relay / Conflict` and `🅿️ Parked` were extended and the `🧵 Ledger` `status` cell was closed. `ledgerMaintained` gates on the rows.
*   **`¶INV_LOOM_STALL_IS_SWEPT_NOT_SENSED`**: the *silence past a timeout* poll runs `engine lane-stall "<sessionDir>" [--minutes N]` and **no second detector is written**. It lists each not-done lane whose freshest signal is older than the threshold with minutes-since-transcript, minutes-since-its-last-`[TAG]`-log-heading and a state — `done` · `parked` · `running` — exits **3** when any lane is stale, and is read-only. It runs **at each loop gate as a cadence taking no slot**, and **before the conductor settles in to wait**, because the gate fires on a unit of progress and a weave where nothing lands never reaches one — a gate-only sweep is absent in the case it exists for. It is an **external** reading, which is the point: every other progress signal here is self-reported by the lane, and a hung lane emits none of them while an absence is indistinguishable from quiet work. **`parked` is the operator's symptom** and rows under `🅿️ Parked` as `stopped without handing back`, kept distinct from a thread the conductor parked for a reason, with the lane's LOG PATH and its next move. Two readings are forbidden: it answers **state, never reachability** (a dead lane's transcript persists, so `parked` is not `gone`; only a `SendMessage` attempt settles addressability), and **`0 lanes seen` is never reported as a clean weave** — it is reconciled against the ledger's live rows, since a sweep blind to this weave's lanes reports no stale lanes, which reads as reassurance. The sweep identifies a lane by a bracketed tag at the **start of the dispatch prompt**, which is why `¶INV_LOOM_AGENTS_NAMED_BY_THREAD` binds the prefix to the prompt as well as the `description`.
*   **`¶INV_LOOM_BOARD_AT_A_BOUNDARY`**: the `/decide` **pass** runs on the gate cadence; the **board renders at a boundary**. A board per unit of progress is **refused, with the cost**: counted from `/decide` §4's declared steps, each one is a dispatched render subagent, an orchestrator integrity pass, two publishes, a captured `docId`, then a fold and a state-doc read at a later gate — and unlike anything else here it acquires an obligation, since §4 blocks a wrap-up on a board published and never read and `decisionPasses` gates Synthesis on those rows, so the obligations accumulate across a loom that lands a thread every few minutes. That is **strictly more** than the weave-status page this file already refuses per gate for a smaller cost shape (`¶INV_LOOM_WAKES_ARE_THE_BILL`). So the loom passes `--no-board` where every mined fork is decidable in chat now by the operator who is present — losing nothing, because §5's confirm was always the authority and §6's record is written either way — and a board earns its render where a page does what a chat question cannot: the fork must reach somebody who was not in the session, must survive this session into an inheritance, or must collect an answer **in the gap** when nobody is at the gate. The hand-off boundary is where all of those hold, so it always renders. **The rhythm is gate → gate → board at a boundary**, never board → board; and *reports between* are the live ledger, already free at every gate, whose gap was never frequency but content — it never said why anything was waiting.
*   **`¶INV_LOOM_A_FORK_ARRIVES_DECIDABLE`**: a question reaching the operator carries what it takes to answer it, and keeps the record of what answered it. The live `🔓 Open claims` block holds one row per unanswered fork — **promoted from the inheritance template, where it was the only copy**, which made an unanswered fork durable only at a hand-over: the one moment a lane sits waiting was the one moment nothing was written. Each row carries a **pointer** to its prepared `§FMT_DECISION_CARD` — `/decide` §6's record, which holds the options as framed and, per `¶INV_REJECTED_OPTIONS_ARE_RECORDED`, what was decided against — and **never a copy of the card's fields**, which would drift from the format and break `§INV_LISTS_INSTEAD_OF_TABLES`. The card was never what was missing; **a path to it from the loom's state was**, since `/decide` §6 routes only a *board's* handles to `🗳️ Boards` and a fork decided in chat has no board row. Each row also names what the thread does **meanwhile** — `/decide` §5's vocabulary, asked when the fork is raised rather than when it is answered — because a thread idling on an unanswered question by default is the stall, and `idle` is legitimate only carrying why. **A row may not close as a bare `answered`**: it closes with the record path, or states what leaves it open (`open — decided in chat at gate N, not yet recorded`), because an answer with no artifact leaves a successor holding a decided row with no record of what decided it. The rows are worked at every gate before fresh forks are mined, carried to the inheritance **transcribed rather than re-mined**, and ride `decisionPasses` rather than a second proof, since a fork exists only where a pass ran.
*   **`¶INV_TICKETS_PRESENTED_BEFORE_ASKED`**: before any question to the operator that mentions a tracker ticket — an `AskUserQuestion`, an interrogation round, a decision card, a `/next` proposal, a loop gate — the agent first prints in chat a list with one entry per ticket the question mentions, in the shape `[KEY](url) — Title [Status since HH:MM D Mon] — two-line summary`. **A thread or topic whose slug is a ticket key counts as a mention**, so a gate that names threads lists their tickets. The key is linked per `§FMT_TICKET_LINK`; the status and the time it began come from the tracker (`get_issue`: its status, with *since* taken from the state-history entry for the current status, else `startedAt` — never `updatedAt`, which moves on any comment or label), shown in the operator's local time; the summary is two plain lines on what the ticket is and where it stands. **Why**: a ticket key inside a question asks the operator to recall what that ticket is, and the list puts it in front of them before they choose. This list is the one chat block `§CMD_ASK_QUESTION_WITH_COMPLETE_CONTEXT` allows ahead of a question, and it holds the entries and nothing else — no recommendation, no options, no recap; the question body still carries its own complete context. **If the tracker cannot be read**, print the entry with the key and `status unread` rather than skip it — a missing entry hides the ticket the question still names.
*   **`¶INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY`**: a wave's lanes are brought back together by the **conductor**, at the **boundary** — every thread in the `🌊 Wave` block's fanned-out set landed or parked with none reading `running` — and **not** at the loop gate, which fires on one thread landing and would merge a lane at a time, which is the per-lane integration this step exists instead of. The base is the **session branch, captured at Setup as a name and a sha** because it is not reconstructable later; a loom with no recorded base reports that and does not integrate. The order is **landing order, first-landed first** — already written down in each lane's `/snapshot` Outcome, and it makes the loser the **later lander**, so the loom keeps `§INV_LOOM_FIRST_CLAIM_WINS`'s single precedence rule rather than acquiring a second. Merging is **`--no-ff`**, which is load-bearing and not cosmetic: the merge commit engages `/pr`'s own refusal to cherry-pick merge commits and so forces the whole-branch path, making the declined per-lane PR structurally unavailable instead of merely remembered. **On a conflict the conductor aborts the merge** — session branch left at its exact pre-merge sha, **never resolved, never `-X`**, the idiom `/pr` binds its cherry-pick to — and **resumes the later lander by name** with its branch, the base sha and the `--diff-filter=U` paths; **that lane merges the session branch INTO its own branch in its own tree**, never the reverse, because shared ground the earlier lanes already landed on is not a resolution surface. A second conflict on one lane is a hard-floor escalation rather than a loop. **This step and the file partition are two answers to one question and a loom runs exactly one**: the partition is *prevention* and a merge is *detection* — the better instrument, since it finds the collisions that happened in the text rather than the ones predicted at allocation — so under worktree-per-lane the conductor computes **no** partition and brokers **no** claims, and under one shared tree there is nothing to merge and the row reads `nothing to merge — shared tree`. The `wavesIntegrated` proof gates Loom→Synthesis on the `🌊 Wave` rows and **clears on an empty result written down**, like `docRegister`. **Where a conflicting lane cannot be resumed the step STOPS and escalates** — `engine lane-stall` cannot settle it, since it answers state and never reachability, so only a `SendMessage` answering *no transcript found* does — and the conductor neither resolves the conflict itself, nor hands it to a fresh lane that did not write the code, nor drops the wave: no fallback has been chosen, and `§INV_LOOM_PASS_ON_NEVER_DISCARD` makes passing the decision on the only legitimate close.
*   **`¶INV_LOOM_GATE_RUNS_ON_THE_INTEGRATED_TREE`**: the once-per-wave suite runs against the **assembled** tree — the conductor's own, on the session branch, after the last merge lands — and the `🌊 Wave` row names the **sha** it ran against. Forbidden: running it in any single lane's tree, and running it on a **partially** integrated wave where one lane merged and another's conflict is still open. That wave records `suite deferred — <threadId> conflict open` and runs nothing, because a green recorded against an assembly nobody will ship is worse than an unrun gate — it is an unrun gate that reads as evidence. The economy that justifies running the suite once per wave rather than once per thread was measured on an assembled tree, so a reading taken anywhere else does not support the default that produced it.
*   **`¶INV_LOOM_HARD_ESCALATION_FLOOR`**: cyclic deadlock · build-fails-after-retries · scrutinize MUST-FIX · thread loopback always reach the user, even under Automagic.
*   **`§INV_RIDE_NEVER_ACTIVATES`**: a composed protocol-tier skill invoked by the conductor **owns no session** — it never runs `engine session activate` or `engine session phase` and writes nothing to `.state.json`, because there is one `.state.json` per session directory carrying a single `currentPhase` and a composed pass advancing it overwrites the conductor's own position in the only file the host has. `/direct` declares the contract in its own `## Composed entry` section and does not execute its phase orchestrator when composed; `/interrogate` already held it. **A conductor that finds a composed skill transitioning its phase stops and reports** rather than continuing from a phase it did not set.
*   **`§INV_NO_DESTRUCTIVE_GIT`**: parallel builders never run tree/index-destructive git. Committing is `/snapshot`'s job.
*   **`§INV_A_PROBE_WRITES_ITS_ANSWER_DOWN`**: a conductor asks a lot of side questions, and an ad-hoc `Agent` dispatched to answer one writes nothing by default — its result dies with the conductor's context while the ledger shows no gap. Every answer-shaped dispatch names a `builds/<slug>.md` path in its brief. Measured here: 7 of 22 agents in one day were transcript-only, including the sweep of every lane log's *"named, not fixed"* — the loom's own leftover inventory, recoverable afterwards only by mining subagent JSONL.
*   **`§INV_OFFER_DONT_FORCE_SKILLS`**: triangulate, snapshot, pr, council are offered, never forced.
*   **`§INV_LISTS_INSTEAD_OF_TABLES`**: no markdown tables in this file (the ledger's table lives in the emitted `TEMPLATE_LOOM_LOG.md`, where tables are allowed).
