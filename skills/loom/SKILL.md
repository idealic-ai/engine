Weave many tickets through the build pipeline at once. `/loom` takes a batch of tickets, runs each as its own **thread** — triangulate → interrogate → build → scrutinize → snapshot → pr → council — and fans the threads out in parallel while a **conductor** (the parent) keeps them from colliding: it brokers who touches which files, relays messages between the build agents, detects deadlocks, and escalates the decisions it cannot make: they reach your manager (the operator if you have none — § The manager chain). A live ledger tracks where every thread is and what documentation the weave has falsified; the session loops — you add threads, adjust a thread, or wrap up — and never rushes to close. When it does end, it writes an **inheritance**: the open rows, in a file a fresh conductor can read without the predecessor's log.

# /loom Protocol (The Conductor)

Execute §CMD_EXECUTE_SKILL_PHASES.

### What /loom is (and is not)

*   **It is** a **parallel-thread orchestrator**. A *thread* is one ticket walking the full chain; many threads run at once. `/loom` composes the building-block skills — it dispatches `/triangulate`, `/ticket`, `/communicate`, `/interrogate`, `/decide`, `/probe`, `/experiment`, `/build`, `/scrutinize`, `/revise`, `/snapshot`, `/pr`, `/council`, `/prove`, `/prove-explore`, `/graph`, `/groom`, `/inbox-post`, `/inbox-next`, `/ticket-search` — and its own work is the conducting: partitioning files, relaying agent messages, brokering conflicts, detecting deadlocks, escalating, keeping the ledger, reading the inheritance a predecessor left, and writing the one its successor reads.
*   **It is NOT** a builder or a writer. `/loom` never writes code, never posts to Linear, never touches git directly (`¶INV_LOOM_COMPOSED_WRITES`). Every mutation happens *inside* a composed skill, under that skill's own confirm or the waiver that skill itself provides for an unattended caller (`/snapshot --yes`) — `/snapshot` posts the status and commits, `/pr` opens the PR. The conductor orchestrates; the sections do the work.
*   **`/loom` vs `/coordinate`**: `/coordinate` is a persistent fleet monitor that answers standing worker questions. `/loom` is task-scoped — it weaves a specific batch of tickets through a specific pipeline and closes when the batch is done. It reuses coordinate-grade relay/escalation mechanics without being an immortal monitor.
*   **`/loom` vs `/do`**: `/do` is one free-form thread of work. `/loom` is *many* threads at once with a conductor between them.

### The thread (`¶INV_LOOM_THREAD_IS_A_TICKET`)

A **thread** = one ticket/task through the full chain:

> triangulate → interrogate → build → scrutinize → snapshot → pr → council

The **interactive** front (triangulate, interrogate) and the **decision** points (triage, snapshot/pr confirms, council findings) involve you or the conductor; the **autonomous** middle (build, scrutinize) runs as parallel background agents. Not every stage fires on every thread — `/triangulate`, `/snapshot`, `/pr`, and `/council` are **offered** per the Setup dispositions and the offer-don't-force rule (`§INV_OFFER_DONT_FORCE_SKILLS`) — while the **ticket-disposition ask** and **interrogation** (per its disposition) are **mandatory** (`¶INV_LOOM_MANDATORY_STEPS`), never turned off by the Autonomy disposition. 🔍 **Scrutinize sits between those two shapes, and the distinction is new.** Its *cadence* is the **Scrutinize** disposition's answer — defaulting to every build lane — rather than the Autonomy disposition's; and under every position of it, *off* included, a lane that was not scrutinized **says so on its ledger row**, and the `/pr` offer standing in front of that lane reads the row (`¶INV_LOOM_SCRUTINY_IS_DECLARED_AND_ROWED`). Calling it mandatory in prose is what this file did in four places while twenty-eight lanes across four seats went unread.

### Thread identity & agent naming (`¶INV_LOOM_AGENTS_NAMED_BY_THREAD`)

Every thread gets a **threadId**: the ticket key `ENG-XXXX` when there is one, else a short SCREAMING slug the conductor derives from the task — `FACTS`, `INTRODOC` (≤12 chars, `[A-Z0-9-]`, starting with a letter, never ending in a hyphen, digit-suffixed on collision: `FACTS`, `FACTS2`) — for a **winged** (un-ticketed) task. A meaningful slug beats a bare letter: `FACTS:build` tells you what the thread is; `A:build` doesn't. Every agent `/loom` spawns belongs to a thread at a stage — `ENG-3141:build`, `ENG-3141:scrutinize`, `FACTS:build`.

**The fleet/status view shows the sub-agent TYPE (`builder`, `writer`, …), not a label you set — so the threadId will NOT appear on its own. You MUST push it into what the agent emits, or the threads are indistinguishable** (the exact symptom this rule exists to prevent). Each of these is required:
*   **Lead the spawn `description` with the threadId in brackets** — `description: "[ENG-3141] build extract-totals"`, `"[FACTS] scrutinize parser"`. That bracketed prefix is what surfaces in the status row next to the `builder`/`writer` type.
*   **Lead the dispatch `prompt` with it too — as its literal first characters**, before any prose: `prompt: "[ENG-3141] You are thread ENG-3141 in a /loom weave. …"`. **The stall sweep below identifies a lane by matching a bracketed tag at the START of the dispatch prompt, so a brief that opens `You are thread ENG-3141…` is a lane the sweep cannot see** — and a sweep that sees no lanes reports no stale lanes, which reads as a clean weave. *(Measured: of this session's lanes whose brief named the session, every one carried its tag later in the prose and none at the head, so the sweep counted zero lanes while the weave ran. The description and the prompt are different strings, and the rule had only ever bound the first.)*
*   **Instruct the agent to prefix EVERY line it emits** — its status/progress reports, its shared-log entries, and its `SendMessage`s to the conductor — with `[<threadId>]`. A build agent's log entry reads `## [ENG-3141] tests green`, not `## tests green`. This is stated in `assets/LOOM_AGENT_DIRECTIONS.md`, which every agent's context pack carries.

This prefix is load-bearing: the ledger, the SendMessage relay, and the fleet view all tell threads apart by it. **Never spawn a loom agent whose `description` and output are not threadId-prefixed.** A winged thread's slug threadId **upgrades to the new `ENG-XXXX`** if a ticket is filed for it — the ticket create/update step runs *after* triangulate + interrogate, before the build, so the ticket carries the scoped understanding.

### The Setup dispositions

Asked once at Setup (`AskUserQuestion`, one per disposition — not `§CMD_SELECT_MODE` mode files; a seat with a parent puts them up as one /ask instead, per Setup's *Ask the dispositions*). They parameterize the whole session and the escalation/relay reference file:

*   **Autonomy** — how much the conductor decides vs. asks: **Automagic** (proceed autonomously; auto-resolve conflicts where safe; escalate only on the hard floor) · **Careful** (escalate liberally; gate more) · **Allow agents to decide** (agents use judgment on when to escalate; conductor relays). **Autonomy tunes how much the conductor *resolves without asking* — it NEVER licenses skipping a mandatory step.** Automagic that skips the ticket-disposition ask or the interrogation is a bug, not autonomy (`¶INV_LOOM_MANDATORY_STEPS`). 🔍 **Scrutinize is the Scrutinize disposition's to answer, and Automagic may not substitute its own reading of it** (`¶INV_LOOM_SCRUTINY_IS_DECLARED_AND_ROWED`) — a conductor deciding a lane is not worth a critique under *every build lane* is changing the disposition, which is the operator's to change and not the conductor's to interpret.
*   **Council** — *when* `/council` runs, chosen once: **selective before PR** (a panel *before* the PR opens, only on threads you flag) · **auto after each PR** *(default — a panel on every thread once its PR is up)* · **none** *(not recommended)*. The timing is the whole distinction: *before PR* reviews the work before it's proposed; *after PR* reviews the proposed change.
*   **Interrogation** — how much `/interrogate` runs per thread: **Reasonable** (a few rounds → `/interrogate --depth quick`) · **Thorough** (→ `--depth deep`) · **None** (skip the interrogate stage).
*   **Detail importance** — how much granular detail matters, i.e. how hard over-zealous `/scrutinize`/`/council` findings get filtered before they reach your manager (the operator if you have none — § The manager chain): **Low / ship-it** (downgrade nitpicks; only genuinely-blocking MUST-FIX surfaces; lean on recommended defaults) · **Balanced** *(default)* · **High / every detail** (surface everything for explicit decision). Low does NOT mean auto-accept — a blocking finding always surfaces.
*   **Scrutinize** — *when* an independent `/scrutinize` pass runs and *how often*: **Every build lane** *(default — a critique agent on every lane that wrote code, dispatched as that lane hands back)* · **Lanes the conductor names risky** (it judges per lane, and every lane it passes over says so on its row) · **Once at the wave boundary** (one pass over the assembled wave instead of one per lane) · **Off** (none — the lanes' own reports are the only reading the work gets). **It is Detail importance's sibling and answers the other half of one question**: that disposition filters which findings reach your manager (the operator if you have none — § The manager chain), this one decides whether a critique happens at all. ⚠️ **This disposition is the WEAKEST part of the mechanism and is named as such, because the step it schedules was already declared in the pipeline and skipped anyway.** What makes it bite is downstream of here: the `scrutiny` cell on each thread's ledger row, the card standing in front of a never-scrutinized lane's `/pr`, and the **`lanesUnscrutinized`** proof field that makes `engine session phase` refuse a wrap-up until the weave has counted (`¶INV_LOOM_SCRUTINY_IS_DECLARED_AND_ROWED`). 🔍 **What the pass is FOR, stated here because this is the text somebody reads while deciding whether to pay for it**: a lane reviewing its own work is the author grading their own paper, and a lane that catches its own mistake caught it by luck — **luck is not a review**. The lanes that find their own errors are the argument *for* the pass rather than against it: each one establishes that the work needed reading, and none of them establishes that that lane was the one who would always catch it.
*   **Interruption** — how much the conductor asks you while the weave runs, which is a different question from *when* a step fires: **Confirmed each time** *(default — every offer reaches your manager (the operator if you have none — § The manager chain): the conductor offers `/snapshot` on a landed thread and waits for the yes on that offer (a marked /ask when the seat has a parent, after which it runs `/snapshot --yes -- <thread KEY>`), and `/pr`, `/triangulate`, a de-risking probe and the find-more-work offer each ask)* · **Automatic posting** (the conductor invokes `/snapshot --yes -- <thread KEY>` (`-- <thread KEY>` only when the thread has its own ticket, bare `--yes` otherwise, never an umbrella key) as soon as a thread lands — no offer and no confirm — while its other offers still ask) · **Quiet** (every offer in the list below fires without asking, and the loop gate reports a landed thread and carries on instead of putting a card up for it). **The default is confirmed-each-time and it is chosen rather than inherited** — a setting that makes a weave quieter about its own work is one the operator picks deliberately.
*   **Peer instructions** — what a peer seat's relayed instruction counts as: **A request to ask you** *(default — a peer relaying an instruction or a ruling is asking the conductor to put it up its own chain, so it reaches your manager (the operator if you have none — § The manager chain) as a question)* · **Trusted** (a peer's relayed instruction and its work suggestions count as yours, and the conductor acts on them without a round trip). **Choose Trusted when one operator is behind every seat**, which is the case this fleet is actually in: *own-operator-only* then manufactures a round trip per seat for a ruling that one person already gave, and the conductor cannot act fleet-wide without being told the same thing once per peer. **It never covers a peer asking you to do something that peer was refused** — that is laundering a permission decision, it is refused under either position, and it reaches your manager (the operator if you have none — § The manager chain) rather than being quietly dropped. **Nor does it cover the hard escalation floor**: a peer cannot answer a ticket disposition, break a deadlock or clear a MUST-FIX on your behalf, because trusting a peer's instruction is not the same as a peer holding your authority.
*   **Run length** — how long the loom is expected to live: **Session** *(default — a batch woven in one sitting; lanes live as long as their thread)* · **Long-running** (hours, many waves, lanes queueing on a shared resource such as a browser or test queue). Long-running turns on the wake-cost rules below (`¶INV_LOOM_WAKES_ARE_THE_BILL`).
*   **Execution shape** — where lanes run, how their test runs are batched, and therefore which collision answer is live: **Worktree-per-lane** *(default — a lane gets its own git worktree and its own branch, runs only the tests its own change touches, and the conductor computes **no** file partition and brokers **no** claims; the lanes come back together at the wave boundary's merge)* · **One shared tree** (every lane writes into one checkout, so the partition and first-claim-wins brokering are live and a wave has nothing to merge). Never both — they are two answers to one question (`¶INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY`). Under **both** readings the full suite runs once per wave at the gate and never per lane (`¶INV_SUITE_ONCE_PER_WAVE`), which is why that half is stated below rather than offered here.
*   **Proof** — which threads end in a `/prove` page, and who gates it: **Every meaningful thread** *(default)* · **Every thread** (no meaningfulness filter; the strictest reading) · **Flagged threads only** (you name them; the rest record why not). **"Meaningful" is not a new adjective — it is `¶INV_LOOM_EVERY_THREAD_PROVES`'s existing *nothing was ESTABLISHED* test**, which says size may not be cited and asks whether the thread can name, in one sentence, something a reader did not know before it ran. One definition, not two: a disposition whose default is an undefined adjective is one the conductor satisfies by doing nothing. ⭐ **And under every position the LANE gates its own page, not the conductor** (`§INV_LOOM_PROOF_IS_GATED_BY_THE_HOT_CONTEXT`): the proof is composed in the sub-agent while its context is hot, `/prove`'s own integrity pass is the gate, and **the conductor does not re-check the lane's claims or re-gate the published page.** The conductor still owns the *variant* choice and the *exemption* call, because only it can see the weave.
*   **Rounds** — whether the conductor proposes a sweep, an integrate, a research or a doc round unasked: **Meaningful suggestions** *(default — a round is proposed when its trigger fires **and** it would establish something, by the same test as Proof)* · **All** (propose on every trigger, including the ones that would add nothing) · **None** (propose none; you ask). These fire as **triggers rather than menu slots** — the declared list below is the whole of it, and a round that is not in it is not a round the conductor invents.
*   **Merge strategy** — how **this loom's own lanes** reach the trunk: **Wave integration branch** *(default — lanes merge onto the session branch at the wave boundary and go out as ONE pull request for the assembled wave)* · **Stacked lane PRs** (each lane branches off the previous rather than off the trunk, so every lane keeps its own pull request and its own diff for individual review while only the tip runs the full suite) · **Direct to trunk** (each lane lands on its own as soon as it is green). ⛔ **It binds the loom's own dispatched lanes and NOTHING ELSE.** A peer seat's branch arriving with its owner's go is not work this loom may hold back into a wave of its own; it lands direct, whatever this disposition says.
*   **Auto-continue** — whether the conductor keeps working when a turn would otherwise end: **On** *(default)* · **Off**. On, the `Stop` hook injects this gate's own read-only cadences in a live weave and `/next` when the session is cold, so the sweeps I would otherwise defer fire on a trigger rather than on memory. **Off writes `autoContinue: false` into `.state.json`**, which is the only value that disables it — absent means on. ⛔ **Because the default is ON, the CEILING is the only thing between this and a loop**: three consecutive continues, reset on any turn the hook does not block, plus a no-op when the last turn ended on an `AskUserQuestion` so it cannot answer the operator's question on their behalf. **Choose Off for a weave where every turn should end with a person**, and say so in the ledger header.
*   **Escalation route** — where this conductor's escalations go (operator ruling, 2026-10-29 01:00): **Up the manager chain via /ask** *(default when the seat has a parent — each escalation goes as an /ask to the live parent, floor and reserved items marked `reserved-for: operator`)* · **Straight to the operator** (the chain is skipped and every escalation is addressed `to: operator`) · **Both** (everything goes to the manager first, and anything on the hard escalation floor also goes as a copy to the operator). A seat with no parent goes to the operator under every position, so the question exists only when the seat has one, and that seat does not block Setup on it: it starts on the default, records `chosen by: default`, and puts the question in its Setup ask (*Ask the dispositions*). **It changes only the destination, never the content**: the floor's items, the `reserved-for: operator` mark and the rule that a waiting conductor keeps working are the same under all three. How each position routes is defined in § The manager chain.

🔍 **What each Scrutinize position COSTS, honestly, because *off* is a legitimate answer and a scolding is not a cost (`¶INV_LOOM_SCRUTINY_IS_DECLARED_AND_ROWED`).** **Every build lane** is one more agent per lane — its own dispatch, its own context over the Build Report and the diff, and a combined triage round whose MUST-FIX is already on the hard escalation floor; on a six-lane wave that is six critiques and one triage, and it is the position that costs the most and hides the least. ⚠️ **It roughly DOUBLES the lane count of a programme already spending most of its bill on wakes** (`¶INV_LOOM_WAKES_ARE_THE_BILL`), and that is a real number rather than a rounding error. **The argument for taking it as the default anyway is the skip rate, not the price**: at a measured 100% skip a blunt default is what produces evidence, and tuning down from it is a decision somebody can make on readings. Shipping the risk-judged variant first inverts that — the position whose judgement is unconstrained is the one that discovers everything is low-risk, which is this session's record arriving by a different route. **Risky lanes only** is the cheapest position that still reads something, and what it costs is that the judgement belongs to the conductor — the same party whose judgement produced the measurement below — which is why it is the position most worth a row. **Once at the wave boundary** pays for one pass instead of `<k>`, and gives up attribution and heat: it reads an assembled tree whose lanes are cold, so a finding costs a re-derivation to place and the lane that wrote the code is no longer there to answer for it. **Off** gives up the only independent reading the work gets *before* it is proposed; what you keep is each lane's own report plus `/pr`'s Copilot and Codex pass, which arrives after the change has been put in front of other people. Choosing it is allowed, and the price is that it is recorded rather than assumed.

🔍 **The default is *every build lane* on a measurement, and the measurement is a FLEET reading rather than one seat's** (`¶INV_LOOM_SCRUTINY_IS_DECLARED_AND_ROWED`). *2026-10-28, four seats in one day*: roughly **twenty-eight build lanes with one independent critique between them** — this conductor dispatched about ten and ran the pass on none (its own reading), `domain:Platform` three rounds with none and two pull requests already opened on the lanes' self-reports alone, `domain:Language` eleven lanes with one critique and `IDE-101` landed on `main` from a one-line test fix read only by the lane that wrote it, `domain:Agent` four. **The last three are relayed from the seats that took them and have not been repeated here** — the `ran`/`relayed` discipline the ticket-disposition step states. Every one of those weaves was running a file that already called this step mandatory in four separate places. ⭐ **That EVERY seat asked reported a failing count, unprompted, is itself the argument**: this was not one conductor being careless, it was a step named in the declared pipeline and skipped by everybody holding the same file — which is the strongest case available that naming it a fifth time changes nothing (`§INV_A_RULE_IN_PROSE_IS_NOT_ENFORCED_UNTIL_A_CHECK_CAN_FAIL`). The figure to carry is not that the step gets skipped sometimes; it is that **nothing in the tree reddened across twenty-eight chances**, which is why this disposition arrives with a ledger cell and a card at the next move rather than on its own. **And a weave that has been skipping it writes its own count down before it starts complying**: every seat above recorded the count as the finding, and a fleet that keeps only the remedy has lost the reason it needed one.

🔍 **What the new default does to work ALREADY IN FLIGHT, which every seat adopting it meets within minutes (`¶INV_LOOM_SCRUTINY_IS_DECLARED_AND_ROWED`).** A lane that has handed back and is not yet proposed gets the pass. **A lane whose operator has already confirmed the next move is NOT retroactively blocked — the gap is DISCLOSED to them instead**: it goes out, and the conductor says plainly that it went out with no separate scrutinize pass, on the row and in the sentence that reports the landing. Blocking it would re-litigate a decision already taken, on grounds the operator did not hold when they took it; hiding it would turn the adoption into a story rather than a measurement. Disclosure costs nothing and loses nothing, which is why it is the rule rather than a concession. *Worked case, `domain:Agent`, 2026-10-28, relayed*: four lanes — two had just handed back and took the pass, two were already confirmed and went out disclosed. **It generalises past this disposition**: whenever a new default meets a decision taken under the old one, disclose rather than re-open. And it is the same mechanism as the `/pr` override below, read at a different moment — in both, the work proceeds and the row says what the reviewer is not getting.

**The worktree default rests on a measurement of this machine, and it is the operator's to re-take** (`¶INV_LOOM_WORKTREE_DEFAULT_IS_MEASURED`). What makes a per-lane tree correct by construction is that the checkout's workspace links are **relative** symlinks, so a copied tree keeps its links inside itself instead of reaching back into the original. *Measured here 2026-10-23, on this machine*: a marker planted in the main checkout's `packages/shared/` was found through that checkout's own `node_modules` link and was **absent** through a real worktree's link, both links reading `../../packages/shared` — so the worktree's link resolves into the worktree's own package. 100 of 100 links in the primary monorepo read relative, 0 absolute; a constructed absolute link in the same invocation correctly read the original's marker through a copied tree, which is what makes that absence a reading rather than a mistyped path. Disk: 299GiB free, and a real worktree measured 524MiB without dependencies, so four lanes cost ~2.1GiB (~13.3GiB if each installs its own). **Choose *one shared tree* on a checkout where that does not hold** — absolute workspace links, or headroom that four trees would exhaust — and say so in the ledger. The reading is a property of a machine and a checkout, so it ages: `readlink` a workspace link and plant a marker rather than trusting this paragraph on an unfamiliar repository.

**The dial that arms `assets/__tests__/wave-integration.test.sh` has landed, so that harness is now red by design.** It holds cases asserting the wave boundary's merge half — unreachable while lanes share one tree — and it arms itself off this section. Armed with no integrated wave to read is a **failure, not a skip**: it says the mechanism is specified and unexercised, and it clears when a loom has actually integrated a wave and `WAVE_LOG` points at that loom's log. Run it in any change that touches this section.

**Interruption reaches `/snapshot`'s own confirm, and that is the half worth stating plainly.** `/snapshot` takes `--yes`, a flag it defines itself for a caller that has already decided, which waives its batch confirm while declining the two actions that must not land unwatched. So **Automatic** invokes `/snapshot --yes -- <thread KEY>` (`-- <thread KEY>` only when the thread has its own ticket, bare `--yes` otherwise, never an umbrella key) and a landed thread costs you no question at all. When a bare run's Outcome stamps `auto-filed <KEY>`, that key becomes the thread's key, so every later snapshot of the thread, the closing one included, runs `/snapshot --yes -- <KEY>`. **The change that made this honest lives in `/snapshot`, not here, and it had to**: an invariant in this file cannot inject a step into a skill it merely invokes, and removing one is that same limit read backwards (`§INV_LOOM_COMPOSED_WRITES`; `§INV_LOOM_HANDBOOK_BEFORE_FILING` gives the reasoning at length). A disposition promising a silent post while `/snapshot` still asked would have been a rule nothing could enforce (`§INV_A_RULE_IN_PROSE_IS_NOT_ENFORCED_UNTIL_A_CHECK_CAN_FAIL`) — the flag is what makes the promise keepable, and a loom running against an older `/snapshot` that does not know the flag simply gets the confirm, which is the safe direction to be wrong in. The price is unchanged: `/snapshot` spawns its reviewer and runs the gates before its confirm would have been reached, so **Automatic** pays that run even on a thread you would have declined at the offer.

**What *Quiet* covers is a list rather than a feeling, because a setting that reads as *bother me less* gets stretched to whatever the conductor finds inconvenient.** It fires these without asking, and they are the offers whose cost is time or a reversible artifact: **`/triangulate`** on a new thread · a **de-risking probe or experiment** when interrogation surfaced an open question · **grouping adjacent threads** into one · **`/prove`** at a thread's end · **`/pr`**, on the reasoning that a pull request proposes a change and is closed again at no cost · **harvesting a thread's findings** into inbox drops · **`/groom`** to cluster them · and **pulling more work** when a thread lands and a slot is free, bounded as always by the global cap. It also lets the **loop gate report a landed thread and carry on** rather than putting a card up for it — which is the change that actually makes a long weave quiet, since the gate is the thing that fires most.

**Five things no position of this setting reaches, named rather than implied.** 🔍 **The scrutiny card in front of a never-scrutinized lane's `/pr`** is the newest of them (`¶INV_LOOM_SCRUTINY_IS_DECLARED_AND_ROWED`): *Quiet* fires the `/pr` offer unasked, so a card riding that offer would disappear in the position a long weave spends most of its time in, which is where the gap is widest. The **wave boundary's merge** keeps its confirm — it is the loom's one unmediated git write and the only place a conflict is resolved, so it is the last thing to go quiet. **`/ticket` and `/inbox-post` keep theirs**, because filing asks a question about scope rather than reporting a result; `/snapshot --yes`'s auto-file of un-ticketed work is the one filing that does not ask, because it files only with no duplicate candidate and after `/ticket`'s Subject Gate and the project's Ticketing Strategy pass, and aborts otherwise. **The hard escalation floor is untouched** (`§INV_LOOM_HARD_ESCALATION_FLOOR`) — the ticket-disposition ask, a cyclic deadlock, a build failing after retries, a scrutinize MUST-FIX and a thread loopback are each a decision, and the floor exists precisely so that no disposition can make a weave silent. And **a composed skill's own confirm is never removed from here** — `/snapshot`'s goes only because `/snapshot` itself provides `--yes`; where a skill offers no such parameter, this setting removes the conductor's offer in front of it and nothing more (`§INV_LOOM_COMPOSED_WRITES`).

**Still two options and not three — and the middle reading is now answered inside `/snapshot` rather than refused here.** The option the set never offered — comments automatic while a status move or a description rewrite still confirms — reached for a real risk: a description edit is a full-field replace that can erase content a person wrote, where a comment only appends. `--yes` answers it by **declining rather than asking**. Under it `/snapshot` skips a description rewrite and hands the drafted body back in its own report, and skips a commit whose gates came back red or unrun; it aborts outright where the target ticket itself is uncertain, since a waived confirm is also a missing warning about the wrong issue. The two actions a human was reading the confirm for therefore never land unwatched, and a third option here would re-ask a question the skill already answers — in the one place that cannot enforce the answer.

**It is orthogonal to the per-thread snapshot cadence stated under Conducting below, and the two answer different questions.** The cadence rule governs *when* `/snapshot` fires — per thread at its landing, never several landed threads behind one confirm. This setting governs *whether anyone is asked before it fires*. Under **Confirmed each time** a six-lane wave produces six offers and six batch confirms; under **Automatic** the same six `/snapshot` runs and no questions at all. Either way it is **six runs, one per landed thread** — the batching the cadence rule refuses is unreachable from this setting in both of its positions.

**Nothing on the hard escalation floor is a post, so this setting never touches it** (`§INV_LOOM_HARD_ESCALATION_FLOOR`). The ticket-disposition ask, a cyclic deadlock, a build failing after retries, a scrutinize MUST-FIX and a thread loopback are each a decision, and a decision is not something a posting skill carries outward. The floor exists so that no disposition can make a weave silent, and this one has no contact surface with it. What it leaves alone is worth naming rather than implying: **`/pr` keeps its offer**, because a pull request proposes a change rather than reporting a status; **the wave boundary's merge keeps the operator's confirm** (a `reserved-for: operator` /ask when the seat has a parent — § The manager chain), the only thing standing in front of the loom's one unmediated git write; and **`/ticket` and `/inbox-post` keep theirs**, because filing is a question about scope rather than the posting of a result. The **commit** is the one that moved, and it is why this setting is chosen rather than inherited: it rides inside `/snapshot`'s batch confirm, so under **Automatic** it lands with the comment — on green gates only, since `--yes` declines a commit the gates did not back.

**Long-running: wakes are the bill (`¶INV_LOOM_WAKES_ARE_THE_BILL`)**. A lane waiting on a background job makes no model calls; the cost is each WAKE. When a job returns after the prompt cache has expired (minutes), the lane re-reads its whole context at full price, so a lane hours old pays for its entire history on every wake, and a throttled queue turns every small run into another cold wake. Under Long-running:
*   **Live lanes = shared slots, and the slots are shared with every other loom** (`¶INV_SLOT_CAP_IS_GLOBAL`, below). Keep at most as many resource-using lanes live as the shared queue has slots, counted across all looms rather than within this one. Queued work waits unstarted (no context, no wakes), in the operator's priority order. Pause a lane that is only queueing (TaskStop; its transcript and LOG survive) rather than let it idle into the queue.
*   **Batch every run.** One queued run per wake, carrying every case, arm and control the lane needs next. A sequence of small runs is a sequence of cold wakes.
*   **Cap a lane's context.** Near ~150K tokens a lane writes its state to its LOG (done, measured with paths, the exact next step) and hands back. The conductor continues from the LOG with a fresh lane instead of resuming an hours-old one; one re-derivation is cheaper than every later wake at full size.
*   **A message to an idle lane is a wake.** The conductor relays to an idle lane only what changes its next step, batched; FYI-only notes wait for the lane's next natural wake or its hand-back.
*   **Name the rules in every brief** (they reach lanes through `assets/LOOM_AGENT_DIRECTIONS.md` § "Long-running sessions").

**Above-ceiling handling (`¶INV_LOOM_SIMPLIFY_DONT_SCARE`)**: when a technical fork would stall the operator, pose it as a **plain-language choice with a clear recommendation** and take the recommended default if they're unsure (noted in the ledger) — never raw technical internals. Escalate to a senior reviewer only for one-way doors.

### What a lane tests, and how many lanes may run (`¶INV_SUITE_ONCE_PER_WAVE`, `¶INV_SLOT_CAP_IS_GLOBAL`)

*This section and the Execution shape disposition are together what earlier notes call the **batching dial** — how a loom batches its test runs and its workers. The part a loom is asked is the disposition; the part below is fixed.*

**A lane runs the tests its own change touches. The full suite runs once, at the wave gate, against the assembled tree.** This is not a dial, because the alternative is measured rather than arguable. *Measured 2026-10-20, over 105 interleaved order-rotated runs*: the same command spread **10.7s–102.0s** (p50 21.5s, p90 58.1s), which made a lane re-running the whole suite at every step the dominant cost of a parallel run. The remedy is to stop running it per step, not to make it faster.

Three things follow, and each has already been tried the other way:
*   **Do not reduce concurrency to make the suite affordable.** *Every* reduction measured worse: disabling file parallelism came in at **311.1s against a 40.4s baseline**, nearly 8×. It is a falsified remedy, not an untried one.
*   **Do not take a single timing as a reading.** On a spread of 10.7s–102.0s one run says almost nothing; a judgement needs an interleaved, order-rotated distribution. A cache advertised as removing 57% of tracked time measured **inside the noise band** — an advertised figure is not a measurement.
*   **Targeted runs let a cross-cutting break reach the wave gate, where attributing it costs more. That is accepted deliberately.** The gate still catches it, and the per-lane alternative is the cost this rule exists to remove. Do not "fix" it by briefing lanes to run the whole suite.

**The worker cap is global across concurrent looms, not per loom.** Two looms that cannot see each other will together exceed any number each keeps to itself, and they contend over one test queue and one machine. So the count lives where a second loom can read it: **one file per loom under `~/.claude/engine/.loom-slots/`**, named for the loom (its session directory, slugified). Before dispatching a lane, the conductor **refreshes its own file with `engine loom-slots --heartbeat <sessionDir> --cap <N> --lanes <threadIds>` and reads every file in the directory** with `engine loom-slots --self <sessionDir> --dispatching <items>`; the global figure is the sum, and the cap is a refusal to dispatch past it.

*   **Each loom writes only its own file and reads everyone's**, which is what makes this race-free without a lock — one writer per file, so two conductors cannot interleave a read-modify-write on the same bytes.
*   A loom's file carries its **session directory**, its **live lane threadIds**, its **cap**, a **heartbeat timestamp** and its **work claims**. **It is written only through `engine loom-slots`, never by hand**: `--heartbeat` rewrites the session directory, cap, lanes and heartbeat whenever the lane set changes, and the claim commands rewrite the claims. Each keeps the fields it was not asked to change, under a lock, because a hand rewrite drops whatever it does not mention.
*   **A file whose heartbeat is older than the staleness window is reported as stale and not counted.** A conductor ended by a context clear cannot delete its own file, so stale rows are the expected state rather than an error — and they are *named in the reading* rather than silently dropped, because a slot count that quietly discards rows cannot be told apart from one that found none.
*   **The file also carries the loom's work claims, and a claim outlives the lanes that made it.** A `claims=` line lists the tickets and paths this loom has taken, each `working`, `done-uncommitted` or `in-pr:<N>` (committed and in open PR N, not merged); `--claim-state` accepts those three (the last written `in-pr <PR#>`) plus `landed`, which removes the claim. **Claim on dispatch**, everything the dispatch takes in one call (`engine loom-slots --claim <sessionDir> <item>,<item>,...`), **mark done-uncommitted on hand-back** (`--claim-state <sessionDir> <item> done-uncommitted`), and **release on landing** (`--claim-state … landed`, or `--release` for work dropped unlanded). Before dispatching, read with `engine loom-slots --self <sessionDir> --dispatching <items>`: it prints every other loom's claims and warns, exiting 4, when one matches a ticket key or overlaps a path. A key is found inside a branch name, a Linear URL or `[KEY]`, and a path is compared within its repository however it is spelled; a ticket and a path never match each other, so claim both when a dispatch has both. A claim is reported however stale its row and however empty its lanes, because that is the case it exists for: *measured 2026-10-23*, a loom read another loom's row as stale with no live lanes and dispatched four lanes into seven tickets that loom had already finished and not yet committed. A claim is cleared by the loom that holds it. An abandoned one, from a loom that will not resume, is released by another conductor only on the operator's ruling, with the release recorded in that conductor's session log.
*   **The directory is the whole mechanism**: no daemon, no lock service, nothing outside the engine's own tree. It follows the `.project-fetch/` and `.ticket-fetch/` precedent — a gitignored directory at the engine root holding one file per item — so it adds no infrastructure to install or keep running.
*   *Measured 2026-10-23, and the reason the count is stored rather than derived*: deriving it from live sessions was tried first and does not work here. `engine find-sessions.sh active` returned exactly one session and **did not include the live session it was run from**, because discovery is scoped to one session root — so a count derived from it cannot see the looms that cannot see each other, which is the entire requirement. `engine lane-stall` has the matching limit from the other side: it answers a lane's **state** and never its **reachability**, and was observed reporting lanes as `running` whose transcripts were 6,369 minutes old.

### The conductor's job (`¶INV_LOOM_CONDUCTOR_RELAYS`)

While threads run, the parent: runs a live message relay (agents `SendMessage` the parent to report progress); keeps the global slot file current and refuses to dispatch past the cap (`¶INV_SLOT_CAP_IS_GLOBAL`); maintains a *waiting-on* graph (a cycle = deadlock) and polls agent status (silence past a timeout → probe → escalate); and escalates per the hard floor, so that each floor item reaches your manager (the operator if you have none — § The manager chain). The rules live in `assets/LOOM_AGENT_DIRECTIONS.md`, fed **by reference** into every build agent's context pack.

**Whether it brokers files at all is the Execution shape disposition's answer, and a loom does exactly one of the two.** Under **one shared tree** it computes an up-front file partition, takes claims on out-of-partition files, and brokers conflicts **first-claim-wins** (`¶INV_LOOM_FIRST_CLAIM_WINS`, the later thread's conflicting step defers to the next wave). Under **worktree-per-lane** it computes **no** partition and brokers **no** claims — every lane owns its own tree, so there is nothing to allocate, and the collisions are found instead by the wave boundary's merge (`¶INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY`). Running both pays for prevention and detection and buys neither: the partition predicts collisions at allocation, the merge finds the ones that actually happened in the text.

**Hard escalation floor (`¶INV_LOOM_HARD_ESCALATION_FLOOR`)** — these ALWAYS reach your manager (the operator if you have none — § The manager chain), marked `reserved-for: operator`, even under Automagic: the **per-thread ticket-disposition question** (always asked before a thread builds — Automagic never suppresses it) · a **cyclic deadlock** the conductor can't break by deferral · a thread's **build failing after retries** · a **scrutinize MUST-FIX** needing a fix/skip/defer call · a **thread loopback** (council/scrutinize → interrogate or build).

### The manager chain

(`¶INV_LOOM_ESCALATES_UP_THE_CHAIN`, `¶INV_ESCALATION_DOES_NOT_BLOCK`.) Wherever this skill says a question **reaches your manager**, this section is what it means; the sites cite it rather than restate it.

*   **Which route this loom takes** is the **Escalation route** Setup disposition, recorded in the ledger header. Under *up the manager chain* (the default when the seat has a parent) everything below applies as written. Under *straight to the operator*, every escalation is written with an explicit `engine ask new --to operator`, because `ask new` defaults `--to` to `$FLEET_PARENT` and would otherwise hand it to the parent; the parent is not consulted. It still travels as an /ask, still carries its marks, and the conductor still keeps working. Under *both*, everything goes to the manager first, and each hard-floor item also goes as a second /ask, `--to operator --related <the first one's id>`: linked by `--related`, never `--dependsOn`, which would hide the copy until the first one is answered. `related` renders collapsed and does not mark a twin, so the operator copy's body opens with **"copy of `<id>`; the first answer on either binds"**. The copies are two files and each can be answered, so **the earliest `answeredAt` across the two binds**. On its next turn the conductor acts on that answer and sets the other copy `superseded`; if the other copy was answered too, that later answer is recorded as superseded and surfaced at the gate, never acted on.
*   **Who is above you.** A conductor whose seat has a parent escalates to its **manager**, not to the operator. The parent is the seat's **live `@pane_parent`, cross-checked against `FLEET_PARENT`**. Read it with `/coordinate`'s `scripts/hop.sh target`, which owns that read; do not re-derive it. At Setup, record the ancestry once with `hop.sh chain > [sessionDir]/hop-chain.txt` and check its exit. A non-zero exit leaves a partial file that would skip a live rung, so **move it aside** to `hop-chain.partial.txt` and name the missing rung in the header's `parent at open` cell (`/coordinate` § 0 *Parent Resolution*). Pass `--chain-file [sessionDir]/hop-chain.txt` on each `target` read **only while that file exists**: `target` given an absent chain file exits 2, which would quietly send every escalation to the operator as a broken hop. Without the file, read `target` bare; a dead manager then routes to the operator (exit 3) rather than to its own parent, which is what the recorded chain buys. Re-run `target` at each escalation rather than trusting the Setup reading. Map the exits as `/coordinate` § 4 Step 5 does. **exit 0**: stdout is the target, the parent or `operator` when there is none. **exit 3**: stdout is still the target (a dead rung skipped by the chain record, or `operator` when the top of the chain is dead); copy the stderr reason into the ask's `🔓 Open claims` row. **exit 2** (no identity, such as a loom outside the fleet), **exit 4** (the tree is unreadable) or **exit 5** (this seat's live edge cannot be read, or it names this seat or `operator`): there is no target. A stale or unset `FLEET_PARENT` is only a stderr note, never exit 5. `to:` takes only the **first token** of stdout (`<window:label>`); the pane id after it is for the ping. A seat with **no parent** escalates to the **operator**, exactly as before this section existed. A question with nowhere to go is never dropped: on exit 2, 4 or 5 it goes to the operator and names the broken edge (`broken hop: <stderr>`).
*   **How it travels.** As an **/ask file** (`engine ask new`; format and CLI per `/ask`) addressed `to:` that seat, never as a blocking `AskUserQuestion` to a parent. The ask is where a loom's fork is asked (`¶INV_LOOM_ASKS_AT_A_BOUNDARY`): its card fields carry the card, and its `context` points at the `/decide` record by path rather than copying it. A board is rendered only when the operator asks for one, and then the ask carries its URL. `AskUserQuestion` is used only when the seat has no parent and the operator is at this terminal (`/ask` § When to write an ask instead of calling AskUserQuestion); a mined fork follows `¶INV_LOOM_ASKS_AT_A_BOUNDARY`'s branch instead, where a seated conductor with no parent still writes the ask. A seat with a parent does not block Setup on it: Setup takes the chain default and puts the dispositions up as one ask it does not wait on (Setup, *Ask the dispositions*).
*   **Gate questions travel the same way.** With a parent, every item the gate would put to a person goes as a marked /ask, never as an `AskUserQuestion`: the loop gate's own keep-going-or-close question, the `/snapshot` and `/pr` confirms the Interruption disposition keeps, the wave boundary's merge confirm, and a re-put `🔓 Open claims` row. Mark each by its grant v1 class: the merge confirm (H) and the `/snapshot` and `/pr` confirms (G) carry `reserved-for: operator`, and every hard-floor item stays `reserved-for: operator`. Several can ride one ask file as separate questions (`/ask` § The format). The gate then reports what it put up and carries on with whatever does not depend on the answers. **When the `/snapshot` ask comes back yes, invoke `/snapshot --yes` with `-- <thread KEY>`** (`-- <thread KEY>` only when the thread has its own ticket, bare `--yes` otherwise, never an umbrella key): the answered ask is the confirm, and `/snapshot` without the flag would ask a second time at a terminal nobody watches. ⚠️ **Open residuals, named rather than papered over**: `/pr` (its MANDATORY confirm, pr SKILL.md:108), `/interrogate` (interaction only by `AskUserQuestion`, interrogate SKILL.md:78) and `/decide` for a board the operator asked for (its primitive is `AskUserQuestion`, decide SKILL.md:17; the loom's own decide pass runs no collect step and needs no waiver) have no waiver today, so a yes on the marked ask cannot reach them. With a parent, the conductor never runs them at an unwatched terminal: it holds each thread's `/pr`, interrogation and an operator-asked board's `/decide` collect step as a `🔓 Open claims` row naming the step and the missing waiver, and does what does not depend on it. Each skill's waiver is owed by that skill's owner; this skill does not supply it. The destination is the session log's `⚖️ Rules owed` block, where the conductor rows the three under **WAIVERS**, each naming its owner (§ *Row a rule a lane could not land*, under Conducting).
*   **What a manager may rule, and what it may only forward.** Everything on the hard escalation floor above, and anything in a class grant v1 reserves (E–H, as `/coordinate` § The Grant defines them), goes up with the header mark **`reserved-for: operator`** (`engine ask new --reserved-for operator`) and your recommendation attached. A manager may **forward** such an ask but never rule on it, and only the operator's answer closes it (`/coordinate` `¶INV_MANAGER_NEVER_RULES_ON_RESERVED`). A manager **may rule** on orientation questions and, in Manager mode only, on grant v1's delegated classes A–D (`/coordinate` § The Grant; a manager in any other mode rules on orientation alone). **The mark is the only enforcement.** The ask app refuses any answerer but the operator on a marked ask, and a manager's `hop.sh may-rule --reserved-for operator` passes it up. Nothing catches an unmarked one: `may-rule --floor` takes the manager's own classification, and its floor list has no ticket disposition. Mark every floor item.
*   **While it is open, keep working.** An open ask blocks only the work that depends on its answer. Dispatch, gate and land everything else, and row the ask in `🔓 Open claims` with what its thread does meanwhile. Stopping every lane is legitimate only when every remaining step depends on that answer, and the row says so. Blocking at one rung becomes blocking at every rung above it.
*   **Re-pinging is manual.** The operator ruled at 23:05 that *"push is fine; timers aren't"* (IDE-135's no-scheduler rule), so nothing re-pings or passes an ask up on a clock. You check on your own turns: at each loop gate, and whenever `/next` surfaces an overdue ask, read `engine ask list --status open --seat <your seat>`. An ask open past 10 minutes is re-pinged once. Past another 10 it is passed up one rung as a deliberate step, per `/ask` § While you wait (`hop.sh target --of <the unanswered seat> --chain-file [sessionDir]/hop-chain.txt` names the rung, its exits read as above, and only the `to:` field changes). The answer arrives by push or, failing that, in the file (`delivery: undelivered`), which you read when you resume.
*   **When you are the manager.** A conductor that manages seats (child conductors whose asks arrive `to:` this seat, which is the director weave's shape) runs the receiving half at each loop gate, before it mines forks. **It holds the Manager-mode grant on the director's rulings**: grant v1 lives only in `/coordinate`'s Manager-mode config (director ruling R7) with the R6 backstops restored (both in `builds/coordhop_BUILD.md` § Fix round 3 of the 2026_10_28_DIRECTOR session), and a loom conductor receiving its child seats' escalations is that receiving half, credited to the director under IDE-232 acceptance 1. The procedure is `/coordinate`'s and is cited, not restated:
    *   Read the asks addressed to this seat with `hop.sh inbox` (§ 4 Step 1, *Asks addressed to this seat*). **`inbox` exit 2** (neither the ask CLI nor the ask root readable): log it and continue the gate; the child's own ping is the fallback channel.
    *   Run the hop check on each with `hop.sh may-rule` (Step 3.0), passing `--config` a session copy of `assets/coordinate.manager.config.json` and **`--reserved-for operator` when the inbox line carries the mark**. On `pass-up`, or **any other exit, which fails closed and marked**, pass it up this loom's own route as Step 5 does.
    *   **`rule` is not yet a ruling.** It continues through the rest of Step 3: **Step 3.1, the category check against the config's `alwaysEscalate`**, where director ruling R6's backstop escalates "merge approval into fleet-owned ground" even when it is classed B; then the confidence assessment and threshold (Steps 3.2 and 3.3, with Step 4a's probe below the threshold). Only a question that clears all of them is answered, within grant v1 (orientation, or classes A–D in Manager mode), and recorded as Step 4 does. An escalation at any of those steps passes up as Step 5 does.
    *   With `/coordinate`'s non-manager config (an empty grant) the loom rules on orientation only; with no config at all `may-rule` exits 2, so every ask passes up marked.
*   **Lanes are unchanged.** A lane escalates to its conductor (`assets/LOOM_AGENT_DIRECTIONS.md`) and never past it. The conductor decides what goes up the chain.

### No rush to close (`¶INV_LOOM_NO_RUSH_TO_CLOSE`)

The loop gate defaults to **keep going**, never "shall we close?". A session ends only when you say so. Durability rides in Linear + git (via the composed `/snapshot` + `/pr`), so a `/loom` session can end cleanly with threads still mid-flight — the ledger records where each stands.

**Context pressure is not a licence to close.** At about 70% on the status line the conductor **dehydrates** rather than recommending a wrap-up; `¶INV_LOOM_DEHYDRATES_AT_SEVENTY` (§ Dehydration and rehydration, below) states the rule in full. That retires the earlier ~150K-token wrap-up recommendation card. **Dehydrating is not closing**: the session stays open, the successor carries the weave on, and your explicit choice is still the only thing that ends the session.

### Dehydration and rehydration — what a conductor owes a successor (`¶INV_LOOM_HANDS_OVER_A_PATH_NOT_AN_ID`)

**For a conductor writing a hand-over, and for the fresh context that reads it.** `§CMD_DEHYDRATE` owns the payload and the restart; `§CMD_RESUME_SESSION` owns the resume algorithm; both apply unchanged. What they do not know is what a *conductor* holds — a ledger, live lanes, brokered file holds, open asks and owed docs — so this section adds only that content and the forms that are forbidden in it.

**When the conductor dehydrates (`¶INV_LOOM_DEHYDRATES_AT_SEVENTY`).** At about **70% on the status line**, the conductor runs `/dehydrate` at the first point it is between moves. The operator's rulings, 2026-10-30: *"tell it to dehydrate after ~70% of context UNLESS something very meaningful is going on right now in discussion etc. when all lanes are out, it should be dehydrating"*, and then, on whether a running lane holds it back: *"no its ok to do it when lan e is running, it'll do/clear so agents survive. it should be like dehydrate when you are not answering, thinking, planning, orchestrating"*.
*   **Which 70%.** The figure is the one the status line displays, not the raw field. `.state.json` `contextUsage` is the **raw** window fraction (`tools/statusline.sh` writes `used_percentage / 100`); the status line displays `contextUsage / OVERFLOW_THRESHOLD`, with `OVERFLOW_THRESHOLD` read from `~/.claude/engine/config.sh` (0.76 by default). So the test is `contextUsage / OVERFLOW_THRESHOLD >= 0.70`, about 0.53 raw by default. Under `DISABLE_AUTO_COMPACT=1`, `config.sh` sets the threshold to 0.95 but `statusline.sh` displays the raw figure itself, so the displayed 70% is `contextUsage >= 0.70`.
*   **Between moves is the trigger.** The conductor dehydrates whenever it is not answering, thinking, planning or orchestrating right now, and that includes waiting on lanes. Running lanes never block it. A lane's work survives the restart through its log, and the successor resumes it from its LOG PATH under the forms below.
*   **The exception is something very meaningful live right now**: the operator is actively deciding with the conductor at this terminal now, or a merge, a push or a landing lease is in progress, whether the conductor holds it or any of its lanes does. `engine lease show` lists every live lease on disk at read time. A lane mid-landing (re-picked, verifying, holding the lease or pushing) holds the dehydration off as surely as the conductor would, because a restart ends the lane between its take and its push. An open ask, an open board or an open claim row is not that. The wait is bounded: the conductor dehydrates at the first point it is between moves after the exception ends. ⛔ **Never dehydrate mid-push or while the conductor or a lane holds the landing lease. The conductor releases its own lease first and waits for a lane's to be released**, because a restart does not carry the lease with it, and the next lander then waits on a holder that no longer exists.
*   **Dehydrating is not closing.** The session stays open, the successor rehydrates into the same weave, and `¶INV_LOOM_NO_RUSH_TO_CLOSE` holds unchanged: only the operator's explicit choice reaches Synthesis.

The figure is the conductor's alone, and it differs from a lane's ~150K-token cap (`¶INV_LOOM_WAKES_ARE_THE_BILL`) because the operator ruled on the conductor and left the lane rule as it was. `§INV_CONTEXT_BUDGET` carries this as its one scoped exception, and the loop gate checks it as the **Dehydration check** on its declared trigger list.

**The rows go in the inheritance file, not in the payload's prose.** Write `LOOM_INHERITANCE.md` at the sessions root (`assets/TEMPLATE_LOOM_INHERITANCE.md`, whose *Where it lives* section is the normative address) and list its **absolute path** in `requiredFiles`: the payload is capped and its prose is not addressable, while a row is. Carry every open row — threads, asks with their `<seat>/<id>`, docs owed, rules owed, open operator claims, un-acked seat handovers, and the standing arrangements that die on their own; the file carries one block per kind, in the order the hand-over receipt counts them. **An open row may be passed on; it may never be dropped** (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`). **Before writing it, run `engine open-asks "<sessionDir>"`** and carry each `OPEN` or `UNPARSED` row into the inheritance's `❓ Lane asks open` block, verbatim with its `logpath=`. These are not `🔓 Open claims`: a lane's ask is owed by the conductor and has no decision card, and it closes when a `✅ Answered` heading for it lands. A lane's question lives in the conductor's context and in the lane's log, and only the log survives the restart. Read the exit status directly (3 = rows to carry, 2 = the reading is incomplete), and pass `--also <dir>` for any lane logs kept outside the session folder. A successor arriving without an inheritance runs the same command first.

**The forbidden forms.** Each is a brief that read as executable and was not, measured on a hand-over in this skill's own history. The redirect is what to write instead, because an agent routes around a prohibition and acts on a replacement.

*   ⛔ **An agent id is never a hand-over handle. Hand over the lane's LOG PATH.** A context clear ends every in-process subagent, so *"resume lane X by name"* is structurally unavailable on arrival — not slow, not idle, gone; `SendMessage` to the id answers *no transcript found*. The lane's `builds/<slug>_BUILD_LOG.md` survives, so the brief names it and the successor dispatches a FRESH lane with that log in its context pack. Resuming by name is a live-context move and belongs nowhere in a restart brief. **`engine lane-stall "<sessionDir>"` closes each row with that path, as `logpath=`** — read it there rather than deriving it, take it as everything after `logpath=` to end of line (`sed 's/.*logpath=//'`, never `awk '{print $NF}'`, since a shared-drive session path holds spaces), treat the `agent=` transcript beside it as diagnostic only, and carry `logpath=none` as the reading it is: a lane with no log is a different hand-over, not a lane to point at its transcript instead.
*   ⛔ **A discriminator both states share is not a discriminator.** Name the field that actually differs, and show it differing in the same invocation. *(A brief that said to print the publish endpoint **and bucket** was satisfied by the wrong store: both stores are named `proofs` and only the port separates them.)*
*   ⛔ **A claim is scoped to the tool class it was measured on, and says so.** *"Writes still worked"* and *"the gate is open"* are different statements; a gate's allowlist admits some tool classes and not others, so a success in one class establishes nothing about another. Write the class into the claim.
*   ⛔ **A lane's log is not a record of what it did after it stopped logging.** Read the artifact before briefing its state — a lane can land files after its last entry, and a brief that infers *unwritten* from a closed log sends the next lane to redo work that exists. Where the directory is untracked git cannot correct you either: `git status --porcelain` on an untracked path prints nothing and exits 0 whatever it holds, so establish TRACKED with `git ls-files --error-unmatch` before reading any path as clean.
*   ⛔ **A standing arrangement is named with what blocks on its absence, never as a note that it exists.** A background watcher re-armed at the maximum two-hour timeout dies on a session that outlives it, and the write gate then blocks the next `Agent` dispatch until it is re-armed — so the row names the ceiling, the tool class that blocks, and the re-arm command. On a long session this is a standing cost, not an incident, so the row says how many ceilings it has already crossed. **Name the classes that stayed ALLOWED alongside the ones that block**, because a claim is scoped to the tool class it was measured on and a couple of successful writes in a passing class is how a dead watcher gets recorded as harmless.
*   ⛔ **A restore instruction that contradicts standing advice carries the contradiction and whose authority settled it.** Otherwise the successor reads *"re-arm it"*, meets the advice against restarting a watcher already at the longest timeout allowed, and re-derives the override from scratch — the exact re-derivation this file exists to prevent. The conflict here is structural rather than anyone's error: a watcher whose maximum lifetime is shorter than the session's creates a **mandatory periodic re-arm** that the harness advises against, so the row names which rule was judged the authority and on what grounds. A judgement taken repeatedly and never written down is a judgement the next context cannot inherit.
*   ⛔ **Every command a brief carries is absolute.** A relative `engine log` path is now **refused** when it would land outside the live session — the guard asks `session.sh find` which session is live, compares the physical paths, prints the corrected absolute path and exits 1 without writing. It does not make a relative command safe to carry: the guard **fails open** when session discovery is unavailable, waives on `ENGINE_LOG_ALLOW_FOREIGN_SESSION=1`, and only fires on a path with a `sessions/` segment, so every other relative form still resolves against whatever CWD the successor happens to hold.
*   ⛔ **A sessions root is never typed from a convention. Compute it, and carry the absolute path.** The root is the parent of the active session directory (`engine session find`; `sessionDir` in the hand-over payload), which agrees with the engine's `resolve_sessions_dir` whenever one root is in play — and more than one is, under a symlinked `sessions/`, a shared-drive artifact root, or a `$WORKSPACE` set for one process and not another, where a session directory of the same name can hold different content at each root. A root a successor cannot compute is an address it cannot read, so the brief carries the inheritance file's absolute path and the template's *Where it lives* section rules the read order.
*   **Every figure in the brief carries its timestamp and is marked re-measure.** A hand-over's facts age between the write and the read, and the brief cannot say which ones moved. Saying so near the top is what makes the successor's first act a measurement rather than an action.

**Rehydration — the successor's first acts, before working any row.** Run `§CMD_RESUME_SESSION`, then take **Phase 0's inheritance intake** — the same step, reached with a payload in hand rather than cold, so there is one mechanism and not two. Before acting:
*   **Re-measure what the brief marked re-measure**, and first among them whether each live lane is addressable at all — that reading decides whether the next move is a resume or a fresh dispatch.
*   **Claim rows and say which you left.** Several looms may share the inheritance file, so write the `## ♻️ Inheritance claimed` entry naming the rows taken, the rows left to another owner, and the readings that had moved.
*   **Refuse a row carrying `UNKNOWN` in a field you need to act**, and report it. Acting on a partial row reproduces the loss the file exists to prevent, with no gap left where it used to be.
*   **A falsified brief claim is recorded as a correction, not worked around silently** — and the refutation is checked before it is relayed, to the same standard as the claim it refutes. A refutation generalised from one tool class is how a correct brief gets called wrong.

### Phase shape

`/loom` is `Setup → Loom → Synthesis` — three phases, like `/do`. Intake and per-thread interrogation are **not** upfront phases: they happen **inside the Loom body every time you add a thread**, because you add threads throughout the session, not all at once. Synthesis is reached only by an **explicit** "wrap up" choice at the loop gate (`¶INV_LOOM_NO_RUSH_TO_CLOSE`).

## 0. Setup

§CMD_REPORT_INTENT:
> 0: Setting up a loom over ___. Trigger: ___.
> Focus: session activation, loading the in-scope tickets, choosing the dispositions.
> Not: building or spawning agents — setup only.

§CMD_EXECUTE_PHASE_STEPS(0.0.*)

*   **[MANDATORY] Read the inheritance before the batch.** A predecessor's open rows arrive as a *file*, not as context, so a conductor that goes straight to the batch has dropped them — and nothing in the tree makes a noise about it. This is the only pass that can see **the operator's answers that arrived after the predecessor composed its rows**, which is what makes it a distinct job rather than a repeat of the hand-over's own sweep. It runs on every start, cold or resumed; the resume path (`§CMD_RESUME_SESSION`, *Rehydration* above) reaches the same intake with a payload in hand, and the payload's absolute path wins over the convention when both are available.
    *   **Resolve the file** per `assets/TEMPLATE_LOOM_INHERITANCE.md`'s *Where it lives* section — compute the root, try the candidates in order, report a copy found at more than one root instead of merging.
    *   **No file at any candidate root** → say so and proceed. A first loom in a tree inherits nothing, and that reading written down is the result; silence is not.
    *   **A file** → **re-measure every reading it marked re-measure before acting on any row**, and first among them whether each live lane is addressable at all, because that decides resume-or-redispatch. Then **claim** the rows whose subject this session is taking, **leave** the rest to their `owner`, and **refuse a row carrying `UNKNOWN` in a field you need to act** — report that row rather than acting on the rest of it (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`).
    *   **Write the `## ♻️ Inheritance claimed` entry** — rows claimed, rows left, roots searched, which readings had moved, rows refused. That entry IS the `inheritanceRead` proof, and like `docRegister` it clears on an empty result: a loom that inherited nothing passes by recording the no-file reading, never by skipping the step (`¶INV_LOOM_MANDATORY_STEPS`).
    *   **A claimed row enters the weave as a thread**, through the add-a-thread flow — including its adjacency assessment, which is where several rows on one subject collapse into one thread. **Do not hand the rows to `/groom` to cluster**: its drain is welded to an inbox adapter, so it cannot take an arbitrary pile as input, and a step that assumes otherwise silently loses every row. This step reads, claims, refuses and records; it does not cluster.
*   **Scope**: Understand the batch of tickets/tasks in play — the inherited rows included, since one of them can change what else is worth loading. Load the candidates via `§CMD_INGEST_CONTEXT_BEFORE_WORK` (the `SRC_RELATED_TICKETS` + any `contextPaths` name them).
*   **Ask the dispositions** (`AskUserQuestion`, one question per disposition — Autonomy · Council · Interrogation · Detail importance · 🔍 Scrutinize · Interruption · Peer instructions · Run length · Execution shape · Proof · Rounds · Merge strategy · Auto-continue · Escalation route; **fourteen of them (thirteen when the seat has no parent, since the route is then fixed), and the tool takes four questions per call, so these go in four calls — 4/4/4/2, or 4/4/4/1 without a parent**). Record the choices as the `dispositions` proof and echo them into the ledger header. **Seven have their own ledger field, each for its own reason rather than for symmetry**: **Execution shape**, because the wave boundary's merge step and the file-brokering job are both conditional on it; **Interruption**, because whether a human saw a posted comment before it went out is **not recoverable from the comment afterwards**, so the field is the only place that reading survives; **Peer instructions**, because a conductor that acted on a peer's word leaves nothing in the artifact saying whose word it was; **Merge strategy**, because a wave's shape is not reconstructable from its result — a wave that integrated and a wave whose lanes landed direct leave different histories but no record of which was *chosen* (`§INV_LOOM_MERGE_STRATEGY_IS_DECLARED_AND_MEASURED`); and **Proof**, because a thread with no page could be a thread that was exempt, a thread the disposition never covered, or a thread the conductor forgot, and **only the header distinguishes the three**. 🔍 **And a sixth, `Scrutinize`, on exactly the Proof argument read onto a different artifact**: a lane with no critique could be a lane the disposition never covered, a lane the conductor judged safe, or a lane nobody got to — and only the header plus the lane's own `scrutiny` cell tells those apart (`¶INV_LOOM_SCRUTINY_IS_DECLARED_AND_ROWED`). **And a seventh, `Escalation route`**, because whose call the route was cannot be reconstructed from the artifacts afterwards: an /ask that reached the operator directly could have been sent under *straight to the operator*, by a seat with no parent, or by a conductor that skipped its manager, and only the header, which records the position and who chose it, tells those apart (§ The manager chain). These parameterize every downstream stage and the escalation/relay reference file.
    *   **Read the parent first; `AskUserQuestion` only when there is no parent.** Record `hop.sh chain` and read `hop.sh target` as § The manager chain says, and write the result into the ledger header's `parent at open` cell. Branch on the exit, never on stdout alone. The no-parent list is **exit 0 printing `operator`** and **exit 2** (no identity, a loom outside the fleet), and **only when `FLEET_PARENT` is empty and stderr carries no stale `FLEET_PARENT` note**: exit 2 is overloaded (an unreadable chain file gives it too, whether named by `--chain-file` or by a `HOP_CHAIN_FILE` pointing at a missing file), and exit 0 printing `operator` is how the live-first read answers a seat whose `@pane_parent` is unset even though `run.sh` launched it under a manager. When either holds with `FLEET_PARENT` set or a stale note present, the seat takes the non-blocking defaults below, sends its Setup ask `--to operator` (routing still honours the live edge) and writes `parent at open: none live (FLEET_PARENT=<x>, <stderr>)`. The parented list is **exit 0 or 3 printing a seat**, **exit 3 printing `operator`** (the parent is dead), **exit 4** and **exit 5**: a manager launched this seat, so it takes the parented path below, and on 4 or 5 the edge could not be used, so it names the broken edge in `parent at open`. No exit is on both lists. ⚠️ **This departs from `/coordinate` § 0 on purpose**: /coordinate STOPs at Setup on a broken hop, and a loom does not, because a launched conductor that stops is the blocking this section exists to remove; it records the edge and keeps working on the defaults. **A seat with no parent and the operator at this terminal asks as above**: thirteen questions in four calls, 4/4/4/1, since the route is fixed to the operator. **A seat with a parent never blocks Setup on `AskUserQuestion`**, because the seat a manager launched is the seat nobody may be watching: it takes the defaults, recorded `chosen by: default` in the header: the Escalation route on *up the manager chain*, **Autonomy on *Careful*** and **Interrogation on *None* until that ask is answered** (neither bullet names a default, and Interrogation's other positions reach `/interrogate`'s `AskUserQuestion`), and every other disposition on its own marked default. It then puts all fourteen dispositions up as ONE non-blocking /ask to its parent (one question per disposition in a single file, `/ask` § The format), and keeps working on the defaults until that ask is answered. An answer then replaces the default it overrides, and the header records who chose it.
*   **[MANDATORY] Open this loom's slot file and read every other loom's** (`§INV_SLOT_CAP_IS_GLOBAL`). Run `engine loom-slots --heartbeat <sessionDir> --cap <N> --lanes ''` to record this loom's session directory, its cap, an empty lane set and a fresh heartbeat. It keeps any `claims=` line already there, so a loom restarted in the same session inherits the claims on its own finished, uncommitted work instead of erasing them. Then read the rest of the directory with `engine loom-slots --self <sessionDir>` and report the global figure — live lanes, and **how many rows were stale** rather than dropping them. A loom that cannot read the directory reports that reading and dispatches **one** lane at a time until it can, rather than assuming it is alone: a loom that believes it holds the whole budget is the failure this file exists to prevent.
*   **[MANDATORY] Record the session branch — its NAME and its sha** (`git branch --show-current` and `git rev-parse HEAD`) into the ledger header's `▶️ Loom Opened` block. That is the `sessionBranch` proof, and it is taken **here** rather than at the wave boundary that uses it because it is not reconstructable later: under worktree-per-lane the conductor's tree is not any lane's, so a base read at integration time is a base guessed (`§INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY`). A detached HEAD or a tree with no branch is **recorded as that reading** and reported, never replaced with a plausible name — a loom whose base is unknown does not integrate.

*Phase 0 proceeds to Phase 1 — **transition without a gate menu: pipe Setup's proof to `engine session phase` and move.** `gate: false` removes the menu, never the transition. A conductor that keeps working in Setup is indistinguishable from one in the Loom body until somebody reads the status line.*

## 1. Loom
*The main body — the persistent parallel weave. Adding a thread, interrogating it, building, conducting, and closing a thread all happen here.*

§CMD_REPORT_INTENT:
> 1: Weaving threads in parallel. Autonomy: ___. Council: ___. Interrogation: ___.
> Focus: add threads (ticket/triangulate/interrogate/write surface), fan out named builds, relay, scrutinize, triage, integrate each wave, offer snapshot/pr, council per policy, keep the ledger live.
> Not: writing Linear/git directly, and never closing on its own — mutations go through composed skills; Synthesis is an explicit choice.

§CMD_EXECUTE_PHASE_STEPS(1.0.*)

This phase is the whole working body. It runs a persistent loop: you **add threads** (each scoped interactively as it enters, while other threads' builds run in the background), the conductor **weaves** them, and the loop ends only when you explicitly choose to wrap up (`¶INV_LOOM_NO_RUSH_TO_CLOSE`).

### Adding a thread (whenever you add one — not a batch upfront)
A background build agent cannot ask you questions, so a new thread is scoped here on the main thread, while other threads keep building. **Each step is marked `[MANDATORY]` (always happens — no Autonomy disposition turns it off) or `[OFFERED]` (you or the conductor may skip).** Autonomy tunes how much the conductor *resolves without asking*; it never decides *which steps run* (`¶INV_LOOM_MANDATORY_STEPS`).

**Adding several at once** — before scoping them, assess adjacency:
*   **Very adjacent / near-duplicative** → **`[OFFERED]` group them into ONE thread** (`§INV_OFFER_DONT_FORCE_SKILLS`) instead of parallel threads — one build, one PR. Grouping collapses them; you decide.
*   **A topic from `/groom` is already grouped — `[MANDATORY]` one topic is one thread.** A groom pass hands the conductor topics rather than items, each with its signals, its disposition and any ticket keys. **When a topic carries several tickets they ride that one thread** — never a thread per ticket. This is the grouping rule above arriving pre-decided, so the conductor adopts it rather than re-deriving it, and work stays batched by subject instead of filling the loom with near-identical lanes.
*   **Distinct but simultaneous** → keep separate threads, but **batch their interrogation**: run the interrogation forks in shared rounds (≤4 questions spanning threads) rather than one `/interrogate` per thread, so each thread's answers inform the others (fewer round-trips).

1.  **[MANDATORY] Assign a threadId** — `ENG-XXXX`, or a conductor-derived SCREAMING slug for a winged task (≤12 chars `[A-Z0-9-]`, starting with a letter, never ending in a hyphen, digit-suffixed on collision: `FACTS`, `FACTS2`). Open/append its ledger row (`TEMPLATE_LOOM_LOG.md`).
2.  **[OFFERED] `/triangulate`** (`§INV_OFFER_DONT_FORCE_SKILLS`) — `Skill(triangulate, "<ticket>")` to validate real/ripe before investing a build. A not-ripe result parks the thread. Skip for an already-triaged ticket. **Pass no `--mode inbox` here**: a ticket is not an intake drop, so the run stays silent and hands the finding back to the conductor rather than commenting on the ticket — `/snapshot` owns what reaches Linear.
3.  **[MANDATORY per the Interrogation disposition] Interrogate** — `Reasonable` → `Skill(interrogate, "<ticket> --depth quick")`; `Thorough` → `--depth deep`; `None` → skip. The **disposition** decides whether it runs — the conductor may NOT skip it when the disposition is Reasonable/Thorough, and may NOT substitute an inline chat exchange for the dispatched `/interrogate`. The digest (`builds/<slug>_INTERROGATE.md`) is the scope half of the thread's build context pack.
4.  **[OFFERED] De-risk the scope** (`§INV_OFFER_DONT_FORCE_SKILLS`) — when interrogation surfaced an **open question** or an **unproven approach**, de-risk before investing a build. Most threads skip this; it's for the ones with a real unknown. Distinct from triangulate (which validates the *problem*): these de-risk the *solution*.
    *   **`/probe`** — a directed, read-only investigation for an open question. `Skill(probe, "<the question>")` sweeps code / DB / tickets and returns an answer-first report. Always safe — it writes nothing, so it needs no partition.
    *   **`/experiment`** — a feasibility spike to prove an approach works. `Skill(experiment, "<hypothesis>")` writes + runs code in-tree and returns a proved / disproved / inconclusive verdict. **It touches files while other threads build in parallel, so it MUST respect the partition** — claim its files first (or run in an isolated worktree), never write another thread's territory (`§INV_NO_DESTRUCTIVE_GIT`, first-claim-wins). Run it here, *before* this thread's partition is finalized (step 6), so its kept files fold into the thread's own set.
    The probe report / experiment verdict joins the thread's build context pack alongside the interrogation digest, and can reshape the ticket disposition (next) and the scope.
5.  **[MANDATORY — always ASK] Ticket disposition** (`AskUserQuestion` only when the operator is at this terminal and the seat has no parent; otherwise an /ask marked `reserved-for: operator`, per § The manager chain; composed-writes only) — asked **here, after triangulate + interrogate**, so the ticket reflects the scoped understanding before the build. **Read the destination before recording the disposition** (`§INV_A_DISPOSITION_OPENS_ITS_DESTINATION`, defined in `/groom`'s constraints) — an update names the ticket, a create names the project and whatever its prior-work sweep found, and *keep as-is* names the ticket it is leaving alone. Read its own text, then record: **fetching the ticket is not reading its body, and opening the project is not reading its open set.** What the condition rests on, with no count in it: **one seat, one grooming pass, eight dispositions, and one body actually read.** That seat fetched all eight tickets it disposed and read status and relations rather than bodies, so a predicate keyed on having opened the thing would have passed on every one of them; the single body later deep-read had gained a merge, a landing order and a wave PR the day before, which was most of what that ticket was about to be re-scoped to carry. **A count stood here and was withdrawn at its source**: it read *five of six*, and its author, asked for the eight dispositions themselves, re-read their own log and reported the figure as an inference from the one demonstrated case rather than six verified ones. The mechanism is what binds and it stands on that one case — a call returning status and relations has opened nothing that matters. **What would settle the general claim**: a second seat's independent pass over its own dispositions, which nobody has run. Do not restore a count here without it. **A figure in a brief says whether it was run or relayed** — the seat that withdrew this one had three of its own relayed figures falsified by its own lanes inside an hour, and now marks every figure it hands on as `ran` or `relayed`. Relayed is not a warning; it says the reading is somebody else's and has not been repeated. **One body read per disposition is the price. That it does not amortise across a thread is an argument rather than a measurement** — the one measured thing is that all eight of those destinations were tracker rows, which cost little wall-clock and a lot of context, and a destination that is a file or another seat's ground is unmeasured on that axis. A disposition naming no destination escapes the condition, and naming a destination is not the same as routing to one. **Record what you read, and how deep** — one line per disposition in the thread's own record, naming the destination and whether you read its text, its row only, or nothing. That line is the whole cost, and what it buys works backwards rather than forwards: it is the only part of this that catches a miss after the fact, because the counter-case seat's own record would have read `read: status + relations` for anyone auditing that pass later, where re-reading the draft caught nothing. **The question ALWAYS reaches your manager (the operator if you have none — § The manager chain)** (its answer may be "keep as-is"), and while it is open only this thread's build waits; it is never skipped by proximity to the offered steps, and Automagic never suppresses it. Three ways:
    *   **Create a new ticket** — `Skill(ticket, "<task>")` for a winged task, framed from the findings; on creation, upgrade the slug threadId to the new `ENG-XXXX`.
    *   **Update the existing ticket** — post the scoped understanding via `/snapshot` or `/communicate`, so it's current before the build.
    *   **Keep it here as-is** — no ticket action; runs against its current ticket, or un-ticketed with its slug.
    Every write happens inside the composed skill under its own confirm (`¶INV_LOOM_COMPOSED_WRITES`).
6.  **[MANDATORY — and the Execution shape disposition decides WHICH of the two it is] Give the thread its write surface.** Under **worktree-per-lane**: create its worktree and its branch, hand it both, and compute **no** partition — overlap is not predicted here, it is found by the wave boundary's merge. The branch is cut from the session branch. **The one exception is a lane whose work needs another lane's unlanded work first**: the conductor may cut it from that lane's head instead, and then rows `based on <threadId> @ <sha>` on its ledger row at dispatch. That row is the only record `§INV_LOOM_STACK_ONLY_ON_A_DISPATCHED_CHAIN` accepts, and the lane leaves the wave merge for a stack. Under **one shared tree**: assign a disjoint file set (the `§CMD_PARALLEL_HANDOFF` non-intersection proof) against the currently-running threads; on overlap the thread queues until the conflicting files free (first-claim-wins). **Dispatching a thread with neither is the failure this step exists to prevent** — a lane told nothing about where it may write defaults to the shared tree it can see.
7.  **[MANDATORY] Fan out its build — a concurrent /build-grade AGENT** — spawn a background builder **agent** (Agent/Task tool) with its `description` **leading with the bracketed threadId** (`description: "[ENG-3141] build extract-totals"`) and a full `/build`-grade context pack (goal + interrogation digest + file partition + hard gates + scope guard + `assets/LOOM_AGENT_DIRECTIONS.md` by reference, which tells it to prefix every line with `[<threadId>]`). **Never `Skill(build)`: the Skill tool is sequential, so a `Skill(build)` call blocks the loop and serializes the very parallelism loom exists for. Loom is carved OUT of `§INV_PREFER_BUILD_SCRUTINIZE`'s "prefer /build" wording — its fan-out is /build-*grade agents* run concurrently, not the /build *skill* in-line.**

### Conducting (continuous, while builds run)
*   **Relay** agent `SendMessage`s: maintain the *waiting-on* graph (a cycle = deadlock); poll agent status (silence past a timeout → probe); keep this loom's slot file current as lanes start and land (`¶INV_SLOT_CAP_IS_GLOBAL`): `--heartbeat … --lanes` when the lane set changes, `--claim` on dispatch, `--claim-state … done-uncommitted` on hand-back, `--claim-state … landed` on landing. Escalate per the **hard floor**: it reaches your manager (the operator if you have none — § The manager chain), and the relay keeps running meanwhile. **Under one shared tree the relay also brokers files** — grant out-of-partition claims when unclaimed, conflicts **first-claim-wins** (loser's step defers); **under worktree-per-lane there are no claims to grant**, and a lane asking for one is a lane whose brief did not reach it.
    *   **The waiting-on graph is ROWED, not remembered (`¶INV_LOOM_WAITING_IS_ROWED`)** — every block a lane reports opens a `## 📡 Relay / Conflict` entry carrying its `Waiting on` in the lane's own words (`assets/LOOM_AGENT_DIRECTIONS.md` § Progress reporting states that grammar), its `Since`, and its resolution; the waiting thread's `🧵 Ledger` `status` cell carries the one-line glance. A graph held only in the conductor's context is a graph a context clear deletes, leaving a cycle to be rediscovered from nothing — and nothing durable then says **why** a lane is waiting until a hand-over, which is exactly the moment it is hardest to reconstruct.
    *   **Instrument the silence-past-a-timeout poll with `engine lane-stall` — do not write a second detector (`¶INV_LOOM_STALL_IS_SWEPT_NOT_SENSED`).** `engine lane-stall "<sessionDir>" [--minutes N]` (default 30) lists every lane that is **not done** whose freshest signal is older than the threshold, reporting per lane the minutes since its transcript last changed, the minutes since its last `## … [TAG] …` heading in its own log under `builds/` (never the conductor's session log, which dates no lane), and a **state**: `done` (handed back) · `parked` (its turn ended with no hand-back) · `running`. It **exits 3 when at least one lane is stale** and 0 when none, and it is read-only — it never touches a lane, a transcript or the log. `--all` shows every lane including the fresh ones, which is how you tell *no lane is stale* from *no lane was seen*.
        *   **Run it at two moments, and the second is the one that matters.** At each loop gate, as a cadence (below) — and **before the conductor settles in to wait on live lanes**, because the gate fires on a *unit of progress* and a weave where nothing lands never reaches a gate. A gate-only sweep is absent in precisely the case it exists for.
        *   **Why an external reading rather than better reporting.** Every other progress signal in this weave is **self-reported by the lane** — a `SendMessage`, a `[TAG]` log heading, a `SubagentHandback`. A lane that has hung emits none of them, and an absence is indistinguishable from quiet work. The sweep reads the filesystem, so it sees a lane that cannot speak.
        *   **`parked` is the reading to act on.** A lane whose turn ended with no hand-back chose nothing and recorded nothing — it is the shape an operator sees as an agent hung up waiting. Row it under `## 🅿️ Parked` as `stopped without handing back`, **distinct from a thread the conductor parked for a reason**, with the lane's **LOG PATH** (its only surviving handle) and the next move. Read that log before briefing its state: a lane can land files after its last entry.
        *   **It reports STATE, never reachability.** A dead lane's transcript stays on disk, so the sweep reads it `parked`, not gone — so it does not answer Phase 0's *"is this lane addressable at all"*, which only a `SendMessage` attempt settles. Treating one as the other is a discriminator both states share.
        *   **A `0 lanes seen` result is not a clean weave** and is never reported as one. Re-run with `--all` and reconcile against the `🧵 Ledger`'s live rows; a count below the ledger's means the sweep is not seeing this weave's lanes, most likely because a brief did not lead its prompt with `[<threadId>]`.
    *   **Escalate a deadlock as a DRAWN graph, not as prose** — `Skill(graph, "<the waiting-on edges>")` renders the cycle in the engine's one ASCII diagram vocabulary (`§CMD_FLOWGRAPH`), which is what makes a cycle legible at the moment whoever answers the escalation has to break it. **Instead of** a sentence naming who waits on whom, which is the least readable thing this skill asks anyone to parse. It fires on the cycle rather than on a menu pick — the deadlock is already a hard-floor escalation, so the drawing rides that escalation (it reaches your manager (the operator if you have none — § The manager chain) inside the /ask, by path) and costs the gate no slot.
*   **🔍 Scrutinize on land, per the Scrutinize disposition — and WRITE THE CELL either way (`¶INV_LOOM_SCRUTINY_IS_DECLARED_AND_ROWED`)** — as each thread's build hands back, spawn a concurrent **scrutinize AGENT** (`description: "[<threadId>] scrutinize …"`, threadId-prefixed like the build) — a `/scrutinize`-grade critique of its Build Report and its diff — **never `Skill(scrutinize)` (it serializes the critiques)**. The **Scrutinize** disposition decides *whether and when* (every build lane · risky lanes the conductor names · once at the wave boundary · off); the **Detail-importance** disposition decides which of the findings reach your manager (the operator if you have none — § The manager chain), never whether the critique happened. Run a combined triage across threads (fix / skip / defer), then dispatch fixers; a MUST-FIX is already on the hard floor. **The half that is new is the cell**: as the lane hands back, its `🧵 Ledger` row's `scrutiny` cell is written in the same move — `dispatched`, then `clean` or `<n> findings → triaged`, or **`not scrutinized — <why>`** naming which it is (`not covered — risky lanes only` · `not covered — disposition off` · `deferred to the wave boundary` · `operator opened the PR anyway at gate N`). **An empty cell is the defect this exists to stop**, because *scrutinized and clean* and *never read by anybody* are the two readings a weave cannot tell apart afterwards, and the second is what twenty-eight lanes across four seats turned out to be. Under *once at the wave boundary* the cell reads `deferred to the wave boundary` until the boundary's pass closes it, and a wave that integrates with that cell still deferred has not run its scrutiny.
*   **Offer `/snapshot` then `/pr`** per landed thread (`§INV_OFFER_DONT_FORCE_SKILLS`, composed-writes) — `/snapshot` posts status + commits the reviewed files; **`/pr` pushes the branch, opens the PR, and carries the whole code review**: it requests an automated Copilot review and watches Copilot plus the Codex connector (gated on its 👀 reaction), relays failing check names with their annotations as `path:line`, treats each finding as a claim to VERIFY rather than an instruction, and posts a reply recording every finding's disposition — accepted, rejected with the evidence, or deferred with a destination. It exits only into a named state and re-arms when a fix push moves the head, so **a PR is complete only when the gates pass AND every review comment carries a reply**. **Do not reach for a separate review step; it is already in there**, and a conductor that adds one is paying twice for the half `/pr` already runs. Advance the ledger. **Both offers are what the Interruption disposition governs**: under *Automatic* the conductor skips the offer and invokes `/snapshot --yes`, which waives the skill's own confirm as well, so the thread lands with no question in front of it — the skill still declines a red-gated commit and a description rewrite on its own authority. Under *Quiet* the `/pr` offer goes the same way, since a pull request proposes a change rather than landing one.
    *   **🔍 BOTH OFFERS READ THE `scrutiny` CELL, AND THAT IS WHERE THIS BITES (`¶INV_LOOM_SCRUTINY_IS_DECLARED_AND_ROWED`).** A skip is not a decision anybody takes — **it happens because a lane hands back clean and the next move is right there.** A disposition chosen at Setup is hours and a context-load away by then, and a ledger column is read only by somebody already reading the ledger, which is not where anyone is standing at that instant. So the row has to be read **at the next move**, and these two offers are that move. They are read differently, deliberately:
        *   **`/snapshot` FLAGS and proceeds.** The card and the ledger line carry `not scrutinized` where the cell says so, and the snapshot runs. **Blocking it is refused**: `/snapshot` commits the lane's own reviewed slice to the lane's own branch and produces the sha the wave merge consumes, so a block strands finished work uncommitted — work at risk, which is a worse failure than an unscrutinized commit on a lane's own branch.
        *   **⛔ `/pr` DOES NOT appear as `/pr` on a never-scrutinized lane.** It appears as **scrutinize first, then PR**, with the scrutinize dispatch as the card's default answer. This is the step that actually failed: a pull request is where the change stops being the loom's problem and becomes a reviewer's, and *2026-10-28, relayed* two pull requests went out on their lanes' self-reports alone. **Opening it unscrutinized stays reachable and is the OPERATOR's choice, never the conductor's**, and it writes its own cell — `not scrutinized — operator opened the PR anyway at gate N` — which travels to the inheritance and into the debrief. The conductor is the party that skipped twenty-eight times, so it is not the party the override belongs to.
        *   **The cost of choosing block over flag here, named rather than hidden**: one extra card per unscrutinized lane at the moment the conductor wanted to open a pull request, and a conductor who genuinely judged a lane not worth reading now spends an operator's keystroke to say so. That is the trade — a flag nobody is obliged to act on is the prose outcome this whole change exists to leave behind, and the override is what keeps the block from becoming friction with no exit. It is the same mechanism as the in-flight disclosure rule above, read at a different moment: the work proceeds, and the row says what the reviewer is not getting.
        *   ⚠️ **No position of *Interruption* reaches this card.** Under *Quiet* the `/pr` offer fires unasked, so a card riding that offer would vanish in exactly the position a long weave spends most of its time in — which would re-open this hole in the one place it is widest. It joins the four things named under that disposition as untouchable: the wave merge's confirm, `/ticket` (the `/snapshot --yes` auto-file of un-ticketed work aside), `/inbox-post`, and the hard escalation floor.
    *   **Where lanes run in their own trees, `/pr` moves to the wave boundary and `/snapshot` does not** (`§INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY`). The per-thread `/snapshot` is what produces the branch and the sha the merge consumes, so it keeps its place; a per-thread `/pr` would propose the per-lane pull request this loom integrates specifically to avoid. One PR per assembled wave, offered there. **The exception is a lane the conductor deliberately dispatched onto another lane's branch** — a dependent lane never joins the wave merge, so its PR is opened per thread against the lane below it and assembled with `/pr --stack` at the boundary (see there).
    *   **It fires per thread at its landing, never per batch, and the confirm cost is deliberate.** One `/snapshot` confirm per thread is six confirms on a six-lane wave, and that cost **is the point**: the confirm is the one place the judgement between *accepting* a thread's work and *committing* it gets made. Batching several landed threads behind a single confirm does not save the judgement, it removes its owner — a conductor holding threads back to snapshot them together has deleted the only moment that call is made. A thread lands, it snapshots. **This rule is about cadence and the Interruption disposition is about whether anyone is asked, so neither overrides the other**: a wave's `/snapshot` count stays one run per landed thread in either position — six runs on a six-lane wave, with six confirms under *Confirmed each time* and none under *Automatic*. Under *Automatic* the judgement this bullet is about was made once, at Setup, for every thread in the weave; that is a different thing from batching it away, since each thread still gets its own run and its own gates, and the one call `--yes` cannot delegate is a commit the gates came back red on.
*   **Council per policy** — run `/council` per the **Council disposition**: *auto after each PR* runs a panel once a thread's PR is up; *selective before PR* runs one **before** the PR opens, only on threads you flag; *none* skips it. A council MUST-FIX is a **thread loopback** — it reaches your manager (the operator if you have none — § The manager chain) marked `reserved-for: operator`, and on the operator's confirm loop that thread back to interrogate or build (for a before-PR panel, that loopback happens before the PR ever opens).
*   **Closing snapshot before the proof** — after council settles (and after any PR-review / CI-gate fix cycle it triggered), **run a final `/snapshot`** on the thread, passing the thread's key after `--` when it has one, an `auto-filed <KEY>` an earlier snapshot of the thread stamped included. The earlier snapshot committed the reviewed *build* and opened the PR; this one **commits everything that landed since** — the council MUST-FIX fixes, the PR-review and gate fixes — and **advances the ticket to `In Review`** (the PR is up and reviewed; loom does not merge, so In Review is the state a thread lands on). It's the thread's closing checkpoint: `/snapshot` commits the thread's files scoped + gated on green, posts a closing comment, and flips the status (non-regressing) — all under its own batch confirm (`¶INV_LOOM_COMPOSED_WRITES`). Run it **before** the auto-proof, so the proof reflects the fully-committed, review-settled state and links the final commit.
*   **⭐ Prove EVERY thread at its end, while its context is still hot (`¶INV_LOOM_EVERY_THREAD_PROVES`)** — the moment a thread finishes its work, and **before its agent is left to go cold**, compile what it found into a shareable visual proof at a public URL. **Every thread, not only the ones that reach a PR**: a read-only investigation, a measurement lane, a repair, a page correction, a scoping sweep — each ends with a proof page. A lane that shipped proves the change; a lane that only investigated proves **what it established and how it knows**. **The timing IS the rule.** A finished lane still holds its screenshots, its raw command output, the hypotheses it rejected and the reason each fell — none of which survives its context ending, and none of which a later reader can reconstruct from the written report alone. A proof compiled a day later is a summary of a report; a proof compiled while the context is hot is evidence. So the proof is produced **BY the thread as its last act** — put it in the brief when you dispatch, and for a lane that has already returned, **resume it by name** (`SendMessage`) rather than dispatching a fresh agent that would have to re-derive everything it knew. Where a thread genuinely has nothing renderable, `/prove` self-skips and the ledger records **`no renderable evidence`** — an explicit skip, never a silent one. It runs **without a gate**: the proof skills are read-only — they change no code, commit nothing, file nothing — so there is nothing to confirm. Invoke as `Skill(<variant>, "<slug> — problem: <what was broken or unknown>; solved: <what was established or shipped + how it is verified>")`, the variant chosen by the shape test below. They trust the trail and never re-investigate. **Record the returned proof URL on the thread's ledger row** — a thread with no URL and no exemption note is an incomplete thread.
    *   **🪞 A pass the conductor runs in its OWN context is a thread, and proves like one.** The rule binds the *work*, not the *actor* — so a ticket filed inline, a grooming pass, a decision pass that published a board the operator asked for, a document published, a measurement taken on the main thread each end in a page, exactly as a dispatched lane does. A decide pass whose output is an ask is outside this rule and needs neither exemption below: the ask file and the `/decide` record its `context` names are its artifact, and `decisionPasses` gates on it. **The conductor's context is the hottest one in the loom and it is the one place nothing was being proved**: measured on a single evening, every lane whose brief carried the instruction produced a page and everything run inline produced none — a ticket filed with a control on every zero, a grooming pass whose entire output was a controlled measurement, and a document verified by content among them. Dispatching is what made the rule fire, which made the rule a property of dispatch rather than of finishing. A conductor holding its own finished finding **resumes nothing and dispatches nothing** — it invokes the skill itself, in place, before moving to the next unit.
    *   **Two exemptions, and nothing else.** Each is recorded on the row as `exempt — <clause> — <what the thread's whole output was>`; a bare `exempt` is an unworked row and `proofPages` does not clear while one stands, the same shape as a bare `open` on an ask row. **It is the conductor's call, never the lane's** — a lane may report that it believes a clause applies and may not act on that belief.
        *   **The SUBJECT would be refused as a ticket's subject.** One discriminator, two uses: `/ticket` §3 step 0 refuses a **guard or check**, **tooling**, **a seat or ownership question**, and **agent-coordination machinery** as ticket subjects, and `¶INV_LOOM_HANDBOOK_BEFORE_FILING` already binds a conductor to that list. A thread whose subject sits in it earns no page either — a lint, a CI job, a hook, gate plumbing, a worktree helper, who owns which file. **The carve-out travels with the list**: in `Product: Orchestration` the orchestration machinery IS the domain work, so a thread on loom, groom, decide, direct, intake or the decision transport is an ordinary subject there and proves. Carrying the carve-out is what stops this clause deleting its own evidence — without it, the lanes whose pages are the thing that works tonight would all be exempt. **And the carve-out stays a project, never a category**: "engine work" and "coordination machinery" buy no page and dodge none, because an exemption any thread can claim by renaming its work is not an exemption.
        *   **NOTHING WAS ESTABLISHED.** Not that the change was small — **size is not the test and may not be cited as one**. The test is whether the thread can name, in one sentence, something a reader did not know before it ran: a figure with its denominator, a zero with the control that fired, a mechanism that was wrong and now is not, or a verdict another agent would act on. A one-character edit that corrected a false belief proves; a large refactor that established nothing does not. **A thread that wrote outward is never exempt under this clause** — a ticket filed, a tracker comment posted, a document published, a commit carrying a corrected mechanism all mean somebody will act on it, so the finding exists whatever the diff size.
    *   **🎚️ Pick the VARIANT by the shape of the answer, and reach past the default.** `/prove` shows one settled claim · `/prove-explore` explains a settled answer too plural to compress, a territory whose sub-questions the brief can name before dispatch · `/prove-visionary` proposes where the answer is NOT settled and someone must choose, options-without-a-recommendation included · `/prove-plan` lays out a route already decided as a page of ordered steps, each with its check and its owner · `/prove-explanation` teaches one mechanism to a newcomer, idea first, then a worked example with real values. **Route by the shape of the answer, never the size of the subject.** The conductor owns this fork because `/prove` names none of its siblings and silently absorbs a misroute, and because every variant's triggers are written as a human's opening request, so none of them fires at thread-close and picking by the nearest-sounding trigger returns `/prove` every time. Measured: nine consecutive briefs in one session named `Skill(prove, …)` and neither sibling was reached for once. **Name the variant in the dispatch brief** rather than leaving the lane to default, and a closed finding with nothing renderable goes to `/prove-explore` with bare sections before `no renderable evidence` is even considered.
*   **📚 Feed the standing documentation lane — batched, on a landed thread (`¶INV_LOOM_DOC_LANE_IS_STANDING_AND_BATCHED`)** — one doc lane lives for the session and the conductor feeds it; it is not re-spawned per thread. **The register, not the lane's context, is what survives**: the conductor keeps the `## 📚 Docs owed` rows and the lane reads and updates them, because a context clear ends every in-process lane while a written row does not. The feeding is bound by these rules:
    *   **Batched on a landed thread, never per change-event.** A wake is the bill (`¶INV_LOOM_WAKES_ARE_THE_BILL`), and a loom landing a thread every few minutes would otherwise wake the lane constantly. One feed per landed thread, carrying that thread's whole claim surface: its Build Report's `## Files touched (authoritative)`, the subjects it changed, and the open `📚 Docs owed` rows it bears on. A thread that changed no documented behaviour is fed as a row saying so, not as a wake.
    *   **The lane runs `/revise`, which is claim-scoped.** `Skill(revise, "<the landed change>")` — it locates the sentences the change falsified, repairs those, and returns a Revise Report. Its `## Register rows owed` is where the conductor's next rows come from. The lane is **forbidden** the tree's index, pages the change does not reach, tree-wide count audits, and inventing a home for an undocumented change — those are `/document`'s, because a diff cannot scope the tree, and the lane rows them back rather than taking them.
    *   **The register row is the state of record.** A row closes as `revised — <report path>`, or states what the lane found that leaves it open; a bare `open` is an unworked row. **Open the rows as the thread lands** rather than at Synthesis: a register written only at the end is lost by exactly the exit this feeding exists to survive.
*   **⚖️ Row a rule a lane could not land, and rule on it (`¶INV_A_RULE_OWED_HAS_AN_OWNER`)** — the shared directive files sit outside every lane's partition, so a lane that learns a durable rule writes a `## Rule owed` block and emits a hand-back line, `rule owed → <file>: <clause>`. That invariant names **the coordinator** as the party who acts on it, and this is where that happens: on a hand-back carrying such a line, open a `## ⚖️ Rules owed` row as the thread lands, then either **land the rule** in the named file or **decline it with the reason**. Both close the row. **The harvest's selectivity does not reach this row** — a rule owed arrives already judged worth keeping by the lane that paid to learn it, and the cost of dropping one is not a lost finding but a rule the next lane rediscovers; nine were lost in one session, two of them twice. A decline stays visible, because a rule rejected on purpose and a rule dropped on the floor read identically once the session ends. **`rulesOwed` gates this, and it clears on an empty result written down, like `docRegister`**: a weave whose lanes owed no rule passes by recording that reading, never by skipping the register — an unwritten empty and a forgotten register are the same artifact.
*   **📨 Hand a topic to another seat — ROW IT, THEN SEND IT (`¶INV_HANDOVER_IS_A_ROW`, `¶INV_HANDOVER_CLOSES_ON_ACK`)** — a groom pass now routinely ends by routing topics to seats that are not this one, and this is the declared verb for it. **An ad-hoc peer `SendMessage` is not a handover; it is a handover's transport.** The move, in this order:
    1.  **Open the `## 📨 Seat handovers` row first** — `direction: sent`, the seat's **from-name and its pane id**, the topic in one line as the receiving seat will read it, and its **member links** (ticket keys, comment ids, inbox roots). A topic named with no members is a row the seat cannot act on, and the member that most needs writing down is the one that was in no topic at all until the routing found it.
    2.  **Then send** the peer message, and **record the delivery reading on the row** — `queued`, `delivered`, or `send failed — <what>`. A queued send is **not** a read: a peer in a different permission mode holds it for its user, and nothing reports back from a Remote Control or a cloud session.
    3.  **Leave it open.** The sender may not close its own row, because an un-acked handover is the case the row exists to show. The row closes on the receiving seat's **own words** — `taken`, `declined — <why>`, or `already done — <the evidence it gave>` — and a decline closes it as surely as a take, on the `⚖️ Rules owed` argument: a topic refused on purpose and a topic dropped on the floor read identically once the session ends. **An ack that arrives as a peer message is transcribed onto the row**; left in the sender's chat it is the bug restated.
    *   **Row what arrives, too.** `direction: received` is a first-class row, not the sender's read backwards: another seat asking this one to act on its own ground — *as `tree`'s owner, should this changelog entry be written* — is the same shape with an owner and an outcome, and a one-way register leaves that round trip exactly as unrowed as the batch it was sent beside.
    *   ⚠️ **The `→ <seat>` reply is NOT this row and may not stand in for it.** `§INV_GROOM_MARKS_WHAT_IT_WRITES` spends `→` as the route marker a pass posts onto an inbox root, and `§INV_EXCLUDE_OWN_COMMENTS` drops it on the next drain so the pass's own reply does not return as fresh signal. It is what stops the root being re-offered. Nothing on the receiving side reads it as an assignment, and making it mean one would couple two meanings onto one marker — the second of which would stop working quietly.
    *   **This is not `## 🤝 Hand-over written`.** That receipt is a conductor handing its own state to its own SUCCESSOR across a context boundary; this is one seat handing one topic to a PEER that keeps its context and answers in its own time. The two were one word and are two registers.
    *   **`seatHandovers` gates this, and it clears on an empty result written down, like `docRegister`**: a weave that handed nothing to another seat passes by recording that reading, never by skipping the register — an unwritten empty and a forgotten register are the same artifact. Un-acked rows **travel to the inheritance** (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`), and they are the kind most exposed there, because the party who owes the ack is not the party handing over.
*   **🧭 Row a vision deviation as the thread lands; never reconcile it yourself (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`)** — when a landed thread contradicts a vision document the weave executes against (a chapter re-scoped, a dependency re-cut, a measurement superseded, a principle falsified), the conductor opens a `## 📚 Docs owed` row with `destination` reading **`/direct` — reconcile**, and the deviating session stops there. **A deviating session does not reconcile the document**: reconciliation is a later composed `/direct` pass's job, and a session correcting the vision it just deviated from is the author grading its own paper. **The destination is chosen when the row is opened, by one question — is the falsified sentence a statement of FACT about the system, or of INTENT about where it is going?** Fact goes to `/revise`, which repairs a claim by making the sentence true. **Intent, or a fact whose supersession the document's history must keep, goes to `/direct`** — because on a vision, making the sentence true *erases the deviation*, which is the decision trail the document exists to hold, so a misrouted row is repaired into invisibility by a lane doing its job correctly.
*   **Harvest good findings at thread end** (`§INV_OFFER_DONT_FORCE_SKILLS`, composed-write) — when a thread finishes its chain, read its Build Report's `## Out-of-scope noticed (not touched)` section plus any `/scrutinize` deferrals, and **offer `/inbox-post` for the genuinely notable ones only** — real bugs, concrete follow-up work worth tracking — not every incidental note. Be selective: a thread that surfaced nothing worth filing posts nothing. **Signals first, a ticket only for a chunk** (`¶INV_LOOM_HANDBOOK_BEFORE_FILING`): a thread's leftovers are findings, so they leave as inbox drops; offer `/ticket` only where a leftover is a whole landing arc in its own right, and route tooling or gate friction to 🛠️ Tooling & Gates rather than letting it become a ticket.
    *   **One finding → `Skill(inbox-post, "<finding>")`**, straight to its channel.
    *   **Several findings → offer `Skill(groom, …)` first**, to cluster them into topics before anything is dropped. A thread that noticed six things should not produce six drops for somebody to group by hand later.
*   **Thread end is not the only moment (`§INV_OFFER_DONT_FORCE_SKILLS`)** — a conductor or a thread noticing something small and out of scope drops it **immediately** via `Skill(inbox-post, …)`, no ceremony and no waiting for the thread to close. Small things are what a held queue loses.
*   **Find the next thread at thread end** (`§INV_OFFER_DONT_FORCE_SKILLS`) — when a thread lands and the loom has capacity, offer to pull more work: `Skill(inbox-next)` when the batch came from a curated Linear project (ranked, in-project), `Skill(groom, …)` when the candidate work is still a pile of ungrouped items — it hands back topics, and one topic is one thread per the grouping rule above — or `Skill(ticket-search, "<keywords>")` to find related tickets by keyword. A chosen result becomes a new thread (the add-a-thread flow). This is how the no-rush loop refills itself.
*   **Keep the ledger live** — rewrite it as threads advance; surface it at each loop gate. Per thread, record its **mandatory-step completion**: the ticket-disposition answer, whether interrogation ran (or was skipped because the Interrogation disposition is None), and 🔍 the **`scrutiny` cell** — the scrutinize agent's id and its outcome, or which position of the Scrutinize disposition left the lane unread (`¶INV_LOOM_SCRUTINY_IS_DECLARED_AND_ROWED`). This record IS the `threadDispositions` proof that gates Loom→Synthesis (`¶INV_LOOM_MANDATORY_STEPS`) — you cannot close a loom whose threads skipped their mandatory steps, and **an empty `scrutiny` cell is an unworked row that does not clear it**, the same shape as a bare `open` on an ask row. A written `not scrutinized — <why>` DOES clear it: the gate exists to stop a skip being invisible, not to stop one being chosen. 🔍 **The cells are also what the `lanesUnscrutinized` proof field is counted FROM at the wrap-up, and that field is the arm that actually refuses** — `engine session phase` exits 1 without it, so a conductor keeping the cells current as lanes land is doing the counting early rather than reconstructing it from memory at the close, which is the point at which a weave least remembers (`¶INV_LOOM_SCRUTINY_IS_DECLARED_AND_ROWED`).

### The wave boundary — integration (`§INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY`)
*Where a wave's lanes are brought back together, and the only place the once-per-wave suite has a tree to run against. **Specified and unexercised** — the merge half cannot fire until lanes run in their own trees, and the clause below says which half ships before that and which waits.*

**What a wave boundary IS, written because nothing here said it.** The loop gate below fires on a **unit of progress** — one thread landing. A **wave** is the whole fan-out: every lane dispatched since the last boundary. These are different cadences, and integrating at the gate merges one lane at a time, which is per-lane integration wearing the boundary's name. The boundary is reached when **every thread in the current `## 🌊 Wave` block's `Threads fanned out` set has landed or parked and none reads `running`** — the conductor takes that from `engine lane-stall "<sessionDir>" --all`, whose `done` · `parked` · `running` states are already the sweep's output (Conducting above rules what each one means, including that it answers **state, never reachability**). **Detecting the boundary is a read: no slot, no confirm. The merge it leads to is a write and takes one** — the loop gate's rule that a cadence may run unconfirmed but may not publish unconfirmed, applied to something with more consequence than a publish.

**This step and the file partition are two answers to ONE question, and a loom runs exactly one of them.** The partition is **prevention** — disjoint file sets allocated up front so two lanes can never touch one file, which is why no conflict has ever arisen here. A merge is **detection**, and the better instrument: it finds the collisions that actually happened, in the text, at the moment the trees meet, rather than the ones predicted at allocation. Under worktree-per-lane **the conductor computes no partition and brokers no claims**, and this section is what "lanes land" means. Under one shared tree **there is nothing to merge** — every lane committed to the same branch already — and the boundary records `nothing to merge — shared tree`. Running both pays for prevention and detection and buys the conductor back the job the worktree shape exists to remove.

**Which half ships without worktrees.** The boundary, the suite-once-against-a-named-sha, and the wave row are exercisable under the shared tree today, with an empty merge step. **The merge, the ordering and the conflict hand-back are not reachable at all until lanes have their own trees** — two worktrees cannot share a branch, so a lane branch to merge does not exist yet. A conductor must not report the unreachable half as working because the reachable half did.

**The mechanism** — each line answers one of the questions `docs/CYCLICAL_LOOM_VISION.md` § `@engine/execution-shape` asks of this step:

*   **WHO — the conductor**, which already holds the ledger, the lane list and the wave block, and is the only participant that can see every lane's branch at once. This is the loom's **one** git write that no composed skill performs, so `§INV_LOOM_COMPOSED_WRITES` carries a narrow carve-out named in Constraints: the conductor may run the merge of a lane's named branch into the session branch, under the operator's confirm (a `reserved-for: operator` /ask when the seat has a parent — § The manager chain), and **nothing else** — it authors no change, resolves no conflict, and rewrites no history.
*   **ONTO WHAT BASE — the session branch, captured at Setup as a name AND a sha** and echoed into the ledger header (`▶️ Loom Opened`). It is recorded at the open because it is not reconstructable at the boundary: under worktree-per-lane the conductor's tree is not any lane's, and a base inferred later is a base guessed. A loom with no recorded session branch does not integrate — it reports the missing field and stops, rather than choosing one.
*   **IN WHAT ORDER — landing order, first-landed first.** Three reasons, and the order is not arbitrary: it is **already written down**, because each lane's `/snapshot` stamps `committed <sha> on <branch>` into its Outcome as it lands; it makes the conflict loser the **later lander**, so the loom keeps the one precedence rule `§INV_LOOM_FIRST_CLAIM_WINS` already states (*the later thread's conflicting step defers*) instead of acquiring a second; and the later lander is the lane likelier to still be warm, which is the lane the conflict answer needs addressable.
*   **WHAT A CONFLICTING LANE DOES — the later lander resolves its own, in its own tree.** On a conflict the conductor **aborts the merge** and leaves the session branch at its exact pre-merge sha — **never resolves, never `-X`**, the same idiom and the same reason `/pr` §Constraints already binds its cherry-pick to. It then resumes that lane (`SendMessage`, by name, mirroring `§INV_LOOM_EVERY_THREAD_PROVES`'s resume-rather-than-redispatch rule) carrying its branch name, the session branch's sha, and the conflicting paths as `git diff --name-only --diff-filter=U` named them. **The lane merges the session branch INTO its own branch and resolves there** — never the reverse, because the session branch is shared ground the earlier lanes have already landed on, and handing it to a lane as a resolution surface is how one lane's bad merge reaches every other lane's work. The conductor re-attempts once the lane reports resolved. **A second conflict on the same lane is a hard-floor escalation, not a loop.**
*   **WHAT THE SUITE RUNS AGAINST — the assembled tree, named by sha (`§INV_LOOM_GATE_RUNS_ON_THE_INTEGRATED_TREE`).** The once-per-wave suite runs in the conductor's tree on the session branch **after the last merge lands**, and the wave row carries the sha it ran against. **A partially integrated tree is forbidden as its subject**: a wave with one lane merged and another's conflict still open records `suite deferred — <threadId> conflict open` and runs nothing, because a green recorded against an assembly nobody will ever ship is worse than an unrun gate — it is an unrun gate that reads as evidence.
*   **ONE PR FOR THE ASSEMBLED WAVE, offered once the integrated tree is green** (`§INV_OFFER_DONT_FORCE_SKILLS`, composed-writes) — `/pr` on the session branch, whole-branch, linking every ticket the wave carried (`Closes` the primary, `Relates` the rest). **A wave branch is MIXED by construction**, and `/pr` §1 offers on a mixed branch to cherry-pick one ticket's commits onto a fresh branch — which is the per-lane-PR shape declined for this step, arriving as a default rather than as a choice. **Merging `--no-ff` is what makes that decline structural instead of remembered**: a merge commit exists, and `/pr`'s own Merge Commit Rule refuses merge commits in a cherry-pick set and forces the whole-branch path. A fast-forwarded single-lane wave leaves no merge commit and re-opens the fork, so `--no-ff` is load-bearing rather than cosmetic.
    *   **A PR STACK IS NOT WHAT THIS STEP BECOMES, and the reason is the thing a stack asserts.** GitHub can chain pull requests into a numbered stack (`1/3`, `2/3`, `3/3`, one root base), and the wave's `<k>` lanes look like `<k>` stackable PRs. They are not. **A stack asserts that each PR depends on the one below it**, and a wave's lanes are parallel *by construction* — the file partition and the conflict broker exist precisely so that they do not depend on each other. The merge order is **landing order**, which is arrival time: stacking by it would assert `<k>-1` dependencies not one of which was measured. One PR for the assembled wave stands.
        *   **What it costs to get this wrong is not cosmetic.** Two independent PRs merge as each is approved; chained, the lower one's merge waits on the upper one's reviewer, and a reviewer is told to read in an order that does not matter. A false chain is worse than the fat PR it was meant to improve on.
        *   **THE ONE CASE A CONDUCTOR MAY OFFER A STACK is one it created itself**: where it dispatched lane B's tree **off lane A's branch** rather than off the session branch, because A's work was a prerequisite B would otherwise have had to wait for. That is a dependency the conductor *decided* and can name, and it leaves two records: B's ledger row, `based on <threadId> @ <sha>`, written at dispatch (*Adding a thread* step 6), and git, where B's branch descends from that sha. Offer `/pr --stack` (its §6) over those lanes' PRs, bottom lane first, and leave every other lane to the wave's one PR. Such lanes do not pass through the wave merge at all; they chain, which is what being dependent means.
        *   **The dispatch record decides, and git checks the record** (`§INV_LOOM_STACK_ONLY_ON_A_DISPATCHED_CHAIN`). The conductor's memory of why it dispatched something is not the record, and neither is a branch that merely descends from another. Where the record exists, `/pr` §6 checks it against git — each upper PR's base ref must be the lower PR's head ref — and refuses to rebase, retarget or reorder anything into line, so a recorded chain git does not show is rejected rather than built.
        *   **Where two threads are independent — the default, and what settles it.** Independence is the *assumption*, and a dependency has to be shown rather than the reverse, so a conductor that cannot tell does not stack. One ordering settles it, and the first that applies wins: **no `based on` record on B's row** → independent, whatever git shows — two threads dispatched off the same session branch are independent **however related their tickets read**, and a branch cut from another's head by accident is the cosmetic chain `/pr` §6 already offers to leave unstacked; **a record, but `/pr` §6's ref check fails** → STOP and report it, nothing stacked; **a record and the refs chain** → offer `/pr --stack`.
        *   **`/pr` §6's `ancestor=1` is not a STOP.** With the refs chaining, it means A moved on after B was cut — A taking review fixes is the ordinary way — and it goes into the stack confirm as `A moved on since B was cut`. Any other non-zero exit is a ref that could not be read, and it stops the offer like a failed ref check. Two threads on the same subsystem, two sub-issues of one parent, two threads the same operator asked for in one breath — all independent, because being *about* the same thing is not being *built on* the same thing. Unstacked is the safe answer and it is also usually the true one.

**This re-times the closing snapshot's `In Review` flip** described in Conducting above: a thread lands into the wave before the wave's PR exists, so its ticket reaches `In Review` when **the wave PR carrying it** is up, not when its own merge landed. The per-thread `/snapshot` is unchanged — it commits the lane's reviewed slice on the lane's own branch, which is exactly what the merge consumes.

**Record the wave in the `## 🌊 Wave` block as the boundary resolves** — the boundary reading, each lane's merge in landing order with its disposition, the integrated sha, the suite's result against that sha, and the wave PR. That row IS the `wavesIntegrated` proof gating Loom→Synthesis, and like `docRegister` it **clears on an empty result written down**: a loom that never reached a boundary, or one on a shared tree with nothing to merge, passes by recording that reading, never by skipping the step.

**⚠️ When every lane is COLD, this step has no settled answer and does not invent one.** Resuming the losing lane is the whole conflict mechanism, and it is unavailable once the lanes have ended — which is the likely state at a session-end integration, and which **`engine lane-stall` cannot tell you**, because it reports state and not reachability: a `done` or `parked` reading is consistent with both an addressable lane and a gone one, and only a `SendMessage` attempt answering *no transcript found* settles it. So a conflict on a wave whose losing lane is unreachable is a **STOP**: the conductor aborts the merge, rows the conflict under `## 📡 Relay / Conflict` with the branch and the `--diff-filter=U` paths, opens a `## 🔓 Open claims` row for the fallback decision, and escalates: the decision reaches your manager (the operator if you have none — § The manager chain). **It does not resolve the conflict itself, hand the conflict to a fresh lane that did not write the code, or drop the wave** — each of those is a choice nobody has made, and `§INV_LOOM_PASS_ON_NEVER_DISCARD` makes passing it on the only legitimate close.

### The loop gate (`AskUserQuestion` only when there is no parent, marked /asks otherwise — § The manager chain; defaults to keep-going per `¶INV_LOOM_NO_RUSH_TO_CLOSE`)
Present after each unit of progress (a thread landing, a batch of builds finishing):

**Lead with the forks, then the exits (`¶INV_LOOM_SURFACES_FORKS_UNASKED`)** — a conductor that manages seats first reads the asks addressed to it (§ The manager chain, *When you are the manager*). Then run the decide pass whenever `/decide`'s §1E cadence says to, and open the gate with the forks it mined, each decidable from its ask; the offer pool below stays underneath it. The decide pass follows `/decide` §1–§3 (mining, the fork test, framing a card) and §6 (the record) as the loom's own procedure, then writes the forks as asks split by mark (below); it does not invoke the skill. `Skill(decide)` is invoked only when the operator asks for a board, and then `/decide`'s own rules apply in full. `/decide` owns the fork test, the cadence, the card discipline and where a non-fork is routed instead — follow those sections there. A mined fork reaches your manager (the operator if you have none — § The manager chain): each goes up as an /ask carrying its card (to `operator` when the seat has no parent), and the gate carries on with what does not depend on it. It replaces the ad-hoc mid-thread question round, never the dispatched `/interrogate` of the add-a-thread flow's step 3 (`¶INV_LOOM_MANDATORY_STEPS`). A pass that mines nothing presents the menu alone.

**The PASS runs on the cadence, and a pass that MINED A FORK writes its ask at that gate (`¶INV_LOOM_ASKS_AT_A_BOUNDARY`).** The loom follows `/decide` §1–§3 and §6 (mine, rank and card, the panel when offered, the record), and in place of §4's board and §5's collect it writes the mined forks with `engine ask new`, one question per fork, addressed per § The manager chain, **split by mark**: `reserved-for` belongs to the whole ask (`tools/ask-app/src/lib/format.ts`), so a mixed ask is either unmarked or blocks the manager from every fork in it. The ordinary forks go in one ask. Hard-floor forks and forks in a grant v1 reserved class (E–H) go in their own ask, `--reserved-for operator`, linked to the ordinary one with `--related`, never `--dependsOn`. **§3's panel offer is an `AskUserQuestion` (`§CMD_OFFER_COUNCIL_REVIEW`); a conductor with a parent puts it in the ask as a question of its own instead of at the terminal, or skips it and says so in the ask's preamble.** Only a seat with no parent, with the operator at this terminal, offers it there. The header and each question's card lines carry what `/decide` would have put on the page: `unblocks`, `lean`, `counter`, `falsifier`, the options as framed, and what was decided against in the `/decide` record its `context` names. A pass that mined nothing clears on the empty sweep (`no forks pending`) and writes nothing. **A board is published only when the operator asks for one**; `/decide` stays the skill for an explicitly requested shareable board, and that board's URL rides in the ask. *Measured 2026-10-29 (IDE-255)*: neither Planner-era board drew an answer on its page before the operator answered elsewhere, and the grant board's answer came in chat.

**A cadence may run without a confirm; it may not PUBLISH without one.** The two properties are independent and conflating them would let a page publish on every gate. A condition-fired offer that only **reads** — the stall sweep, the asks read, a reconcile against an open row — rightly takes no slot and needs no confirm: an operator should not have to choose to be told a lane died. A cadence that would **render and publish a page** is the expensive half wearing a cadence's clothes, and it reaches your manager (the operator if you have none — § The manager chain) as a boundary decision instead. So when a new condition-fired entry joins this gate, the question is not whether it is confirmed but **whether it publishes**. The decide pass publishes nothing: an ask file is a write to the asks store, not a page, and a board the operator asked for goes up under its own confirm.

**And "reports in between" already exists, free.** The live ledger is surfaced at every gate and is authoritative (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`). What it was missing is not frequency but **content** — it never said why anything was waiting, which is what made a weave with a live ledger read as a weave with no reports. The `🧵 Ledger` `status` grammar, the `📡 Relay / Conflict` `Waiting on` field and the live `🔓 Open claims` block fill that at no recurring cost. A shareable page on top stays `/prove-explore`'s, on demand (below).

**Row every ask, then read it at the next gate** — a pass that writes an ask opens its row in the log's `## 🗳️ Asks` block as it writes it: the `<seat>/<id>` that `engine ask new` printed, the seat it went `to:`, the gate, and the forks it holds. At the next gate, before mining fresh forks, work each open row with the Asks read below: `engine ask list --seat <your seat>` for what is still open and who holds it now, then `engine ask read <seat>/<id>` on each settled one, which stamps this seat's `readAt`. Carry what was answered into the pass and stamp `engine ask acted` once it is used. Re-pinging stays manual (§ The manager chain).

**A row closes on an ANSWER, or states what keeps it open.** An answer closes it once read (`answered gate N — <the choice> — <record path>`). A row still open records why: `open — to <seat> since gate N`, `open — passed up to <seat>`, `declined — <reason>`, `open — decided in chat at gate N, not yet recorded` (`engine ask acted … --ruled-in-chat` closes that one honestly). A bare `open` is an unworked row, and `decisionPasses` does not clear while one stands. **The ask file is the fork's state of record**; the row is the loom's pointer to it.

**Work the `🔓 Open claims` rows before mining fresh forks (`¶INV_LOOM_A_FORK_ARRIVES_DECIDABLE`).** The block is live in the log, sibling to the thread ledger, and it is the loom's answer to a lane sitting on an unanswered question. At each gate, per open row: **re-put it** if the thread still waits on it, carrying its `prepared context` (as a marked /ask when the seat has a parent — § The manager chain) so whoever answers reads a `§FMT_DECISION_CARD` rather than a re-asked question; **close it** against the record path; or **state what leaves it open**. What binds the rows:
> - **A row carries a POINTER to its card, never a copy of the card's fields.** `/decide` §6 already writes the fork, the options as framed, the lean with its trade-off, the falsifier and — per `¶INV_REJECTED_OPTIONS_ARE_RECORDED` — what was decided against, to `builds/<slug>_DECIDE.md`. Point at it. Inlining those fields into a row would both drift from `§FMT_DECISION_CARD` and break `§INV_LISTS_INSTEAD_OF_TABLES`, and the card is not what was missing — **a path to it from the loom's state was.** A fork's ask is rowed in `🗳️ Asks`, and its open-claims row points at it by `<seat>/<id>`.
> - **Every row names what the thread does MEANWHILE**, and a thread does not idle on an unanswered fork by default. `/decide` §5's vocabulary is the shape of that answer — proceed provisionally with the falsifier, hand it to the lane inside a stated bound, defer with a trigger — asked when the fork is **raised** rather than when it is answered. `idle` is legitimate and is the only value that spends the operator's attention now, so it carries why idling was the right call.
> - **A row may not close as a bare `answered`.** It closes as `answered gate N — <the choice> — <record path>`, or it states what leaves it open (`open — decided in chat at gate N, not yet recorded`). An answer with no artifact is what leaves a successor holding a decided row with no record of what decided it, so the honest open beats the false close — the same shape as a bare `open` on an ask row, and the conductor's call rather than a lane's.

**Record each pass** — a log entry (`## 💡 Decision`) naming the gate it fired at and either the forks it put up with each one's call or **`no forks pending`**, a legitimate outcome: `decisionPasses` gates Loom→Synthesis on the record of the passes, never on a fork count, so an unblocked loom satisfies it with the empty sweep written down rather than a fork found to fill it.

**The gate is a DECLARED POOL surfaced by relevance, never a fixed menu (`¶INV_LOOM_GATE_SURFACES_BY_RELEVANCE`).** `AskUserQuestion` caps what it *displays*, not what a gate may offer: `§CMD_DECISION_TREE` declares N peers, surfaces the most relevant four, and reaches the rest through the built-in Other field — `¶INV_ASK_SURFACE_FOUR` and `¶INV_ASK_SLASH_FOR_MORE` own that mechanism, and this gate uses it rather than restating it. The fixed menu is why every other offer in this file stayed in prose the gate never read, surfaced only when a conductor remembered it.

> "The loom is running. What next?"

**Always surfaced** — the ones that act on the weave itself:
> - **"Add a thread"** — scope + fan out a new thread (the add-a-thread flow above). The session stays open.
> - **"Adjust a thread"** — loop a thread back (council/scrutinize → interrogate or build), or re-triage.

**Surfaced on its condition.** Each names the moment it earns a slot and what it is **instead of**; where its condition does not hold it drops to the pool, reachable via `/`, and the slot goes to the next one whose does (`§INV_OFFER_DONT_FORCE_SKILLS` — an offer that would add nothing is skipped silently, not displayed and declined):
> - **"Read the open asks"** — the asks read left a `🗳️ Asks` row open: an answer not yet read, or an ask still unanswered. The offer carries each `<seat>/<id>`, who holds it and since which gate. **It takes the first slot while it stands.** **Instead of** re-asking the same forks in chat.
> - **"Keep weaving"** — a lane is live. Nothing to add; let running threads continue, re-present when the next lands.
> - **"Pull more work"** — a thread just landed and the loom has capacity. Routes to the find-the-next-thread offer in Conducting above — `/inbox-next` for a curated project, `/groom` for an ungrouped pile, `/ticket-search` by keyword — and a chosen result enters the add-a-thread flow. **Instead of** the loom going quiet until the operator notices. The offer was already written; what was missing was a gate that reads it.
> - **"Publish a shareable status"** — the weave's state has to reach somebody who was not watching it. The clause below rules what this is and is not. **Instead of** pasting the ledger into a message.
> - **"Wrap up"** — proceed to Synthesis. **Only** when you explicitly choose it. It surfaces on a signalled closing intent; otherwise it sits in the pool (a high context reading brings a dehydration under `¶INV_LOOM_DEHYDRATES_AT_SEVENTY`, never this card), because a close option displayed at every gate *is* the gate asking "shall we close?", which is the one thing that invariant forbids. Demoting it loses nothing — an explicit "done" already skips the menu entirely (below).

**THE DECLARED TRIGGER LIST — this is the whole of it, and a conductor reads it rather than remembering it (`§INV_LOOM_TRIGGERS_ARE_DECLARED`).** An offer that fires on a **condition** takes no slot and competes with nothing; the gate evaluates every trigger below each time it composes a card. **Each entry states four things, and the fourth is the rule that keeps the list honest: a cadence may RUN unconfirmed and may never PUBLISH unconfirmed.** A round in the *Rounds* disposition fires here too, and under *Meaningful suggestions* it fires only when it would establish something. **A round or cadence not on this list is not one the conductor invents**, and adding one is an edit here rather than a habit.

*   **Stall sweep**
  *   **Fires when**: the gate is composing a card, and again before the conductor settles in to wait on live lanes
  *   **Runs**: `engine lane-stall "<sessionDir>"` — Conducting above rules the readings and what each means
  *   **Instead of**: an operator having to ask whether a lane died
  *   **Publishes**: no — read-only, no confirm. Every `STALE` row advances to a `🅿️ Parked` row with its next move or is resumed from its LOG PATH; **a `0 lanes seen` reading is reconciled against the ledger and never reported as clean**

*   **Dehydration check** (`¶INV_LOOM_DEHYDRATES_AT_SEVENTY`)
  *   **Fires when**: the status-line figure reads about 70% or above (`contextUsage / OVERFLOW_THRESHOLD >= 0.70` with auto-compact on, the default; raw `contextUsage >= 0.70` with `DISABLE_AUTO_COMPACT=1`; § Dehydration and rehydration rules both) and the conductor is between moves, the gate composing a card or the conductor settling in to wait on lanes among them. Running lanes do not stop it. It holds off only while something very meaningful is live, as that section narrows it, and never fires mid-push or while the conductor or any lane holds the landing lease (`engine lease show`)
  *   **Runs**: `Skill(dehydrate, …)`, after any landing lease the conductor holds is released
  *   **Instead of**: a conductor idling at a full context, or riding into an overflow dehydration with its registers unwritten
  *   **Publishes**: no — it writes the hand-over and `LOOM_INHERITANCE.md` and restarts the same session, which stays open (`¶INV_LOOM_NO_RUSH_TO_CLOSE`). Anything its pre-work would publish keeps that skill's own confirm

*   **🔍 Scrutiny sweep** (`¶INV_LOOM_SCRUTINY_IS_DECLARED_AND_ROWED`)
  *   **Fires when**: a `🧵 Ledger` row whose build has handed back carries an **empty or `not scrutinized`** `scrutiny` cell, and the gate is composing a card — and again, unconditionally, before the conductor offers `/pr` on any lane
  *   **Runs**: the scrutinize agent for that lane in the shape the **Scrutinize** disposition names, or the cell written with which position left it unread. Where the lane is cold, it is resumed by name rather than re-dispatched, on `¶INV_LOOM_EVERY_THREAD_PROVES`'s resume-rather-than-redispatch argument
  *   **Instead of**: a lane's own report standing as its review, which is the author grading their own paper — **luck is not a review**
  *   **Publishes**: no — a critique is read-only, and its MUST-FIX is already on the hard escalation floor. ⛔ **But it takes the first slot while it stands on a lane the conductor is about to propose**, alongside the open-ask row, because `/pr` puts the change in front of other people and this is the last moment before it does. **A `0 lanes unscrutinized` reading is reconciled against the ledger's live rows and never reported as clean** — an empty cell is not a pass, it is the absence of a reading, the same error `0 lanes seen` is on the stall sweep

*   **Register sweep**
  *   **Fires when**: the gate is composing a card
  *   **Runs**: `engine sweep-check "<sessionDir>/LOOM_LOG.md"`, read by its exit status and **never through a pipeline**
  *   **Instead of**: an operator having to ask whether a logged decision was ever rowed
  *   **Publishes**: no. ⚠️ **Its claim is temporal and narrow.** Exit 3 lists each `UNROWED` decision — logged after the latest write of every register block it reads, so it cannot have been rowed. Exit 0 means only that *no decision is certainly unrowed*: a `FOLLOWED` decision is **not** shown to be rowed, because the later write may not mention it, and rewriting a register block clears the check without anyone rowing anything. It compares no content. **A conductor appending a short Ledger update rather than a full rewrite hides every earlier decision from it.** And it reads **five of the eight registers — `🌊 Wave`, `⚖️ Rules owed` and `📨 Seat handovers` are not among them**, its list being hardcoded in `scripts/sweep-check.sh`, so a register declared in the template does not reach it by being declared. Those three are read from the log itself; a clean exit here says nothing about them. `/sweep` is the judgement half and fires before a hand-over, never here

*   **Asks read**
  *   **Fires when**: a `🗳️ Asks` row is open and the gate is composing a card
  *   **Runs**: `engine ask list --seat <your seat>`, then `engine ask read <seat>/<id>` on each settled ask, **in that order, and before the gate reports anything about that ask**; at a gate the conductor is already awake for, never on a watcher or a poll loop (`¶INV_LOOM_WAKES_ARE_THE_BILL`)
  *   **Instead of**: an answer sitting in a file nobody read
  *   **Publishes**: no — but the row it closes is what `decisionPasses` gates on, so an unread answer or an unanswered ask takes the first slot while it stands. A `delivery: delivered` is a queued push, never a read (`/ask`, on how an answer comes back)

*   **Decide pass**
  *   **Fires when**: `/decide`'s own §1E cadence says so
  *   **Runs**: `/decide` §1–§3 (mining, the fork test, framing a card) and §6 (the record), followed as the loom's own procedure rather than by invoking the skill, then `engine ask new` for the forks it mined, leading the gate with them
  *   **Instead of**: the operator having to ask *what do you need from me*
  *   **Publishes**: no — the forks are asked in an ask file (`¶INV_LOOM_ASKS_AT_A_BOUNDARY`); a board publishes only when the operator asks for one, under its own confirm

*   **Vision reconcile** *(a doc round)*
  *   **Fires when**: an open `📚 Docs owed` row names `/direct` as its destination
  *   **Runs**: `Skill(direct, "reconcile <vision path> — <what moved>")`, which **rides this session** (`§INV_RIDE_NEVER_ACTIVATES`)
  *   **Instead of**: the deviation sitting in the register until a reader discovers the document is wrong
  *   **Publishes**: no — it records what already happened, and gating a record of what happened is how the record goes unwritten. ⚠️ A **revision** — the operator wanting the direction itself different — is not this trigger and never fires on a condition

*   **Claim repair** *(a doc round)*
  *   **Fires when**: a landed thread falsified a located sentence and its `📚 Docs owed` row names `/revise`
  *   **Runs**: `Skill(revise, "<the landed change>")` through the standing doc lane, batched on the landing (`¶INV_LOOM_DOC_LANE_IS_STANDING_AND_BATCHED`)
  *   **Instead of**: a false sentence outliving the change that falsified it
  *   **Publishes**: no

*   **Research round**
  *   **Fires when**: an interrogation or a scrutinize finding leaves an **open question of fact** that no lane owns and no probe answered
  *   **Runs**: `Skill(probe, "<the question>")` for something the tree can answer, `Skill(research, …)` where the answer is outside it
  *   **Instead of**: a thread proceeding on an assumption nobody measured
  *   **Publishes**: no — both write their answer to a named path (`§INV_A_PROBE_WRITES_ITS_ANSWER_DOWN`)

*   **Integrate round**
  *   **Fires when**: every thread in the current `## 🌊 Wave` block's fanned-out set reads `done` or `parked` and **none reads `running`**
  *   **Runs**: the wave boundary, in the shape the **Merge strategy** disposition names
  *   **Instead of**: per-lane integration wearing the boundary's name
  *   **Publishes**: ⛔ **YES — the merge is a write and takes the operator's confirm.** Detecting the boundary is a read and takes none. That split is the whole of this entry

*   **Harvest round**
  *   **Fires when**: a thread finishes its chain
  *   **Runs**: `Skill(inbox-post, …)` for a notable finding, or `Skill(groom, …)` first where there are several
  *   **Instead of**: a thread's leftovers dying with its context
  *   **Publishes**: ⛔ **YES — filing asks a question about scope, so `/ticket` and `/inbox-post` keep their own confirms** under every position of *Interruption*

*   **Routed item**
  *   **Fires when**: a `/decide` pass routes an item whose answer is a fact somebody must supply
  *   **Runs**: `Skill(interrogate, "<the routed subject>")`, or the item is carried into the thread's own interrogation
  *   **Instead of**: a fork re-mined every pass with nobody ever acting on it
  *   **Publishes**: no

*   **Status render**
  *   **Fires when**: a reader needs the weave's present state — **never per gate**
  *   **Runs**: `engine loom-page "<sessionDir>/LOOM_LOG.md"` (**the LOG FILE, not the session directory** — handed a directory it exits 2)
  *   **Instead of**: pasting the ledger into a message
  *   **Publishes**: no. A **shareable** page is `/prove-explore`'s and on demand, per the clause below

**The status page is `/prove-explore`'s, it is ON DEMAND, and it does not replace the ledger.** `Skill(prove-explore, "weave status — <what the reader must be able to understand>")` over the ledger: its own §1 advertises a state-of-a-body-of-work question, so this needs no new artifact. **Its trigger is a reader, never a gate** — the operator handing the state to somebody who was not watching, or a wrap-up whose debrief is written for us rather than for them. ⚠️ **Per gate is refused**: a run dispatches an assembling subagent, composes a page, walks a per-section honesty gate and publishes, and the loop gate fires after every unit of progress — making it the most expensive recurring event in the session, against `¶INV_LOOM_WAKES_ARE_THE_BILL`. **And the ledger keeps its job**: for the conductor's own bearings and for a successor's, the live ledger and `LOOM_INHERITANCE.md` are cheaper and authoritative (`¶INV_LOOM_PASS_ON_NEVER_DISCARD` makes the row authoritative, not a page about it). The only thing the ledger is not is **shareable**, and that single gap is all this offer fills. The page IS a proof page, so a conductor publishing one has already satisfied `¶INV_LOOM_EVERY_THREAD_PROVES` for that pass and owes no second one.

**🔍 A WRAP-UP REFUSES TO CLOSE until the weave has counted its unscrutinized lanes, and this is the one arm in this change that can actually go red (`¶INV_LOOM_SCRUTINY_IS_DECLARED_AND_ROWED`).** Phase 1 declares **`lanesUnscrutinized`** in its `proof[]`, so the Loom→Synthesis transition carries a count: the weave's build lanes against the independent critiques it ran, and for each shortfall which position of the **Scrutinize** disposition left it so. *Measured 2026-10-28, with a firing control*: `engine session phase` validates a leaving phase's declared proof fields (`scripts/session.sh`, the FROM-validation block) — on a Phase 1 declaring this field, **no proof on stdin exits 1** (*Proof required to leave phase '1: Loom'*), **the field omitted while others are supplied exits 1** (*Missing proof … lanesUnscrutinized*), **the field left as the `________` blank exits 1**, and both fields filled transitions at exit 0. The control passing is what makes the three refusals readings rather than a broken harness. ⚠️ **Scope the claim honestly: the value is a free string, so the arm catches an OMISSION and not a falsehood.** That is the right target — nobody decided to skip, four seats all *forgot*, and this is the only thing in the tree that makes forgetting impossible. `0 unscrutinized` is the cheapest honest answer and `28 build lanes, 1 critique` is a legitimate one; what is unavailable is reaching Synthesis without saying which. ⚠️ **A loom already running does not acquire the arm mid-session**: the phases are copied into `.state.json` at activation and the validator reads them from there, so a weave activated before this field existed closes without it. That is the in-flight disclosure rule applied to this mechanism itself — such a weave states its count in the debrief anyway, as the thing it would have been refused for.

If the user explicitly says "done"/"close", skip the gate and proceed to Synthesis — **after working every open `🗳️ Asks`, `📚 Docs owed` and `🔓 Open claims` row**: read the ask, close the doc row against its Revise Report, close the open claim against its record path, or record the finding that leaves any of them open. The menu is what an explicit close skips; the rows are not part of the menu, and this is the gate a closing loom most needs to pass, since nothing later will ask.

**A handing-over close may carry an open row; a close that would DISCARD one may not (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`).** A row that cannot be closed here — an ask whose answer has not arrived, a doc claim with no home, an operator fork still unanswered — is **inherited**: written to the sessions root's `LOOM_INHERITANCE.md` with what closes it, and read by the next startup pass (Phase 0's inheritance intake). The gate's intent is unchanged, because it exists to stop answers being thrown away rather than to stop a session ending: pass-on is allowed, discard is still refused. Without this provision a session that intends to hand over cannot satisfy the gate at all — it has no next gate to fold at — so the gate would make the hand-over impossible rather than careful.

## Constraints

*   **`¶INV_LOOM_COMPOSED_WRITES`**: `/loom` never writes code, Linear, or git directly. Every mutation goes through a composed skill (`/build`, `/snapshot`, `/pr`) under that skill's own confirm. **One carve-out, named rather than described**: the wave boundary's merge of a lane's branch into the session branch, because no composed skill performs an assembly and a step with no owner runs nowhere (`§INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY`). Add-a-thread and adjust-a-thread always surface; every other offer names **the condition that earns it a slot** and **what it is instead of**, and is skipped silently where it would add nothing (`§INV_OFFER_DONT_FORCE_SKILLS`). Wrap-up is **conditioned, not standing** — a close option displayed at every gate is the gate asking *"shall we close?"*, which `¶INV_LOOM_NO_RUSH_TO_CLOSE` forbids, and an explicit "done" reaches Synthesis without the menu regardless. **An offer that fires on a condition takes no slot** — the `/decide` pass, the asks read, the thread-end harvest and the deadlock drawing are cadences, and a cadence competing for a slot is a design error. **Three things are ruled OUT of the pool, so they are not re-imported**: `/summarize`, because a loom's narrative of its own work is the Synthesis debrief and a second one competes with it; `/report`, because it reconstructs state *blind* from the transcript while a loom's state of record is a deliberately-maintained ledger plus an authoritative inheritance row (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`); and `/design`, because it composes a page directly and `¶INV_LOOM_EVERY_THREAD_PROVES` requires a proof skill's own protocol, *"never a hand-composed page in its shape"* — offering it is a route around that invariant. **A weave status page is `/prove-explore`'s, on demand and never per gate** (`¶INV_LOOM_WAKES_ARE_THE_BILL`); it fills the ledger's shareability gap and replaces neither the ledger nor the inheritance file.
*   **`¶INV_LOOM_SURFACES_FORKS_UNASKED`**: a conductor surfaces the forks holding threads up rather than waiting to be asked — the loop gate runs a `/decide` pass on that skill's §1E cadence and leads with the mined forks above its offer pool, because the operator asking *"what do you need from me"* means a pass was already overdue. `/decide` owns the fork test, the cadence and the card discipline (`§INV_DECIDE_FIRES_PREEMPTIVELY`, declared there); it feeds this gate and never replaces it, and it stands in for the ad-hoc mid-thread question round, never for a mandatory step (`¶INV_LOOM_MANDATORY_STEPS`). The `decisionPasses` proof gates Loom→Synthesis on the record of those passes — each one's gate and its outcome, `no forks pending` included — never on a fork count, so a loom nothing blocked clears it by recording the empty sweep. A pass that writes an ask rows it in the log's `## 🗳️ Asks` block, and the next gate reads that row before mining (`engine ask list --seat`, then `engine ask read`); the file is how answers come back, so no watcher and no poll loop (`¶INV_LOOM_WAKES_ARE_THE_BILL`). **`decisionPasses` gates on every open ask too** — each row reads `answered` with its record path or states what keeps it open, and an ask still unanswered at a close is carried in `LOOM_INHERITANCE.md` rather than dropped.
*   **`¶INV_LOOM_NO_RUSH_TO_CLOSE`**: the loop gate defaults to keep-going. The session closes only on the user's explicit choice. A spent context budget is never a close the conductor takes for itself: it **dehydrates** instead (`¶INV_LOOM_DEHYDRATES_AT_SEVENTY`), which restarts the same open session and is a hand-over, not a close.
*   **`¶INV_LOOM_DEHYDRATES_AT_SEVENTY`**: at about 70% on the status line, a conductor between moves runs `/dehydrate`; running lanes never block it, and it never dehydrates mid-push or holding the landing lease. § Dehydration and rehydration states the rule, its one exception and which field it reads; the gate's **Dehydration check** fires it.
*   **`¶INV_LOOM_DOC_LANE_IS_STANDING_AND_BATCHED`**: documentation rides ONE standing lane the conductor feeds, fed **batched on a landed thread** and never per change-event, because a wake is the bill and a loom landing threads every few minutes would otherwise wake it constantly. **The conductor owns the register, the lane does not**: the `📚 Docs owed` rows live in the log (and in the inheritance at a hand-over), so what is owed survives a context clear while a lane's memory does not. The lane runs `/revise`, which is **claim-scoped** — a located sentence a landed change falsified, repaired against the code — and is **forbidden** the tree's index, pages the change does not reach, tree-wide count or link audits, and inventing a home for an undocumented change; those are `/document`'s, because no single diff can scope them and a per-thread lane asked to do them either skips them or never finishes. It rows them back instead, and the conductor routes the row. A row closes as `revised — <report path>` or states what the lane found that leaves it open; a bare `open` is an unworked row, and `docRegister` gates Loom→Synthesis on the rows rather than on a doc count, so a loom that falsified no claim clears it with the empty register written down.
*   **`¶INV_LOOM_HANDS_OVER_A_PATH_NOT_AN_ID`**: a hand-over written for a restart names a lane's **LOG PATH**, never an agent id — a context clear ends every in-process subagent, so an id is executable only while the parent context lives and `SendMessage` to it answers *no transcript found* on arrival. The successor dispatches a fresh lane with that log in its context pack. The same brief states every reading's timestamp and marks it re-measure, scopes a claim to the tool class it was measured on, names the field that actually discriminates rather than one both states share, re-reads an artifact before briefing its state (a lane's log is not a record of what it did after it stopped logging, and an untracked path's `git status` is silent at exit 0), names each standing arrangement with what blocks on its absence and how to re-arm it, and writes every command with an absolute path. `§CMD_DEHYDRATE` and `§CMD_RESUME_SESSION` own the payload and the resume; this invariant owns only what a conductor adds to them. **Not every log path is the same handle, and the hand-over says which kind it is.** A lane's own `builds/<slug>_BUILD_LOG.md` briefs a successor on that lane alone; the shared session log briefs it on the whole weave, and `logpath=none` briefs it on nothing. *Measured on one session, 2026-10-23*: `engine lane-stall --all` reported 112 lanes, of which **46 read `logpath=none`** and a further set pointed at the shared `LOOM_LOG.md` — so for those rows "resume it from its log path" lands a successor in an eight-thousand-line shared log, or nowhere, which is a materially weaker handle than this rule reads as promising. A hand-over therefore **names the kind**: `own log` · `shared log only` · `no log`. For the last two the conductor adds what the lane's own log would have carried — the files it touched, what it established, where it stopped — or says that is unrecoverable, because a successor briefed with a path that cannot brief it is worse off than one told the record is missing.
*   **`¶INV_SUITE_ONCE_PER_WAVE`**: a lane runs the tests its own change touches; the **full suite runs once per wave, at the gate, against the assembled tree** — never once per thread and never at each of a lane's steps. *Measured 2026-10-20 over 105 interleaved order-rotated runs*: the same command spread 10.7s–102.0s (p50 21.5s, p90 58.1s), making a per-step full suite the dominant cost of a parallel run. **Three remedies are falsified rather than untried and may not be re-attempted as fixes for it**: reducing concurrency (every reduction measured worse — disabling file parallelism came in at 311.1s against a 40.4s baseline, nearly 8×), trusting an advertised speed-up (a cache advertised at removing 57% of tracked time measured inside the noise band), and judging the change from any single timing (on that spread, one run is near meaningless — a judgement needs an interleaved, order-rotated distribution). Making the suite faster is **out of scope**: this routes around the cost rather than reducing it. The known cost of the rule is accepted deliberately — a cross-cutting break reaches the wave gate, where attributing it is more expensive — and briefing lanes to run the whole suite is not a permitted way to buy that back.
*   **`¶INV_SLOT_CAP_IS_GLOBAL`**: the live-lane cap is enforced **across concurrent looms**, not within one, because two looms that cannot see each other will together exceed any number each keeps privately and will contend over one test queue and one machine. The count lives in `~/.claude/engine/.loom-slots/`, one file per loom; **each loom writes only its own file and reads every file**, which makes the read race-free without a lock. A row whose heartbeat has aged past the staleness window is **reported as stale and not counted** — a conductor ended by a context clear cannot delete its own row, so stale rows are expected, and naming them in the reading is what separates a count that discarded rows from one that found none. A loom that cannot read the directory dispatches one lane at a time and says so, rather than assuming it is alone. The file also carries the loom's **work claims**, which are not liveness and never age out: a stale row with no lanes still reports them, and only landing or an explicit release removes one. Every write goes through `engine loom-slots`, which keeps the fields it was not asked to change. **Deriving the count instead of storing it is falsified here** (*measured 2026-10-23*): `engine find-sessions.sh active` returned one session and omitted the live session it ran from, because discovery is scoped to a single session root — and `engine lane-stall` answers a lane's state, never its reachability, reporting lanes as `running` whose transcripts were 6,369 minutes old. The mechanism adds no service and nothing outside the engine's own tree.
*   **`¶INV_LOOM_WORKTREE_DEFAULT_IS_MEASURED`**: worktree-per-lane is the default **on the strength of a measurement of the machine it runs on**, never on figures carried from another repository — disk headroom and workspace-link structure are properties of a checkout, so an imported number cannot establish them. The measurement that justifies it is **a marker planted in a package directory and read back through the workspace link**, with a control in the same invocation that fires: a `readlink` saying `../../` and a grep finding no absolute path are both satisfied by a mistyped path, while a marker that appears through one tree's link and is absent through a copied tree's link is the property itself. *Measured here 2026-10-23*: 100 of 100 links relative in the primary monorepo, the planted marker absent through a real worktree's link with the positive control firing through the main checkout's, 299GiB free and a real worktree at 524MiB. **Where that measurement does not hold the default flips to opt-in** — the operator picks *one shared tree* and the ledger records why — and the reading is not inherited: it is re-taken on a checkout nobody has measured.
*   **`¶INV_LOOM_PASS_ON_NEVER_DISCARD`**: an open row — an ask still unanswered, a doc claim, an unanswered operator fork — may be **inherited** by a handing-over close and may never be **dropped** by one. It is written to the sessions root's `LOOM_INHERITANCE.md` — at an address **computed** from the active session directory rather than typed, per the template's *Where it lives* section — and read by the next startup pass. The rows are the state and the session log is the narrative; the inheritance file is authoritative for a row from the moment it is written, so no row has two owners. A field the writer could not fill reads `UNKNOWN — <why>` rather than blank, and a successor finding `UNKNOWN` in a field it needs **stops and reports that row** instead of acting on the rest of it — a partial row acted on silently rebuilds the original loss with no gap left where it used to be.
*   **`¶INV_HANDOVER_IS_A_ROW`**: a topic handed to another seat is a **row**, not only a message. A handover that exists only in a peer `SendMessage` and the sender's narrative log is forbidden, because **a topic its seat never picked up then looks exactly like one it took**, and the only way to tell is to read the sender's story. The row is opened **before** the send — the send is the moment a context most often ends, and a row written afterwards is the one the failure mode deletes — and it carries the seat's from-name **with its pane id**, the topic, its **member links**, and the delivery reading rather than a boolean, because a queued send is not a read and silence is not an ack. Measured twice eleven days apart in one weave: five seats handed topics, then seven, five acks returned as peer messages each time, and **not one became a row** on either occasion. The register is `## 📨 Seat handovers`, live in the log and copied to the inheritance, and `seatHandovers` gates Loom→Synthesis on its rows, clearing on an empty result written down like `docRegister`. **It is a different register from `## 🤝 Hand-over written`** — that one is a conductor handing its own state to its own successor, this one is a peer taking a topic or declining it. ⚠️ **`→` may not be spent on it**: `§INV_GROOM_MARKS_WHAT_IT_WRITES` already uses that marker to stop a drained inbox root being re-offered, and nothing on the receiving side reads it as an assignment.
*   **`¶INV_HANDOVER_CLOSES_ON_ACK`**: a handover row **stays open until the receiving seat acks it**, and the sender may not mark it done on sending — an un-acked handover is precisely the case the row exists to show, so a sender closing its own row has written the bug down instead of the handover. The row closes on the receiving seat's **own words**, and a **decline closes it as surely as a take**: `taken`, `declined — <why>` and `already done — <the evidence the seat gave>` all close it, on the `§INV_A_RULE_OWED_HAS_AN_OWNER` argument that a topic refused on purpose and a topic dropped on the floor read identically once the session ends. A bare `acked` is an unworked row and blocks Synthesis, like a bare `open` on an ask row. **An ack that reached only the sender's chat is not an ack** — the reply is transcribed onto the row, because an ack that is only a peer message is the original defect restated one step later. An open row therefore **travels to the inheritance** (`¶INV_LOOM_PASS_ON_NEVER_DISCARD`) and is the kind most exposed at a hand-over, since the party who owes the ack is not the party handing over; a successor **re-measures the pane before acting on one**, because a seat renamed or a name since taken by another session makes a handover sent nowhere read exactly like one sent.
*   **`¶INV_LOOM_WAITING_IS_ROWED`**: a lane's wait is written down, never only remembered. Every block a lane reports opens a `## 📡 Relay / Conflict` entry carrying `Waiting on` in the lane's own grammar (`assets/LOOM_AGENT_DIRECTIONS.md` § Progress reporting), `Since`, and its resolution, and the waiting thread's `🧵 Ledger` `status` cell carries the glance — a **closed grammar** naming what it waits on, how long, and what it does meanwhile, because `in flight` on a thread that has stopped is not a reading but the absence of one. The *waiting-on graph* is therefore the rows rather than the conductor's context: a graph a context clear deletes is a cycle rediscovered from nothing, and before this nothing durable said **why** a lane was waiting until a hand-over, which is the moment it is hardest to reconstruct. **No fourth register was added for this** — `📡 Relay / Conflict` and `🅿️ Parked` were extended and the `🧵 Ledger` `status` cell was closed. `ledgerMaintained` gates on the rows.
*   **`¶INV_LOOM_STALL_IS_SWEPT_NOT_SENSED`**: the *silence past a timeout* poll runs `engine lane-stall "<sessionDir>" [--minutes N]` and **no second detector is written**. It lists each not-done lane whose freshest signal is older than the threshold with minutes-since-transcript, minutes-since-its-last-`[TAG]`-log-heading and a state — `done` · `parked` · `running` — exits **3** when any lane is stale, and is read-only. It runs **at each loop gate as a cadence taking no slot**, and **before the conductor settles in to wait**, because the gate fires on a unit of progress and a weave where nothing lands never reaches one — a gate-only sweep is absent in the case it exists for. It is an **external** reading, which is the point: every other progress signal here is self-reported by the lane, and a hung lane emits none of them while an absence is indistinguishable from quiet work. **`parked` is the operator's symptom** and rows under `🅿️ Parked` as `stopped without handing back`, kept distinct from a thread the conductor parked for a reason, with the lane's LOG PATH and its next move. Two readings are forbidden: it answers **state, never reachability** (a dead lane's transcript persists, so `parked` is not `gone`; only a `SendMessage` attempt settles addressability), and **`0 lanes seen` is never reported as a clean weave** — it is reconciled against the ledger's live rows, since a sweep blind to this weave's lanes reports no stale lanes, which reads as reassurance. The sweep identifies a lane by a bracketed tag at the **start of the dispatch prompt**, which is why `¶INV_LOOM_AGENTS_NAMED_BY_THREAD` binds the prefix to the prompt as well as the `description`.
*   **`¶INV_LOOM_ASKS_AT_A_BOUNDARY`**: the `/decide` **pass** runs on the gate cadence, and **a pass that mined a fork writes its ask at that gate** (`engine ask new`, routed per § The manager chain), never a board unless the operator asks for one (IDE-255; operator ruling 2026-10-29 00:51). The pass keeps `/decide`'s disciplines: it mines preemptively, names what each fork unblocks, and records what was decided against, carried in the ask's header and body and in the `/decide` record its `context` names. `/decide` is not retired; it stays the skill for an explicitly requested shareable board. The ask is a write to the asks store, not a page, so the pass publishes nothing; re-pinging is manual and no timer is added (IDE-182). With no parent, the branch is the seat: a seated conductor with no parent writes the ask `--to operator` and does not repeat it in chat, and a loom with no seat (outside the fleet, where `engine ask new` has no asking seat to name) puts the forks in chat as `§FMT_DECISION_CARD`s while the operator is at this terminal and rows each in `🔓 Open claims` with its `/decide` record path, the one case where chat is the asking surface. **Forbidden**: publishing a board for a mined fork the operator did not ask for, and asking a fork in chat beside its ask.
*   **`¶INV_LOOM_A_FORK_ARRIVES_DECIDABLE`**: a question that reaches your manager (the operator if you have none — § The manager chain) carries what it takes to answer it, and keeps the record of what answered it. The live `🔓 Open claims` block holds one row per unanswered fork — **promoted from the inheritance template, where it was the only copy**, which made an unanswered fork durable only at a hand-over: the one moment a lane sits waiting was the one moment nothing was written. Each row carries a **pointer** to its prepared `§FMT_DECISION_CARD` — `/decide` §6's record, which holds the options as framed and, per `¶INV_REJECTED_OPTIONS_ARE_RECORDED`, what was decided against — and **never a copy of the card's fields**, which would drift from the format and break `§INV_LISTS_INSTEAD_OF_TABLES`. The card was never what was missing; **a path to it from the loom's state was**, since a fork decided in chat had no row anywhere; a fork the loom asked is rowed in `🗳️ Asks`. Each row also names what the thread does **meanwhile** — `/decide` §5's vocabulary, asked when the fork is raised rather than when it is answered — because a thread idling on an unanswered question by default is the stall, and `idle` is legitimate only carrying why. **A row may not close as a bare `answered`**: it closes with the record path, or states what leaves it open (`open — decided in chat at gate N, not yet recorded`), because an answer with no artifact leaves a successor holding a decided row with no record of what decided it. The rows are worked at every gate before fresh forks are mined, carried to the inheritance **transcribed rather than re-mined**, and ride `decisionPasses` rather than a second proof, since a fork exists only where a pass ran.
*   **`¶INV_TICKETS_PRESENTED_BEFORE_ASKED`**: before any question to the operator that mentions a tracker ticket — an `AskUserQuestion`, an interrogation round, a decision card, a `/next` proposal, a loop gate — the agent first prints in chat a list with one entry per ticket the question mentions, in the shape `[KEY](url) — Title [Status since HH:MM D Mon] — two-line summary`. **When the carrier is an /ask** (§ The manager chain), the list goes at the top of the ask body instead, because chat is not where its answerer reads. **A thread or topic whose slug is a ticket key counts as a mention**, so a gate that names threads lists their tickets. The key is linked per `§FMT_TICKET_LINK`; the status and the time it began come from the tracker (`get_issue`: its status, with *since* taken from the state-history entry for the current status, else `startedAt` — never `updatedAt`, which moves on any comment or label), shown in the operator's local time; the summary is two plain lines on what the ticket is and where it stands. **Why**: a ticket key inside a question asks the operator to recall what that ticket is, and the list puts it in front of them before they choose. This list is the one chat block `§CMD_ASK_QUESTION_WITH_COMPLETE_CONTEXT` allows ahead of a question, and it holds the entries and nothing else — no recommendation, no options, no recap; the question body still carries its own complete context. **If the tracker cannot be read**, print the entry with the key and `status unread` rather than skip it — a missing entry hides the ticket the question still names.
*   **`¶INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY`**: a wave's lanes are brought back together by the **conductor**, at the **boundary** — every thread in the `🌊 Wave` block's fanned-out set landed or parked with none reading `running` — and **not** at the loop gate, which fires on one thread landing and would merge a lane at a time, which is the per-lane integration this step exists instead of. **The one exception is a chain the conductor dispatched** (`§INV_LOOM_STACK_ONLY_ON_A_DISPATCHED_CHAIN`): its lanes do not join the wave merge and reach the base as a stack. The base is the **session branch, captured at Setup as a name and a sha** because it is not reconstructable later; a loom with no recorded base reports that and does not integrate. The order is **landing order, first-landed first** — already written down in each lane's `/snapshot` Outcome, and it makes the loser the **later lander**, so the loom keeps `§INV_LOOM_FIRST_CLAIM_WINS`'s single precedence rule rather than acquiring a second. Merging is **`--no-ff`**, which is load-bearing and not cosmetic: the merge commit engages `/pr`'s own refusal to cherry-pick merge commits and so forces the whole-branch path, making the declined per-lane PR structurally unavailable instead of merely remembered. **On a conflict the conductor aborts the merge** — session branch left at its exact pre-merge sha, **never resolved, never `-X`**, the idiom `/pr` binds its cherry-pick to — and **resumes the later lander by name** with its branch, the base sha and the `--diff-filter=U` paths; **that lane merges the session branch INTO its own branch in its own tree**, never the reverse, because shared ground the earlier lanes already landed on is not a resolution surface. A second conflict on one lane is a hard-floor escalation rather than a loop. **This step and the file partition are two answers to one question and a loom runs exactly one**: the partition is *prevention* and a merge is *detection* — the better instrument, since it finds the collisions that happened in the text rather than the ones predicted at allocation — so under worktree-per-lane the conductor computes **no** partition and brokers **no** claims, and under one shared tree there is nothing to merge and the row reads `nothing to merge — shared tree`. The `wavesIntegrated` proof gates Loom→Synthesis on the `🌊 Wave` rows and **clears on an empty result written down**, like `docRegister`. **Where a conflicting lane cannot be resumed the step STOPS and escalates** (the decision reaches your manager (the operator if you have none — § The manager chain), and other waves' work continues) — `engine lane-stall` cannot settle it, since it answers state and never reachability, so only a `SendMessage` answering *no transcript found* does — and the conductor neither resolves the conflict itself, nor hands it to a fresh lane that did not write the code, nor drops the wave: no fallback has been chosen, and `§INV_LOOM_PASS_ON_NEVER_DISCARD` makes passing the decision on the only legitimate close.
*   **`¶INV_LOOM_STACK_ONLY_ON_A_DISPATCHED_CHAIN`**: the loom offers a stacked PR (`/pr --stack`, `/pr` §6) **only over a chain it dispatched itself** — lane B's branch cut from lane A's head at *Adding a thread* step 6 because A's work was B's prerequisite, with `based on <threadId> @ <sha>` rowed on B's ledger row at that moment. **A wave never becomes a stack**: its lanes are cut from the session branch and are parallel by construction, so stacking them in landing order asserts dependencies nobody measured; they leave as the wave's one PR. The record decides whether a chain exists and git checks the record: `/pr` §6's ref check (each upper PR's base ref is the lower PR's head ref) must pass, and on a fail `/pr` stops rather than rebase, retarget or reorder, so neither half manufactures the chain. No record means no stack, whatever git shows. `ancestor=1` with chaining refs means A moved on after B was cut, and it is carried into the stack confirm rather than stopping it. A chain's lanes, its bottom lane included, stay out of the wave merge and reach the base through the stack. The stack POST is a `/pr` confirm (class G, `reserved-for: operator`), so with a parent it travels as § The manager chain says and is held under the `/pr` waiver residual named there. **Why**: a stack holds each lower PR's merge behind the upper PR's reviewer, so a false chain costs merges rather than tidiness; and ancestry alone also holds for a branch cut from another by accident, so git can check a dependency the loom decided but cannot stand in for the decision. Defined in § The wave boundary.
*   **`¶INV_LOOM_GATE_RUNS_ON_THE_INTEGRATED_TREE`**: the once-per-wave suite runs against the **assembled** tree — the conductor's own, on the session branch, after the last merge lands — and the `🌊 Wave` row names the **sha** it ran against. Forbidden: running it in any single lane's tree, and running it on a **partially** integrated wave where one lane merged and another's conflict is still open. That wave records `suite deferred — <threadId> conflict open` and runs nothing, because a green recorded against an assembly nobody will ship is worse than an unrun gate — it is an unrun gate that reads as evidence. The economy that justifies running the suite once per wave rather than once per thread was measured on an assembled tree, so a reading taken anywhere else does not support the default that produced it.
*   **`¶INV_LOOM_HARD_ESCALATION_FLOOR`**: cyclic deadlock · build-fails-after-retries · scrutinize MUST-FIX · thread loopback always reach your manager (the operator if you have none — § The manager chain), marked `reserved-for: operator`, even under Automagic.
*   **`¶INV_LOOM_ESCALATES_UP_THE_CHAIN`**: a conductor whose seat has a parent (live `@pane_parent`, cross-checked against `FLEET_PARENT`) escalates to that parent as an /ask file, and a seat with no parent escalates to the operator. **Forbidden**: a seated conductor putting an escalation straight to the operator past its parent, unless the Escalation route disposition is *straight to the operator* or *both* (§ The manager chain); a blocking `AskUserQuestion` aimed at a parent, or a seat with a parent blocking Setup or the loop gate on one; a manager ruling on an ask marked `reserved-for: operator` (floor items and grant v1's E–H), which it may only forward; and a parentless question dropped or left with nowhere to go. **Why**: every conductor's only route up was the operator, through a call that blocks until answered. In Planner's loom four escalations sat there (IDE-231 premise), while the operator ruled that the manager is the front door (`manager-tier_INTERROGATE.md` § Escalation routing). Defined in § The manager chain.
*   **`¶INV_ESCALATION_DOES_NOT_BLOCK`**: a conductor with an open ask keeps dispatching, gating and landing whatever does not depend on its answer, and re-pings or passes the ask up on its own turns. **Forbidden**: stopping every lane while an ask is open, unless every remaining step depends on that answer and the `🔓 Open claims` row says so; and any timer, watcher or poll that re-pings or passes an ask up on a clock. **Why**: blocking at one rung becomes blocking at every rung above it (IDE-231). The operator ruled at 23:05 that "push is fine; timers aren't" (IDE-135's no-scheduler rule). Defined in § The manager chain.
*   **`§INV_RIDE_NEVER_ACTIVATES`**: a composed protocol-tier skill invoked by the conductor **owns no session** — it never runs `engine session activate` or `engine session phase` and writes nothing to `.state.json`, because there is one `.state.json` per session directory carrying a single `currentPhase` and a composed pass advancing it overwrites the conductor's own position in the only file the host has. `/direct` declares the contract in its own `## Composed entry` section and does not execute its phase orchestrator when composed; `/interrogate` already held it. **A conductor that finds a composed skill transitioning its phase stops and reports** rather than continuing from a phase it did not set.
*   **`§INV_NO_DESTRUCTIVE_GIT`**: parallel builders never run tree/index-destructive git. Committing is `/snapshot`'s job.
*   **`§INV_A_PROBE_WRITES_ITS_ANSWER_DOWN`**: a conductor asks a lot of side questions, and an ad-hoc `Agent` dispatched to answer one writes nothing by default — its result dies with the conductor's context while the ledger shows no gap. Every answer-shaped dispatch names a `builds/<slug>.md` path in its brief. Measured here: 7 of 22 agents in one day were transcript-only, including the sweep of every lane log's *"named, not fixed"* — the loom's own leftover inventory, recoverable afterwards only by mining subagent JSONL.
*   **`§INV_OFFER_DONT_FORCE_SKILLS`**: triangulate, snapshot, pr, council are offered, never forced.
*   **`§INV_LISTS_INSTEAD_OF_TABLES`**: no markdown tables in this file (the ledger's table lives in the emitted `TEMPLATE_LOOM_LOG.md`, where tables are allowed).
