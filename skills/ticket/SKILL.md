Translate a body of in-context work into a well-framed ticket — **one**, or none at all, unless a human asks for a split. A background agent analyzes the scope, drafts PREMISE-FIRST tickets (the problem, the intent, the constraints, the non-goals, the acceptance signals — deliberately NOT a prescribed algorithm or solution), you calibrate each draft via questions, then it posts to the tracker. Sessionless: no session dir, no phases, no debrief — analyze → draft → calibrate → post, then stop. A **building block**: it drafts and files tickets from work; it never writes code, fixes bugs, or commits. When this run follows a `/build` or `/experiment`, it reuses that run's `<slug>` so the tickets cluster beside that work's report, and it feeds `LESSONS.md` so the tickets you file shape the next handoff.

This is distinct from just calling the tracker MCP directly. It front-loads a **prior-work sweep** (`/ticket-search`, dispatched before drafting, so a duplicate surfaces while folding is still the cheap answer) and a **premise-first draft** derived from actual work (so the ticket captures *why* and *what*, not a half-baked solution), runs an interactive **per-ticket calibration gate** (you own title, scope, labels, and placement), and makes the **sub-issue-vs-new** decision from context — inheriting the parent's metadata when it files under an existing ticket.

**Tracker Note (Linear):**
This project files to **Linear**, via the `linear` MCP tools (`list_teams`, `list_issue_labels`, `list_issue_statuses`, `get_issue`, `list_issues`, `save_issue`) — the tracker and its tool set are constant; only the **issue-key prefix** and **team** vary per project and come from CLAUDE.md § Tracker (resolve them in §1, inject into the subagent prompt). Tickets use that prefix — `<PREFIX>-NNNN` (e.g. `ENG`, so keys look like `ENG-3141`). `save_issue` both creates and updates. On create, it takes **human names/identifiers, not UUIDs** — `team`, `parentId` (accepts `"<PREFIX>-NNNN"` directly), `labels` (label NAMES), `assignee` (name/email/`"me"`), `project`, `cycle`, `state`, `priority` (int), `title`, `description` (Markdown). There is no separate ID-resolution step. Load tool schemas on demand (ToolSearch `linear`). If no Linear MCP is connected, degrade gracefully: draft and calibrate as usual, then hand the user the finalized ticket bodies in chat to copy-paste, noting that posting was skipped.

# /ticket Protocol

## Gate route — who answers this run's questions

Every decision this skill takes from a person — the scope pick, the Subject Gate redirect, the Prior-Work Gate, the calibration, the placement and the post confirm — is a **gate question**, and where a gate question goes is settled here, once, before §1 asks anything. A seat whose operator is not at its terminal must never wait on a question nobody is there to answer: when every gate was a terminal prompt, seats sat on one for close to an hour. The approval tiers are the operator's ruling `ruling-ticket-tier` (2026-10-29): a routine ticket is approved by the seat's manager, a scope-level one by the operator, and a new ticket never goes out without one of them.

1. **Resolve the target.** Run `bash ~/.claude/engine/skills/coordinate/scripts/hop.sh target` and read its exit code directly, not through a pipe. Take the target exactly as `§CMD_CONTINUE_ON_STOP` step 4.1 rules it: the **first word** of what it prints, never the whole line, chosen by exit code (0 or 3 → that word; 5 → the seat stderr names as `FLEET_PARENT='<seat>'` when this seat is off the live tree, otherwise `operator`; 2 or 4 → `operator`). On any exit other than 0, the ask's body starts with `broken hop: <hop's stderr>`.
2. **Pick the route.** Read these in order; the first that matches decides.
   - **A loom lane, or any subagent another agent dispatched, stops here.** You are one when another agent started you with its Agent or Task tool inside its own session (a loom lane's brief cites `LOOM_AGENT_DIRECTIONS.md`). A seat whose manager merely sent it work by message or ask is not one: it runs in its own pane and asks from its own seat. A subagent inherits its dispatcher's `FLEET_PANE`, so an ask it wrote would go out under the dispatcher's seat and the answer would be pushed to an agent that never asked. Write no ask and call no `AskUserQuestion`: hand the draft back to the agent that dispatched you, which runs this route from its own seat.
   - **A seat (any first word but `operator`) → the ask route.** Every gate question goes up as one ask, below. This holds even when the answer is the operator's to give, and even when someone is typing in this seat: the ruling makes a routine ticket the manager's to approve, so this route is stricter than `/ask`'s "a person demonstrably at your terminal" exception, on purpose.
   - **`operator`, and nobody is at this terminal, or you cannot tell** (an unattended stretch, a Stop-hook wake, any doubt) → the ask route, addressed `--to operator`.
   - **`operator`, and the operator is demonstrably at this terminal** — an interactive session the operator started and is driving right now → the **terminal route**: each gate question below is an `AskUserQuestion` for the operator, asked where the step stands. This is the only branch in which this skill calls `AskUserQuestion`.
3. **The ask route — ONE ask per run, carrying the full draft.** §1 runs `/ticket-search --report`, which asks nothing and returns the duplicate candidates; §2's drafter asks nothing. Before writing the ask, run §4 step 1 (label reconcile and the backstop dedup) against the proposed placement, so the labels the answerer approves are the ones that would post. Then put the calibration and the post confirm — and every duplicate decision — into **ONE ask**, written per `skills/ask/SKILL.md` § Writing one and its author guide `skills/ask/assets/ASK_AUTHOR_GUIDE.md`:
   - **The id is unique per ask.** `ticket-<slug>-<UTC yyyymmddHHMM>` (append `-2`, `-3` if two asks land in one minute, as a split's drafts do); a re-ask of the same draft is `<that id>-r<N>`. Never the slug alone: a `/build` slug is reused across runs, and `engine ask new` refuses an id that already exists.
   - **The command.** `engine ask new --to <target> --id <id> --topic "<team>: <title>" --tickets "<context ticket, duplicate candidates>" --context "<trailDir>/<slug>_TICKETS.md" --why "<what filing it unblocks>" --importance <level> --stakes "<cost of a wrong filing>"`, plus `--reserved-for operator` only as ruled below, with the body on stdin.
   - **The body opens with the whole draft.** A short card first — title · placement (`sub-issue of <PREFIX>-NNNN "title" · state · team` | `new in <team>, backlog`) · priority · labels after reconcile, with any dropped · assignee and inherited fields · evidence to attach · the `/ticket-search` headline — then the ticket's **"Rendered description (postable)"** block, verbatim, inside a four-backtick markdown fence. The fence keeps the draft's `## Premise`/`## Acceptance` sections as prose; unfenced, a `##` heading in the body is read as a fork. The answerer approves exactly the text that would post, without opening another file.
   - **The forks** (at most five, each named `¶ASK_<NAME>`, each with its own `Stake:`, `Lean:`, `Counter:` and `Confidence:`; codes of four characters or fewer while the operator's app is v1):
     - `¶ASK_DUP` (and `¶ASK_DUP2`) — one per candidate the `--report` sweep or the backstop flagged, options `FOLD` · `SIB` · `UNRL` as the Prior-Work Gate defines them; `SIB` is offered only with the defect the candidate lacks named in its description. Lean `FOLD`. More than two candidates → a second ask linked by the header's `--dependsOn`, never a sixth fork.
     - `¶ASK_PLACE` — the placement, its options as §3 step 4 lists them; a caller-pinned placement is its lean, a low-confidence parent gets no lean.
     - `¶ASK_FILE` — calibration and post confirm in one: `FILE` (post the fenced draft exactly, at the chosen placement) · `EDIT` · `DROP`, with `¶ASK_EDITS` (`Text`, `DependsOn: ASK_FILE=EDIT`) for the change. Name any scope candidate not drafted (§1) and any split the drafter noted in its `Counter:` — a split is still only the human's to make, here by an `EDIT`.
     - **A refused subject is its own ask.** When the §3 Subject Gate refuses the draft, nothing is offered for filing: the ask's only forks are `¶ASK_SUBJ` (`TOOL` when the project has a 🛠️ channel · `REPO` · `INST`, with no override, as step 0 states) and `¶ASK_INST` (`Text`, `DependsOn: ASK_SUBJ=INST`). When `TOOL` is offered, the body also carries the 🛠️ Tooling & Gates template **already filled** from the draft (every field of it: what is wrong, whose tooling, the command and its real output, what it blocks, where the resolution should land), in its own four-backtick fence, so a `TOOL` answer approves the exact drop.
   - **Reserve it for the operator only when the ticket is scope-level.** Pass `--reserved-for operator` when the ticket **opens new scope**, **crosses areas**, **creates or changes a project or initiative**, or **reverses an operator ruling** — and say which in `--why`. **A routine ticket — new work inside the area's existing scope — goes to the parent unreserved**; the manager answers it, and the operator can overrule it from the "ruled below you" view. **An area is what the target project's handbook says it is**: its `## Boundaries` (read in §1 through `§CMD_READ_PROJECT_HANDBOOK`) — the ticket opens new scope when neither a Boundaries entry nor an existing project milestone covers its subject, and crosses areas when a Boundaries entry routes the work to a neighbouring project. When the handbook publishes no Boundaries, those two tests cannot be read, and the case is unclear.
   - **PROVISIONAL (interpretation of `ruling-ticket-tier`, OK'd by manager:director at 02:17 pending the operator, who may rule "reserve" instead): when a scope-level test cannot be settled from what the run holds, send the ask unreserved and name the doubt — which test, and why it could not be read — in `--why`.**
   - **Leave the pointer** where `§CMD_CONTINUE_ON_STOP` step 4.3 says (a seat's `## [TAG] ❓ Ask <id>: …` log heading; a conductor's `🔓 Open claims` row), then keep working on whatever does not depend on the answer. Nothing posts before it.
4. **Resume on the answer.** When the `[ask-answer]` push arrives or `/next` picks it up, read it with `engine ask read <seat>/<id>` — the read stamp is the record that you saw it. Then:
   - **`FOLD`** on any duplicate fork → file nothing; §5 reports what the draft adds to that ticket. It outranks `FILE`.
   - **`FILE` counts only when every visible fork is answered** — every fork not hidden by an unmet `DependsOn:`, so each `¶ASK_DUP` and `¶ASK_PLACE` as well as `¶ASK_FILE`. A `FILE` that left any of them blank is not a confirm: **re-ask**, below, with the same forks.
   - **`FILE`, fully answered → re-check before posting.** Hours may have passed. Re-run §4 step 1's backstop dedup and, for a sub-issue, re-read the parent with `get_issue`: it must still be open and on the same team. **If either check now differs from what the ask showed, post nothing and re-ask** with the new fact in the card. Otherwise run §4 steps 2, 4 and 5 at the answered placement, posting the `description` **lifted from the fence of the ask that was answered** (`engine ask path <seat> <id>`), not from `<slug>_TICKETS.md` — that copy is what the answerer approved. The answer is the §4 step 3 batch confirm; do not ask again.
   - **`EDIT`** → apply the `¶ASK_EDITS` text to the draft, re-render the postable block into `<slug>_TICKETS.md`, then **re-ask**. Never file an edited draft its answerer has not seen.
   - **Re-ask** (after `EDIT`, a partial answer, or a re-check that changed something): close the answered ask with `engine ask acted <seat>/<id> "re-asked as <id>-r<N>: <why>"`, then `engine ask new` with the id `<id>-r<N>` (N = 2, 3, …), the same forks and the current draft, `--related <seat>/<id>`, and the same `--to` and reservation. `engine ask revise` cannot do this: it refuses an ask that is already answered.
   - **`DROP`, or a decline** → file nothing; §5 reports it.
   - **`TOOL`** → write the fenced 🛠️ fields to `<trailDir>/<slug>_TOOLING.md` and run `/inbox-post --channel "<project> :: 🛠️ Tooling & Gates" --fields <trailDir>/<slug>_TOOLING.md`, which posts without asking anything. If it refuses with missing fields, re-ask with a `Text` fork `¶ASK_FLDS` naming each missing field. **`REPO`** → record the resolution at the destination the handbook named. **`INST`** → put the `¶ASK_INST` text into the premise and re-enter the Subject Gate.
   - Close every settled ask with `engine ask acted <seat>/<id> "<filed <PREFIX>-NNNN | folded | dropped | re-asked as …>"`.
5. **No answer is not a yes.** An unanswered ask files nothing, however long it waits; the re-ping and the pass-up follow `/ask` § While you wait. A caller's `--yes` does not waive it either (Constraints).

## 1. Scope & Goal

Establish the two anchors the run depends on: **what work** the ticket(s) come from, and **the intent** behind it.

**Resolve the tracker config (do this first):** Read CLAUDE.md's `## Tracker` block (the orchestrator sees CLAUDE.md; the subagent will NOT, so you must resolve here and inject in §2). Resolve: the **issue-key prefix** — `<PREFIX>` uppercase for keys (`<PREFIX>-NNNN`) and its lowercase form for branches (`<prefix>-NNNN-…`) — and the **team**. For example: prefix `ENG` / team `Acme`. **Fallback — no `## Tracker` block** (unconfigured project): keep today's behavior — detect a `ENG`-style key (an uppercase-alpha prefix + `-NNNN`) from the branch/slug/conversation at lower confidence. The config is never a hard requirement; absent it, degrade to detection, don't error.

**Read the TARGET project's handbook — `§CMD_READ_PROJECT_HANDBOOK`.** A seat filing into another project obeys THAT project's lines, not the habits of the project it happens to be working in, so read them off the project the ticket will LAND in. **Run this AFTER the context-ticket detection below** (and after a caller pinned a placement, §3), since those are what name the project; running it first leaves nothing to resolve. Ask it for `ticketing-strategy`, `boundaries`, `channels` and `repo-destinations`, and pass no `ask` — an unresolvable project degrades rather than prompting. The atom owns the whole read: resolution, the fresh re-fetch, the Project-description fallback on a pre-move project, and the one-line degradation when a project publishes nothing.

What each returned part is actually for, so none of it is carried decoratively:
- **`## Ticketing Strategy`** → the §2 drafter (the **Size** dial rules finding-vs-chunk; the drafter cannot read Linear documents on its own). It does **not** feed the §3 Subject Gate: its dials are Volume, Size and Substance — how many and how big — and none of them rules a *subject*. The Subject Gate runs on its own floor, which is why it needs no handbook and admits no override.
- **`## Boundaries`** → §3 **placement**. An entry whose test routes this work to a neighbouring project is a placement finding, surfaced there rather than filed into the wrong project.
- **The channel set and the repo destinations** → the §3 Subject Gate's refusal, which names destinations **this project published** and invents none.

**A missing handbook never blocks a filing.** The atom degrades in one line; `/ticket` carries on unchanged.

**Scope** — the body of work to turn into ticket(s). Resolve from args, else infer and confirm:
- *(bare)* / a descriptor → the active session's log/plan/`DIALOGUE.md` (the current chunk / what we just did), else the recent conversation.
- `diff` → the uncommitted working-tree diff (`git status` + `git diff`) — ticket the change or the follow-ups it implies.
- `session` → the work described in the active session's artifacts.
- text after `--` → an intent/framing override (what these tickets are really *for*).
*If scope is ambiguous, present the candidates as a gate question (§ Gate route). On the ask route, draft the likeliest candidate and name the others in the ask's `¶ASK_FILE` counter, so the run still asks once.*

**Detect the context ticket** (drives placement in §3): Scan for a parent key `<PREFIX>-NNNN` (prefix from § Tracker) in the **session slug** (example, prefix=ENG: `2026_07_02_ENG_2737_...` → `ENG-2737`), the **git branch** (lowercase prefix: `<prefix>-2712-...` → `<PREFIX>-2712`), or the conversation. Call `get_issue` now to resolve enough to display the parent's **title · state · team** at placement (and to read its labels/project/cycle for inheritance in §4). Note the confidence: a **branch-derived** key that contradicts a **slug-derived** key, or a parent that is **Done/Canceled/archived**, is a low-confidence CANDIDATE, not a default — §3 forces a pick in that case.

**Resolve the trail** (used in §2/§5): `<trailDir> = <sessionDir>/builds/`. Pick a `<slug>` once — a short kebab-case string of the scope (e.g., `identity-model-fix`, `recap-flat-followups`). If this run follows a `/build` or `/experiment`, reuse that run's slug so the tickets sit beside its report. Otherwise, before minting a fresh slug, `ls <trailDir>` — if an existing `<slug>_*.md` clearly matches this work (same chunk / ticket / topic), REUSE that slug so the trail clusters under one name; only mint a new one for genuinely new work.

**Sweep for prior work — dispatch `/ticket-search` BEFORE drafting.** Invoke the `ticket-search` skill in the **background** with the scope as its search intent — **on the ask route as `/ticket-search --report`**, which sweeps, writes its report and returns the duplicate candidates without walking them or asking anything (§ Gate route; the terminal route keeps its full walkthrough) — then proceed straight to §2; the two run in parallel and the report is waiting when calibration starts. It is read-only, it deep-reads each candidate's full body **and comment thread** inside its own subagent, and it returns a duplicate/overlapping-work callout split by state. This is the run's PRIMARY duplicate check — §4.1's `list_issues` pass is only a late backstop, and a duplicate discovered there arrives after the draft is written and approved, when the cheapest move has already been foreclosed.

Seed the search with **the defect's coordinates, not its vocabulary**. A ticket about the same problem is routinely titled after a different layer of it, so title keywords and solution nouns are the weakest possible key. Search the stable identifiers the defect carries wherever it is described: fixture / corpus ids, file and page numbers, error strings, the literal text of the offending row, the failing test name, the symptom's own words. Run the vocabulary query too — just never *only* it.

*If no tracker MCP is connected, skip the sweep and say so in one line; do not silently proceed as though it came back clean.*

**Echo back in one line:** `Ticketing <scope> — intent: <intent>; context ticket: <<PREFIX>-NNNN "title" · state · team | none>; ticketing strategy: <<project> handbook | none published>; prior-work sweep: <dispatched | skipped, reason>; trail: <trailDir>/<slug>_TICKETS.md.`

## 2. Draft — Spawn the Drafting Agent (Background)

**Backgroundable & parallelizable.** This sub-agent dispatch is a composable building block: it can run in the background (`run_in_background: true`) so the orchestrator keeps working while it runs, and when the work splits into independent chunks, several such sub-agents can be fanned out in parallel and reconciled.

> **Before dispatching — `§CMD_LOG_SKILL_INVOCATION`**: log this dispatch to the session log (why + context-pack pointer + one-line re-tread) so a restarted session can re-tread it. Fire it as the last step before the `Task`/`Agent` handoff.

Spawn **one** background agent (a `general-purpose`/`analyzer`) to analyze the scope and draft the ticket(s). It does the heavy reading and framing; you keep the thread for calibration. Build its prompt so it is entirely self-contained. Use the exact prompt structure below:

> **System Prompt for Drafter:**
> You are drafting one or more **premise-first** tickets from a body of work. Your goal is to orient the future builder to the PROBLEM and its terrain, not to provide a line-by-line map. Point at the **general areas / modules** involved (dirs, file-groups — never an exhaustive path/line dump, which rots immediately), define "done" by observable **outcome**, and name the traps you already see. You cannot know everything up front and shouldn't pretend to — the implementor discovers the specifics. Your job is to bound the problem sharply and flag the landmines. Analyze the scope; do NOT write code or file anything.
>
> **Inputs:**
> - **Tracker config (resolved from CLAUDE.md § Tracker — the orchestrator fills these; you cannot read CLAUDE.md):** Linear (linear MCP) · issue-key prefix `<PREFIX>` (keys `<PREFIX>-NNNN`, branches `<prefix>-NNNN`) · team `<team>`. Use this prefix wherever a key/placement appears; do NOT assume `ENG`.
> - **The target project's `## Ticketing Strategy`, verbatim (the orchestrator read it in §1; you cannot read Linear documents):** `<the section, or "none published — draft to the skill's own floor">`. Volume, Size and Substance bound how many tickets this scope should become and what makes one worth existing — weigh them in the decompose call below rather than treating them as prose.
> - **Intent (what this work is for):** `<intent>`
> - **Scope to analyze:** `<scope + concrete pointers: session artifacts / git diff cmd / files / conversation digest>`
> - **Read for context:** `<session log / plan / build report / relevant modules>`
>
> **Rules of Engagement:**
> - **A finding is a SIGNAL; only a chunk of work is a TICKET — so the default output is zero tickets.** Before decomposing, rule what you are holding. A **chunk** is one landing arc — build, critique, landing with a proof page, days not hours — and that is the bar the project's `## Ticketing Strategy` **Size** dial sets above (each project dials its own; apply the one you were handed, not a remembered default). Anything below it is a finding, and a finding's destination is an inbox drop via `/inbox-post`, not a ticket. A run holding N findings therefore returns **N signals and no tickets**, and reports that as a successful run. **Agent-initiated batches are refused**: propose at most ONE ticket per run unless the human explicitly asked for more — a set of drafts out of a single sweep is the exact shape this rule exists to stop.
> - **The human splits; you propose ONE.** Having ruled that a ticket is warranted at all, draft exactly one coherent ticket with one premise. **You do not split on your own judgement, even when the work touches two decoupled systems** — note the candidate split in `open questions` and let the user make it at calibration. Draft more than one only when the orchestrator tells you the human asked for a split, and then draft what they asked for.
> - **PREMISE-FIRST, not a solution.** Each ticket states the PROBLEM and its BOUNDARIES, not how to code it. Fill the template fields (`assets/TEMPLATE_TICKET_DRAFT.md`) meticulously; the terse roster and its load-bearing nuances: `title` (crisp, outcome-oriented) · `plain-terms` — **ONE sentence, and it becomes the ticket's first line**: what this is about in language someone outside the project understands, with **zero coined vocabulary** and no internal nouns. It is a comprehension gate, not a summary: if you cannot write it without project jargon, you do not yet understand the ticket well enough to file it, and the fix is to go understand it — not to reach for the jargon. A reader who has never seen this project should get the gist from this line alone · `type` (bug/feature/chore/tech-debt/spike — maps to a label, drives the rest) · `premise/problem` (grounded in the work) · `intent/why now` · `evidence/grounding` — **the anti-solutioning field** (general areas/modules + observed symptom + provenance; a representative pointer or two, NOT an exhaustive `file:line` dump that rots) · `constraints` (what bounds the WORK — guardrails that expire when it lands) · `invariants` — **properties the RESULT must have**, each stated so a violation is pointable, optionally tagged `INV_UPPER_SNAKE` after the sentence. Distinct from constraints: a constraint says how to proceed, an invariant says what must be TRUE of the built thing a year later. Write each as rule → what it FORBIDS → the reason in one clause, because agents route around a stated preference but not a stated prohibition. **Omit the field entirely when the ticket has none — never pad it with restated constraints** · `non-goals` · `acceptance signals` (observable outcomes, not an algorithm) · `first step` — **the entry point, deliberately NOT a plan**: the one concrete action that starts the work, in a single line (the file or module to open first, the query or command to run, the question to go answer). This does not violate premise-not-algorithm and must not be allowed to drift into it: a first step says *where to put your hands*, an algorithm says *what to build*. One line, never a sequence — if you are writing "then", you have crossed into prescribing. **Required even on a `spike`**, where it is the first unknown to attack; a research ticket with open questions and no named starting point strands whoever picks it up · `implementation traps` (conceptual "you'll be tempted to X, don't, because Y" — not a path dump) · `escalation triggers` — **the specific conditions under which the builder should STOP and return to the user** rather than guessing · `reproduction` (bugs only) · `open questions/unknowns` (incl. a split not taken) · `dependencies` (by DRAFT #: `blocked-by #2`/`blocks #3`/`relates-to #2`) · `suggested priority + labels` — labels are **SUGGESTED only, to be reconciled against the real team label set at §4.1** — the drafter doesn't know the team yet · `proposed placement`. Do NOT prescribe an implementation/algorithm; if the work implies one, note it as a brief optional "possible direction" at most (dropped from the filed ticket unless the user explicitly keeps it).
> - **Never claim the work is unowned or novel.** A separate prior-work sweep owns that question and its report is not yours to pre-empt. Do not write "no ticket covers this", "this has never been owned", or "this is a new class" — and if an upstream report you were handed says so, carry its **confidence and its stated blind spots** with the claim rather than the bare conclusion. A medium-confidence "never owned" that arrives stripped of its qualifier reads as fact and files a duplicate.
> - **Spike escape-hatch.** If the scope is fundamentally a research task with no genuine acceptance criteria yet, do NOT fabricate constraints/acceptance to fill the form — force **Type = `spike`** and heavily populate **Open questions / unknowns** instead, with acceptance framed as "the questions are answered."
> - **Return contract:** WRITE the draft(s) to `<trailDir>/<slug>_TICKETS.md` using the Ticket Draft template (this skill's `assets/TEMPLATE_TICKET_DRAFT.md` — the orchestrator gives you its path; do not hardcode `~/.claude`), one block per ticket. Per ticket, ALSO render the final postable `description` Markdown — the exact body `save_issue` will receive — into that ticket's block under a clearly-labeled **"Rendered description (postable)"** slot: **opening with the `plain-terms` sentence as the body's very first line** (`**In plain terms:** …`, before any heading) **followed immediately by `**First step:** …` as the second line** — the two orientation lines come before any section so a reader knows what this is and where to start without scrolling — then the premise-first fields as `## Premise` / `## Intent` / `## Constraints` / `## Invariants` (omit when none) / `## Non-goals` / `## Acceptance` sections plus the Evidence/grounding and (bugs only) Reproduction headers, all already rendered, with any "possible direction" already **EXCLUDED unless the user flagged it to keep**. Render it complete and ready-to-post — §4 lifts this block VERBATIM. Then return a 3–5 line summary to the orchestrator: how many tickets, each title, and the proposed placement.

Prefer background execution (`run_in_background: true`) so the user can keep working; relay the summary when it lands. For a tiny, obvious single-ticket scope, you MAY draft inline instead of spawning — state this in one line if you do.

## 3. Calibrate — Walk the Drafts with the User

The interactive **calibration gate is the core of `/ticket`** — the user, not the model, finalizes each ticket before anything is posted. Run it explicitly; never post a draft as-is. It takes the shape of `§CMD_WALK_THROUGH_RESULTS` — the context block and the per-item decision — but not that atom's terminal prompts, which § Gate route replaces. **Who answers it follows § Gate route**: on the terminal route the steps below are asked one at a time; on the ask route they define what each fork of the run's one ask decides, and the §4 batch confirm rides in that same ask.

0. **Subject Gate — rule each draft's SUBJECT before anything else.** A tracker holds domain work: the product, its behaviour, its language, what a customer gets. Run this **first**, ahead of the Prior-Work Gate — a draft refused here needs no duplicate search.

   **Refused as a SUBJECT:** a **guard or check** (a gate, a lint, an assertion suite, a CI job) · **tooling** (hooks, worktree helpers, donor clones, gate plumbing — anything serving the build rather than the product) · **a seat or ownership question** (who owns a surface, which lane holds a file) · **agent-coordination machinery** (relays, partitions, handoff formats, how skills call each other).

   **One project is carved out, and it is named rather than described** — `Product: Orchestration` (`P-IDE-10`, team Idealic, `https://linear.app/idealic/project/product-orchestration-bfe9d92b7318`), whose domain work IS the orchestration machinery: loom, groom, decide, direct, intake, and the transport carrying decisions back. A conductor's boundaries, a hand-off format, a durable ledger row or a decision transport is an **ordinary domain subject when the ticket is filed THERE**, and refused everywhere else. **The exception is a project, never a category** — "engine work", "coordination machinery" and "tooling" stay refused as subjects wherever they are filed, because a category-shaped exception is one any seat can claim by renaming its work, and the product trackers fill with plumbing anyway. **It answers the subject question and nothing else**: the instance requirement below still binds, Volume, Size and Substance still bind, and a finding filed there is still a signal rather than a ticket — which is why the route-around below still holds — a product whose domain IS checking needs no exemption at all, only an instance. **Every other project's protection is unchanged**, redirected to the destinations named below.

   **This paragraph is the single statement of the carve-out that a filer reads.** Everywhere else — this skill's frontmatter and Constraints, `/groom`'s 🛠️ route, `/inbox-post`'s classification rule — cites it by name instead of restating it, because the rule stated in several wordings is the defect that produced the carve-out's own ticket. Extend the carve-out to a second project only by editing this paragraph.

   **The discriminator is the PREMISE: does a defect in the product exist right now, independent of the guard?** Strip the proposed fix and ask what is left wrong. If a false statement, a wrong output, a missing capability or a broken behaviour remains — **name it, and the draft stands, even when every acceptance signal is a guard**. If what remains is only that nothing would catch the problem should it ever occur, the guard's absence *is* the complaint: the subject is the guard, and it is refused. **A guard may be the acceptance; it may never be the premise.**

   So the gate has a field, and it is the gate: **the premise must name the instance that is wrong today** — the file, the row, the output, the page, the behaviour. A premise that cannot name one has no defect behind it yet. **Refuse an empty one** rather than reading intent into it.

   *The nearest-neighbour pair (`§INV_NEGATIVE_CASE_IS_THE_NEAREST_NEIGHBOUR`), both describing the same world:* *"`agreement.md` states 14 refusal classes; the registry defines 17, so the page is wrong where it is read as authoritative"* **passes** — strip every proposed check and a false page remains. *"The teaching pages have no automated agreement with the registry, so a future edit could diverge unnoticed"* **is refused** — strip the check and nothing is wrong today; the complaint is the missing guard. Same area, same likely remedy, different premise: one names a defect, the other names an absence of detection.

   **The route-around is the mechanism, not a leak.** A refused draft becomes a passing one by naming the live instance behind it — *"add a hook blocking migrations with no journal entry"* refused, *"migration `0042_foo.sql` has no journal entry, so it will silently not run in staging"* passed, same remedy, same assignee. **That is the gate working.** A guard ticket forced to name the defect it exists for is a better ticket: it tells the builder what is broken, it can be verified, and it dies when the instance is fixed rather than lingering as an open intention. The gate is not trying to keep the work out of the tracker — it is making the work state its evidence. **It follows that a product whose domain IS checking keeps its domain work**: *"the compiler accepts `<construct>`, which the spec forbids"* names an instance and passes, as does a conformance table that omits a real divergence or a refusal message that states something false. A project whose remit is gates files its gate work this way; it does not need an exemption, it needs an instance.

   **Refuse by naming the destination, never by dropping the item.** An agent routes around a stated preference but not a stated prohibition, and a refusal that names no destination simply loses the item. The destination has a reporting half and a resolving half, and **this skill names neither by path** — it is a global skill and a path that exists in one repository does not exist in the next:
   - **The report** goes to the target project's **🛠️ Tooling & Gates** inbox channel via `Skill(inbox-post, …)`. Tooling friction is inherently cross-seat — agents complaining about each other's gates — which is why it has no honest home in a defect channel. **Items in that channel do not graduate to tickets**; the channel is the record, not a staging area.
   - **The resolution** lives in the **repository**, not the tracker, **at the destinations this project's handbook names** (`§CMD_READ_PROJECT_HANDBOOK` returns them; a 🛠️ channel publishes them in its `## Directions`). Typical kinds are a row on the repo's gate board where it keeps one, an invariant or pitfall in the owning package's `.directives/` file, or the repo's ownership line. **Name the one the project published; invent no path it did not.**
   - **Most projects have no 🛠️ channel, and that is the normal case, not an error.** When the handbook reports none, say so and offer the repository half as the sole destination — never post a tooling item into a defect channel as a substitute, and never invent a channel.

   Report the refusal with its destination in the same gate question (§ Gate route) that offers the redirect: **post it to 🛠️ Tooling & Gates** (offered only when the project has one) · **record it in the repository instead** (naming a destination the project published) · **name the live instance**, which converts the draft into a domain premise and re-enters it here. There is no override option, and none is needed — the way past this gate is an instance, not a waiver, and a draft with no instance to name has nothing a builder could verify.

1. **Prior-Work Gate — settle every duplicate candidate BEFORE calibrating content.** Read the §1 `/ticket-search` report. For each candidate it flags as a duplicate or overlapping work, present the candidate (`<PREFIX>-NNNN "title" · state`) beside the draft it collides with, then force a decision with a gate question (§ Gate route; on the ask route, a `¶ASK_DUP` fork) — **`Fold` is the default**:
   - **Fold into `<PREFIX>-NNNN`** — don't file. Report what the draft adds that the existing ticket lacks, so the user can route it to a comment or a `/snapshot` scope-widening. This is the default outcome.
   - **File as sibling** — permitted **only** when you can name a **defect** the candidate does not describe. State it in one sentence before the option is offered.
   - **Not related** — the search's ranking was wrong; say why in one clause.

   **Dedup on the DEFECT, not on the fix, not on the title.** Two tickets describing the same broken thing are duplicates even when they propose different solutions, sit at different layers, or are titled after different concepts. A candidate that names the same rows / files / fixtures / failing behaviour as the draft IS the same ticket, however differently it frames the remedy. "We're sending it somewhere else" and "that ticket is about the vocabulary, this one is about the routing" are descriptions of a *fix*, not of a defect — neither clears this gate. If the candidate poses the draft's whole thesis as an open question, the draft is an **answer to that ticket**, not a new one.
   *Smell test before choosing `File as sibling`:* if this draft were deleted and its new facts added as a comment on the candidate, what would be lost? If the honest answer is "nothing" or "only the framing", fold.

2. **Granularity Gate (one gate question, terminal route only):** **Normally skipped**; on the ask route it never fires: each draft of a human-requested split goes up as its own ask, shaped as § Gate route step 3 describes — a run drafts one ticket, so go straight to its calibration. It fires only on a human-requested split, where N > 1: "How do you want to walk the N drafts?"
   - **Each** (one at a time)
   - **Groups** (batches of ≤4, for a large requested split)
   - **Accept all as drafted** (skip straight to the post gate).

3. **Per Ticket (or group of ≤4) — Context Block + gate question (§ Gate route; on the ask route, `¶ASK_FILE` with the context block as the ask's opening card):**
   First, present a 2-part context block in chat (`§FMT_CONTEXT_BLOCK`):
   - Line 1: `[#]: <title> — proposed placement`
   - Line 2: The premise + the acceptance signals + suggested priority/labels.
   Then ask the gate question (`header` = ticket number on the terminal route) with this option tree:
   - **Approve:** Take the draft as-is into the post set.
   - **Edit:** Adjust title / premise / scope / acceptance / priority / labels. Capture the change, re-show the finalized block.
   - **Split:** This should be N tickets; define the split (each gets its own premise).
   - **Merge:** Fold into another draft (name which).
   - **Drop:** Don't file this one.

4. **Placement Per Ticket:** For each ticket kept, confirm placement (this is the one decision `/ticket` makes from context, but the user always confirms it explicitly). **Echo the resolved parent** (`<PREFIX>-NNNN "title" · state · team`, from the §1 `get_issue`) so the decision shows what is being nested under:
   - **Caller-pinned placement — check this FIRST** (a calling skill that owns its own filing model): when `/ticket` is invoked *by another skill* that dictates where the issue must land — e.g. an inbox-grooming pass graduating a signal into a specific work-type **milestone** — that placement is **authoritative and skips parent detection entirely**. The caller passes `project` + `milestone` + "new issue, never a sub-issue"; echo it and confirm it like any other placement, but do **not** offer a detected parent as the default. The reason it must skip rather than merely outrank detection: the parent that *would* be detected there is the **source artifact** (a frozen collector ticket the signal arrived on), and nesting under it is forbidden by the caller's own model — the grooming skill parks such sub-issues straight back out again. This is the one branch where detection is bypassed rather than user-overridden.
   - **Detected parent, high confidence** (`<PREFIX>-NNNN`, open, same team as the target) → Default to **sub-issue** of it. Inherit **labels + assignee + team + project + cycle**; `title / premise / priority` stay per-ticket. Show the inherited set so the user can prune.
   - **Low-confidence parent** (branch-derived key ≠ slug-derived key, or parent is Done/Canceled/archived, or a different team) → Treat it as a **CANDIDATE, not a default**. Surface the candidate(s) **plus "new top-level"** as a gate question (§ Gate route; on the ask route, `¶ASK_PLACE` with no lean) and **force a pick** — never silently nest.
   - **No parent detected** → Default to **new top-level issue**, baseline **status = Backlog, unassigned, no priority**. When the scope suggests sensible **labels / project** (from the work area, related issues, or the context ticket even if not a strict parent), **offer to apply them** — don't silently blank them, and don't force them.
   - **Sanity check:** Any parent must be **open** (not Done/Canceled/archived) and **on the same team** as the target before defaulting to sub-issue. If either fails, drop to the candidate branch above.

5. **Batch Shortcuts:** Honor these immediately. If the user says "all as sub-issues of `<PREFIX>-N`" or "drop the last one," apply it and move on. **"Approve all" is content-only** — it takes every draft's title/premise/fields as-is into the post set but does **NOT** decide placement; placement stays an explicit per-ticket confirm (and is re-confirmed at the §4 batch gate). It clears neither the Subject Gate nor the Prior-Work Gate: a refused subject and a flagged duplicate are each settled by their own decision, never swept up by a batch approval.

After the walk, assemble the **post set**: each finalized ticket with its resolved placement + fields. If nothing survives, report that and stop.

## 4. Post — To Linear (Single Batch Confirm)

Reconcile, dedup, confirm once, then create — and wire dependencies in a second pass. `save_issue` takes **human names/identifiers, not UUIDs**; there is no ID-resolution dance.

1. **Reconcile + Dedup** (the team is now known from §3 placement):
   - **Labels:** Pull the real team label set (`list_issue_labels`, team-scoped) and reconcile each ticket's SUGGESTED labels against it. Keep matches; **drop or flag any label not in the set** (surface the drop so the user can create it or pick another). The drafter never knew the team, so this is where suggested labels become real ones.
   - **Dedup (BACKSTOP only — the real check was §1's `/ticket-search`):** Before building the create calls, run `list_issues` for each draft, scoped to the target `team`. Query the **defect's coordinates** (fixture ids, file/page numbers, error strings, the offending row's literal text) as well as title keywords — `list_issues`'s `query` is a fuzzy search over title and description, so a ticket that frames the same defect at another layer will not surface on solution nouns alone. Anything this pass turns up that §1 did not is a **late duplicate**: send it back through the §3 Prior-Work Gate rather than carrying it forward as a footnote, because the same fold-vs-file decision is owed to it. Whatever survives is surfaced at the batch confirm (step 3) as **"possible duplicate of `<PREFIX>-NNNN`"**.

2. **Build one `save_issue` per ticket** — the real field shape:
   ```javascript
   save_issue({ team, parentId: "<PREFIX>-NNNN", title, description, priority, state, labels: [names], assignee, project, milestone, cycle })
   ```
   - **`milestone`** (a project milestone — NAME resolves directly, or its UUID): set it when a caller pinned one (§3's caller-pinned branch) or when the target project uses milestones as its routing model rather than as release markers. Omit otherwise. If a name is ambiguous or you are unsure it exists, run `list_milestones` on the project first — do not guess, and do not silently drop the field, because a project whose whole triage model is milestones will file the issue into nowhere visible.
   - **Sub-issue:** Set `parentId: "<PREFIX>-NNNN"` (the resolved-prefix identifier directly — no ID lookup) + the inherited `team` / `labels` / `assignee` / `project` / `cycle` (read off the parent via `get_issue`, used ONLY to copy those values), with the per-ticket `title`, `description`, and `priority`.
   - **New top-level:** Set `team` + the calibrated fields. **Pass `state: "backlog"`** — prefer the state **TYPE** `"backlog"` (robust if a team renamed its backlog status) so the issue actually lands in Backlog rather than the team default (which is Triage when enabled); if unsure the team has one, verify via `list_issue_statuses`.
   - **Map priority:** Word → int: None→0, Urgent→1, High→2, Medium→3, Low→4.
   - **`description` is Markdown:** **LIFT the drafter's "Rendered description (postable)" block VERBATIM** from `<trailDir>/<slug>_TICKETS.md` into `save_issue({ description })`. The drafter already rendered the premise-first body (section headers `## Premise` / `## Intent` / `## Constraints` / `## Invariants` (omit when none) / `## Non-goals` / `## Acceptance` + Evidence/grounding + any bug Reproduction, **"possible direction" excluded unless the user flagged it to keep**); the orchestrator does NOT re-render it. Apply only the edits the user made at calibration (§3) to that block before lifting.
   - **Dependencies:** Cross-ticket dependencies stay unset here (the sibling has no `<PREFIX>-NNNN` yet) — they are wired in step 4.

3. **Single Batch Confirm (a gate question, MANDATORY):** Posting is outward-facing and hard to undo. **On the ask route this confirm is the run's one ask** (§ Gate route step 3): its `FILE` answer is the "Post all" below, and nothing here is asked a second time. First, render the **full per-ticket set in a chat block** above the question. For each ticket, show: title, placement (`sub-issue of <PREFIX>-NNNN` | `new in <team>`), priority, labels, assignee, any **"possible duplicate of `<PREFIX>-NNNN`"** flag from step 1, and any **evidence to attach** (screenshots/artifacts — see below).
   Then ask **"Post all N to Linear?"** with options: **Post all / Edit one first / Cancel**.
   - On a flagged duplicate, offer **fold into `<PREFIX>-NNNN` / skip / file anyway** for that ticket — in that order, `fold` first. A duplicate flag **inverts the default**: the burden is to show the draft is not a duplicate, never to note in passing that it might be. Do not argue past a flag in prose and proceed; if the flag is wrong, the user says so.
   - On **"Edit one first"**, ask a follow-up gate question for the ticket number, loop to that ticket's §3 calibration, then **re-present the full confirm**.
   - Only on **Post all** do you create.

4. **Create + Wire + Capture:** Run the `save_issue` create calls, collect each new issue's **identifier (`<PREFIX>-NNNN`) + URL**.
   **Then, second pass:** If any draft declared a cross-ticket dependency (by draft #), run a second `save_issue` per edge — map draft # → the newly-returned `<PREFIX>-NNNN` and set `blockedBy` / `blocks` / `relatedTo` (these are append-only and accept identifiers). If a create fails, report which and stop (don't retry blindly).

5. **Attach ready evidence (opt-in, after create):** If — and ONLY if — the agent already has supporting evidence **in hand from this run**, attach it to the matching filed issue. Qualifying: **screenshots / images** the agent captured (UI screenshots, overlay or diagram images, a chart) and **well-made standalone artifacts** that materially support the ticket (an evidence doc, an important report, a writeup — e.g. from `/writeup`, `/analyze`, or a design doc). **Do NOT attach internal session process artifacts** — session debriefs, `*_LOG.md`, `DIALOGUE.md`, plan files, or the build-trail reports (`*_BUILD.md`/`*_TICKETS.md` etc.) — and **never fabricate or generate a screenshot** just to have one; attach only what genuinely already exists. Attach via the Linear attachment flow to each ticket's `issueId` (`prepare_attachment_upload` → upload the bytes → `create_attachment_from_upload` for a local file; or `create_attachment` for a URL — load schemas via ToolSearch `linear`). Attaching is outward-facing, so the exact attachment set is shown in the step-3 batch confirm and nothing uploads without that approval; best-effort — an attach failure is reported, it does not abort the filed tickets.

## 5. Report

Summarize in chat: what was filed (each `<PREFIX>-NNNN` + URL + placement), what was **refused at the Subject Gate** (and the destination it went to instead — the channel, the repo location, or a restated subject), what was **folded into an existing ticket** (which one, and what the draft added that it lacked), what was dropped/merged, and any create that failed. Link the drafts trail (`§CMD_LINK_FILE`). A run that files nothing is a **successful** run — report it that way, not as a failure. That covers all three ways it happens: everything folded, everything was a finding and went out as signals, or a subject was refused and redirected.

**Paper Trail:** Update `<trailDir>/<slug>_TICKETS.md` — mark each draft with its outcome (`→ filed <PREFIX>-NNNN <url>` / `folded into <PREFIX>-NNNN (what it added)` / `merged into #` / `dropped`). Append across the run so a killed/resumed run keeps the record.

**Feed the Ledger** (Compounding memory, same as `/build`+`/scrutinize`): Append the durable outcome to `<trailDir>/LESSONS.md` — one terse bullet: what was filed, the identifiers, and any framing decision worth carrying (e.g., *"Split the cutover into `<PREFIX>-A` identity + `<PREFIX>-B` reader-swap; `<PREFIX>-B` blocked on `<PREFIX>-A`"*). Use `engine log`. The next `/build`/`/scrutinize` reads these, so the tickets you filed shape the next handoff. Do NOT commit anything.

## Constraints
- **The subject must be domain work; a guard may only be the acceptance.** A guard or check, tooling, a seat/ownership question, or agent-coordination machinery is refused as a ticket's SUBJECT — strip the proposed fix, and a ticket with nothing left wrong in the product was never a ticket. A ticket whose premise is a product defect stands even when every acceptance signal is a guard. **Refuse by naming the destination, never by dropping the item**: the report to the project's 🛠️ Tooling & Gates channel where it has one (that channel does not graduate to tickets), and the resolution to the repository, **at the destinations the project's own handbook names** — this skill is global and hardcodes no repository path. There is no override; the way past the gate is naming the instance that is wrong today, which is the gate doing its job rather than a leak. **One named project is carved out of the subject half — see §3 step 0, which states it once; do not restate it here.** It clears the subject question alone: that project's filings still face this gate's instance requirement, the Volume/Size/Substance dials, and the finding-is-a-signal floor.
- **The target project's lines bind, not the working project's.** §1 reads the project the ticket will land in via `§CMD_READ_PROJECT_HANDBOOK` and carries its `## Ticketing Strategy` into the drafter and the Subject Gate. A missing handbook degrades to one line and never blocks a filing.
- **Premise, not algorithm.** Every ticket states the problem + boundaries + acceptance, never a prescribed implementation. If the work implies a solution, it's an optional one-liner at most — the ticket must survive a different approach.
- **A finding is a signal; a chunk of work is a ticket.** The default output of a run holding findings is inbox drops via `/inbox-post` and **zero** tickets — a ticket is the exception a human asks for, never the natural product of noticing things. The bar is the project's **Size** dial (`## Ticketing Strategy`, read in §1): one landing arc, days not hours. **An agent proposes at most one ticket per run** unless the human asked for more; a batch of drafts out of one sweep is refused.
- **One ticket, and the human owns any split.** The skill drafts exactly one; a candidate split is reported as an open question, never acted on. Only the user raises the count — invoking the skill as *"split this into tickets"* is that ask, stated up front; nothing the drafter notices on its own is.
- **The user owns every ticket.** The drafter proposes; title, scope, labels, placement, and the decision to file are all a person's, through the gate question § Gate route selects. Never post an un-calibrated draft.
- **A seat with a parent never waits at its own terminal.** When `hop.sh target` names a seat, the calibration and the post confirm go up as ONE ask carrying the full draft, and the run resumes on `engine ask read`; a terminal prompt is only for a seat with no parent whose operator is at the terminal. The ask is reserved for the operator only when the ticket is scope-level (new scope, cross-area, a project or initiative change, reversing a ruling); a routine ticket in existing scope goes to the parent unreserved (`ruling-ticket-tier`).
- **Placement is context-driven, always confirmable.** A high-confidence parent (open, same team) → sub-issue inheriting labels+assignee+team+project+cycle; a low-confidence one → an explicit candidate pick, never a silent default; no parent → new issue posted with `state: "backlog"` (the baseline is *enforced*, not assumed — omitting `state` lets Linear fall to the team default), offering inferred labels/project. Placement is never swept up by "approve all"; the user confirms it explicitly and overrides either way.
- **Check for prior work before drafting, and dedup on the DEFECT.** `/ticket-search` runs in §1, before a line is drafted — not at posting time, where a duplicate arrives too late for the cheapest response. Search the defect's stable coordinates (fixture ids, files, pages, error strings, the offending row's own text), never only its title keywords or the fix's vocabulary. Two tickets describing the same broken thing are duplicates even when they propose different solutions or sit at different layers; a candidate that poses the draft's thesis as an open question makes the draft an **answer to that ticket**, not a new one. Finding a candidate and reasoning past it in prose is the failure this rule exists to stop — the gate is a decision, not a footnote, and its default is fold.
- **One batch confirm before posting.** Posting is outward-facing and hard to undo — a single explicit confirm of the whole set is mandatory; there is no auto-post. **No caller's `--yes`, Automatic posting disposition or unattended stretch waives it for a new ticket**: a new ticket always takes the manager's confirm, or the operator's when it is scope-level (`ruling-ticket-tier`), and an unanswered ask files nothing.
- **Plain terms first, jargon never.** Every body opens with the one-sentence `plain-terms` line before any heading, written for someone outside the project: no coined vocabulary, no internal nouns, and skills/tools named concretely (`/ticket`, not "the ticket-filing skill" — a periphrasis is *more* cryptic, not more portable). A ticket that only its author can parse is not filed, it is buried.
- **`/ticket` writes the FIRST body; it does not own later edits.** Material changes to a filed ticket's description go through `/snapshot`'s drift flow — an evergreen rewrite carrying every prior `## Change history` entry verbatim plus one new dated line, with the current description re-read immediately before the full-field replace. Do NOT freehand-overwrite a description, and do NOT stack correction blocks inside the body: a body that records its own edit history forces every future reader to reconstruct what is currently true. Routine progress is a comment, not a rewrite.
- **Paper trail always.** The drafts + outcomes persist to `<trailDir>/<slug>_TICKETS.md` and feed `LESSONS.md`, mirroring `/build`+`/scrutinize`.
- **Attach ready evidence, not process artifacts.** When the agent already has supporting screenshots/images or a well-made standalone artifact (evidence doc, important report, writeup) in hand, attach it to the filed issue (under the batch confirm, best-effort). NEVER attach session debriefs/logs/plans/build-trail files, and never fabricate a screenshot to fill the slot.
- **Sessionless + read-only on code.** `/ticket` owns no session dir and changes no code — it reads work and writes tickets. No commit unless the user asks.
- **Graceful without the tracker.** No Linear MCP → still draft + calibrate, hand over the finalized bodies to paste, note posting was skipped.
