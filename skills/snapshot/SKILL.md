Checkpoint a body of work. A reviewer subagent **actively verifies** the work read-only (running relevant gates to prove that what is claimed "done" is actually done), checks that it **follows the ticket's direction**, and **catalogs leftovers**. Once you confirm, the orchestrator **commits the reviewed work (scoped, gated on green)** and posts a status update to the ticket. This update includes a thorough comment, a proposed status transition, and—only when the premise has materially drifted—an evergreen description edit; on a closing snapshot it also attaches the session debrief as the ticket's permanent record. It is a menu, not a monolith: the batch confirm lets you decline any action — a commit-only checkpoint, a comment-only update, or the full **commit + comment + status + description** are all valid; **you pick what lands at the confirm.** Sessionless and lightweight: it runs *within* the active session—review → propose → one confirm → commit + post, then stop.

This is **not `/scrutinize`**: it does not hunt for code bugs or fix anything. Its job is to **follow the direction, verify the claims, find the leftovers**, and then **stamp a checkpoint**. It commits the reviewed slice and reports it outward to the ticket so a later human or reviewer-agent can trust the status without re-deriving it. It consumes the artifacts of `/build` and `/scrutinize` (`_BUILD.md`, `_CRITIQUE.md`, `_FIX.md`) to understand what happened. Multiple `/snapshot` checkpoints eventually roll up into a single `/pr` (which operates at the branch level, not the chunk level). As a **building block**, it verifies, commits, reports, and updates; it never repairs code or files followups (leftovers are merely guidance in the comment).

**Related — `/summarize`:** The §2 reviewer drafts its own comment body, but that "distill this work into a status" logic is exactly what `/summarize` does read-only. When a rich inward digest already exists (or you want one), `/snapshot` MAY generate its comment via `/summarize` and post that. `/summarize` is the report engine; `/snapshot` adds the verify + commit + outward post. This is optional wiring; the default self-contained draft path still stands.

**Tracker note:** This project uses **Linear** via the `linear` MCP — the tracker + its tools are constant; only the **issue-key prefix** and **team** vary per project and come from CLAUDE.md § Tracker (resolve them in §1, inject into the subagent prompt; keys are `<PREFIX>-NNNN` — `ENG` in the examples here). Tools: `get_issue` (read the ticket's intent/description/state/team/canonical branch), `list_issue_statuses` (resolve a target state), `save_comment` (post the comment), `save_issue` (move state and/or replace the description); with `--wave` / `--rollup` also `get_status_updates` + `save_status_update` (project and initiative status updates) and `get_initiative` (read-only — this skill never calls `save_initiative`). Load schemas on demand (ToolSearch `linear`). **No Linear MCP →** The **commit still happens** (it needs no MCP), but the ticket half degrades. The direction reference falls back to args/conversation (state explicitly that On-direction is lower-confidence), the **description proposal is SUPPRESSED** (Part 3 → "skipped — cannot read current body to preserve history"), and only the comment + a suggested status are handed to the user to paste manually. Note that posting was skipped.

**Unattended runs (`--yes`).** `--yes` waives the §3 batch confirm: the drafted set is taken as approved and the run posts without asking. It is for a caller that has already made the call — a `/loom` weave with Outward posting set to *Automatic*, an unattended stretch — and never a default; a human-driven run has no use for it. *(`--silent` and `--no-confirm` read as the same flag. `--yes` is the spelling, matching the data CLIs that already use it for this.)*

It waives the question and never a guard. **Two of the four actions are declined rather than assumed**, because they are the ones the human at the confirm was reading for (and, when the run carries `--wave` / `--rollup`, two more — see the third and fourth bullets):
- **A commit over red or unrun gates is skipped**, and the rest of the update still posts. Committing red work is an explicit opt-in here; a waived confirm is not an opt-in, so this flag cannot supply one.
- **A description rewrite is skipped**, with the drafted body handed back in the report (§4) for a later pass. A description edit is a full-field replace, and its guards protect `## Change history` rather than the rest of the body — a draft that quietly drops a paragraph of premise passes every one of them. Under a confirm a person reads that body; under `--yes` nobody does.
- **A project update whose health could not be derived is skipped**, per project, and the rest still posts. Health is the one field a reader of Linear's project view takes on trust; under a confirm a person picks it, under `--yes` the run declines rather than guess one (§ *Wave-end updates*).
- **An initiative roll-up with no posted project update under it is skipped.** A roll-up is built from posted updates or not at all; under a confirm the person sees the empty set, under `--yes` it is simply not drafted.

**`--yes` files a ticket only for work that has none, and only once the run is known to proceed.** (Operator ruling 2026-10-30 03:06, IDE-341, with the round-4 rulings agreed by manager:director; it replaces the earlier rule that an unattended run files no ticket at all.) It applies when a `--yes` run has no explicit key, no `pending` or `filed` `.snapshot-autofiled` entry for this work (§1; a `spent` one is ignored), and §1 detects no key at any confidence: none from the slug, a branch key, the conversation or the commits being snapshotted. A low-confidence or ambiguous detection, a single commit key with no `--` included, still aborts. Every check that can abort runs first, in this order, and filing is the last step before the commit, so an abort never leaves a filed ticket behind:
1. **§1 decides eligibility.** With no branch key and no commit key, the would-be key passes §1's cross-check by construction (its commit-key set is empty and a lane branch only warns), so no §1 abort can follow the filing.
2. **Project and team, never guessed.** The project comes from the work's own repository first: the `skills/inbox-post/assets/INBOX_REGISTRY.md` section of the project whose area the work's paths belong to, where its project id alone resolves the project. Then the session's `linearProject` parameter. When more than one registry project plausibly owns the work → abort and name the candidates; never pick. The team is § Tracker's. Name the source used in the report; if neither resolves → abort and say so. The project's handbook is read through `§CMD_READ_PROJECT_HANDBOOK`, and a project with no handbook document (Realm's case) only means no handbook rules apply.
3. **§2 reviews and runs the gates** with no direction reference. The reviewer also drafts the ticket, premise-first as `/ticket` §2 does: it opens with the `**In plain terms:**` line and is sized by the project's `## Ticketing Strategy`.
4. **The draft passes `/ticket`'s gates that are not confirms**: its §3 Subject Gate, and the project's Ticketing Strategy with its Size dial (a finding rather than a chunk of work is refused). A refusal by any of them aborts with its reason.
5. **Duplicate search.** Run `/ticket-search --report` over the work, and file only when it returns no candidates. Here a candidate is a ticket the report classifies as a duplicate or an overlap: its §2 duplicate/overlap bucket, which the relay returns as `<KEY> · "title" · state · overlap` lines. A related-for-context hit is not a candidate. On any candidate, abort and print each as `<KEY> · title` with its state, so the seat re-runs with `-- <KEY>`. Never attach, never post to a guessed ticket, and never to a Done one.
6. **Linear backstop.** The duplicate search is lexical and the session record can miss a ticket an earlier run filed, so also query Linear (`list_issues`) for an open issue with the label `auto-filed` whose body names this session or, off `dev`/`main`, this branch; if one exists, abort and print it as `<KEY> · title` with its state, so the seat re-runs with `-- <KEY>`.
7. **§3's checks**: the staged-content check and the green re-check in §3 [1], when a commit is going to be made.
8. **File**, at §3 step 3 [0]: `save_issue` with the team, the project, `state: "backlog"`, the label `auto-filed` (create it in the § Tracker team if missing) and a body that opens with the line `auto-filed by /snapshot --yes` followed by `session: <sessionDir>` and `branch: <branch>` (the lines step 6 matches), with no ask. It is routine, never reserved: no `reserved-for: operator`. It is the one `save_issue` here without an `id` (Constraints). The record in `<sessionDir>/.snapshot-autofiled` moves through three states, each a new JSON line with the same `id` (§1): `pending` is appended before `save_issue`; `filed` with the `<KEY>` the moment `save_issue` returns, so the key is never lost; and `spent` when the commit carrying the key lands (§3 [1]). Its `branch` is `-` until a feature branch exists: on `dev`/`main`, Branch safety names the branch from the new key after [0], and only then is a `filed` line bound to that branch appended, so an entry is never bound to `dev`/`main`. If `save_issue` fails, or the run dies before it returns, the line stays `pending`, and §1 aborts on it until a person clears it. §1 reads the file first on a re-run. Then record a settled ask under the seat, "auto-filed <KEY> for <work>", answered by the seat, so it shows in the ask app's "Ruled below you". *(Owed: today's `engine ask` refuses an ask to oneself and an asker's own answer — `answerersOf` in `tools/ask-app/src/lib/store.ts` — so until it has a verb for a self-ruled record, §4 names the record as owed rather than writing the file by hand.)*
9. **Commit and post against the new key.** It is the run's explicit key from here on, as if passed after `--`, so the commit message carries the new key and a lane branch only warns (§1).

Apart from that one filing, every `save_issue` this skill sends carries the `id` of the §1 target, a leftover that seems to want a ticket of its own is reported in §4, never filed, and `--wave` / `--rollup` post status updates, never issues. A status move or checkpoint comment to a ticket that already exists stays routine (`ruling-ticket-tier`, 2026-10-29). **Scope-level reservation still applies to a ticket a seat files deliberately through `/ticket`**: there a new ticket takes the manager's confirm, or the operator's when it is scope-level, through `/ticket`'s gate route.

**Three situations abort the run** rather than guess, because each is the confirm doing its other job, which is telling you the target may be wrong: the §1 ticket detection is **low-confidence or ambiguous** (there is no confirm left to resolve it), the §1 **wrong-ticket cross-check fails** (the branch key names a different ticket key than the explicit one, an explicit source does not name the target, or there is no explicit key and the branch is not the ticket's canonical one; a lane branch under an explicit key only warns), or the **staged content holds something unexpected** (§3 [1]). An abort posts nothing, commits nothing and files nothing — an auto-file (above) comes after every check that can abort — and reports why.

Everything else is unchanged: mixed files take their standing default (skip the mixed file, commit the clean ones), the four actions stay best-effort and independent, and every hard stop still fires — the branch-safety abort, the `{{COMMIT_SHA}}` sentinel guard, the change-history guard, the TOCTOU re-read mismatch. **§4's Outcome names the flag**, because whether a human saw a comment before it went out is not recoverable from the comment afterwards; the report is the only place that reading survives.

## Wave-end updates (`--wave`, `--rollup`)

Operator ruling (2026-10-28, DIRECTOR session, "Updates and initiatives"): **every wave, one project update per project the wave touched**, posted by the worker's `/snapshot` with a health it proposes, which the manager may override; **one initiative per manager** (idealic, app, domain, docs) with its workers' projects under it, and the manager's `/snapshot` rolls its workers' wave updates into one initiative update. The director has no initiative.

Both are **opt-in by flag** — a run without `--wave` or `--rollup` behaves exactly as before and posts no status update. The caller that knows it is closing a wave (a `/loom` lane's snapshot, or the step `/next` offers at a wave boundary) passes them.

*   **`--wave <id>[@<ISO start>]`** — adds action **[6] Project update** for every project this run *touched*. **Touched = this run lands a commit, comment or status move on a ticket in that project.** A project whose ticket's actions were all skipped is not touched and gets no update. The `<id>` names the wave (e.g. `DIRECTOR/w3`) and becomes the update's last line, `— wave <id>`, which is what makes it idempotent. `@<ISO start>` is the wave's start; it is passed to the renderer as `since`, and only updates created after it count. **Pass it.** Absent it, the window is `-P1D` and the confirm says so; an update carrying *another* wave's marker is ignored either way, so a second wave the same day still posts, but an unmarked update in that day-long window cannot be placed and declines with a reason naming the missing start.
*   **`--rollup <initiative>`** — a manager's run: adds action **[7] Initiative roll-up**. It may run with no work of its own: then there is no target ticket to detect, so §1's ticket detection and its `--yes` abort do not apply, §2 is skipped, and the confirm carries only [7] and its overrides. It requires `--wave` — the roll-up is of one wave.
*   **`--override <project>=<health>:<reason>`** (repeatable, `--rollup` only) — the manager's health override of a worker's project update. It edits that update in place: the health field **and** a line in its body, `**Health set to <h> by the <manager> manager (was <h0>):** <reason>`, so the override is visible in Linear rather than only in a field's current value. An override with no reason is declined.

**The shape is `/intake`'s, reused**: capture the `save_status_update` id, edit that same update in place on a later pass, and keep the body cold-readable (`¶INV_UPDATE_READS_COLD` in `/intake`: no session paths, no phase names, no before/after deltas). It adds the two things a wave needs and intake did not: a proposed health, and a guard against a second update in one wave.

**The rules live in one renderer, `assets/wave-update.mjs`** (pure stdin → stdout; tests: `engine/scripts/tests/test-snapshot-update-sh.sh`). The orchestrator feeds it what Linear returned and posts what it decides; it never hand-writes a body or picks a health itself. `node <skill>/assets/wave-update.mjs project|rollup|health < input.json` is also the dry run: it renders the exact body, health and create/edit/decline decision without posting anything.

*   **Health** (`health` mode, fed the §2 PART 5 signals): `blocked`, red gates, or drift → **offTrack**; unrun gates, a re-scope, or an open critique MUST-FIX → **atRisk**; green (or no runnable gate) and aligned → **onTrack**. **All four signals are required, in PART 5's vocabulary** (gates `green|red|unrun|none`, direction `aligned|rescoped|drifted`, blocked `yes|no`, MUST-FIX a count ≥ 0); a missing one or `unknown` makes it `underivable` — never a default. Under a confirm the person picks one (posted as `healthSource: chosen`); under `--yes` that project's update is declined, and the renderer enforces it: every `--yes` call passes `unattended: true`, which refuses a chosen `health`.
*   **One update per project per wave** (`project` mode, fed `get_status_updates({type:"project", project, createdAt:<window start>})`): none of this wave's → **create**; exactly one carrying this wave's marker → **edit it by id**, replacing this ticket's section or adding it beside another lane's, with project health the worst lane's; **an update carrying another wave's marker is ignored**; **an unmarked update in the window** (an `/intake` Project Update, a hand post) → **decline** and surface the ids; an update with text the renderer did not write, or a lane with no readable health → **decline**, never rewritten. **A manager's override stands across worker re-posts only while the lanes are no worse than what it ruled on**: its note records that health as `(was X)`, it is carried forward, and while it stands the field and lead keep its health (the result says `overrideStands`, and `lanesWorst` shows what the lanes alone say). Once a lane is worse than `X`, the override **lapses**: the lanes' worst health posts, the lead no longer credits the manager, and a regenerated `**Override lapsed:**` line says which health it was ruled on and what the lanes show now. A manager who ruled on atRisk did not rule on red. A sequential retry or second lane therefore edits. Two lanes creating within seconds can still both create; [6]'s post-create re-read repairs that (below). A lane whose text carries a local file path is declined: the update must read cold.
*   **The roll-up is built only from posted updates** (`rollup` mode, fed `get_initiative({query, includeProjects:true})`, then each project's `get_status_updates` in the window, plus the initiative's own): only updates carrying this wave's marker count; zero → **decline, no body drafted**. Each project line links its update (an update with no `url` or no readable `health` declines the roll-up rather than linking nothing or guessing), so the roll-up traces to its sources; initiative health is the worst included project's (after overrides). An override that names a project with no wave update is reported in `declined`, never silently dropped; overrides stack in the body and the last one sets the health. An existing roll-up for the wave is edited, not duplicated. **The first roll-ups will be thin. Do not pad them.**
*   **Never create an initiative.** `--rollup` names one; `get_initiative` not finding it → [7] declines with "initiative not found" and the run reports it. Creating the four manager initiatives and attaching projects is an operator action outside this skill.

# /snapshot Protocol

## 1. Scope & target ticket

Establish two things: the **work under review** and the **ticket it reports to**.

- **Resolve the tracker config (do this first):** Read CLAUDE.md's `## Tracker` block (the orchestrator sees CLAUDE.md; the reviewer subagent does NOT — resolve here, inject in §2). Resolve the **issue-key prefix** (`<PREFIX>` uppercase for keys `<PREFIX>-NNNN` / its lowercase for branches `<prefix>-NNNN-…`) and the **team**. For example: prefix `ENG`, team `Acme`. **Fallback — no `## Tracker` block** (unconfigured): keep today's behavior — detect a `ENG`-style key (uppercase-alpha prefix + `-NNNN`) from the slug/branch/conversation at lower confidence. The config is never a hard requirement; absent it, degrade to detection, don't error.
- **Work under review**: Resolve from args, else the active session (log / plan / build reports / critiques / `IMPLEMENTATION_LOG`), else the working-tree diff, else the conversation. This is what the checkpoint is *about*—and it defines the exact file set that gets committed (§3).
- **Target ticket**: The `<PREFIX>-NNNN` key (prefix from § Tracker) from the session slug (example, prefix=ENG: `2026_07_02_ENG_2737_…` → `ENG-2737`), the git branch's **branch key**, or the conversation (text after `--` overrides). The **branch key** is a `/`-separated segment of the branch name that starts with `<prefix>-NNNN` or `<prefix>NNNN`, any case (`eng-2712-…` → `ENG-2712`, `writer/eng150-x` → `ENG-150`); in fallback mode (no § Tracker) only `<PREFIX>-NNNN` counts. **`<sessionDir>/.snapshot-autofiled` is read first.** It holds one JSON object per line, appended and never edited — `{"id", "state", "key", "branch", "sha", "files", "time"}`, where `state` is `pending`, `filed` or `spent` — and the last line for an `id` is that entry's state (§ *Unattended runs*, step 8). An entry is for this work when its `branch` is the current branch or is `-` (filed before any feature branch existed, so it applies to every run that reads the file), and nothing else is compared: not the sha, not the file set; `sha` and `files` are there for the person reading the line. An entry never selects the target ticket. It only blocks a re-filing: under `--yes`, a `pending` or `filed` entry for this work aborts the run before §2 and prints what it holds — a `filed` entry's `<KEY>`, or for a `pending` entry that no key was recorded — with both exits. The exits: re-run with `-- <KEY>` if this work is that ticket's, which retires a `filed` line, but the key may belong to another thread on this lane, so pass it only when this work is that ticket's own. For a `pending` line, a person checks Linear for an open ticket with the `auto-filed` label naming this branch or session, then clears the line by appending it as `spent`, or re-runs with `-- <KEY>` if one is found. Without `--yes`, a `pending` or `filed` entry for this work is asked about through one `AskUserQuestion` rather than aborting: use its `<KEY>` as the target, or proceed without it. A `spent` entry is recorded, not recomputed: it is appended when the commit carrying its key lands (§3 [1]) or when a `-- <KEY>` run retires it, and it never blocks a run again and never comes back. A real `-- <KEY>` is how a run reaches a ticket, and no entry blocks it: when it names a `filed` entry's key it retires that line, appending it as `spent` once the run's commit or comment carrying `<KEY>` lands, and when it names another key the entry is left as it is and §4 names it. So thread B landing on the same lane while thread A's auto-filed IDE-342 is still `filed` never posts to IDE-342 on its own: it aborts and prints IDE-342, and reaches a ticket only on a `-- <KEY>` re-run its caller chooses. Once A's entry is `spent`, B's commit range may carry IDE-342 as a single commit key, which aborts (below); otherwise B is un-ticketed work and goes through the duplicate search and the Linear backstop like any other. **A `-- <KEY>` argument is high-confidence** detection: it overrides the slug, branch and conversation keys and clears the branch-key ≠ slug-key flag. Only text after `--` is the argument — a bare key after `/snapshot --yes` with no `--` is not the argument; it is a conversation key. **`get_issue` it now** to read its **title, description (the intent/premise + any acceptance criteria), current state, team, and canonical branch name**. This is the *direction reference* the review checks against, and its snapshot is the base for the description read-before-write (§3). If detection is low-confidence (e.g., branch-key ≠ slug-key) or ambiguous, confirm the ticket via one `AskUserQuestion` before reviewing. **Under `--yes` there is no confirm left to ask with, so a low-confidence or ambiguous detection ABORTS the run and reports** — reviewing against a guessed ticket is how an update reaches the wrong issue. No key at all is neither: under `--yes` that work gets a ticket filed for it (§ *Unattended runs*). But a single key carried by the commits being snapshotted, with no `--`, is a low-confidence detection: under `--yes` it aborts rather than files.
- **Wrong-ticket cross-check:** Compare `get_issue`'s returned canonical branch name (`gitBranchName`) against the *actual current git branch* (`git branch --show-current`). What a mismatch means depends on whether the run has an **explicit ticket key**, and **the explicit key is the target**: the run has one only when the target from *Target ticket* equals the `-- <KEY>` argument or a key carried by the commits being snapshotted (a key in their subjects or trailers). The *commits being snapshotted* are `git log --no-merges origin/<default branch>..HEAD` — the remote default branch, never `@{u}`, which shrinks to the unpushed commits once `/pr` sets an upstream — excluding the commit §3 is about to draft: it carries the target by construction, so it cannot vouch for it. Their keys are read as a set. **With a `--` key, the commits' key set must contain the target or be empty**, or the run aborts under `--yes`; keys for other tickets in that set are only a warning, because a wave lane, or a lane stacked on another lane's branch, carries earlier tickets' commits. **Without `--`, two or more keys among the commits is ambiguous and aborts under `--yes`**, and a single commit key that is not the target aborts too (the reused lane below). The session's `.state.json` `tickets[]` corroborates and is never a source on its own: it is a watch list that keeps every thread's key, so a key that is only in `tickets[]` is not explicit, and a `tickets[]` that lacks the target is noted, never an abort. A lane branch (`runner/wave1b`, `writer/ide150-archetype`) never equals the canonical name, so the bare comparison cannot be the test when the key was stated. A trusted `--` typo (`-- IDE-331` meaning IDE-313, no keyed commits) posts to the real IDE-331: that is the cost of trusting the argument.
  - **Explicit key, branch is not the ticket's canonical one → WARN and proceed**, for a status-only run and a commit alike, with or without `--yes`. The §3 confirm header carries a branch-mismatch note; the commit records the branch in a `Snapshot-Branch: <branch>` trailer and the comment names the branch, so the ticket shows where the work actually sits.
  - **Explicit key, branch key names a different key → ABORT under `--yes`** (under a confirm: the prominent wrong-ticket warning). A branch key (*Target ticket* above) that is not the target names a different ticket: branch `ide-312-x` with key `IDE-313` aborts. This holds in fallback mode too: in fallback mode a hyphenated `<PREFIX>-NNNN` branch key still aborts, and only the unhyphenated lane-name forms warn (*Target ticket* counts only the hyphenated form there). A branch with no branch key, or whose branch key is the target (`writer/ide150-archetype` with `IDE-150`), is the warn case above.
  - **Explicit sources disagree → ABORT under `--yes`** (under a confirm: ask once, here in §1 before review, as for a low-confidence detection). The commit-key rule above fails: with `--`, the commits carry keys but not the target; without `--`, they carry one key other than the target, or two or more keys. A reused lane whose slug names `IDE-313` while its commits carry `IDE-312` aborts (no argument; the target is the slug's IDE-313, which the commits do not name).
  - **No explicit key → unchanged:** the key was inferred from the slug, the branch or the conversation (not after `--`), so a mismatch is **surfaced prominently in the §3 confirm header** even if no slug/branch-key conflict was flagged — a reused-branch key can silently point at the wrong issue — and **under `--yes` a mismatch ABORTS**; nothing posts to a ticket the run is not sure of. A stale `tickets[]` entry the conversation happened to name (IDE-150 from an earlier thread, on `runner/wave1b`) is this case: it falls to the no-explicit-key case and aborts under `--yes`.
  (The canonical branch name is also what §3 step [1] uses to branch off `dev`/`main`.)

- **Wave targets (only with `--wave` / `--rollup`):** for each target ticket, take its **project** from the `get_issue` you already made. Record the wave id and window start. With `--rollup`, `get_initiative({ query: "<initiative>", includeProjects: true })` now; not found → [7] will decline, the rest of the run is unaffected. Never `save_initiative`.

**Resolve the trail**: `<trailDir> = <sessionDir>/builds/`. Pick a `<slug>` once (kebab-case of the work). Before minting a fresh slug, `ls <trailDir>`—if an existing `<slug>_*.md` clearly matches this work (same chunk / ticket / topic), REUSE that slug so the trail clusters under one name. Only mint a new one for genuinely new work. Ledger/log appends (§3) use `engine log`.

Echo back one line: `Snapshotting <PREFIX>-NNNN "<title>" (state: <current>, branch: <branch>) from <work>; trail: <trailDir>/<slug>_SNAPSHOT.md.`

## 2. Review — spawn the reviewer subagent (active verify, read-only)

**When to skip the subagent:** If there is **no target ticket** (commit-only checkpoint) **and no runnable gate** for the work (e.g., docs / markdown / config with nothing to `tsc`/test/build), the reviewer is a near no-op. There's nothing to verify and no comment to draft. In that case, skip the spawn and do the commit **scoping inline** (identify the exact file set, classify CLEAN/MIXED via `git diff -- <path>`, propose the message), then go straight to §3. Otherwise, spawn the reviewer.

**Backgroundable & parallelizable.** This sub-agent dispatch is a composable building block: it can run in the background (`run_in_background: true`) so the orchestrator keeps working while it runs, and when the work splits into independent chunks, several such sub-agents can be fanned out in parallel and reconciled.

> **Before dispatching — `§CMD_LOG_SKILL_INVOCATION`**: log this dispatch to the session log (why + context-pack pointer + one-line re-tread) so a restarted session can re-tread it. Fire it as the last step before the `Task`/`Agent` handoff.

Spawn **one** subagent (a `general-purpose`/`analyzer`) to review the work, verify it, identify the exact commit file set, and draft the update. It does the verification + framing; **it never touches the tree**. You (the orchestrator) keep the thread and perform the commit + posts in §3. Build its prompt self-contained:

> You are drafting a historical CHECKPOINT for a ticket. Write it for a future engineer debugging a production outage caused by THIS exact code six months from now. Be dense, precise, and brutally honest about fragility. A tautological "aligned with intent, realizes the ticket as written" line is worthless padding. You VERIFY, FOLLOW THE DIRECTION, and FIND LEFTOVERS. You do NOT hunt for code bugs (that's a different skill) and you do NOT fix anything.
> - **Tracker config (resolved from CLAUDE.md § Tracker — the orchestrator fills these; you cannot read CLAUDE.md):** Linear (linear MCP) · issue-key prefix `<PREFIX>` (keys `<PREFIX>-NNNN`, branches `<prefix>-NNNN`) · team `<team>`. Use this prefix for the ticket key and in the commit message; do NOT assume `ENG`.
> - **Target ticket (the direction reference):** `<PREFIX>-NNNN` — intent/premise: `<from get_issue description>`; acceptance: `<if stated>`; current state: `<state>`; branch: `<current branch>` (canonical: `<gitBranchName>`, or "same").
> - **Work under review:** `<scope + concrete pointers: session artifacts / git diff cmd / build+critique reports / conversation digest>`.
> - **READ THE FULL ARTIFACT TRAIL FIRST — not just the diff, but SCOPED to this work's `<slug>`.** Before judging, read the COMPLETE trail for THIS work. It carries the decisions, critiques, verdicts, and rationale a diff can't show, and grounds the On-direction / Verified / Leftovers / Decisions&rationale / Risks review in everything that happened:
>   - In `<trailDir>` (`<sessionDir>/builds/`) read THIS work's `<slug>_*.md` — its `_BUILD.md`, `_CONTEXT_PACK.md`, `_CRITIQUE.md`, `_FIX.md`, `_EXPERIMENT.md`, `_TICKETS.md` — PLUS the session artifacts (`*_LOG.md`, the plan, `DIALOGUE.md`) and `LESSONS.md`. A `<slug>_TICKETS.md` (written by `/ticket`) means a leftover was **already captured as a filed followup** — don't re-list it under Leftovers. In a long session, `builds/` holds many unrelated slugs; only SKIM other-slug artifacts if directly relevant — never read the whole dir indiscriminately.
>   - Full context IN → a tight distilled status OUT (the comment stays tight, TL;DR on top — the trail makes the status far richer than the diff alone; it does not bloat the comment).
> - **READ-ONLY VERIFICATION — this is a hard fence.** Run ONLY non-mutating gates (`tsc --noEmit`, unit tests, `build`/`lint` — e.g., `cd packages/X && npx tsc --noEmit`, `yarn workspace @acme/X test`). NEVER run `db:reset`/`db:migrate`/`db:seed`, e2e/integration suites needing live services, or anything hitting a real/prod DB or network mutation. NEVER `git add`/`commit`/`push`/`stash`/`checkout` or otherwise touch the working tree — it is expected to be dirty; **leave it exactly as found**. Delete any coverage/artifact you generate. If the only gate is destructive, DON'T run it — report "not verified (gate is destructive)". Report exact commands → exact results; never assert a green you didn't see.
> - **Detect SUPERSEDED CLAIMS on the ticket:** Read the ticket's existing comments (`list_comments`). Does this work FALSIFY something an earlier comment asserts as fact — a measurement, a page/entity map, a count, a root cause, a "this is the hard part" framing? A prior comment is read as ground truth by whoever picks the ticket up next, so a stale one costs more than a missing one. Name each: the claim, where it lives (comment date), and what replaced it. Only genuine contradictions — work that merely ADDS to an earlier comment supersedes nothing.
> - **Check ON-DIRECTION:** Is the work aligned with the ticket's intent/acceptance? On track / drifted (say how + why) / re-scoped. This is the core judgment.
> - **Detect LEFTOVERS & followups:** What is unfinished, deferred, or open (plan/acceptance items not done, skipped tests, critique findings not yet addressed, TODOs)? Distinguish real leftovers from intended non-goals. These are guidance, not work to do.
> - **Identify the COMMIT file set, classify each file CLEAN vs MIXED, + propose a message (you do NOT commit).** From the work under review, list the **exact files** that belong to this checkpoint (relative paths). The tree is dirty with parallel-agent churn, so name only this work's files, never a wildcard. **Classify each with `git diff -- <path>`:**
>   - **CLEAN** = the file carries ONLY this work's changes.
>   - **MIXED** = the file also carries hunks *outside* this work (unrelated parallel churn).
>   This matters because `git add -- <path>` stages the WHOLE file. A MIXED file would drag its churn into the commit. The orchestrator whole-file-stages CLEAN files and SURFACES MIXED files to the user for a per-file decision. It NEVER patch-stages, stashes, or unrolls to split a file. Propose a conventional commit message `type(scope): <PREFIX>-NNNN <summary>` matching the repo's `git log` style; when the orchestrator says the branch is not the ticket's canonical one, end it with a `Snapshot-Branch: <branch>` trailer and put a `**Branch:** \`<branch>\`` line under the comment's TL;DR. The ORCHESTRATOR stages and commits after the user confirms — you never touch git.
> - **Draft the status comment** using the section palette below. Keep a tight **Status + TL;DR always on top** (with a `Covers:` line for the window this update spans), then add as much detail as the work warrants. Headers + bullets keep a big comment scannable; big is fine, padding is not. Include-if-present: skip a section rather than write "none".
>   - **ALWAYS-ON:** `Status / TL;DR` (+ `Covers:` window) · `On-direction` (aligned / drifted-because) · `Verified` (what you ran → result) · `Confidence & fragility` (where it will break first) · `Leftovers & followups` (guidance for the next person/agent).
>   - **INCLUDE-IF-PRESENT:** `Supersedes` (an earlier comment's claim this work disproved — quote it, then state what replaced it and the evidence; a correction the next reader will hit BEFORE the stale claim) · `What the diff doesn't show` · `Hurdles & mismatches` · `Findings` · `Results / evidence` (concrete numbers) · `Decisions & rationale` (key choices + WHY) · `Risks / watch-outs` (done-but-watch, distinct from leftovers) · `Links` (PRs / commit / session / build-reports).
>   - **Commit SHA sentinel:** Anywhere you reference the checkpoint commit (TL;DR "Committed …", `Verified` "Checkpointed as …", `Links` "commit …"), write the literal sentinel `{{COMMIT_SHA}}` — never invent a SHA. The orchestrator substitutes the real short SHA after committing, or STRIPS the whole commit claim if no commit lands (§3 scrub).
> - **Propose a status transition** if the work implies one (`<current>` → `<suggested>`) with a one-line reason. If it doesn't, say "no state change." **Read `<current>` from `get_issue`, not from the session's memory of it** — a parallel lane may have moved it, and a ticket often never left the state it was FILED in. Propose from wherever it actually sits:
>   - **Not-started** (Backlog / Todo / Triage) **with work landed** → the state the work reached (In Progress / In Review / Done). A ticket whose work is finished while it still reads Backlog is the most common drift, not an edge case — never leave it because "it was never In Progress."
>   - **In Progress** → In Review / Blocked / Done.
>   - **Terminal already** (Done / Canceled / Duplicate) → no state change; note it if the work contradicts the close.
>   - Ground the target in what SHIPPED, not what compiles: work on an unpushed branch with no remote is at most In Review, whatever the acceptance says. Match the state sibling tickets on the same branch carry.
> - **Assess DESCRIPTION drift:** Has the ticket's premise / scope / acceptance MATERIALLY changed (not just progressed)? If NO → no description edit. If YES → draft the **single complete final description body**: the evergreen rewritten text PLUS a `## Change history` section containing **every prior entry copied verbatim** + one new appended line `- <YYYY-MM-DD>: <what changed> (<why>)`. The description is a full-field replace — a body missing any prior entry erases history, so carry them all. Never rewrite for routine progress.
> - **Wave health signals (only when the orchestrator says the run carries `--wave`):** fill PART 5 of the template — per target ticket its project, and the four signals in the exact vocabulary there (gates `green|red|unrun|none`, direction `aligned|rescoped|drifted`, blocked `yes|no`, open MUST-FIX as a number) plus a one-line cold-readable TL;DR. Write `unknown` for any signal you could not establish. You report signals; you do NOT pick a health.
> - **Return contract:** WRITE the draft to `<trailDir>/<slug>_SNAPSHOT.md` using the template (in THIS skill's `assets/TEMPLATE_SNAPSHOT.md` — the orchestrator gives you its base dir; **do not hardcode `~/.claude`**): the commit proposal (message + staged file list with each file classified CLEAN/MIXED + branch), the comment (rendered Markdown, using the `{{COMMIT_SHA}}` sentinel for any commit reference), the status proposal, and the description proposal (single full body, or "no drift"). Then return a 4–6 line summary: the proposed commit message + file count, the proposed state change, whether a description edit is proposed, and the headline status.
> - Do NOT: fix code, file tickets, commit, push, or move the ticket yourself — you draft; the orchestrator commits + posts after the user confirms.

Background is available (`run_in_background: true`) and relaying the summary when it lands still applies — but this step **commonly runs foreground**, since §3's confirm needs the reviewer's draft in hand right after. Run foreground when you need the result inline for the next step.

## 3. Calibrate, commit & post (single batch confirm)

> **HARD RULE — NO GIT GYMNASTICS (top-line safety constraint).** The orchestrator NEVER stashes, `git checkout`/`git restore`s, reverts, or temporarily removes ANY change (its own or a parallel agent's) to "clean up" a commit with intent to restore it later. That unroll-then-restore dance is HIGH-RISK and can silently lose a parallel agent's uncommitted work. It NEVER `git add -p` / patch-stages / surgically splits hunks. The **only** working-tree/index operation it may perform is `git add -- <clean path>`. If the reviewed work cannot be committed by whole-file staging of CLEAN files alone, the orchestrator **SURFACES the situation and lets the USER decide** — it does not manipulate the tree or index to force a clean commit.

1. **Relay** the draft: the proposed commit (message + file list *with each file's CLEAN/MIXED classification* + branch), the TL;DR, the proposed state change, and whether a description edit is proposed. Render the comment body in chat (or a tight digest + the trail link if very long).
2. **Batch confirm** (`AskUserQuestion`, MANDATORY unless `--yes` waived it — this both mutates the tree and posts outward; the waiver's two declined actions and three aborts are stated in § *Unattended runs* above). The header renders the **ticket title + current state** — and, on a §1 wrong-ticket cross-check mismatch (a branch key naming a different key, or any mismatch with no explicit key), a **prominent wrong-ticket warning** (not just the number); with an explicit key on a non-canonical branch, a one-line branch-mismatch note naming the branch instead (disagreeing sources were already asked in §1, before review): **"Post to `<PREFIX>-NNNN` '<title>' (In Progress)?"**. Present ALL proposed actions together, up to four (plus [6] / [7] when `--wave` / `--rollup` is set). Each is **BEST-EFFORT and independent** (step 3):
   - **[1] Commit** — the proposed message + the staged file set (each file shown **CLEAN** = will stage, or **MIXED** = also carries churn outside the work) + the target branch. The commit action offers, **regardless of gate color**: **commit as proposed / edit message / edit the staged file set / skip the commit (post update only)**.
     - **MIXED files are never auto-split, stashed, or unrolled.** Per mixed file, the user chooses: **commit the whole file as-is (churn included — explicitly flagged here)** / **skip that file (checkpoint only the clean files)** / **defer the whole commit**. Default suggestion: **skip the mixed file**, commit the clean ones — the user can override.
     - **Green gate:** If the §2 verify gates were **red or unrun**, the confirm SAYS SO. "Skip the commit (post update only)" is a **first-class** choice at any gate color; committing red work is an explicit opt-in.
   - **[2] Comment** — the rendered body, plus any **ready evidence to attach** (screenshots/artifacts the agent already has in hand — see step 3 [2b]; "none" if there are none), and — **on a closing snapshot** (Done transition or session wrap-up) — **+ session debrief attached** (see step 3 [2c]; shown as "no debrief yet — skipped" when none exists).
   - **[3] Status move** — `<current>` → `<suggested>`, or "none".
   - **[4] Description edit** — the single full body incl. `## Change history`, or "no drift".
   - **[6] Project update(s)** *(only with `--wave`)* — per touched project: the rendered body, the health with its source (derived + the rule's reason, or `underivable` → **pick onTrack / atRisk / offTrack, or skip this project**), and create vs edit-in-place (with the id) vs decline (with the reason and the conflicting ids).
   - **[7] Initiative roll-up** *(only with `--rollup`)* — the rendered body, its health, the source update ids, and each override as `<project>: <was> → <now> — <reason>`; or "declined — no posted project updates for this wave".
   → **Post all / Edit one first / Cancel.** On "Edit one first", ask which (commit / comment / status / description / project update / roll-up), loop to it, and re-present the confirm.
3. **On Post all, execute the four actions in order — commit FIRST, then comment → status → description** — then, when flagged, **[6] project update(s) → [7] initiative roll-up** (the roll-up reads what [6] and the workers posted, so it goes after) — then a final **[5] notify** of local siblings — so a landed commit SHA can be embedded in the comment and summarized in the notify. **The four actions are BEST-EFFORT and non-atomic:** attempt each; a failure or skip in ONE does NOT abort the others. **Never CLAIM an action that didn't happen** — do what lands, report honestly (step 4).
   - **[1] Commit (orchestrator only — the subagent never commits):**
     - **Skip** entirely if the user chose skip-the-commit, or if all reviewed files were mixed→skipped. A skipped or failed commit routes through the **commit-claim scrub** (below) but the other three actions still run.
     - **Branch safety:** Under a [0] auto-file it runs after [0], not here, because the key the branch name needs does not exist before [0]: stage, inspect, re-check, then [0] files the key, then Branch safety names the branch from the new key (its `get_issue`), then commit. Otherwise: if on the default branch (`dev` or `main`), create the feature branch FIRST using the **canonical branch name from `get_issue`** (§1), falling back to `<prefix>-<ticket>-<slug>` only if absent; then commit. **If branch creation FAILS → ABORT the commit and report — NEVER commit onto `dev`/`main`.** Off the default branch, commit on the current branch (surfaced in the confirm).
     - **Stage ONLY the CLEAN reviewed files** — `git add -- <exact path> <exact path> …` (plus any MIXED file the user explicitly approved *whole*). **NEVER `git add -u` / `-A` / `.`**, and per the HARD RULE **never `git add -p` / stash / checkout / restore / revert** — this repo's tree is always dirty with parallel-agent churn (CLAUDE.md rule).
     - **Inspect the staged CONTENT before committing:** Run `git diff --cached` (or `--stat` + hunk count) and render it in the relay/confirm so the user approves the actual STAGED CONTENT, not just a file list. **Eyeball it — if anything unexpected is staged, STOP and re-surface** (do not silently commit).
     - **Green re-check (TOCTOU):** After staging, before commit, re-run the NARROWEST relevant §2 gate on the workspace when cheap (e.g., `cd packages/X && npx tsc --noEmit` — re-running a gate is read-only, allowed, and NOT git gymnastics). If not feasible, stamp the verify time in the confirm ("green as-of <time>; files may have changed since").
     - **[0] Auto-file — `--yes` on un-ticketed work only (§ *Unattended runs*, step 8):** here, after the staged-content check and the green re-check and before the commit, append the `pending` line, call `save_issue`, and append the `filed <KEY>` line the moment it returns, with `branch` set to the current branch, or `-` on `dev`/`main`; every check that can abort has run by now. On `dev`/`main`, Branch safety then runs (its bullet above says why it waits) and names the new branch from the new key, and a `filed` line bound to that branch is appended. When the commit carrying the key lands, append the `spent` line. When [1] is skipped (red or unrun gates), [0] still runs at this point in the order, before [2], and the entry stays `filed`, so the next run for this work aborts and prints `<KEY>` (§1).
     - **Commit** with the approved message `type(scope): <PREFIX>-NNNN <summary>` (see `git log --oneline -5` for style), ending with **the environment's required commit trailer** — the `Co-Authored-By:` line the harness/repo prescribes (do NOT hardcode a model name/version; use whatever the current environment specifies). Do NOT push (unless the user asked).
     - Capture the short SHA: `git rev-parse --short HEAD`. Substitute it for the `{{COMMIT_SHA}}` sentinel in the comment's TL;DR / `Verified` / `Links` slots before posting.
     - **Commit-claim scrub — when the commit is SKIPPED or FAILS:** Before posting the comment, STRIP every commit claim from the body. Remove the TL;DR "Committed …" clause, the `Verified` "Checkpointed as …" line, and the `Links` commit entry (or replace it with "commit: not committed"). **Guard: NEVER post a comment body still containing an unresolved `{{COMMIT_SHA}}` sentinel — if one remains, STOP.**
   - **[2] Comment** → Post the **reviewer-rendered comment body VERBATIM** (from `<trailDir>/<slug>_SNAPSHOT.md` / the §2 relay) **through `§CMD_POST_TICKET_COMMENT`** — the canonical subscribe-check → `save_comment({ issueId: "<PREFIX>-NNNN", body })` → notify atom (its step 3 IS the [5] notify below, so the sibling-notify rides with the post). The orchestrator does NOT re-render or rewrite the body. The ONLY mutations allowed are substituting the `{{COMMIT_SHA}}` sentinel with the real short SHA, or scrubbing the commit-claims when no commit landed (per the scrub rule above).
   - **[2b] Attach ready evidence** (rides with the comment, if approved) → If — and ONLY if — the agent already has supporting evidence **in hand from this run**, attach it to the issue after the comment posts. Qualifying: **screenshots / images** the agent captured (UI screenshots, overlay or diagram images, a chart) and **well-made standalone artifacts** that back the checkpoint (an evidence doc, an important report, or a writeup — e.g. from `/writeup` or `/analyze`). **Do NOT attach internal process artifacts** — the `*_LOG.md`, `DIALOGUE.md`, the plan, or the build-trail reports (`*_BUILD.md`/`*_CRITIQUE.md`/`*_SNAPSHOT.md` etc.; those already ride as `Links` in the comment) — and **never fabricate a screenshot**; attach only what genuinely already exists. *(The session **debrief** is the ONE deliberate exception, and only on a closing snapshot — see [2c]; everywhere else it stays a process artifact and is not attached.)* Attach to `issueId: "<PREFIX>-NNNN"` via the Linear attachment flow (`prepare_attachment_upload` → upload the bytes → `create_attachment_from_upload` for a local file; or `create_attachment` for a URL — load schemas via ToolSearch `linear`). Best-effort like the other actions — an attach failure is reported, it never aborts the commit/comment/status/description.
   - **[2c] Attach the session debrief — closing snapshot only** (rides with the comment, if approved) → On a **closing** checkpoint — EITHER the [3] status move is into a **terminal / Done (closed) state**, OR this snapshot is the **session's wrap-up** (a closing update, signaled by an existing session debrief = the session has synthesized) — attach the **session debrief** to the issue as its permanent record. **Resolve the debrief:** the `#needs-review`-tagged synthesis artifact in `<sessionDir>` (`IMPLEMENTATION.md` / `DO.md` / `ANALYSIS.md` / `FIX.md` / the active skill's debrief) — **NOT** a `*_LOG.md`, `DIALOGUE.md`, or the plan. **No debrief present** (snapshot ran mid-work, before synthesis) → **SKIP with a one-line note** ("no debrief yet — attach skipped"); never fabricate one or substitute the raw log. **Not a closing snapshot** (routine in-progress checkpoint) → skip silently — mid-work updates stay comment-only. Attach to `issueId: "<PREFIX>-NNNN"` via the same Linear local-file flow (`prepare_attachment_upload` → upload the bytes → `create_attachment_from_upload`; load schemas via ToolSearch `linear`). Best-effort like every other action — an attach failure is reported, it never aborts the commit/comment/status/description. This is the deliberate exception to [2b]'s no-process-artifacts rule: on a close, the debrief IS the evidence.
   - **[3] Status** (if approved) → `save_issue({ id: "<PREFIX>-NNNN", state: "<name-or-type>" })` — **`id` is REQUIRED**; a `save_issue` with no `id` CREATES a new issue. Resolve the state via `list_issue_statuses` (needs `team` from §1) if needed.
   - **[4] Description** (if approved) → **Re-`get_issue` immediately before posting** (TOCTOU) and re-read the CURRENT description (not the §1 snapshot). Copy its `## Change history` block unchanged, append the single new line, and assemble the full body. **If the current description differs from the §1 snapshot the draft was built on → STOP and re-surface**, don't clobber. **If the assembled body does not contain every prior `## Change history` entry → STOP, do not post.** Then `save_issue({ id: "<PREFIX>-NNNN", description: <full assembled body> })` — a full-field replace.
   - **[6] Project update(s)** (if approved; `--wave` only) → For each project, decide **after** [1]–[4] ran: a project whose ticket had nothing land is not touched — skip it. Re-read the window **immediately before posting** (`get_status_updates({ type: "project", project, createdAt: <window start> })` — TOCTOU, since a sibling lane may have posted since the confirm), feed it with this ticket's lane (PART 5 signals + TL;DR + the real short SHA if [1] landed + the state move if [3] landed), `since` (the wave start), `unattended: true` under `--yes`, and `confirmed` (the action, id and health shown at the confirm) to `wave-update.mjs project`. Map each Linear update to `{id, body, health, createdAt}`. Act on its answer:
     - **`reconfirm: true`** (what would post now differs from what the confirm showed — another lane merged in, create became edit, the health moved) → re-present that project's [6] with the `drift` named and post only on a fresh yes. Under `--yes` the renderer has already turned this into a decline, which is reported with `wouldHavePosted`.
     - **create** → re-read the window once more **immediately before** creating and re-run the renderer; if the answer is no longer create, act on the new one. Then `save_status_update({ type: "project", project, body, health })`, and **re-read after creating**: if this wave now shows two of ours, run the renderer again with `selfId: <the id just created>` — it answers **edit** on the earliest with both lanes' sections merged, `retire: [<own id>]` and `repair: true`. This repair call proceeds under `--yes` too: it is a mechanical merge of this run's own create, not a new choice, so the renderer does not hold it to the confirmed `create`. **Order it: post the merge edit first, re-read the canonical update and confirm it now carries this lane's section, and only then `delete_status_update` the own duplicate.** If the edit fails or the re-read does not show the section, do not delete — report both updates. Only ever delete the `selfId` this run created; another lane's duplicate (`duplicates`) is reported, never deleted.
     - **edit** → `save_status_update({ type: "project", id, body, health })`.
     - **decline** → post nothing, report the reason.
     The body is posted **verbatim** from the renderer. Capture each returned id + URL. Best-effort per project: one failure never aborts another.
   - **[7] Initiative roll-up** (if approved; `--rollup` only) → Re-read every attached project's updates in the window and the initiative's own (`get_status_updates({ type: "initiative", initiative, createdAt })`), map each to `{id, project: <its parent project's name exactly as get_initiative lists it>, url, health, body, createdAt}`, and feed them with `since`, the overrides, `unattended` and `confirmed` to `wave-update.mjs rollup` (`reconfirm` / drift are handled as in [6]), then: post each override edit first (`save_status_update({ type: "project", id, body, health })`), then **create** / **edit** the initiative update (`save_status_update({ type: "initiative", initiative | id, body, health })`), or on **decline** post nothing. Overrides are posted only from an explicit `--override` (or one chosen at the confirm) — never inferred. A non-empty `declined` (an override that matched no update, had no reason, or met a body the renderer did not write) is reported as a failed action under `--yes`, and shown at the confirm otherwise. On a roll-up **decline**, the override edits do not post either.
   - **[5] Notify local siblings** → This is **step 3 of `§CMD_POST_TICKET_COMMENT`** — when [2] posted a comment through the atom, the notify already rode with it; this step just ensures it fires ONCE whenever anything landed (a commit/status/description with no comment still warrants a wake). Fire `engine ticket notify <PREFIX>-NNNN "<decision-grade note>"` to wake every *other* local session subscribed to the ticket (per `~/.claude/.directives/AGENTS.md` §"Notify when you post a ticket comment"). `notify` auto-excludes this session (pass `--from <this-session>` to make it explicit). On wake a sibling drains ONLY this note — no Linear fetch — so make it decision-grade: the **real short SHA from [1]** if a commit landed (the actual SHA, NEVER the `{{COMMIT_SHA}}` sentinel), the **one-phrase what-changed**, and an **affects-you verdict** (`no action` / `rebase onto <sha>` / `your files untouched` / `needs your reply`). Example (prefix=ENG): `engine ticket notify ENG-2833 "2db0ecea6: entities/ scaffold committed; scope.ts left for ENG-2737 — no action for you"`. Fire whenever a target ticket exists AND anything landed (commit and/or comment/status/description). **Skip** when there is no target ticket, when nothing landed, or when running solo (no sibling sessions to wake). It is a **local dirty-flag, not an outward post** — so it needs no separate confirm and is best-effort: a `notify` failure is reported, never aborts anything.
   Capture the commit SHA (if any), the comment URL + the issue URL.
4. **Report + trail.** Stamp the draft's Outcome with EXACTLY what landed per action — each of **committed `<sha>` on `<branch>` | comment `<url>` | status moved | description updated** marked **done / skipped / failed** — and hand back any un-posted artifact for manual retry. Never stamp an action that didn't land. **With `--wave` / `--rollup` it also stamps each project update and the roll-up (created / edited / declined + reason) with its URL and health. Under `--yes` the Outcome also names the flag and every action it declined** — the skipped commit over red or unrun gates, the skipped description rewrite with its drafted body handed back — because whether a human approved this checkpoint is a fact the posted comment cannot carry. Link it (`§CMD_LINK_FILE`). ## Constraints
- **HARD RULE — no git gymnastics.** The orchestrator NEVER stashes, `git checkout`/`restore`s, reverts, patch-stages (`git add -p`), or temporarily removes any change to force a clean commit. That unroll-then-restore dance can silently lose a parallel agent's uncommitted work. The ONLY working-tree/index op is `git add -- <clean path>`. If the clean files alone can't form the commit, SURFACE it and let the USER decide; never manipulate the tree/index to force it.
- **Not `/scrutinize`.** It verifies the *direction*, the *claims*, and the *leftovers* — it does not hunt for code bugs or fix anything. A bug it happens to notice is a leftover/risk line in the comment, not a repair.
- **Verify, don't assert.** "Done" claims are confirmed by RUNNING the gates and cross-checking the diff — never taken on faith. A gate that couldn't run (or is destructive) is stated as such, not reported green.

- **Correct the record, don't just add to it.** A checkpoint reads the ticket's existing comments and says so when this work DISPROVED one of them. An earlier comment is ground truth to whoever picks the ticket up next; leaving a falsified measurement or page-map standing under a newer comment that never mentions it sends the next reader to build the wrong thing. Supersede in the new comment (quote the claim, state what replaced it) rather than editing the old one — the history of being wrong is worth keeping.
- **Read-only verify subagent.** The reviewer runs only non-mutating gates and NEVER touches the working tree (no `git add`/`commit`/`stash`; no `db:reset`/`migrate`/`seed`; no e2e/live-service suites). The **commit is strictly an orchestrator action** after the confirm.
- **Scoped commit, clean vs mixed, gated on green.** Stage ONLY the CLEAN reviewed files with `git add -- <path>` — never `git add -u`/`-A`/`.`. MIXED files (carrying churn outside the work) are SURFACED to the user per file (commit whole as-is / skip / defer), never auto-split. Before committing, review `git diff --cached` so the user approves actual staged content, and re-check the narrowest gate (TOCTOU). Branch-first on `dev`/`main` using the canonical branch name (abort the commit if that fails). Message `type(scope): <PREFIX>-NNNN …` + the `Co-Authored-By` trailer. Only checkpoint green work by default; **"skip the commit (post update only)" is always a first-class choice**. No push unless asked.
- **Notify siblings after a ticket update.** Once the ticket-facing actions land, fire `engine ticket notify <PREFIX>-NNNN "<decision-grade note>"` so other local sessions subscribed to the ticket wake — a local dirty-flag, not an outward post, so it needs no confirm and is best-effort. This operationalizes `~/.claude/.directives/AGENTS.md` §"Notify when you post a ticket comment" at the exact operative step: the general directive states the rule; a linear skill run reads its numbered steps and would otherwise skip a free-standing directive, so the notify is embedded here where the miss happened. Skip when running solo (no siblings) or when nothing landed.
- **Four best-effort actions, honest outcome.** Commit + comment + status + description are attempted independently under one confirm; a failure or skip in one NEVER aborts the others. A skipped/failed commit is scrubbed from the comment (no "Committed …", no unresolved `{{COMMIT_SHA}}`) and the rest still post. The Outcome stamps exactly what landed per action (done / skipped / failed) — never claim an action that didn't happen.
- **Attach ready evidence, not process artifacts.** When the agent already has supporting screenshots/images or a well-made standalone artifact (evidence doc, important report, writeup) in hand, attach it to the ticket alongside the comment (under the batch confirm, best-effort). NEVER attach the session log/plan or build-trail files, and never fabricate a screenshot to fill the slot.
- **Attach the session debrief on a closing snapshot.** On a closing checkpoint — a status move into a terminal/Done state, or a session wrap-up (an existing `#needs-review` debrief means the session synthesized) — attach the session **debrief** (the synthesis artifact, e.g. `IMPLEMENTATION.md`/`DO.md`/`ANALYSIS.md`, NOT a `*_LOG.md`) as the ticket's permanent record, under the same batch confirm, best-effort. No debrief present → skip with a note (never fabricate or substitute the log). Routine in-progress checkpoints stay comment-only. This is the sole, deliberate exception to the "no process artifacts" rule above.
- **Building block.** It reports + commits the checkpoint + updates the ticket; it never fixes code or files followups. Leftovers are guidance.
- **Description edits only on material drift**, single full body carrying **every prior `## Change history` entry verbatim** + one new line, with the current description re-read immediately before the full-field replace (never clobbered, never partial). Routine progress → comment only.
- **`save_issue` always carries `id`**, except the one § *Unattended runs* auto-file, which creates the ticket. Anywhere else a missing `id` creates a duplicate ticket — pin `save_issue({ id: "<PREFIX>-NNNN", … })` and `save_comment({ issueId: "<PREFIX>-NNNN", body })`.
- **One batch confirm before any commit or outward post.** Nothing auto-commits or auto-posts; the user sees all up-to-four actions (commit + comment + status + description) together and approves the set (or edits one). **`--yes` waives that confirm and only that confirm**, for a caller that has already decided: the commit over red or unrun gates and the description rewrite are declined rather than assumed, target-uncertainty aborts stand where those questions would have, and every hard stop is intact (§ *Unattended runs*).
- **Thorough, with a tight TL;DR on top.** Big comments are welcome; a skimmer/reviewer-agent must still get the gist from the first lines. No padding; skip empty sections.
- **Wave updates: one per project per wave, health derived or declined, roll-up from posted updates only.** Project and initiative status updates post only under `--wave` / `--rollup`, under the same batch confirm (or `--yes`). A sequential retry or second lane edits the wave's update by id, a concurrent double create is repaired by the later lane, another wave's update is ignored, and an unmarked update in the window declines rather than double-posts. What posts must match what was confirmed, or it is re-asked (declined under `--yes`). A manager's override survives worker re-posts until a lane gets worse than what it ruled on, and then it visibly lapses. An underivable health is picked by a person at the confirm or declined under `--yes` — never guessed. A roll-up with no posted project update under it is not drafted. A manager's override is written into the worker's update body. The skill never creates an initiative. All of it is decided by `assets/wave-update.mjs`, not hand-written.
- **Lightweight + sessionless.** Runs within the active session — review → confirm → commit + post, then stop.
