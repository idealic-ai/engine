Read the state the work is in, and run the sequence of moves that advances it — clearing first, new work last, under one consent.

# /next Protocol (The Cold Entry)

[!!!] This is a **sessionless utility** skill. No session directory of its own, no logging, no debrief — the same pattern as `/inbox-next` and `/inbox-post`. It reads sources that already exist and adds no durable store (`§INV_NEXT_INVENTS_NO_STORE`), **with one exception the operator ruled**: documentation signals that have no channel to go to yet are held in `<sessionDir>/NEXT_DOC_SIGNALS.tsv` until one exists (§ *Documentation signals*).

## What this is and who it is for

**For whoever just sat down.** A person returning after a gap has no live loom and no idle session, so neither state-reading router in the engine will answer them: `§CMD_PRESENT_NEXT_STEPS` states its own prerequisite as `lifecycle=idle` — it runs only after a session closes — and `/loom`'s loop gate presents *"after each unit of progress"* and opens with *"The loom is running. What next?"*. **The one thing this skill adds is an entry that works when neither of those holds.**

*   **It is** the **join plus a precedence rule**. Every state it reads is read somewhere already; nothing in the engine reads them *together* and orders them, and the ordering is the only part that is judgement rather than sequence.
*   **It is NOT a router of its own invention.** Three of its routes are conditions `/loom`'s loop gate already declares, under a pool mechanism that is itself a declared rule (`§INV_LOOM_GATE_SURFACES_BY_RELEVANCE`): the stalled-lane sweep (`§INV_LOOM_STALL_IS_SWEPT_NOT_SENSED`), the fork pass and the board fold (`§INV_LOOM_SURFACES_FORKS_UNASKED`, `§INV_LOOM_A_FORK_ARRIVES_DECIDABLE`), and the *"Pull more work"* offer that already reaches for `/groom` and `/inbox-next`. **Each is cited by its rule name or by the offer's own label, never by line number** — that file is edited often enough that a line cite rots within the day, measured. **Those conditions are borrowed BY CITATION and restated nowhere in this file** — a citation cannot drift the way a copy does, and "a second thing to keep in step" is the whole objection this skill has to survive. So each rule above is named and followed at its own definition site; where a reading is in question, that site is the authority and this file is not.
*   **Only one reading here is this skill's own**: the state of the working tree, specified properly below because nothing else specifies it. Measured in `skills/loom/SKILL.md` against a `snapshot` control that fires: `uncommitted` → 0 and `working tree` → 0. **The wave half of that route is no longer this skill's**, and the honest reading changed under it — `§INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY` has since landed in that file and now owns bringing a wave's trees back together, so this skill cites it rather than claiming the gap. What remains unspecified anywhere else is the **dirty-or-ahead tree reading**, and that is the only part asserted as new here.
*   **It is NOT a conductor.** It mints no lanes, keeps no ledger, and holds no partition. The moment it dispatches its own workers it has become a second conductor, which is the shape the standing *extend-`/loom`-do-not-fork-it* decision is aimed at and the falsifier that would retire this skill into `/loom`.
*   **It is NOT a clusterer or a ranker** (`§INV_NEXT_BORROWS_THE_GROUPING`). `/groom` owns grouping work into topics; `engine project next` owns the order of open work. Two rankings of the same work drift apart and a reader cannot tell which one they are looking at — `skills/groom/SKILL.md:20` records that exact failure for the pair that already exists, and a third ranking is the same bug.
*   **It writes nothing.** No code, no tracker row, no git object, no status, no assignee. Every mutation happens inside a composed skill under that skill's own confirm. Documentation signals are posted by `/inbox-post`, not by this skill. The one file this skill writes itself is the held-signals file, and only inside an accepted plain run or an `all` run (§ *Documentation signals*).

## `/next` vs `/groom` vs `/inbox-next` — the one place all three are stated together

Three skills answer three different questions, and the words people type do not separate them, so the precedence is written down rather than left to whichever file the reader opened:

*   **`/inbox-next`** answers *which ticket do I pick* — it ranks a project's open work and routes one item into `/implement`, `/fix`, `/brainstorm` or `/ticket`. It owns **`pick my next ticket`**, in that phrase's narrow sense: one ranked item out of a project's open work, asked for as one item.
*   **`/groom`** answers *what is the batched shape of everything open here* — it drains the inbox, the open tickets and the un-ticketed leftovers, clusters them into topics across all of those, disposes each topic once, and hands each to a loom as one thread. It owns the **batched framing** — *what is open here*, *batch up the related tickets* — and it **composes** `/inbox-next` for the ranking rather than re-deriving it.
*   **`/next`** answers *what is in the way, and what do I do once it isn't* — it reads the states that block a return, clears them in order, and carries on to new work in the same run. The clearing moves are frequently not tickets at all. It owns the **front-door phrases**: **`what's next`**, **`what should I work on`**, **`what is blocking me`**, **`where did we leave off`**. It **composes both of the above**, and ranks and clusters nothing itself.

**Why the front door is here and not on the picker.** This is the only one of the three that can answer the question *wrongly asked*. Someone typing *what's next* when the real obstacle is a lane that stopped without handing back, an unanswered fork, or finished work sitting uncommitted gets routed to the obstacle rather than handed a ticket to start — and the ticket they would have been handed was never the answer to what they asked. The picker is right about the question it was asked and cannot tell that it is the wrong one.

⚠️ **The cost of that, stated rather than hidden, because it is the strongest case against the arrangement.** This skill is the **least-proven surface of the three** and the words now arrive here first: it has had **two live runs**, and its own acceptance signal — that a run the operator *declines* dispatches, commits, files and transitions nothing — **had never been demonstrated** when the allocation was made. Those two facts are the whole of the claim; no comparison of the three skills' ages supports it, and one stated here was withdrawn when git put all three files' first commit on the same day. **The falsifier is exactly that** — and it is the plain run's, since `/next all` has no proposal to decline (IDE-236): a declined plain run that nonetheless writes something retires this allocation and sends the words back, because a front door has to be the surface that is safest to enter. Every write-free guarantee above (`§INV_NEXT_PROPOSES_NEVER_DECIDES`, the composed-skill confirms) is load-bearing for the allocation and not only for the run.

**`/sweep` borders this skill, and the boundary is stated here and in `skills/sweep/SKILL.md`.** `/sweep` answers *what does this one living loom know that nobody wrote down* — its own registers, logs and live context — and fires before a hand-over or on demand. `/next` reads a loom's *state* (stalled lanes, open forks, a dirty tree) to order the moves; it does not look for decisions nobody rowed, and it does not run `/sweep`. `/sweep` in turn does not read stalled lanes, the tree or the inheritance, and it ranks and clusters nothing, so it never competes with this skill's ordering. When this skill's run reaches a loom that is about to be handed over, it may offer `/sweep` as a step (`§INV_OFFER_DONT_FORCE_SKILLS`); the findings it writes go to `/groom`, which this skill already composes.

**Where the words overlap, the wider question wins and hands down.** An ask about the state of the work — *where were we*, *what is blocking*, *what do I do now* — is this skill's. Handing down is the normal ending, not a fallback.

**It hands down to the BATCHED pass, and to the single pick only when a person asks for one item in those words.** An ask that names a ticket or a pick is `/inbox-next`'s and goes straight there; everything else that reaches the bottom of the ladder goes to `/groom`. **The asymmetry is deliberate and it is an economy, not a taste**: one worker fed several related tickets is one context load, one test run and one review, where a ticket at a time is one of each per ticket — the same argument `¶INV_LOOM_WAKES_ARE_THE_BILL` makes one level down, applied to the entry point. *Measured against a live run: this skill shipped with the single pick as its floor, and the first operator to use it was offered one ticket to start when a batch was available — nothing-blocking is the common case, so a single-pick floor is not a fallback but the default behaviour wearing a fallback's clothes.* A batched pass that finds only one topic worth taking degrades to one worker by itself and records `not dispatched — <reason>` for the rest, so nothing is lost by preferring it.

## Requirements, and what a missing one costs

Nothing here is a hard requirement. Each source that cannot be read is **reported as unread rather than read as empty**, because the two are indistinguishable at the call site and treating one as the other is how a blocking state goes unnamed:

*   **A session directory**, for the state file, the ledger blocks and the stall sweep. Resolved as: `--session <dir>` · else the engine's active session · else the most recently modified session directory under the sessions root. **No session resolvable** → say so and run the cold floor (step 5): with no ledger to read, the batched pass over what is open still names a move.
*   **`engine project next`** + `LINEAR_API_KEY`, for the ranked open work. Absent → report it and propose from the states that did read.
*   **`engine lane-stall <sessionDir> [--minutes N]`** for the stall reading. **No second detector is written** — if it is not on the path, say the stall state is unread and do not substitute an improvised one.
*   **A git repository.** The work being read may live in a different repository from the engine; resolve which one the session was working in before reading its tree, and say which you read.
*   **`engine loom-page <logFile>`** for the present-state render that precedes the question (step 5) — the log file itself, which this skill resolves inside the session directory rather than passing the directory. Absent, or no loom log in the resolved session → say the state was not rendered and put the question up anyway. It is the only source here whose absence costs presentation rather than judgement.

## The maximal run is the DEFAULT (`¶INV_NEXT_MAXIMAL_BY_DEFAULT`)

**Every invocation proposes everything this skill can do.** A bare `/next` is the maximal run: every rung that holds rides the sequence, the brake reports its count without shortening anything, and the conditional offers are included rather than weighed. **`all` no longer means only the default: it is the one argument that also waives the confirms** (§ *`/next all`* below). An ask in other words (*do everything*, *the full run*) proposes the same maximal sequence and still asks, because only the word waives (`¶INV_NEXT_ALL_IS_THE_WORD_ONLY`). **The operator's reason, which is the whole of the argument**: the trimming was this skill's own judgement about how much to propose, and it was wrong often enough to be friction — a run that proposes less than it found hands back an iteration rather than a decision. What was a flag is now the behaviour, and what is removed is a judgement rather than a safety property.

*   **Every rung that holds rides the sequence.** The ladder orders them blocking-first (step 3); nothing is dropped for length. A rung that holds but needs nothing from this run is still named and carried, which is step 3's last paragraph rather than a concession to `all`.
*   **The brake reports its count and shortens nothing** (step 4). This is what `§INV_NEXT_BRAKE_IS_NUMBERED` means by a brake rather than a gate — the count is said out loud, because an operator overriding a number should see the number they overrode.
*   **The conditional offers are included rather than weighed** — the fold-and-read of an unread board, and `/sweep` where the resolved loom is about to be handed over. Each is normally offered when the moment earns it (`§INV_OFFER_DONT_FORCE_SKILLS`); the maximal default is that moment, stated by the operator instead of inferred.
*   **The run still ends at the destination** — the batched pass, and its own dispatch offer into the weave. The single ranked pick stays out: it is reached only from an explicit ask for one item, and the maximal run is the opposite of that ask.
*   **The default widens what is proposed, never what is assumed.** Every source is read and every unread one named exactly as in an ordinary run (step 2). A source that did not read is reported unread; it is never read as empty because the operator asked for everything.
*   **A rung whose state does not hold is still skipped silently.** Proposing everything is not an instruction to invent work — what is removed is the trimming, never the reading.

**A plain run does not bypass the consent, and that is deliberate.** It fixes the proposal at maximum: the one `AskUserQuestion` still goes up, the recommended answer is the whole sequence named end to end, and the alternatives collapse to one trim (*stop before the new work*) plus decline — one keystroke accepts it. The guarantee that a declined run writes nothing is what this skill's front-door allocation stands on, and its stated falsifier; a flag that wrote before the operator answered would retire that allocation rather than extend it. One keystroke turned out to be one too many when the operator asked for everything, and the change was made where this sentence said it belonged: `§INV_NEXT_PROPOSES_NEVER_DECIDES` now carries an exception for `all`, and nothing about the plain run moved.

## `/next all` — the run that asks nothing (`¶INV_NEXT_ALL_WAIVES_EVERY_CONFIRM`, IDE-236)

**The operator's ruling, verbatim**: *"if i ask for `next all` it shouldnt ask 'what to do' and do all"*, and, asked how far that reaches, *"Waive every confirm."* This is an **explicit amendment of IDE-154's two consent invariants for the `all` argument only**; both invariants below carry it as a named exception. A plain `/next` keeps the shipped behaviour exactly: it asks once, and a declined plain run writes nothing.

**Decide the mode by running the resolver, never by judging the phrasing.** Hand it the operator's literal argument text — exactly what they typed after `/next`, byte for byte — **on stdin, through a quoted heredoc, and never on a shell line**:

```bash
bash ~/.claude/engine/skills/next/assets/consent-mode.sh <<'NEXT_ARGS'
<the operator's argument text after /next, verbatim; an empty line when there is none>
NEXT_ARGS
```

The quoted delimiter is what keeps the text literal: nothing in it is expanded, unquoted, split or executed, so `'all'` arrives as `'all'` and `all; …` runs nothing after the `;`. Pasting the text into a command line instead (`consent-mode.sh <args>`) is forbidden — the shell strips quotes, honours `;` and `#`, and turns what the operator typed into something else before the resolver sees it; the resolver therefore treats **any** command-line argument as a plain run (`reason=argv`). It never blocks: stdin that is neither a regular file nor a pipe (a tty, `/dev/null`, or the Bash tool's held-open socket) is a plain run (`reason=no-stdin`), and a pipe that has not delivered its bytes and closed within a second is a plain run (`reason=stdin-held-open`) — `§PTF_BLOCKING_CAT_ON_STDIN`. Two mechanical cases skip the resolver and are plain: argument text containing a line that is exactly `NEXT_ARGS` (it would close the heredoc early), and a `/next` the operator did not type — reached from prose, or a `Skill(next, …)` call another agent composed — since there is then no operator argument text to hand over, and an agent writing `all` into its own call is the judgement this rule forbids.

It prints `mode=`, `consent=`, `reason=`, one `step.<skill>=` line per composed step, `halt.snapshot=` and the `notice=` template, and it is the only place the waiver is decided (`scripts/tests/test-next-all.sh` holds it to `¶INV_NEXT_ALL_IS_THE_WORD_ONLY`, with two planted defects — a plain run that waives, and punctuation tolerance — that must each go red). **Only an exact `/next all`, with nothing after it, waives.** Every other form asks: free text after `all` (`all but don't commit`, `all myproject`), quoting (`'all'`, `"all"`), punctuation (`all,`, `all;`), leading whitespace (` all`), and `all` as anything but the sole token (`myproject all`, `show me all`) — as do *do everything*, *the full run*, `ALL`, `--all`, and a past run that was `all`.

**What `all` changes, and nothing else:**

*   **`/next`'s own consent question is not asked.** Steps 1–4 run unchanged, the present-state render still runs, and the would-be proposal (every state, each marked in-the-sequence / named-and-unacted / owed, and every source that did not read) is **printed as the run's header** in place of the question, so the operator sees what is about to run even though nobody is asked.
*   **Each composed step is invoked in its waiver form where one exists.** As the resolver prints them:
    *   **Resume a lane** (`step.resume=dispatch`) — `/next`'s own dispatch from the lane's log path; the consent it rode was `/next`'s, so it is dispatched unasked.
    *   **The checkpoint** (`step.snapshot=--yes`) — **`/snapshot --yes -- <KEY>`**, `<KEY>` taken only from the session slug's key, a keyed branch, or the lane log's thread key — never from `tickets[]`, which is a watch list — and bare `--yes` otherwise; an `auto-filed <KEY>` an earlier `/snapshot --yes` stamped in its Outcome is that thread's key from then on, only when that Outcome's `on <branch>` is the current branch, and otherwise bare `--yes`. Its own floors stand (`skills/snapshot/SKILL.md` § *Unattended runs*): it still declines a commit over red or unrun gates and a description rewrite — **and posts the rest of the update anyway** (the comment, the status move) — and **it aborts on a low-confidence or ambiguous target ticket, and that abort ends the run.** Say this plainly in the header, because it is the usual outcome in a cold start: a conductor session's slug (`…_DIRECTOR`) carries no ticket key, so when a key is only weakly named (a single commit key, a branch key that differs from the slug's) target detection is low-confidence, `--yes` has no confirm left to ask with, and the checkpoint aborts — the run then stops there and does not reach new work; when nothing names a key at all, `/snapshot --yes` files a ticket for it instead (its § *Unattended runs*), and any duplicate candidate or gate refusal there aborts the same way. That is the floor working, not a bug. Waiving a confirm does not change a composed skill's floors (IDE-236 non-goal).
    *   **A checkpoint that did not land ends the sequence** (`halt.snapshot=commit-not-done`). Under `all` nobody is at `/snapshot`'s confirm to see the red gates, so a `/snapshot --yes` whose Outcome stamps the commit as anything but **done** — **skipped** (red or unrun gates), **failed** (for example, branch creation on `main`/`dev` failed, so `/snapshot` aborted the commit — `skills/snapshot/SKILL.md` § *Branch safety*), or a run that **aborted** or **STOPped** (an ambiguous ticket, an unresolved commit sentinel) — is a step that did not land: the run stops there and **goes on neither to `/groom` nor to any new work** (`¶INV_NEXT_BLOCKING_FIRST` — the uncommitted work is still on disk). `/snapshot`'s other actions are best-effort and independent, so the comment and the status move may still have posted. The notice names what was declined or failed (*commit skipped — gates red*, *commit failed — could not create the branch on main*, *description rewrite skipped*, *aborted — ticket ambiguous*) and what posted anyway.
    *   **The batched pass** (`step.groom=waiver-owed`) — **`/groom` has no waiver today**, so it runs as itself and its cluster confirm, per-topic confirm and dispatch confirm still ask. That step is **named as owed** in the report — owed to `/groom`'s owner, as a `--yes` that skill does not yet define — and is never skipped to keep the run silent. The filings it routes (`/ticket`, `/inbox-post`) have no waiver either and are owed the same way.
    *   **The decision pass** (`step.decide=decisions-asked+confirms-owed`) — `/decide` runs, and its **decisions** are put to the operator as usual: *"Waive every confirm"* waives confirms, never the decisions only the operator can make. Its **confirms** are a different thing — the `I've-got-this` / `FYI` buckets batched in one confirm, and the panel offer (`skills/decide/SKILL.md` §3, *offered, never forced*) — and those are confirms the ruling does reach; `/decide` has no waiver flag (its `args:` line), so they still ask and are **waiver-owed to `/decide`'s owner**, named in the notice like `/groom`'s.
    *   **`/sweep`** (`step.sweep=nothing-to-waive`) — it reports and files nothing, so there is nothing to waive.
    *   **Documentation signals**: these post without `/next` asking, as the operator ruled (*"Plain asks once; `all` posts"*). Each `post` row goes to `/inbox-post` with the project and the 🟦 channel already resolved. **`/inbox-post` has no waiver today**: its args line takes only item text, and its channel confirm and missing-fields round are its own. Whatever it still asks is **waiver-owed to `/inbox-post`'s owner** and is named in the `all:` notice's `waiver owed` slot, as `/groom`'s is. The resolver prints no `step.` line for this step. Its notice is the separate `docs:` line below, and `consent-mode.sh` is unchanged.
    *   **The single pick** (`step.inbox-next=not-reached`) — `all` is the opposite of an ask for one item.
*   **The run stops at every stop `/next` can detect, and names it and its owner.** `/next`'s own readings detect these, and each ends an `all` run at that point with nothing run after it: an `UNKNOWN — <why>` inheritance field · the stall state unread, so a parked lane may still be live (**a plain run promotes this into the question's framing; an `all` run has no question, so it stops before the step it makes unsafe** — stopping is the safe direction to be wrong in) · a between-step re-read that contradicts the plan · a step that fails · a checkpoint that did not land (above). **The loom's hard escalation floor (`§INV_LOOM_HARD_ESCALATION_FLOOR`) is not one of `/next`'s readings**: a cyclic deadlock, a build failing after retries, a scrutinize MUST-FIX, a thread loopback and the per-thread ticket-disposition ask are events inside a live weave, and they fire inside the weave `/groom` dispatches into, under that loom's own manager chain. `/next` stops on one only when it surfaces through a composed skill it is running.
*   **Nothing is read as more permissive than it is.** `all` widens no source reading (an unread source is still reported unread) and adds no step the resolver did not name.

⚠️ **Known conflict, operator-ruled and surfaced rather than hidden.** `/loom` names **five things no Interruption setting reaches** (`skills/loom/SKILL.md`, *Five things no position of this setting reaches*): **the scrutiny card** in front of a never-scrutinized lane's `/pr`; **the wave boundary's merge** (its one unmediated git write); **`/ticket` / `/inbox-post`** (filing is a question about scope); **the hard escalation floor**; and **a composed skill's own confirm**, which goes only where that skill provides a waiver. The operator ruled that `all` waives every confirm anyway. What this build does about each: `/next` never runs the wave merge — it reports an unassembled wave and names its owner — so that confirm is untouched; the filing confirms and every composed skill without a waiver still ask and are named owed; and the scrutiny card and the floor live inside the weave. **`all` stops at the weave `/groom` dispatches into**: it does not propagate into that loom, which runs under its own Interruption setting, and the per-thread ticket-disposition ask always fires there — so an operator's "do all" ends, honestly, at the first question the weave puts up. The notice names the weave as owed (*its loom's setting governs*). If any of these skills later gains a waiver, `all` would pass it, and that is when the conflict becomes live; the notice is where it shows.

**The report carries one line naming what ran unconfirmed** (step 7), on **every** exit of an `all` run — a stop included — taken from the resolver's `notice=` template: `all: ran unconfirmed — <steps run in their waiver form>; resumed unasked — <lanes>; snapshot declined — <commit skipped | description rewrite skipped | aborted: why | none>; posted anyway — <comment, status move | none>; waiver owed — <steps that still asked, and to whom, the weave included>; still asked (decisions) — <steps>; stopped at — <step and why | none: reached new work>`.

**A second line follows it on every exit of an `all` run: the `docs:` line**, printed by `doc-signals.sh notice --mode all --plan … --posted … --lost …`. It reads:

`docs: posted — <n> (<kind> <file> → <project> <channel> (<comment link>); …); held — <n> (<this run's holds and reasons>); owner-unresolved — <n> (<files>); over-cap — <n> (<items>); carried — <n> (<count per reason>); deduped — <n>`

*   **Every posted item is listed with its link.**
*   This run's holds, the unresolved owners and the over-cap items are each named, at most five per slot followed by *+k more*.
*   Holds carried from earlier runs are counted per reason and not reprinted, so the line stays readable.
*   On a stop before the docs step, the line comes from `--mode stopped` and says nothing was posted or held.

## Documentation signals — every run, cross-project (`¶INV_NEXT_DOC_SIGNALS_ROUTE_OR_HOLD`, NEXTDOCS)

**The operator's ask, verbatim**: *"undocumented new features, issues with docs, redundancy, etc anything"*. The scope was settled by an interrogation the operator answered, which is recorded in the session that built this section (NEXTDOCS). **Every `/next` run, plain or `all`, checks for documentation signals in what changed since the last `/next`.** It posts each one through **`/inbox-post`** to the 🟦 Documentation channel of **the project that owns the file**, which may be a different project from the seat's own. A signal with no channel to go to is **held** and posted once that channel exists. This is not a broad documentation sweep. Older documentation debt that no change touched is not found by this route.

**The detector is `assets/doc-signals.sh`**, and it owns the mechanics. It is cited here and not restated. It posts nothing. It says what to post, what to hold, and what an open comment already covers. **A signal has to help.** The operator ruled for signals that help, not a flood. Precision therefore beats recall at every rule below, and a run posts at most a handful.

*   **What it reads: the commits in the range, and nothing else** (NEXTDOCS fix round 1, R1). That is the commits since the last `/next`, plus this run's own checkpoint commit. The working tree and untracked files are not read: another seat's half-written work is not this run's diff. Docs are read from the committed tree too, so a half-written doc neither raises a signal nor suppresses one.
*   **The kind vocabulary** (`¶INV_NEXT_DOC_KINDS`): `undocumented-feature · stale-reference · redundancy · contradiction · other`. The detector emits the first three:
    *   **undocumented-feature** is a new skill, command, flag, bin or route that no doc names:
        *   a new skill: no doc names `/x` or `skills/x`;
        *   a new command: an added file that is executable (mode 100755) and starts with a shebang. Test files (`*.test.*`, `__tests__/`), `*.conf` files and sourced helpers (100644) are never commands;
        *   a new flag that a command handles, as a case arm (`-h|--help)` included) or as a test (`[ "$1" = --x ]`). It counts as new only if it appears nowhere in the file's pre-image, so a moved or reflowed arm is not new;
        *   TypeScript: a new `bin` in a `package.json`, or a new route string (`.get("/api/x"`) in a changed non-test source file.
    *   **stale-reference**: a doc that still names a path which was deleted or renamed.
    *   **redundancy**: a long passage added in the range that one or two other docs already carry word for word. Each pair is reported once. **Redundancy is detected, not posted.** It is held as `detected-not-posted` until a re-labelled run shows it is at least 50% true (`plan --hold-kinds`, default `redundancy`).

    `contradiction` and `other` are for a signal you raise by hand. It goes through `plan` like any other signal. A kind outside the five makes `plan` exit 2.
*   **Every file is repo-keyed**: `<repo-id>:<path>`. The repo-id is the basename of the repository's `origin`, which every worktree of one repository shares. The same `README.md` in two repositories is therefore two keys, for dedup, for holding and for ownership.
*   **The range.**
    *   **Where it starts.** `doc-signals.sh since --held <file> --repo <dir> --sessions-root <sessions root>` prints the marker that the last applied run recorded.
        *   With none in this session's file, it seeds from the newest marker for that repository in any session's held file under the sessions root, and names the file it used.
        *   With none anywhere, `detect` reads the last 24 hours.
        *   A marker that is no longer a commit, or no longer an ancestor of HEAD, also falls back to 24 hours, with a warning. It never fails the run.
        *   The marker is keyed by the realpath of the repository's top level.
    *   **Reading it.** `detect --repo <dir> --since <sha>` returns at once when the range is empty. Its exit code is a finding: **3** means signals were found, **0** none, **2** an error. Read it from a bare invocation. Measured cost (S6), with CPU as user plus sys:
        *   **Typical range** (the commits since one `/next`): under 3 s CPU. The engine since `HEAD~60` (154 changes) took 3.1 s.
        *   **kit ranges of 606 and 856 changed files**: about 10 s and 15 s CPU.
        *   **Why there is no 5 s wall bound**: on this machine, at load average about 480, the same engine range measured 6 s of wall time in one run and 942 s in another. Wall time there is scheduling, not work.
        *   **What bounds it instead**: the empty-range skip; the lazy doc archive; one awk pass for every query; and no process forked per changed file to test whether it is executable.
*   **The owning project, from the doc owners** (director rulings D1–D3, 03:21). The owner map is called **doc owners**, and its rows are `repo-id<TAB>prefix<TAB>project`. The longest prefix within the same repository wins. A row whose project is `-` claims its prefix for nobody, so its files stay `owner-unresolved` and a shorter prefix cannot take them.
    *   **Deriving them**: the doc owners come from the repository's own Ownership line: each lane's paths, plus the lane → project list and the sub-path overrides beside it. The repository names the file that carries it. No path is typed here.
    *   `doc-signals.sh owners-from-doc --repo <dir> <file>` derives the rows mechanically. It emits a path only when it exists at HEAD and names every item it skips. A lane that maps to `none` emits `-` rows.
    *   **The format it parses is pinned in the script's header.** A reshape of the source line must keep it. A file with the anchor but no lane → project list, or one that yields no row, **exits 2 with the reason**. It never returns an empty map at exit 0, so the map is reported as unread, never as empty.
    *   **Path-level override rows may be appended by hand**, for an ownership the line states in prose that a parser cannot read. Examples: Runner's world-runner entry points, `handbook/` sections, `design/` themes.
    *   **A file no row covers is held as `owner-unresolved`.** The `docs:` line names it, and it is never assigned to the seat's own project. A repository with no Ownership line, the engine today, has every signal `owner-unresolved`.
*   **The channel map.** Build `project<TAB>channel` rows from the 🟦 entry in each project's channel set. Read it from Linear through `§CMD_READ_PROJECT_HANDBOOK`, or from `doc-signals.sh registry-channels skills/inbox-post/assets/INBOX_REGISTRY.md` once the registry has caught up. **Never type a channel id into this file.** Channels are filed by manager:docs (DOCCHAN), so the set grows under you. A project with no 🟦 channel is a normal state: its signals are held and listed, and that is not an error.
*   **The cap: `plan --max N`, default 3 per run.** Every postable signal past the cap is held as `over-cap` and named in the `docs:` line. It is never dropped, and it posts on a later run.
*   **Dedup is by repo-keyed file plus kind** against the **open** comments of every 🟦 channel a row routes to, plus the channel of each held `marker-lost` row. Every posted signal carries one marker line, `doc-signal: <kind> <repo-id>:<path>`, on a line of its own. Pipe the bodies of those channels' unresolved comments through `doc-signals.sh open-keys` to get the keys that `plan --open` reads. `open-keys` reads the marker however markdown dressed it: plain, in inline code, after a bold label, inside a `[text](url)` link or an `<autolink>`, or escaped (`my\_guide.md`). The key runs to the end of the line, so a path with a space reads back whole. A held row, a repeat within one run, and a key any seat holds as `marker-lost` are also deduplicated.
*   **The held file is `<sessionDir>/NEXT_DOC_SIGNALS.tsv`**: session-local, and re-read by every run (`plan --held`). It also carries the since-marker for each repository. A held row whose project now has a channel turns into a `post` row by itself.
    *   **Only `doc-signals.sh apply` writes it**, under a lock. It is written after every accepted plain run and every `all` run, **with zero signals too**, so the marker advances and the range stays bounded.
    *   `apply` **merges**: an earlier held row that the plan does not mention is kept, never dropped. A missing plan, or a failed write, exits non-zero and leaves the file as it was.
    *   A declined plain run writes nothing, and the same range is re-detected next time.
    *   **A cold run with no session directory cannot hold.** Its hold rows are reported as *not held: no session* and named owed to manager:docs.
*   **Posting is `/inbox-post`'s**, once per `post` row. Pass the project and the 🟦 channel already resolved, and the subject and evidence, with the marker line in the body. A row's subject may hold several folded findings (`a; b; c`): rows that share a file and kind become one post, and that post names every finding. Never re-implement the post.
*   **The read-back guard runs after every post that created a comment** (re-review M1). Run the guard only when `/inbox-post` reports that it created a comment. A post the operator declined at `/inbox-post`'s own confirm, or one whose call failed, goes to neither the posted file nor the lost file, so it stays `post-not-landed` and is offered again next run. The guard makes owed items (1) and (2) below self-enforcing:
    1.  Read the 🟦 channel's comments back and pipe their bodies through `doc-signals.sh open-keys`.
    2.  Run `doc-signals.sh landed --open <those keys> <kind> <file>`.
    3.  **Exit 0 (`landed`)**: only now write the row to the posted file, as `kind<TAB>file<TAB>project<TAB>channel<TAB>comment-url`.
    4.  **Exit 1 (`marker-lost`)**: `/inbox-post` dropped the marker, or moved the item out of 🟦. Every later run, on every seat, would then post the same item again. So:
        *   write the row to a lost file instead;
        *   **stop posting for this run**; the rows not yet posted stay `post-not-landed`;
        *   the `docs:` line leads with `marker-lost — <n> (…), posting paused until its marker reads back`.

        A marker-lost row is held as `marker-lost` and is never re-posted by a later run. Its comment exists; what is missing is the read-back.
    5.  Then run `apply --plan … --held … --posted … --lost … --since-repo <dir> --since-sha <the head detect printed>`. A `post` row that was not attempted stays held as `post-not-landed`.
*   **A held marker-lost row pauses all posting, on every seat, until it clears.** Run `plan … --sessions-root <sessions root>`, the same root `since` scans. `plan` then reads the `marker-lost` rows of every `<sessions root>/*/NEXT_DOC_SIGNALS.tsv`, not only this session's.
    *   A signal whose key another seat holds as lost is deduplicated (`dedup … marker-lost`): that seat's comment already covers it.
    *   While any lost row's key is missing from the open keys, every postable row is held as `posting-paused` instead of posted, and the `docs:` line leads with `posting paused — <n> (…) while a marker-lost comment is held`. A broken `/inbox-post` therefore costs one comment per seat that posts before the first lost row is applied, not one per seat per run.
    *   **It clears when the lost comment's marker reads back.** Restore the `doc-signal: …` line in that comment in Linear; the next `plan` sees its key among the open keys, the row leaves as `dedup … open-comment`, and the paused rows post. Fix `/inbox-post` first, or the next post is lost the same way.
    *   **The boundary.** The pause and the dedup reach only the seats under one sessions root. A seat under another root (another project's sessions directory) that detects the same commit is not covered.
    *   **Owed to `/inbox-post`'s owner, stated and not edited from here:**
        *   (1) the caller's marker line survives template filling, or dedup breaks and every run reposts;
        *   (2) a channel the caller resolved is not reclassified. A tooling-shaped item passed with the 🟦 channel must stay in 🟦, because one moved to 🛠️ is invisible to the 🟦 dedup read and reposts on every run;
        *   (3) a waiver form, so that `all` posts unasked.

        The read-back guard and the pause enforce (1) and (2) for every seat under the sessions root: when either fails, posting stops at the first lost post, the post that failed is held for good, and no seat under that root posts again until it clears. The cap limits what one run can post before that happens. (3) fails safe, because `/inbox-post` still asks.
*   **Where it sits in the run.** It is not a rung, because it neither blocks progress nor adds new work.
    *   Step 2 runs `detect` and `plan` once as a **preview**, so the consent body can name the drafts.
    *   **The docs step itself runs after the checkpoint (rung 3) and before the batched pass (rung 4).** There it re-runs `detect` (the between-step re-read), so this run's own checkpoint commit is inside the range.
    *   `/groom` then drains an inbox that already holds the drops.
    *   A run that stops before this step posts nothing and holds nothing. Its `docs:` line says so (`notice --mode stopped`).

## Algorithm

### 1. Establish where you are, in one line, before reading anything else

Read the resolved session's `.state.json` and say which case you are in — the cases differ in what you may touch:

*   **No session, or no state file** → **cold**. Steps 2 and 3 run on whatever sources exist; the session-shaped readings report as unread.
*   **`lifecycle=idle`** → a session that closed. `§CMD_PRESENT_NEXT_STEPS` owns this case and is the better answer when the question is *which skill next for this session's work*; say it exists, and continue only because the question asked here is wider.
*   **`lifecycle=active`** → a live session. **Ride it and activate nothing** (`§INV_RIDE_NEVER_ACTIVATES`): run no `engine session activate` and no `engine session phase`, and write nothing to `.state.json`. There is one state file per session carrying a single `currentPhase`, so a composed pass that advances it overwrites its host's own position in the only file the host has. Where `taskType` is `LOOM` and the phase is the loom body, **the loop gate is the operator's better surface** — it is already awake and already runs these conditions as cadences. Say so, and prefer it.

**The state file does not carry its own path.** Its `sessionDir` field reads `null` on a live session, so compute the directory from the file's own location rather than from the field — a measured trap, and a skill that trusts the field resolves `null` and reads nothing.

### 2. Read the states — each reading, and what its absence means

Read all of them before proposing anything; precedence needs the whole set, and a skill that stops at the first hit cannot show the operator what it is not acting on.

*   **Lanes.** `engine lane-stall "<sessionDir>" [--minutes N]` — read-only, exit **3** when any lane is stale, which is a finding rather than a failure. **`§INV_LOOM_STALL_IS_SWEPT_NOT_SENSED` rules what each reading means and which two readings are forbidden; follow it there and write no second detector.** Read that exit code from a bare invocation: a pipeline's status is its LAST command's, so a sweep read through `head` or `tail` reports the pager's success.
    *   **The LOG path is the sweep's own `logpath=` column — take it from there and resolve nothing by hand.** It closes each row, because `§INV_LOOM_HANDS_OVER_A_PATH_NOT_AN_ID` forbids forwarding the `agent=` transcript beside it. **Read it as everything after `logpath=` to end of line — `sed 's/.*logpath=//'`, never `awk '{print $NF}'`** — a session directory on a shared drive holds spaces, and the last whitespace field of such a row is a truncated path that still looks like one. A row reading `logpath=none` is a lane with no log, and that is a **different hand-over** from a lane with one: report it as that reading rather than substituting the transcript.
    *   **Read the `window=` on the sweep's first line and say it with any count you report.** Every row is scoped to that window, and the window defaults to the session's own age rather than a fixed span — so `0 lanes seen` is a claim about a horizon and is meaningless without it.
*   **The ledger blocks**, from the session's loom log: the thread ledger, the open claims, the boards, the docs owed, the parked rows, the relay and conflict entries. **The log is append-only, so a block's heading recurs every time the conductor rewrote it** — read the LATEST occurrence of each and never a count of all of them. A count over the whole file reports a weave's history as its present state; measured on one weave's log, the parked heading appears repeatedly while the number of lanes actually parked right now is whatever the newest block says.
*   **Forks and boards.** An open claims row with no record path is an unanswered fork; a boards row whose fold state is unread or absent is a board **never folded**; a row folded with nothing on it is a board **published and unanswered**. **Three readings, not two** — and the last is the one that reads as finished while a decision is still outstanding. **What closes any of them, and what a fold that comes back empty means, are `§INV_LOOM_A_FORK_ARRIVES_DECIDABLE` and `/decide` §4's; read them rather than a summary here.**
*   **The tree — this skill's own reading, and the one it specifies.** Establish, in this order, and say which repository you read, since the work may live in a different one from the engine:
    *   **Which repository.** Resolve it from the session's own record of what it was working in. Walk up from a path the session names; never assume the engine's root, and never read a repository you cannot name.
    *   **Dirty or clean.** `git status --porcelain`, and read it as the dirty reading. **The silence to guard against is NOT here** — measured, a plain `--porcelain` on an untracked path prints `?? <path>` at exit 0, so this command does see new files. It goes silent at exit 0 in two narrower cases: run with `-uno`, and on a path `.gitignore` matches. Use neither when asking whether work is uncommitted.
    *   **The silence that actually bites is history-based.** Measured on an untracked file: `git log -- <path>` and `git diff HEAD -- <path>` each print nothing at exit 0, while the same two commands on a tracked file in the same repository return output. So any verification that leans on log or diff reads an untracked file as unchanged whatever it contains, and the engine's own most-edited skill files are untracked. **Establish tracked-ness with `git ls-files --error-unmatch <path>` before reading any history silence as clean**, and for an untracked path treat *landed* and *committed* as different claims: the first is read from the path, only the second from git.
    *   **Ahead of its base.** `git rev-list --count <base>..HEAD` against the base the project publishes. Commits that exist only locally are work at risk in the same way uncommitted edits are, and a tree that is clean but ahead is a different proposal from one that is dirty.
    *   **A wave nobody brought back together.** Several lanes' worth of landed work sitting on one branch with no assembled result. **This state is REPORTED, never acted on** — the step that assembles it is not built, and inventing interim behaviour for it is out of scope (see rung 3).
*   **Inheritance.** `LOOM_INHERITANCE.md` at the sessions root, at an address **computed** from the session directory rather than typed. A field reading `UNKNOWN — <why>` stops the run and is reported (`§INV_LOOM_PASS_ON_NEVER_DISCARD` owns why a partial row may not be acted on). Measured on one sessions root: the file was simply absent, which is a legitimate reading and is reported as *no inheritance written*, distinct from *not read*.
*   **Asks — the seat's own question files** (`/ask`; its § *How the answer reaches you* names this skill as the asker's pickup). **Read them only when both guards hold**, and otherwise report **"cannot read asks — <why>"**, never *no asks* and never another seat's:
    *   `[ -n "${FLEET_PANE:-}" ]` — the seat is set **and non-empty**. An empty `FLEET_PANE` is not "no seat filter": the CLI reads `--to ""` / `--seat ""` as no filter at all (`tools/ask-app/src/cli.ts`, the `list` branch's `!opt.to`), so it would list every seat's asks, name them owed to this one, and a fold would stamp another seat's answer read. Why: *FLEET_PANE unset or empty*.
    *   `[ -d "$(engine ask path)" ]` — the ask store exists. `engine ask path` prints the resolved `ASK_ROOT`; a missing directory makes `engine ask list --json` print `[]` at exit 0, which is indistinguishable from *no asks*. Why: *no ask store at <path>*.

    Then two readings, both read-only:
    *   **Open asks addressed to the seat** — `engine ask list --status open --to "$FLEET_PANE" --json`. **Every one is owed by this seat**: someone is waiting on it. Those whose `header.created` is more than **10 minutes** old are marked **overdue** — that is the asker's re-ping mark (`/ask` § *While you wait*), so it says how long the asker has waited, not when the ask became owed.
    *   **Asks with an unread answer** — `engine ask list --status all --seat "$FLEET_PANE" --json`, keeping those with an `answer` present and **no `header.readAt`**. That is the store's own definition of unread (`tools/ask-app/src/lib/store.ts`, `pickupUnread` — *"The seat's /next pickup"*), and it **includes a declined ask**, which is also an answer the asker needs. **`delivery` is not consulted**: `delivery: delivered` means *queued* at a session's socket, not read (`cli.ts`, `lifeOf`), and a seat whose session died while an answer sat queued is exactly the cold start this skill exists for. ⚠️ `skills/ask/SKILL.md` § *How the answer reaches you* still prescribes `--status answered` and the delivery reading; that line is stale against the CLI and is owed to the `/ask` owner (the ASK v2 lane), not edited from here.
*   **Context, when the resolved session is a loom.** `contextUsage` from that session's `.state.json` (the status-line figure, already normalised), together with whether any row of `engine lane-stall "<sessionDir>" --all` reads `running`. Step 3 uses the pair to decide whether the sequence opens with `/dehydrate`. A missing field is reported as *context unread*, never as low.
*   **Groomable work.** `engine project next` for the ranked open work; the inbox and the un-ticketed leftovers are `/groom`'s to drain, and this skill asks only *whether there is anything there*, never *what shape it is in*.
*   **Documentation signals (the preview).** For each repository the session worked in, run `doc-signals.sh detect` over the range `since` gives. Then run `plan` against the doc owners, the channel map, the open-comment keys, the held file and the sessions root (§ *Documentation signals*). This preview drafts the consent body, and the docs step re-runs it after the checkpoint. `plan` writes nothing. Each map that could not be built is reported as unread, never as empty: no MCP and a registry with no 🟦 row is *channel map unread*, not *no channels*.

### 3. Apply precedence — blocking-first (`§INV_NEXT_BLOCKING_FIRST`)

**What stops progress outranks what adds progress**, because something is already waiting on the former. **The ladder ORDERS the run; it does not truncate it.** Walk every rung, keep each one that holds, and the kept rungs in ladder order are the run — clearing first, new work last.

**This is the correction of a shipped floor, and it is the second one this entry point has taken from its own use.** The skill shipped proposing the first rung that held and stopping there, so an operator with obligations open reached new work only by invoking it again, rung by rung — *iterating a state machine by hand*, in the operator's own words at the run that found it. **Blocking-first was never the defect**; truncating at the first hit was. Ordering satisfies both at once: nothing new starts while something waits, and the run still arrives at new work.

**Before the rungs: a loom past its dehydration point restarts first.** When the resolved session is a loom, `contextUsage` reads 0.70 or above, and no lane reads `running`, the sequence's first step is `/dehydrate`, unless the operator is present and mid-discussion. That rule is `/loom`'s (`§INV_LOOM_DEHYDRATES_AT_SEVENTY`); this skill reads it as a step and does not restate it. **It is a restart, not a close**: the session stays open, and the rungs below run in the successor, which re-reads every state.

Walk all four rungs. **This is the whole sequence by construction** — every rung that holds is kept, and no judgement about trimming is applied:

1.  **A lane stopped without handing back.** Something was mid-flight and nobody is holding it. → **Offer the resume, from the lane's LOG PATH and never from an agent id** (`§INV_LOOM_HANDS_OVER_A_PATH_NOT_AN_ID` gives the reason and the payload; the successor is a fresh lane carrying that log in its context pack).
2.  **An unanswered fork, a board never folded, or a board folded and still unanswered — the rung where `/next` PUTS QUESTIONS TO YOU.** **The seat's asks rank here too**: an answer nobody has read is folded with **`engine ask read "$FLEET_PANE/<id>"`**, which prints the answer and **stamps `readAt`** (and `readBy`) in the ask file, so the next run no longer sees it as unread — reading the file by hand stamps nothing and re-surfaces the same answer on every run. The stamp is a write to the seat's own ask file, so in a plain run it happens only inside the accepted sequence, and under `all` it runs as a step of the sequence; Fold **one id at a time**, never with `engine ask read --unread`: that bulk form prints every unread answer, stamped or not (`tools/ask-app/src/lib/store.ts`, `pickupUnread`), but an answer it could not stamp says so only on stderr as `(not stamped read: <why>)`, which is easy to lose among the others and lost entirely by anything that keeps only stdout. The stamp lands only for a recipient of the answer (the ask's `from:` and its forward chain); where the command prints `(not stamped read: <why>)`, report the answer as folded but unstamped, with that why. Every open ask addressed to the seat is named as owed to the seat, the overdue ones first — answering it is the seat's decision, so this skill never answers it, under `all` or otherwise (`/ask`: *never answer your own ask*). A thread is waiting on a person, or the page its forks were put on is still waiting to be looked at. **All three rank together at this rung**, because `/decide` §5 makes the published page the asking surface: a board nobody has answered IS an unanswered fork that happens to live on a page, not a lesser state filed underneath the forks. → **The decision pass** (`Skill(decide, …)`), or the board's own row — **folded first, then reported.** The fold is agent-run, so an answer sits in the presigned events inbox until it is run; a rung that reads the state doc without folding reports *no answers yet* forever while the answers sit there, and `/decide` §4 rules that a `404` or a stale read means **not yet folded** rather than zero answers. Where a board holds the forks, say what the operator is being waited on for — *we are waiting for the decision page* — rather than listing it as a row to tidy. **The pass is DISPATCHED, and an inline question round may not be substituted for it** — the same prohibition `/loom` carries for a required `/interrogate`, and measured here twice in one evening: a conductor holding this whole file read the rung as a state to clear, asked inline instead, and a fork sat hours unasked because the claim was rowed rather than made decidable. ⚠️ **No board atom exists among the atoms `/decide` declares**, so the route invokes the whole skill and inherits its cadence and its wrap-up obligation — say that cost when proposing the route, and never read it as a reason to ask inline instead.
3.  **Uncommitted work, or a wave nobody brought back together.** Finished work sitting only on disk is the state this programme has actually lost work to. → **The checkpoint** (`Skill(snapshot, …)`), which verifies before it commits and is the only route here that writes.
    *   **The wave half belongs to the loom, not here.** `§INV_LOOM_INTEGRATES_AT_THE_WAVE_BOUNDARY` owns bringing a wave's trees back together; follow it there and invent no interim behaviour. Where a wave is unassembled and no conductor is awake to run that boundary, **report it and name the owner** — do not improvise a merge from an entry point that holds no partition and no ledger. [IDE-132](https://linear.app/idealic/issue/IDE-132) carries the surrounding open questions.
    *   **The uncommitted half is this skill's**, and it is the proposal that fires: the checkpoint over the paths this session actually touched.
4.  **Groomable work.** Nothing is in the way. → **The batched pass** (`Skill(groom, …)`), and its own dispatch offer carries it into the weave. **This is the destination, and it is batched** — one worker takes a topic's related tickets together, which is `/groom`'s own stated purpose rather than something arranged here. **Hand down to `/inbox-next` only when a person asked for one item in those words**; a quiet reading is never a reason to offer a single ticket, because quiet is the ordinary condition at this rung and the whole point of reaching it is to start a batch.

**This rung order is the whole of the judgement in this skill.** A dead lane and an unanswered fork outrank a commit, and a commit outranks starting something new; starting new work while three things wait is the failure the ladder exists to prevent.

**Rung 4 is the run's destination, not its last resort (`§INV_NEXT_LANDS_ON_NEW_WORK`).** A run that cleared three blockers and stopped has left the operator exactly where they started: knowing what was in the way and holding no work. So the batched pass is appended to every sequence whose earlier rungs are clearable in this run, and a sequence that cannot reach it says which rung stops it — a lane whose resume must finish before anything else can be judged, a fork only the operator can answer. **"The blockers were cleared" is not an outcome; it is a precondition**, and a run reporting only that is the truncation defect wearing a longer sequence's clothes.

**A rung that holds but needs nothing from this run is kept in the SEQUENCE and not in the WORK.** Today's live instance, as the reading that produced this paragraph: fourteen lanes read parked and twelve had their output already on disk or committed, so rung 1 held as a reading and called for no resume. Name it, carry it, act on none of it — a rung is cleared by establishing it needs nothing just as truly as by doing something about it.

### 4. The brake (`§INV_NEXT_BRAKE_IS_NUMBERED`)

**Past the threshold, propose closing rather than starting — and name what to close, with the count that put you there.** A refusal reading *"too much in flight"* is discretion wearing a rule's clothes, so the number is stated and the rows are named:

*   **The quantity** is the count of **open obligation rows**: open claims with no record path, boards not folded and read, docs owed still open, and parked lanes. It is **not** the context budget, which `§INV_LOOM_NO_RUSH_TO_CLOSE` already governs with its own number — two different quantities, and conflating them is how an unnumbered rule misfired before.
*   **The threshold is 5 open rows**, and its derivation is stated because it is an imperfect anchor rather than a measurement of itself: five is the number of lanes whose finished work nobody committed on this programme — the one observed instance of the pile costing real work, recorded at `builds/next-integrate_INTERROGATE.md:62`. **The quantities differ** (lanes there, obligation rows here), so this is a starting dial and the first weave that runs healthily past it should re-measure rather than defend it.
*   **It is a brake, not a gate.** It changes what is proposed; it refuses nothing the operator chooses anyway. **The maximal default is that choice made up front** — the count is reported, the sequence is not shortened by it, and the report says the brake was overridden rather than going quiet about it.
*   **Past the threshold it lengthens the closing half of the run; it does not remove the destination.** The sequence takes on more clearing rungs before the new work and says so with the count — *"six rows open, so this run closes three of them before it starts anything"*. **Forbidden: dropping rung 4 to honour the brake.** That reinstates the truncation this skill was just repaired for, with a number attached to make it look principled, and it hands the operator back the same empty-handed run. Where the open rows genuinely cannot be cleared inside one run, the sequence ends at the furthest rung it can reach and names the row that stopped it.

### 5. Propose the SEQUENCE in one question, and show what is not in it

**Render the weave's present state first, before the question goes up.** Where the run resolved a session holding a loom log, `engine loom-page <logFile>` projects that log's present state as a page. **It takes the log FILE, not the session directory** — handed a directory it exits non-zero without rendering. Read-only, and it costs no wake this run was not already paying, since step 2 has already read the states. **It runs on every invocation that has a log to read; it is not a menu slot and nobody chooses to be shown it**, because the value is in the operator seeing the weave as it stands and then choosing, rather than choosing and then discovering. The script owns its contract — cite it by name and restate none of its behaviour here, since a copy drifts and a citation cannot.

Two properties of its output matter to you as its reader. It reports the **present** state — each rewritten register at its latest occurrence, never a count over the whole log, which is the same append-only reading step 2 already obeys. And it **names every heading it could not parse**, which is the part to actually read rather than skip: a grammar drift that gets swallowed under-reports and leaves the page looking healthy, so a render carrying no drift list is a stronger reading than a quiet one. Its **exit status is a finding, not a failure** — read it directly from a bare invocation, because a pipeline reports its last command's status and a render read through `head` reports the pager's success. **If the command is not on the path, say the state was not rendered and carry on** — it is a presentation step, never a gate, and its absence is reported like any other unread source.

**Under `all` (`consent=waived` from `assets/consent-mode.sh`) the question is not put up**: print the body this step would have carried as the run's header, and go to step 6 (§ *`/next all`*). Everything below describes the plain run.

Then put the question up. One `AskUserQuestion` via `§CMD_DECISION_TREE`, which owns the declare-N-surface-four mechanism (`§INV_ASK_SURFACE_FOUR`, `§INV_ASK_SLASH_FOR_MORE`). Use it; never a fixed menu. **This one question is the CONSENT question, and it is the only thing this skill asks on its own behalf** — every substantive question the work needs answered is rung 2's and goes to `/decide` dispatched. So *can `/next` ask me things* is answered yes, at rung 2 and not here.

*   **Tickets first**: when the proposal names a tracker ticket, print the ticket list in chat before the question (`§INV_TICKETS_PRESENTED_BEFORE_ASKED`).
*   **The recommended option is the WHOLE sequence, named end to end and in ladder order**, phrased as moves rather than states: *"Resume SCRUTFIX from its log, checkpoint the four touched paths, then groom the open work"* — not *"a lane is parked"*, and not the first rung alone.
*   **In a plain run, the sequence is consent to ATTEMPT, never consent to write** (`§INV_NEXT_ONE_CONSENT_PER_RUN`). That is what makes one accept over several steps as safe as one accept over one: every route lands in a composed skill that holds its own confirm — `/snapshot` batches commit, comment and status behind one, `/groom` confirms its dispatch, `/decide` confirms at §5 — so a misread state later in the sequence is caught by that skill's gate rather than by this skill's absence. **In a plain run, a step whose routed skill holds NO confirm of its own may not ride a sequence accept** and is put up as its own question. *(Under `all` there is no question to put it up as: the confirm-less lane resume is dispatched unasked and named in the notice's `resumed unasked` slot — `¶INV_NEXT_ALL_WAIVES_EVERY_CONFIRM`.)*
*   **The alternatives are shorter prefixes of the same sequence, never a different one.** *Clear the blockers and stop before the new work* · *skip to the new work and leave the rows open* · *just the one rung*. An operator who wants less gets a prefix; an operator who wants a different order is told which rung forbids it and why, because the order is the judgement and not a preference. **The prefixes collapse to one** — a single *shorter — stop before the new work* beside the maximal recommendation — since the maximal proposal has already answered the how-much question and re-asking it four ways is the per-rung iteration this skill was repaired for, wearing a menu's clothes.
*   **The body carries every applicable state, with each marked as in-the-sequence or named-and-unacted** — and for an unacted one, what would clear it and why this run is not doing it. What was lossy before was dropping states; what is lossy now would be hiding which ones the accept covers.
*   **The body also carries what did not read** — each source that was unavailable, so a quiet state is never mistaken for a clear one.
*   **The body carries the drafted documentation signals**, as the `docs:` line from `doc-signals.sh notice --mode plain`: `docs: will post — …; will hold — …; deduped — …`. The recommended sequence names them as a move between the checkpoint and the batched pass (*"…, post 2 doc signals and hold 3, then groom the open work"*). **They ride the one consent, and no second question is asked for them.** In a plain run, `/inbox-post`'s own confirm still asks for each post, because posting is its step.
*   **A state this run can neither act on nor route is marked OWED, with the person or skill it is owed to** (`§INV_NEXT_ESCALATES_WHAT_IT_CANNOT_ROUTE`). This is a third marking beside in-the-sequence and named-and-unacted, **not a second asking surface** — minting one would be exactly what this skill refuses `/loom`. Four readings land here, each already specified above and each previously ending in a report that nothing then happened to: an `UNKNOWN — <why>` field in the inheritance · an unassembled wave with no conductor awake · a rung that holds whose route is blocked, such as a parked lane whose sweep row reads `logpath=none` · open rows the run cannot clear inside itself. **Owed means a named owner, not a mention**: *"nobody is awake to run the wave boundary — that is yours or a conductor's"* rather than *"the wave is unassembled"*. Where the unroutable reading makes the PROPOSAL unsafe — the stall state unread, so a parked lane may still be live — it is **promoted out of the body into the question's framing**, and the recommended answer becomes settling it rather than running a sequence (under `all`, which has no question, it stops the run before the step it makes unsafe instead — § *`/next all`*). Where it needs a decision rather than an answer, it is rung 2's and goes to `/decide` like any other fork. **None of these is a ground question**: this skill touches no shared ground, so may-I-push, who-merges and which-root-is-canonical cannot arise in it — they arise inside a routed skill, under that skill's own confirm.
*   **A run always names a move, and normally names several ending in new work** (`§INV_NEXT_ALWAYS_A_MOVE`, `§INV_NEXT_LANDS_ON_NEW_WORK`). The destination is the batched pass — `Skill(groom, …)` over what is open, handing each topic's related tickets to one worker. An invocation ending in *"nothing to do"* is a bug, and so is one ending in *"and now the blockers are cleared"*. **The destination is deliberately not a single ticket**, even though a ranked order is cheaply available: arriving there means nothing is blocking, which is the ordinary condition, so whatever sits there is what the skill does most of the time.

### 6. Run the accepted sequence in order, each step through its composed skill

Invoke each step's skill in ladder order and carry on to the next. **One consent per invocation, several moves under it** (`§INV_NEXT_ONE_CONSENT_PER_RUN`): in a plain run the accept covers the sequence as named, and under `all` the printed header does; nothing outside it is run.

*   Resume a lane → dispatch a fresh lane with that lane's **log path** in its context pack.
*   Fork or board → `Skill(decide, …)`, dispatched — never an inline question round of this skill's own.
*   Uncommitted → `Skill(snapshot, …)`; under `all`, **`/snapshot --yes -- <KEY>`** with `<KEY>` from the session slug's key, a keyed branch, or the lane log's thread key, never from `tickets[]`; bare `--yes` otherwise (the resolver's `step.snapshot`); an `auto-filed <KEY>` an earlier `/snapshot --yes` stamped in its Outcome is that thread's key from then on, only when that Outcome's `on <branch>` is the current branch, and otherwise bare `--yes`.
*   Documentation signals: this step runs after the checkpoint and before the batched pass (§ *Documentation signals*).
    *   Re-run `detect` and `plan`. This run's checkpoint commit is now inside the range.
    *   `Skill(inbox-post, …)` once per `post` row, each that created a comment followed by the read-back guard (`doc-signals.sh landed`). There are at most `--max` of them, default 3. A `marker-lost` stops posting for the run and pauses it on every seat until it clears.
    *   Run `doc-signals.sh apply` with the head that `detect` printed, **even when there were no signals**, so the marker advances.
    *   A declined or failed `/inbox-post` in the docs step does not end the sequence, the one exception to the rule below. The row stays held as `post-not-landed`, the remaining `post` rows are still offered, and the run carries on, because a documentation drop blocks nothing after it.
*   Groomable → `Skill(groom, …)` — the destination, and batched. Under `all` it runs as itself, since it has no waiver, and the step is named owed in the report.
*   Ranked pick → `Skill(inbox-next, …)`, reached only from an explicit ask for one item.

**Between steps, re-read the state the next step depends on (`§INV_POINT_IN_TIME_CHECKS_EXPIRE`).** A sequence is consent to a plan read at its start, and the earlier steps change the tree: a checkpoint that commits is exactly what makes the dirty reading stale. Re-read, and **where the re-read contradicts the plan, stop the sequence there and report the contradiction** rather than running a step against a state that has moved. That is the sequence's own falsifier, and it is cheap — one reading per step.

**A long sequence changes nothing here.** The between-step re-read still runs, a re-read that contradicts the plan still stops the sequence, and, in a plain run, every write still passes its own skill's confirm (under `all`, each composed skill runs in its waiver form where it has one, and the ones without still ask — § *`/next all`*). A longer sequence is more steps under one consent, not a looser one — and the longer it is, the more the per-step re-read is what keeps it honest.

**A step that fails, or whose composed skill is declined, ends the sequence** (a single `/inbox-post` in the docs step excepted, above). Report which step stopped it, what the state is now, and which steps did not run. Forbidden: skipping a failed step to reach the new work — the order exists because the later steps assume the earlier ones landed.

**Under `all`, a checkpoint whose commit was skipped, or that aborted, ends the sequence — and so does any commit outcome but done, a failed commit included** (`halt.snapshot=commit-not-done`). `/snapshot --yes` returns normally when it skips or fails a commit — the comment and status still post, it is not a step failure, and nobody declined it — so this is stated rather than left to the re-read: the run goes on neither to `/groom` nor to new work while the uncommitted work is still on disk. Name what `/snapshot` declined and what it posted anyway (the comment, the status move).

**Under `all`, every stop `/next` can detect ends the sequence there**, exactly as a failed step does (§ *`/next all`*), and a floor event that surfaces through a composed skill it is running does the same.

**On every one of these stops, under `all`, print the `all:` notice** (step 7) with its `stopped at` slot filled — a stopped `all` run is the one whose unconfirmed writes most need naming.

**Declined at the proposal** (plain run only) → report the reading and stop. Nothing is dispatched, committed, filed or transitioned in a run the operator did not accept, which is demonstrable by running to the proposal and declining.

### 7. Report

One terse line per step run — which state it acted on and which skill took it — then the state the run ended in and what remains named-and-unacted. **Under `all`, add the one-line notice on every exit of an `all` run** — the completed run and every stop alike — filled from the resolver's `notice=` template: `all: ran unconfirmed — …; resumed unasked — …; snapshot declined — …; posted anyway — …; waiver owed — …; still asked (decisions) — …; stopped at — …` (§ *`/next all`*). No slot is dropped; an empty one reads `none`. **Every run, plain or `all`, also prints the `docs:` line** (§ *Documentation signals*): `docs: posted — …` under `all`, the same posted form after an accepted plain run (`notice --mode all --posted … --lost …`, where `all` names the line's form and not the consent), and `--mode stopped` when the run ended before the docs step. **Say explicitly whether the run reached new work**, because that is the outcome the sequence exists for and a reader cannot infer it from a list of cleared rows. Then stop — what happens next belongs to the last routed skill.

## Constraints

*   **`¶INV_NEXT_PROPOSES_NEVER_DECIDES`**: it proposes; the operator accepts. Dispatching a lane, committing, filing or transitioning anything on its own reading of state is forbidden — an entry point acting on a misread state does damage nobody asked for, and every state here is read from a surface that can be stale, partial or silent at exit 0. **Exception — `all` (IDE-236, operator-ruled: *"if i ask for `next all` it shouldnt ask 'what to do' and do all"*; *"Waive every confirm."*)**: the explicit `all` is the operator's acceptance given up front, so the sequence runs without the proposal being accepted, each composed skill in its waiver form; every stop `/next` can detect still ends it (§ *`/next all`*), and a plain run keeps this invariant exactly as written.
*   **`¶INV_NEXT_ONE_CONSENT_PER_RUN`**: one consent per invocation, covering the sequence as it was named, and several moves under it. Running a route the operator was not shown is forbidden, and so is re-asking between steps of an accepted sequence — that is the per-rung iteration this rule replaced, moved inside one call. **Replaces `INV_NEXT_ONE_MOVE_PER_RUN`**, which required a fresh invocation per rung; it survived one live run. Its safety argument is inherited rather than dropped: consent here is consent to *attempt*, and every write still passes the routed skill's own confirm, so in a plain run a step whose skill holds no confirm is put up as its own question. **Exception — `all` (IDE-236, operator-ruled: *"Waive every confirm."*)**: an `all` run has zero consents from `/next` and passes each composed skill its waiver where one exists (`/snapshot --yes`); a skill with none still asks and is named owed; the confirm-less lane resume is dispatched unasked and named in the notice's `resumed unasked` slot; a plain run keeps one consent per run as written.
*   **`¶INV_NEXT_LANDS_ON_NEW_WORK`**: a run normally ends at the batched pass, and a run that cannot says which rung stopped it. Dropping the destination to honour the brake is forbidden, and reporting a run whose whole outcome is cleared blockers as complete is forbidden — the operator is then holding what they already had, which is a reading.
*   **`¶INV_NEXT_BORROWS_THE_GROUPING`**: it groups nothing and ranks nothing of its own. Any clustering of items into topics, or any ordering of open work, computed inside this skill is forbidden — `/groom`'s topics and `engine project next`'s order are the sources. This is `skills/groom/SKILL.md:20`'s own rule applied to a third party.
*   **`¶INV_NEXT_BLOCKING_FIRST`**: what stops progress outranks what adds progress. **The rule orders the run and does not end it** — starting new work *before* a parked lane, an unanswered fork or uncommitted work has been dealt with is forbidden; reaching new work *after* them in the same run is the point. Truncating at the first rung that holds is forbidden.
*   **`¶INV_NEXT_BRAKE_IS_NUMBERED`**: a refusal to advance names what to close and cites its count. Braking on an unnumbered judgement is forbidden.
*   **`¶INV_NEXT_MAXIMAL_BY_DEFAULT`**: every run proposes every rung that holds, with no trimming and no shortening by the brake — and a plain run does not bypass the consent (`all` does, under `¶INV_NEXT_ALL_WAIVES_EVERY_CONFIRM`), widen what any step may write, or license a step the operator was not shown. In a plain run, writing anything before the one question is answered is forbidden, because the declined-run-writes-nothing guarantee is this skill's own falsifier and the thing its front-door allocation stands on (an `all` run puts up no question; what it may write is `¶INV_NEXT_ALL_WAIVES_EVERY_CONFIRM`'s). Also forbidden: reading an unread source as empty, or inventing a rung whose state does not hold, because the proposal is maximal. **Replaces `INV_NEXT_ALL_IS_MAXIMAL_NOT_UNCONSENTED`**, which made this a flag; the operator ruled the maximal run the default, on the grounds that the trimming it removed was never a safety property.
*   **`¶INV_NEXT_ALL_WAIVES_EVERY_CONFIRM`** (IDE-236): `/next all` asks nothing of its own and invokes each composed skill in its waiver form; a step with no waiver is named owed and still runs as itself. Forbidden: skipping a step because it would ask, waiving a composed skill's own floors, treating a decision (`/decide`'s decisions, a ticket-disposition ask, a cyclic deadlock, a MUST-FIX) as a confirm, calling a skill's confirms unwaivable when they are only waiver-owed (`/decide`'s bucket batch and panel offer), going on to `/groom` or new work after a `/snapshot --yes` whose commit is anything but done (skipped, failed, aborted, stopped), and any exit of an `all` run — a stop included — whose report omits the notice line.
*   **`¶INV_NEXT_ALL_IS_THE_WORD_ONLY`** (IDE-236): only an exact `/next all`, typed by the operator with nothing after it, waives — decided by `assets/consent-mode.sh`, which reads the operator's literal argument text on stdin through a quoted heredoc (`<<'NEXT_ARGS'`) and waives only on the bytes `all` plus at most the heredoc's one newline. The text is never interpolated into a shell line, and a command-line argument to the resolver resolves plain. Every other form asks: free text after `all`, quoting (`'all'`, `"all"`), punctuation (`all,`, `all;`), leading whitespace, and `all` as anything but the sole token — as do *do everything*, *the full run*, `ALL`, `--all`, and a past run. Forbidden: inferring a waiver from other phrasing or from a past run, an agent composing `all` into a `/next` call the operator did not type, and deciding the mode by judgement instead of by the resolver.
*   **`¶INV_NEXT_ALWAYS_A_MOVE`**: a run always names a move. Ending with "nothing to do" is forbidden.
*   **`¶INV_NEXT_ESCALATES_WHAT_IT_CANNOT_ROUTE`**: a state this run can neither act on nor route is marked owed and given a named owner, and, in a plain run, one that makes the proposal unsafe is promoted into the question's framing (an `all` run has no question, so such a state stops it before the step it makes unsafe). Reporting such a state with no owner is forbidden, and so is minting a second asking surface for it — escalation here is a marking on the one question plus, where the state needs deciding rather than answering, rung 2's dispatched `/decide`.
*   **`¶INV_NEXT_INVENTS_NO_STORE`**: it reads only sources that already exist and writes no ledger, no cache and no state of its own. A state that cannot be read without one is **reported as unread** and the reason given. **Exception — the held documentation signals** (NEXTDOCS, operator-ruled: *"record the signal and post it once the channel exists"*). That ruling needs a record, and there is exactly one: `<sessionDir>/NEXT_DOC_SIGNALS.tsv`. It holds the signals with no channel to go to, and **the since-marker sits inside this exception** (director's Q1 ruling). That marker is the per-repository sha of the last applied run, together with that run's utc time. It is what bounds "the commits since the last `/next`", and a new session seeds from the newest one in any session's file. The file is written only by `doc-signals.sh apply`, under a lock, and only after consent. Any second file, or any other use of this one, is still forbidden.
*   **`¶INV_NEXT_DOC_SIGNALS_ROUTE_OR_HOLD`** (NEXTDOCS): every run reads documentation signals from the commits since the last `/next`, its own checkpoint commit included. It never reads the working tree or untracked files. Each signal ends as exactly one of these:
    *   posted through `/inbox-post` to the owning project's 🟦 Documentation channel, at most `--max` per run;
    *   deduplicated against an open comment with the same repo-keyed file and kind, or against a comment a seat holds as `marker-lost`;
    *   held, with a reason (`no-docs-channel`, `owner-unresolved`, `over-cap`, `detected-not-posted`, `post-not-landed`, `marker-lost`, `posting-paused`).

    The rule forbids:
    *   posting by any route other than `/inbox-post`;
    *   posting to the seat's own project because the owner did not resolve;
    *   posting past the cap;
    *   counting a post as landed before `doc-signals.sh landed` reads its key back, reading back a post that created no comment, and posting while any seat under the sessions root holds a `marker-lost` row;
    *   posting redundancy before a re-labelled run shows it is at least 50% true;
    *   resolving an owner from anything but the doc owners;
    *   dropping a signal that has no channel;
    *   typing a channel id or a repository path into this skill;
    *   writing the held file before consent;
    *   any `all` exit whose report omits the `docs:` line.
*   **`¶INV_NEXT_DOC_KINDS`** (NEXTDOCS): the kinds are `undocumented-feature`, `stale-reference`, `redundancy`, `contradiction` and `other`. `doc-signals.sh plan` refuses any other kind with exit 2. The marker line in a posted body, `doc-signal: <kind> <repo-id>:<path>`, is what dedup reads, so changing a kind's spelling makes every open comment of that kind look new.
*   **`¶INV_NEXT_MINTS_NO_LANES`**: it dispatches no workers of its own beyond the resumes the accepted sequence named (in an `all` run, the resumes its printed header named), and keeps no ledger, no partition and no waiting-on graph. This is the falsifier the skill stands on: if it starts conducting, it folds back into `/loom`. **A multi-step run is where this gets tested** — a sequence is not a licence to fan out, and the dispatching inside `/groom` and `/snapshot` is theirs rather than this skill's.
*   **`§INV_RIDE_NEVER_ACTIVATES`**: riding a live session, it activates nothing and moves no phase.
*   **`§INV_OFFER_DONT_FORCE_SKILLS`**: every route is an offer. A route whose state does not hold is skipped silently rather than displayed and declined.
*   **`§INV_LISTS_INSTEAD_OF_TABLES`**: no markdown tables in this file.
