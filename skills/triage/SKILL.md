Read-only triage of a subject: work out what is actually being claimed, gather the evidence that settles it, then report. Investigate and hand back — never edit, never file, and post only when `--post` says to.

# /triage Protocol (The Triage Investigator)

[!!!] **Sessionless and read-only toward the subject.** It **never edits data and never files tickets**; the disposition stays with the caller (`¶INV_INTAKE_DISPATCHES_NEVER_EXECUTES`, `¶INV_TRIAGE_BEFORE_TICKET`).

[!!!] **Posting is an argument, and the default is `--no-post`.** A run publishes nothing unless the caller asks. **In inbox mode the default flips to `--post`**, because an intake signal has a reporter waiting on a thread — and inbox mode is inferred from the subject rather than passed (§ *Inbox mode*), so read that section before you conclude you are silent. When posting is on, the writes this skill is permitted are one comment onto the origin thread plus a one-line pointer onto each ticket that comment names — the pointers on by default, and off only when the caller passes `--no-cross-post`, in which case the roster is still built and returned for the caller to post. Everything governing both lives in **§ Publishing**, and none of it binds a silent run.

[!!!] **What you post is NOT your report** (`¶INV_COMMENT_REPORTS_THE_SUBJECT_NOT_THE_METHOD`). The report is an investigation record written for the next triage pass; the comment is written for **the person who owns the subject**, from `assets/TEMPLATE_TICKET_COMMENT.md`, and the report rides it as an attachment. Detail is welcome — length was never the problem. *Subject* is: above the one-line footer, every sentence is about the thing being triaged, never about how it was investigated.

*   **`--post`** — you are the terminal producer of this finding: dispatched singly by a caller that wants the answer on the record, or run standalone with posting asked for. Post it.
*   **`--no-post` (default)** — you are an *intermediate*, or nobody asked for a comment. **Return the report and post nothing.** Two angle-reports landing on a thread before adjudication show the reporter two possibly-contradictory answers and a third comment resolving them — intermediates presented as conclusions.

**Triage ≠ research.** This is *light*: establish, reproduce, relate — enough to make the subject actionable. Deep root-causing happens later, on a graduated `Needs research` ticket.

> **If the claim you were handed looks wrong, say that instead of answering it.** *"The premise of this question is false, and here is why"* is a more useful result than a careful answer to the wrong question. You are being asked to test a claim, not to assume it.

> **Screenshots and attachments in the context pack are evidence — open them.** With Linear, pass the markdown holding the image reference to **`mcp__linear__extract_images`**. **Never `curl` an `uploads.linear.app` URL**: it returns 401 and always will, because the bare `assetUrl` is a reference rather than a fetchable link. Reporting "I could not see the attachment" after a failed `curl` is a **false negative you caused**, not a limit you found. And read the image against the claim — a capture often fails to show the thing the reporter says it shows, which is a finding worth more than agreeing with them.

> **If you are one angle of a triangulation**, a sibling is investigating the same subject from a different vantage point. **You do not need to do anything to stay independent of it** — it posts nothing and writes to a different file, so there is no output of theirs you could see. Read your prompt, investigate your assigned angle, return. Prior-wave `✅ result` replies remain fine to read: both angles start from the same shared context, and symmetric priors do not compromise independence — seeing each other's *conclusions* would.

## Input — a context pack the caller does not have to predigest

**The input is whatever the caller knows, in whatever shape they have it**: a claim in prose, a ticket key, a Linear comment id or URL, a PR or a commit, local file paths, a log excerpt, a screenshot, a handoff prompt written from a template, or several of those at once. **The caller is not required to normalize it, and you may not require them to** — working out what is actually being claimed, and from which surfaces, is the first half of this skill's job.

So begin by **restating the subject in one sentence**, and say what kind of thing it is: a product defect, a claim about the codebase, a failing test, a piece of tooling, a process. That sentence drives every later choice — which project owns it, whether the run reaches data, which recipe branch applies. Put it at the top of your report. If your restatement and the caller's framing come apart, **investigate your restatement and flag the gap** rather than answering the framing.

**Say what you were NOT given.** A pack that points at a thread and hands you only a body, names a file you cannot find, or cites a number with no source — record each in the Boundary. It means your caller withheld material you needed, and that is a finding about the request.

**In inbox mode the input is an origin comment, and its REPLIES are part of the signal** (`¶INV_REPLIES_ARE_SIGNAL`). Read them. Prior triage results, corrections and the reporter's own follow-ups live there, and they are often the most-processed evidence on the item — a wave once filed a ticket asserting something had never been investigated, four days after a reply on that same thread gave the answer.

## Resolve the subject — infer, confirm, then investigate

**A silent misresolution costs the whole run**: it reads another project's recipe, chases the wrong evidence, and returns a confident answer about the wrong thing. So resolution happens **before** you investigate, out loud, and the operator gets a chance to correct it.

**1 · Infer the owning project.** Derive the `Product:`-prefixed Linear project from the subject itself — the component the claim names, the repo path it touches, the screen it describes, the ticket it cites. Two catalogs help, and neither is authoritative:

*   `../intake/assets/project-schema.json` → `scope.projects` — project names plus handbook slugs.
*   `../inbox-post/assets/INBOX_REGISTRY.md` — per-project handbook rows and channel lists.

**Prefer deriving over trusting either list.** The schema's own `$note` states the authoritative membership test is **live** — a project belongs iff it carries an `Inboxes` milestone — and the pasted list has already been measured stale once, reading five projects for weeks while twelve qualified. The live query is `list_projects(includeMilestones)`, client-filtered on an `Inboxes` milestone. Use a catalog as the fast path, and run the live query when the fast path offers no plausible row.

**2 · Show the guess and let it be corrected.** State the project you resolved in one line, with the evidence that picked it — *"Product: Document Extraction, because the claim is about a page-count field written by the extraction pipeline"* — and give the operator the chance to say otherwise **before you investigate**. A caller who already knows passes `--project <name>`, and this step becomes a one-line confirmation rather than a question. In inbox mode a dispatching wave has usually resolved it already and named it in the handoff; treat that as the answer.

**3 · Read the resolved project's Inbox Handbook.** Resolution does not stop at the catalog row. The handbook's **`## What triage will chase`** section **is the per-project recipe** — it names the tools that actually establish a subject in *this* project (a workflow store for one, a staging database plus product analytics for another, the stored document plus its source PDF for a third) and is deliberately different in every project. **Never reuse another project's.** Fetch it by the slug the catalog carries, via `get_document`.

**4 · When no project owns the subject, say so and run the generic recipe.** A refactor of the tooling itself, a failing test in a repo with no tracked project, a claim about a local script — these have no handbook and no Directions, and that is a normal outcome rather than a degraded one. Record *"no owning project; running the generic recipe"* in the Boundary and carry on. **Do not invent a project to have one**, and do not stretch a plausible-looking row over a subject it does not cover.

## A batch of subjects (`--batch`) — one investigation, per-subject rows back

**Without `--batch` you hold one subject and this section is not for you.** Nothing below changes an ordinary run.

`--batch` means your caller handed you **several subjects at once** and wants them established in one pass — typically a wave of sibling drops on one intake channel. It is passed, never inferred here: `/triangulate` § *1b* counts the threads a finding would be posted to, and you cannot see them from a handoff path.

*   **Restate every subject, not the batch.** One line each. A single restatement reading *"eight reports of X"* has merged them before you looked, and merging them is the caller's hypothesis rather than your finding.
*   **Do not assume they share a cause — you are being asked WHETHER they do.** Say which subjects your evidence groups together, which it separates, and which it cannot place. **A group of one is a normal answer**, and so is one group per subject.
*   **Carry each subject's OWN numbers.** Your report's `## Per-subject` section takes one row per subject: its ids, its own counts, its dates, its sender, what its own evidence showed, and which group you put it in. **Class-level facts do not substitute.** Your caller writes a separate comment to each subject's reporter out of these rows, and a row that would be equally true of every sibling gives that reporter nothing — measured on a batch whose adjudicated finding was entirely class-level, leaving the per-subject specifics to be re-fetched from the original signal bodies afterwards.
*   **A subject you could not reach still gets a row**, saying so and what would settle it. A silently dropped subject is a reporter who gets nothing.
*   **One report file, named for the BATCH** — `builds/triage-<batch-id>[-<angle>].md`. The investigation happened once, so it has one record.
*   **Under `--adjudicate --batch`** your ruling carries the groupings: every subject in at least one, a subject nobody could place in one of its own marked unplaced, and a subject whose evidence spans classes in each of them by facet rather than forced whole into the largest.

## Primed with a known-signal recipe (`--primed`)

**Every dispatch carries this flag, and it has two values.** `--primed <path>` hands you the project's known-signal recipe — a forensic checklist, a registry of known root causes with the signature that recognises each — and `--primed none` says you were handed none. **Like `--batch`, it is passed rather than inferred here**: `/triangulate` §1 resolves it from the owning project and primes at most one angle of a pair, which you cannot see from a handoff path. A standalone caller holding a recipe passes the path itself; a standalone caller holding none passes nothing and reads as `--primed none`.

**Fill `**Primed with**` from the flag, verbatim** — the recipe or `not primed` — and **on a primed run fill `## Ruled out`**: one row per class you considered and rejected, naming the signal that excluded it. *"Matched class 7"* on its own is an oracle nobody can argue with; the exclusions are the surface your partner angle and the adjudicator can attack, which is the whole reason you were primed rather than left open (`/triangulate` §2c). A class you could not test gets a row saying so and what would settle it. **On `--primed none` cut `## Ruled out` entirely** — that is compliance with the template, not a deviation from it.

## Inbox mode — inferred from the subject, overridable in both directions

**Inbox mode turns itself on. It is not a flag anyone has to remember**, because a flag an agent must remember is weaker than a rule that fires on its own (`¶INV_INDEPENDENCE_BY_CONSTRUCTION`, same reasoning).

**What turns it on**: the subject you were handed is an **intake drop** — a **Linear comment** (an id, a `#comment-` URL, or a comment body the pack names as the thing to triage), or a **Linear inbox channel ticket** (a ticket that *is* one of an intake project's channels: its project carries an `Inboxes` milestone and its description is a channel scope plus `## Directions`). Either one means a reporter is waiting under a thread, which is the only thing the intake behaviours exist for. Infer it from the pack yourself; no caller has to pass anything.

**What does NOT turn it on: an ordinary work ticket.** A bug, a feature, a build thread's own ticket — a ticket someone is *working*, rather than a channel someone drops into — leaves inbox mode off. Posting there writes a triage comment onto a record whose updates belong to whoever owns the work, and `/loom` validates a thread's ticket through `/triangulate` for exactly this reason: the finding goes back to the conductor and `/snapshot` owns what reaches Linear. **When you cannot tell which kind of ticket you are holding, treat it as ordinary work and say so in the Boundary** — guessing wrong toward plain costs the caller a post it can still make; guessing wrong toward inbox puts your comment on someone else's ticket, which it cannot unmake.

**Two explicit overrides, and an explicit flag always beats the inference:**

*   **`--mode inbox`** — force it on where the inference had nothing to fire on: a drop pasted in as a bare body, a screenshot with no comment id, a URL the pack never marks as the subject.
*   **`--mode plain`** — force it off. This is the *"yes it is a Linear ticket, and no it is not an intake drop"* escape, and it is the flag to reach for **whenever a wrapper owns publishing**: a thread validating its own ticket, a duplicate sweep, a refactor check. Say it out loud rather than relying on the ticket-kind test to come out your way.
*   **`--post` / `--no-post` stay independent of both.** Inbox mode moves the posting *default*; an explicit posting flag moves the behaviour and outranks the default whichever way the mode landed.

**Say which mode you are in, in one line at the top of your report** — `inbox mode: on (inferred: origin comment id)` / `off (--mode plain)` / `off (ordinary work ticket)`. An inference nobody can see is an inference nobody can correct, and correcting it is a re-run rather than an argument.

Everything above and below still applies. Inbox mode adds the intake pipeline's behaviours, and a run that is not in it gets none of them:

*   **Posting defaults to ON.** See § Publishing.
*   **Read all three surfaces, not just the channel's.** An intake project's context is split across: the **Project description** (project-wide — `## Directions`, `## Stakeholders`), each **inbox channel ticket's description** (that channel's one-line scope + its `## Directions`), and the project's **Inbox Handbook** document (`¶INV_CHANNEL_MACHINERY_IN_ONE_DOC` — the shared machinery: report template, what-happens-next, how a comment becomes a ticket, the `## Ticketing Strategy`, plus that project's own `## What triage will chase`, which names the tools that actually establish a subject here and is deliberately different in every project — never reuse another project's). When dispatched by a wave, all of it arrives in the handoff prompt — treat it as complete and do **not** go re-read the project. Running standalone with only a comment id, read all three yourself; reading only the channel silently drops both the project-level steer and the recipe.
*   **Channels are deliberately thin now.** If a channel description looks sparse, that is correct — the machinery was hoisted to the handbook so one edit updates every channel. Do not treat a thin channel as a missing spec, and do not reconstruct the handbook from a channel.
*   **Directions outrank the recipe** (`¶INV_DIRECTIONS_IN_DESCRIPTIONS`). They say what this project is chasing right now, what counts as enough evidence here, and what to skip. Precedence: channel > project > the recipe below. When the Directions and the generic recipe disagree, follow the Directions and record which line you followed. When the Directions ask for something you could not get, say so explicitly in the Boundary rather than silently substituting the default. No Directions present → the recipe below is the default, unchanged.
*   **Ticketing Strategy bounds your recommendation** (`¶INV_TICKETING_STRATEGY_IN_HANDBOOK`). It lives in the project's **Inbox Handbook**; on a project predating the move it may still sit on the Project description, so fall back there. It arrives in its **own** block, separate from Directions — a different question: Directions steer what's worth *chasing*, this steers what's worth becoming *its own ticket* (Volume · Size · Substance). Your "ripe to graduate → which milestone" recommendation is a graduation-volume call, so weigh it against these bullets: when an item is well-formed but reads as a facet of something already tracked, recommend **fold into &lt;parent issue key&gt;** rather than a new ticket, and say which bullet drove that. "Not its own ticket" never means discard — it means fold or keep marinating. If the block is missing from your prompt, say so in the Boundary rather than assuming maximum ticketing.
*   **Stakeholders tell you who to ask** (optional; absent is normal). Facts about people, never authority — when a gap cannot be closed from the read-only sources, name the person who could close it in your **Boundary** rather than guessing or silently degrading to a weaker finding. Do **not** contact them yourself; you are read-only and report-only, and the orchestrator owns every outward message.
*   **The Steering read feeds a Decision Board.** See § Output.

Outside inbox mode these sources usually do not exist. Their absence is normal, gets one clause in the Boundary, and is never treated as a blocked run.

## Credential preflight — judge whether this run reaches data, and lean yes

**Ask one question before you plan anything: is this investigation going to touch a database, an MCP server, a signed-in application, or a cloud credential?** Most of the time the answer is yes — establishing a subject usually means reading something you need a key for. **When the answer is yes, or you are unsure, run the preflight and treat a non-zero exit as a STOP:**

```
engine env doctor --tier triage
```

Fix what it names and re-run; do not begin investigating. `--tier triage` evaluates only the rows a triage run needs, at the severity declared for triage — so a missing Slack token or an unauthenticated Notion MCP will not stop you, and a missing app login or read-only database credential will. `--domain` defaults to `intake`; a run in another credential domain names its own. Under a wave that already gated at its Phase 0, running it again costs a second and proves it for the run that is actually about to happen.

**Skip it only when you can say, in one clause, what this run will read instead** — the working tree, a local file the caller handed you, a public page — and record that clause in the Boundary. **A wrongly-skipped preflight surfaces as a capability that appears not to exist**, halfway in, after the plan is already built on it.

**Say the KEY, never a capability.** `¶INV_UNAVAILABLE_IS_A_CLAIM` forbids concluding a *capability* is gone from a diagnostic signal — a WARN on `AWS_PROFILE` once became *"no database"*, and the tunnel opened in twenty seconds. This gate asserts something different in kind: a named credential is absent, checked directly. So report *"`FINCH_AGENT_APP_PASSWORD` did not resolve — run `engine env setup --domain intake`"*, never *"the UI angle is unavailable"*. The first is a fact you verified; the second is an inference this protocol does not let you draw.

**Resolve secrets through the resolver, never a literal**: `engine env resolve <KEY> --show-value`. You never type or paste a credential, and one that does not resolve means an unprovisioned environment — say so plainly rather than asking anyone to send you one. The KEY NAMES come from the project's access directive below; the mechanism is the engine's.

**A `SEAM-INFLUENCED` run is not a verification.** Test seams (`ENV_MANIFEST`, `ENV_MCP_LIST_OUTPUT`, `ENV_STS_ARN`, …) were set, so the green says nothing about the real setup — re-run with them unset.

## Reaching the subject — resolve this after the preflight

This skill names **no product**. Everything concrete — which hosts to open, how to sign in, how to reach a read-only database, which URL patterns build a deep link, which quirks will mislead you — comes from the project, in this order:

1.  **The project's triage-access directive** — **`.directives/INBOX_TRIAGE_ACCESS.md` at the repo root. READ IT BY PATH, as your first act, before you plan anything.** It is the authority on hosts, credentials, data access and app-driving mechanics. Finch's is the worked example.
    ⚠️ **`engine discover-directives` will NOT return it** — that command walks a fixed list of filenames and this is not one of them. Nothing auto-loads this file. **Reading it is your job, by name, and it is the reason this step exists.**
    **An absent access directive and an unread one look identical from the inside**, and the failure surfaces much later wearing a disguise: a capability that appears not to exist, or a plausible route that turns out to be the fallback. One run reached for a public database instance gated by an IP allowlist — whose failure mode is a silent timeout with no permission error — while holding the tunnel grant that needed no allowlist at all. It produced a confident, well-argued diagnosis of the wrong thing. **`cat` the path. If it is genuinely absent, say so in the Boundary rather than improvising a route.**
2.  **The Inbox Handbook's `## What triage will chase`** — the per-project recipe you resolved above, which names the tools that establish a subject *in this project* and may override the app base.
3.  **The context pack**, when a caller already resolved a shared endpoint and named it.

**Absent all three, degrade rather than guess.** Work from whatever is reachable — the working tree, the tracker, the artifact you were handed — and say plainly in the Boundary that the project publishes no access directive; that absence is a finding about the project, not a failure of the run. Never invent a hostname, a role name or a URL pattern.

## The recipe (do what's reachable; degrade gracefully when a source is missing)

**Branch by claim shape first.** A single failure that needs a *cause* → start from the most detailed per-incident record: the workflow history, the specific failed row, the failing test's own output. A recurring "keeps happening" claim that needs the *pattern* → start from an aggregate (count the failures for rate, onset and breadth), then drill into whichever individual incidents are still recoverable — the aggregate is what reveals that a "recurring" report is often several different failures, not one bug. A claim about what the code *does* → start from the shipped source and the history that produced it, never from a description of it.

1.  **Establish** — pin the concrete subject. Where it is a product defect, that means **which account/org** and **which record** plus its **page URL**, matched on the names, identifiers and dates visible in the capture; the access directive names the instruments — typically a read-only database for turning a capture into ids, and an in-app selector for when you have a name but no id. Where the subject is code, tooling or a process, it means the **exact file, symbol, commit or command** the claim is about, cited as `path:line`. Note every secondary identifier you find; it is what makes the next lookup a substitution rather than a re-derivation.
2.  **Product analytics** (if the claim is sourced from them — a session link or an event): pull the session plus the surrounding events for what the user actually did and saw.
3.  **Reproduce** — attempt a repro from the established state; record steps + frequency (always / intermittent / couldn't). For data issues (e.g. "extraction failed 5×"), confirm the current stored state rather than a live UI repro. For a code or tooling claim, **run the thing** — the test, the command, the script — rather than reasoning about what it would do.

    **Where the project provisions an agent account, you can open the customer's screens yourself, as yourself.** Triage used to stop at a link for someone else to click. Seeing the screen is often the finding, because a capture frequently fails to show the thing the reporter says it shows. **The mechanics are the access directive's** — credentials from the resolver rather than a literal, the sign-in traps, the wait conditions, how to point a session at an account, which navigation quirks produce a confidently-wrong capture, and where captures may be written. Read it before driving anything; every rule in it was earned on a run that went wrong without it.

    Two rules hold regardless of subject, because both are about what your run leaves behind:

    *   **Captures never land in the repo.** A full-page screenshot of a customer's data, and an `innerText` dump of the same, are the same disclosure in two forms — and the second one greps. Write them to a temp directory, cite the path in the report, and attach anything that must persist to the ticket, which is access-controlled in a way a repository is not.
    *   **Every script this run writes is TypeScript. Never Python.** That covers the repro, an ad-hoc aggregation, a one-off parser — anything executable you leave behind or run to reach a finding. Write `.ts` and run it with `npx tsx <path>`.
        **Why, so the rule survives contact with a moment where Python looks easier** (and it will — it usually is, for the first ten minutes): the subject of a triage here is a **TypeScript monorepo**, so a `.ts` script imports the project's own Drizzle schema, its clients and its env loading, and inherits the types that make a wrong column a compile error rather than a wrong answer. A Python script re-implements all of that against a hand-written idea of the schema, and **a repro that quietly drifts from the schema is worse than no repro** — it runs, it prints something, and the number is stale. Two further costs land on other people: the repo has **no Python toolchain**, so whoever inherits your repro cannot run it without setting one up; and a Python script needs its own connection and credential handling, which is a new place for a `data_ro` URL to end up in plaintext. Neither cost is visible to you at the moment you choose. **Where the subject genuinely lives in another language, write the repro in that subject's own language** and say which — the rule forbids reaching for a second toolchain the project does not have, not the project's own.
        **If you catch yourself reaching for Python because the TypeScript setup is friction, that friction is the finding** — say so in the Boundary. It means the repo makes its own data hard to query, which is worth more to the reader than the script was.
    *   **Attach the script you wrote; do NOT turn it into a test.** If you drove the app or ran a probe to reproduce something, save it to `builds/triage-<subject-id>[-<angle>]-repro.ts` and hand that path back — it is the cheapest possible handoff, because whoever takes the fix inherits a working reproduction instead of rebuilding one from your prose.
        **It uploads as its OWN attachment — it does NOT go inside the dossier.** The one-card rule (`§INV_CHANNEL_EVIDENCE_RIDES_THE_COMMENT`) governs **prose** evidence, where four attachments compete for one reader's attention. A script is not prose: it is picked up by a *different person for a different purpose*, and whoever takes the fix runs it. Fenced inside a 30 KB markdown dossier it has to be found, extracted, un-fenced and re-named before it can run, which destroys the exact property being claimed for it. **Under `--no-post` you upload nothing** — return the path; the caller uploads it (`§INV_TERMINAL_PRODUCER_POSTS`). But leave it as a repro. **A repro and a regression test answer different questions**: a repro asks *does this happen*, a test asks *does this still not happen*, and the second can only be written once the fix is known, which triage deliberately does not determine. A repro also hard-codes the real account and record it was about — committed as a test, that puts customer identifiers in the repo and breaks the moment that data legitimately changes. Say in the report that the script is a repro and what a test would need; that is the useful sentence, not a half-made test.

4.  **Relate** — search existing issues (a `list_issues`-style query on the account / symptom / component) for duplicates or the same root cause, **then OPEN each promising candidate through `§CMD_READ_RELATED_TICKET`** (the full issue + its comments + its state), never a bare issue fetch and never the search stub alone. A search call returns issue stubs and never a thread, so a Relate that stops there has read no prior triage, no retraction, no design constraint — the very things this step exists to find (see the bold note below, and `§INV_POINT_IN_TIME_CHECKS_EXPIRE` for why the read must be fresh at the moment you use it). List candidate issue keys with why-related, and say for each whether you opened it or only saw the stub. **When the reporter is a repeat filer in this channel, run Relate *first*** — search their own recent drops before investigating, so you don't re-derive facts they already wrote down 48 hours ago.

    **A ticket you are going to NAME in your output is by definition promising — open it.** There is no tier below "promising" for a ticket you cite; a list assembled for the `## Related` section and never read is this step failing while looking exactly like it worked. **Measured**: a run rediscovered a finding that had been sitting on one of the tickets it went on to cite — same mechanism, same code sites, same symptom refutation — posted three weeks earlier by an earlier two-agent investigation. The run named that ticket and never read what was on it. Two investigations of one defect, three weeks apart, that never met, and the second paid full price for what the first had already established.

    🔴 **Relate lands BEFORE you draft the verdict, not merely before you post it.** The ordering is not politeness toward the record — it is what stops you writing a conclusion you will have to withdraw. Where a project has an active prior wave, the existing tickets **and their comment threads** *are* the literature review: a retraction comment can reframe a numeric picture you would otherwise spend an hour deriving, and a design comment can invert the operational advice your own evidence appears to support.

    **Measured twice in one wave.** One run found a wide, populated, unread table and reached for the obvious *"switch the read on"* — then found, in a comment on the ticket that owned the cutover, that column grain runs against the fact layer, so flipping it that day would lose more than it revealed. **Same evidence, opposite advice**; the only difference was whether Relate had landed first. A second run in the same wave reported that two of its own conclusions did not survive its sweep, and said so unprompted.

    **If you catch yourself drafting while the sweep is still open, stop.** The draft will anchor you, and this is the cheapest step in the protocol.

## Triage craft

The recipe is the steps; this is the judgment that makes them land. Every rule here was earned on a real run and applies to **every** subject — the per-project handbook names the tools, this names the habits.

*   **Find the join key first.** Before crossing surfaces (screenshot → database → workflow store → tickets, or claim → source → commit → ticket), find the one id that unifies them and confirm it *is* the same id across each. A single value often wears several names in different places; pin it once and every later lookup is a substitution, not a re-derivation.
*   **Route, don't chase.** A subject often belongs to a different project than the one it landed in — a mis-read field belongs to the extraction team, not the app team; a classification miss belongs to the pipeline, not the screen. Naming the right home *is* triage; route it rather than triaging the wrong subject deep.
*   **Is it the failure you think it is?** Several failures look identical from the outside and need opposite fixes: a bad extraction vs an auto-apply clobbering a human-edited field; a genuine crash vs a product limit tripping a guard; a deterministic failure vs one that recovers on retry; a broken implementation vs a stale expectation in the test asserting it. Name which one before you write it up.
*   **Check your evidence's shelf life before you promise a cause.** Every source ages out — a workflow store's retention, an audit table's window, a CI log's expiry. Learn the window before you rely on it; if the evidence is already gone, say so in the Boundary rather than reconstructing the past from what the record reads *today* (it may have been revised since).
*   **A negative result is only as strong as the search behind it.** Before reporting that something is absent — no such ticket, no such row, no such caller, no such owner — say *what you searched*, not just what you didn't find. One id lookup that misses is not proof of absence; an enumeration under a transposed name has overturned "it doesn't exist" more than once. **This applies with full force to "not reproducible".** One run declared a prior measurement's predicate unrecoverable after a sixteen-query sweep; the predicate was documented in full in a comment on a ticket those sixteen queries never reached, and the claim was overturned on review. *"I could not find it"* and *"it does not exist"* are different sentences, and only the first is ever yours to write — **a negative with no stated search is a false negative waiting to be quoted.**
*   **Pin the provenance.** Record the model id / pipeline version / commit behind the thing you're judging. Provenance that doesn't pin it blends generations, and a later change then reads as a mystery regression instead of expected drift.
*   **Leave a friction note for the recipe.** At the end of a run, jot where the recipe helped and where it misled — the table that didn't hold the error, the step that was a dead end, the ordering wrong for this claim's shape. That note is the raw material `/inbox-handbook capture` turns into a Keep/Add/Cut recipe delta; without it the lesson decays into anecdote.

## Output

0.  **Reproduce links (REQUIRED)** — every entity established renders as something the reader can **one-click to reproduce**: a deep app URL where the subject has one, a `path:line` or a commit SHA where it does not. These appear in BOTH the report (a "Links (reproduce)" section) AND any comment. Record every entity id so the links can be built. **The app base and the URL patterns come from the project's access directive**, and the Inbox Handbook may override the base for a project that runs somewhere else — some projects have no separate production. Prefer the most-specific deep link (the exact tab, document or sub-view the finding is about), never just the record root.
1.  **Triage report** → `builds/triage-<subject-id>[-<angle>].md` — the angle suffix only when you are one angle of a triangulation, so two parallel runs never collide — following `assets/TEMPLATE_TRIAGE_REPORT.md` **exactly**: Verdict box · Entities (ids + links) · Signal · Findings — each tagged `[confirmed]` / `[inferred]` / `[needs-source]` · **`## Ruled out`** on a `--primed <path>` run only, cut entirely under `--primed none` (one row per class of the project's known-signal recipe you rejected, naming the signal that excluded it — a classification with no exclusions is an oracle nobody can attack; § *Primed with a known-signal recipe*) · **Queries verbatim** (the exact read-only queries and commands + key results — reproducible, never prose descriptions) · **`## Per-subject`** on a `--batch` run only (one row per subject, its own ids and numbers — what the caller's per-subject comments are written from) · Scope · Related · Recommendation & **Boundary** (what triage could NOT determine → research) · **Steering read** (process-steering, NOT solutions — `¶INV_STEERING_NOT_SOLUTIONS`: a legitimacy/confidence read + still-open questions + concrete what-to-measure-next + 3–5 suggested board options `{key,label}`, all oriented by the project's Directions where it publishes any; the caller polishes the options into a Decision Board's steering widgets — options to react to, never a manufactured answer). Record the **data source + timestamp** (a live primary vs a nightly replica — data moves, and which one you read changes what a number means). In the report, ticket keys render via `§FMT_TICKET_LINK` and any reference to a **specific comment** (the origin signal, a related/duplicate comment) via `§FMT_TICKET_COMMENT_LINK` deep-links — never a bare comment id.
2.  **1-line headline** — the finding in one line, for the caller to relay.
3.  **The repro script's path, if you wrote one** — named separately in what you return, never only mentioned in prose. A path buried in a paragraph is a path the caller does not upload.

**`<subject-id>`** = the stable id of what's being triaged — the **origin comment id** for a comment signal, the **issue key** for a ticket or sub-issue, and otherwise a short stable slug the caller can predict (a test name, a command, a component). Use it verbatim in the filename so concurrent triages never collide. **On a `--batch` run it is the batch's id, not any member's** — one investigation, one report, one filename; a file named for one member reads as that member's report and is not.

This skill produces the **report** only. Where a caller wrote a handoff prompt to dispatch you (`builds/triage-handoff-<subject-id>[-<angle>].md`), that prompt is **its** artifact — your *input*, not your output. A caller that publishes bundles **both** (report + handoff) into the single dossier it links from the comment, so the full chain (question → answer) is reproducible without the comment body having to narrate it.

**Return the report path + recommendation + headline + the mode you ran in** (`inbox` or `plain`, and what fired it where it was inferred) — plus the posted comment URL when `--post` was on, **and one row per cross-posted pointer** (`{ticket, commentUrl, suppressedBy?}`, `¶INV_EVERY_NAMED_TICKET_GETS_A_POINTER`) — the roster you built before posting, so a caller can count its rows against the tickets the comment names without reading a word of the finding. Under `--no-cross-post` the roster is returned unchanged with every `commentUrl` null and `suppressedBy` naming the flag. **The mode rides the return value because it was inferred**: a caller that expected the other one finds out from the answer rather than from a comment landing where it should not have.

## Publishing (`--post`)

**Nothing in this section binds a `--no-post` run.** A silent run finishes when it returns its report path; there is no unpublished-work failure to account for, because no publication was asked for.

**When `--post` IS on, the accounting is what makes it real.** One wave produced three complete investigations that were written, never posted, and found days later — because posting was a trailing bullet with nothing checking it. **The fix is that whoever posts must return the resolvable comment URL, and the caller's accounting cannot complete without it** (`triageAccounting`). Moving the write around does not help; making it verifiable does. So on a posting run: **post to the origin thread first, then return**, and the return value carries the URL.

**What you post is a comment written from `assets/TEMPLATE_TICKET_COMMENT.md` — not the report.** Write the report to `builds/` first, then *project its findings* into the comment shape: what's wrong · what the reporter got right and wrong · where (ids + deep links) · the evidence · how widespread · is it still happening · what to do · not established · a one-line `<sub>` footer. Then **upload the report and link it once** as a clickable `[📄 filename](assetUrl)` (`§INV_CHANNEL_EVIDENCE_RIDES_THE_COMMENT`) — naming a file in prose is not linking it, and the link must stand **alone in its own block, nothing after it on that line**, or the tracker renders it as plain text instead of a preview card. **A `builds/…` repo path is prose naming a file**, wherever it sits and however it is punctuated — in the body, or in the `<sub>` footer — because a teammate without repo access cannot open one. Upload the bytes through `prepare_attachment_upload` and link what comes back.

**Sections of your report that must NOT survive into the comment**: the `**Angle**:` header · the whole `Steering read` (it is written for a Decision Board — `¶INV_STEERING_NOT_SOLUTIONS`) · the `[confirmed]`/`[inferred]`/`[needs-source]` basis tags (in a comment the cited source *is* the basis) · `Queries (verbatim)` (they live in the attached report) · and any framing of `Boundary` as a limit of *the investigation* — rewrite each open item as a property of **the subject**, with the cheapest thing that would settle it.

### Cross-post a pointer to every ticket the comment names

**Every ticket your published comment names gets a one-line pointer posted on it. Every one, unconditionally.**

**The cross-post is ON by default, and `--no-cross-post` is the only thing that turns it off** — a caller whose phase forbids writes onto other people's tickets, or a wrapper that publishes its own updates, exactly as `--mode plain` exists for a caller that owns publishing. **Even then, build the roster and return it whole** with every URL empty and `suppressedBy: "--no-cross-post"` on each row, so the caller who took the decision inherits a countable list of what it now owns. Say `cross-post: off` in one line rather than letting the absence speak.

**Build the roster before the first post**, from the comment body itself: every ticket key that appears above the `<sub>` footer, minus the thread you are posting on. Post one pointer per row, and return the row's comment URL beside the finding's own (`¶INV_TERMINAL_PRODUCER_POSTS` — an unposted pointer is invisible in exactly the way an unposted finding is).

> ### 🔴 The unconditional part is the rule. Do not refine it into "post where it matters."
>
> The tempting refinement is to cross-post only where the finding **changes** the target ticket — and that refinement is precisely what failed. It requires someone to judge whether a mention matters, in the moment they are finished and want to be done, and **the judgement is the failure mode**.
>
> **Measured**: a run named five tickets in its published comment. One learned about it, because the operator noticed and asked. The other four were never told — including one whose stated count the finding had just corrected, and one whose acceptance signal the finding had just shown to be hazardous. A change-based rule would have scored that second one as borderline, because it was flagged only as a hazard, and it was the ticket that mattered most.
>
> Post to every ticket the comment names instead, and let the pointer's own content rule say whether there is anything to say.
>
> **`--no-cross-post` is not that refinement, and does not reopen it.** The refinement asks the **run**, at the end of its work, to judge **per ticket** whether a mention mattered. The flag is the **caller**, **once**, **before** anything runs, over the **whole roster**. **Unconditional still binds inside the roster**: flag absent, every named ticket is posted to and none is skipped for reading borderline; flag present, none is, and the roster comes back for the caller to post. A run that posts to some of its roster has invented a middle that does not exist.

**What a pointer is**: one or two sentences — what routed here, from where, and anything the finding corrects about *this* ticket — plus a link back to the origin thread where the workings live. **It is not the finding, not the dossier, and not a copy of the published comment**; those live on the origin thread and travel by link. The shape is in `assets/TEMPLATE_TICKET_COMMENT.md` § *The pointer*.

**What it must not become**: a stub on a busy ticket, which teaches people to skip the comments there. **So it says something, or it says what changed.** A pointer whose whole content is *"you were mentioned"* is noise — the tracker already renders the mention — and where the finding genuinely touches nothing on the target, the pointer says what the target is now relied on for, which is the fact the reader needs.

If you are one angle of a triangulation you are `--no-post` and none of this applies to you — return your report and let the wrapper publish.

## Data access (read-only)

**Prefer the path that guarantees read-only by GRANT, not by a flag.** A role with no write grant cannot be talked out of it; a session setting can be flipped, by you or by anything that shares your connection.

The concrete path — the host, the role, the secret, the tunnel and its gotchas — is the **project's access directive**. What binds regardless of project:

*   **Never connect as a read-write role.** If ever forced to, set the session read-only *and* open an explicitly read-only transaction — but treat that as a guardrail, not a guarantee.
*   **When a caller has already opened the shared connection**, use the endpoint the context pack names; do not open your own. A second tunnel usually fails to bind and costs the whole wave the port.
*   **Record the source and the timestamp on every number you report.** A live primary and a nightly replica disagree, and a reader cannot tell which you read unless you say.

## Constraints
*   **¶INV_COMMENT_REPORTS_THE_SUBJECT_NOT_THE_METHOD**: A comment posted to a ticket is addressed to **the person who owns the subject**, and reports the subject. The investigation record is a *different artifact for a different reader* — it is attached, never pasted. Method-talk gets one `<sub>` line at the bottom naming the method, the provenance and the date; above that line, every sentence's subject is the thing being triaged. **Detail is not the enemy** — a long, dense, evidence-heavy comment is often the right one; a comment that spends its length on how the answer was reached is not. **Shared with `/triangulate` via `TEMPLATE_TICKET_COMMENT.md`, deliberately** — a rule that binds only one entry point is undone by running the other. **Reason, measured**: a triangulated run on [FIN-3940](https://linear.app/finchclaims/issue/FIN-3940) published a comment roughly half of which was about the investigation — which sub-run checked which commit, whether their agreement was genuine, a critique of the orchestrator's own briefing, and that briefing attached for audit. The findings under it were correct and well-evidenced; the reader was a product owner who wanted to know whether a money column was still wrong. **The protocol had required it**, so the fix is here in the protocol rather than in anyone's discipline. Practical test: read your draft as someone who has never heard of these skills. If a paragraph teaches them about triage instead of about the subject, it belongs in the report.
*   **¶INV_EVERY_NAMED_TICKET_GETS_A_POINTER**: A published finding that names another ticket posts a **one-line pointer** on that ticket — **every ticket named, unconditionally**, with no test for whether the mention matters. The roster is built from the comment body before the first post, and each pointer's URL is returned beside the finding's own. **A pointer is one or two sentences** — what routed here, from where, what the finding corrects about *this* ticket — plus a link back to the origin thread; it is never the finding, the dossier or a copy of the comment, which stay on the origin thread and travel by link. **It must still say something, or say what changed**: a bare *"you were mentioned"* is noise the tracker already renders, and a stub on a busy ticket teaches people to skip its comments. **Shared with `/triangulate` via `TEMPLATE_TICKET_COMMENT.md`, deliberately** — a rule binding only one entry point is undone by running the other. **Reason, measured, and it is why the unconditional half is load-bearing**: a run named five tickets in one published comment and only one of them learned about it, because the operator noticed and asked; among the four that were never told were a ticket whose stated count the finding had just corrected and a ticket whose acceptance signal the finding had just shown to be hazardous — which a change-based rule would have scored as borderline, since it was flagged only as a hazard. **The cost was already paid before the rule existed**: the same run rediscovered a finding that had sat for three weeks on one of the tickets it cited — same mechanism, same code sites, same symptom refutation, posted by an earlier two-agent investigation — having named that ticket without ever reading it. **The judgement is the failure mode; removing it is the point.** **The cross-post is ON by default and only `--no-cross-post` turns it off** — the caller's decision, taken once before the run, over the whole roster, for a phase that forbids writes onto other people's tickets; never the run deciding per ticket at the end, which is the judgement that failed. Off still builds the roster and returns it whole with each row's URL empty and the suppression named, so what was switched off stays countable.
*   **Read-only, everywhere.** Database access is via a role that is SELECT-only *by grant*. Never mutate data. Never create/edit/close tickets. Never call the tracker's save-comment/save-issue tools — *except* the permitted comments when running `--post`: the one finding on the origin thread, and one pointer per ticket that comment names (`¶INV_EVERY_NAMED_TICKET_GETS_A_POINTER`).
*   **Evidence over assertion.** Every claim you establish cites the record, query, command or `path:line` that supports it.
*   **Bounded.** This is triage, not a deep dive — if closing a gap needs real research, say so in the recommendation (→ `Needs research`) rather than doing it here.
